# 调研：微信语音「边有歌声、边能说话」（2026-10-13）

> 触发：用户问「想在微信上边有歌声、边能说话，像视频一样的，可以吗？做的不能冲突」。
> 方法：外部调研（6 问，含来源）+ 仓内现状对账（只读）。**本文是快照**：结论只代表这一天，
> 引用外部链接均为调研时可见；「未找到权威来源」的条目如实标注，未编造。
> 相关既有文档：`docs/微信语音-长文分段发送方案.md`（60s 预算）、`docs/特效声板设计.md`（混音语义）。

---

## 一、一句话结论

**可以，而且主路线已经躺在仓库里了**：微信语音消息本身就能承载「人声说话 + 歌声/BGM 垫底」——
没有内容类型限制，录到什么发什么；真正的约束只有两条：**单条 60 秒上限**（已在分段发送方案里解决）
和 **16kHz 人声优化编码会把音乐高频截掉**（听感发闷，只能靠混音策略缓解）。
「像视频一样」若指**一条消息里同时有歌有话**，语音消息就是正解；若指**视频画面**，那走发视频文件，
与本应用的语音链路是两回事。

「不能冲突」经对账确认：**不需要动 `wechat_voice.py` 的任何发送自动化**——歌声混进人声
发生在合成侧（发送之前），发送链路拿到的只是一条普通 wav。与声板/预混的关系是**同一段 DSP 的延伸**，
不产生新的锁竞争。

### Q1 微信语音消息的技术规格

- **单条最长 60 秒**，手机端与 PC 端一致（PC 端教程明确「与手机端一致，最多 60s」）。
- 编码 **SILK v3**（腾讯在标准 SILK 头前加 1 字节 `0x02`；旧版/部分场景 AMR）。文件后缀
  可能是 `.amr/.silk/.aud`，但实为 SILK。
- **采样率 16kHz**（宽带，按「纯人声场景」设计）；SILK 码率范围 6~40 kbps（微信确切码率
  官方未公布——无权威来源）。
- PC 端交互：微信 **4.1.9 for Windows（2026-04-21）**首次支持发送语音消息；按住式
  （语音按钮/按住 Alt → 录音 → 松开发送）。与仓内实现一致（`wechat_voice.py` 走话筒点击/Alt，
  已在真机跑通）。

### Q2 语音消息能否包含音乐/唱歌，有无风控

- **未找到任何官方规定说语音消息只能是说话声**。技术上「录到什么发什么」，带 BGM 的语音
  能正常发送、正常播放。大量生活攻略公开教人「放伴奏录语音唱歌」——行为普遍性本身就是
  未被拦截的旁证。
- **真正的约束是音质**：语音链路按人声设计（16kHz 采样 + 人声优化编码）。约 8kHz 以上的
  音乐频谱被截掉、低码率下连续音乐信号损耗大——发出去的是「闷/糊的 BGM」，而不是发送失败。
- **风控**：未找到「发带 BGM/唱歌语音被限制」的实锤案例或官方说明。腾讯云的「语音消息审核」
  文档是企业业务方的涉政涉诈类目拦截，与个人聊天语音无关。⚠️ 2026-07 有单源报道称语音
  **通话**中播放 TTY 机械音触发了实时违规警告（说明微信有通话音频检测能力），但语音**消息**
  是否做同类审核无权威来源。

## 三、仓内现状对账（结论：基本零冲突，主路线已有 80%）

### 3.1 「歌声+人声」在哪一层发生：合成侧，不是发送侧

现有发送链路（`m2_server/wechat_voice.py`）对音频内容**完全无感知**——它只负责
「切卡 → 播 wav → 微信录音 → 校验 → 还原」。歌声与说话声**混成一条 wav** 之后，
对发送链路来说就是一条普通音频。所以：

> **`wechat_voice.py` 一行都不用改。** 「边唱边说」是合成侧功能，发送侧天然兼容。

### 3.2 混音 DSP 已经存在：`sfx_lib.mix_into`

`m2_server/sfx_lib.py:285` 的 `mix_into(voice, sr, inserts)` 已经实现了全部所需语义：

| 需求 | `mix_into` 现有能力 | 缺口 |
|---|---|---|
| 歌声垫在人声下面 | `mode=layer`：`at_s` 秒处叠加，`gain` 控制音量（默认 0.9） | 无 |
| 防削波 | `_peak_norm`：叠加后整体等比回缩到峰值 0.97 | 无 |
| 跨采样率 | `_resample`：线性插值（素材 48k ↔ TTS 44.1k） | 无 |
| 垫整段 BGM | `at_s=0` + 长素材即可；越界自动贴尾并记 notes | 见 3.4 ①② |

预混端点 `POST /api/soundboard/premix`（`m2_server/soundboard.py:354`）就是这条 DSP 的
HTTP 封装：`输出 sfxmix_<原名>.wav → 发送目标换成它`。**「歌声版预混」= 同一条链路
换一种素材**。

### 3.3 已被真机验证的相邻路径（trust 现成的理由）

- 声板预混 4 组真机验收全过（`docs/真机验收清单-2026-09-21.md` §H 表）：
  append/layer 语义正确（层叠窗口 RMS +0.114、窗外 −0.015）、混好后真发进微信
  （`outcome: ok`、会话条数 6→7→8）、实时插播也通过（§H 表第 4 行）。
- `mix_into` 有 30 条单测守卫（`m2_server/tests/test_premix.py`）。

### 3.4 缺口清单（真要做成功能时补什么）

1. **长素材淡入淡出**：`mix_into` 的 layer 叠加是硬贴——一段 3 分钟的歌垫在 30 秒人声下，
   开头结尾是硬切。需要加 `fade_in/fade_out`（或利用 `cover_api` 的 ffmpeg amix 路线，
   `m2_server/cover_api.py:146` 的 `mix_back` 已有 `amix` 实践）。
2. **BGM 音量语义**：声板的 `gain=0.9` 语义是「音效与人声同量级」；垫 BGM 需要
   「BGM 比人声低 ~10dB」的默认（翻唱链路 `AUTO_VOCAL_LEAD_DB=2.5` 的思路可复用：
   按 RMS 实测配平而不是让用户盲猜滑块）。
3. **素材入口**：歌声从哪来？三条现成路——
   a. **翻唱链路产物**（`cover_api`：整首歌 → demucs 分离 → RVC 换声 → 合回）——用户已能
      产出「某首歌的袋鼠音色翻唱」，截 60s 内一段垫底即可；
   b. **本地音频文件/在线扒歌**（`ytdlp_fetch` 已能拉歌）；
   c. 用户自带伴奏/歌曲文件（导入，类似声板 `/import` 但放宽 5s 限制）。
4. **60s 预算对齐**：混了 BGM 之后总时长 = max(人声, BGM)。分段发送方案
   （`docs/微信语音-长文分段发送方案.md`）的 `pack_chunks` 按人声句切分，
   BGM 不能跟着切（切歌很难听）——**BGM 版建议单条 ≤54s 不分段**，或 BGM 分段时按
   音乐小节/静音切。这是产品决定，不是技术限制。
5. **16kHz 音质预期管理**：SILK 会把 8kHz 以上截掉——垫的是「闷一点的歌」。
   BGM 侧把能量集中在中低频（人声频段外）听感最好；这是文案/预期管理，不是 bug。

### 3.5 「不能冲突」逐项对账

| 交互点 | 结论 | 依据 |
|---|---|---|
| 发送链路（`wechat_voice.py`） | **零改动**，输入只是一条 wav | §3.1 |
| `_send_lock` / `_restore_lock` / `_history_lock` | 无新增竞争——混音在发送之前完成，不碰发送期声卡 | 三把锁的语义见 `wechat_voice.py:150,353,356` |
| 实时声板（`board_worker.py`） | 不共用播放器——发送链路用 `play_worker`，声板自带 worker（行协议隔离，防「playing/done 被对方吃掉」的静默错发）。BGM 若做实时垫歌需**复用声板 worker**（它支持任意长 wav 非阻塞播放），**不要**走 `play_worker`（单命令串行，长 BGM 会占死 handle） | `board_worker.py:3-14` 的分工注释 |
| 预混端点（`/premix`） | 同源 DSP（`sfx_lib`），扩展 `mix_into` 参数即可，无新锁 | `sfx_lib.py` 是无路由叶子模块，两个消费者共用的设计初衷 |
| 60s 预算护栏 | 混音后时长可能变长（BGM 比人声长）——护栏判据 `PLAY_LEAD+audio+TAIL ≤ 60` 天然覆盖（音频变长了预算就变紧），无需改护栏逻辑 | `docs/微信语音-长文分段发送方案.md` §2 |
| UIA/鼠标自动化 | 行为不变、频率不变（还是一次发送一条/一批），不触碰新增风险面 | §Q6 |

**唯一的真冲突点**（预判）：若将来做「**实时**边唱边说」（录音进行中往 CABLE 叠 BGM），
必须走声板 worker 路线且**遵守它「抢占式 one-shot」语义之外的新约束**——BGM 是长播放，
不能被下一格音效抢占中断；需要给 worker 加「垫底层」概念（多条叠加而非抢占）。这是
新功能域，不在本次调研的必要路径上（预混路线已能满足「一条语音里有歌有话」）。

## 四、产品路线建议（按性价比排序）

| 档 | 内容 | 复用度 | 工作量 |
|---|---|---|---|
| **A. 歌声垫底预混**（推荐先做） | 声板面板加「垫 BGM」素材区：选一首歌/翻唱产物 → `mix_into` layer 全程叠加（自动配平 + 淡入淡出）→ 产物走现有发送链路 | ~85%（DSP/端点/发送全现成） | 小：`mix_into` 加 fade/配平参数 + 一个素材选择 UI |
| **B. 翻唱直发** | 翻唱产物（`cover_api` 输出已是「人声+伴奏混好」的完整歌曲）截 ≤54s 直接 send_voice | ~95%（两端都现成，缺一个「截 60s」入口） | 极小 |
| **C. 实时垫歌** | 录音（说话/实时变声）进行中往 CABLE 叠 BGM——需给声板 worker 加「垫底层」（非抢占、可调音量、随时停） | ~50%（worker 行协议要扩展） | 中 |
| D. 视频载体 | 生成带画面的视频（如课程视频链路产物）发文件 | 另一个功能域 | 大 |

**建议**：A 和 B 覆盖「边有歌声、边能说话」的绝大多数真实诉求（语音消息形式），
且与现有架构零冲突；C 是体验升级，等 A/B 真机跑通后再评估；D 与本调研的问题相距最远。

## 五、诚实边界

- 外部结论里「语音消息无内容限制」「虚拟声卡无封号判例」都是**基于公开信息的 absence of
  evidence**——不等于腾讯承诺允许，只说明无公开拦截案例。项目一贯的「不 Hook、不注入、
  只模拟人手」红线继续维持，就是当前最优的风险姿态。
- Q2 的通话内容检测（2026-07 头条单源）与 Q6 的影刀实例都说明**行为特征与内容合规**
  是真实存在的检测维度——高频/批量/异常内容永远是比「加不加 BGM」更大的风险源。
- 「像视频一样」若用户本意是**画面**，语音消息路线给不了——需要明确引导到视频文件路线（D 档）。
