# 犯错指南 · 微信 PC 端自动化 & 工程流程

> 建立于 2026-09-10。**每踩一个新坑就往这里补一条**，写清「症状 / 根因 / 对策 / 证据」，
> 并标注可信度：`✅本机实测` / `📚社区库声称` / `❓未验证`。
>
> 相关文件：`m2_server/wechat_voice.py`（主实现）、`m2_server/tests/test_wechat_record.py`（32 用例）、
> `tools/wechat_e2e_check.py`（真机自检）、`tools/tts_and_send.py`（文字→袋鼠音色→微信）、
> `tools/uia_probe.py`（**UIA 热激活探测，见 §5.1**）、
> `tools/cable_diag.py` + `tools/cable_watch.py`（**虚拟音频通断实测 / 默认设备探针，见 §2.15**）。
> 社区参考库：`_ref/wechatauto-replica/`、`_ref/pywechat/`（已 gitignore，仅本地参考）。

## 二、微信 4.x 语音发送：错误档案

### 2.1 点击穿透：`WS_EX_TRANSPARENT` ✅

**症状**：`SendInput` / `mouse_event` 移动光标到话筒图标上，hover 有效（图标有反应），
但 click 完全无效，像点在了空气上。

**诊断**：枚举微信渲染子窗口（类名 `MMUIRenderSubWindow*`），读扩展样式：

```python
u.GetWindowLongW(render, -20)   # 实测得到 0x80020
# 0x20 = WS_EX_TRANSPARENT  ← 元凶：鼠标消息穿透
# 0x80000 = WS_EX_LAYERED
```

**根因**：微信 4.x 聊天区是自绘渲染窗口，带 `WS_EX_TRANSPARENT`，真实鼠标点击会穿透到下面的主窗口。
`wechatauto-replica` 独立得出了同一结论（`guia.py:901-923`「渲染子窗口设置了
`WS_EX_LAYERED | WS_EX_TRANSPARENT`，导致 mouse_event 的点击会穿透到主窗口」），
并在其技术文档里写明 4.1.12+ 聊天区「对 UIAutomation / MSAA 完全不暴露内容」。

**对策**：临时摘掉样式位 → 操作 → **立刻还原**。

```python
old = _exstyle_clear_transparent(render)        # SetWindowLongW(render, -20, ex & ~0x20)
try:
    ...
finally:
    _exstyle_restore_if_needed()                # 还原成 old，别忘了
```

**⚠️ 注意（我们与社区结论不完全一致）**：社区库称"必须摘样式"，
但 2026-09-10 本机 A/B 实测：**单击方式下摘不摘都能起浮层**。
摘样式在"点浮层绿钮"这步仍是保留动作（稳妥），不要据此认定它是唯一根因——
曾因为过早把它当成根因，浪费了好几轮排查（真正的根因见 §3.1）。

---

### 2.2 发出去却是 60 秒 ✅（最贵的一个坑）

**症状**：`outcome=ok`、脚本 6 步全过，但微信聊天里显示 **60"**，内容是整段静音+音频。

**根因**：`_trigger_record` 在话筒处按下（DOWN）启动录音，而 `_finish_record` 是
"**另起一轮** DOWN+UP 去点绿钮"——**原始那个 DOWN 从未被 UP 解除**。
微信内部的长按/录音计时一直挂着，直到 60 秒硬上限自动截断才发出。

**试过但错误的方向**（记下来别再走）：
- 用 `PostMessage` 直投 `WM_LBUTTONUP` → 被微信吞掉，录到 59s 超时。
- 在话筒原位置 `SendInput UP` → 无效（浮层出现后 mic 已移位，且 Qt 内部计时不吃这一套）。
- "移到绿钮再松手"（模拟 drag-to-send 手势）→ 仍是未解除的按住状态，依然 60s。

**修复**（commit `e05ddba` → 后由 `23cdc25` 定型）：**单击进入持续录音，点绿钮 ↑ 发送**。

**判据**：录制时长 ≈ `LEAD_S(0.35) + 0.25 + 音频时长 + TAIL_S(0.3)` ≈ 音频 + 1s。
发 10.7s 音频，微信应显示 **15"** 左右；显示 60" 就是本坑复发。

---

### 2.3 「按住」还是「单击」——最终定论 ✅

微信 4.x 输入框右下角的**圆形声波按钮是单击开始持续录音**，不是微信手机端的"按住说话"。

| 操作 | 本机实测结果 |
|---|---|
| `SendInput` 按住不松 6s | ❌ 浮层**从不出现**，最后抛 `RuntimeError` 走降级 |
| `SendInput` 单击（DOWN+UP 各 60ms） | ✅ 浮层立刻出现，持续录音，点绿钮发送 |

**与社区的矛盾点**（记录备查）：`pywechat`/`pyweixin` 的 `send_audios_to_friend` 用的是
**按住**（`send_audio_button.click_input()` 按住 → 播放 → `mouse.click` 释放），
且要求微信 **≥ 4.1.9**（低于此版本直接打印"当前微信版本不支持发送语音!"）。
→ 说明该交互**随版本变化**。升级微信后若单击失效，先回来重测这一条。

### 2.4 浮层判据：灰度差分不可靠 ✅

**演化过程**（两个方向都试过，记下来省得再试）：

| 方案 | 结果 |
|---|---|
| 常驻绿色"发送"钮判据（早期） | ❌ 假阳性——输入条上本来就有个灰绿色按钮，误判成"浮层已起" |
| 灰度差分（基线 vs 当前，阈值 `VM_WECHAT_OVERLAY_DIFF=1.0`，commit `0b21806`） | ⚠️ 当时的标定是"噪声 0.000 / 信号 2.329"，但 09-10 复查发现浮层出现时该区域差分 **< 0.2**，无法稳定区分 → 曾因此漏检浮层，误判失败去降级，留下挂起录音 |
| **HSV 识别绿色 ↑ 钮**（当前方案） | ✅ 稳定：`R<120 & G>150 & 80<B<180`，像素数 > 50 取质心 |

**教训**：判据要在"**真出问题的那一次**"上验证，不是在"顺利的那一次"上标定。
一次 2.329 的信号可能来自别的干扰源（当时正好有控制台窗口弹出），不能作为阈值依据。

### 2.5 话筒图标会漂移，单模板必挂 ✅

同一个图标，实测 NCC 匹配分数从 **1.0 → 0.326** 断崖式下跌（界面状态/主题/版本都会影响）。

**对策**：多模板 + 取最高分。`m2_server/assets/wechat_mic_template.png`、
`wechat_mic_template2.png`，`_mic_templates()` 用 `glob("wechat_mic_template*.png")` 全收。

**运维动作**：图标再变了、分数掉到 0.75 阈值以下时，**裁一张新模板丢进
`m2_server/assets/wechat_mic_template3.png` 即自动纳入**，不用改代码。

**技术细节**：NCC 用 numpy 纯实现，`ds=1`（**全精度，不降采样**）——
降采样会把话筒这类细线图标「抹掉」，分数直接崩。

### 2.6 临时控制台窗口遮挡 → 自动发送全废 ✅（最隐蔽的一个）

**症状**：手动跑明明能成，走脚本 100% 降级成 `manual_fallback`。

**根因**：切声卡/播放音频会 `subprocess` 弹出控制台窗口，**正好遮住微信底部的浮层区域**，
截图检测到的全是黑窗口，浮层判据永远 False。

**修复**：所有 subprocess 一律加

```python
creationflags = 0x08000000   # CREATE_NO_WINDOW
```

效果对比（commit `0b21806`）：隐藏前 41s 失败 → 隐藏后 **13s 成功**。

> 推论（通用）：**任何"截图 + 视觉判据"的自动化，都必须先保证屏幕上没有别的窗口**。
> 自己的子进程、弹窗、日志窗都算干扰源。

---

### 2.7 `_ensure_onscreen` 把窗口推出屏外 ✅

**症状**：请求把窗口拉回屏内，结果窗口底边反而超出屏幕 9px，被任务栏挡住 → 后续坐标全偏。

**根因**：原逻辑优先处理顶边，导致底边反推越界。

**修复**：**底边优先**——底边超屏就整体上移；只有"整个窗口在屏幕外"时才动顶边。
已加 3 个边界回归测试锁死行为。

---

### 2.8 坐标取域必须 clamp 到屏幕 ✅

`ImageGrab.grab(bbox=...)` 的 bbox 超出屏幕时，PIL 会把屏外部分**填黑**。
最大化窗口底边常溢出几像素，若绿钮正好落在填黑区，就**永远检测不到**。

```python
sw, sh = u.GetSystemMetrics(0), u.GetSystemMetrics(1)
box = (max(0, min(r, sw) - 560), max(0, min(b, sh) - 140), min(r, sw), min(b, sh))
if box[2] <= box[0] or box[3] <= box[1]:
    return None
```

同类坑：`_window_rect` 实测拿到过 `(-9, -9, 1289, 1600)`（窗口贴边/负坐标），
所有截屏与坐标换算都要能容忍负值。

---

### 2.9 时长约束：最短 1s / 最长 60s ✅

- **最短 1 秒**（用户观察确认）：太短微信直接提示"说话时间太短"**不发**。
  我们的流程录音时长 ≈ 音频 + 1s，所以音频 > 1s 即安全。
- **最长 60 秒**自动截断，超出部分丢弃。
- 社区补充：`pywechat` 的 `audio_length` 限 **1~60s**，与我们实测一致。

---

### 2.10 右 Alt 快捷键：软件注入**彻底无效** ✅（2026-09-10 五组对照实测）

微信语音按钮的官方提示就是「**按住右 Alt**」（UIA 读到的控件 Name 原话
`发语音 ( 按住右 Alt )`），用户手动长按确实能起录音浮层、松开发送。
但**所有软件注入方式都不行**：

| 注入方式 | 结果 |
|---|---|
| `SendInput` `VK_LMENU`(0xA4)——旧实现 | ✗ 浮层不出现 |
| `SendInput` `VK_RMENU`(0xA5) + `KEYEVENTF_EXTENDEDKEY`(0x0001) | ✗ |
| `keybd_event` `VK_RMENU` + 扩展标志（老式输入管线） | ✗ |
| `SendInput` `VK_MENU`(0x12) 不带扩展位 | ✗ |
| `PostMessage WM_KEYDOWN/WM_KEYUP` 直投渲染子窗口 | ✗ |

**决定性对照**：同一时刻 `SendInput` 注入普通字符 `'a'` **能落进输入框**（文本读到 `嗄a`）——
说明注入的键盘事件**确实到达了微信窗口**，只是被输入法吃成了候选字。可 Alt 快捷键就是不响应，
所以微信对**快捷键**另有一条识别路径（低级键盘钩子按 `LLKHF_INJECTED` 过滤，或走 RawInput 只认硬件），
**不是**"注入没送到"。

**顺带排除的两个假设**：
- ✗ "必须先点击输入框聚焦" —— 实测 `ChatInputField.HasKeyboardFocus == True` 时注入依旧无效。
  用户观察到的"要先点一下输入框"是**手动操作**的前置条件，对注入路径没有帮助。
- ✗ "切英文输入法就行" —— 微信窗口拿不到 IME context（`ImmGetContext` 返回 0），Qt 自管输入法。

**结论**：不要在这条路上继续投入。自动化只能走**鼠标路径**（UIA Click 或 SendInput 单击语音按钮）。
`VM_WECHAT_RECORD_METHOD=alt` 仅剩"引导用户手动按 Alt"的意义（`_guided_fallback`）。

### 2.12 语音开头多出 3~4 秒空白：播放子进程的 import 开销被录了进去 ✅

**症状（2026-09-10 真机）**：

| 音频时长 | 微信消息显示 | 多出来 |
|---|---|---|
| 2.72s | `语音7"秒` | +4.3s |
| 10.80s | `语音15"秒` | +4.2s |

偏差**恒定 ≈ 4.2s**，与音频长短无关 → 说明是固定开销，不是比例问题。

**根因**：`_play_to_cable()` 是**同步** `subprocess.run()`。调用链是
「点录音 → `sleep(0.6)` → 起子进程 → 播」，而子进程起来要：

```
python 启动 + import numpy / sounddevice / soundfile  ≈ 2.5~3s   ← 微信已经在录了！
+ LEAD_S 0.35 + 音频 + TAIL_S 0.3 + 发送前 sleep 0.3
```

这段启动时间被微信**完整录进语音**，听感就是"点开语音先愣 3 秒"。

**对策：把播放提前到点击录音之前，用开播信号对齐**

1. `_PLAY_SCRIPT` 在 `sd.play()` 前 `print("PLAYING", flush=True)`；
2. `_start_play()` 用 `Popen(stdout=PIPE, text=True, bufsize=1)` **后台**起进程；
3. 主进程 `_wait_play_start()` 阻塞读一行，读到 `PLAYING` 才点录音；
4. 静音头（`PLAY_LEAD_S`，默认 0.8s）此时正在播，正好盖住「点按钮 → 微信真正开始录」的延迟；
5. `_wait_play_done()` 等子进程退出（= 播完），再点发送。

```python
proc = _start_play(wav)          # 后台起，import 开销发生在录音之前
_wait_play_start(proc)           # 等 PLAYING
_trigger_record()                # 此刻静音头在播 → 不丢开头
_wait_play_done(proc, duration)
time.sleep(0.15)                 # 只留驱动缓冲；播放脚本尾部已自带 TAIL_S
_finish_record()
```

**修复后**：2.72s → `语音4"秒`，12.24s → `语音14"秒`（空白 ~1.8s）。

⚠️ 两个注意点：
- `PLAY_LEAD_S` 是**权衡值**：太小会削掉第一个字，太大开头留白。`VM_WECHAT_PLAY_LEAD_S` 可调。
  降级引导路径（`_guided_fallback`）仍用同步 `_play_to_cable`，它的 2s 静音头是留给**人**手动按 Alt 的，不要改。
- 异常路径必须 `proc.kill()`，否则子进程会一直往 CABLE 灌声音。

### 2.13 UIA 发送校验的两个误报 ✅

`_uia_verify_sent()` 靠读 `mmui::ChatVoiceItemView` 的名称（`语音15"秒`）判断有没有真发出去。
它有两个反直觉的坑：

**坑 A：条数恒定不变**
聊天消息是**虚拟列表**，UIA 只暴露可视区那十几条。实测无论发不发，`voice_messages()` 永远返回 11 条。
→ **"条数 11→11" 完全不能作为"没发出去"的证据**，只是说明可视区没变。

**坑 B：连续两条时长相同的语音，文本一模一样**
UIA 名称只有时长信息。上一条 `语音15"秒`，新发的也是 15 秒 → 文本相同 →
原逻辑（`msg != before_msg`）判定"本次可能没发出去"，**把成功报成失败**。

**正确判据（或关系）**：

```python
added = before_count >= 0 and count > before_count   # 条数变多（正向佐证）
if not added and msg == before_msg:                  # 两者都没变才可疑
    → "可能没发出去"
```

判定时要**先读 `latest_voice_message()` 再读 `voice_messages()`，且分开 try**——
放一个 `try` 里，`voice_messages()` 一抛异常会把已经读到的 `msg` 一起清空，
退化成"读不到语音消息"。（这个 bug 在补 `FakeUia.voice_messages()` 时才暴露。）

### 2.14 音色不像：链路漏了 RVC ✅

**症状（2026-09-10）**：语音成功发出，但用户一听"不像袋鼠"。

**根因：整条链路里根本没有 RVC。** `tools/tts_and_send.py` 只做了

```
文字 → qwen3_tts.tts(ref_audio=袋鼠 reference.wav) → 发送
```

也就是**纯 TTS 零样本克隆**。但零样本克隆**复现不了袋鼠音色**——
2026-08-31 用户 A/B 亲耳判定过（base 与 QLoRA 都不行，见 `MEMORY.md` 技术路线定论）。

**袋鼠音色的唯一来源是 RVC 模型** `logs/kangaroo_v2`。正确分工是
**TTS 管"怎么说"、RVC 管"谁在说"**——这正是项目里 ASR→TTS→RVC 级联的既定设计。

**修好的链路**：

```
文字 → TTS（任意音色，出韵律） → RVC 换声（袋鼠） → 微信发送
```

```bash
.venv/Scripts/python.exe tools/tts_and_send.py --text "..."              # 默认带 RVC
.venv/Scripts/python.exe tools/tts_and_send.py --voice kangaroo_v2_40k   # 换模型
.venv/Scripts/python.exe tools/tts_and_send.py --no-rvc                  # 纯克隆（音色会不像）
```

⚠️ **给任何"克隆音色"需求做验证前，先确认链路里有没有 RVC 这一环**，
别拿 `ref_audio` 当音色开关——它只是韵律/语气的参考。

**配套踩坑**：RVC 子进程 `ModuleNotFoundError: No module named 'infer'`

- `offline_vc_infer.main()` 里 `from infer.audio import load_audio` 排在 `load_vc()` **之前**，
  而 `setup_env()`（chdir RVC 根 + `sys.path.insert`）在 `load_vc()` 内部才执行 → 必然报错。
- **光给 `subprocess.run` 加 `cwd=` 没用**：Windows 下跑脚本时 `sys.path[0]` 是脚本目录，
  cwd 不会自动进 `sys.path`。
- 正解：`main()` 里先 `setup_env()` 再 import；因为 `setup_env()` 会 chdir，
  相对路径要先用 `os.path.abspath()` 钉死。

> 这个 bug 在 `m2_server/offline_vc.py` 的线上离线转换里同样存在（它也是子进程调这个脚本），
> 已一并修掉。

### 2.15 「VB-CABLE 坏了」是假象：微信根本没在听 CABLE ✅（2026-09-11 实测定性）

排查了一整天、重装驱动两次、重启电脑两次，最后**驱动是无辜的**。动 CABLE 之前先读这条。

**症状**

- 声音进 CABLE Input（音量条会跳），但从 CABLE Output 录出来是**纯静音**。
- 于是怀疑 Windows 11 25H2 预览版（build 26200）不兼容 VB-CABLE 驱动。

**实测结论：驱动完好，桥接 100% 通**（`tools/cable_diag.py` 在 本机跑出来的数字）

| 维度 | 结果 |
|---|---|
| MME @44100（**老程序走的 API**） | ✔ peak 0.763 |
| DirectSound @44100 | ✔ peak 0.763 |
| WASAPI @48000 | ✔ peak 0.763 |
| 采集端 8000/16000/22050/32000/44100/48000 Hz | ✔ 全部有声 |
| MME 下 1 / 2 / 16 声道 | ✔ 全部有声 |

驱动 `VB-Audio Virtual Cable 3.3.1.7`（2024-10-07，WHQL 签名），
`Get-PnpDevice` 状态 `OK / CM_PROB_NONE`，三个 AudioEndpoint 全部 Present。
**这三条加起来可以排除驱动层。**

**真根因：微信不选 default endpoint，它有自己的设备绑定**

锤子 evidence 来自微信自己的遥测，`%APPDATA%\Tencent\xwechat\net\kvcomm\*_input.statistic`：

```
start_record {"chatname":"filehelper"; "err_code":0; "rec_start_result":1}
96,1,165,184,205,0,0,0,0, 麦克风阵列 (Senary Audio) ,,,    ← 实际输入设备
end_record   {"rec_ms":6600; "rec_end_result":1}
send_record  {"err_code":0; "rec_send_result":1; "sub_err_code":0}
```

`err_code=0`、成功录了 6.6s 并发出去了——**但它用的是本机物理麦，不是 CABLE Output**。
所以录到的是安静房间声，听起来就是"静音"。

**为什么是物理麦**：微信在**进程启动 / 音频会话初始化时**就已枚举并绑定了 capture device。
`SetDefaultEndpoint` 之后改 Windows 默认设备，**对已经建立的设备选择不会热生效**。

**对策（2026-09-12 已自动化进发送链路）**

`m2_server/wechat_proc.py`（进程/窗口底层）+ `wechat_voice._prepare_recording_env()`：

```
杀微信(Weixin.exe) → audio_config.ps1 apply（默认麦 → CABLE Output）→ 拉起微信 → 等主窗口就绪 → 播放 + 录音
```

顺序是硬约束：**微信必须在「默认麦已经是 CABLE」之后才启动**（它只在进程启动时枚举设备）。
先 apply 再重启微信也成立；代码取"先杀"只为保证微信绝不会带着旧绑定被这次录音取用。

- 要不要重启由 `VM_WECHAT_RESTART` 决定：`auto`（默认）按**微信自己的遥测证据**判断——
  上次录音设备名里含 `cable` 就不重启（省 10~30s），否则重启；**读不到证据时保守重启**
  （漏重启 = 静音语音真的发出去，误重启只是多等十几秒，代价不对称）。
  `1` = 每次强制重启；`0` = 从不重启（旧行为）。
- 重启最长 10~30s，已整体提前到与 TTS 合成**并行**（`_PendingRecordingEnv`），不额外拖慢端到端。
- 发送前想先看判断，打 `GET /api/wechat/precheck`（**只读**，不动声卡、不碰微信），
  会返回 `restart_needed / reason / last_input_device / wechat_exe`。
- 微信停在登录页时**绝不硬录**：主窗口面积 < `VM_WECHAT_MIN_CHAT_AREA`（默认 20 万 px²）
  就报错让用户先登录——否则点话筒点的是错坐标。
- 找不到微信主程序时报错并提示设 `VM_WECHAT_EXE`；切卡中途失败也会**兜底把微信拉回来**，
  绝不因为一次发送失败把用户的微信丢在死状态。

手动确认（重启影响面小的时候）：

1. 想亲自确认微信用了哪个设备，直接看那条遥测，别猜：
   `grep -a 'start_record\|end_record' "%APPDATA%/Tencent/xwechat/net/kvcomm/"*_input.statistic`

**两个会把人带偏的观察错觉**

- ❌ **"CABLE Output 的电平条是 0" 不能当作故障证据。** CABLE 是**直通**缓冲，
  **没有 consumer 正在读的时候它就是 0**，播放一停也立刻归 0。
  你看到的 0 很可能只是"你去看的时候播放已经结束了"。判据只能是**边播边录**。
- ❌ **"这台机器上 WASAPI 在 16k 采集端打不开 ≠ 微信录不到。"** 那是 PortAudio 的限制，
  Windows 音频引擎在共享模式下会自己做重采样（MME 层 8k/16k 实测全通就是反证）。

**顺手发现的真故障**：`audio_config.ps1` 的 restore 没成功时会**把系统默认麦留在 CABLE 上**，
导致日常通话也说不了话。用 `tools/cable_watch.py --status` 一眼能看出来。

**新增诊断工具**

| 工具 | 用途 |
|---|---|
| `tools/cable_diag.py` | 虚拟音频**实际通断**实测：按 API / 采样率 / 通道数三个维度扫，直接给 RMS/peak |
| `tools/cable_watch.py` | Core Audio 层探针：读三个角色当前默认设备、监控被谁改回去（不用 `Add-Type`，沙箱也能跑） |

> 教训：**"我怀疑 X 坏了" 要在动手重装之前先确认 X 真的坏了。**
> 一次三分钟的实测，省掉两次驱动重装 + 两次重启。

### 2.16 设备判据退化成 "vb-audio"：Voicemeeter Point 被当成 CABLE ✅（2026-09-18 实测）

- **症状**：auto 模式下判"无需重启微信"，语音录成静音发出去——**与 §2.15 症状一样，但成因完全不同**，日志里也看不出任何异常。
- **根因**：`_device_keyword()` 取 `OUTPUT_DEVICE_KEYWORD` 的**首词**。该常量原本是
  `"CABLE Input (VB-Audio Virtual Cable)"`（首词 `CABLE` 恰好采集端也有），后来为了兼容中文系统
  改成常量串 `"VB-Audio Virtual Cable"`（`wechat_voice.py:73` 的注释解释了这个改动），
  首词于是变成 `vb-audio`——而本机设备表里还有 **Voicemeeter 的**
  `CABLE Output (VB-Audio Point)` / `Input (VB-Audio Point)`：**含 "vb-audio"，但不含 "virtual cable"**。
- **判据为何会被骗**：`_need_wechat_restart()` 用的是 `kw in dev.lower()`，正例匹配通过、反例也能通过。
- **对策**：剥掉端点词（`CABLE Input` / `扬声器`…）后拿**中段串**做包含判断；回归守卫
  `test_device_keyword_is_not_just_first_token` + 参数化用例 `CABLE Output (VB-Audio Point) → 需要重启`。
- **证据**：✅本机实测（2026-09-18）：旧实现 `_device_keyword()` 返回 `"vb-audio"`；
  `sounddevice.query_devices()` 确实列出上述 Point 设备；**变异测试**把实现换回旧版，这 3 条用例全红。
- **教训**：**"取第一个词"这种约定，会在上游常量一改时静默失效。** 判据要写成"能不能区分**反例**"，
  而不是"能不能匹配正例"。

### 2.17 `VM_WECHAT_RESTART=0` 把绑定检查整体短路：静音语音无人提醒 ✅（2026-09-18）

- **症状**：用户拍板默认不重启（2026-09-17 起默认 `0`，理由是会退回登录页）之后，
  "微信绑的不是 CABLE"这个已知静音成因**再也没人过问**：微信用着物理麦也照样发语音，
  用户只能听完才发现是静音。
- **根因**：`_need_wechat_restart()` 在 `mode == "0"` 时**在读遥测之前**就 `return False` ——
  把"要不要提醒"和"要不要重启"绑成了同一件事。可前者只是读操作，完全免费。
- **对策**：新增只读的 `_binding_warning()`，只在 mode=0 且未重启时跑：微信没运行 → 提示
  "不会自动拉起，本次会降级为手动发送"；设备不匹配 → 提示"可能录成静音"；读不到遥测 →
  "无法确认"（不谎称一定错）。结果接进 `_prepare_recording_env()` 的 `summary`（带 ⚠）随 steps 上前端。
- **证据**：✅本机实测（当前机器 `restart_mode=0`、微信未运行，正是会静默降级的组合）。

### 2.18 UIA 点击成功后浮层检测超时 → 会重复点击话筒 ✅（2026-09-18 复核）

- **症状**：偶发"录音中途莫名结束"或"发出去一条不完整的语音"。
- **根因**：`_trigger_record()` 原判据是 `if _uia.click_voice_button() and _wait_record_overlay(...)`——
  **浮层检测**失败就整体落到像素分支，**又点一次话筒**。而 §2.3 已定论：这个话筒是"单击开始持续录音"，
  第二次点击会把进行中的录音停掉／送出去。把"点击没生效"与"我没看见浮层"当成同一件事，是这里的根因。
- **对策**：记住"点击已发出"这个事实——点击成功但检测没命中时**只抛错、绝不重复点击**，
  并把检测多给一次机会（5s + 0.5s + 2s）以容忍浮层渲染慢。
- **证据**：✅变异测试：换回旧写法时 `test_trigger_never_clicks_twice_when_overlay_missing` 必红
  （`mouse_calls` 会变成 `[True, False]`）。

### 2.20 CLI 入口会把默认麦留在 CABLE Output（后台还原线程被进程退出杀死）✅（2026-09-18 实测）

- **症状**：用 `tools/tts_and_send.py --wav xxx.wav` 发完一条语音后，系统默认麦克风**仍然停在 CABLE Output**，
  于是后续真人语音/通话全部“听不见你说话”——与 §2.15 末尾那个“顺手发现的真故障”同症状，
  但这次是**必然而不是偶发**。
- **根因**：`_do_send()` 成功时把声卡还原交给 **daemon 线程**（`threading.Thread(target=_restore_async, daemon=True)`）
  并立即返回（`restored: None` 就是“还没还原”）。短命进程（CLI 脚本）在 return 后立刻退出 →
  daemon 线程被当场掐死 → 还原逻辑根本没跑完。**服务端（FastAPI）与桌宠路径不受影响**，它们是长驻进程。
- **复现（不发任何消息）**：`_run_audio('apply')` → 起 `_restore_async` 线程 → 立即退出 → 等 8s 后
  `tools/cable_watch.py --status` 仍为 CABLE Output（实测 2/2 次）。
- **对策（未做）**：CLI 入口要**等还原结束**（join 线程或轮询设备）；`_do_send` 可提供一个“还原同步完成”的选项；
  至少把 `声卡还原=None` 打印成“pending”而不是让人误读为“已还原”。
- **教训**：**“不阻塞返回”的优化只对长驻进程成立**。给服务端做的异步化，套到 CLI 上就变成了“不做”。

### 2.21 §2.15 的“必须重启微信”需要重新验证（微信可能已经会跟随默认设备切换）❓（2026-09-18 观察到反例）

- **§2.15 的结论**：微信在**进程启动时**绑定采集设备，之后再改 Windows 默认麦克风对它不热生效，
  所以必须“杀微信 → 切卡 → 拉起”才能录到 CABLE。
- **今日反例（待复验）**：微信 4.1.13.12 于 14:40 启动（当时默认麦 = `麦克风阵列 (Senary Audio)`），

  静音基线（不播任何声音）= 暗像素 215 / 纵向跳度 **6px**（一条平的点线）；

### 2.24 跑一遍单测，往**用户真实历史**里塞了一条假发送记录 ✅（2026-09-18 实测定位）

- **症状**：跑完 `pytest tests/`，真实 `outputs/wechat_send_history.json` 多出一条
  `tts_x.wav / 1.0s`。用户打开桌宠「最近发送」看到「1 分钟前 · 1s」，以为是自己刚发的
  —— 排查静音问题时这个假记录直接把方向带偏（`tts_x.wav` 在 `outputs/` 根本不存在）。
- **根因**：`_persist_verify()` / `_restore_async()` 都是 **daemon 后台线程**，运行时才解析
  模块全局 `HISTORY_FILE`。单测里 `monkeypatch` 把 `HISTORY_FILE` 指到 `tmp_path`，
  但线程的生命周期**跨越了调用方的作用域**：
  - 线程**读**的时候，patch 还在 → 读到 tmp_path 的内容；
  - 线程**写**的时候，测试已结束、patch 已撤销 → 写进用户真实路径。
  → 于是"tmp_path 里的记录"被原样搬进了真实文件。
  `_persist_verify` 尤其隐蔽：调用方写成 `target=lambda: _persist_verify(_uia_verify_sent(...))`，
  lambda 体要等 `_uia_verify_sent` **扫微信窗口**（几百 ms~3s）跑完才执行 —— 哪怕只晚几百毫秒，
  也足够跨过作用域边界。
- **诊断手法（可复用）**：
  1. **哨兵实验**：往真实文件写一条 `{"wav":"SENTINEL.wav"}`，跑完测试看是否被改/被替换。
     比翻日志快且无歧义 —— 本次一次就看出是"整体替换"而非"追加"。
  2. **`--basetemp` 对照**：发现 tmp_path 里记录**写对了**、真实文件**也被写** →
     立刻指向"读写到了两个不同文件"，而不是"patch 没生效"（后者会让人白查 monkeypatch）。
  3. **逐文件跑 + 每次查哨兵**，把范围收敛：本次 8 个最可疑文件（play_worker / wechat_retry /
     wechat_restart / wechat_send_text / send_chain / tts_send_chain / wechat_regression / history，
     共 143 用例）全跑一遍、哨兵纹丝不动 → 确认修复有效。
  4. **别用全量跑来定位**：本次全量 5 分钟没结束（有别的用例在等真实资源超时），
     耗时且干扰判断；逐文件反而 1~3 秒一个。
- **对策**：
  1. 路径由**调用方在起线程那一刻**定下来并传进去 —— `args=(HISTORY_FILE,)`，
     或 lambda 闭包捕获 `hist_path = HISTORY_FILE` 局部变量。绝不让线程体自己去读全局。
  2. `m2_server/tests/conftest.py` 加**全局 autouse 隔离**：`cfg.OUTPUTS_DIR` 与
     `wv.HISTORY_FILE` **都要** patch —— 后者是**模块级常量**（导入时由 `cfg.OUTPUTS_DIR` 求值），
     只 patch `cfg` 不管用。
  3. **变异验证**：把 `hist_path` 那行删掉 → `test_do_send_captures_history_path_when_thread_starts`
     转红（实测 `AssertionError: 'verify' in {...}`）。不转红的测试等于没写。
- **教训**：**"测试通过"不等于"没有副作用"。** 一个会写文件的函数被后台线程调用时，
  "什么时候写"和"写哪个文件"是两个独立问题；测试隔离（monkeypatch）只管得住前者。
  推而广之：**任何跨线程/跨进程传递的路径、句柄、配置，都要在"起线程那一刻"快照下来，
  不要留给线程运行时去查全局。**
- **残余风险**：`m2_server/test_wechat_voice.py` 位于 `tests/` **之外**，不受新 conftest 保护
  （它每个用例自己 patch `HISTORY_FILE`，本次实测干净）。将来新增写文件的用例时，
  放在 `tests/` 下才有 autouse 兜底。
- **证据**：✅本机实测（哨兵 + `--basetemp` 对照 + 逐文件收敛 + 变异转红，四重）。

### 2.25 级联"启动即退出"：设备关键词单点写死 + 同一个坑只修了一处 ✅（2026-09-19 实测）

- **症状**：桌宠面板红字「启动失败：级联子进程启动即退出（日志见 outputs/cascade_run.log）」。

  1. **播放端名字会漂移**：VB-Audio 的渲染端在 MME 枚举里，中文 Windows 叫

     端点词只在英文系统命中（完整驱动名匹配不上被截断的名字）。

     `play_worker.py` 四处没跟上 —— 它们共用**同一个环境变量** `VM_LIVE_OUTPUT_DEVICE`，
     默认值却不一致。
- **诊断手法**：
  1. **面板文案只给方向，真错在日志**：`cascade.py:240` 那句"启动即退出（日志见 …）"已经
     把路径写出来了，第一件事就是 `tail outputs/cascade_run.log`。
  2. **直接枚举设备名对比**：`sd.query_devices()` 过滤出 MME，打印所有输出端名字 ——
     一眼就能看出 `"CABLE Input"` 这个串在 MME 里**根本不存在**。
     注意 MMDevice（`audio_config.ps1 -list`）与 MME（sounddevice）**名字格式不同**，
     别拿前者的输出判断后者能不能匹配。
  3. **日志"先成功后失败"要当心**：`cascade_run.log` 是**追加**的，前面几轮成功可能是
     历史运行留下的，不能据此判断"刚才还能用"。
- **对策**：
  1. 默认值统一为**双候选** `"VB-Audio Virtual Cable|CABLE Input"`（驱动名优先、端点词兜底），
     消费方按 `|` 拆开逐个试（`find_device` / `_resolve_device` / `_device_matches`）。
  2. `wechat_voice._device_keyword()` **只取第一个候选** —— 它产出的是"剥掉端点词的中段串"，
     用来比对微信遥测里的设备名；拿端点词候选去比会误判。
  3. `find_device` 失败时把 MME 下可用的输出设备**全列进报错**（这次就是靠肉眼比对才定性的）。
  4. 新增 `tests/test_cable_keyword_consistency.py`：**五处默认值必须完全相同**、驱动名必须是
     首候选、候选必须覆盖中英文两种叫法、不许误命中 `CABLE In 16 Ch` 变体。
- **教训**：**同一个环境变量的默认值散落在 N 个文件里，就是 N 个会各自漂移的点。**
  改这类常量前先 `grep` 出全部消费点（本次 5 处），再写一条"逐处比对"的守卫测试 ——
  单点断言挡不住"只改了一处"。
- **证据**：✅本机实测。修复前 `find_device("CABLE Input", is_input=False)` → 找不到设备；
  修复后 `resolve_devices()` → `(1, 7, '麦克风阵列 (Senary Audio)', '扬声器 (VB-Audio Virtual Cable)')`。
  变异验证（把 `cascade.py` 改回单个端点词）→ 守卫测试 2 条精确转红。

### 2.26 一块虚拟声卡有两个播放端：`_device_matches` 会误命中 16 通道变体 ✅（2026-09-18 实测）

- **症状（潜伏，当前未爆发）**：变声结果播出去、微信侧听不到（静音），但设备列表"看起来"都正常。
  触发前提是把设备名来源从 MME 换成 MMDevice —— 不换就没事，一换就**静默选错**。
- **背景**（用户问"为什么会有两个虚拟声卡"）：`Get-PnpDevice -Class MEDIA` 只有**一个**
  VB-Audio 设备（`ROOT\MEDIA\0000`），但它暴露**三个音频端点**：

  | 端点名 | 方向 | 本项目 |
  |---|---|---|
  | `扬声器 (VB-Audio Virtual Cable)` | 播放端 | ✅ 变声结果播进这里 |
  | `CABLE Output (VB-Audio Virtual Cable)` | 采集端 | ✅ 微信把它当麦克风 |
  | `CABLE In 16 Ch (VB-Audio Virtual Cable)` | 16 通道播放端 | ❌ 不用 |

  Windows「输出」列表里因此并排出现**两条 VB-Audio**（扬声器 + CABLE In 16 Ch），
  「输入」列表里是第三条采集端。**这是驱动的正常设计，在用的两个端点绝不能禁用/卸载。**
- **根因**：`rvc_live._device_matches` 的匹配式
  `b in a or a in b or a[:28] in b or b[:28] in a` 里，`b in a`（**候选被设备名包含**）这一支：

  | 设备名来源 | 16Ch 的名字 | 候选 `VB-Audio Virtual Cable` |
  |---|---|---|
  | MME（`sd.query_devices()`） | `'CABLE In 16 Ch (VB-Audio Virtua'`（截断到 31 字符） | 匹配不上 ✅ |
  | MMDevice（`audio_config.ps1 -action list`） | `'CABLE In 16 Ch (VB-Audio Virtual Cable)'`（完整） | **误命中** ❌ |

  当前三个调用点（`_live_devices` 的第 671/680 行、`rvc_live_audio_devices_set` 的第 992 行）
  都走 MME，所以不会触发。**但这是运气，不是保证** —— 枚举顺序恰好把立体声排在前面而已。
- **对策**：
  1. 新增 `_mentions_16ch()`；`_device_matches` 里 **设备名带 16ch 而候选不带 → 直接跳过**。
     否决只看**名字**、不看通道数 —— 采集端 `CABLE Output` 的 `in` 通道数也是 16，
     拿通道数判断会把采集端一起误杀，变声链路直接断（微信录不到）。
  2. 新增 `tests/test_device_match.py`（20 条，**行为级**）：完整名/截断名两种形态下 16Ch 都必须被拒、
     候选显式带 `16 ch` 时仍要能命中、立体声端点与采集端仍要正常命中、
     枚举顺序把 16Ch 排前面时仍选立体声端、只有 16Ch 时**宁可返回 `None`**（走"沿用旧配置"）
     也不许选错端点。
- **教训**：**"包含匹配"天生会把同类设备的变体一起捞进来。**
  凡是用 `in` 做设备名匹配的地方，都要多问一句"这个名字会不会其实是**另一个端点**"——
  尤其是同一驱动暴露多端点的情况（VB-Audio 的 2ch/16ch、Steam 的 Speakers/Microphone）。
- **证据**：✅本机实测。`_resolve_device_names()` → `('麦克风阵列 (Senary Audio)', '扬声器 (VB-Audio Virtual Cable)')`
  （选中的是立体声端，不是 16Ch）；变异验证（把否决那行改成 `if False and …`）→
  `test_sixteen_ch_full_name_is_rejected`、`test_pick_skips_16ch_even_when_listed_first`、
  `test_pick_returns_none_when_only_16ch_present` **3 条精确转红**。

### 2.27 测试跨用例污染：模块级并发计数器 + 拿固定 sleep 当同步手段 ✅（2026-09-18 实测）

- **症状**：`pytest tests/test_pet_market.py` **单文件跑必红 2 条** ——

  1. **模块级全局状态 `monkeypatch` 复位不了**：`pet_market._TASKS` / `_QUEUE` /
     `_ALL_IDS` / `_RUNNING` 都是模块全局，`iso` fixture 只 patch 了目录和状态文件。
  2. **`is_busy()` 看不见 `_RUNNING`**：`_install_worker` 是**先把任务标成终结态、再**在
     `finally` 里 `_RUNNING -= 1`，中间还隔着一次 `shutil.rmtree`。上一条用例用
     `while is_busy()` 收尾时，任务状态一终结循环就退出 —— 此刻 `_RUNNING` 还是 1。
     下一条用例把 `MAX_CONCURRENT_INSTALLS` 设成 1，`_kick()` 的
     `_RUNNING < MAX_CONCURRENT_INSTALLS` 直接不成立 → worker 永不启动 → 任务永远停在 `queued`。
- **诊断手法**：
  1. **"单跑绿、连跑红" 就是跨用例污染**，第一反应不是改断言，而是找**没被复位的东西**。
     二分定位：`pytest -k "test_install_remote_gif_skin or test_install_queue_two_then_both_done"`。
  2. **别信固定 sleep**：那条用例用 `time.sleep(0.2)` 等 worker 起来，机器一忙就不够；
     而失败形态是"两个都还 queued"，看不出是**等得不够**还是**队列坏了**。
- **对策（全部在测试侧，不动生产代码）**：
  1. `iso` fixture 增加 `_drain_install_queue()`：**只等 worker 线程收尾**（`_RUNNING > 0`），
     然后清掉 `_TASKS`/`_QUEUE`/`_ALL_IDS`。
     ⚠️ **不要等"任务全部终结"** —— 本文件有用例（`test_busy_counts_queued_task`）
     故意把任务留在飞以断言 `is_busy()`，等"全部终结"会白等满 30 秒超时（实测 22 条用例
     从 27 秒变成 >2 分钟）。
     ⚠️ **也绝不改写 `_RUNNING`**：强置 0 之后，仍在跑的 worker 收尾时再 `-= 1` 会把它压成
     **负数**，而 `_kick()` 的 `_RUNNING < MAX_CONCURRENT_INSTALLS` 在负数下恒真，
     会一次放出超过并发上限的 worker（该文件有用例把上限设成 1，一冲就乱）。
  2. `test_install_queue_two_then_both_done` 的 `time.sleep(0.2)` 换成**轮询**（10s 上限），
     等 `pixel-cat` 真的进入 `downloading`/`installing`。
- **教训**：**模块级全局状态是测试隔离的盲区。** `monkeypatch` 只还原"你显式 patch 过的属性"，
  计数器 / 队列 / 缓存这类全局量必须由 fixture 自己复位。另外**永远不要拿固定 sleep 当同步手段** ——
  它把"慢"翻译成"坏"，而且会把失败留给下一条用例（一次失败放大成一串）。
- **证据**：✅本机实测。修复前 `pytest tests/test_pet_market.py` → `2 failed, 20 passed`；
  修复后 → **`22 passed`**（26.67s）。

### 2.28 Windows 下用 `md5sum` 核对文件一致性：68 个文件全部假红（也会假绿）✅（2026-09-18 实测）

- **症状**：核对「源码 vs 安装版副本」是否漂移，逐文件跑
  `md5sum "$src/$b" | cut -d' ' -f1` 与 `md5sum "$dst/$b" | cut -d' ' -f1` 比较，
  结果 **68 个 `.py` 全部报"不一致"** —— 但 `cmp` 说零差异、`stat -c%s` 两边**字节数完全相同**。
  "全部不一致"本身就是不可能的信号（真实漂移不会 100% 覆盖），看到就该怀疑工具而不是文件。
- **根因**：Git Bash / MSYS2 的 coreutils `md5sum` 在**文件名含反斜杠**（Windows 路径）时，
  会在哈希前加一个 `\` 前缀，表示"这个文件名已被转义"：

  ```
  $ md5sum m2_server/common.py
  e6f32025c093741f618c21b6a304e2de *m2_server/common.py          ← 相对路径，无反斜杠，无前缀
  $ md5sum "C:\Users\mouxu\AppData\Local\...\common.py"
  \e6f32025c093741f618c21b6a304e2de *C:\\Users\\mouxu\\...        ← 绝对路径，有前缀
  ```

  哈希本身**完全相同**，是 `cut` 取到的字符串字面不等（`\e6f...` ≠ `e6f...`）→ 逐条误判。
- **危险性（双向，假绿更致命）**：
  - **假红**（本次踩到）：一侧是相对路径、一侧是绝对 Windows 路径 → 把**一致**误报为不一致
    → 白忙一场，甚至可能去"修复"并不存在的漂移（覆盖掉本来是好的文件）。
  - **假绿**（真正危险）：两侧**都用绝对 Windows 路径** → 两边都带 `\` 前缀 → 字面相等
    → **真实的漂移被误报为一致**。这正好会把 §2.29 那类「半新半旧混装」放过去：
    `rvc_live.py` 是新版、`qwen3_tts.py` 是旧版，本该被拦下，却因为比对方式失灵而"验证通过"。
- **对策**：
  1. **核对文件内容一律用 `cmp -s`**（逐字节，靠退出码判断），不要用 `md5sum | cut`：
     ```bash
     if cmp -s "$src/$b" "$dst/$b"; then echo "一致"; else echo "不一致: $b"; fi
     ```
  2. 一定要哈希就加 `--tag`（输出 `MD5 (file) = hash`，不触发转义前缀），或干脆用
     Python `filecmp.cmp(a, b, shallow=False)` / `hashlib` —— **不受 shell 路径形态影响**。
  3. 别用 `diff -rq --include="*.py"` 这类带过滤的对比（见 §2.30），过滤规则会漏文件。
- **证据**：✅本机实测（2026-09-18）。
  `md5sum` 两侧输出仅差一个 `\`；`cmp -s ...; echo $?` → **`0`**；
  改用 `cmp` 全量重跑 → `m2_server` **68/68 一致**、`web_dist` **33/33 一致**、
  `tools` **55/55 一致**、`pet` **4/4 一致**，零漂移。

### 2.30 `diff -rq --include` 给出「零差异」假象 ✅（2026-09-18 实测）

- **症状**：对比源码与安装版副本，跑
  `diff -rq --include="*.py" src dst | grep -v "Only in"` → **输出为空**，
  一度据此判定"两边一致"。

### 2.31 沙箱批量删除守卫让测试假红：同一套件内 39 failed、外 0 failed ✅（2026-09-18 实测）

- **症状**：同一份代码、同一条命令，在受限执行环境（沙箱）里跑全量套件得到

  → 这是**环境假红**，不是代码坏了。第一回合首次跑往往还是干净的，更具迷惑性。
- **识别特征**（四条里中一条就该怀疑是环境）：
  1. 报错里出现 `[safe-delete]` / `SAFE_DELETE_BULK_CONFIRM_REQUIRED`；

  3. **每次失败的用例都不一样**（1 个 / 5 个 / 16 个随机）—— 因为计数累积、阈值是滚动的；
  4. 同一命令在别处跑是绿的（单文件跑全绿）。
- **对策（按推荐顺序）**：

  1. **最直接：关掉那个 shim** —— 跑测试/构建前设 `CODEBUDDY_SAFE_DELETE_ENABLED=0`

     ```bash
     CODEBUDDY_SAFE_DELETE_ENABLED=0 .venv/Scripts/python.exe -m pytest m2_server -q
     ```

     实测：加它之后全量 **905 passed / 0 failed**；同一命令不加则是随机假红。
     ⚠️ 它只作用于该子进程；用户终端 / CI 上这个变量本就不存在，设了也无副作用。

  2. **走项目自检脚本**（**日常推荐这条**）：`tools/check.py` 已自动给 pytest

     ```bash
     .venv/Scripts/python.exe tools/check.py               # 全量（与 CI 同一条命令）
     .venv/Scripts/python.exe tools/check.py --ci-fidelity # 再复刻 CI 干净 venv + 裸 runner
     ```

- **⚠️ 这个坑 2026-09-06 就记录过**（`.workbuddy-ai/memory/2026-09-06.md` 有专门一节），
  2026-09-18 还是又踩了一次（当时只想到"换个环境跑"，没想到关 shim）。
  **知识记在 memory 里 ≠ 会被检索到** —— 所以这次把解法**固化进 `tools/check.py`**
  （自动设变量），让它不再依赖"人记得"。
- **证据**：✅本机实测（2026-09-18）。沙箱内 39 failed；沙箱外同一命令

### 2.33 系统命令子进程解码失败 → `stdout` 变 `None`（不是抛异常）✅（2026-09-18 实测）

- **症状**（两条线索，都指向同一根因）：
  1. 测试全绿，但 `warnings summary` 里有 `PytestUnhandledThreadExceptionWarning:
     UnicodeDecodeError: 'utf-8' codec can't decode byte 0xbb in position 2`；
  2. 日志里出现 `AttributeError: 'NoneType' object has no attribute 'splitlines'`，
     或端口/进程枚举**静默返回空**（`_pids_on_port()` → `[]`）。
- **根因**：Windows 系统命令（`netstat`、进程枚举脚本等）的输出编码是
  **控制台代码页**（中文 Windows = GBK），**不受 `PYTHONUTF8` 影响**；
  而 `subprocess.run(..., text=True)` 默认按 `locale.getpreferredencoding()` 解码。
  实测对照（同一台机器、同一条 netstat 命令）：

  | 环境 | `getpreferredencoding()` | 结果 |
  |---|---|---|
  | 生产（`backend.cjs` 只设 `PYTHONIOENCODING=utf-8`） | `cp936` | ✅ 正常，136 行 |
  | `PYTHONUTF8=1` | `utf-8` | ❌ 解码失败，`stdout is None` |

  中文 netstat 的表头「活动连接」= GBK `BB EE`，而输出开头是 `\r\n`（2 字节），
  于是**第 3 个字节正是 `0xBB`** —— 就是报错里的 `byte 0xbb in position 2`。
- **最关键的一点（最容易漏）**：`text=True` 的解码发生在 **reader 子线程**里。
  解码失败时，**主线程不会收到异常**，而是拿到 `stdout = None`：

  ```python
  out = subprocess.run([...], capture_output=True, text=True).stdout  # → None，不抛
  for line in out.splitlines():        # → AttributeError（被外层 except 吞掉）
  ```

  所以真实故障表现是"**静默返回空**"，而不是"报错"。
- **影响面（本次实测到的）**：
  - `qwen3_tts._pids_on_port()` 返回空 → `shutdown_worker()` 回收不了端口上的
    遗留 worker → **~4.8GB 显存泄漏**（与端口 8001 上那个遗留进程吻合）；
  - `rvc_common` 的通用进程枚举、`finetune._find_train_pid` 静默返回空 →
    进程存活判断失效。

  ```python
                       timeout=10, creationflags=_NO_WINDOW).stdout or ""
  ```

- **识别特征**：报错里 `position` 很小且字节是 `0xBB` / `0xD1` / `0xC9` 这类
  **GBK 首字节**；或"枚举类函数莫名返回空"。

- **证据**：✅本机实测（2026-09-18，commit `195d9ef`）。修 4 处

### 2.35 electron-builder 无视 `files` 白名单：前端库在 asar 里存了第二份（占 37.4MB）✅（2026-09-19 实测）

- **症状**：安装包比预期肥。拆开 `app.asar`（47.1MB / 5305 个条目）：
  **5236 个条目在 `node_modules` 下，共 37.4MB** —— lucide-react 19MB、react-dom 7MB、
  `@fontsource/*` 6.2MB、@remix-run 2.5MB…… 而 `dist/`（真正的界面）只有 3.7MB。
- **根因**：`web/package.json` 把这 13 个包写在 `dependencies` 里。
  electron-builder 会把 **`dependencies` 整棵树**拷进 `resources/app.asar`，
  **`files` 白名单管不住它**（`files: ["dist/**/*", "electron/**/*"]` 写了也白写）。
  而这些包 vite 早已打进 `dist/assets/*.js` → **同一份代码在包里存两遍**。
  更能说明问题的是：`web/electron/**/*.cjs` 对第三方包的 require 数是 **0**
  （只有 `fs`/`path`/`child_process`/`os`/`net`/`url` 和 `electron` 自身）。
  连当时列在 `dependencies` 的 `electron-log` / `electron-store` 也是全仓无人引用。
- **对策**：`build.files` 里加一条 **`"!node_modules/**/*"`**。
  实测有效：asar 6.74MB / 71 条目，安装包 93.4MB。
  （electron-builder 的 `files` 默认只是"加/减"而不是白名单，所以这条 `!` 能生效。）
- **⚠️ 那条排除是"一刀切"的，有前提**：`files` 里的正向白名单拦不住
  `dependencies` 那棵树，所以排除只能整棵排；**前提是主进程不 require 任何第三方包**
  （目前确实为 0）。主进程真要引包时，必须把排除改成白名单（只放行那个包），
  否则安装版运行期 `MODULE_NOT_FOUND`。
  门禁：`m2_server/tests/test_desktop_packaging.py` 同时钉住"排除存在"与
  "主进程 require 第三方包数为 0"这一对。
- **❌ 试过但被否决的替代方案：把 13 个前端库全挪进 `devDependencies`。**
  效果完全一样（asar 同为 6.74MB），但会让许可门禁当场变红：
  `tools/audit_licenses.py` 的登记口径只看 `dependencies`（它的注释写着
  "devDependencies 不进发行物，不登记"），而 `@fontsource/*` 的 woff2
  **真的随 `dist/assets/` 发出去** → 一挪就报"载荷里的字体已不是声明依赖（残留）"，
  等于**把 OFL 署名义务漏掉**（而许可是事后补不回来的）。
  → **教训：依赖写在哪个分区是 npm 语义，什么进发行物是打包器的事，两者不该混为一谈。**
  用 `files` 排除就只改打包行为，`dependencies` 保持语义正确，许可登记口径不受影响。
- **实测收益**：app.asar **47.1MB → 6.74MB**（-85.7%），
  安装包 **101.5MB → 93.4MB**（-8.0%）。
  注意后者的比例：40MB 的 asar 只换来 8MB 安装包 —— 因为 **安装包的七成是 Electron 本体**，
  指望"少放源码"瘦身是幻觉（详见 `docs/插件化设计.md` §1）。
- **怎么快速自检**：`node_modules/.bin/asar list <app.asar> | wc -l`
  （会变的只有几十条，不是几千条）；或 `npm ls --omit=dev` 看生产树里到底有什么。
- **证据**：✅本机实测（2026-09-19，`web/package.json` + 三次 `electron-builder --dir`／
  `--win` 对照，路径 `D:/tmp/probe2`）。已进 `tools/test-packaging.cjs` 门禁（14 个脚本全绿）。

### 2.38 缺一个**可选**依赖 → 整个后端起不来（26 处模块级 import）✅（2026-09-19 实测）

- **症状**：用户装好包、点开应用，**只看到一个空界面**。
  日志里只有一行 `RuntimeError` / `ImportError`，看起来像「代码写错了」——
  于是人会去改源码（而源码其实是对的）。
- **根因**：`m2_server/server.py` 的 26 处路由注册写成了**模块级**导入：
  ```python
  from seed_vc import router as seedvc_router   # 这一行失败，整个 server.py 就不存在了
  ```
  Python 的模块级 `import` 没有任何隔离：任何一处抛异常，模块加载失败，**后续一行都不执行**。
  而这些模块的「重」是设计上就承认的（TTS 4.9G 权重 / 实时变声要 RVC 整合包+虚拟声卡 /
  微信发送要微信 PC 版）—— **用户没装其中任一项都是正常状态**，不该表现为「软件打不开」。
- **实测对照**（用一个假装是 `seed_vc` 的坏模块抢占 `sys.path`，子进程里 `import server`）：

  | | returncode | 输出 |
  |---|---|---|
  | 改写前 | **1** | `RuntimeError: 模拟：这台机器没装 Seed-VC 的依赖` |
  | 改写后 | **0** | `路由模块 25/26 个已加载` + `不可用: seed_vc —— RuntimeError: …` |

- **对策**：`m2_server/plugin_loader.py` 容错加载（失败只记一笔）+ `server.py` 的
  `_register(...)` 表驱动。两个细节：
  - 记账粒度是 **(模块, 用途)** 而不是模块 —— `audio_api` 既提供 router 又提供启动钩子，
    共用一个 key 的话 router 成功会把钩子失败静静盖掉；
  - 只吞 `Exception`，**不吞** `BaseException` —— 后者会让启动期的 Ctrl+C 失灵。
- **⚠️ 容错最大的风险是变成「静默」**：所以启动时必须 print 出
  「已加载 N/M + 逐条失败原因」（见 §2.36 同类教训）。否则「崩溃」只是换成了
  「这个功能静悄悄地不能用」，反而更难查。
- **⚠️ 新引入的风险要盯住**：启动钩子从 `from x import y` 改成了字符串
  `("x", "y")`，**拼错不再报错，只会静默不生效** —— 每个钩子必须有
  一条把名字钉在真属性上的用例（`_start_audio_audit` 这类私有名尤其容易写错）。
- **另一个别动的约束**：注册**顺序**是行为。FastAPI 按注册顺序匹配路由，
  重排会让重叠路径换一个 handler 接 —— 所以顺序被用例逐字冻结，
  要改先读 `server.py` 里 `_register` 上方那段注释。
- **普适教训**：**可选能力的加载不能写在模块级 import 里**。
  只要一个依赖是「用户可能没装」的，它就必须走容错入口，
  而不是让整张导入表的失败粒度 = 整个进程。
- **证据**：✅本机实测（2026-09-19）。门禁：`m2_server/tests/test_plugin_loader.py`
  13 条（含子进程端到端毒模块对照、顺序冻结、钩子名拼写）。

### 2.40 签名失败 ≠ 「你没设密码」：先问「这份证书对**目标机器**算不算可信」✅（2026-09-20 实测）

- **症状**：`npm run electron:build` 最后一步失败，日志末尾是
  `SignTool Error: The specified PFX password is not correct.`。
  很自然（也很错）的结论是「你没设 pfx 密码 → 去把密码设好才能打包」，
  于是把问题推给用户 —— **本轮我就这么误判了一次**，还据此让用户「自己设密码跑发版」。
- **真相三条**：
  1. **报错那行命令里根本没有 `/p`**：
     `signtool.exe sign /t http://timestamp.digicert.com /f ../certs/black-seraph.pfx /d 变声工坊 /debug …`
     → 不是「密码错」，是「**没传密码**」。后果取决于 pfx 本身：空密码的能开，非空的开不了。
  2. **判定只需一条只读命令**：`openssl pkcs12 -in certs/black-seraph.pfx -nokeys -passin pass: -noout`
     → 报 `Mac verify error: invalid password?`，说明这个 pfx **有**密码。**别猜，量一下。**
  3. **密码不一定是「用户设过」的**。本例它在**未被 git 跟踪**的 `scripts/vm-test.config.ps1`
     的 `$CertPassword` 里（`.gitignore:139` 忽略它）：当初生成证书的脚本从环境变量取值，
     值只活在那个本地配置里。**先去找 ignored 的本地配置，别先去找人。**
- **更该先问的问题（本例真正的教训）**：**谁需要信任这份签名？**
  `certs/black-seraph.pfx` 是**自签**证书（`CN=VoiceMorph Dev Signing, O=VoiceMorph`），
  `gen-selfsigned-cert.ps1:10,34-48` 只在**本机**把它写进 `CurrentUser\Root` ——
  所以 `Get-AuthenticodeSignature` 只在**本机**返回 `Valid`，**别人机器上仍是「未知发布者」**，SmartScreen 照拦。
  旁证在同一个配置文件里：`$ImportCert=$true` 时会**把证书导入 guest 的 `LocalMachine\Root`**
  才能消除「未知发布者」提示 —— 这正说明**可信性由目标机决定，与「有没有签名」无关**。
  实测三个产物同机状态：`VoiceMorph-Setup-0.2.2.exe` = `Valid`、
  **`VoiceMorph-Setup-0.2.3.exe` = `NotSigned`**（现役发布物就是没签的）、`win-unpacked\变声工坊.exe` = `NotSigned`。
  → **自签阶段的「签 vs 不签」对分发几乎无差**；签名的真实价值是**把链路跑通**，将来换正式证书时平滑。
- **对策**：① 签名失败先 `openssl` 验「这 pfx 到底要不要密码」，别先下结论；
  ② 要密码时先查 ignored 的本地配置（**别向用户索要**，也别把它写进命令行 ——
  `signtool /p <值>` 会留在进程列表与日志里）；
  ③ **决定要不要签之前先回答「谁需要信任它」**，否则会为一个对用户零收益的步骤
  去索要一个机密，还把它逼进对话记录。
- **相关**：正式入口只有 `scripts/release.ps1`（`npm run electron:build` 不带签名前置检查）；
  无密码时用 `-SkipSign`（走 `electron-builder.nosign.cjs`，**不能靠 CLI 覆盖 `certificateFile`**）。
- **证据**：✅本机实测（2026-09-20）：无 `/p` 的 signtool 命令原文、`openssl … pass:` 报 invalid password、
  `Get-AuthenticodeSignature` 三个产物的状态、`gen-selfsigned-cert.ps1` 的 `CurrentUser\Root` 写入。

### 2.41 发版唯一入口被一句**中文 JSON 说明**卡死：PS 5.1 的 `Get-Content` 默认按 ANSI 解码 ✅（2026-09-20 实测）

- **症状**：`scripts/release.ps1` 在 **第 1/7 步（前置检查）** 就死，报
  `ConvertFrom-Json : … ArgumentException`，控制台把整个 `web/package.json` 吐出来。
  **而 JS 侧一切正常**（`JSON.parse`、`npm install`、electron-builder、vite 全部能读它），
  所以任何用 node/npm 做的检查都看不出问题。
- **根因**：**PowerShell 5.1 的 `Get-Content` 对无 BOM 文件按 ANSI(GBK) 解码**。
  本仓 `web/package.json` 是**无 BOM 的 UTF-8**（历史如此，不是谁弄丢的 BOM），
  一旦里面出现中文（`"//"` 说明数组），GBK 双字节会**连带吃掉后面的引号**（如 `AD 22`：
  0x22 是合法 GBK 尾字节）→ JSON 结构当场断掉 → 报的是「无法分析 JSON」，
  **不是「编码不对」** —— 这个错误信息会把排查方向完全带偏。
- **反直觉之处**：同一份文件用 `-Encoding UTF8` 能读过，说明文件本身没坏。
  一条命令即可区分：`(Get-Content $p -Raw | ConvertFrom-Json)` 失败而
  `-Encoding UTF8` 成功 ⇒ 是**读者**的问题，不是**文件**的问题。
- **对策**：① 读**我们自己的 JSON**（`package.json` / `latest.json` / 测试产物）一律
  `Get-Content … -Raw -Encoding UTF8`（本次修 15 处）；HTTP 响应（`$r.Content`）不走这条，不受影响；
  ② 给 `scripts/test-ps1-lint.ps1` 加第 5 条规则（**AST 判定**同一管道里的
  `Get-Content` 是否带 `-Encoding`，附 7 例自检），已用变异测试确认会 FAIL 并点名行号；
  ③ 别把中文改成英文来“修” —— 那是把根因（默认编码）藏起来，下一个人换个文件名还会踩。
- **报应循环**：这句中文说明正是本仓 09-19 为解释「asar 里为何有 37MB 重复依赖」而加的，
  加完当天就把发版入口弄坏了，而**发现它的时机是「真要发版那一刻」**—— 所以
  **改了 `package.json` 就应该顺手 `-DryRun` 一次发版脚本**（前置检查是秒级的）。
- **证据**：✅本机实测（2026-09-20）：默认编码读失败 / `-Encoding UTF8` 读成功（两者同一文件、
  同一时刻）；`scripts/test-ps1-lint.ps1` 变异后 `[FAIL] release.ps1 json read uses -Encoding UTF8 -- L68`。

### 3.8 `EnumProcesses` 在 psapi.dll，不在 kernel32 ✅（2026-09-12）

写 `wechat_proc.list_wechat_processes()` 的 ctypes 兜底时按直觉写了
`ctypes.windll.kernel32.EnumProcesses` → 运行即
`AttributeError: function 'EnumProcesses' not found`。
kernel32 只导出 `K32EnumProcesses`，裸名 `EnumProcesses` 属于 **psapi.dll**。

对策：`ctypes.WinDLL("psapi").EnumProcesses`，失败再退 `kernel32.K32EnumProcesses`；

退路本身报错并把异常抛给调用方，比没有退路更糟。

### 3.9 本机全绿 ≠ 干净环境能跑：缺的是"传递依赖"，不是代码 ✅（2026-09-13）

**症状**：本机 `.venv` 跑 `tools/check.py --no-web` 全绿（576 passed）。按 CI 的方式
建一个**只装 `requirements-dev.txt`** 的干净 venv，同一条命令立刻红：

```

```

**根因**：`Pillow`(PIL) 和 `comtypes` **从未写进任何 requirements 文件**，本机有只是因为它们
是**别的包的传递依赖**——Pillow 来自 gradio/matplotlib/tensorboard，comtypes 来自
pycaw/uiautomation（都是 RVC/训练侧顺手装的，不在 `requirements.txt` 里）。
唯一能看穿这一点的是 `pip show pillow` 的 `Required-by` 一栏。

**后果比 CI 变红严重**：`m2_server/wechat_voice.py` 的 `_grab_gray` / `_find_green_send`
是**主进程内**的截图定位（`from PIL import ImageGrab` 写在函数体里），所以
`python -c "import server"` 干净环境也能成功、启动一切正常 —— **懒加载的 import 骗过了
"能不能启动"这个检查**。新用户按 README 装完依赖，跑到"发送语音"才炸。

**对策**：

1. 判断标准不是"哪里 import"，而是"**哪个进程会执行到这行**"：
   测试 / `tools/` 会碰的 → `requirements-dev.txt`；生产进程会碰的 → `requirements.txt`。
2. 本机验完**必须再用干净 venv 验一次**（CI 复刻，约 3 分钟）。已封装成一条命令：

```bash
python tools/check.py --ci-fidelity     # 改了依赖 / 加了测试之后跑它
python tools/check.py --ci-fidelity --recreate   # 手工装过东西、要零污染时
```

它做的事（手工也能复现，但没必要）：版本号从 `.github/workflows/ci.yml` **读**
（不写死，否则复刻自己会漂移）→ 建/更新 `.venv-ci/`（只装 `requirements-dev.txt`，
依赖指纹没变就跳过 pip install）→ 用它跑 CI 那条 `--no-web` 命令 + `tsc -b`。

输出末尾会诚实列出**没被复刻的差异**（runner 镜像、Linux 大小写、`npm ci` 全新安装、
偶发并发），别把它的绿当成 CI 一定绿 —— 但它的红一定是真红。

3. 别指望传递依赖：上游换实现或降级，你的功能就无声消失。测试路径上的可选依赖
   要么显式声明，要么 `pytest.importorskip` —— 但**不能两头都不做**。

**证据**：`git grep -ln PIL -- m2_server tools` = `wechat_voice.py` + 3 个 `tools/` 脚本 +
1 个测试；`pip show pillow` → `Required-by: gradio, matplotlib, tensorboard`。
另一条旁证：修复后瘦环境装到的是 **Pillow 12.3.0**，而本机 `.venv` 里是 **10.4.0**
（传递依赖钉的旧版）—— 两个环境连依赖版本都不一样，"本机验过"本来就不等于"能跑"。
修复（补声明）后：瘦环境 **573 passed + 3 skipped**、本机 **576 passed**，两边全绿。

**泛化教训**：`import` 写在函数体里（为了懒加载 / 可选降级）会让"启动成功"变成假的安全信号。
CI 的价值不在于它多跑一遍测试，而在于它跑在一个**和你机器不一样的环境**里。

```
ERROR  test_pet_skin_build.py ×4                              - FileNotFoundError
```

**根因**：13 条红**没有一条是代码缺陷**，全部是"开发机有、runner 没有"的外部资源：

| 资源 | 中招用例 | 为什么报错看不出真因 |
|---|---|---|
| ffmpeg | 9 条（5 failed + 4 errors） | `common.find_ffmpeg()` 找不到时会**回落到字面量 `"ffmpeg"`**（生产代码需要这个兜底，好让 PATH 兜底），于是失败发生在 subprocess 里，只报 `[WinError 2]` |
| `D:\RVC\.venv` | 2 条 | `rvc_convert()` 的人话守卫 `raise RvcError("找不到 RVC 运行环境…")` 看着像生产代码坏了，其实是测试没桩掉 |
| kangaroo 微调产物 | 1 条 | 断言直接写"本机必须存在产物"，干净 runner 上必然红 |
| 开发机屏幕 1938×1609 | 1 条 | `_find_green_send` 会把取域 clamp 到屏幕内，而用例没桩屏幕尺寸 —— 断言里的 `1378 + 480` 其实编码的是**开发机分辨率**；runner 是 1024×768 → `box[0]` 从 1378 变 464 → 拿到 953 |

**为什么 `--ci-fidelity` 没拦住**：它只复刻了**依赖集**这一根轴（§3.9 的产物）。
"本机绿 ≠ CI 绿"其实有**两根轴**，轴②（本机资源）它完全看不见 —— 而且它当时是**绿的**，
这比不跑更危险：它给了一个"已经复刻过 CI 了"的错觉。

**对策**（三层，缺一层都拦不住）：

1. **资源探测集中到一处**：`m2_server/conftest.py` 顶部提供 `ffmpeg_bin` 夹具与
   `missing_local()`，缺资源时 **本机 skip（附安装提示）、CI 上 fail**。非对称是刻意的：
   本机缺 = 你没装，跳过即可；CI 缺 = workflow 的环境准备步骤没生效，
   **不许用 skip 把它掩盖成绿**。测试里别再写 `subprocess.run(["ffmpeg", ...])`。
2. **`--ci-fidelity` 加"裸 runner"模拟**（两层）：
   - `VM_BARE_RUNNER=1` → 探测一律判"不存在"，跳过集与 CI 对齐；
   - **从 PATH 摘掉含 ffmpeg 的目录** → 这层才是关键：第 1 层只约束"走了探测"的用例，
     而上面 9 条正是**绕过探测**直接调 ffmpeg 的写法，本机 PATH 上有它就照样绿。
3. **ffmpeg 在 CI 里真装**（`choco install ffmpeg`）。它是运行时依赖（提轨 / pet 皮肤转换 /
   预览生成），把 9 条用例 skip 掉换个绿色等于**整条 pet 链路在 CI 上没人管**。
   注意此时 `--ci-fidelity` 会跳过这些用例（模拟裸机器）、CI 会真跑它们 ——
   **两个绿灯合起来才是真绿**。

**写这个工具时又踩的两个坑**（都值得记住）：

- 验证"PATH 摘掉后 ffmpeg 就没了"时，我在**同一个进程**里 `subprocess.run(["ffmpeg"])`，
  结果**仍然成功**。因为 Windows `CreateProcess` 的搜索路径取的是**调用方进程**的 PATH，
  而不是你传给子进程的那份 `env`。必须在**剥净环境里再起一层进程**才是真实调用链。
- `shutil.which("ffmpeg")` 返回 `None` **不等于** `subprocess.run(["ffmpeg"])` 会失败：
  前者只看 PATH，后者的 Win32 搜索顺序还包含**应用目录**和**当前目录**。

**证据**：`gh run view 34768644638 --log-failed` 全量清单；
`VM_BARE_RUNNER=1 pytest` 本机 **108 passed + 9 skipped**（无一条崩）；
两层验证脚本实测"裸环境里 `subprocess.run(["ffmpeg"])` → `FileNotFoundError`"；
修复后本机全量 **656 passed**（原来 642 条 = 626 + 9 + 3 + 4）。

**泛化教训**：测试一旦依赖"开发机上的某样东西"，它测的就不再是代码。
凡是外部程序 / 绝对路径 / 屏幕尺寸 / 本机模型产物，要么走统一探测并显式跳过，
要么桩掉 —— **别让它以 `[WinError 2]` 的形式在 CI 上出现**，那种报错没人能一眼看出真因。
反过来，"本机绿 ≠ CI 绿"要按**轴**数：依赖集一根，资源一根，环境本身（镜像、大小写、
并发时序）一根。每发现一根，就得有一条机器对策，否则它会以同样的方式再犯一次。

### 3.11 「审计说历史干净」可能是工具自己判错了 ✅（2026-09-14）

**症状**：`python tools/audit_git_history.py` 报 13 处命中，**每一处**都标着 `[仅历史]`，
处置建议是"先清工作区，历史里的需 `git filter-repo` 重写"。可 `git grep` 一查，
工作区里明明还有 **7 个入库文件**带着第三方素材名 —— 结论与事实不符。

**根因**（四个独立的坑凑在一起，把结论带偏了）：

| # | 坑 | 表现 |
|---|---|---|
| 1 | `_tag()` 拿 `head[path] == blob_sha` 判「HEAD 仍含」 | blob sha 是**整份文件**的哈希：文件被重命名、或同一次提交里顺带改了别的行，sha 就变了 —— 而命中的那个片段可能一个字都没动、还挂在 HEAD 上。误报成 `[仅历史]` 的代价是：把"改工作区就能解决"错判成"只有重写历史能清"，要么白改一遍历史，要么让人以为"改了没用"就不改了 |
| 2 | 规则里**根本没有"第三方素材名"这一类** | 工作区里的片名压根不会被报出，于是"工作区已干净"这个判断缺机器守护；被报出来的那 13 处，命中的其实是 `/Users/<用户名>/` 这类**家目录**规则 |
| 3 | 规则源码**命中它自己** | 把来源标记（B 站站名之类）直接写成完整字符串，规则源码就命中了它自己 —— 历史清干净了这道门还是红的，然后大家学会无视它 |
| 4 | 工具扫的是**已提交**内容，工作区的改动它看不见 | 刚改完就复跑，报告还是旧结论（满屏 `[HEAD 仍含]`），差点据此以为"改了没用" |

**对策**：

1. **判定改成内容层面**：先扫一遍 HEAD 的内容建 `{命中片段: [含它的 HEAD 路径]}` 索引，
   片段在 HEAD 里出现过就是「仍含」（并指出在哪个文件），否则才是「仅历史」。
   片段是内容层面的东西，就用内容层面判 —— blob sha 只是个粗粒度的近似。
2. **第三方素材名单列一节**。具体标题**绝不写进仓库**（哪怕只写进那个防泄漏的工具 ——
   那是泄漏源换了个位置、还更隐蔽）：改从**不入库**的 `.audit-materials.txt` 读，
   一行一个子串，按字面匹配（`re.escape`，不是正则 —— 片名里的 `.` `）` 当正则会静默失配）。
3. **规则里的"机械痕迹"也拼出来**（`"哔哩" + "哔"`），同 `test_check_secrets.py` 里
   `_pv()` 那条纪律。
4. **摘要行拆成两类**：`HEAD 仍含 N 处 → 要动的文件：<文件名列表>` 与
   `仅历史 M 处 → 只有 filter-repo 能清`；工作区有未提交改动时额外打一行提示。
5. `--allow-history-only` 的**非对称**语义：只放行"仅历史 **且** 非凭据"，
   凭据类（任何位置）与「HEAD 仍含」（任何类别）都不接受降级 ——
   能降级的东西必须一眼看得出边界，把凭据也一起降级这道门就废了。

**证据**：`m2_server/tests/test_audit_git_history.py`（25 条）。其中
`test_old_sha_equality_judgement_would_have_misjudged` 把老判据写成反例钉住，
`test_tool_source_is_clean_under_its_own_rules` 钉住坑 3，
`test_allow_history_only_is_asymmetric` 钉住那四条边界。

**泛化教训**：**"扫描工具没报" ≠ "没有问题"**。工具给出 `[仅历史]` 这类结论时，
先手工 `grep` 一个反例再信它 —— 尤其是当它的输出会决定"要不要重写 git 历史"这种
**不可逆**动作时，它的判据本身得先被测试钉住。顺带一条：**工具不能命中它自己**，
否则它永远红、然后被人无视，跟没有一样。

### 3.12 `torch.jit.load` 打不开中文路径：C++ `fopen` 的窄字符坑 ✅（2026-09-14）

**症状**：MeanVC2 冒烟推理第 1 步就崩：

```
[1/5] Loading ASR model (JIT)...
RuntimeError: open file failed because of errno 2 on fopen: No such file or directory,
file path: D:\变声\tts_trial\MeanVC2\preprocess/ckpts/fastu2pp_80ms.pt
```

可 Python 侧 `os.path.exists()`、`os.path.getsize()` 都是 **True**，文件确实在
（Glob、`Get-Item` 都能找到；236MB 整）。

**根因**：同一个路径，Python 的文件 API（`torch.load`、`sf.read` 等）走 **宽字符** API，
`D:\变声` 毫无压力；而 `torch.jit.load` 底层是 C++ 的
`import_ir_module` → **窄字符 `fopen`**，非 ASCII 路径直接 `errno 2`。
所以这不是文件缺失，是"**PyTorch 的 JIT 序列化层在 Windows 上不吃中文路径**"。

**对策**：统一走一个 fallback 包装，失败时把权重复制到英文临时目录再 `jit.load`：

```python
def _jit_load_cn(ckpt_path, device):
    try:
        return torch.jit.load(ckpt_path, map_location=device)
    except (OSError, RuntimeError):
        if not os.path.exists(ckpt_path):
            raise                        # 真缺失就别吞错
        tmpdir = tempfile.mkdtemp(prefix="meanvc2_jit_")
        tmp_ckpt = os.path.join(tmpdir, os.path.basename(ckpt_path))
        try:
            shutil.copyfile(ckpt_path, tmp_ckpt)
            return torch.jit.load(tmp_ckpt, map_location=device)
        finally:
            shutil.rmtree(tmpdir, ignore_errors=True)
```

已落在 `tts_trial/MeanVC2/src/infer/infer_e2e.py`（ASR + Vocos 两处 JIT 加载都走它）。
该第三方仓库**不入库**（`.gitignore` 加 `tts_trial/MeanVC2/`，同 Qwen3-TTS / seed_vc 惯例），
补丁只在本机。

**证据**：对照实验 —— 同一 `fastu2pp_80ms.pt`，中文路径 `jit.load` 抛 `RuntimeError`；
复制到 `C:\Users\<你的用户名>\AppData\Local\Temp\` 后加载成功。补丁后完整推理冒烟通过
（BN (86,256)、SpkEmb (256,)，1 步 VC 出 3.4s 音频，`smoke_out.wav`）。

**可信度**：`✅本机实测`（torch 2.8.0+cu129 / Windows 11）。±：`torch.load` 走 Python
IO 层，不在本坑范围内 —— 只有 JIT 序列化（`torch.jit.load`）和原生库直读受影响。

### 3.13 本项目 x-vector 的 SECS 量程塌缩：单看相似度必误判 ✅（2026-09-14）

**症状**：做 MeanVC2 vs RVC 客观对比时，用项目自己的
`POST /emb`（`m2_server/qwen3_tts_service.py` 的 Qwen3-TTS x-vector）算 SECS，
结果"没转换的源音频"拿到 **0.964**，转换后的 MeanVC2 反而是 **0.954–0.960** ——
看起来"越转换越不像"，纯属荒谬。

**根因**：这个说话人向量的**余弦相似度量程被压缩**了。本轮实测动态范围只有约
**0.04**（底噪 0.964 → 参考音 1.000），而正常 ECAPA/x-vector 在同一说话人 vs
不同说话人之间通常拉开 0.2–0.5。量程一旦塌缩：
- 区分度低于数值噪声，排序基本随机；
- "未转换底噪"本身就很高，任何转换都难"跑赢"它。

**对策**：**判音色相似度必须配谱包络指标**，本项目用 **LTAS**（Long-Time Average
Spectrum，长时平均对数谱）互相关 —— 它对"是否朝目标音色的频谱包络靠拢"直接敏感，
且与具体模型无关。再加 **F0 统计**（YIN 中位 + 浊音比）看音高迁移是否到位。

本轮同一批音频的三方对照（同源同目标同条件）：

| 音频 | SECS | LTAS | F0中位 |
|---|---|---|---|
| 源音 未转换 | 0.964 | 0.866 | 125.0 |
| RVC kangaroo_v2 | 0.981 | **0.958** | 112.1 |
| MeanVC2 120ms | 0.954 | 0.936 | 119.2 |

→ LTAS 排序（RVC 0.958 > MeanVC2 0.936 > 未转换 0.866）**才是真相**；
SECS 排序（未转换 0.964 > MeanVC2 0.954）是假象。
F0 也在讲同一个故事：RVC 把 125→112 拉向目标，MeanVC2 只动 ~6Hz。

**推论（可复用）**：以后任何"音色像不像"的客观评测，**必须至少两轴**
（谱包络 + 音高），且**先跑一遍"未转换"做底噪基线** —— 底噪离 1.000 太近
（<0.05）就说明这个 embedding 在本任务上不可用作唯一判据。

**可信度**：`✅本机实测`（2026-09-14，`D:\meanvc2_exp\ab_metrics2.py`）。
±：量程塌缩是本项目 **Qwen3-TTS x-vector** 的特性，不代表 ECAPA 等标准 x-vector
也如此；换 embedding 前先重测底噪。

### 3.14 JIT 模型搬到别的设备会崩：trace 时冻结的常量不跟着 `map_location` 走 ✅（2026-09-14）

**症状**：把 MeanVC2 的 Fast-U2++ ASR 从 CPU 挪到 CUDA（`torch.jit.load(ckpt, map_location="cuda")`
+ 把输入/cache 一起 `.to("cuda")`，看起来该搬的都搬了），前向直接炸：

```
RuntimeError: The following operation failed in the TorchScript interpreter.
...
  p = torch.view((linear_pos).forward1(argument_3, ), ...)
RuntimeError: Expected all tensors to be on the same device,
but got mat2 is on cuda:0, different from other tensors on cpu
```

诡异点：报的是 **weight 在 cuda、input 在 cpu**，可我明明把 input 搬过去了。

**根因**：`map_location` 只负责搬 **注册的 `parameter` / `buffer`**。而 trace 时如果某个张量
被当成**常量冻结进图**（典型是位置编码、正弦表、`torch.zeros` 预建的 cache 之类的中间量），
它就**不随 `map_location` 搬家**，永远停在 trace 时的设备上。
于是权重到了 CUDA、那个常量还赖在 CPU → 设备不匹配。

**一眼识别**：看 torch 给的 "TorchScript, original code" 路径里的**环境名**：

```
D:\miniconda\envs\meanvc_cpu\Lib\site-packages\...   ← CPU-only 环境 trace 的，别想上卡
/home/xxx/miniconda3/envs/allin/...                  ← Linux 环境 trace 的
```

路径里出现 `cpu` / `allin` 这类痕迹，基本就可以判定**该 JIT 产物锁死在 trace 环境**，
不是改几行 `.to()` 能解决的。本项目 Vocos 也是 Linux 环境 trace 的，但它恰好**没有**被冻结的
常量张量，所以能上 CUDA —— **所以不能只看 trace 环境就一刀切，要实跑验证**。

**对策**：

1. **优先保持原设备**。MeanVC2 官方把 ASR 写死 `"cpu"` 就是这个原因，而它 CPU 上
   warm RTF 仅 0.062，本来就不是瓶颈。
2. 确实要跨设备，只有两条路：**重新 trace/导出**（需要原始训练代码），或
   **在 JIT 里定位并显式注册那些常量**（把常量改成 `register_buffer` 再重导出）。
3. **别浪费时间调 `.to()`** —— 症状会一直复现，而且报错位置（哪个算子）每次都不同，很误导。

**顺带**：同一轮里 `vocos.decode() on cuda` 也报过一次设备错误，但那次是**我自己的脚本 bug**
（CPU 轮次把 CPU 上的 mel 喂给了加载在 CUDA 的 vocos）。**跨设备基准脚本必须给每个 device
各加载一份模型**，别复用同实例。

**可信度**：`✅本机实测`（torch 2.8.0+cu129 / RTX 5060 / Windows 11）。
±：这是 TorchScript trace 的固有语义，不限 MeanVC2；ONNX / TensorRT 的导出有类似性质的
"常量烘进图"问题。

### 3.15 性能/资源测量的四个陷阱（本轮连踩，全是"数字看起来对但其实错"）✅（2026-09-14）

做 CPU/显存/RAM 三轴资源账时，**连续四次拿到假数字**。整理成通用清单：

**① 平均值被冷启动污染（与测 JIT 模型同源）**

RVC 稳态单次转换 0.27s，但首轮 **19.6–20.9s**（pipeline 构建 / CUDA 图捕获）。
10 次取平均得 2.42s，"看起来像是 9 倍退化"，实际是第 1 次把平均值拉飞了。
**对策**：先跑 2 次 discard 再统计；**任何"每次调用"的基准，先确认首轮是否含一次性初始化**。

**② 子进程 CPU 时间必须统计「进程树」，否则会得出物理上不可能的结论**

第一版只量 worker 进程，得出「等效 14.41 核」——而该进程只有 **1 个线程**，
单进程不可能用 14 核。真相：worker 是个 1 线程转发壳，真正推理在
**119 线程的子进程**里。**对策**：`psutil.Process.children(recursive=True)` 一并累加；
**结论违反物理上限（核数 > 线程数）时，一定是测量对象错了，不是机器神奇。**

**③ RAM 要区分「加载瞬时峰值」与「稳态驻留」**

MeanVC2 加载时 RSS 峰值 **3617MB**，稳态只有 **2285MB**（差 1.3GB）。
差额来自 WavLM-Large 的 1.2GB checkpoint 字典 + 模型实例的临时副本。
**报峰值会把成本夸大 58%**。**对策**：稳态要在"全部加载完 + 跑过一轮推理"之后取，
且至少稳定采样 3 轮。另外**进程内读 RSS 别手搓 ctypes 结构**（`PROCESS_MEMORY_COUNTERS`
对齐/字段易错，本轮得到 0MB 和 6MB 两个假值）——**用父进程 psutil 轮询子进程最可靠**。

**④ 别手写复刻上游的推理函数**

为了"逐块计时"自己复刻了一份 `vc_inference`，结果在
`apply_rotary_pos_emb` 报 `size of tensor a (28) must match b (16)` ——
kv_cache 的 `offset` / 切片语义抄错了。**对策**：计时就用 `time.perf_counter()`
包住上游原函数；真要逐块计时，改上游加钩子也不要重写。
**"为了测量而重写被测对象"是本末倒置，测出来的也不代表原件。**

**可信度**：`✅本机实测`（2026-09-14，`D:\meanvc2_exp` 下的 `rt_bench*.py` /
`rvc_cpu_cost*.py` / `mem_probe*.py`）。

### 3.15b Node 测试写了、看着也"能跑"，但从来没在自检里跑过 ✅（2026-09-14）
<!-- 编号修正 2026-09-17：本节原也写成 3.15，与上一节重号；改为 3.15b 以免后续编号整体位移。 -->

**症状**：`tools/` 下 4 个 `test-*.cjs`（`test-model-setup` / `test-setup-ipc` /
`test-updater` / `test-update-hook`）只靠人工敲 `node tools/test-xxx.cjs`，
`tools/check.py` 里没有任何一步会执行它们，CI 更不会。于是 `test-setup-ipc.cjs`
里 **3 条用例长期红着**，一直没人知道 —— 直到本轮改动了它依赖的
`runFirstRunGuide` 才暴露。

**根因**：这些脚本开头写的是
`require.resolve("electron", { paths: [webRoot] })`，**要求 `web/node_modules`
真实存在**。而 CI 的 backend job（windows-latest）**从不 `npm install`**，
所以就算把它们接进 `check.py`，在 CI 上也会 `MODULE_NOT_FOUND` 直接挂。
**"跑不了"和"没跑"互相掩护**：因为跑不了，所以没人接；因为没人接，所以没人发现跑不了。

**对策**：抽 `tools/electron-stub.cjs`，用 `Module._resolveFilename` 把
`require("electron")` 重定向到一个**不落盘的合成 id**，彻底不依赖 `web/node_modules`：

```js
const STUB_ID = "__vm_electron_stub__";
const orig = Module._resolveFilename;
Module._resolveFilename = function (request, ...rest) {
  if (request === "electron") return STUB_ID;   // 返回合成 id，不查磁盘
  return orig.call(this, request, ...rest);
};
require.cache[STUB_ID] = { id: STUB_ID, filename: STUB_ID, loaded: true, exports: stub };
```

（关键点：`_resolveFilename` 的返回值**不需要是个真实路径**，只要 `require.cache`
里有同 key 的条目即可命中缓存。写 `<stub>.cjs` 临时文件反而会污染仓库。）

然后在 `tools/check.py` 加 `nodetest` 步：glob `tools/test-*.cjs` 逐个 `node` 执行。
注意 `test-check-require.cjs` / `test-electron-load.cjs` **由别的步骤负责，
必须从 glob 里排除**，否则重复跑。

**证据**：接入后 `nodetest` = 7 个脚本全绿；`test-setup-ipc.cjs` 27 条通过
（改前 14 通过 / 3 失败，那 3 条从未被任何入口判定过）。
**可信度**：`✅本机实测`。
**推论（通用）**：**"测试文件存在" ≠ "测试在跑"**。新增测试文件时，
必须同时确认它被某个自动化入口 glob 到 —— 否则它只是一份文档。

#### 3.15 后续：接进门禁 ≠ 门禁就绿 —— "本机绿 ≠ CI 绿"的**第三根轴** ✅（2026-09-14 同日）

把 `nodetest` 接进 `check.py` 后本机七步全绿、`--ci-fidelity` 也绿，
**CI 却当场红**：`[FAIL] nodetest 2/7 个失败：test-model-scan.cjs, smoke-loadpath.cjs`
（run `34855104217`），报错都是 `Cannot find module 'electron'`。

**根因**：`--ci-fidelity` 只复刻了两件事（依赖集 + 缺本机资源），
**没有复刻"缺 npm 依赖"**。而 CI 的 backend job（windows-latest）**从不 `npm install`**。
所以凡是脚本里还有一处 `require("electron")` / `require.resolve("electron")`，
本机（有 `web/node_modules`）必绿、CI 必红：

- `web/electron/smoke-loadpath.cjs` 用 `require.cache[require.resolve("electron")]` 顶桩
- `tools/test-model-scan.cjs` 在一条用例里 `require("setup-ipc.cjs")`，而后者顶层 require electron

**第三根轴**（补进"本机绿 ≠ CI 绿"那张表）：① 依赖集 ② 本机资源 ③ **npm 依赖是否被需要**。

**对策（两层）**：

1. **改代码** —— 桩的实现搬到 `web/electron/electron-stub.cjs`（与受测模块同目录，
   且 `web/electron/**` 会进 app.asar，路径在打包后依然有效）；`tools/electron-stub.cjs`
   退化成薄转发。全部入口脚本改用 `installElectronStub()`。
2. **加静态守卫** —— `check.py` 的 `_check_node_tests` 在跑每个入口脚本前，先用
   `_stray_electron_requires()` 扫一行级正则
   `require(?:\.resolve)?\s*\(\s*['"]electron['"]`（跳过注释行）。命中即硬失败。
   **理由：本机总有 node_modules，动态跑永远发现不了，只能静态拦。**

**怎么在本机验证"没 npm 依赖"也能跑**（关键手法）：CI 没装的不是 ffmpeg，
是 `web/node_modules`，而 node 的解析是**从脚本目录向上找 `node_modules`**，
没有开关能关掉。唯一诚实的复刻是**把目录挪走再挪回来**：

```bash
mv web/node_modules web/__nm_hidden_ci_sim__ ; \
  node tools/test-model-scan.cjs ; node web/electron/smoke-loadpath.cjs ; \
  mv web/__nm_hidden_ci_sim__ web/node_modules
```

（同一分区内的 `mv` 是 O(1) 改名，不动数据；用 `;` 而非 `&&` 保证一定还原。
实测 6 个脚本全 OK，这就是 CI 的等价条件。）

**证据**：挪走 `web/node_modules` 后 6 个脚本全 OK；静态守卫对 7 个入口脚本零误报，
对 `require("electron")` / `require.resolve("electron")` 合成反例命中、对纯注释不命中。
**可信度**：`✅本机实测`（含 CI run `34855104217` 的真实红）。
**推论（通用）**：**"本机绿"要问清是绿的哪一根轴**。给门禁加新步骤时，
先问一句"CI 那个 job 里，这个步骤需要的东西都在吗？"—— 尤其是
**npm 依赖、系统命令、外部目录**这三类 CI 与本地不对等的东西。

### 3.17 "变声器不被反作弊封号" ≠ "本项目安全"：把舆论结论套到自己头上 ✅（2026-09-14）

**问法**：用户问"游戏里用变声器会不会被反作弊搞"。网上搜到的结论清一色是
"没事，变声器不封号"。

**坑**：这个结论**对"用户态变声器"成立，对本项目不成立**——而舆论几乎
不区分这两者（写博客的是卖软件的人，他们的产品恰好都是用户态的）。

**拆开看，这是两个完全独立的问题**：

| 问题 | 结局 | 判据 |
|---|---|---|
| **会不会被封号** | ❌ 不会 | 只有**注入游戏进程 / 改内存 / 给竞技优势**才封 |
| **会不会被拒绝启动** | ⚠️ 可能（VAN148） | 装了反作弊**不信任的内核驱动（.sys）** |

**根因**：反作弊（如 Vanguard）是**内核级**的，它扫的是内核驱动加载、
游戏内存完整性。**"变声器不被封号"的真正理由是"用户态软件碰不到内核"**——
可本项目末端用的 **VB-CABLE 恰好是内核驱动**（要当虚拟麦克风就必须是）。
所以本项目落在**第二个问题（启动）的风险面**上，而不是第一个（封号）的安全面。

**证据**：
- Riot 官方支持页（`support.riotgames.com/.../error-van-incompatible-software`）：
  "VAN: Incompatible Software" = 检测到不兼容的 `.sys`，**阻止启动**、弹窗直接列出文件名。
- 官方/社区公布的常见被点名文件（`ene.sys`/`rtcore64.sys`/`inpoutx64.sys`/`AsIO.sys`…）
  **全是 RGB / 超频 / 监控 / 主板工具，无一为音频驱动**。
- 厂商博客（`voxbooster`，**有立场**）承认 VB-CABLE 的内核驱动**曾被 Vanguard 1.x 标记**，
  导致无法启动，**后续 Vanguard 更新已修复**。
- 结论定级：✅ 一手（机制 = 启动拦截、非封号）；⚠️ 二手（VB-CABLE 曾被标记）；
  ❓ 未证实（当前版本共存性）。
**可信度**：机制 `✅一手（Riot 官方）`；VB-CABLE 具体指控 `📚二手/利益相关`；
当前版本共存 `❓未验证`。

**对策（写进 §2.4 的四条）**：

1. **换 VC 模型不解决这个问题**——暴露点是 VB-CABLE，不是 RVC / MeanVC2。
2. **风险等级 = 可逆**（开不了游戏 → 卸 CABLE → 恢复），**与账号无关**。
3. 真要上 PC 游戏场景，**在一台装了目标游戏的机器上实测一次"装 CABLE 后能否启动"**
   即可（10 分钟），不必提前决策。
4. 备选：Voicemeeter（同为内核驱动，同一风险面）、外接 USB 声卡物理环路、
   或**只在不开反作弊游戏时启用 CABLE**。

**推论（通用）**：**引用"某类工具安全"的结论前，先确认自己的实现落在同一类里。**
"用户态安全"这个前提，一个内核态依赖就打破了——而项目往往把这依赖当基础设施，
不会主动想起来它也是"驱动"。

### 3.18 同一文件并行两处编辑，其中一处会静默丢失 ✅（2026-09-14）

**现象**：给 `scripts/release.ps1` 加 `-SkipSign` 开关，一条消息里发了两处编辑
（文件头用法注释 + `param()` 里加 `[switch]$SkipSign`）。**两处都返回"编辑成功"。**
提交后跑脚本，`-SkipSign` 完全没效果，仍旧走签名分支。

**根因**：两处编辑**各自读了一份原文件、各自整体写回** —— 后写的覆盖先写的。
注释那处生效了，`param()` 那处丢了。声明没了 → `$SkipSign` 成了未定义变量 →
`if ($SkipSign)` 恒为 `$null`（假）→ **静默走 else 分支**。

**为什么特别难发现**：

- 工具报"成功"（它确实写成功了，只是写的是旧快照）。
- 语法完全合法：PS 不要求变量先声明，`ps1lint` 全绿、token 数也对得上。
- 脚本**照常运行**，只是走了错分支 —— 无报错、无警告。

**发现方式**：改完用 `(Get-Command <脚本>).Parameters.Keys` 列出脚本**实际声明**的参数，
才看到 `SkipSign` 不在里面。（`grep '\[switch\]'` 等效。）

**对策**：

1. **同一文件的多处修改串行发**，不要放在一条消息里并行。
2. 改完要验证"**确实改了**"，而不是"工具说改了" —— 参数看声明列表，逻辑看 grep 命中。
3. **"声明 + 使用分离"的结构是静默失败高发区**：声明漏了，使用处只变成 `$null`
   （PS）/ `undefined`（JS），一路无痛跑到底。

**推论（通用）**：任何"匹配 old_string 再整文件写回"的编辑，都在一个读-写窗口里工作；
同文件并行编辑 = 竞态。这类竞态**不报错，只丢改动** —— 而且丢的往往是"声明"、
留下的往往是"使用"，组合起来正好是一个能跑但行为不对的程序。

### 3.19 读/建 Windows 快捷方式：COM 被拦 + `.lnk` 双编码假象 ✅（2026-09-15）

**现象**：要确认桌面「变声工坊」快捷方式指向哪份安装，用官方姿势读：

```powershell
(New-Object -ComObject WScript.Shell).CreateShortcut("$env:USERPROFILE\Desktop\变声工坊.lnk").TargetPath
```

被安全策略直接拦：*"COM object instantiation can run arbitrary code"*。
**读**和**建**都被拦 —— `CreateShortcut(...).Save()` 同样走不通。

**备选路线也全废**（都是"看起来能绕、实际绕不过"）：

| 路线 | 失败原因 |
|---|---|
| 符号链接 | 需要管理员权限 |
| 硬链接 | 需要同盘（目标在 C:，构建产物在 D:） |
| `Start-Process` 拉起 | 只能启动，改不了已有 `.lnk` |

**第二个坑（更隐蔽）**：退而求其次去 grep `.lnk` 的字节找路径，得到的是**假象**：

```
C:\Users\<user>\AppData\Local\Programs\voice-morph-desktop\
.exe                      ← 看起来像"目标缺文件名"
```

真实目标是 `...\voice-morph-desktop\变声工坊.exe`。**根因**：`.lnk` 里
`LinkInfo.LocalBasePath` 用**系统 ANSI 代码页**存（简中 = GBK），
`变声工坊.exe` 的 GBK 字节是 `B1E4 C9F9 B9A4 B7BB 2E657865` ——
只有尾部 `.exe` 落在可打印 ASCII 区，中文名部分对 `[\x20-\x7e]` 完全不可见。
**grep 出来的"目录 + .exe"不是截断，是编码盲区。**

**第三个坑**：**不能把整个 `.lnk` 当单一编码解码**。同一个目标路径在文件里
**同时存在两份**：ANSI 的 `LocalBasePath`（`LinkInfo` 段）和 UTF-16 的
`LinkTargetIDList`。按 UTF-16 整体解会得到一堆乱码汉字，按 ASCII 整体解会漏掉中文名。

**对策**：

1. **读**：按 [MS-SHLLINK](https://learn.microsoft.com/openspecs/windows_protocols/ms-shllink/)
   结构解析字节，只读、无副作用、不需要权限。已落地为
   `tools/check-shortcuts.py`（`python tools/check-shortcuts.py`，退出码 0/1 可直接进自检）：
   读 Header 的 `LinkFlags` → 按 `HasLinkTargetIDList` 跳 IDList → 取
   `LinkInfo.LocalBasePath`（`bytes.decode("mbcs")`）+ `CommonPathSuffix`。
2. **建**：既然建不了 `.lnk`，就别建。**用新版安装器覆盖安装** ——
   安装器会自己重建正确的快捷方式，顺带修好注册表版本号与已安装代码，
   一次动作解决"快捷方式指错 + 已安装版本过期"两件事。
   覆盖安装前必须确认 `deleteAppDataOnUninstall: false`（本项目已是），
   否则 `%APPDATA%\<app>` 里的 `config.json` / `pet.json` 会被清掉。
   静默参数 `/S`，退出码 0 **不等于装完**（NSIS 会先返回、子进程继续），
   必须**回读产物指纹**验证，别信退出码。

**推论（通用）**：**"读不出来"时先怀疑编码，再怀疑权限。** 混合编码容器
（`.lnk` / Windows 注册表 `REG_EXPAND_SZ` / Office 二进制格式）里，
"按单一编码 grep"得到的干净结果，往往正是最误导人的那种结果 ——
它不会报错，只会让你看到一个**语法合法、语义错误**的值。

### 3.20 全量跑才偶发红的测试：后台线程 + 真 ffmpeg + 硬 deadline ✅现象 / ✅根因（2026-09-16 现象，09-18 定根因）

**现象**：给 `m2_server` 加了一个新测试文件（18 条，纯协议层、不载模型）后，
全量跑出现**随机的 2 条红**，且**每次红的用例不一样**：

| 轮次 | 结果 |
|---|---|
| 第 1 轮 | `test_pet_market.py::test_install_remote_gif_skin` |
| 第 2 轮 | `test_pet_market.py::test_install_remote_gif_skin` + `test_pet_scan.py::test_scan_pixel_json_goes_live` |
| 第 3–5 轮 | **824 passed 全绿**（连续三次） |

失败的永远是 **pet（桌宠）** 那两个，与本次改动（TTS API / 首页文案）零关系。

**定位过程（哪一步有效、哪一步是白费）**：

| 做法 | 结论 |
|---|---|
| 单跑那条用例 | ✅ 绿 |
| 两条一起跑 | ✅ 绿 |
| 「我的新文件 + pet 文件」按序跑（怀疑字母序邻接：`test_openai_compat` 正好排在 `test_pet_*` 前） | ✅ 绿 —— **邻接假设被否定** |
| 全量**排除**我的新文件（806 条） | ✅ 绿 |
| 全量**含**我的新文件，连跑 | 2 红 / 3 绿 —— **不是确定性失败，是负载相关的偶发** |

**根因（❓未验证 —— 没抓到失败断言原文）**：两条用例的共性结构可疑：

```python
# test_pet_scan.py:96
def _wait_status(pred, deadline=30.0, interval=0.05):   # ← 30 秒硬超时
    ...
    raise AssertionError(f"等待超时, 当前状态: {pet_scan.progress_scan()}")
```

两条都**在后台 worker 线程里调真 ffmpeg**（gif→webp strip / pixel JSON 试转），
然后按 deadline 轮询状态。全量跑到第 800 条时机器已有大量 ffmpeg 子进程与线程，
**30 秒可能不够**。旁证：同在 `test_pet_market.py` 里的兄弟用例用的是 **60 秒**
（`deadline = time.time() + 60`），两边不一致 —— 像是随手写的值。

> 当时之所以标 ❓：**没有抓到失败时的断言原文**（只看到 `- Ass...` 被截断）。
> 09-18 补齐了 —— 见本节的「已定根因」，**结论是两种形态并存**：当年的
> "deadline 不够"假设只对了一半（形态 B），还有一半是进程根本创建不出来（形态 A）。

**对策**：

1. **判定 flaky 的标准动作（本次有效）**：单跑绿 + 全量偶发 + 失败用例每次不同 →
   基本可判环境/时序，而非逻辑缺陷。**别急着改产品代码去"修"它。**
2. **别只跑一次全量就下结论**。本次 2 红 3 绿，只跑一轮会得出完全相反的结论
   （第 2 轮红 → 以为代码坏了；第 5 轮绿 → 以为修好了）。**连跑 2~3 轮**才算数。
3. **排他法定责**：全量 `--ignore=<新文件>` 跑一次。绿 → 差异只可能来自新文件或其负载；
   但仍需注意"负载相关"时它并不构成因果，只能说明**相关**。
4. **待办**：把 `_wait_status` 的 deadline 与兄弟用例对齐（30 → 60s），
   并在失败消息里带上已等待秒数 —— 否则下次红还是只能猜。

**✅ 已定根因（2026-09-18 补）**：这一族红有**两种形态**，都是环境，都不是代码。

| 形态 | 失败时的状态 | 触发条件 |
|---|---|---|
| A. 进程创建失败 | `status: 'failed'`（且 **message 为空**） | commit 峰值逼近上限，`CreateProcess` 报 `WinError 1450/1455` |
| B. 机器整体变慢 | `status: 'installing'` / `'queued'`（**根本没走到完成**） | 负载高 → 用例自带的硬 deadline 不够（即上面那版假设，**它是对的，只是不唯一**） |

**怎么区分**：看失败断言里的 `status`。`failed` = 形态 A；`installing/queued` = 形态 B。
两种都不能靠改业务代码修 —— A 要腾空间 / 调大页面文件，B 是"这台机器此刻跑不动"。

**形态 A 的原文证据**（`--tb=long` 落盘后 grep）：

```
assert done["status"] == "done", done
E  AssertionError: {'skin_id': 'pixel-cat', 'status': 'failed', 'phase': '失败', ...}
...
try:
>   hp, ht, pid, tid = _winapi.CreateProcess(...)
E   OSError: [WinError 1455] 页面文件太小，无法完成操作。
```

另一轮抓到的是兄弟错误码 `[WinError 1450] 系统资源不足，无法完成请求的服务`。

**形态 B 的原文证据**（同日稍后一轮，同样是这两条用例）：

```
E       AssertionError: {'skin_id': 'pixel-cat', 'status': 'installing', ...}
E       assert 'installing' == 'done'
E       AssertionError: {'pixel-cat': 'queued', 'pixel-capybara': 'queued'}
E       assert 'queued' in ('downloading', 'installing')
```

**一个便宜的机器状态探针：同一次全量的总耗时。** 正常 **~2m30s**；
出现形态 B 的那一轮是 **7m07s**（≈3×）。耗时异常拉长本身就是"这轮结果别当真"的信号，
比逐条读断言快得多。

**机制**：`test_pet_market` 的安装用例在后台 worker 里 `subprocess` 拉起 ffmpeg
做 gif→webp。全量跑到第 800+ 条时系统 commit 已接近上限（本机 C 盘长期 ~96% 满、
页面文件很小），于是要么 `CreateProcess` 直接失败（形态 A），要么每个子进程都慢一截
把 deadline 拖爆（形态 B）。

**推论**：
1. **排他法依然是最有效的定责手段**：全量 `--ignore=<本次新增/改动的测试文件>`
   跑一次，同一用例照样红 → 与本次改动无关（本次两轮都验过）。
2. 见到这两条：先 grep `WinError 145`；没命中且 `status` 是 `installing/queued` → 形态 B。
   **别去改业务代码"修"它。**
3. `test_pet_market` 把子进程异常吞成空 message 上报，**诊断性很弱** ——
   待办：worker 里把异常串写进 `message`，否则每次都要翻 subprocess 栈才知道是环境。

### 3.21 一句 TDZ 崩掉整个渲染器脚本：桌宠只剩一圈「透明玻璃球」 ✅本机实测（2026-09-17）

**现象**（用户原话）：「我的桌面人偶变成这样了 —— 为什么是透明的有这种颜色，
而且鼠标移在上面，像一个手掌一样，是你可以抓取的。这肯定是颜色不知道哪里有问题。」

截图实测：只有一个极淡的圆环 + 底部一点蓝灰渐变，**全图最暗像素 rgb(205,214,224)、
最大饱和度仅 20**（正常渲染的芙宁娜含大量深色描边，最暗接近纯黑）。

**根因**：不是颜色问题，是**脚本根本没跑**。

`web/electron/pet/pet.html` 里，2026-09-10 `b91707b`（动态皮肤）把

```js
applySkin();                                   // ← 调用在这里（第 377 行）
const BUBBLE = { ... };
...
const petBox  = document.getElementById("pet");
const sprite  = document.getElementById("sprite");   // ← 声明在这里（第 394 行）
```

`applySkin()` 内部要写 `sprite.style.setProperty(...)`，而 `sprite` 是**下方才声明的
顶层 `const`** → 暂时性死区（TDZ）→ 第一句就抛
`ReferenceError: Cannot access 'sprite' before initialization` → **整个内联脚本中断**。

脚本一断，后面所有事都没发生：

| 没发生的事 | 用户看到的现象 |
|---|---|
| `setSprite()` 从未执行 → 精灵图没有 `background-image` | 只剩 CSS `#pet::before` 那圈 `radial-gradient` 光晕 + `inset` 边框 =「透明玻璃球」 |
| 末尾 `window.pet.setIgnoreMouse(true)`（初始全窗穿透）从未执行 | 整个 220×480 透明窗一直吃鼠标、挡住底下窗口；光标停在 `#pet` 的 `cursor: grab` 上 =「像手掌，能抓取」 |
| 状态轮询 / 气泡 / 悬停快捷面板 / 拖拽 全部失效 | 桌宠完全没反应 |

**关键点：`cursor: grab` 是设计如此**（拖拽由 JS+IPC 手动实现），
它只是**最后一个还能生效的东西**——因为它是 CSS，不依赖 JS。用户把它当成症状，
其实是"病灶已经蔓延到只剩 CSS 还活着"的证据。

**为什么静态看代码看不出来**：`applySkin` 的定义在调用点之前（函数声明会提升），
看起来完全正常；坏的是**调用时机**相对 `const` 声明的先后。
这类顺序错误 ESLint 默认也不报（`no-use-before-define` 需显式开，且对函数内引用
不一定覆盖）。

**对策**：

1. **修**：把 `applySkin();` 挪到「DOM 引用」段（`petBox`/`sprite` 声明）之后，
   并在函数注释里写明"必须在 DOM 引用段之后调用"。
2. **补测（关键）**：`tools/test-pet-renderer-script.cjs` —— 喂一套最小 DOM 桩，
   `eval` **真实内联脚本**，捕获任何顶层异常；并断言 `sprite` 拿到了
   `background-image`/`--fw`/`--fh`、`#pet` 拿到了 `--dw`/`--dh`、
   初始穿透已下发。`tools/test-*.cjs` 被 `check.py` 的 nodetest 步 glob 自动收网。
3. **反向对照**：该测试支持传入 pet.html 路径。拿 `b91707b` 的旧版本跑 →
   **8/8 全红**；拿 `b91707b^`（用户一直看着正常的版本）跑 →
   渲染相关的 3 条断言全绿（`background-size: 5550px 150px` / `svg/idle.webp` 与修复版一致）。
   这证明"修好了"不是靠肉眼，而是与已知可用版本**参数等价**。
4. **顺带修的同类坑**：`--dw/--dh` 原写在 `sprite` 上，而 `var(--dw)` 的消费方是
   **父元素 `#pet`** —— 自定义属性不向上继承，`#pet` 永远退回硬编码 150px。
   内置皮肤恰好也是 150 所以看不出来，一旦换非 150 帧尺寸的皮肤，
   `::before` 光晕就会比角色小一圈。现在改写到 `petBox` 上。

**证据**（本机实测）：

| 命令 | 结果 |
|---|---|
| `node tools/test-pet-renderer-script.cjs` | **8 通过, 0 失败** |
| 同上，传 `b91707b:web/electron/pet/pet.html` | **0 通过, 8 失败**（含 `ReferenceError: Cannot access 'sprite' before initialization @ pet.html:349`） |
| 同上，传 `b91707b^:web/electron/pet/pet.html` | 渲染相关 3 条绿（与修复版参数一致） |
| `python tools/check.py --only nodetest` | 10 个脚本全绿 |

**推论（通用）**：**"样式/颜色看起来不对"要先问"脚本跑完了吗"。**
一个 `const` 顺序错误能让整个 `<script>` 静默死掉，而**残留的 CSS 会继续渲染**，
于是症状表现得像"样式 bug"。排查顺序应当是：
先看渲染进程 console 有没有异常 → 再查 DOM 上的内联样式有没有被写进去 →
最后才怀疑 CSS 本身。本次正是"CSS 是好的、JS 死了"，只看 CSS 会查反方向。

> **⚠️ 修完不等于用户看到修完**：`web/electron/**` 不在后端自动镜像
> （`backend_autosync.py` 只镜像 `m2_server`/`tools`/`web/dist`），
> 而安装版 `pet.cjs` 的 `PET_DIR` 只认 `resources/backend/web/electron/pet`
> 或 app.asar 内置副本 —— 改完必须重打包（`npm run electron:build`），
> 或临时把修好的 pet 目录放到 `resources/backend/web/electron/pet/` 热替。

### 3.22 无 GUI 时怎么"看见"UI：headless Chromium 出图 + 量测，别让用户当我的眼睛 ✅本机实测（2026-09-17）

**背景**：桌宠改版要验收 `web/electron/pet/pet.html` 的视觉效果，但 Electron GUI
在本机沙箱里起不来（Chromium GPU 进程必崩，`web/electron/smoke-pet-render.cjs`

**做法**：Playwright 缓存里的 `chromium-headless-shell` 就是标准 Chromium，

落地产物：`tools/pet-panel-preview.cjs`（`--measure` 出数字，默认出图）。
它把 pet.html 复制到临时目录、在主脚本前后注入「假 preload 桥 + 假后端 + 展开面板」，
一次跑完 7 个场景（待机/亮色/离线/变声中/处理中/导览/忙态）。

**连踩的五个坑**（每一个都会让"看起来出图了"变成"图是假的"）：

| # | 坑 | 症状 | 对策 |

| a | `fs.cpSync` 拷 2.5MB 精灵图 | **node 进程直接消失**：无异常、无输出、exit 127（沙箱拦截，不是 ENOENT） | 一个字节都不拷：注入 `<base href="file:///…/pet/">`，让相对路径 `svg/*.webp` 直接解析回源目录 |

### 3.23 「我写的测试」从来没跑过它声称要测的东西（假信心测试）✅本机实测（2026-09-17）

**现象**：为"后端离线提示一闪即逝"的修复写了断言"连续几轮轮询后提示仍在"，
断言**通过**。随后做变异反向对照——把修复退回旧写法（`if (backendOffline && !wasOffline) {…return}`），
断言**依然通过**。也就是说这条断言是空转的。

**根因**：驱动轮询时写了 `intervals[0]()`，想当然认为第一个 `setInterval` 是状态轮询。
实际 pet.html 里：

```
1272: setInterval(() => { …待机小剧场… }, 5000);   ← intervals[0]
1283: setInterval(tick, 1000);                    ← intervals[1] 才是轮询
```

驱动小剧场回调什么也没发生（它第一句就 `if (… || backendOffline) return`），
所以药丸当然一直是「后端离线」——**不是因为修复生效，而是因为根本没跑第二轮**。

**对策**：
1. 桩里记录周期：`setInterval = (fn, ms) => intervals.push({fn, ms})`，
   按 `ms === 1000` 唯一识别 tick，并断言"恰好一个"（周期变了会立刻报出来，
   而不是静默退化成空转）。
2. **每条新断言都做变异反向对照**：把被测的修复逐条退回旧写法，确认断言变红。
   本次 10 条新断言全部做了对照，其中就靠这一步揪出了上面这条空转。

**同类假通过（同一轮另一次）**：断言"亮色令牌块存在"时写成
`css.slice(mediaIdx).includes("--c-surface")` —— 把整个亮色令牌块删掉后**依然通过**，
因为文件后续规则里到处是 `var(--c-surface)` **引用**。
必须按大括号配对取出媒体块的**规则体**，并检查令牌是被**声明**（`--c-surface\s*:`）
而不是被引用。

**推论（通用）**：**"测试通过"和"测试有效"是两件事。**
断言写完必须问一句："如果我把这处代码改坏，这条断言会红吗？"
答不上来就去做变异对照——这比读一遍断言可靠得多。
`assert.ok(x.includes(...))` 这类"截尾/模糊匹配"断言尤其容易假通过，
要收紧到"结构性定位 + 精确判据"。

### 3.24 「反向对照」本身也会撒谎：变异没应用 / 测试没真跑 ✅本机实测（2026-09-17）

**现象**：按 3.23 的规矩给新断言做变异对照，脚本报"4 条变异全部被拦住"，
看起来很成功。但打开输出细看——**一条 FAIL 都没有**。
去查原因：测试进程报的是
`Error: ENOENT: no such file or directory, open 'D:\tmp\tmp.1ibjFUmcVX\m.html'`。
也就是说 4 个"被拦住"全是**读不到文件导致的崩溃退出**，跟断言一点关系没有。

**根因（两层）**：

1. **路径跨了两种世界观**。Git Bash 的 `mktemp -d` 给出 `/tmp/tmp.xxx`，
   MSYS 的 `cp` 把它写到 MSYS 自己的 `/tmp`（≈ `%TEMP%`）；
   而 Node 在 Windows 上把 `/tmp/tmp.xxx` 解析成**当前盘符下的 `\tmp\`**（`D:\tmp\...`）。
   一个写、一个读，两边根本不是同一个目录。
2. **判据太弱**。脚本只用"退出码非 0"判断"变异被拦住"——
   而**崩溃**的退出码也是非 0。于是崩溃被当成了"断言生效"。

**对策**：

1. 变异文件放在**两边都能解析的路径**（仓库内 `outputs/_mut/`，或传绝对 Windows 路径），
   别用 `mktemp` 的 MSYS 路径喂给 Node。
2. **先证明变异真的落盘了**：`grep -c` 改动前后的特征串计数，数不上变化就直接报"结论无效"。
   ```bash
   before=$(grep -c 'setBubbleVisible(false)' m.html)
   sed -i 's|{ setBubbleVisible(false); return; }|{ bubble.style.display="none"; return; }|' m.html
   after=$(grep -c 'setBubbleVisible(false)' m.html)   # 必须真的少 1，否则 sed 没匹配上
   ```
3. **再证明失败原因是断言而不是崩溃**：输出里必须出现 `FAIL <断言名>`；
   只要出现 `ENOENT` / `TypeError` / 栈回溯就判"结论无效"。
   判据写成"输出里同时有 `FAIL` 且没有异常栈"，而不是只看退出码。
4. 变异脚本本身也有 bug 时会静默放过（例：`if [ $? -eq 0 ]` 取的是上一条 `grep` 的退出码，
   不是测试的）——所以**判据只认输出内容，别认管道里飘忽的 `$?`**。

**证据**：修正路径 + 加落盘校验后重跑，6 条变异全部由**正确的断言名**拦住
（如"气泡显隐只有一个写入口"、"导览气泡走同一入口"），且还原后 md5 与改动前一致。

**推论（通用）**：**变异对照是"元测试"——它自己也需要被验证。**
顺序永远是：① 变异真的写进文件了吗 → ② 测试真的跑起来了吗 → ③ 失败原因是我预期的断言吗。
三步缺一步，"被拦住"就可能是巧合。

### 3.25 同一窗口里两个浮层抢高度：让位，而不是把整体做小 ✅本机实测（2026-09-17）

**现象**：桌宠快捷面板底部「最近发送」那行被切掉一截，并冒出内部滚动条。
只在**气泡同时出现**时发生（导览/处理中/后端离线），待机时一切正常。

**根因**：气泡与面板是同一个 220×480 透明窗里的**兄弟 flex 项**，
可用高是固定预算：

```
可用高 = 480(窗高) - 18(#root 上下留白) - 150(角色) - 6(面板下边距) - 气泡 - 6(气泡下边距)
```

量测三个场景（`tools/pet-panel-preview.cjs --measure`）：

| 场景 | 气泡高 | 面板拿到 | 面板自然高 | 被切 |
|---|---|---|---|---|
| guide | 82 | 217.8 | 224 | **6px** |
| think | 60 | 240 | 256 | **16px** |
| offline | 78 | 222 | 256 | **34px** |

面板 `flex` 默认可收缩，于是它被压扁、`overflow-y: auto` 生效，最下面那块被切。

**为什么不能"把面板整体做小"**：最坏情况（长导览文案 + 长状态文案）要砍 80px 才够，
那等于常态下永久牺牲呼吸感。而且窗口就这么大，两个浮层的内容量是**加法**，
靠"整体缩小"去追是追不上的。

**对策：让位（yield），只在冲突发生时才收**。
1. 冲突的判据是"气泡在屏"——加 `#root.compact`，在里面**收起最占地方、
   而此刻语义上最不重要的那一块**（这里是 `#recent`，50px + 9px 上边距 = 59px），
   顺带把行距各收 2~3px。让位后 guide 面板自然高 224 → 156，余量 60px。
2. **把触发点收敛成唯一入口**：气泡显隐散落在 4 处（`setState` 两分支、`playGuide`、
   离线分支），任何一处漏掉同步，那一处就会带着多余的内容去抢高度。
   统一成 `setBubbleVisible(show)`，它同时写 `display` 和 `.compact`，
   再用一条静态断言钉住"`bubble.style.display =` 全文件只出现一次"。
3. **让位块要选"本来就会显隐"的那个**：`#recent` 已经会随数据在有无之间切换
   （`:empty { display: none }`），所以它的出现/消失不是新行为，不会显得突兀。
   选一个"从来都在"的块去隐藏，用户会觉得功能坏了。

**验证**：新增 `tools/test-pet-panel-layout.cjs`，用真实 headless Chromium 量测并断言
"面板内容不溢出 / 没有元素被挤出窗口 / 按钮不被裁 / 让位规则与气泡显隐一致"。
7 个场景全部 `overflow=false`、`clipped=0`、`petTop` 一致。

**推论（通用）**：固定尺寸容器里两个浮层抢空间时，优先问三件事：
**① 谁可以按状态收起？（让位）② 收起哪个块最不伤功能？③ 触发点能不能收敛成一个入口？**
"整体等比缩小"几乎总是最差解——它同时牺牲了所有状态的观感，还未必够。

### 3.26 「测不出溢出」≠「没有溢出」：`scrollWidth` 的三种失明方式 ✅本机实测（2026-09-17）

**症状**：给桌宠加了一个分段开关，量测报 `scrollWidth(63) == clientWidth(63)`，
我据此判断"按钮宽度零余量、文字随时会被挤成省略号"，于是又缩字号又改内边距，
还砍掉了本想加的运行指示灯。

**根因**：我拿 `scrollWidth > clientWidth` 当"文字被截断"的判据，但它在这个场景下
**恒定不成立**，而且失败方式不止一种：

1. **居中溢出的方向问题（主要）**：`justify-content: center` 的内容放不下时，
   会向**两侧**溢出。而 `scrollWidth` 只统计"滚动可达的溢出"，
   起始侧（左边）那半截根本不计入 → `scrollWidth == clientWidth`。
2. **`overflow: hidden` 的容器**：滚动区域被裁剪，`scrollWidth` 会被钳到 `clientWidth`。
   偏偏 `overflow: hidden` 又是 `text-overflow: ellipsis` 生效的**前提条件** ——
   也就是说，**所有会显示省略号的按钮，这个判据都是瞎的**。
3. 反过来说，`scrollWidth == clientWidth` 也不等于"刚好卡满"：
   它只说明"没测到溢出"，真实余量可能还有 20px（我这次实测就是
   文字 41.36px / 可用 62px，富余得很）。

**对策**：别问滚动盒有多大，直接量**文字的自然宽度**（Range 给的是布局矩形，
裁剪发生在绘制阶段，不影响它）：

```js
var rng = document.createRange();
rng.selectNodeContents(el);           // 取内容的自然宽度
var textW = 0;                        // 多行的取最大一段
for (var r of rng.getClientRects()) textW = Math.max(textW, r.width);
var cs  = getComputedStyle(el);
var avail = el.clientWidth - (parseFloat(cs.paddingLeft) || 0) - (parseFloat(cs.paddingRight) || 0);
var clipped = textW > avail + 1;      // 这才叫证据
```

**证据**：把分段容器强制改窄（`VM_PET_HTML` 指到变异副本，不动仓库真文件），
新判据报 `textW 41.36 / availW 26 → clipped:true`；真文件 9 个场景全部 `clipped:false`。

**推论（比这条本身更重要）**：**换判据之前，先确认旧判据到底会不会失败。**
我这次的代价是做了三个没有必要的视觉妥协 —— 而只要先造一个"确定会截断"的变异
跑一遍，当场就能发现旧判据压根不报警。

### 3.27 「选定态」≠「运行态」：UI 必须对系统现状说真话 ✅本机实测（2026-09-17）

**症状（用户原话）**："千万变身，还有 RVC 变身。这两个用户不确定是用到底哪一种……
我觉得应该在桌宠上面应该会有一种体现提示，用户应该是哪一种变身？"

**根因（有两个，第二个更隐蔽）**：

1. 两个引擎（RVC 实时 / 千问变声）在后端是互斥的，但桌宠**根本开不了千问**：
   开关走的是主进程 `liveToggle` IPC，而它只认 `/api/rvc/live/*`。
2. 加了分段开关后，**最容易写错的一行**是把"高亮/药丸/按钮文案"挂在
   **`engine`（用户选了谁）**上，而不是 **`runningEngine`（实际在跑谁）**。
   于是在"我选了 RVC、但千问还在跑"（切换的那一瞬间，或从主界面另开的）
   就会告诉用户错的引擎 —— **这比没提示更糟**。

**对策**：

- 状态机里存**两个**变量，并让所有视觉输出**只**由 `runningEngine` 推导：
  选中 = 品牌紫，运行中 = 绿色 + 呼吸；两者可以同时出现（"选了 A、B 在跑"是合法状态）。
- 按钮文案也跟着 `runningEngine`：选中 RVC 但千问在跑 → 按钮写「开 RVC」，
  **不写**「停 千问」。
- 药丸/气泡标题点名引擎（「千问变声中」），别用无主的「变声中」。

**证据**：`qwen-dark` 场景实测 —— `sel=rvc, on=["rvc"], runningMark=["qwen"],
pill="千问变声中", liveLabel="开 RVC"`。8 条变异对照里，
「把药丸改由 `engine` 推导」这一条被专门断言拦住。

**推论（通用）**：凡是"用户的选择"与"系统的实际状态"可能不一致的地方
（引擎、播放/暂停、连接、开关），**展示必须在分歧时选择说真话**。
"用户刚才点了什么"是意图，"现在正在发生什么"才是事实。

### 3.28 关掉主窗 ≠ 关掉应用：一个 hide 掉的窗口就能把进程钉在后台 ✅本机实测（2026-09-17）

**症状（用户原话）**："我把这个应用给关了，它这个还在上面啊"、
"任务管理器看到它还在后台运行……右下角桌宠也没看到，只有任务管理器才能把它搞掉"。
同时那个置顶横幅还糊在屏幕上。

**根因**：Electron 的 `window-all-closed` 要"**一个窗口都不剩**"才触发。
而退出逻辑写在它里面：

```
主窗 closed → 只销毁了桌宠，漏了置顶横幅窗口
           → 横幅窗口仍存活（哪怕已 hide）
           → window-all-closed 永不触发
           → app.quit() 永不执行
           → 进程留在后台，且主窗/桌宠都已销毁 ⇒ 用户看不到任何 UI，只能开任务管理器
```

三个放大器凑在一起才让它这么难查：
① 那个窗口是 `transparent + frame:false + alwaysOnTop("screen-saver") + setIgnoreMouseEvents`，
   关不掉也点不到；② `hideAltHint()` 只调 `hide()`（窗口对象还活着，只是不可见）；
   ③ 应用没有托盘图标，进程活着却**完全没有入口**让用户关掉它。

**对策**（三层，缺一层都可能复发）：

1. 给每个"用完就藏"的窗口一个**真正的销毁函数**（`destroy()`，不是 `hide()`），
   并在主窗 `closed` 里逐个调；
2. `before-quit` 里再兜底销毁一遍（覆盖所有退出路径）；
3. **不要只依赖 `window-all-closed`** —— 它太脆弱，任何漏网窗口都会让它永不触发。
   在主窗 `closed` 里显式判断"已无窗口则 `app.quit()`"，把意图写死。

**证据**：改动后主进程加载自检 18 文件 0 失败；新增 `tools/test-electron-exit.cjs`
8 条静态断言；4 条变异（漏销毁 / 只 hide / 去兜底 / 退回半自动）全部被预期断言名拦住。

**推论（通用）**：**"关掉了"是用户的感知，不是程序的状态。**
凡是常驻/置顶/透明/无边框的辅助窗口，都要在退出链路上单独确认它被销毁；
而"进程还活着但没有任何可见入口"是最糟的失败形态 —— 用户既不知道它在跑，
也没有办法关掉它。

### 3.29 静态断言匹配到了注释：把真代码删掉，测试照样全绿 ✅本机实测（2026-09-17）

**症状**：为 §3.28 的修复写了 8 条静态断言，全绿。跑变异对照时却发现
"删掉 `app.quit()`"这条**没有触发任何失败** —— 退出码 0，测试仍然全绿。

**根因**：断言写的是"closed 处理器里包含 `app.quit()`"，而它匹配到的其实是
**我在上方注释里写的一句解释**：

```js
// window-all-closed 永不触发 → app.quit() 永不执行 → 应用无声无息留在后台
```

也就是说，这条断言从头到尾测的都是**我自己的注释**，跟代码在不在毫无关系。
这是 §3.23「假信心测试」的一个具体变体，而且更隐蔽 —— 因为注释是我刚写的、
内容还正好描述了这段代码，看起来"很合理"。

**两个连带错误**（同一批变异里一起暴露）：

1. **把代码注释掉不算有效变异**：`// altHint.destroyAltHint();` 之后，
   正则 `/altHint\.destroyAltHint\(\)/` **依然匹配**（字符串还在，只是不执行）。
   要验证断言有效，变异必须**整行删除**。
2. **按长度切代码块会越界**：我取"从 `win.on("closed"` 起 900 字符"，
   结果圈进了后面的无关代码与注释。必须**按结构切**（切到处理器自己的 `});`）。

**对策**：

```js
function stripComments(src) {
  return src.replace(/\/\*[\s\S]*?\*\//g, "")
            .replace(/(^|[^:'"`\\])\/\/[^\n]*/g, "$1");  // 避开 http:// 之类
}
```

**凡是断言"某段代码存在"，先剥注释再匹配。**（`[^:'"`\\]` 是为了不误伤 URL 里的 `//`。）

**推论**：写完静态断言后，至少做一次"**整行删除**"式变异确认它会红。
只做"注释掉"式变异是自欺 —— 注释掉的东西，正则照样认得。

### 3.30 打分器一加载，后面的 RVC 子进程就崩：跨进程 CUDA 上下文竞争 ✅本机实测（2026-09-18）

**症状**：试音间批量试音，**第一个音色成功，第二个起全部失败**。错误是
`RuntimeError: cuDNN error: CUDNN_STATUS_EXECUTION_FAILED`。

**看起来像**：显存不够。**实际不是**——当时 GPU 5498/8151，还剩 ~2.6GB，而单次 RVC 只要 ~1.0GB。

**根因**：客观打分器（CAM++ 声纹 `speaker_sep` + NatScore 的 whisper-small）是在**后端主进程**里
加载的，它占住了那个进程的 CUDA 上下文。而每件音色的 RVC 推理是**另起子进程**跑的，
两个 CUDA 上下文撞在一起 → cuDNN 执行失败。所以"第一件成功"是因为当时主进程还没加载打分模型；
一旦第一件跑完就去打分，第二件必崩。

**判据（怎么一眼认出这个坑）**：失败件数 = 总数 − 1，且错误里带 `cuDNN`/`CUDNN_STATUS`。
换权重、换音色、加显存都不管用 —— 因为问题不在显存，在**谁先碰了 GPU**。

**对策（顺序即一切）**：
1. **推理阶段绝不加载任何打分模型**，打分统一放**独立子进程**（`m2_server/audition_score.py`），
   跑完即退出、显存全还。顺带一个好处：整批只加载一次模型，比逐件起进程快 N 倍。
2. 阶段拆分：先跑完**所有**推理 → 释放独占位与任务锁 → 再异步打分。
   用户不该为了几个附加分数等着开不了实时变声。
3. 打分是附加信息：超时（`SCORE_TIMEOUT=300`）、子进程崩、权重缺失，一律只记
   `score_error`，**绝不把已经出来的试音结果标成失败**。

**同族推论**：任何"父进程加载模型 + 子进程也要用 GPU"的组合都要问一句"谁先占的"。
本项目里 `_live_proc_alive` / `_cascade_alive` 那套互斥只覆盖了"另一个子进程"，
没覆盖"本进程自己占着"。

### 3.31 子进程报错信息被 warning 淹没：报出来的"原因"是假的 ✅本机实测（2026-09-18）

**症状**：RVC 推理明明崩了，界面却显示
`RVC 推理失败: …/weight_norm.py:143: FutureWarning: torch.nn.utils.weight_norm is deprecated … |
WeightNorm.apply(module, name, dim)`。看着像"跑通了只是有个警告"，完全指不到真因
（真因是上一条的 cuDNN）。

**根因**：错误信息是取 `stderr` 的**最后 3 行**。torch 导入期会打一条两行的弃用警告
（警告本身 + 源码片段），它恰好压在末尾，把真正的 `RuntimeError` 挤出窗口。

**对策**：`ab_chain._fail_tail(stderr, stdout)` —— 先找含 `Error` / `error` / `Traceback` 的行；
没有才退而求其次，**去掉警告与源码片段/caret 行**再取末尾。已覆盖
`test_fail_tail_prefers_real_error_over_warning` 等 4 条回归。

**推论**：凡是"取末尾 N 行"的日志摘要，都要先问"末尾会不会是噪声"。
更稳的做法是**按特征挑**（关键错误行优先），而不是按位置取。

### 3.32 打分器去 ping 远端权重新鲜度：本地缓存齐全也要白等 2 分钟 ✅本机实测（2026-09-18）

**症状**：第一次算自然度分，卡了 ~2 分钟才出分。日志里是
`ReadTimeoutError(host='hf-mirror.com', port=443) … while requesting HEAD …/whisper-small/model.safetensors`
`Retrying in 1s [Retry 1/5]`。

**看起来像**：权重没下载。**实际相反** —— `~/.cache/huggingface/hub/models--openai--whisper-small`
有 923MB，权重早就齐了。

**根因**：transformers 每次加载都会去远端 ping 一次权重新鲜度；网络不通时它会重试 5 次、

**对策**：在**导入 transformers 之前**设 `HF_HUB_OFFLINE=1` + `TRANSFORMERS_OFFLINE=1`
（这两个开关是导入期读的，设晚了不生效）。缓存真缺时会**立刻**报错而不是干等 —— 比等 2 分钟更好。
见 `m2_server/audition_score.py` 与 `test_audition_score_cli_offline_by_default`。

### 3.33 把"每次探测都很贵"的状态接口当廉价接口轮询 ✅本机实测（2026-09-18）

**症状**：试音间前端每 5 秒拉一次 `/api/audition/env`，而单次探测要起 **PowerShell 查进程**
（`_live_proc_alive` 1.31s + `_cascade_alive` 1.26s）→ 每次 2~3 秒，5 秒一次等于长期占着 CPU。

**根因**：数字看起来很小（"就一次 HTTP 请求"），但后端那侧的实现是**进程枚举**，不是读缓存。
同类测试也踩了：`test_env_shape` 里把 `audition_env()` 写在 12 个 key 的循环里 → 单条用例 31.8 秒。

**对策**：
- 前端：**空闲才轮**（跑任务时按钮已被任务状态禁掉，再探测没意义），间隔 8s，另留手动刷新。
- 测试：一次调用、多处断言，别在循环里调。用 `--durations` 定期体检，30 秒级的用例基本都有问题。

**推论**：写轮询之前先量一次单次调用耗时；超过 100ms 的都要考虑"什么时候真需要刷新"。

### 3.34 常驻 GPU worker 与「另一个要内存的子进程」不能共存 ✅本机实测（2026-09-19）

**背景**：试音间批量换声。一次性 CLI（`offline_vc_infer.py`）每个音色都要重新 `load_vc()`，
4.2s 音频实测**墙钟 32s**（推理只占 4.2s）→ 4 个音色 128s。项目里本来就有常驻 worker
（`--serve`，按 `(pth,index)` 缓存引擎），改用它后同一批 **19.6s**、第二轮 1.0s。

**但换上去之后，同一批的"客观分"全部失败**。症状分三种，且**随并发状态不同而不同**：

| 场景 | 打分结果 |
|---|---|
| 常驻 worker 不在 | ✅ 正常（secs 0.547 / nats 3.099） |
| 常驻 worker 活着并缓存了 4 个引擎 | ❌ `自然度打分失败：页面文件太小 (os error 1455)` |
| 只卸掉引擎缓存、**worker 进程仍在** | ❌❌ 打分子进程**直接崩**，退出码 `0xC0000005`（ACCESS_VIOLATION），无产物 |

**根因**：worker 进程本身（torch + hubert）就占着 1.5GB+ **提交内存**。打分子进程要再装
一份 torch + whisper-small + CAM++。这台机器提交上限本来就紧（C 盘 ~96% 满），
两者叠加就超了。

**★ 最值得记的一条：我最初的设计被自己的实验否掉了。**
第一版是"跑完 `unload` 一下：只丢引擎缓存、保留 hubert，这样既省显存又不用重付 10.5s 冷启"。
听起来很合理 —— **实测不够**：上表第三行说明卸引擎后 worker 进程仍占着那 1.5GB，
打分子进程反而崩得更彻底。**"意图正确"不等于"效果达成"**，删掉这个功能是对的，
留着一个"目的已被证伪"的接口比没有它更危险（下一个人会以为它在起作用）。

**对策（顺序即一切）**：批量推理结束 → **整个 `stop_worker()`**（进程退出，内存与显存全还）
→ 再起打分子进程。代价是下一批要重付 ~10.5s 冷启；相比"每个音色都重载"的子进程路径
仍然快一个数量级（实测 4 个全新音色：**128s → 73s，且打分从失败变成全部成功**）。

**判据**：凡是"A 常驻占资源 + B 也要资源"的组合，都要实测叠加后的余量；
别用"我卸一部分应该够了"来推。另外这类失败**必须能被看见** —— 打分失败只记
`score_error`，试音结果照常返回（见 §3.35 的反面：那个是"看不见"）。

### 3.35 多阶段任务留下"两个标志都是 False"的窗口：前端停止轮询、结果永远不显示 ✅本机实测（2026-09-19）

**症状**：批量试音跑完，界面显示"试音完成"，但四个结果的分数**永远停在"不可算"**，
而且没有任何错误提示（`score_error` 是空串）。手动再调接口，分数其实已经算好了。

**根因**：后端是两阶段任务，两个标志控进度 —— `running`（推理中）与 `scoring`（算分中）。
原来的写法是"决定要打分 → 先 `stop_worker()`（可达 10s）→ 再由打分线程把 `scoring` 立起来"。
于是中间有 ~10s 窗口，**两个标志都是 False**：

```python
finally:
    _mark(running=False)      # ← 第一个标志先落下
    stop_worker()             # ← 10s
    # 这里 scoring 还是 False（要等线程起来才置 True）
...
threading.Thread(target=_score_pass, ...).start()
```

前端轮询的判断是 `if (!running && !scoring) return`（不再拉）→ 在这 10s 窗口里正好
判定"任务彻底结束"→ 停止轮询 → 等分数真算出来也没人去取 → 界面卡在"不可算"。
**对用户说的是一句假话**：真实状态是"还没开始算"，界面说的是"算不了"（同一族的 §3.27）。

**对策**：**"进行中"的标志要在进入下一阶段之前立起来，而不是在阶段内部立。**
```python
finally:
    _mark(running=False)
    will_score = score and 有产物
    if will_score:
        _mark(scoring=True, score_total=len(pending))   # ← 先立标志
    stop_worker()                                       # ← 再去做耗时的事
```
并用 `will_score` 决定要不要起线程（而不是起完线程再让线程报"我没干活"）。

**守卫**：`test_batch_stops_worker_before_scoring` 断言顺序必须是
`["stop_worker", "score"]` —— 顺序写反就红。

**推论**：只要进度由**多个布尔标志**拼出来，就要问一句"有没有任意两个阶段之间存在
『所有标志都 False』的瞬间"。有 → 前端一定会在这个瞬间断掉轮询。
更稳的做法是给状态机一个显式的 `phase` 字段，而不是若干可以同时为假的 bool。

### 3.36 配置里引用了插件、requirements 里没声明它：只有 `--ci-fidelity` 看得见 ✅本机实测（2026-09-19）

**症状**：本机全量自检全绿（钩子、pre-push、`tools/check.py` 都过），
而 `python tools/check.py --ci-fidelity` 一跑就红：

```
=== [pytest] D:\变声\.venv-ci\Scripts\python.exe -m pytest m2_server -q --no-header …
ERROR: usage: python -m pytest [options] [file_or_dir] [...]
python -m pytest: error: unrecognized arguments: --cov=m2_server --cov-report=term-missing …
  inifile: D:\变声\pyproject.toml
```

**根因**：`pyproject.toml` 的 addopts 从建立那天就写着
`--cov=m2_server --cov-report=term-missing --cov-report=html --cov-report=json`，
而 **`pytest-cov` 既不在 `requirements.txt` 也不在 `requirements-dev.txt`** ——
它只存在于本机 `.venv`（某次手工装的残留，同批还有 `pytest-xdist` / `pytest-clarity`）。
于是：本机绿是因为那个残留，CI（只装 `requirements-dev.txt`）则**连参数解析都过不去**，
而且报错长得像"配置写错了"，不像"缺个包"。

**为什么三道门禁全是盲区**（这才是这个坑值得记的理由）：

- `ruff` 不看 pytest 配置；`requires` 只对账"测试 import 了什么"，而缺的不是 import；
- `--ci-fidelity` 的依赖指纹只管"requirements 变了就重装"，**不管"该写的没写"**；
- 其他所有检查都跑在本机 `.venv` —— 而那正是唯一装了这个包的地方。
  **一个包只在本机存在，就等于它不受任何门禁保护。**

**对策**：`requirements-dev.txt` 补上 `pytest-cov`（带注释说明为何不能改成给 CI 加
`-o addopts=` 去掉覆盖率：ci.yml 的立身之本就是"与本地、与 git 钩子跑同一条命令"）。

**守卫**（`m2_server/tests/test_check_ci_fidelity.py` §6）：静态对照
`pyproject.toml` 的 pytest 配置 ↔ `requirements-dev.txt` 的声明，两张表两个方向：

- `_ADDOPTS_OWNERS`（addopts 的长选项 → 发行包）**未知就失败** ——
  “未知”正是要强制人做一次显式决定的地方；
- `_INI_KEY_OWNERS`（插件提供的 ini 键 → 发行包）**已知就必须声明** ——
  ini 键大多是 pytest 自带的（`testpaths` / `filterwarnings`…），反向穷举会变成维护负担。

解析 requirements 时会剥掉注释 —— 那段解释为何要装它的注释自己就写着 `pytest-cov`，
注释被误当声明就又是一个假绿。
变异验证：① 把 `pytest-cov` 那行注释掉 → 正好 2 条变红；
② 把 `asyncio_mode = "auto"` 加回去 → `test_plugin_owned_ini_keys_have_their_plugin_declared` 变红。

**同一个“干净机盲区”里还埋着第二、第三件事**（同一个 `--ci-fidelity` 跑出来的）：

1. **anyio 4.15 把 `anyio.abc.BlockingPortal` 改成惰性别名**（`__getattr__` 时发废弃警告），
   而 **starlette 1.6.0 的 `testclient.py` 顶层还在引用它** ——
   叠上 `filterwarnings` 里的 `error::DeprecationWarning`，就变成 **import `fastapi.testclient` 即红**：
   6 条收集期 ERROR（`test_server` / `test_storage` / `test_ab_chain` / `test_cors_file_origin` …）。
   本机 `.venv`（anyio 4.14.2）全绿、干净 venv（anyio 4.15.1）全红 —— **同一个仓库，只因装没装最新版**。
   属于第三方自己的事，按已有先例（`pydub`/`audioop`）加一条**只匹配该消息**的 `ignore:`，
   并在注释里写明“starlette 更新后回来删掉这行”。
2. **`asyncio_mode = "auto"` / `asyncio_default_fixture_loop_scope` 是**惰性配置****：
   `pytest-asyncio` 不在任何 requirements 里（本项目也真的一条 async 用例都没有），
   在干净机上它只产出 `PytestConfigWarning: Unknown config option` ——
   一份“看着像已接好、实际是假的”配置。删掉这两项，要写 async 用例时再连同插件一起加。

**普适教训**：**配置里引用了一个能力，就必须有一道门禁去对账"那个能力是谁提供的、声明了没"。**
只装在开发机的包与只写在配置文件里的选项，是同一类隐形依赖。
且注意这里的第二个普遍形状：**“本机绿”可能只是因为本机恰好旧了一个版本** ——
依赖不钉死时，`--ci-fidelity` 复刻的不只是“干净机”，而是“**今天新装一台干净机**”。
加依赖后跑一次它（`docs/分发与打包说明.md` §2 也这么要求）。

## 五、备选路线（5.1 已落地为方案 A）

### 5.1 UIA 热激活 ✅ **2026-09-10 已落地**（微信 4.1.13.12）

**原理**（社区库 `wechatauto-replica/uia_driver.py:6-11` 的发现 + 我们实测复现）：
微信 4.x 冷启动时 **Qt accessibility gate 的 active byte = 0**，此时 UIA 只能拿到
`Qt51514QWindowIcon` 空壳；把该 byte 热写成 1，**UIA 树立刻物化为 `mmui::MainWindow`**，
微信不用重启。

**实测证据**（同一进程，写前写后对比）：

| | 热激活前 | 热激活后 |
|---|---|---|
| 根节点 | `WindowControl \| Qt51514QWindowIcon \| '微信'` | `WindowControl \| mmui::MainWindow \| '微信'` |
| 节点数（深度 3） | **2** | 10+（深挖 9 层共 68 个） |
| 内容 | 纯空壳 | `mmui::MainView` / `mmui::MainTabBar` / `mmui::TitleBar`（置顶·最小化·最大化·关闭 都带中文名） |

**怎么找到那个 byte**（`tools/uia_probe.py` 已实现）：
读 `Weixin.dll` → PE 解析 → 找 `qt.accessibility.core` 字符串的代码交叉引用 →
用正则 `48 85 C9 0F 84 ?? ?? ?? ?? 80 3D <disp32> 00 0F 84` 匹配 gate 指令 →
算出目标 RVA（要求在 **可写** 段，且距 `qt.accessibility.core` 的 xref **< 0x20000**，即"同一代码岛"）。

本机结果：`Weixin.dll` 188.2MB，**唯一候选 RVA = 0xad19668**（与 xref 距离 0xb74），
字节当前值 0，`OpenProcess|PROCESS_VM_READ|WRITE` 权限**可用**（同用户即可，无需管理员）。

> **算法是版本无关的**：社区库的版本兜底表只登记到 `4.1.11.22`，我们这台是 `4.1.13.12`，
> 纯靠扫描就命中了，且**只有一个候选**。

### 5.2 `keybd_event` 替代 `SendInput` 📚

## 八、桌面控制 / UIA 通用坑（2026-09-18，配套 `tools/desktop-control/`）

背景：为了给 agent 一对"眼睛 + 手"，写了 `tools/desktop-control/dc.ps1`
（PowerShell 5.1 + UI Automation，零第三方依赖，自带 `selftest` 与 WPF 沙箱靶子）。
下面这些坑**与微信链路无关**——任何 UIA / 桌面自动化都会撞上。

### §8.1 PowerShell 变量不区分大小写 → `$out` 撞参数 `-Out`

- **症状**：`probe` 报 `WriteAllText ... 找不到路径 'D:\变声\System.Collections.Specialized.OrderedDictionary\probe.json'`。
- **根因**：PowerShell 变量名大小写不敏感，`$out = [ordered]@{...}` 就是给参数 `$Out` 赋值；
  `switch` 块与脚本**同一作用域**，于是输出目录静默变成字典。
- **对策**：脚本里局部变量别与参数同形（`dc.ps1` 已把它改成 `$payload` 并留注释）。
- **证据**：✅本机实测，首次 `probe` 即撞。

### §8.2 `[ref]$null` 假成功 → UIA 模式探测全空

- **症状**：`tree` 里每个控件的 `pat`（支持的模式）都是空，包括右键能点的按钮。
- **根因**：`$el.TryGetCurrentPattern($pattern, [ref]$null)` 抛错的路径没有、结果永远拿不到 → 恒 false。
- **对策**：`$probe = $null; ... [ref]$probe`（真实变量）。
- **证据**：✅本机实测（修前 WinForms / WPF 的按钮都"没有模式"）。

### §8.3 WinForms 控件在 UIA 里是哑巴

- **症状**：自建靶子（WinForms `TextBox` + `Button`）在 UIA 里 `ControlType=Pane`、`Name` 为空、
  `AutomationId` 是句柄数字（`590846`），拿不到 `ValuePattern` → `type`/`click` 都难定位。
- **根因**：WinForms 走 **MSAA→UIA 桥**；`Control.Name` 不映射 AutomationId，
  `AccessibleName` 也不作为 UIA Name（TextBox 的 Name 取的是文本）。
- **对策**：测试靶子用 **WPF**（`AutomationProperties.AutomationId` 原生映射、TextBox 原生支持 ValuePattern）。
- **证据**：✅本机实测（WinForms `edit_found=false`；换 WPF 后 `edit_patterns=Value`，`type` 走 `uia:ValuePattern`）。

### §8.4 给 agent 看的截图必须先降采样

- **症状**：`read_files` 对 2560×1600 的 PNG 返回 `[FILE_TOO_LARGE] ... images over 768 KB cannot be attached`。
- **根因**：附件上限 768KB，全屏 PNG 约 1.4MB。

### §8.10 WorkBuddy 环境里启动 Electron 应用会静默失败：`ELECTRON_RUN_AS_NODE=1` ✅本机实测（2026-09-19）

- **症状**：从 agent 的 shell 里 `Start-Process 变声工坊.exe --remote-debugging-port=9222`，
  报 `...\变声工坊.exe: bad option: --remote-debugging-port=9222` 且 `ExitCode=9`（主进程立刻退出）；
  **不带参数**启动则毫无报错、进程也不出现。带不带沙箱一个样。
- **根因**：WorkBuddy AI 给所有子进程注入了 `ELECTRON_RUN_AS_NODE=1`（外加 `NODE_OPTIONS` 指向它的
  node shim）。这个变量让 **Electron 应用退化成纯 Node 进程** —— 不加载 Chromium，于是 Chromium 专有的
  `--remote-debugging-port` 成了未知的 node 选项，node 报 `bad option` 并以 **9** 退出。
  识别线索：`bad option` 是 **node 的措辞**，不是 Windows / Electron 的。
- **对策**：启动前清掉这两个变量（只影响当前 PowerShell 进程，不动系统环境）：
  ```powershell
  Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
  Remove-Item Env:NODE_OPTIONS -ErrorAction SilentlyContinue
  Start-Process -FilePath $exe -ArgumentList "--remote-debugging-port=9222"
  ```
  诊断请用 `[System.Environment]::GetEnvironmentVariable('ELECTRON_RUN_AS_NODE')`，
  **别用 `Get-ChildItem Env:`** —— 本机有 `Path`/`PATH` 重复键，它会直接抛"已添加了具有相同键的项"。
- **证据**：✅本机实测，清变量后同一 exe 立即正常启动（CDP 9222 出现 `pet.html` 与主窗口两个 target）。

### §8.11 安装版的 `MEDIA_DIR` 是**包内空目录**，不是 `D:\变声\media` ✅本机实测（2026-09-19）

- **症状**：安装版（`变声工坊.exe`）里 `/api/voices` 只列 RVC 模型、`has_reference` 全 false；
  桌宠「合成并发送」必报 **`请先选择音色`**（HTTP 400）。
- **根因**：`m2_server/config.py` 的 `ROOT = Path(__file__).resolve().parent.parent`。安装版后端代码在
  `resources/backend/`，故 `MEDIA_DIR = resources/backend/media` —— 而那个 `media/voicebank/` 是**空的**，
  `D:\变声\media\voicebank\kangaroo\reference.wav` 不在它视野里。
  ⚠️ `RVC_ROOT` 默认是绝对路径 `D:/RVC`，所以 RVC 模型照样找得到 —— 这种"一半找得到一半找不到"
  最容易误判成"音色没训练好"。
- **对策**：启动时用 `VM_MEDIA_DIR` 覆盖（`config._path()` 中环境变量优先于默认值）：
  ```powershell
  $env:VM_MEDIA_DIR = "D:\变声\media"
  ```
- **证据**：✅本机实测，覆盖后 `/api/voices` 立刻多出 `kangaroo`（`袋鼠骑士`，`has_reference=true`）。

### §8.12 桌宠面板只认 CDP 派发的可信鼠标事件 ✅本机实测（2026-09-19）

- **症状**：`pet.py hoverel "#pet"` / `rawmove` 之后 `#panel` 的 `display` 仍是 `none`；
  坐标算得没错（`#pet` 中心 = 屏幕 2230,683），`unwrap` 也报穿透已摘掉。
- **根因**：面板由 `petBox`（即 `#pet`）的 `mouseenter` 触发，而桌宠默认
  `setIgnoreMouseEvents(true,{forward:true})`。Electron 的 forward 依赖低级鼠标钩子，
  **合成的鼠标移动不会被可靠转发** → 页面收不到 mousemove → 不会 `setIgnoreMouse(false)` → 死锁。
  `SetCursorPos` 分步移动**不是每次都灵**（本次连试两次都失败）。
- **对策**：走 CDP 派发**可信**事件（进渲染进程自己的输入管线，点击穿透拦不住它）：
  ```python
  from cdp import Session, pick, devtools_targets
  s = Session(pick(devtools_targets(9222), 'pet.html')['webSocketDebuggerUrl'])
  b = s.rect('#pet'); x, y = b['x']+b['width']/2, b['y']+b['height']/2
  for i in range(8):
      s.call('Input.dispatchMouseEvent', type='mouseMoved', x=x-40+i*5, y=y-30+i*4)
  ```
  同理 `cdp.py click "#send"` / `cdp.py type "#say" "文字"` 也比"算坐标硬点"稳（元素矩形变了也不会点偏）。
- **证据**：✅本机实测，8 次 `mouseMoved` 后面板立即 `display: block`；`click "#send"` 成功触发发送。

### §8.13 `Start-Process -RedirectStandardOutput` 会撞环境变量重复键 ✅本机实测（2026-09-19）

- **症状**：`Start-Process ... -RedirectStandardOutput x.log -RedirectStandardError y.log`

### §8.21 「正则扒源码对账」的门禁在重构后会**两边都空**地白绿 ✅本机实测（2026-09-20）

- **症状**：`test_plugin_manifest.py` 原有两条门禁 —— 从 `App.tsx` 抓

     不许静态 import 页面、不许硬编码导航数组；**并且正面要求它确实调用了
     `buildRoutes(` / `navItems(`**（只看"没有写死"不够 —— 两条路都不走也是"没写死"）。
  2. **B 冻结快照**（`test_manifest_*_are_the_frozen_*`）：清单现在是 IA 的唯一来源，
     少一条没有任何别的东西会发现，所以要显式冻结。
     `A ∧ B ⇒ 前端呈现的集合 == 冻结的那一份`，与原命题等价。
  3. 另加**空集哨兵**（`assert literals` / `assert plugins`），
     防止"把 `<Routes>` 整块删掉"也通过。
- **反例对照（为什么不是所有冻结都该留）**：第 3 步**删掉**了「路由挂载全序」的冻结，
  因为那份顺序**没有语义**（实测 139 条路由 0 重叠）；而导航 IA **是产品决定**
  （「试音间进开始组」09-18 拍板）→ 冻结它才有意义。
  **冻结"有语义的东西"，别冻结实现细节**，否则只会带来无意义的快照 churn。
