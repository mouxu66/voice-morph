# 「按住说话」真机验收清单（2026-09-29）

> 用途：**你照着按 5 次**，就能判断这个手势的手感、时长上限、失败提示对不对。
> 每条都给了「怎么按 → 该看到什么 → 不对时先查哪里」，最后有一张能直接填的表。
>
> 为什么要单独写一份：`docs/桌宠遥控器.md` 第七节把**能自动验的**全验了
> （49 个渲染器用例 + 66 个布局量测 + 后端 pytest），但有三件事**只能靠真麦克风和耳朵**：
> ① 抓到的到底是不是你的真实麦克风（抓错会双重变声）；② 换声到底有没有生效；
> ③ 按下到开始录的那段延迟会不会吃掉你开头几个字。这三条没验过，功能就不算完成。

## 〇、先决条件（做错这一步，按下去只会毫无反应）

「按住说话」跨了**三层**，任一层没同步都会表现为「按了没反应」：

| 层 | 文件 | 怎么生效 |
|---|---|---|
| 渲染侧 | `web/electron/pet/pet.html` | **两处都要更**：安装目录的磁盘副本 + asar 里那份（见 `docs/桌宠遥控器.md` 第六节） |
| **主进程** | `pet-actions.cjs` / `pet.cjs` / `preload.cjs` | **必须重打 asar**（`npm run electron:build` 或定向重打） |
| 后端 | `mic_capture.py` / `capture_api.py` / `rvc_live.py` / `voices_api.py` | `tools/sync_backend.ps1 -TargetRoot <安装目录>\resources\backend` → `python tools/verify_backend_sync.py` |

**一分钟自检**（在项目根）：

```bash
python tools/verify_backend_sync.py                     # 后端 10 个文件逐字节比对
grep -c "micHoldStart" "$LOCALAPPDATA/Programs/voice-morph-desktop/resources/app.asar"
#   ↑ 应 ≥ 1（0 = asar 还是旧的，主进程没有这条手势）
grep -c "holdMic" "$LOCALAPPDATA/Programs/voice-morph-desktop/resources/backend/web/electron/pet/pet.html"
#   ↑ 应 ≥ 1（0 = 渲染侧磁盘副本还是旧的）
```

> **别用 `md5sum` 比**（含反斜杠的 Windows 路径会加 `\` 前缀 → 全假红/假绿，见 `docs/犯错档案-微信.md` §2.28）；
> 要手工比就用 `cmp -s A B`。
> **完全退出应用再打开**（桌宠窗口是懒创建 + `hide()/show()` 复用，**不重载页面**，重启才生效）。

主进程要是旧的，界面会**明确告诉你**（这是这次专门加的兜底，不是让你猜的）：

> 状态行：**「按住说话需要新版桌面端：主进程还是旧的（pet.html 已热替换、asar 未重打）」**

看到这句就直接回上表第二行，不用继续。

## 一、开按之前的准备（三件事）

1. **把微信切到「文件传输助手」**（或你自己的另一个号）。
   这条链路会**真发出去** —— 别在和生产环境/同事的聊天窗里验收。
2. **确认系统默认录音设备是你想用的那只麦**。
   ⚠️ 已知边界：「按住说话」**不提供设备选择**，它按这个顺序挑：WASAPI 真实输入设备里 →
   优先系统默认录音设备（只要它不是虚拟声卡）→ 否则取第一个真实的；
   **一个真实麦克风都没有时直接报错，绝不将就录虚拟声卡**（录 CABLE 会得到双重变声的怪声音）。
   所以：先看 Windows 声音设置里的默认输入。想换麦目前只能改系统默认。
3. **把后端日志挂上**（下面每条出问题都要看它）：

```bash
tail -f "$APPDATA/voice-morph-desktop/backend.log"       # 后端日志
ls -lt /d/变声/outputs/.session/ | head                   # 刚录的那几份产物（见下）
```

**产物在哪**：原始录音落在 **`D:\变声\outputs\.session\`**（会话产物，**退出即删**；
只有显式点「保存」才会进作品库）——这是排查的黄金证据：

| 文件 | 是什么 |
|---|---|
| `mic_raw_*.wav` | **你按住期间的真实麦克风录音**（未经任何处理）—— 用它判断「抓的是不是你的麦」和「双重变声」 |
| 换声后的 `*.wav` | RVC 输出，也就是最终发进微信的那条 |

`stop` 响应里还带 `raw_file` / `device` / `duration_s` / `auto_stopped`，见第四节的手调命令。

## 二、五个必按场景

每条按顺序做，**每条都记下「按下→变红」和「松手→已发送」这两个耗时**（后面要填表）。

### A. 最短路径：按住 3 秒说一句话

- **怎么按**：悬停桌宠 → 点「按住说话」页签 → 按住那颗按钮，说「测试一二三」，松手。
- **该看到什么**（按顺序）：
  1. 按下后**很快**变红，按钮下方出现 `0.1s / 59s` 这样的秒数，**每 200ms 跳一次**；
  2. 状态行出现「松手结束并发送」；
  3. 松手后状态行变「正在换声…」→ 再变「正在发进微信…」（换声可能要十几秒，**这段别动键鼠**）；
  4. 气泡：**「已发送到微信 ✓」**，副标题里有 `音频 N.Ns（xxx.wav）`；
  5. 微信「文件传输助手」里出现那条语音。
- **不对时先查**：
  - 按下去**超过 1 秒才变红** → 记下这个时间，写进表里（这说明 `mic/start` 慢，你开头几个字会被吃掉，是个真问题）；
  - 秒数**不动**或跳得断续 → 渲染侧的秒表挂了（看日志有没有报错）；
  - 变红但状态行没变 → 主进程的 `pet:mic-state` 没到（asar 半新半旧）；
  - 松手后没有任何反应 → `mic/stop` 没发出去（看 `backend.log` 有没有 POST）。

### B. 太短：按住只点一下（约 0.1~0.2 秒）

- **该看到什么**：气泡「出错了」+ **「录到的太短（0.12s）—— 按住不放、说完再松手」**，
  微信里**什么都不该出现**。
- **为什么值得测**：0.3 秒这条线（`MIN_HOLD_SECONDS`）是「误触 vs 真说话」的分界；
  它必须**可读地说出来**，而不是静默发一条 0.1 秒的空语音。
- **顺带看一眼**：按住 **0.5 秒**（过线但很短）→ 会发出大约 1 秒的语音吗？
  （微信语音最短 1 秒，既有的补静音头逻辑在这里是否生效 —— 记下实测时长。）

### C. 滑出按钮：按住 3 秒，中途把鼠标/手指拖出面板再松手

- **该看到什么**：**照样收尾并发送**（红色保持到松手那一刻），微信里出现完整的 3 秒语音。
- **为什么必测**：这是指针捕获 + 主进程 `wantStop` 竞态那条链路的真机版。
  如果失败，表现是「录音一直录到 59 秒上限才停」——**这不只是不好用，是发错东西**。
- **不对时先查**：`mic_raw_*.wav` 的时长是不是 3 秒左右（不是 59 秒）。

### D. 按住不放：一直按住超过 59 秒

- **该看到什么**：秒数到 `59.0s / 59s` 时**自己收尾**（不用你松手），接着换声、发送，
  发出去的那条约 59 秒。
- **为什么必测**：微信单条上限 60 秒，这条链路留了 1 秒余量。
  上限自动收尾是「手指滑出 / up 事件丢失」时的最后一道保险。
- **不对时先查**：真录成了 60 秒以上 → 上限没生效（看日志里 `max_seconds` 是不是 59）。

### E. 失败提示（三条，各按一次，都不用真的发出去）

| 怎么造 | 该看到什么（气泡原样透传后端 detail） |
|---|---|
| 微信完全没开（连托盘都没有） | 「出错了」+ 后端的 precheck/409 文案 → 建议里带「按上面的提示把微信弄好后再点一次」 |
| 面板音色下拉选「主界面选中」，而主界面**没选过任何音色** | 「没有可用音色 —— 先在电脑上选一个音色再按住说话」 |
| 选一个**只有参考音、没有 RVC 权重**的音色 | 「音色「X」没有可用的 RVC 模型 —— 按住说话靠 RVC 定音色」 |

- **要点**：这三条都必须在**气泡上看得懂**，而不是「按了没反应」。
  气泡看不清时，`backend.log` 里有同样的 detail。
- ⚠ **2026-09-29 更新**：这里原先写着「按住说话这条路不做发送前探活」—— **已经不成立了**。
  现在按下**之前**就会拉一次 `GET /api/wechat/precheck`，并在按住页最上面那行写出结论
  （见下面的 F）。E1 那条（微信没开）因此应该**在按下之前就能看到**，而不是松手后才报。

### F. 按下之前：那行预检说对了没（2026-09-29 新增）

按住页最上面那行叫「预检」，它只回答一件事：**这次按下去发得出去吗**。
它在进页时、停在页上每 5 秒、以及刚发完一次后刷新。

| 怎么造 | 该看到什么（行文字 + 颜色） |
|---|---|
| 微信开着、停在聊天窗，`VM_WECHAT_RESTART=0`（默认） | 绿：`微信已打开 · 直接切麦克风` |
| **把微信完全退出**（连托盘也没有），再切到按住页 | 红：`⚠ 微信没有在运行`（鼠标悬停能看到完整原因：请先打开微信并登录…） |
| 微信只**收进托盘**（进程在、没有可见窗） | 红：`⚠ 微信没有任何可见窗口`（悬停看全句：pid…它还在运行、多半被关进了托盘）—— 与上一条是**两句不同的话**，这是分因的价值 |
| 停在登录页（未登录） | 红：`⚠ 微信主窗口没就绪`（悬停看全句：面积多少 px²、要么还停在登录页），不是「没在运行」 |
| 后端还是旧版（没有 `block_reason` 字段） | 黄：`预检没有结论（后端版本比桌宠旧？）` |
| `hook.wechat` 关掉 | 页签与页体整个消失，看不到这行（正常） |

- **必验的三件事**（都不是“看得见就行”）：
  1. **拿微信退出与「收托盘」两种情形各看一次**，两句话必须不一样 —— 如果都显示「没有在运行」，
     说明后端的窗口分因没透到行上，那这行就只是个模糊警报。
  2. **它不许拦住你**：红着的时候按下去**必须照样开录**（告警只提前告知，不替你做决定——
     你可能刚刚才把微信打开）。如果按不下去，那是 bug。
  3. **它不该只在那一行**：颜色应是红/黄/绿三档，字号跟下面那行提示一样小、**只有一行**
     （若它占了两行，面板底部的「最近发送」就会被顶掉——纵向预算门禁盯的就是这个）。
- **不对时先查**：
  ```powershell
  Invoke-RestMethod 'http://127.0.0.1:8000/api/wechat/precheck' | Format-List
  ```
  对照 `block_reason` / `wechat_running` / `restart_needed` 三个字段——行上的每一句都对应它们之一。
  行上写「预检打不开」而这条命令有输出 ⇒ 是桌宠连不上后端（和发送失败同源）。
- 顺带：`hook.wechat` 被关掉时，「按住说话」页签与页体应当**整个消失**（不是点了报 404）。

## 三、只能靠耳朵判的三件事（真正的验收）

### ① 换声真的生效了吗

把 `outputs/.session/mic_raw_*.wav` 和换声后的那份**都播一遍**：

- raw 里应当是**你自己的声音**（正常说话，没有怪音）；
- 换声后应当是**目标音色**在说同一句话、语速节奏一致。

>  只听到自己的原声 = 换声没生效（看 `resolve_rvc_voice` 那条：音色库 id 与 RVC 实验名是两套命名，
>  `kangaroo` 要映到 `kangaroo_v2`）。这时 `stop` 的响应里 `converted` 会是 false 或有报错。

### ② 有没有抓到虚拟声卡（双重变声）

- **症状**：发出去的语音像「变了声又变了一次」，或者根本不是你的音色。
- **判据**：听 raw。如果 raw 里**已经不是你本人的声音**（是变过声的），说明抓到了 CABLE。
- **为什么不该发生**：`pick_mic_device` 会显式避开虚拟设备（名字里含 cable/vb-audio/虚拟/立体声混音 等），
  一个真实麦都没有时**直接报错**而不是将就。真发生了就是 bug，请把 `start` 响应里的 `device` 字段抄下来。

### ③ 微信侧的静音告警

- 微信如果绑在**物理麦**上（而不是虚拟声卡），录进去的可能是静音 —— 这是既有的 `warning` 机制，
  面板状态行会显示「已发出 N，但可能有静音：…」。**在微信里放一遍**确认。
- 这条与「按住说话」无关（它是发送链路的固有属性），但验收时顺手确认一次，
  免得把「发送链路的老毛病」误记到新功能头上。

## 四、出问题时的只读定位命令

后端没在跑就别硬起（会预热 4.9G 模型）。以下命令都是**只读或等价于按一次按钮**：

```powershell
# 1) 它会挑哪个麦（不录，只报设备）—— 直接看 start 响应的 device 字段
Invoke-RestMethod -Method Post -ContentType 'application/json' `
  -Uri 'http://127.0.0.1:8000/api/capture/mic/start' -Body '{"max_seconds":59}'
# 2) 停（真录了的话会落一份 mic_raw_*.wav 到 outputs/.session/）
Invoke-RestMethod -Method Post -ContentType 'application/json' `
  -Uri 'http://127.0.0.1:8000/api/capture/mic/stop' -Body '{"raw":true}'   # raw=true：只录不换声
# 3) 没有正在录的时候调 stop → 应得到 400「没有正在进行的录音」（用来确认没有残留录音线程）
Invoke-RestMethod -Method Post -ContentType 'application/json' `
  -Uri 'http://127.0.0.1:8000/api/capture/mic/stop' -Body '{}'
```

- `raw: true` 是**专门为排查留的**：只录不换声，用来分辨「录错了」还是「换声错了」。
- 想确认实时变声那边有没有残留：`GET /api/rvc/live/status` 看 `live_running`。
- 桌宠状态条上那个 **`82ms`** 是**单块推理耗时**（不是端到端延迟）——验收延迟时别拿它对表，
  口径见 `docs/桌宠遥控器.md` 第三节。

## 六、这份清单**没有**覆盖的

- **不同麦克风/采样率**（WASAPI 设备可能是 44.1k/48k，16k 单声道转换在采集后统一做，没逐个设备验）；
- **蓝牙耳机麦克风**（免提模式会把系统默认录音设备切成另一只，属于「①先确认真实麦克风」那一节的变体）；
- **多屏/缩放比例**（按钮命中区域与缩放无关，但面板是 220px 固定窗，高 DPI 下未验）；
- **并发**：一次只允许一个「按住」——第 2 次按下会被忽略（`micPhase !== "idle"` 时直接 return），
  没验过「按住中途切页签/切到音效页」的表现。
