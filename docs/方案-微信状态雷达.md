# 方案：微信「该不该回」状态雷达

> 本文所有数字均来自 2026-10-23 本机实测（RTX 5060 Laptop 8GB / 2560x1600 / 微信 4.x）
> 实测脚本与截图证据：`C:/Users/mouxu/AppData/Local/Temp/vltest/`

## 一、为什么是这个架构

三条路都测过了，差距不是一点点：

| 方案 | 左右位置 | 时间戳 | 耗时 | 可调试性 |
|---|---|---|---|---|
| Qwen3-VL-4B 一次读整段 | **0/4 对** | 0/2 | 5.76s | 错在哪不知道 |
| Qwen3-VL-4B 分段读 | 4/4 对 | 0/2 | 4.38s | 错在哪不知道 |
| **像素行投影（本文方案）** | **11/11 对** | **2/2 对** | **171ms** | **每个数字都能打印** |

结论：**判断"该不该回"所需的信息，全部是几何量，不需要读文字。**

需要的就是四个数：最后一条在左还是右、距现在多久、我上次说话在多久前、对方连发了几条。
这四个数用像素算，100% 确定；用 VLM 算，位置会错、时间戳会漏。

**VLM 不是被否定，是被挪到它擅长的位置**——读文字内容，只在用户要回话时才用。

---

## 二、三层架构

```
L0 感知   像素 CV (numpy)      171ms（可优化到 20ms）
          抓图 → 行投影 → 左右归属 → 时间戳/系统消息识别

L1 判断   规则引擎 + 千问       本地 <1ms，边界情况 200-400ms
          4 个特征 → score「现在插话的合适程度 0-5」

L2 生成   千问 VL + 千问文本    按需，1.5-4s
          只在用户点「这怎么回」时触发
```

**关键：L0 永远不调模型，L2 永远不参与判断。** 判断层拿不到文字，也就不可能被文字的歧义带偏。

## 三、L0 实现要点（已验证可跑）

### 3.1 抓图：必须带 PW_RENDERFULLCONTENT

```python
hwnd = user32.FindWindowW("Qt51514QWindowIcon", "微信")   # 用类名找，标题可能变
ok = user32.PrintWindow(hwnd, mdc, 2)                     # 2 = PW_RENDERFULLCONTENT
```

实测对比（真微信窗口，被 WorkBuddy 全屏遮挡）：
- `flag=2`：mean=240.0 / 黑屏率 **0.0%** → 穿透遮挡拿到完整界面
- `flag=0`：mean=5.8 / 黑屏率 **97.7%** → 几乎全黑

> 不带这个 flag 会以为"Windows 抓不到微信"，其实只是没带参数。这一个数字能省两天。

### 3.2 左右归属：行投影 + 最长连续段

不需要 OCR，不需要模型，纯 numpy：

```python
gray = a.mean(axis=2)
sat  = a.max(axis=2) - a.min(axis=2)
fg   = (gray < 205) & ~((sat > 40) & (gray > 150))   # 排除彩色气泡底色
fg[:62, :] = False      # 屏蔽标题栏
fg[1300:, :] = False    # 屏蔽输入框

rowcnt = fg.sum(axis=1)                      # 行投影
# 连续非零段 → 一条消息（空隙 >5px 断开）
# 每段内取「最长连续列段」→ 真实 x 范围（滤掉孤立噪声）

cx = (x0 + x1) / 2
side = "左" if cx/W < 0.42 else ("右" if cx/W > 0.58 else "居中")
```

实测结果（117 群）**11/11 全对**：

| # | 内容 | 判定 |
|---|---|---|
| 1 | 视频 0:04 | 左 ✓ |
| 2-4 | 李河璋 666 / 神了 / 哈哈哈 | 左 ✓ |
| 5 | `10:51` 时间戳 | 居中 ✓ |
| 6 | 罗文轩 @牟旭 投什么 | 左 ✓ |
| 7 | （一条短消息） | 右 ✓ |
| 8 | 罗文轩 OK | 左 ✓ |
| 9 | `12:48` 时间戳 | 居中 ✓ |
| 10 | 我的红包 | 右 ✓ |
| 11 | 李河璋领取了你的红包 | 居中 ✓ |

**三个「居中」自动区分了时间戳和系统消息**——它们本来就都居中，靠 `行高` 再细分：
- 行高 ≤ 20px → 时间戳（纯数字/日期，等宽短）
- 行高 > 20px → 系统提示（有汉字）

### 3.3 两个必须注意的坑

1. **亮度阈值不能设太低**。用 140 时，`10:51` 和「李河璋领取了你的红包」全部漏检（浅灰小字，亮度 160-190）。改成 205 后全部检出。
   这两项正是 VLM 也漏掉的，说明是"显眼程度"问题，不是模态问题。
2. **取 x 范围不能用 min/max**。左侧边缘的孤立噪声点会把中心拉偏，导致时间戳被判成"左"。要用**最长连续列段**。

### 3.4 性能

当前 171ms（Python 循环 + np.where）。优化方向：
- `rowcnt` 已是向量化，主要开销在逐行 `np.where`
- 改成切片批量判断，或把 ROI 缩到会话区实际高度（约 1300px），可降到 **20-40ms**
- 500ms 轮询一次完全够用

## 四、L1 判断：千问怎么用

### 4.1 特征（全部来自 L0，零额外成本）

| 特征 | 来源 |
|---|---|
| `last_side` | 最后一行的左右判定 |
| `last_change_ts` | 本进程记录的最后一条出现时刻 |
| `gap_seconds` | 现在 − last_change_ts |
| `streak` | 末尾连续「左」的行数 |
| `my_last_reply_age` | 最后一个「右」气泡距现在多久 |

### 4.2 分级触发（钱花在刀刃上）

```
gap < 30s           → 不打扰（对方刚发，可能还在打）
gap > 10min 且 left → 提示「该回了」（规则，零成本）
30s ~ 10min 边界区  → 这里才调千问
```

实测千问文本调用一次约 200-400ms，成本可忽略：

| 模型 | 输入（元/百万 token） | 输出 |
|---|---|---|
| `qwen-flash` | 0.15–0.6 | 1.5–6 |
| `qwen-plus` | 1–3 | 10–30 |

一次判断约 100 input token + 5 output token → **百万次约 ¥0.02**。可以放开用。

### 4.3 提问方式（关键）

**不要问开放问题，要问有界问题。** 这正是 Jev 那套 `choice/noul/score` 的思路，用千问也能表达：

```python
# score：合适度
"当前状态：对方最后发言，已过 {gap} 秒，对方连发 {streak} 条，我上次回复在 {my_age} 秒前。
 请给出「现在插话的合适程度」，只输出 0-5 的整数。"
```

要求只输出一个数字 → 输出 1-2 个 token → 快且稳定。
**不要让它解释原因**，解释会让它生成 100 个 token，慢 10 倍还容易编。

### 4.4 本地替代

不想连云端就上 **Chinese-Jev**（322M，中文 ACC 69.2%，ECE 3.78%，14ms，CPU 可跑）
或 **Laya**（Apache 2.0）。它们天生只做 `choice/noul/score`，正好匹配这个任务。

> 注意：Jev 只解决「快」，不解决「输入错」。
> 所以在 L0 换成像素法之前，接 Jev 等于给错误结论加一张更快的嘴。

## 五、L2 生成：千问 VL 怎么用

只在用户点「这怎么回」时触发。两条路：

### 路线 A：云端 `qwen-vl-ocr`（推荐）

| 项 | 值 |
|---|---|
| 价格 | 输入 ¥0.3 / 输出 ¥0.5 每百万 token |
| 免费额度 | 100 万 token ≈ 5000 张（250x600） |
| 限制 | **不支持结构化输出 / Function Calling**，JSON 要自己解析 |

用法：裁**最后 3-5 条气泡**（约 100 万 px，不要整屏），让它照抄文字。

### 路线 B：本地 Qwen3-VL-4B

- 模型：`D:/Qwen3VL-4B-Instruct-Q4_K_M.gguf` + `D:/mmproj-Qwen3VL-4B-Instruct-Q8_0.gguf`
- 启动：`llama-server -m ... --mmproj ... -ngl 99 -c 8192 --port 8090`
- 8GB 显存装 4B 无压力（实测加载后余量充足）
- **首次调用有预热开销**（实测 52s → 预热后 4.4s），产品里要启动时先跑一次空转

### 提问方式的铁律

| 别做 | 该做 | 实测差 |
|---|---|---|
| 「列出所有消息」 | 「最后一条是谁发的」 | 3.72s → 0.16s |
| 「这张图里有什么」 | 「这三条里有没有问号」 | 4.4s → 0.2s |
| 大图一次读 | 切成 ≤150 万 px 分段 | 整段位置 0/4，分段 4/4 |

**延迟 = 视觉 prefill（∝像素）+ 输出 decode（∝输出字数）。**
答案越窄，越快越准。让它"列清单"是唯一确定会失败的做法：慢 7.5 倍，还会漏掉最后 1-2 行。

## 六、落地顺序（建议）

| 步 | 做什么 | 工作量 | 验收标准 |
|---|---|---|---|
| 1 | 抓图 + 行投影 + 左右归属 | 半天 | 在你自己的聊天窗口上跑到 11/11 |
| 2 | 加时间戳/系统消息细分 | 2 小时 | 三个"居中"能正确分到两类 |
| 3 | 4 个特征 + 规则引擎 | 半天 | 「该回了」判断在真实对话里不出误报 |
| 4 | 边界情况接千问 flash | 2 小时 | 单次 <400ms |
| 5 | 用户点「怎么回」→ VL 读最后 3 条 | 半天 | 文字照抄准确，不含位置判断 |

**第 1 步没跑通之前，不要碰后面任何一步。**

## 七、已知限制（别指望绕过）

1. **微信进程必须在跑**。完全退出时屏幕上没东西可读。
2. **滚出可视区的历史抓不到**。只能处理当前屏，历史要自己增量累积。
3. **语音条读不出内容**，只能拿到"15 秒"这个时长。
4. **DPI 缩放/多显示器变化**会让所有硬编码坐标失效，每次启动和窗口尺寸变化都要重算。
5. **合规**：微信把「截图、录屏获取聊天记录」明确列入违规。自用无人管，**要分发就是另一回事**——分发版只能读虚拟声卡音频 + 用户主动粘贴。

---

## 八、一句话

**像素负责"看见"，千问负责"说话"，中间那个"要不要开口"的判断，交给 5 毫秒的规则。**
把这三件事混给一个模型干，结果是 4 秒、位置错、还会漏。

## 九、实现状态（2026-10-23 已落地）

### 9.1 代码位置与用法

```
m2_server/chat_radar/
    capture.py   窗口查找 + PrintWindow 抓图 + 聊天区 ROI 自动定位
    layout.py    行投影 → 消息块（方向 / 类型 / 坐标）
    state.py     帧间跟踪 → 带时间的 4 个信号（gap / streak / last_side / my_last_reply_age）
    judge.py     规则引擎 + 可选千问边界判断
    radar.py     编排：一次 tick = 抓图 → 解析 → 更新状态 → 判断
    cli.py       命令行
m2_server/tests/test_chat_radar.py   32 个纯逻辑测试（合成图，不碰微信）
```

```bash
cd m2_server
python -m chat_radar probe            # 看窗口与聊天区矩形
python -m chat_radar once --save out  # 抓一帧，输出块表 + 判断 + 可视化
python -m chat_radar watch --live      # 常驻，单行刷新看 gap 在涨
python -m chat_radar bench -n 20       # 测单帧耗时
```

环境变量（都可选）：
`VM_RADAR_LLM_KEY` / `VM_RADAR_LLM_MODEL`（默认 qwen-flash）/ `VM_RADAR_LLM_BASE`。
不配就走纯规则，功能完整，只是没有边界档的细化评分。

### 9.2 实测性能（比第五节的原估算又快了一截）

| 阶段 | 耗时（中位） | 说明 |
|---|---|---|
| `grab_window`（PrintWindow） | **57 ms** | GDI 固定成本，上 DXGI 才能再降 |
| `analyze`（解析） | **30 ms** | 原方案 171ms，见下 |
| `feed`（状态跟踪） | **8 ms** | 底部条带 4×4 池化后差分 |
| 合计 | **97 ms**（p95 121ms） | 500ms 轮询 → 单核约 19% |

**从 171ms 降到 30ms 的关键**：不再为了"排除彩色气泡"去算 `max(axis=2)` 和
`min(axis=2)`——numpy 的 uint8 归约是逐列比较，2.78M 像素要 **85ms**，
占了三分之二。改成「相对背景的亮度差」当唯一判据后，彩色气泡（绿/蓝/红包）
整块进入前景，方向判得比只框文字**更准**，同时省掉 85ms。
这是少见的「更快」和「更准」同时改善。

### 9.3 实现中踩到的三个坑（都是真机暴露的）

**① ROI 会被聊天区里的大图带偏**
原判据「从右往左找第一个偏离背景的列」，遇到一张 452px 高的照片时，
那几列的中位亮度被拉低，扫描停在图片左缘——实测左边界从 `343` 判成 `568`，
整个 ROI 切掉一半。现在要求「边界左侧是一段**均匀**的会话列表背景」
（`std < 3`），图片列方差大，不会再被误认。

**② 冷启动时 gap 不能当精确值**
第一版把「首次观察时刻」当成「消息出现时刻」，于是启动时已经放了 10 分钟的消息
被报成「刚发 0 秒」，永远不提醒——**静默漏报，比误报更难发现**。
现在区分 `gap_lower_bound`：没观察到过真实变化就是「至少 N 秒」，文案里也带「至少」。
并且这种情况下动作是 **`unknown`（观察中）而不是 `wait`**——
说「对方刚发」等于编造，只过了 3 秒的那条消息也可能已经躺了半小时。
`test_gap_on_cold_start_is_lower_bound` 和 `test_rule_cold_start_is_unknown_not_wait`
是这条的回归测试。

**③ media 判定要跟着前景判据一起改**
改成「彩色气泡整块进前景」之后，长文字气泡的 fill 也变高了，
`fill > 0.75` 会把「李河璋 待会儿第一节下课之后要打扫卫生」这种长消息标成图片。
改成 `fill > 0.9 且 height > 60`（实测视频缩略图 fill=97.5% / 高 234px，
文字块 fill 仅 10-14%）。

### 9.4 已验证的识别准确率（真机截图，人工逐条核对）

| 会话 | 块数 | 结果 |
|---|---|---|
| 117 群（视频+4条文字+红包+2时间戳+系统提示） | 11 | **11/11** |
| 同群（红包/绿气泡/系统提示/浅灰时间戳） | 14 | **14/14** |
| 另一群（含 400px 高照片消息） | 10 | **10/10** |

浅灰时间戳（亮度 171-172）和灰色系统提示（亮度 128-171）全部检出并正确归到「居中」，
这两项正是 Qwen3-VL-4B 两次漏掉的。

### 9.5 还没做的

- **会话列表侧的时间戳**：目前 `gap` 靠本进程观察累计，冷启动只能给下界。
  要拿精确值得读会话列表里的 "10/16" / "12:49"，那是文字 → 需要 L2 的 OCR。
- **未读红点**：会话列表上的红点是"对方连发"的强信号，同理需要读列表列。
- **FastAPI 路由**：现在只有 CLI。要接桌面端就在 `radar.py` 外面包一层 `/api/radar/state`。
- **L2 生成**：用户点「怎么回」→ `qwen-vl-ocr` 读最后 3-5 条 → `qwen-plus` 写回复。未实现。
