# 历史重写方案（git filter-repo）· 2026-09-14

> **决策：不重写。** 本文是"如果哪天必须重写"的**可执行方案 + 影响面 + 回滚预案**，备而不用。
> 触发条件写在 §2 —— 满足任一条才值得动，否则成本远大于收益。
> 相关：`docs/开源前待办清单-2026-09-12.md` §3、`tools/audit_git_history.py`、`docs/犯错指南.md` §3.11。

## 1 现状（2026-09-14 提交后实测）

| 指标 | 数值 |
|---|---|
| `HEAD 仍含` | **0 处**（工作区已闭环） |
| `仅历史` | **109 处**（素材名 100 + 隐私 9） |
| 凭据 | **0 处**（任何位置都没有 —— 这是"不重写"能成立的**硬前提**） |
| 仓库 `.git` | **31 MB** |
| `--allow-history-only` 退出码 | **0** |

命中性质（逐条看过，没有误报）：

- **素材名 100 处**：全是**历史提交里的下载文件名**（老文档的清理清单、几个 experiment 脚本的字面路径、`_clip_picks.txt` / `_f0.json`），
  加上**不入库的** `.audit-materials.txt` 里的标题在历史中的出现。HEAD 里已全部清掉。
- **隐私 9 处**：`C:\Users\<用户名>` 形式的路径。⚠️ 用户名已因 GitHub 账号公开而**失去隐蔽价值** ——
  这一类的重写收益≈0，别为它单独重写。

### 1.1 「不重写」真正的代价在哪 —— 不是隐私，是体积

历史里最大的 6 个 blob 全是**已被 webp 取代的宠物皮肤源 SVG**：

```
2.56 MB  web/electron/pet/svg/error.svg
2.45 MB  web/electron/pet/svg/idle.svg
2.09 MB  web/electron/pet/svg/idle-look.svg
2.03 MB  web/electron/pet/svg/thinking.svg
1.58 MB  web/electron/pet/svg/conducting.svg
1.04 MB  web/electron/pet/svg/building.svg
合计 11.75 MB ≈ .git 的 38%
```

关键事实：**HEAD 里 `.svg` 数量 = 0**（`git ls-files "*.svg"` 实测），现役是 6 个 `.webp`（合计 2.5 MB）。
也就是说这 11.75 MB 是**纯历史包袱**，且可以用最安全的方式摘掉（见 §3 步骤 5b）。
→ 若将来真要重写，**体积才是第一理由，隐私只是搭头**。

## 2 什么时候才值得重写（触发条件）

| 优先级 | 条件 | 说明 |
|---|---|---|
| **P0** | 历史里出现**真实凭据**（密钥 / 私钥 / 密码 / token） | 此时**先轮换密钥**，再谈重写 —— 泄露过的密钥不会因为改写历史而变安全 |
| P1 | 历史里出现**素材片名本体**（不是文件名里的来源标记），且权利人提出异议 | 目前没有 |
| P2 | 仓库要用于商业场景 / 被要求提供 clean history（尽调、法务） | 目前没有 |
| P3 | 单纯想让仓库变小（§1.1） | **单独为这个理由不值得**（force push + 哈希全变） |

## 3 可执行方案

### 3.0 前置：`git filter-repo` 本机**没装**

```
$ git filter-repo --version
git: 'filter-repo' is not a git command.        # 2026-09-14 实测
```

两种装法，**推荐第二种**：

1. `pip install git-filter-repo` —— 需要挑解释器。**不要装进项目 `.venv`**（那里的 torch/transformers 版本很敏感，见 `MEMORY.md` §2）。
2. 用官方**单文件脚本**（`github.com/newren/git-filter-repo` 的 `git-filter-repo` 是自包含 Python 脚本）：
   下到 `outputs/`（**该目录已 gitignore**，不入库），直接 `python outputs/git-filter-repo <args>`。
   > 注意：脚本本身是第三方代码，**别提交进仓库**；要用就写进 `THIRD_PARTY_NOTICES.md` 的运行时表（它目前不在我们的依赖集里）。

### 3.1 冻结 + 备份（**先做，别跳**）

```bash
# 1) 记下当前 HEAD，回滚时要用
git rev-parse HEAD > outputs/pre-rewrite-head.txt

# 2) 全 ref 备份（含远端跟踪 ref）。放 D 盘：C 盘 90% 满
git bundle create ../voice-morph-pre-rewrite.bundle --all
git bundle verify ../voice-morph-pre-rewrite.bundle      # 必须 OK 再往下走
```

bundle 是**唯一**的回滚凭据：重写后旧对象会在本地 gc 掉，没有它就只能靠 GitHub 上的旧 ref（而它会被 force push 覆盖）。

### 3.2 **在全新 clone 上做，不在 `D:\变声` 里做**

filter-repo 会重写**所有 ref**，并且默认拒绝在有 remote / 有未提交改动的库上运行。
在现有工作库上做，等于把唯一的干净副本也赌进去。

```bash
git clone --mirror https://github.com/mouxu66/voice-morph.git ../vm-rewrite.git
cd ../vm-rewrite.git
python <filter-repo> --analyze          # 产出历史体积分析（不写库）
```

> ⚠️ **本机特有坑（`MEMORY.md` §7）**：本机 `git fetch` / `update-ref` 对 `.git/refs/remotes/` 的写入
> **被静默丢弃**（`refs/heads/` 正常）。所以：
> · 校验"远端到底指哪"用 **`git ls-remote origin`**，**别信** `refs/remotes/origin/*`；
> · 推之前先 `git ls-remote origin master` 存一份，用来做 `--force-with-lease` 的期望值。

### 3.3 先 `--dry-run` 看一眼再动

```bash
python <filter-repo> --replace-text ../vm-rewrite-expressions.txt --dry-run
```

表达式文件**不入库**（放 `outputs/`），内容两段：

- 由 `.audit-materials.txt` 的标题逐行生成 `标题==>第三方素材 NN`（按 `f79e767` 那次的编号约定）；
- 用户名路径：`regex:C:\\\\Users\\\\[^\\\\]+\\\\==>C:\\Users\\<user>\\` 一类。
  **用 `regex:` 前缀**时留意反斜杠转义层数 —— 写错会静默不替换（跑完必须按 §3.5 校验）。

### 3.4 正式重写

```bash
python <filter-repo> --replace-text ../vm-rewrite-expressions.txt
```

### 3.5 校验（**三步缺一不可**）

```bash
# ① 片段层面：目标 0 / 0（先提交再跑 —— 它扫的是已提交内容）
python /d/变声/tools/audit_git_history.py               # 期望 HEAD 仍含 0 + 仅历史 0

# ② 内容层面：重写只应改到"该改的片段"，其他必须逐字节一致
git diff <old-head> <new-head> --stat                    # 期望：只有被替换的文件/行

# ③ 远端层面：本机 refs/remotes 不可信 → 直接问远端
git ls-remote origin master
```

### 3.6 发布

```bash
git push --force-with-lease origin master        # 不要 --force
```

### 3.7 回滚预案

| 时机 | 动作 |
|---|---|
| 重写后发现不对，**还没 push** | 删掉 `../vm-rewrite.git`，`D:\变声` 本身没动过 |
| **已 force push** | 用备份 bundle 重建一个库 → 再把旧历史 force push 回去：`git bundle unbundle` / `git clone ../voice-morph-pre-rewrite.bundle` → `push --force` |
| bundle 也丢了 | 只能等 GitHub 的 unreachable object 被 gc —— **当作不可恢复**。所以 bundle 要留到确认稳定为止 |

## 4 影响面（重写的真实代价，量化）

- **所有 commit hash 变化**。仓库里引用了 **40 处 / 20 个不同 hash / 分布在 7 个文件**
  （`docs/犯错指南.md`、`docs/开源前待办清单-2026-09-12.md`、部分测试与脚本注释里的
  `f79e767` / `dc20ad3` / `a1d0f40` / `5dd1fdf` / `d1a9b4c` …）→ 重写后**全部指向不存在的提交**，
  要么批量改文档（且新旧对照本身要留档），要么接受文档里的引用集体失效。
- 已 clone / fork 的人必须**重新 clone**（重新 push 会让他们的历史分叉）。
- GitHub 上 issue/PR 里的 `#commit` 引用、release 附件、Actions 的历史 runs 与 commit 绑定全部错位。
- `--ci-fidelity` / pre-push 钩子不受影响（它们看的是工作区）。

## 5 结论

1. **不重写**：凭据 0 是硬前提，剩下的两类（素材名标记、已公开的用户名）收益有限，代价是 40 处引用 + 全部公开哈希失效。
2. 日常门禁继续用 `--allow-history-only`（**非对称**：只放行"仅历史且非凭据"，「HEAD 仍含」任何类别一律失败）。
3. **把 `HEAD 仍含 = 0` 当成维护目标**：新增内容一律不得带来源标记/片名/用户名路径（`tools/audit_licenses.py` 与 `audit_git_history.py` 都能机器拦）。
4. 若哪天想减仓库体积（11.75 MB 的死 SVG），**那是一次独立的决定**，别顺手和隐私清理绑在一起 ——
   混在一起做，出问题时无法判断是哪一步导致的差异。
