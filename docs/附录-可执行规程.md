## 1 发版 SOP

> 更新源、签名、回滚、`scripts/release.ps1`。发版前逐条照做。
> 原文：`release-sop.md`（2026-10-27 并入）

### 变声工坊 · 发版 SOP

> 一条命令发版：`scripts/release.ps1`。本文覆盖发版前检查、命令序列、常见错误、回滚方法。
> 首次发版请完整读一遍；熟悉后可直接跳到「二、标准发版流程」。

#### 〇、发版节奏（先读：什么时候该发，什么时候不该发）

> 2026-09-14 用户拍板：**按大版本发，不随每次改动发**。频繁上传没必要。

**先分清两件事**——它们完全无关：

| 动作 | 客户端能否感知 | 代价 |
|---|---|---|
| `git push` 代码到 GitHub | **完全不能**。客户端从不读仓库源码，只读 `releases/latest/download/latest.json` 这一个永久别名 | 几秒，随便推 |
| 发 Release（`release.ps1 -Publish`） | 能。启动 12s 后会检查到 | 构建几分钟 + **上传 ~100MB 安装包** + 签名密码。**这才是"上传"** |

**所以"每次改动都往网上传"是个误解**：日常改完只 `git push` 就行，客户端零变化。

**已定节奏**：

- **日常改动** → 只 `git push`，**不发 Release**。自己用本地构建（见下）。**版本号一个字都不碰**
- **里程碑**（`0.3.0` / `1.0.0` 这种）→ `release.ps1 -Publish -BumpLevel minor`（或 `major`）
- **必须让所有人升级的关键修复** → 发，并加 `-Mandatory`
  （普通更新用户能点「跳过此版本」，标了 mandatory 的**跳不过去**，见 `updater.cjs`）

**少发是安全的（有代码依据，不用怕）**：线上没有 Release 时，`latest.json` 返回 404 →
`checkForUpdates()` 返回 `{ok:false, hasUpdate:false}` → 调用处直接 `return`。
客户端**不下载、不安装、不报错**，界面上也不弹任何东西。所以"几个月不发"没有任何副作用。

**唯一代价**：不发 Release = **别人拿不到你的修复**，永远停在旧版本。
你本机可以随时跑最新本地构建，但**别的机器 / 已安装的用户**不会自己变新。

**版本号只在发版那一步升，本地开发天然不碰它**：`release.ps1` 的升版本在第 3 步（构建之后），
日常 `git push` 和本地 `--dir` 打包都不会改 `web/package.json` 的 version。所以"本地搞"不需要任何额外动作。

但**升多少必须跟节奏对齐**：`release.ps1` 默认只升 `patch`（0.2.3 → 0.2.4），
而"只在大版本发"要的是 `0.2.3 → 0.3.0` —— 所以里程碑发版**必须显式给 `-BumpLevel minor`**，
否则你会一路发出 0.2.4 / 0.2.5 …，里程碑和补丁分不出来（`compareVersion` 只要求递增，不挑级别，
所以它不会报错，只会悄悄发错版本号）。

重发同版本（修包重传）用 `-SkipBump`。

##### 本地日常怎么用最新代码（不发 Release 的前提）

```bash
cd web && npm run build && npx electron-builder --dir   # 只出 win-unpacked：不打安装包、不签名，快得多
# 然后直接跑 web/release2/win-unpacked/变声工坊.exe
```

**注意**：`win-unpacked` 出来的也是 `app.isPackaged === true`，**照样会**在启动 12s 后静默检查更新。
不想让本地绿色版被更新提示打扰，设环境变量 **`VM_UPDATE_URL=off`**
（`checkForUpdates()` 会返回 `configured:false`「更新源已关闭」，不再请求网络）。

#### 一、发版前检查清单

发版前逐项确认，任何一项不通过就**不要发**。

| # | 检查项 | 怎么查 | 不通过的后果 |
|---|---|---|---|
| 1 | 该提交的都提交了 | `git status` 应为 clean | 包里的代码与仓库不一致，无法追溯 |
| 2 | 前端能构建 | `cd web && npm run build` | 打包会中途失败 |
| 3 | **签名证书密码已设** | `$env:CSC_KEY_PASSWORD` 非空 | 包不带签名 → 用户看到「未知发布者」 |
| 4 | 证书文件在 | `Test-Path certs\black-seraph.pfx` | electron-builder 签名步骤失败 |
| 5 | 更新源可达 | VM 内 `Invoke-WebRequest <更新源>/latest.json` | 用户检查更新报「无法连接更新源」 |
| 6 | 版本号没发错 | `web/package.json` 的 version | **最危险**：版本倒退会导致用户更新死循环 |
| 7 | 更新说明写好了 | 准备好 `-Notes` 或 `-NotesFile` | latest.json 的 notes 为空，用户看不到更新内容 |

##### 一键前置检查

```powershell
powershell -ExecutionPolicy Bypass -File D:\变声\scripts\release.ps1 -DryRun -BaseUrl http://192.168.1.100:9000
```

只检查不构建，输出当前版本 / 证书状态 / 产物目录 / 更新源地址。**建议每次发版先跑这个。**

#### 二、标准发版流程

##### 命令序列

```powershell
# 0) 进仓库根（脚本不依赖 CWD，但习惯上在这跑）
cd D:\变声

# 1) 设签名密码（每次新开终端都要设，不写进文件、也不写进本手册）
$env:CSC_KEY_PASSWORD = '<你的 pfx 密码>'

# 2) 前置检查（可选，推荐）
powershell -ExecutionPolicy Bypass -File scripts\release.ps1 -DryRun -Publish

# 3) 一条命令发版：打包 + 生成清单 + 发 GitHub Release
powershell -ExecutionPolicy Bypass -File scripts\release.ps1 -Publish -Notes "修复录音卡顿"

# 完事。客户端（已安装的旧版）启动 12 秒后会静默检查到，弹更新页。
```

**不再需要手动上传**：`-Publish` 会把 `exe` / `.blockmap` / `latest.json` 作为 asset 挂到
新建的 GitHub Release 上。客户端读的是永久别名 `releases/latest/download/latest.json`，
所以发新版客户端**不用改任何配置**。

不用 GitHub 时（对象存储 / 局域网 / 网盘）仍走老路子：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\release.ps1 `
  -BaseUrl https://example.com/voicemorph/download -Notes "修复录音卡顿"
# 然后手动把「待上传文件」三个文件传到 -BaseUrl 指向的位置
```

##### release.ps1 干了什么

```
1/7 前置检查        版本号 / CSC_KEY_PASSWORD / 证书文件 / 产物目录 / 更新源地址
                    └─ -Publish 时另查：gh 可执行文件、gh 登录状态
2/7 前端构建        cd web && npm run build （tsc -b && vite build）
3/7 版本号 +1       npm version patch --no-git-tag-version（不自动 git commit）
4/7 签名打包        npm run electron:build（electron-builder --win，实为 build + pack）
                    └─ -SkipSign 时改跑 npm run build + electron-builder -c.win.certificateFile=（跳过签名）
4.5 签名校验        Get-AuthenticodeSignature，Valid / NotSigned 明确提示
5/7 生成清单        node electron/make-update-manifest.cjs --dir release2 --version <新版本>
                    └─ -Publish 且未给 -BaseUrl 时，自动推导 GitHub asset 直链作为 base-url
                    └─ 自校验：清单 sha256 与磁盘文件实际值比对，不一致直接 FAIL
                    └─ 自校验：清单 version 与 package.json 一致
6/7 发布到 GitHub   gh release create v<新版本> --latest，上传 exe / blockmap / latest.json
                    └─ 自校验：实测 releases/latest/download/latest.json 的版本号是否为新版本
7/7 清理历史产物     release2 里只保留最近 2 个版本的安装包（先截断到 0 字节再删，见下）
                    + 打印待上传文件清单与体积
```

##### 常用参数

| 参数 | 用途 |
|---|---|
| `-Publish` | 打完后直接发 GitHub Release（建 tag + Release + 上传 asset + 探测别名）。**推荐** |
| `-Repo <owner/name>` | `-Publish` 的目标仓库，默认 `mouxu66/voice-morph` |
| `-SkipPrune` | 不清理 `release2` 里的历史安装包（默认保留最近 2 个版本） |
| `-BaseUrl <url>` | 更新源对外地址；清单 url 变成 `<url>/VoiceMorph-Setup-x.x.x.exe`。`-Publish` 时会自动推导，无需手填 |
| `-Notes "文本"` | 更新说明短文本，进 latest.json 的 `notes`，同时作为 Release 说明 |
| `-NotesFile path.md` | 更新说明文件（优先级高于 `-Notes`） |
| `-Mandatory` | 强制更新，前端不给「跳过此版本」 |
| `-SkipBump` | 不升版本，只重打包当前版本（重发同版本时用） |
| `-BumpLevel patch\|minor\|major` | 升版本级别，默认 `patch`。**按「〇、发版节奏」只在大版本发时用 `minor`（0.2.3 → 0.3.0）或 `major`**；非法值在任何构建之前就 FAIL（不白跑打包） |
| `-SkipBuild` | 跳过单独的前端构建（`electron:build` 内部已含） |
| `-DryRun` | 只做前置检查 |

> **清理历史产物**：`release2` 每发一次版就多一个 ~100MB 安装包，长期堆积几百 MB。
> 现在默认只留最近 2 个版本（回滚够用）。删除前先 `SetLength(0)` 截断再删 ——
> 本机的「安全删除」会把文件挪进回收站、空间不会立刻归还，截断过再删即使进回收站也只是空壳
> （约定见 `tools/hard_delete.py`）。要留全量就加 `-SkipPrune`。

##### 安装行为：升级 = 原地替换

客户端装过一次后，再装新版**不会**产生第二份安装，也不会多一个桌面图标。
这不是靠约定，是靠三处机制（2026-09-14 逐行核对 electron-builder 的 NSIS 模板确认）：

| 机制 | 落点 | 作用 |
|---|---|---|
| 安装路径 | `HKCU\Software\<GUID>` → `InstallLocation` | 安装器每次先读它，装回原处 |
| 快捷方式名 | 同键 → `ShortcutName` | 名字不变则同名覆盖；变了则 `Rename` 迁移旧图标 |
| 旧版本 | `installSection.nsh` → `uninstallOldVersion` | 装之前先卸旧版（`KeepShortcuts=true` 时保留快捷方式） |

`web/package.json` 的 `nsis` 段刻意做了三件事，改动前先看 `tools/test-packaging.cjs` 的守卫：

- `allowToChangeInstallationDirectory: false` —— 不显示目录选择页。**这是"升级绝不并存"的关键**：
  开着的时候安装向导那页路径可编辑，手滑改到别的目录就会装出第二份。
- `shortcutName: "变声工坊"` —— 钉死快捷方式名，不再从 `productName` 推导。
- `deleteAppDataOnUninstall: false` —— 卸载保留 `userData`（模型路径 / 声卡设置 / 更新源）。

> **要自定义安装目录**（例如装到 D 盘）：命令行传 NSIS 标准开关 ——
> `"VoiceMorph-Setup-0.2.3.exe" /D=D:\Apps\VoiceMorph`。
> `/D` 必须是**最后一个参数**，且路径**不能加引号**。


#### 三、更新源怎么配

##### 局域网 / 本机测试

```powershell
# 主机起静态服务（release.ps1 会在结尾把这行打印出来）
python -m http.server 9000 --directory D:\变声\web\release2
```

客户端（或 VM）环境变量指向**主机 IP**（不能用 `localhost`——VM 里的 localhost 是 VM 自己）：

```
VM_UPDATE_URL = http://192.168.1.100:9000/latest.json
```

##### 正式分发 · GitHub Releases（默认，推荐）

`DEFAULT_MANIFEST_URL` 已经写死为本仓库的最新版永久别名：

```
https://github.com/mouxu66/voice-morph/releases/latest/download/latest.json
```

`/releases/latest/download/<asset>` 由 GitHub 动态解析到**最新**那个 Release 的同名 asset ——
所以发新版只要 `-Publish`，客户端不换配置就能跟上。

要点：

1. 每个版本一个 Release（tag 形如 `v0.2.3`），asset 放三个文件：`VoiceMorph-Setup-x.y.z.exe`、
   同名 `.blockmap`、`latest.json`。**`latest.json` 必须与安装包在同一个 Release 里**，
   永久别名才取得到。
2. `-Publish` 会自动 `--latest` 标记，避免 GitHub 按它自己的规则挑错"最新"。
3. 仓库必须 **public**（私有仓库的 asset 需要 token，本项目 updater 不带 token）；
   也正因如此，release 里的安装包是**公开可下载**的。
4. GitHub 的 asset 直链会 302 到 CDN，updater 已支持跟随重定向（最多 5 跳）。

##### 正式分发 · 自建源（对象存储 / 网盘 / 局域网共享）

1. 把 `latest.json` 与安装包、blockmap 上传到同一目录
2. 发版时用 `-BaseUrl https://your.domain/path`，让清单里的 url 指向正确地址
3. 客户端 `VM_UPDATE_URL` 指向该地址下的 `latest.json`

##### 客户端怎么指向

| 场景 | 做法 |
|---|---|
| 默认（安装版） | 什么都不用做，读 `DEFAULT_MANIFEST_URL` 的 GitHub 别名 |
| 内网 / 自建源 / 调试 | 环境变量 `VM_UPDATE_URL=https://.../latest.json` |
| 要完全离线 | 环境变量 `VM_UPDATE_URL=off`（也接受 `0` / `none` / `false` / `disabled`），一个请求都不发 |

> `VM_UPDATE_URL` 优先级**高于** `DEFAULT_MANIFEST_URL`。注意：环境变量留空**不等于**关闭
> —— 留空会回落到默认 GitHub 源；要关就用 `off`。改默认源要动
> `web/electron/updater.cjs` 的常量，且**必须重新打包**才对已安装的旧版生效
> （旧版读的是它自己 asar 里那份旧常量）。

#### 四、常见错误处理

##### E1 · 用户报「无法连接更新源」

- 更新源地址填的是 `localhost` → 改成可达 IP/域名。
- 防火墙拦了 9000 → 主机放行：`New-NetFirewallRule -DisplayName "update-src" -Direction Inbound -LocalPort 9000 -Protocol TCP -Action Allow`。
- HTTP 服务没起 → 检查 `python -m http.server` 是否还在跑（关终端会一起关）。

##### E2 · 用户报「更新源返回 HTTP 404」

- 文件名对不上：清单里的 `url` 与实际上传的文件名不一致。**执行 `release.ps1` 时给 `-BaseUrl`，让脚本自己拼**，别手写。
- 文件传到了子目录：所有文件必须在**同一层**（与 latest.json 同级）。

##### E3 · 用户报「安装包校验失败：期望 xxx 实际 yyy」

- **清单与安装包不匹配**。典型场景：重打了包但没重新生成 `latest.json`，或手动改过清单。
- 对策：重跑 `release.ps1`（或者 `-SkipBump` 重打包当前版本），它会**自动校验 sha256 并在不一致时直接 FAIL**。
- 注意 `updater.cjs` 有缓存复用逻辑：同文件名内容变了会**自动重下**，不用手动清客户端缓存。

##### E4 · 用户报「装完版本号没变 / 更新一直弹」

- 说明装上去的包不是新版。检查 `latest.json` 的 `version` 是否真的比用户当前版本大。
- **发版时版本号必须递增**。`release.ps1` 用 `npm version patch` 自动 +1，别手动改回去。
- 极端情况：用户装的是「版本号倒退」的包 → 见下面「回滚」。

##### E5 · 打包报签名失败 / 包不带签名

- `CSC_KEY_PASSWORD` 没设或设错 → 重新设（具体值见证书管理处，**不落盘、不入库**）。
- 证书文件缺失 → 确认 `certs/black-seraph.pfx` 存在。
- 只想本地测：加 **`-SkipSign`**。脚本会改用 `web/electron-builder.nosign.cjs`
  把 `win.certificateFile` 置成 `null` 跳过签名；包能用，只是用户会看到「未知发布者」。
  **正式分发禁止加这个开关。**
- ⚠️ **别试图用 CLI 覆盖证书路径，走不通**。electron-builder 判断"要不要签名"用的是
  `certificateFile != null`（只看是不是 null、不看真假），于是：
  `-c.win.certificateFile=` → 空串被当成证书路径 → `ENOENT: open ''`；
  `-c.win.certificateFile=null` → CLI 不做 JSON 解析 → 被当成文件名 → `open '...\web\null'`。
  **只有在配置文件里给真正的 `null` 才生效** —— 这就是 `-SkipSign` 走 `--config` 的原因。

##### E6 · 用户安装时弹「Windows 已保护你的电脑」（SmartScreen）

- 自签证书的固有现象，**不是 bug**。用户点「更多信息 → 仍要运行」即可。
- 要消除：让用户把根证书导入「受信任的根证书颁发机构」（`scripts/gen-selfsigned-cert.ps1` 可参考生成流程）。
- 商用要彻底消除需买代码签名证书。

##### E7 · `npm run electron:build` 中途失败

- 常见于 Node 依赖缺失：`cd web && npm install` 后重试。
- 磁盘空间不足：安装包约 100MB，加上中间产物需预留 1GB+。
- 前端类型错误：先单独跑 `npm run build` 看 tsc 报错。

##### E8 · 清单选中了错误的安装包版本

- `make-update-manifest.cjs` 会**优先按 package.json 版本号精确匹配文件名**（`VoiceMorph-Setup-<version>.exe`），
  只有匹配不到才退化为「取 mtime 最新的 exe」并打警告。
- 看到那行 `⚠ 没有文件名精确匹配版本 x.x.x 的安装包` 就要警觉：说明产物命名不符合 `artifactName` 模板，
  或版本号与包名不一致。**此时不要发版**，先查清为什么没匹配上。
- 候选池只收**纯 ASCII 文件名**的 `.exe`：中文名旧包（`变声工坊-Setup-*.exe`）即使同版本也会被排除，
  避免和 ASCII 新包同时命中导致发错包；`.blockmap` / `uninstall.exe` 同样被排除。
- **自查命令**：`node tools/test-manifest-pick.cjs`（17 项，覆盖候选过滤 / 版本边界 / mtime 优先级）。
  改动过 `make-update-manifest.cjs` 或 `artifactName` 后务必跑一遍。
- 事故后果的严重性：选错包 = 把旧包的 sha256 写进清单，客户端**校验通过、静默装回旧版**，日志无异常。

##### E9 · `-Publish` 报「gh 未登录」/ 找不到 gh

- **找不到 gh**：脚本先在 PATH 找，找不到会退回 WorkBuddy 自带那份
  （`%USERPROFILE%\.workbuddy-ai\bin\gh\bin\gh.exe`）。都没有就装一个，或去掉 `-Publish` 手动上传。
- **报未登录但明明登录过**：本机 gh 默认读 `%APPDATA%\GitHub CLI`，而凭据在 `~/.config\gh`
  —— 脚本会自动补 `GH_CONFIG_DIR`（2026-09-14 实测的坑）。若仍报错，手动设：
  ```powershell
  $env:GH_CONFIG_DIR = "$env:USERPROFILE\.config\gh"
  gh auth status
  ```
- **真的没登录**：`gh auth login -h github.com -s repo,workflow`（`repo` 就够发 Release，
  `workflow` 是为了以后加 Actions 不用重新授权）。

##### E10 · `-Publish` 报「Release vX.Y.Z 已存在」

- 同一版本重发。GitHub 上先删掉那个 Release（tag 可留可删），或去掉 `-Publish` 走手动上传覆盖。
- 若只想重打包**同版本**并覆盖：`-SkipBump` + 手动覆盖 asset（`gh release upload --clobber`）。

##### E11 · `-Publish` 后别名探测失败 / 版本对不上

- 刚发布几十秒内 GitHub 的 `/releases/latest/...` 可能还没生效，等一会儿重试。
- 版本对不上：检查这次 Release 是否被标成 latest（脚本已带 `--latest`）；若手动在网页上发过
  Release，把新的那个标为 latest，或删掉多的那个。
- 别名能通但客户端仍不更新：确认 `latest.json` **和安装包在同一个 Release 里**
  （永久别名只解析同 Release 的 asset），且清单 `version` 确实大于客户端版本。

#### 五、回滚方法

##### 场景 A · 用户装坏了 / 新版有严重 bug，想退回旧版本

**关键认知**：自动更新器**只往版本号大的方向走**（`compareVersion(latest.version, current) <= 0` 就当「已是最新」）。
所以**不能靠改 latest.json 指向旧版本来回滚**——用户端根本不会降级。

正确做法是**发一个版本号更高的修复版**：

```powershell
# 1) 从 git 找到上一个好版本，把它的代码拉回来（或直接修 bug）
git log --oneline            # 找到目标提交
git checkout <good-commit> -- web/src m2_server web/electron

# 2) 正常发版（版本号会从当前值继续 +1，天然高于坏版本）
powershell -ExecutionPolicy Bypass -File scripts\release.ps1 `
  -BaseUrl http://192.168.1.100:9000 `
  -Notes "回滚：修复 x.x.x 引入的录音崩溃"

# 3) 上传，用户检查更新即会升到这个修复版
```

> 例：0.3.0 坏了 → 发 0.3.1（内含 0.2.9 的代码）→ 用户升到 0.3.1 即等于回到旧行为。

##### 场景 B · 必须让用户立刻停止自动更新

把更新源的 `latest.json` 临时下线（重命名或删掉）：

```powershell
# 自建源（局域网 / 对象存储）
Rename-Item D:\变声\web\release2\latest.json latest.json.disabled
```

GitHub Releases 上没有"重命名 asset"这回事，改用下面任一方式：

```powershell
# 方式 1：把最新 Release 标成 prerelease —— /releases/latest/ 会跳过它，别名随即失效
gh release edit v0.3.0 --prerelease --repo mouxu66/voice-morph

# 方式 2：删掉 latest.json 这个 asset（安装包留着，方便手动救急）
gh release delete-asset v0.3.0 latest.json --repo mouxu66/voice-morph

# 恢复：改回来即可
gh release edit v0.3.0 --prerelease=false --latest --repo mouxu66/voice-morph
```

用户端会报「无法连接更新源 / HTTP 404」，但**不会崩**——更新失败是静默的，
不影响本地功能。修好后改回来即可。

##### 场景 C · 单个用户被卡住，要手动救

让用户手动装旧版安装包（`web/release2/` 里保留着历史版本）：

1. 关掉应用
2. 直接运行旧版 `VoiceMorph-Setup-x.x.x.exe` 覆盖安装
   （NSIS 记住上次安装路径，会原地覆盖）
3. 若提示已安装，可先在「设置 → 应用」里卸载，再装旧版

> **注意**：`release2` 默认只保留**最近 2 个版本**（见 §二 的清理说明）。要救更旧的版本，
> 得从 git 拉回对应代码重打包，或去 GitHub Releases 里翻历史 asset 手动下载。
> 想长期留全量就发版时加 `-SkipPrune`。

**注意**：手动装回旧版后，自动更新会立刻提示升级到新版。要暂时压住，可在应用里点「跳过此版本」。

##### 场景 D · 本地开发时想重发同版本

```powershell
# 不升版本，重打包 + 重生成清单（适合修了构建配置、要重发同一版本）
powershell -ExecutionPolicy Bypass -File scripts\release.ps1 -SkipBump -BaseUrl http://192.168.1.100:9000
```

> 因为 `updater.cjs` 会按 sha256 判断缓存，重发的包内容若变了，用户端会**自动重下**，不会卡在旧包上。

##### 6.1 三条已修的事故（`m2_server/tests/test_desktop_packaging.py` 守）

**① `dependencies` 整棵树被重复打进 asar（曾占 37.4MB）**

electron-builder 会把 `package.json` 的 `dependencies` **整棵树**拷进 `app.asar`，
而 `files` 里的正向白名单（`dist/**/*`、`electron/**/*`）**管不住它**；
而 vite 早已把前端代码打进 `dist/`。实测 app.asar 5305 个条目里 5236 个是 `node_modules`
（lucide-react 19MB / react-dom 7MB / @fontsource 6.2MB…），而主进程 `web/electron/**/*.cjs`
对第三方包的 require 数是 **0**（只有 `fs`/`path`/`child_process`/`electron`）。

- 对策：`build.files` 里加一条 **`"!node_modules/**/*"`**。
- 实测：app.asar 47.1MB → 6.74MB（5305 → 71 条目）；安装包 101.5MB → 93.4MB。
  （0.2.4 实打一次验证过同一组数字：asar 6,744,704 B、安装包 93,432,832 B。）
- ⚠️ **这条排除是一刀切的，改动前先读 `web/package.json` 顶部的 `"//"` 注释**：
  它成立的前提是主进程不 require 任何第三方包。以后主进程真要引包，
  必须把排除改成白名单，否则安装版运行期 `MODULE_NOT_FOUND`。
- ❌ 别改成"把前端库挪进 `devDependencies`"：效果一样，但会让
  `tools/audit_licenses.py` 判定"载荷里的字体已不是声明依赖"——
  `@fontsource/*` 的 woff2 **真的随 `dist/` 发出去**，挪走等于漏掉 OFL 署名义务。

  > 依赖写在哪个分区是 **npm 语义**，什么进发行物是 **打包器的事** —— 两者不该混为一谈。

**② `!**/data/**` 把一份生产文件挡在包外（静默退化）**

`extraResources` 里 m2_server 那条 filter 带 `"!**/data/**"`，而 `m2_server/data/rvc_texts.txt`（4KB）
是**生产文件** —— `config.load_rvc_texts()` 读它当 RVC 训练语料模板。
它有内置 20 句兜底，所以**安装版不会报错**，只是把语料从 100+ 句场景句悄悄退回 20 句通用句。
用户只会觉得"训出来不太像"，永远查不到是打包漏了个文件。

**③ `tools/` 那条 `extraResources` 一条 filter 都没有**

后果：`tools/desktop-control/out/`（87 张调试截图 / 95MB，2026-09-19 入库）、`__pycache__`、
`.pytest_cache`、`.bak-*` 备份全部会进包。已补 filter，口径与
`tools/verify_backend_sync.py` 的 `_IGNORE_RULES` **对齐** —— 那边是唯一权威，改一处要同步另一处。

##### 6.2 改打包配置后怎么自测

```bash
cd web && npm run build && npx electron-builder --dir --config electron-builder.nosign.cjs
# 产物在 web/release2/win-unpacked/，然后跑打包门禁（产物存在时会自动逐项对照真实文件）：
.venv/Scripts/python.exe -m pytest m2_server/tests/test_desktop_packaging.py -v --no-cov
```

只想看安装包体积、不想覆盖 `release2/` 里的现役产物时，加 `-c.directories.output=<临时目录>`。

##### 6.3 一个会骗人的坑：`tsconfig.tsbuildinfo` 会掩盖类型错误

`npm run build` 是 `tsc -b && vite build`，而 `tsc -b` 是**增量**的。
本地 `web/tsconfig.tsbuildinfo` 一旦是最新的，`tsc -b` 会直接跳过检查 →
**类型错误一直存在着却从不报错**，直到某次改依赖把 program 失效。
2026-09-19 就是这样暴露出一条 `openGuideLink` 的返回类型错误（声明 `Promise<boolean>`，
实返回 `{ok,url}` 对象 → 对象恒为真值 → 调用方的失败提示永远不会触发）。

- 改完依赖跑一次 `npm run build`，**别只看 `vite build` 过没过**；
- 要确认干净结果就 `rm web/tsconfig.tsbuildinfo` 再 build。

##### 6.4 ⚠️ `verify_backend_sync.py` 的「零漂移」不等于「副本干净」

2026-09-19 同步后实测：它报 ✅ 生产代码零漂移，而副本里同时躺着
`tools/desktop-control/`（91 个文件 / **95MB** 调试截图）与 `m2_server/tests/`
（60 个文件 / 764K）—— 副本总计 121MB，几乎全是这两块。

原因：`sync_backend.ps1` 与 `backend_autosync.py` 的排除列表是**刻意最小**的
（只有 `__pycache__` / `.pyc` / `.pyo` / `.log` / `.bak` / `.tmp`），两者还被一条测试
强制保持一致（`test_backend_autosync.py::test_sync_ps1_exclude_rule_matches_autosync`）。
而 `verify_backend_sync.py` 的 `_IGNORE_RULES` 是**容忍**这些杂质
（归类为「可忽略项」而不是漂移），**不是**要求它们不存在。

两条反直觉的推论：

- **「零漂移」只证明源和副本一致，证明不了副本里没垃圾。**
- **把副本同步到零漂移，可能是把杂质也一起镜像过去。** 本次同步就把 4 个测试文件 +
  11 个截图/json 送进了副本；而「可忽略项」计数反而从 15 **降到** 1 ——
  因为两边都有就不算「副本多出」了。**计数下降不等于变干净。**

用户真正拿到的那份（安装包）不受影响：`web/package.json` 的 extraResources filter
已经排掉 `tests/` 与 `desktop-control/`（见 §6.1），实测两者都不在包里。

##### 6.6 芙宁娜皮肤在仓库里存了两份 —— **是有意的，别合并**（2026-09-19 查证）

| | `web/electron/pet/svg/` | `m2_server/assets/pet-skins/furina/` |
|---|---|---|
| 体积 | 2.5MB / 6 个 webp | 2.5MB / 6 个 webp + `skin.json` + `LICENSE` + `preview.png` |
| 文件名 | `idle` / `idle-look` / `thinking` / `conducting` / `building` / `error` | `idle` / `listen` / `think` / `play` / `build` / `error` |
| 谁读 | `pet.html` 的 `SPRITES`（**相对路径，不起后端**） | `pet_market.py`（物化到 `outputs/pet-skins/` → 皮肤市场列表 + `preview` + sheet 接口） |

**6 个 webp 逐字节完全相同，只是改了名**（`cmp -s` 全过）。看似可以直接合并，但两边的存在理由都是承重的：

- 渲染侧那份是为了让**后端挂掉时桌宠仍然出得来**（`sheetUrl()` 对 `petSkin.id === "furina"` 硬编码回退本地 `svg/`）。
  桌面宠物的定位就是“后端不可用时的降级 UI”，把它改成去读 `m2_server/` 目录 = 把降级 UI 接回它要降级的那个东西上。
- 后端那份是为了让内置皮肤能走完整市场路径：`skin.json` 描述帧数、`LICENSE` 满足署名义务、
  `_make_preview()` 从 idle 条带生成市场卡片图、`/api/pet-market/sheet/<id>` 提供 sheet。

**因此不合并。** 代价是 git 里多 2.5MB（对仓库总量无感），换来两条互相独立的不变量。
唯一要注意的是：**两边文件名不一样**，重新生成 sprite 时必须两边同步改名，
否则 `pet.html` 会静默回退到 `SPRITES.idle`、而市场里的帧数还是旧的。

#### 七、用户数据放在哪：**userData**，不是安装目录（2026-09-21 改）

| 形态 | 代码根（只读，随版本整体覆盖） | 用户数据根（可写，永不被替换） |
|---|---|---|

| 安装版 `变声工坊.exe` | `<安装目录>\resources\backend` | **`%APPDATA%\voice-morph-desktop`** |

安装版的 `userData` 目录名实测就是 `voice-morph-desktop`（不是 `productName` 的"变声工坊"）：
`backend.log` / `config.json` / `pet.json` / `updates\` 一直在那儿，包内 `package.json` 的 `name` 就是它。

数据根下两个目录（`backend.cjs` 算出根后，用 `VM_MEDIA_DIR` / `VM_OUTPUTS_DIR` 注入后端）：

- `outputs\` —— 音色市场下载（`market/`）、桌宠皮肤（`pet-skins/`）、**能力开关（`plugins.json`）**、

**为什么要改**：旧规则拿「`root` 下有 `media/` 吗」当探针，而 `media/voicebank/` 是**后端自己**

（`sync_backend.ps1`、安装包 `extraResources`）会**整体替换**的目录，用户数据等于随时被清掉。
源码模式看不出来（`D:\变声\media` 一直存在，两种规则给出同一个答案），
所以这个 bug 只在安装版上暴露。实测证据：旧位置的 `outputs/market` mtime = 当天，
而 `%APPDATA%\voice-morph-desktop\outputs` 停在首次启动那天、是空的。

##### 7.1 一次性迁移（`migrateLegacyData`，主进程启动时跑）

| 规则 | 实现 |
|---|---|
| 搬什么 | `outputs/` 整棵 + `media/` 下 `voicebank` / `clips` / `raw_videos` 三个子目录（`USER_MEDIA_SUBDIRS`）|
| 不搬什么 | `media/assets`、`media/pet-skins` 等**仓库自带**素材（整体拷 `media/` 会白搬 665MB）|
| 写入语义 | **只补不改**：目标已有同名文件一律不覆盖 |
| 删除语义 | **只拷不删**：旧位置一个字节都不动，确认无误后你自己删 |
| 记账 | 完成后写 `<新根>\outputs\.migrated-from-legacy.json`，**有记录就永不重跑** |
| 目标已有数据 | 只记账、不搬（避免覆盖新版本里刚产生的数据）|
| 失败 | 不阻塞启动，只在 `backend.log` 里留一行 `[data] 数据根 … → …` |

想重跑一次（比如手工把旧位置的数据补进来）：删掉迁移记账再启动应用。

`web/electron/**` 逐文件对账：缺失（含「被包内模块 require → 启动即崩」的判定）、
陈旧（`smoke-*` 自检白名单内允许）、多余、以及包内 `version` / `_asarVersion` 的错位报告。

**两条要注意的**（都是这次踩到的）：

1. **别以为“只差代码版本”就顺手把 6 个主进程文件一起换。** 那次 `diff` 出了
   `pet.cjs` / `pet-actions.cjs` / `preload.cjs` / `setup-ipc.cjs` / `updater.cjs` / `smoke-loadpath.cjs`
   六份差异，而 `setup-ipc.cjs` **依赖一个旧包里没有的新文件** `build-watch.cjs`

   1 个 `__pycache__` / 99 个 `.pyc`，而 `verify_backend_sync.py` 的

### 音频故障排查手册（AI 可读）

> 用途：当出现"扬声器没声音 / 恢复音频无效 / 变声后电脑无声"等问题时，供 AI 或开发者按此文档快速精确定位。
> 最后更新：2026-08-27（真实案例：扬声器显示正常但完全无声，重启后恢复）

#### 一、本机固定音频设备约定（永久有效，勿改）

| 角色 | 设备完整名 | 说明 |
|---|---|---|
| 系统扬声器 | `扬声器 (Senary Audio)` | 笔记本原生声卡，枚举顺序第 3 |
| 系统麦克风 | `麦克风阵列 (Senary Audio)` | 原生麦克风 |
| 变声虚拟声卡输出 | `CABLE Input (VB-Audio Virtual Cable)` | RVC 变声结果的写入端 |
| 变声虚拟声卡录音 | `CABLE Output (VB-Audio Virtual Cable)` | 微信/游戏从这里录到变声后的人声 |
| Steam 虚拟设备 | `扬声器/麦克风/内部 AUX (Steam Streaming ...)` | **永远不能设为默认设备**，枚举顺序靠前（第 1），是历史事故根源 |

铁律：任何 apply/restore/reset 兜底逻辑都绝不能把默认设备设到 Steam 设备上。判断时必须用「描述 + 提供方」完整名（如 `扬声器 (Senary Audio)`），只看描述"扬声器"无法区分同名设备。

#### 二、变声功能的音频链路（rvc_live.py 实现）

```
麦克风阵列 (Senary Audio)
   ↓ 输入
RVC realtime_gui.py（D:\RVC\realtime_gui.py --auto-start）
   ↓ 实时推理输出
CABLE Input (VB-Audio Virtual Cable)          ← RVC 的输出设备
   ↓ 虚拟声卡内部转发
CABLE Output                                   ← 系统默认【录音】设备被切到这里
   ↓
微信/游戏/QQ 等（它们的"麦克风"= CABLE Output = 变声后的人声）
```

关键点：
- 一键开启（`POST /api/rvc/live/start`）：备份当前默认设备 → 录音默认切到 CABLE Output → 后台拉起 RVC 窗口；**系统播放（扬声器）不被改动**，所以正常情况下不会导致"电脑放音乐没声音"。
- 一键关闭/窗口关闭：restore 备份还原，失败再 reset 兜底（找非 CABLE/非 Steam 的真实设备，优先 Senary）。
- 相关文件：`m2_server/rvc_live.py`（编排）、`m2_server/audio_config.ps1`（设备切换与还原）、备份文件 `%LOCALAPPDATA%\rvc_audio_backup.txt`。
- **闭环实测记录（2026-08-27，通过）**：start → 录音三角色=CABLE Output、播放三角色=扬声器(Senary) 不动、RVC 进程存活；stop → restore=true，录音三角色回到麦克风阵列，备份文件删除。参照此基准判断回归。

#### 三、故障树（按症状查）

##### 症状 A：设置里默认设备全对，但扬声器完全无声
**2026-08-27 已发生并解决的真实案例。**

- 判定方法：运行 `tts_trial/audio_probe.py`（播音 + IAudioMeterInformation 测峰值），
  结果写 `tts_trial/probe_out.txt`：
  - `peak > 0.01` → 链路通，问题在别处（音量/应用级静音）
  - `peak = 0` 且耳机有声 → 扬声器端点卡死
- 根因：Senary 驱动处于「等待系统重新启动才能完成上一次操作」的挂起态
  （用管理员跑 `pnputil /restart-device <设备实例ID>` 可确诊，会报"设备正在等待系统重新启动"；
  此时 `Disable-PnpDevice` 报"常规故障"，`Enable-PnpDevice` 假成功）。
- 解法：**重启电脑**（唯一解）。重启后重跑 audio_probe.py 确认 peak > 0。
- 备注：插耳机有声说明驱动总栈活着，仅扬声器端点是"僵尸"，与音量/默认设备无关。

##### 症状 B：变声开始后没声音 / 恢复音频无效
1. 先看默认设备被切到哪：`powershell -File m2_server/audio_config.ps1 -action status`
   （或 `-action diag` 看全量设备状态。state 含义：1=Active 2=Disabled 4=NotPresent）
2. 若播放默认变成了 Steam 设备 → 不应发生，检查 audio_config.ps1 是否为修复版
   （特征：包含 `FindReal` 且匹配 `Steam Streaming` 排除逻辑），并手动 reset：
   `POST /api/rvc/live/reset`
3. 若录音默认还在 CABLE Output 但 RVC 窗口已关 → 备份残留，调 `/api/rvc/live/reset`；
   服务器启动时会自动做同样的清理（见 rvc_live.py `_auto_clean()`）。
4. 若恢复后再遇症状 A（播放端点仍无声），转症状 A 流程。

##### 症状 C：变声功能本身不可用
依次检查：
1. 主服务 8000 存活：`GET http://127.0.0.1:8000/api/health`（必须用 `D:\变声\.venv` 启动）
2. `GET /api/rvc/live/status` → model_ok（缺 `D:\RVC\logs\<音色名>\<音色名>.pth`+index 则要先训练）
3. CABLE 设备存在且 Active（diag 里 state=1）；VB-Cable 被禁用会导致 apply 找不到 CABLE Output
4. RVC 窗口秒退 → 看 `D:\RVC\logs\<音色名>\realtime_gui.log`

#### 四、给 AI 的运维工具箱

| 脚本 | 作用 | 结果落盘 |
|---|---|---|
| `tts_trial/audio_probe.py` | 播 440Hz 测试音 + 测默认扬声器峰值电平（判定"真有无声"的金标准） | `tts_trial/probe_out.txt` |
| `tts_trial/audio_diag.py` | 设备全量状态 + audio_config.ps1 diag + 服务状态 + 备份文件是否存在 | `tts_trial/diag_out.txt` |
| `tts_trial/endpoint_test.py` | 枚举全部端点 + 测试目标端点 WASAPI 共享模式初始化 | `tts_trial/endpoint_test.txt` |
| `tts_trial/audio_vol_check.py` | 主音量/静音 + 各会话音量 | `tts_trial/vol_out.txt` |

约定（重要）：
- 需要提权（UAC）的脚本**必须放在纯英文路径**（如 `C:\Users\<你的用户名>\AppData\Local\Temp\`），
  中文路径会让 `Start-Process -Verb RunAs` 的参数乱码 → 提权进程静默失败（exit 0 无日志）。
- 终端长任务会被超时杀死：验证类脚本一律结果写文件 + `Start-Process` 分离运行。

### 嗓音保存评测协议（大创研究层）

> **现役**。与 `tools/voicebank_eval.py` 的实现一致，看到不对就该改它。
> 代码：`tools/voicebank_eval.py`（矩阵 / 测量 / 统计）·
> 门禁：`m2_server/tests/test_voicebank_eval.py`（99 条）。
> 指标口径来自 `docs/交接-AI必读.md` 与 `tools/voice_metrics.py`。
>
> 一句话：**这份文档是把「嗓音保存」从一个功能变成一项研究的那一环** ——
> 定义自变量、因变量、对照、被试、执行步骤和诚实边界。
> 没有它，代码只是工具；有了它，才能得出可写进申报书与论文的结论。

---

#### 1. 研究问题

| # | 问题 | 为什么问它 |
|---|---|---|
| **RQ1** | 参考音时长从 3s 增到 60s，复现质量如何变化？**收益在哪一档饱和？** | 直接回答「最少要录多久」——对录制困难的人群是最关键的一个数 |
| **RQ2** | 不同文本条件下（同文 / 跨文 / 跨情感 / 长句），同一参考音的质量差异有多大？ | 「保存下来的声音」能泛化到什么程度；同文好但跨文崩 = 保存失败 |
| **RQ3** | 客观指标与人工主观评分（MOS / ABX）的相关性如何？**能否替代人工听测？** | 决定能否做**自动质量门禁**；也是"自动评价"这类工作的通用问题 |

---

#### 2. 对照对象（★ 申报书铁律要求，必须写清）

**对照是「参考音时长」，不是「模型」。** 依据来自 ALS 官方指南
（`youralsguide.com/voice-banking`，ALS Association 生态）原文口径：

| 方案 | 录制门槛 | 出处 |
|---|---|---|
| 传统声音银行（Acapela / SpeakUnique / The Voice Keeper / ModelTalker） | **50–200 句** | 📚 同上，**二手转述，投稿前需核一手** |
| 云端 AI 克隆（ElevenLabs 等） | **1 分钟**得 instant clone，**10+ 分钟**才接近本人 | 📚 同上 |
| Apple Personal Voice | 免费、端侧 | 仅 iPhone / iPad / Mac |
| **本项目** | **秒级参考音（3–60s）** | 待测：质量代价有多大？ |

★ 注意：**不要**把「Windows 本地没人做过」当主要卖点（弱论证 —— Apple 同样免费 + 端侧）。
真正的支点是**离线可用性**：ALS 官方指南原文点名云端 AI 克隆
*"在医院、护理机构、飞机上无法使用"*，而行动受限人群长期就在这些环境。
**离线对他们是刚需，不是加分项。**

---

#### 3. 实验设计

##### 3.1 变量

| 类型 | 取值 |
|---|---|
| **自变量** | 参考音时长 **3s / 10s / 30s / 60s**（默认档；300s 需自备长录音脚本） |
| **自变量（条件）** | `same` 同文 · `cross` 跨文 · `emotion` 跨情感 · `long` 长句（>30 字） |
| **因变量（客观）** | `emb_sim` 声纹余弦 · `hnr` · `h1_h2` · `spectral_tilt` · `jitter_local` · `shimmer_local` · `asr_overlap` |
| **因变量（主观）** | `mos`（自然度 5 分制） · `abx`（与真实录音二选一，1=选对） |
| **控制变量** | 同一说话人 / 同一麦 / 同一房间 / **同一批录音切分** |

##### 3.2 指标方向（★ 写反 = 结论整个反掉）

与 `docs/交接-AI必读.md` §8.1 同口径，代码里集中在 `HIGHER_IS_BETTER`：

| 指标 | 方向 | 备注 |
|---|---|---|
| `emb_sim` / `hnr` / `asr_overlap` | **越大越好** | |
| `spectral_tilt` | **越大越好**（更接近 0） | ⚠️ 与其余指标不同向，三灯文档记过这个坑 |
| `h1_h2` | **越小越好** | 越大 = 滚降越陡 = 越挤压（**本机合成信号实测标定**，与文献通用表述相反） |
| `jitter_local` / `shimmer_local` | **越小越好** | |

##### 3.3 规模（默认）

```
12 名说话人 × 4 个时长档 × 4 个条件 = 192 个合成样本
听测：24 名被试（每人不重复抽 40–60 个样本）
```

规模可调，但**说话人少于 8 人时 RQ1 的主效应不可信**，别为了省事砍到 3–4 人。

---

#### 4. 录音协议

##### 4.1 环境与设备（每名说话人必须完全一致）

- **房间**：安静、关窗、关空调/风扇；优先小房间（混响低）。避免走廊、教室。
- **麦克风**：全程**同一支**；USB 电容麦或耳麦均可，但别中途换。
- **距离**：嘴到麦 15–20cm，偏轴约 30°（减少爆破音）。
- **增益**：固定，**峰值不超过 −3 dBFS**（削波会直接毁掉 HNR 与 jitter）。
- **格式**：WAV，44.1k 或 48k，单声道（双声道也可，评测前会转单）。

##### 4.2 录制内容

1. **参考录音**：**一次连续录完整脚本**（`python tools/voicebank_eval.py corpus` 打印）。
   - ★ 必须一次录完、不中断 —— 各时长档是从**同一段录音**做前缀截取，
     否则「10s 档比 3s 档好」可能只是第二次录得更放松。
2. **真实录音（truth）**：每个条件念一遍，共 4 条：
   `truth/<说话人>/same.wav` · `cross.wav` · `emotion.wav` · `long.wav`
   - 这是 ABX 的对照，**必须有**；缺了就只能听绝对质量，测不出相似度。

##### 4.3 切分参考音

```
refs/<说话人>/3s.wav  10s.wav  30s.wav  60s.wav
```

- ★ **对齐到句末**：取「不超过目标时长的最大整句前缀」，别在句子中间硬切
  （半句话会同时劣化自然度与可懂度，把自变量污染掉）。
- 在 `matrix.json` 或记录表里**记下每档的实际秒数** —— 报结论时要用实际值，
  不能拿标称值冒充（"3s 档"实际是 2.4s 就写 2.4s）。

**用 `split` 子命令一次切完**（四档必须出自同一次录音，见 §4.2 的控制变量要求）：

```bash
python tools/voicebank_eval.py split --exp <实验名> --speaker <说话人> \
    --source <整段录音.wav>
```

产出 `refs/<说话人>/{3s,10s,30s,60s}.wav` + `<exp>/split.json`。`split.json` 里
逐档记了 `duration_s`（标称）/ `actual_s`（实际）/ `aligned` / `cut_reason` /
`deviation_s`，**报结论时就取 `actual_s`**，别再手工抄。

两条实现上的守卫（都踩过坑，别绕开）：

- **对齐有 25% 上界**：静音探测找不出目标附近的句末时**退回硬切**并记
  `aligned=false`，而不是一路往前找。否则「60s 档」会被对到 35.4s，而 `analyze`
  按标称 `duration_s` 分组 —— 自变量就被静默改了。
- **噪声门限自适应 + 逐级放宽**：先按整段 RMS−15dB 试，探不到静音再依次放宽到
  −30/−27/−24/−21/−18dB。单一门限会正好压在探测边缘（实测同一段音频 −34.8dB 判
  0 段、−30dB 判 2 段、−20dB 判 34 段）。若显式传了 `--noise-db` 则**不放宽**，
  保证结论可复现。切完请人耳确认切点，`split.json` 里的 `silence_spans` 是追溯依据。

##### 4.4 录音质检（录完立刻做，别攒到最后）

- 跑 `python tools/voice_qc.py --dataset <目录>` 看语速与响度
  （**语速 > 6 字/秒要重录** —— 项目实测语速过快会直接劣化可懂度）。
- 抽听 2–3 条确认无爆音、无电流声、无旁人说话。

#### 5. 合成协议

对矩阵里每一格生成一个样本，落到：

```
samples/<说话人>/<时长档>/<条件>.wav
```

- 用本项目现役链路（`m2_server/qwen3_tts.py` 小样本克隆；需要 RVC 时另记）。
- ★ **用 `tools/voicebank_synth.py` 逐格合成**（2026-10-08 新增）：在此之前
  这一环没有工具，48 格只能手工点 —— 而手工点会产生两个**静默**错误：
  挑错参考音（自变量标签错，`analyze` 照常出报告）、漏一格（错因指向统计而非采集））：

  ```bash
  python tools/voicebank_synth.py --exp vb01 --dry-run   # 先看会合成哪些格
  python tools/voicebank_synth.py --exp vb01             # 真跑；断点续跑
  ```

  每格用**自己那一档**的参考音注册临时音色后调 `POST /api/tts`，跑完即删临时音色。
  前置：后端在跑（app 或 `python m2_server/server.py`）；后端认的 media 目录
  与 `--media-dir` 不一致时它会报「音色不存在」并提示排查方向。
- **必须记录**：引擎、模型版本、随机种子（若可设）、生成时间。
  → `provenance.json` **由上面的工具自动落盘**（每格记参考音/文本/实际时长/时间；
    该链路不暴露随机种子，字段如实写 `null`，不编）。
- ★ **ref_text 默认不带**（走纯声纹）：参考音是录音脚本的**前缀截取**，
  没人知道第 3 秒停在哪句中间 —— 猜出来的稿子与音频不符，只会污染
  「复刻质量」这个因变量。要带就由操作者用 `--ref-texts <dir>` 显式给每档一份 txt。
- 每格建议生成 **1 条**（192 格）；若算力允许可生成 3 条取中位数，
  但那会把样本量乘 3，听测成本也跟着涨 —— **先按 1 条跑通全流程**。

---

#### 6. 主观听测协议

##### 6.1 被试

- **24 人**（同学即可），听力正常、无语音学专业训练（避免"专家效应"）。
- 每人只听 **40–60 个样本**（超过会疲劳，后段评分不可信）。
- 样本**随机分配**，同一被试不重复听同一格的多个版本。

##### 6.2 播放

- 耳机（**同一副**），音量固定，环境安静。
- **盲测**：界面不显示说话人、时长档、条件。
  ⚠️ 2026-10-05 更正：此前这里写"项目已有盲听页（`ab_api.py`）可直接复用"——
  那条**只适用于产品里的音色 A/B 试听**，它不产研究用的评分表。研究听测
  走下面的 `listen` 子命令（见 §6.4）。

##### 6.3 评分

| 任务 | 口径 |
|---|---|
| **MOS（自然度）** | 5 分制：5 完全自然 / 4 自然 / 3 一般 / 2 明显机械 / 1 难以接受 |
| **ABX（相似度）** | 合成样本 vs 真实录音（`truth/`），二选一，记 1 = 选对 |

★ **ABX 必须真的放真实录音做对照**，不能拿两个合成样本互比 —— 那测的是偏好不是相似度。

##### 6.4 生成听测材料（`listen` 子命令）

**不要手工拼文件名、手工遮条件名** —— 手工遮会留下线索（文件名、目录结构、
播放顺序都是线索），而一旦听者猜到"这条是 60s 档"，评分就被先验预期污染，
RQ3 想检验的东西正好被实验条件本身破坏了。

```bash
python tools/voicebank_eval.py listen --exp vb01            # 默认种子 20261005
```

产出三个文件（落在 `<exp>/listen/`）：

| 文件 | 给谁 | 内容 |
|---|---|---|
| `sheet.csv` | **发给听者** | 只有 `blind_id`（`S-0001`…）+ 空的 `mos` / `abx` / `note` 列 |
| `key.csv` | ⚠️ **研究者自己留，不发** | 盲号 → `sample_id` / 说话人 / 档位 / 条件 / 音频路径 |
| `playlist.txt` | 播放者 | 随机化后的播放顺序（照着放，别自己翻目录） |

三条设计约束（都踩过）：

- **`sheet.csv` 里绝不能有身份信息**。有单测逐字检查表头与正文不含
  说话人名、档位、条件、`.wav` 等任何线索。
- **播放顺序随机化，种子落盘**。听者疲劳会随时序累积（后听的打低分），
  固定顺序 = 把"位置效应"混进"条件效应"。同种子必然复现同一顺序。
- **缺 `truth` 的样本单独列**：ABX 需要对照，没对照就只能评 MOS。
  工具会报 `n_missing_truth`，不静默少给。

##### 6.5 汇总与落盘格式

每名听者填完自己的 `sheet.csv`（**改个名，别覆盖原件**），然后合并：

```bash
python tools/voicebank_eval.py merge-listen --exp vb01 \
    --sheets 听者甲.csv,听者乙.csv,听者丙.csv
```

产出 `<exp>/subjective.csv`，直接喂给分析：

```bash
python tools/voicebank_eval.py analyze --exp vb01 --subjective subjective.csv
```

合并口径（三个决定，都不是随意的）：

- **先算每个人的分，再对人数平均**（等权听者）。直接对所有行求平均会让
  "评得多的听者"权重更大 —— 而评得多往往只是因为他没跳题，与评分松紧无关，
  那属于噪音权重而非信息权重。
- **多给一列 `n_mos` / `n_abx`**：`analyze` 只认 `sample_id` / `mos` / `abx`
  三列（多出来的列会被忽略），但研究者需要看到每个样本被几个人评过。
- **非法的值剔除并上报，绝不夹紧**。`mos=9` 或 `abx=7` 会被记录进 `invalid`
  并跳过该字段 —— **不夹到 5**，否则一条填错的数据会悄悄混进相关性分析。
  字段是各自独立校验的：`mos` 非法但 `abx` 合法时，该行仍以 `abx` 存活
  （丢掉整行等于把听者一条有效判断也删了）。

> ★ 这次是真的要真人了：工具能把材料备好、把分数合好，
> 但**它不会替人听**。"24 名听者"这一步没有任何代码能替代。

#### 8. 分析与产出

- **RQ1**：各时长档的指标中位数 → 主效应；`saturation_point()` 给出饱和档位
  （判据：相邻档增量 < 总增益的 **10%** —— 这是工程阈值，报结论时要连同这个数字一起说，
  别当成客观真理）。
  ★ 返回值有 **三种**，报结论时别混为一谈：
  - `saturated` —— 找到饱和档，可以直接说「录到 N 秒就够了」
  - `still_climbing` —— 逐档都在涨，**尚未饱和**（别硬指一个档位）
  - `non_monotonic` —— 指标随档位**出现回退**，趋势不成立，**饱和点不可判定**
  - 返回 `None` = 档位不足 2 档 / 总增益 ≤ 0，**数据不足以判定**
  （`non_monotonic` 这一档是端到端演示实测补的：旧判据会把
  「首个增量是负的」误报成「第一档就饱和」，而它根本没饱和。）
  ★ **自空间天花板（2026-10-11 实测）**：`emb_sim` 是 Qwen 自空间余弦（与合成同源模型），
  同人分被压到 0.978–0.991（30s 档 100% ≥0.98）、异人最高只到 0.955 ——**阈值型门禁几乎
  没有分辨空间**；同一批样本上 CAM++ 独立声纹是同人 0.65–0.83 vs 异人 ≈0.15，对时长的
  敏感度约 12 倍。→ 门禁与饱和判据**以独立声纹为主、自空间为辅（或双门槛）**；证据见
  `m2_server/tests/data/dachuang-2026-10/pilotC-公开语料证据/dual_embed/README.md`
  （边界：n=3、公开语料拼接参考音、非被试，只作方法与量级证据）。
  ★ **已落地的门禁**：`tools/voice_dual_gate.py`（纯函数）—— CAM++ 主判两档
  `cam_pass=0.53` / `cam_warn=0.38` + 自空间下限 `qwen_floor=0.97`，由实测两簇间隔按 7:3
  推导（不是手填）；判词 `pass / review / reject / unknown`（`unknown` = 未测）。
  在线路径（嗓音档案随访）见 `voicepreserve.assess_sample` / `add_followup`，
  回归测试 `m2_server/tests/test_voice_dual_gate.py` 拿 144 对实测分数重放。
  ⚠️ 这三个数字**只对本项目这条路（Qwen3-TTS 克隆 + 16k 中文 + 公开语料标定）负责**：
  RVC 变声验收（`voice_qc` 的 100 分制 `emb_sim` 项）刻度不同，要改先在本机重标。
  ★ **RVC 变声验收实测（2026-10-11，本项目自己的标定，不是照搬）**：现役 `emb_sim` 的
  **≥0.95 站不住** —— 12 对同人只有 6 对过线（**误杀一半**），异人上界 0.9534 离 0.95 只差 0.0034。
  **也不能照搬上面那三个数**：拿 `voice_dual_gate.DUAL`（`cam_pass=0.53`）重放同一批，同人只过 2/12 ——
  两条路径的刻度不可互用（实测）。这一批两把尺子的同人/异人簇**都重叠**
  （自空间 0.9108 ≤ 0.9534；CAM++ 0.2659 ≤ 0.4859），即**任何绝对阈值都有错判**；
  而**相对判据可行**：同一份输出 vs 全部 8 支参考音，CAM++ **12/12** 都把自己的目标参考排第 1
  （余量 +0.024 ~ +0.516），自空间只有 8/12（余量最小 −0.021）。→ 该换的是**判法（相对余量）**，
  不是尺子；自空间不该当准入线。
  **已落地（2026-10-11）**：`emb_sim` 项的 pass 换成**相对余量**
  （`CAM++(输出, 目标参考) > CAM++(输出, 输入者本人)`，即 `voice_qc._voice_margin`）；
  `results.json` 的 `prod_margin` 是它的从证据重放：**12/12 通过，最小余量 +0.2137**；
  问不出来时（自转换 / CAM++ 权重未缓存）如实记「未测」（`pass=null`，总判定放行）。
  分制与另三项未动；参考音 **<5s** 时在结果里提示（验收 `warnings`、随访 `rec.warnings`，
  口径唯一定义在 `m2_server/speaker_sep.MIN_REF_SECONDS`；**提示，不作废判定**）。
  证据：`m2_server/tests/data/dachuang-2026-10/rvc-qc-判据标定/`（96 对逐条分数 `pairs.csv` + `results.json` + `report.md`）；
  重标：`tools/voice_qc_ruler_calib.py --reuse`；回归：`m2_server/tests/test_voice_qc_ruler_calib.py` +
  `m2_server/tests/test_voice_qc_emb_judgement.py`（后者拿证据重放**上线判据**）。
  边界：3 说话人 / 4 支模型 / 12 同人对；参考音 4.2~30s 不等（卡通市场音色只带 4.2s preview，
  是 CAM++ 簇重叠的主因），换素材要重标。
- **RQ2**：条件间指标中位数对比；重点看 `cross` 相对 `same` 掉多少。
- **RQ3**：Spearman 秩相关（对 MOS / ABX 分别算）。

### 减负实测协议（大创减负层）

> **现役**。与 `tools/voice_load.py`（发声负荷测量）和 `tools/vfi_score.py`（量表计分）
> 的实现一致，看到不对就该改它们。
> 门禁：`m2_server/tests/test_voice_load.py` + `m2_server/tests/test_vfi_score.py`。
>
> **与 [`docs/附录-可执行规程.md`](嗓音保存评测协议.md) 的关系**：那边回答
> "复现的声音**像不像、录多久才够**"（RQ1–RQ3，质量边界）；这边回答
> "用它录课，**嗓子到底省多少**"（RQ-B，节省量）。两条合起来才是"减负"的完整论证：
> **质量是前提（那边），节省是结果（这边）** —— 缺任何一半，评审问"那减负本身
> 到底能不能成？"都接不住。

---

#### 1. 三层证据结构（"减负"不是口号，是三层可辩护的证据）

| 层 | 内容 | 性质 | 状态 |
|---|---|---|---|
| **L1 发声时长节省**（最硬） | 同一节课，本人全程口播 vs 讲稿转旁白流程，量**发声总时长 / 连续发声时长 / 发声占空比**下降多少 | **客观、可复现、链路内可测** | 本协议 + `voice_load.py` 已落地，**待实测** |
| **L2 主观量表**（探索性） | VFI（嗓音疲劳指数）前后测 + VAS（0–100）每次录课前后自评 | 小样本、自评、**只看趋势不作硬结论** | `vfi_score.py` 已落地，**待实测** |
| **L3 文献因果链** | "发声时长/负荷下降 → 嗓音疲劳减轻"在职业嗓音文献被接受（教师嗓音干预 RCT，如 ReSt 应用 📚 立项后核验一手） | 引文，非本项目数据 | 申报书已按此口径写 |

机制就一条：**你自己不用开口了**。L1 直接测"不开口省了多少"；L2 探"主观感觉有没有跟着变"；
L3 补"L1 → 疲劳减轻"的文献后半段。三层都不越红线：**测的是发声时长与自评，不是疗效**。

#### 2. 研究问题（减负层）

| 编号 | 问题 | 类型 |
|---|---|---|
| **RQ-B1（主）** | 同一节课，"讲稿转旁白"流程相对"本人全程口播"，**发声总时长、最长连续发声、发声占空比**下降多少？ | 定量、within-subject |
| **RQ-B2** | 走旁白流程一段时间后，VFI/VAS 自评是否出现下降趋势？ | 探索性（n 小，只看方向） |
| **RQ-B3** | B 侧产物的复现质量能否过自动门禁？ | **直接引用 RQ1 的结论**——质量前提不成立，节省量无意义 |

#### 3. A/B 实验设计

##### 3.1 两侧定义

| 侧 | 内容 | 本人开口部分 |
|---|---|---|
| **A（基线）** | 同一讲稿，**本人全程开口讲完整课**（一条连续录音）。★ 基线要尽量接近真实讲课：**对着 PPT/教案自然讲**（允许停顿、重复、补充）；逐字念稿只可用于链路彩排；**绝不能用合成音念 A 侧**（用工具产物当基线 = 循环论证，必得 100% 减负）。理由与 5 页 PPT 做法见 [`大创申报-2026-10/pilot-讲稿-10分钟.md`](大创申报-2026-10/pilot-讲稿-10分钟.md) §0.5 | 全部 |
| **B（流程）** | 讲稿/备注 → 平台逐页合成旁白（复用本人音色，走既有讲稿录课链路） | **只有补录/改稿重录的开口录音**；写稿、审听、播放**不计**（没有口腔发声，也没有录音可测） |

★ B 侧本人发声**用录音文件计量**（把 B 流程里本人开口的每条录音都存下来喂给工具），
**不人工估时** —— 人估的"大概几分钟"既不可复现，也会往对自己有利的方向漂。

##### 3.2 计量口径（★ 报结论时连同口径一起说）

- "发声" = **能量法**：ffmpeg `silencedetect` 自适应门限找静音（与嗓音保存协议 §4.3
  切档是**同一套实现**），发声段 = 全程 − 静音段。它量的是**发声活动时长**
  （speech activity time），**不是**严格生理 phonation time：呼吸声、桌面噪声可能计入，
  < 0.3s 的换气间隙算连续发声。职业嗓音文献的对应概念是发声时间剂量（time dose）
  与占空比（duty cycle，Titze vocal dose 框架）📚 —— 能量法是可接受的近似，别混同。
- **电平必须达标**（录音协议 §4.1：同麦、峰值 ≤ −3 dBFS）：低电平录音会被门限整段
  吞成"没发声" → 占空比假低 → 节省率假高。每次测量**先看 JSON 里的 `peak_dbfs`**。
- A/B 两侧**用同一组参数**测（同 `--min-silence`、同门限策略），参数随 JSON 落盘。

##### 3.3 控制与顺序

- 同一人 / 同一麦 / 同一房间 / **同一讲稿**（内容变了就不是"同一节课"）。
- 顺序效应：讲同一遍课第二遍更熟。**AB / BA 交替平衡**（一半被试先 A 后 B，
  一半相反），两轮至少隔一天。
- B 流程里本人开口的录音命名即脱敏（`s01_retake_01.wav`），从命名开始不带真名。

##### 3.4 规模

- **Pilot：3 人**（与《真人小样本试跑-执行卡》同批被试可合并：录完音色顺手做 A/B）。
- **主实验：12 人**（与 §2.4 主实验同批师范生），AB/BA 交叉 + VFI 前后测。
- 写进申报书时必须标注：n、健康说话人、能量法口径、**不外推总体**。

#### 4. 指标定义

| 指标 | 定义 | 来源字段 |
|---|---|---|
| 发声总时长 | 发声段时长之和 | `phonation_s` |
| 发声占空比 | `phonation_s / total_s` | `duty_cycle` |
| 最长连续发声 | 最长发声段（< min_silence 的间隙算连续） | `longest_continuous_s` |
| **发声时长节省率** | `(A.phonation − ΣB.phonation) / A.phonation` | `saving.saving_rate` |

> A 侧发声为 0 时节省率返回 `null`（未定义），工具**绝不**编 0% 或 100%。

> **A 侧口播不可能自动化** —— 被测变量就是"本人口腔发声时长"，让 TTS 代念 A 侧
> 是循环论证（用"不用开口"当基线必然得出"减负 100%"），数据的"人"字就没了。

#### 6. 主观量表（L2，探索性）

- **VFI**：19 条、0（从不）–4（总是），三因子（11 用嗓后疲劳与嗓音恶化 /
  5 躯体不适 / 3 休息后改善）📚 Nanjundeswaran et al., 2015, *Journal of Voice*，
  立项后核验一手；是否存在经信效度检验的中文版 ❓ 未核验。**题目原文不入库**
  （本仓开源 + 量表条目有版权）：研究者从一手文献誊录进自己的问卷，回收按
  `v01..v19` 填 CSV，本工具只做计分。**未核验前只报因子分，不做分档/诊断。**
- **VAS**：0–100 单条自评，每次录课前、后各一次（`vas_pre` / `vas_post`）。
- **知情同意**：按嗓音保存评测协议 §9 执行（用途、只留本机、可随时退出、留签字件）。
- 报告口径：**探索性指标**，只描述趋势方向，不作显著性硬结论。

#### 7. 文献因果链（L3）

- 申报书的写法：**"减负的技术前提是声音像你且像真人，这个前提的质量边界正是
  本研究要回答的"**（§2.1 已写）—— 那是**前提**；本协议补**结果**：机制有文献
  （L3）、手段有平台、节省量有实测方案（L1）。
- 前半段（发声时长下降）自己测；后半段（时长下降 → 疲劳减轻）**引职业嗓音文献**，
  不自己声称。ReSt 等教师嗓音干预 RCT 属这一类证据 📚 立项后核验一手再引。

#### 8. 诚实边界与红线

1. **测的是发声时长与自评，不是治疗效果**；全文无"已减轻嗓音疾病"类表述。
2. B 侧本人开口可能为 0 → 如实写"该课本人口腔发声 X 分钟（B）"，**不写成
   "零负担"**：写稿、审听的时间成本是真实存在的，本协议只对**发声**负荷负责。
3. 能量法口径的近似性（§3.2）随结论一起报；低电平素材的测量结果不采信。
4. 申报书口径只写"定位/拟应用 + 实测方案"，拿到 L1 数据前**从不说"已减轻"**。
5. 结论不外推：n、人群、单机单卡、中文 —— 同嗓音保存协议 §9 的边界条款。

#### 9. 申报书粘贴模板（拿到数据后照填，别手改口径）

> **减负实测（RQ-B，within-subject，n=3 pilot / n=12）**：同一讲稿下，本人全程口播
> 与讲稿转旁白两种流程的发声负荷对比显示：发声总时长由 X 分钟降至 Y 分钟

##### 步骤（核心场景 B：② 半自动 / 文字转语音 —— 用户主场景之二）

1. 先在网页上合成一段文字语音（单段合成）；
2. 回到「微信发送 → ② 半自动」，点「开始播放」，按提示去微信按住 Alt；
3. **播放那几秒里**点一下「掌声」（或警报）；
4. 松开 Alt 发送 → 点开听。

##### 步骤（核心场景 C：实时变声页边变声边打音效 —— 2026-09-24 新增，现在是**主场景**）

为什么它升级成主场景：实时变声页的自我监听回环（`rvc_monitor.py`）**tap 的正是 CABLE Output**，
所以写进 CABLE 的音效**你自己耳机里也听得到** —— 点击→当场听到→对方也听到，是这个功能唯一
闭环的用法。场景 A 没有这个回环，点完只能回微信里回放验证。

前置同 A，另需在实时变声页看到「音效声板」那一块（挂在 02 变声控制台的开始/停止按钮下方）。

1. 进「实时变声」（默认 RVC 实时 tab）→ 选好音色 → 点「开始实时变声」；
2. 等状态变成"运行中"（模型加载约 10~20 秒），**打开「自我监听」**（为了耳朵验证，不是必需）；
3. 微信里打开与自己的聊天窗，**按住 Alt** 开始说话（持续说，别停）；
4. 说到一半，去网页点一下「💥 爆炸」；
5. 松开 Alt 发送 → 在微信里点开这条语音；
6. **再听耳机**：第 4 步点下去的那一刻，自我监听里应同时有"你自己的变声"与那声爆炸；
7. 切到「千问变声」tab 重做一次（说话 → 等它播出目标音色 → 那一秒点掌声）。

##### 预期现象

- 语音消息里**同时**听到人声与音效（顺序取决于你点的时机，两者是叠加而非拼接）；
- 点格子时页面立刻高亮（乐观 UI），**不因「正在发送/正在播放」而变灰不能用**；
- 多次点同一格子 = 音效重新播一遍（抢断），不是排队；
- 点「停止」后当前音效立即停。

##### 观测点

- 后端日志：`board_worker` 只应启动**一次**（后续点击复用常驻进程）；
- `outputs/soundboard_stats.json`：每次成功播放 +1（catalog 的 `count` 同源）；
- 微信那条语音的**时长** ≈ 你按住 Alt 的时长（声板不该改变录音长度）。

##### 失败判据（命中任一条即不合格）

| # | 判据 | 说明 |
|---|---|---|
| G1 | 点格子后**没有任何声音进入语音消息** | 先查系统录音设备是不是 CABLE Output、以及 `play` 是否返回 503 |
| G2 | **按下 Alt 的录音被中断**（消息没发出去 / 变成了文字或图片） | 这就是设计稿里那个未验证的风险：焦点离开微信导致录音取消 → 退路是「预混模式」或全局热键（P3） |
| G3 | 语音消息里音效**盖过人声**或明显削波失真 | 把 `gain` 调小（前端接 gain 滑杆是 P2；先手工改请求）|
| G4 | 点格子要等 2~3 秒才响（第一次除外） | 说明常驻播放器没复用，每次都付了冷导入 —— 查 `/warm` 是否失败 |
| G5 | **TTS 那条语音被截断**（开头少字/中间断）| 那是声板与发送链路串了管道 —— 严重回归，见 `board_worker.py` 头注释里那个故障场景 |
| G6 | 变声运行中点格子，**微信那条语音里没有人声**（只剩音效）| 两路抢了设备：查 `sg_wasapi_exclusive` 是否被人改成 `True`（共享模式才允许并发写，应为 `False`）|
| G7 | 实时变声页**看不到**音效声板这一块 | 开关问题：设置 → 能力里把「特效声板」打开（**改开关要完全重启应用**）；或前端没同步到安装目录（`cd web && npm run ship`）|
| G8 | 自我监听里**只有变声、没有音效** | 理论上不该发生（监听 tap 的就是 CABLE Output）—— 先看 `board_worker` 是否报过 `device_not_found`（那它就压根没出声）|

##### 已知边界（别误判）

- 声板播放**不进 `_send_lock`** 是**刻意的**：发送期间点格子畅通才行。
  所以「发送中」时格子仍然可点，这不是 bug。
- 出厂音效是**程序化合成**的（`tools/gen_sfx.py`），偏「游戏提示音」风格，
  不是好莱坞拟音。要更真的素材是 P2（市场下载包）。
- 音效长度都 ≤1.6s：故意做短的（微信语音是叠加进人声，长音效会把整条消息搞糊）。
- 实时变声页的声板**没有「预混」档**（连模式切换按钮都不会出现）—— 实时链路里没有
  "要混的那条合成产物"，这是故意的，不是漏了。

##### 回执

三段证据：① 语音消息的录屏/截图（证明里面有音效）；② `curl /api/soundboard/catalog`
里对应条目的 `count` 已 +1；③ 后端日志里 `board_worker` 的启动行数（应为 1）。
**G2 若命中**，额外回执「微信版本 + 录音方式（Alt / 话筒图标）」，那就是这条路径的真实边界。

#### H. 预混模式：发送前把音效烘进音频（2026-09-24 新增）

**背景**：§G 那条路有一个没验证过的前提 —— **点格子会把鼠标焦点从微信挪走**，
按住的 Alt 录音可能被取消（G2）。预混模式是那条路走不通时的**确定性兑底**：
音效在发送**之前**就被混进音频文件（`sfxmix_<原名>.wav`），发送目标换成它，
全程不需要在微信里点任何东西，也就不存在"抢焦点"这件事。

两条链共用同一份 DSP（`sfx_lib.mix_into`），三个位置的说法完全一致：

| 位置 | 听感 | 等价于实时声板的什么 |
|---|---|---|
| **叠加** | 音效与人声同时响 | 录制中点格子（主场景） |
| **开头** | 先炸一声，再说话 | 按 Alt 前点一下 |
| **结尾** | 说完来一声 | 松开前点一下 |

##### 前置

- 后端与桌面端均为最新（同 §G：`sound.fx-board` 已启用）；
- **已有一条合成产物**（`outputs/tts_*.wav`）—— 预混的源就是它（未合成时按钮不可用）。

##### 只读探针（不用微信、不发任何消息）

```bash
# ① 混一条出来（append 到末尾，便于对照听"尾音多了一声"）
curl --noproxy '*' -s -X POST -H 'Content-Type: application/json' \
  -d '{"inserts":[{"sample":"boom","mode":"append","gain":1.0}]}' \
  http://127.0.0.1:8000/api/soundboard/premix
# 预期：{"ok":true,"wav":"sfxmix_tts_*.wav","seconds":<原时长+1.4>,"inserts":1,"skipped":[]}
```

**自动化可自证的部分（不用耳朵）**：混出的文件时长 = 原时长 + 音效时长（拼接档），
或与原时长相同（叠加档）；且 `glob("tts_*.wav")` 的结果**不变**（混出的文件不叫 `tts_*`，
所以不会顶替"最近一条合成产物"这个默认发送目标）。两条都有单测钉子。

##### 步骤（当默认发送目标用）

1. 先在「单段合成」生成一条语音；
2. 到「微信发送 → ② 半自动」的声板面板，**切到「预混」**；
3. 点「爆炸」格子（只勾上，不发声）→ 胶囊上点一下切到「开头」；
4. 点「混进这条语音」→ 上方「发送内容」卡会变成 `sfxmix_*.wav` 并显示「已混入 1 条音效」；
5. **先点试听**：应先听到爆炸、再听到人声；
6. 点「自动发送到微信」（或 ②「开始播放」+ 手动按 Alt）；
7. 在微信里点开这条语音确认。

##### 失败判据

- H1 试听里没有人声或没有爆炸（→ 看 `skipped` 是否非空、音效 id 是否真存在）；
- H2 发送出去的是**没混过**的那条（→ 检查「发送内容」卡显示的是不是 `sfxmix_*`）；
- H3 混完再合成一条新语音，发送却仍发旧的混音（→ **设计上源一变就自动失效**，
  此时卡片上的「已混入」徽标应当消失；没消失就是回归）；
- H4 点「混进」报「没有这个音效」（→ 素材被删了，面板目录还没刷新）；
- H5 微信收到的是**两条**语音或空消息（→ 发送链路的问题，不是预混）。

##### 回执

- 「发送内容」卡截图（应显示 `sfxmix_*.wav` + 已混入 N 条）+ 微信里那条语音的截图；
- 一句话：试听与微信里的听感是否一致（爆炸在开头/末尾/同时）。

##### H-bis. 「混好并直接发送」（2026-09-25 加，一键）

上面 §H 的步骤是**两步**（② 混 → ① 发）。而两步之间那个「发送目标已换成 `sfxmix_*`」
在界面上**看不见**：用户在两步之间重新合成了一条，`useWechatSend` 会（正确地）让预混失效，
于是发出去的是**没混**的那条，且一句提示都没有。新按钮把两步合成一步 ——
`wav` 显式交给发送方，顺序只剩一种（前提不变：`send_voice` 那条链路本来就是
程序点话筒起录、点绿钮发送，**不需要人按 Alt**，所以这条路没有 §G 的抢焦点问题）。

**步骤**：勾「爆炸」→ 胶囊上点一下切到「开头」→ 点**「混好并直接发送」** →
等 ① 卡片显示「发送中」（约 wav 时长 + 3s），**全程不要动键鼠**（微信会被抢前台）。

**预期**：微信里到达**一条**语音，先一声爆炸、再是 TTS 人声（开头档）；网页上不再有第二次点击。

- **H6** 点完没有任何语音到达 → 网页会显示是 `premix` 还是 `send_voice` 失败：
  - `premix` 失败 = 音频/素材问题（同 H1/H4）；
  - `send_voice` 失败多半是微信没开或停在登录页 →
    `curl --noproxy '*' -s http://127.0.0.1:8000/api/wechat/precheck` 一眼看出；
- **H7** 收到的那条**没有音效** → 发出去的是没混的那条（同 H2）；查发送历史里那条的 `wav` 名
  是不是 `sfxmix_*`。

| 预混（切「预混」→ 勾「💥爆炸」→ 胶囊点到「**结尾**」） | `sfxmix_tts_1790313081466_kangaroo_v2.wav` **7.22s** = 5.82 + 1.40 |

##### H-ter. 精确时间点：第 N 秒（2026-09-25 加）

「叠加」档的胶囊上多了一个输入框：`💥 叠加 第 [ 1.2 ] 秒`（只对叠加有意义 ——
开头/结尾是拼接，位置由档位本身决定；其它档位上不会出现这个框）。

**步骤**：勾「爆炸」→ 胶囊上**点一下切到「叠加」** → 在输入框里填 `2`（或面板上给的源时长的
中间值）→「混进这条语音」→ 试听：爆炸应出现在第 2 秒，而**不是**开头；源时长不变。

- **H8** 试听里爆炸仍在开头 → 框里填的值没发出去（看请求体里 `at_s` 是否为 2）；
- **H9** 填一个**超出源时长**的数（人声 4s 时填 30）→ 预期：面板先给一行琥珀色提醒
  （"它会被贴到末尾，而不是在你填的那一秒响"），混完后下方**再列一条后端回报**
  （"指定第 30.0s 超出人声长度（4.4s），已贴到末尾"），并且**混音依旧成功**（不是 4xx
  —— 它确实没地方响，但也不该让整条语音发不出去）。
  - 若只看到前半句、看不到后端回报 → 后端那份还是旧的（本轮只定向换了一个文件）。

**波形拖动**（2026-09-25 同日跟进）：勾「爆炸」并切到「叠加」后，面板上会出现一条
**源人声的波形**，「💥 0s」就是它的记号。

**步骤**：把那个记号拖到波形中间 → 胶囊上的秒数框应同步变成约「2.0」（源 4s 时）；
聚焦记号后按 ← → 应每次 ±0.1s；勾两条叠加音效时应看到**两枚**记号，各自拖得动。

- **H10** 波形区一直停在「波形加载中…」或干脆空白 → 先看是不是取不到音频
  （`last_tts` 的 `url` 404 / 输出目录里那条已被清掉）。**这不是致命失败**（秒数框仍能定位），
  但要看界面写没写原因 —— 空白与“加载中”在界面上分不出来，那是要报的。
- **H11** 拖完记号，秒数框没跟着变（或反之）→ 两处不是同一份状态（回归）；
- **H12** 点波形空白处把记号挪走了 → 回归：本设计**刻意**不响应轨道点击
  （多枚音效时"点一下该动谁"没有正确答案，误移比不移更糟）。

3. 音量观感：`layer` 那次用的是 `gain 0.8`，微信里若盖过人声就调小。

##### A. 单条导入

#### K. 悬浮特效声板窗（2026-09-25 新增，P2.7）

独立小窗，**不抢前台窗口** —— 于是可以「微信里按住 Alt 说着话，鼠标点一声爆炸」。
设计与取舍见 `docs/交接-AI必读.md` §五之「桌面特效窗口」。

**怎么弄出来**：① 热键 **Ctrl+Alt+S**（随时唤出/收起）；② **桌宠右键菜单** →「特效声板窗口」；
③ **录音引导期间自己浮现**（切到「手动发变声语音（自己说话）」进入按住 Alt 那条路时）。
它**默认不出现**，只会在这三处被叫出来；音量跟实时声板一致（写进 CABLE Input）。

**步骤（人能验的部分）**：

1. 热键唤出 → 确认它出现在**右下角、桌宠正上方**；拖标题栏换个位置 → 收起 → 再唤出，
   位置应该记得；
2. （切到微信，按住 Alt 说起一句话不松）→ 点窗里任一格 → 松开 Alt 发送 → 回微信回放：
   **人声里应该夹着那一声**，且**录音没被中断**；
3. 点关闭（—）收起；完全退出应用再打开 → 窗口不该自己冒出来。

**失败判据**：

- **K1** 按了 Ctrl+Alt+S 没反应 → 热键被别的程序占了（后端日志里有 `[sfx] 热键 … 注册失败`），
  换一个不含单 Alt 的组合（改 `sfx-window.cjs` 的 `SFX_HOTKEY`，要重打 asar）；
- **K2** 点了格子**界面亮、但没声** → 看窗底那行字（它会把后端原话写出来，
  典型是 `CABLE 设备找不到` / `没有这个音效`）；不能只看格子动画就当成了；
- **K3** **点了它，微信的 Alt 录音断了** → 这条最严重：说明「非激活窗」没成立。
  查三件事：建窗是不是 `focusable:false`（单测已钉）、是不是误调了 `show()`（单测已钉）、
  是不是**安全软件/输入法把窗口激活了**（罕见但存在）。退路：改用 **F1–F6 逐格热键**
  （P3 已留位，零鼠标参与，绕开激活路径）；
- **K4** 说完话一松手，微信发出去的是**旧语音** → 与声板无关（声板只往声卡里塞声音，
  不碰发送链路）；查那一条的 `wav` 是不是你以为的那条；
- **K5** 收起后应用退不掉、任务管理器里还有进程 → 隐藏窗没被销毁：
  `main.cjs` 的 `closed` / `before-quit` 里必须有 `destroySfxWindow()`（已有，别删）。

#### 一、开按之前的准备（三件事）

#### 二、五个必按场景

每条按顺序做，**每条都记下「按下→变红」和「松手→已发送」这两个耗时**（后面要填表）。

##### A. 最短路径：按住 3 秒说一句话

- **怎么按**：悬停桌宠 → 点「按住说话」页签 → 按住那颗按钮，说「测试一二三」，松手。
- **该看到什么**（按顺序）：
  1. 按下后**很快**变红，按钮下方出现 `0.1s / 59s` 这样的秒数，**每 200ms 跳一次**；
  2. 状态行出现「松手结束并发送」；
  3. 松手后状态行变「正在换声…」→ 再变「正在发进微信…」（换声可能要十几秒，**这段别动键鼠**）；
  4. 气泡：**「已发送到微信 ✓」**，副标题里有 `音频 N.Ns（xxx.wav）`；
  5. 微信「文件传输助手」里出现那条语音。
- **不对时先查**：
  - 按下去**超过 1 秒才变红** → 记下这个时间，写进表里（这说明 `mic/start` 慢，你开头几个字会被吃掉，是个真问题）；
  - 秒数**不动**或跳得断续 → 渲染侧的秒表挂了（看日志有没有报错）；
  - 变红但状态行没变 → 主进程的 `pet:mic-state` 没到（asar 半新半旧）；
  - 松手后没有任何反应 → `mic/stop` 没发出去（看 `backend.log` 有没有 POST）。

##### B. 太短：按住只点一下（约 0.1~0.2 秒）

- **该看到什么**：气泡「出错了」+ **「录到的太短（0.12s）—— 按住不放、说完再松手」**，
  微信里**什么都不该出现**。
- **为什么值得测**：0.3 秒这条线（`MIN_HOLD_SECONDS`）是「误触 vs 真说话」的分界；
  它必须**可读地说出来**，而不是静默发一条 0.1 秒的空语音。
- **顺带看一眼**：按住 **0.5 秒**（过线但很短）→ 会发出大约 1 秒的语音吗？
  （微信语音最短 1 秒，既有的补静音头逻辑在这里是否生效 —— 记下实测时长。）

##### C. 滑出按钮：按住 3 秒，中途把鼠标/手指拖出面板再松手

- **该看到什么**：**照样收尾并发送**（红色保持到松手那一刻），微信里出现完整的 3 秒语音。
- **为什么必测**：这是指针捕获 + 主进程 `wantStop` 竞态那条链路的真机版。
  如果失败，表现是「录音一直录到 59 秒上限才停」——**这不只是不好用，是发错东西**。
- **不对时先查**：`mic_raw_*.wav` 的时长是不是 3 秒左右（不是 59 秒）。

##### D. 按住不放：一直按住超过 59 秒

- **该看到什么**：秒数到 `59.0s / 59s` 时**自己收尾**（不用你松手），接着换声、发送，
  发出去的那条约 59 秒。
- **为什么必测**：微信单条上限 60 秒，这条链路留了 1 秒余量。
  上限自动收尾是「手指滑出 / up 事件丢失」时的最后一道保险。
- **不对时先查**：真录成了 60 秒以上 → 上限没生效（看日志里 `max_seconds` 是不是 59）。

##### E. 失败提示（三条，各按一次，都不用真的发出去）

| 怎么造 | 该看到什么（气泡原样透传后端 detail） |
|---|---|
| 微信完全没开（连托盘都没有） | 「出错了」+ 后端的 precheck/409 文案 → 建议里带「按上面的提示把微信弄好后再点一次」 |
| 面板音色下拉选「主界面选中」，而主界面**没选过任何音色** | 「没有可用音色 —— 先在电脑上选一个音色再按住说话」 |
| 选一个**只有参考音、没有 RVC 权重**的音色 | 「音色「X」没有可用的 RVC 模型 —— 按住说话靠 RVC 定音色」 |

- **要点**：这三条都必须在**气泡上看得懂**，而不是「按了没反应」。
  气泡看不清时，`backend.log` 里有同样的 detail。
- ⚠ **2026-09-29 更新**：这里原先写着「按住说话这条路不做发送前探活」—— **已经不成立了**。
  现在按下**之前**就会拉一次 `GET /api/wechat/precheck`，并在按住页最上面那行写出结论
  （见下面的 F）。E1 那条（微信没开）因此应该**在按下之前就能看到**，而不是松手后才报。

##### F. 按下之前：那行预检说对了没（2026-09-29 新增）

按住页最上面那行叫「预检」，它只回答一件事：**这次按下去发得出去吗**。
它在进页时、停在页上每 5 秒、以及刚发完一次后刷新。

| 怎么造 | 该看到什么（行文字 + 颜色） |
|---|---|
| 微信开着、停在聊天窗，`VM_WECHAT_RESTART=0`（默认） | 绿：`微信已打开 · 直接切麦克风` |
| **把微信完全退出**（连托盘也没有），再切到按住页 | 红：`⚠ 微信没有在运行`（鼠标悬停能看到完整原因：请先打开微信并登录…） |
| 微信只**收进托盘**（进程在、没有可见窗） | 红：`⚠ 微信没有任何可见窗口`（悬停看全句：pid…它还在运行、多半被关进了托盘）—— 与上一条是**两句不同的话**，这是分因的价值 |
| 停在登录页（未登录） | 红：`⚠ 微信主窗口没就绪`（悬停看全句：面积多少 px²、要么还停在登录页），不是「没在运行」 |
| 后端还是旧版（没有 `block_reason` 字段） | 黄：`预检没有结论（后端版本比桌宠旧？）` |
| `hook.wechat` 关掉 | 页签与页体整个消失，看不到这行（正常） |

- **必验的三件事**（都不是“看得见就行”）：
  1. **拿微信退出与「收托盘」两种情形各看一次**，两句话必须不一样 —— 如果都显示「没有在运行」，
     说明后端的窗口分因没透到行上，那这行就只是个模糊警报。
  2. **它不许拦住你**：红着的时候按下去**必须照样开录**（告警只提前告知，不替你做决定——
     你可能刚刚才把微信打开）。如果按不下去，那是 bug。
  3. **它不该只在那一行**：颜色应是红/黄/绿三档，字号跟下面那行提示一样小、**只有一行**
     （若它占了两行，面板底部的「最近发送」就会被顶掉——纵向预算门禁盯的就是这个）。
- **不对时先查**：
  ```powershell
  Invoke-RestMethod 'http://127.0.0.1:8000/api/wechat/precheck' | Format-List
  ```
  对照 `block_reason` / `wechat_running` / `restart_needed` 三个字段——行上的每一句都对应它们之一。
  行上写「预检打不开」而这条命令有输出 ⇒ 是桌宠连不上后端（和发送失败同源）。
- 顺带：`hook.wechat` 被关掉时，「按住说话」页签与页体应当**整个消失**（不是点了报 404）。

#### 三、只能靠耳朵判的三件事（真正的验收）

##### ① 换声真的生效了吗

把 `outputs/.session/mic_raw_*.wav` 和换声后的那份**都播一遍**：

- raw 里应当是**你自己的声音**（正常说话，没有怪音）；
- 换声后应当是**目标音色**在说同一句话、语速节奏一致。

>  只听到自己的原声 = 换声没生效（看 `resolve_rvc_voice` 那条：音色库 id 与 RVC 实验名是两套命名，
>  `kangaroo` 要映到 `kangaroo_v2`）。这时 `stop` 的响应里 `converted` 会是 false 或有报错。

##### ② 有没有抓到虚拟声卡（双重变声）

- **症状**：发出去的语音像「变了声又变了一次」，或者根本不是你的音色。
- **判据**：听 raw。如果 raw 里**已经不是你本人的声音**（是变过声的），说明抓到了 CABLE。
- **为什么不该发生**：`pick_mic_device` 会显式避开虚拟设备（名字里含 cable/vb-audio/虚拟/立体声混音 等），
  一个真实麦都没有时**直接报错**而不是将就。真发生了就是 bug，请把 `start` 响应里的 `device` 字段抄下来。

##### ③ 微信侧的静音告警

- 微信如果绑在**物理麦**上（而不是虚拟声卡），录进去的可能是静音 —— 这是既有的 `warning` 机制，
  面板状态行会显示「已发出 N，但可能有静音：…」。**在微信里放一遍**确认。
- 这条与「按住说话」无关（它是发送链路的固有属性），但验收时顺手确认一次，
  免得把「发送链路的老毛病」误记到新功能头上。

#### 四、出问题时的只读定位命令

后端没在跑就别硬起（会预热 4.9G 模型）。以下命令都是**只读或等价于按一次按钮**：

```powershell
# 1) 它会挑哪个麦（不录，只报设备）—— 直接看 start 响应的 device 字段
Invoke-RestMethod -Method Post -ContentType 'application/json' `
  -Uri 'http://127.0.0.1:8000/api/capture/mic/start' -Body '{"max_seconds":59}'
# 2) 停（真录了的话会落一份 mic_raw_*.wav 到 outputs/.session/）
Invoke-RestMethod -Method Post -ContentType 'application/json' `
  -Uri 'http://127.0.0.1:8000/api/capture/mic/stop' -Body '{"raw":true}'   # raw=true：只录不换声
# 3) 没有正在录的时候调 stop → 应得到 400「没有正在进行的录音」（用来确认没有残留录音线程）
Invoke-RestMethod -Method Post -ContentType 'application/json' `
  -Uri 'http://127.0.0.1:8000/api/capture/mic/stop' -Body '{}'
```

- `raw: true` 是**专门为排查留的**：只录不换声，用来分辨「录错了」还是「换声错了」。
- 想确认实时变声那边有没有残留：`GET /api/rvc/live/status` 看 `live_running`。
- 桌宠状态条上那个 **`82ms`** 是**单块推理耗时**（不是端到端延迟）——验收延迟时别拿它对表，
  口径见 `docs/交接-AI必读.md` 第三节。

### 情感录制稿 · 2026-10（给 RVC 补「情绪状态下的音色」）

#### 〇、先读这 6 条（比内容重要）

1. **同一套设备、同一间房、同一个距离**：和 2026-10-supp 一样——手机自带录音机、
   嘴距 15–20cm、嘴偏开麦克风轴线一点。**别用微信发**（会压高频），用数据线/AirDrop/网盘。
2. **不降噪、不压缩、不 EQ、不加混响、不开美颜音效**。手机录音机原文件最干净；
   任何“后期处理”都会把情绪音色（气声、哭腔、压嗓）洗掉。
3. **安静小房间**：关窗、关空调/风扇/电视；衣柜旁、衣帽间、停着的车里都行。
   **不要**浴室/厨房/空大房间（混响会被模型学走）。
4. **峰值不超过 −6dBFS，绝不能削波**（录的时候看电平条，最大只到 2/3）。
   情绪爆发那几条尤其容易顶满：离远 2–3cm，或把手机录音音量降一档。
5. **不要“演”到破音/挤压/喊**。我们要的是**真实**的温柔、克制、哽咽、笑意，
   不是夸张的舞台腔；嗓子一紧/一痛就停，降一点重来。
6. **每条之间停 1 秒**；说错/卡壳整条重来，不用在原地补救。文件名随便，
   建议 `01_温柔.m4a`、`02_克制.m4a` …（我会按组切）。

> 为什么不用“情感”这个词当标签：RVC 没有情感标签，它学的是**声音的形状**。
> 你只要把“温柔时的气声、哽咽时的断句、笑意时的口腔形状、叹息时的长呼气”录进去，
> 模型才有这些样本；否则所有情绪都会被平均成同一个中性音色。

#### 一、录制矩阵（10 组，共 6–10 分钟）

| 组 | 内容 | 关键要点 | 时长 |
|---|---|---|---|
| 01 | **温柔 / 近讲** | 像在耳边跟一个人说话；气声多、音量小、句尾轻收 | 30–45s |
| 02 | **克制 / 隐忍** | 想哭但忍住；压着唱/说，句尾不要放出去，带一点鼻音 | 30–45s |
| 03 | **哽咽 / 哭腔** | 真的难过（想一件具体的事）；允许断句、吸气、声音抖，但别真哭到失控 | 30–45s |
| 04 | **笑意 / 明亮** | 笑着说话/唱；口腔抬高、眼睛笑；句尾上扬，但别变成假甜 | 30–45s |
| 05 | **叹息 / 疲惫** | 长呼气开头，句尾下沉；像下班后瘫在沙发上说话 | 30–45s |
| 06 | **爆发 / 用力** | 安全的强声（不是喊）；腰腹支撑、喉咙放松；句尾不要劈 | 30–45s |
| 07 | **耳语 / 气声** | 真·耳语（不发声带振动），近讲；这条教“气声”的频谱 | 30s |
| 08 | **念白 / 独白** | 像对一个人讲一段话，不是朗读；有停顿、有重音、有呼吸 | 45s |
| 09 | **长音渐强渐弱 + 滑音 + 颤音启停** | 一个舒服的中音：pp→ff→pp 各 5–8s；直音→颤音→直音 | 45s |
| 10 | **同一句 × 5 情绪（核心）** | 同一句话，用 01–05 的情绪各说/唱一遍；这是后面盲听辨情绪的关键 | 60–90s |

#### 二、每组怎么录（照着做就行）

##### 01 温柔 / 近讲（30–45s）

说 3–5 句日常话，像哄人/安慰人：

> “没事的，我在。”
> “你慢慢说，不着急。”
> “今天辛苦了，先歇一会儿。”
> “别怕，有我呢。”

然后**用同样的温柔唱**一句舒服的歌（《好久不见》《送别》《茉莉花》都行），
不要飙高音，像哼给旁边的人听。

##### 02 克制 / 隐忍（30–45s）

说 3–5 句“想发火但压住”/“想哭但忍住”的话：

> “行，我知道了。”
> “没关系，真的没关系。”
> “你先走吧，我想一个人待会儿。”
> “这件事……以后再说吧。”

要点：**句尾收住**，不要放出去；音量比 01 大一点，但情绪是往里压的。

##### 03 哽咽 / 哭腔（30–45s）

先想一件**具体**的难过的事（不要抽象地“演难过”），然后说/唱：

> “我以为我早就忘了。”
> “你怎么都不跟我说一声。”
> “我没事……我真的没事。”

允许：断句、吸气、鼻音、声音抖、某个字突然没声。
不允许：真哭到喘不上气、破音、喊。

##### 04 笑意 / 明亮（30–45s）

先笑两下（真笑，不是“哈哈哈”表演），然后带着笑说：

> “你别逗我了。”
> “真的假的？你也太厉害了吧。”
> “行行行，你赢了。”

再笑着唱一句（嘴角抬起来，声音会自然变亮）。

##### 05 叹息 / 疲惫（30–45s）

先**长呼气**（“唉——”），再说话：

> “累死了，今天什么都不想干。”
> “算了，明天再说吧。”
> “我就想躺一会儿。”

要点：句尾**往下掉**，不要提气；允许声音有点散、有点沙。

##### 06 爆发 / 用力（30–45s）

**安全第一**：不是吼，是“有支撑的强声”。先热身（哼鸣 1 分钟），然后：

> “我受够了！”
> “这次我真的不想再让了。”
> “你听我说完！”

每条 2–3 遍，**嗓子一紧就停**；不要连续喊超过 3 条。
这条教模型“强声时的音色”，不是教它“音量”。

##### 07 耳语 / 气声（30s）

真耳语（声带不闭合、只有气），嘴距 10–15cm：

> “别出声，跟我来。”
> “我告诉你一个秘密。”
> “你睡着了吗？”

这条会让模型学到“气声”的高频形状；不要用正常发声“小声说”代替。

##### 08 念白 / 独白（45s）

像电影旁白/对一个人讲一段话，**不要朗读腔**：

> “好久不见。
>  那天我在街上看到一个人，背影特别像你。
>  我站了很久，最后还是没敢叫。
>  其实我有一句话，一直没跟你说……”

要点：有停顿、有重音、有呼吸；不要每个字都咬得很清楚。

##### 09 长音 / 滑音 / 颤音（45s）

选一个**最舒服**的中音（大约你说话略高一点）：

1. 「啊——」**pp → ff → pp**（渐强渐弱），5–8 秒 × 2 遍；
2. 「呜——」从低音**慢滑**到舒服的高音再滑回，5–8 秒 × 2 遍；
3. 「啊——」**直音 2 秒 → 颤音 2 秒 → 直音 2 秒** × 2 遍（颤音要自然，不要刻意抖）；
4. 「咦——」「哦——」各一遍，音色尽量圆。

> 这条是教模型“音量/音高变化时音色怎么变”，不是练声；稳比响重要。

##### 10 同一句 × 5 情绪（60–90s，最重要）

选**一句**你最顺口的（建议“好久不见”或“你还好吗”），用 01–05 的情绪各说一遍、
再各唱一遍（同一句、同一个调，不要改旋律）：

| 遍 | 情绪 | 提示 |
|---|---|---|
| 1 | 温柔 | 像在耳边 |
| 2 | 克制 | 压着，句尾收 |
| 3 | 哽咽 | 断句、吸气、声音抖 |
| 4 | 笑意 | 嘴角抬起来 |
| 5 | 疲惫 | 叹气开头，句尾下沉 |

这条是后面**盲听辨情绪**的 test set：如果新模型在这五遍上听起来还是同一个人、
但情绪分得开，说明“情感”真的学进去了；如果五遍一模一样，说明素材不够。

---

#### 三、非语言声音（可选，但很值钱）

如果方便，额外录 30–60 秒：

- 真叹息 3 次（“唉——”，每次 3–5 秒）；
- 真笑 3 次（短笑/大笑各一次）；
- 吸气/呼气各 3 次（靠近麦克风，但别喷麦）；
- 一句“带哭腔的吸气后开口”（像刚哭完说话）。

这些不是“噪音”，是情绪音色的一部分；RVC 训练会把它们当成音色样本。

- [ ] 06 爆发组嗓子没有不舒服；如果有，告诉我，这组可以少录。

1. 解码到 40k 单声道，逐条 QC（削波/底噪/时长/电平平直）；
2. 与旧 15.06min 混成数据集（旧素材保留，保证中性锚点），**分两档各训一版**：

## 9 在线扒歌：配置与边界

> `sound.ytdlp` 插件的外部工具桥。拉不动歌时按「先查这三节」的顺序。
> 原文：`在线扒歌-配置与边界.md`（2026-10-27 并入）

### 在线扒歌（yt-dlp 外部工具桥）

> 插件 id `sound.ytdlp` · 页面 `/ytdlp` · 代码 `m2_server/ytdlp_fetch.py` + `m2_server/ytdlp_api.py`
> **这一页写给"拉不动歌的人"**：先看「拉不动时按这个顺序查」，八成的问题在前三节。

---

#### 0. 它是什么 / 不是什么

它是**取歌的第 3 条路**，与前两条并列（三条产物都落同一个会话目录、都退出即删）：

| # | 入口 | 场景 | 实现 |
|---|---|---|---|
| ① | 上传文件 | 歌已经在本地 | `cover_api` 上传 |
| ② | 粘直链 | 手上有**能直接下**的 URL | `url_fetch.py`（自己发 HTTP，逐跳校验） |
| ③ | **在线扒歌** | 手上只有**平台分享链接** | `ytdlp_fetch.py`（调外部 yt-dlp） |

**不是**：本项目不内置 yt-dlp、不代管它的更新、不解析任何平台接口。
仓库里**没有一行绕 DRM 的代码** —— 工具由用户自己装、自己升、自己承担使用边界。
所以它是个**可关的插件**（`plugin.json` 里 `extras.external[].kind = "app"`），
关掉它不影响 ①② 两条路。

为什么选 yt-dlp 而不是那些"解析接口"（2026-09-26 调研结论，别再走一遍）：

* 第三方 PHP 解析接口（`music.xxx.php?msg=`）—— 无维护者、平均几个月失效，
  而且绕的就是平台 DRM，写进源码是开源/比赛的硬伤。**否掉**。
* `NeteaseCloudMusicApi` 及其 fork —— 原版作者**主动删库停更**
  （README 只剩"保护版权，此仓库不再维护"）。**否掉**。
* **yt-dlp** —— 官方维护、发版极勤，`netease:*` / `qqmusic:*` 是一等公民 extractor，
  平台改版有整个社区一起修。**选它**。

---

#### 1. 装 yt-dlp

本项目不代管这一步。三种方式任选：

```bash
pip install -U yt-dlp        # 装成模块，会进 PATH
winget install yt-dlp
# 或直接下 yt-dlp.exe 丢进任意目录
```

装完**让它能被找到**：放进 `PATH`，或设环境变量 `VM_YTDLP` 指到可执行文件的完整路径。

> 本机（✅2026-09-27 实测）：`yt-dlp 2026.03.17`，在
> `%LOCALAPPDATA%\Packages\PythonSoftwareFoundation.Python.3.13_...\Scripts\yt-dlp.exe`，
> 已能被自动发现，`VM_YTDLP` 不用设。

**平台一改版旧版本就会认不出链接**，所以偶尔 `yt-dlp -U`。这是选它的代价，也是它的优点来源。

> `-x --audio-format mp3` 的**转码依赖 ffmpeg**。本机已在 PATH（WinGet 装的 9.0 full build）。
> 缺了不会报错，只是产物会保持原容器（`.m4a` / `.webm` 等）—— 上游照样能吃，不影响翻唱。

---

#### 2. 登录态（QQ 音乐、部分网易云曲目**必需**）

##### 为什么需要

QQ 音乐几乎全曲库都要登录态才发音频流。实测报错原文是：

```
ERROR: [qqmusic] 0023jgxa0Ym5yo: This video is only available for registered users.
Use --cookies-from-browser or --cookies for the authentication
```

注意是 **registered users（注册用户）**，不是 VIP —— **免费账号通常就够**，
128kbps 也能拿去跑人声分离。所以"要登录"不等于"这首歌要付费"。

**默认是匿名请求**：不配下面任何一个环境变量，就发匿名请求。
读浏览器 cookie 库是侵入性操作，这个插件是"外部工具桥"，不该顺手摸用户的浏览器凭据。

##### 做法 A（推荐）：导出 cookies.txt

1. 浏览器装一个能导出 Netscape 格式 cookies.txt 的扩展（搜 `Get cookies.txt LOCALLY`
   这类本地导出的，别用把 cookie 传上云的那种）；
2. **先登录**该音乐站点，再在站点页面上导出 `cookies.txt`；
3. 设环境变量指过去，**重启后端**：

```bash
VM_YTDLP_COOKIES=D:\somewhere\cookies.txt
```

配完后在「在线扒歌」页点**「重新检测」**，环境卡上会显示"登录态 cookies 文件" ——
不用靠"再拉一次看看"来验证。

##### 做法 B（图省事）：让 yt-dlp 自己读浏览器

```bash
VM_YTDLP_COOKIES_BROWSER=edge      # 或 chrome / firefox
```

**但 Windows 上这条路经常不灵，原因是环境而不是代码**（✅2026-09-27 本机逐条复现）：

| 浏览器 | 报错 | 原因 |
|---|---|---|
| Chrome | `Failed to decrypt with DPAPI` | Chrome ≥ v127 启用 App-Bound Encryption（yt-dlp issue #10927） |
| Edge / Chrome | `Could not copy Chrome cookie database` | **浏览器还开着**，sqlite 库被独占锁（issue #7271） |

而且本机 Edge 的 `Local State` 里确认有 `app_bound_encrypted_key`
（✅ 实测读出来的，即已启用 ABE），所以**即使把 Edge 完全退出，也未必读得出来**。
结论：**做法 A 才是稳的**，B 只当"反正刚好能用"。

两个都配时**以文件为准**（文件是确定性的）。文件配了却不存在 → 直接报错，
不会静默退回匿名（静默忽略的后果是用户以为配好了，然后拿着"要登录"的报错反复试）。

---

#### 3. 分享链接会被**规范化**（"粘进去没反应"的头号原因）

从 App 点「分享」得到的链接，经常**不是** yt-dlp 认的那个地址。
2026-09-27 用用户给的真实链接实测（QQ 音乐《唯一》）：

```
用户粘的   https://c6.y.qq.com/base/fcgi-bin/u?__=yY3vbmLH9kYO
  ↓ 302（在服务端跳，用户看不见）
跳到       https://i2.y.qq.com/n3/other/pages/playsong/index.html?songmid=0023jgxa0Ym5yo
  ↓ 再跳
最终       https://y.qq.com/n/ryqq_v2/songDetail/0023jgxa0Ym5yo
           ↑ yt-dlp 报 `Unsupported URL` —— 它只认旧的 /n/ryqq/songDetail/<mid>
```

所以"没反应"里有一大类**不是版权问题，是地址形式问题**。
`normalize()` 的做法：从链接里抠出稳定 ID（QQ 的 `songmid`、网易云的 `id`），
再用 ID **自己拼**官方规范地址。

| 你粘的 | 交给 yt-dlp 的 |
|---|---|
| `c6.y.qq.com/base/fcgi-bin/u?__=…` | `y.qq.com/n/ryqq/songDetail/<mid>` |
| `i.y.qq.com/v8/playsong.html?songmid=<mid>` | 同上 |
| `y.qq.com/n/ryqq_v2/songDetail/<mid>` | 同上 |
| `music.163.com/#/song?id=…` | `music.163.com/song?id=…` |
| `y.music.163.com/m/song?id=…` | 同上 |
| B站 / FMA / Jamendo 的链接 | **原样**（没有 ID 规则就不动它，改了反而可能改坏） |

界面在结果里会显示**实际解析到的地址**（只在与你输入不同时出现），
这样"这条链接为什么行/不行"一眼可见。

##### 顺带扩了站点白名单

QQ 音乐的短链域是 `c1~c9.y.qq.com`，逐个列举没有出路。
所以白名单从"精确主机名"扩成了**精确 + 点号锚定的域名族**：

```python
host == "y.qq.com" or host.endswith(".y.qq.com")
```

点号锚定是这里**唯一的安全性质**：`.y.qq.com` **不**匹配
`y.qq.com.evil.example`（买个子域就能绕过的经典写法），也**不**匹配 `noty.qq.com`。
回归测试 `test_host_match_is_exact_not_prefix` 显式钉住这几种伪装。

##### 安全边界（改这块之前先读）

* 短链解析是**唯一**会发 HTTP 的地方，且只在**入参 host 已过白名单**后才可能触发；
* 跳转目标**绝不会**被直接交给 yt-dlp —— 只用它抠 ID，再用 ID 拼自己构造的地址。
  否则白名单就等于让给了任意服务端重定向（在任意放行站点上找个开放重定向即可绕过）；
* 抠出来的 ID 字符集本身就是安全性质（排掉 `/` `.` `?` `#` `%`），
  那是本模块唯一手工拼字符串的地方。

---

#### 4. 其它边界

* **随用随删**：产物由 `-P` / `-o` 钉死在 `<OUTPUTS_DIR>/.session`，
  退出即清。`_cleanup` 只删**本轮** `stem` 前缀，绝不删整个会话目录
  （那里面有用户刚下好、还没跑翻唱的歌）。
* **产物定位要按 stem 过滤**：会话目录里可能躺着上一次刚扒好的歌。
  扫全目录的话，"这次什么都没产出"会被上一次的残留伪装成成功 —— 用户拿到的是
  **上一首**，而且他多半发现不了。连着扒两首时必现。
* **单曲语义**：粘歌单 / 合集链接只会取第一首（`--no-playlist`）。
* **法律**："中文歌多 + 曲库全 + 免费 + 合法"是不可能三角，必须选一边放弃。
  本项目的取舍是：工具中立、用户自装、仓库干净，**使用边界由用户自己承担**。
  付费/会员曲目拿不到音频流是**正常结果，不是故障**。

##### 取回可以停（2026-09-27 起）

改之前的样子：`subprocess.run(timeout=600)` —— 粘一条坏链接，界面只能干等
"取回中…"最长十分钟，用户唯一能做的是**关页面**，而后台 yt-dlp 还在跑；
而且 `run` 的超时只 kill **直接子进程**，yt-dlp 拉起的 ffmpeg 会变成孤儿
继续往会话目录里写。现在三条一起管住了：

| 出口 | 怎么触发 | 行为 |
|---|---|---|
| **取消** | 界面上的「取消」按 | 先叫后端取消（`POST /api/ytdlp/fetch/{job_id}/cancel`），再 abort 本地请求 |
| **关页面** | 用户直接关掉/刷新 | HTTP 连接断 → 后端把同一个作业取消掉，**不会**在后台把歌拉完 |
| **卡住** | 连续 90s 一行输出都没有 | 中止，报"判定卡住了"（与"超时"分开：两者要做的事不一样） |
| **超时** | 墙钟 600s | 兜底上限，报"N 秒没拉完" |

前两条都走同一条路：**按进程树杀**（Windows `taskkill /F /T`，POSIX `killpg`），
然后带重试地清掉本轮 `stem` 前缀的半截文件 —— 刚被杀的进程持有的句柄不是立刻
释放的，一次 `unlink` 常撞 `WinError 32`。

进度：`GET /api/ytdlp/fetch/{job_id}` 会返回 `{stage, percent}`（界面按秒轮询）。
`percent` 为 `null` 表示"还没读到进度行"，界面**不会**显示成 0% —— 那是
"一点没下"的意思，不是"还不知道"。

---

#### 5. 会员曲兜底：从官方 MV 抽音轨（`VM_MV_FALLBACK`，**可选，默认关**）

##### 它解决的问题

QQ 音乐有一部分曲子是**会员曲**，`vkey` 接口对它们返回 `purl` 空 +
`fnameHitCa`（`Ca` = Copyright authority，版权授权不通过）。实测证据
（2026-09-27，《唯一》= `0023jgxa0Ym5yo`）：

```
pay_play=1  pay_month=1  price_track=200  pay_status=0    ← 会员曲
匿名 vkey        → purl 空
配了真登录态 vkey → 仍 purl 空（Ca）
24 种 filename × platform 组合穷举 → 全部 purl 空
```

也就是说：**这不是"缺登录态"，是账号没有这首歌的授权**。配 cookies 也解决不了。
yt-dlp 在这条路上只能报 `No video formats found!`。

##### 怎么绕过去的

用户给了关键线索：**QQ 音乐的 MV 网页一直是免费能看的**。顺着实测下来：

| | 歌曲音频接口 | MV 播放页 |
|---|---|---|
| 端点 | `vkey.CgiGetVkey` | 页面内部吐的 `.m3u8` / `.ts` |
| 匿名结果 | `purl` 空 / `fnameHitCa` | **200，直接出流** |
| 要登录态吗 | 要（会员曲还要 VIP） | **不要** |
| 文件本身 | 加密（mflac/mgg） | **明文 MPEG-TS** |

链路（`m2_server/mv_audio_fallback.py`）：

```
get_song_detail 拿关联 vid  →  浏览器打开 y.qq.com/n/ryqq/mv/<vid>
  →  截 .m3u8 索引 + 全部 .ts 分片  →  按序合并  →  ffmpeg -vn -acodec copy
```

实测《唯一》：27 片 / 36.38 MB / 720p / 271.2s，抽出 **192 kbps AAC 完整音轨**。

##### ⚠️ 音质代价（必须让用户知道）

**MV 音轨 ≠ 唱片母带。**

* MV 抽出来是 **192 kbps AAC**；正版音源是 **FLAC 无损（~1000 kbps）**，差 5 倍。
* MV 音轨混了**影像的声音设计**（环境声、镜头切换的气口），可能带画面声。

**做粗料够用，做音源不够。** 所以兜底成功时接口会返回 `via: "mv_fallback"` +
`quality_note`，界面用琥珀色告警条显示 —— **不能让兜底产物看起来和正版音源一样**。

##### 怎么开

```bash
# Windows PowerShell（临时，只在当前会话生效）
$env:VM_MV_FALLBACK = "1"

# 或写进后端启动环境（持久）
```

依赖三样，缺一样就用不了（`status` 接口会报出来）：

| 依赖 | 说明 |
|---|---|
| `node` | 驱动浏览器。找不到走 PATH |
| `playwright-core` | 默认猜 `<repo>/web/node_modules/playwright-core`；可用 `VM_PLAYWRIGHT_CORE` 指 |
| `ffmpeg` | 抽音轨。可用 `VM_FFMPEG` 指 |

查当前状态：

```bash
python m2_server/mv_audio_fallback.py status
```

##### 三条刻意守住的边界

1. **默认关**。这是"绕平台会员授权"的取音路径，与 `VM_YTDLP_COOKIES` 同一口径：
   用户自己开、自己承担使用边界。
2. **只对 `y.qq.com` 生效**。别家没有等价的免费 MV 通路，误触发等于乱发请求。
3. **独立成模块，不进 `ytdlp_fetch`** —— 那个模块"没有一行绕 DRM 的代码"是
   刻意维持的性质（比赛/开源脱敏时这块天然干净）。

##### 兜底的语义是"多做一次尝试"

* 只在 **yt-dlp 失败之后**跑。主路成功时不碰它（否则每首歌白抓一次 MV）。
* 自己失败**不盖掉 yt-dlp 的原话**。用户能行动的是"配登录态 / 换来源 / 升版本"，
  那些都在 yt-dlp 的归因里；兜底的失败原因（没关联 MV / 抓不全）对他没用。
* 任何意外都不外溢成 500。

##### 改这块之前先读：四个实测踩过的坑

| 坑 | 现象 | 正确做法 |
|---|---|---|
| **分片 URL 完全相同** | 用 `Map<url, body>` 收 → 被覆盖成 1 片，合并出来只有 387KB | 必须用**数组按到达顺序**收 |
| **直链是一次性签名路径** | 每次刷新 m3u8 前缀都不同（`15541F1F…` / `0A9C88EC…` / `5B6B0D92…`） | **抓到就立刻下**，不能先存 URL 再排队 |
| **分片是惰性加载的** | 只播开头 → 只拿到开头几片，**静默**产出截断的歌 | 先读 m3u8 数 `#EXTINF` 行数当预期，不足即失败 |
| **MV 接口显式调用要鉴权** | `MV.getMVUrl` 返回 `860100005` / `860100001` | 别走 API，走**播放页**（页面内部那条路不校验） |

★ 第三条尤其要紧：**给用户一首被截断的歌，比明确告诉他"没抓全"糟得多** ——
他可能拿去跑完翻唱才发现少了尾部。所以 `_grab_mv` 用"片数"把关，
`fetch_from_mv` 再用"时长"把关（第二道，容忍 3s —— MV 的音频流本就比视频流略短）。

---

#### 6. 拉不动时按这个顺序查

```bash
# ① 工具在不在、什么版本、登录态配了没（只读、不联网）
python m2_server/ytdlp_fetch.py probe

# ② 这条链接会被改成什么、属于哪个站点（不跑 yt-dlp、不落盘）
python m2_server/ytdlp_fetch.py resolve "https://c6.y.qq.com/base/fcgi-bin/u?__=xxxx"

# ③ 真跑一次，看点名的人话报错
python m2_server/ytdlp_fetch.py fetch "https://c6.y.qq.com/base/fcgi-bin/u?__=xxxx"

# ④ 会员曲兜底：开关状态 / 这首歌有没有关联 MV / 单跑一次兜底
python m2_server/mv_audio_fallback.py status
python m2_server/mv_audio_fallback.py vid 0023jgxa0Ym5yo
python m2_server/mv_audio_fallback.py fetch 0023jgxa0Ym5yo
```

对照表：

| 报错 | 下一步 |
|---|---|
| `暂不支持 <host>` | 站点不在白名单。用该站**分享出来的歌曲链接**，或走「翻唱」页的上传/粘直链 |
| `没找到 yt-dlp` | 见第 1 节 |
| `要给登录态才发音频流` | 见第 2 节（做法 A）。若是**会员曲**，配了也拿不到 —— 见第 5 节 |
| `yt-dlp 认不出这条链接` | 先 `yt-dlp -U`；还不行就是这种页面形式它还没支持 |
| `跑完了但没拿到音频文件` | ①未配登录态 ②付费/独家曲 ③平台改版，升级 yt-dlp。QQ 音乐的会员曲可开第 5 节的兜底 |
| `yt-dlp 超过 N 秒没拉完` | 网络慢或歌太大；重试即可 |
| `连续 90 秒没有任何输出，判定卡住` | 这条链接对应的取流挂了。换条链接，或走「翻唱」页的上传/粘直链 |
| `已取消取回（yt-dlp 已中止…）` | 用户按的取消，**不是故障**；界面只给一句确认，不弹红条 |
| `MV 兜底没开启` | 见第 5 节；用 `VM_MV_FALLBACK=1` 打开 |
| `这首歌在 QQ 音乐没有关联的官方 MV` | 这条兜底走不通，换一首或换来源 |
| `MV 分片没抓全（拿到 N/M 片）` | 网络慢或视频较长；稍后重试，一直不行就换来源 |
| `抽出来的音轨只有 Ns，MV 本身是 Ms` | 同上（这是第二道完整性把关） |

#### 0. 严重级别约定

每条审查意见必须标注级别，与「火眼眼」评审格式一致：

| 级别 | 含义 | 处理要求 |
|---|---|---|
| 🔴 **阻断（Blocker）** | 安全漏洞、数据丢失/损坏、并发竞态、破坏契约、关键路径无错误处理 | 合入前**必须**清零 |

| 💭 **提示（Nit）** | 风格不一致（无 linter 兜底时）、小命名、文档缺口、可选写法 | 可选，不阻塞 |

**原则**：一条评论只讲一件事，给「为什么」+「建议改法」。先肯定亮点，再指出问题。

#### 1. 通用审查维度（所有语言）

##### 1.1 正确性
- 逻辑是否真的实现了需求？边界条件（空输入、None、0、负数、超长）是否处理？
- 是否破坏了既有 API/契约（路由签名、返回结构、配置字段、数据库 schema）？改动是否向后兼容？
- 字符串/路径拼接、浮点比较、时区、编码（本项目音频多为 22050Hz 单声道 wav）是否正确处理？

##### 1.2 安全（🔴 优先）
- 用户输入是否经过校验/转义？SQL 用参数化、命令用白名单、外部值不进 `eval`/`exec`/`pickle.loads`/`yaml.load`（yaml 须 `safe_load`）。
- **密钥红线**：`.env` / `credentials.json` / 私钥 / GitHub `gho_` 令牌**绝不可进入版本库**。审查时 `git diff --cached` 扫一遍新增文件，确认 `.gitignore` 已覆盖。
- 网络请求：外部 URL 是否可能被 SSRF（如用户传入本地地址）？是否带超时与重试上限？
- 文件路径穿越：用户提供的 `voice_id` / 文件名是否做白名单（参考 `market_images.py` 的 `白名单防穿越`）？

##### 1.3 错误处理（本项目头号问题）
> 实测痛点：`m2_server/rvc_live.py` 有 22+ 处 `except Exception`，多数静默 `pass`/`continue` 不记录，**故障不可观测**。

- 🔴 禁止静默吞异常：`except Exception: pass` 或只 `continue` 不记日志 = 阻断级。
- 捕获应**尽量窄**（具体异常类型），不要一揽子 `except Exception` 包住不相干代码。
- 关键路径失败必须返回明确错误 / 写日志 / 触发降级（如实时 RVC 加载失败应降级 TTS 直出并记 `STATE.rvc_error`）。
- 资源清理用 `try/finally` 或上下文管理器；不要在异常分支泄漏文件句柄 / 子进程 / GPU 显存。

##### 1.4 并发与状态
> 实测痛点：`m2_server` 有 18 处 `global` 可变状态；`cascade_stream.py` 用 `threading.Lock` + 常驻 `load_vc`。

- 🔴 共享可变状态（全局 dict、`STATE`、模型句柄）必须有锁或原子操作保护；审查锁的**覆盖范围**是否包含全部读写。
- 常驻推理资源（RVC engine、TTS model）必须 `warmup()` 完成后才对外服务；首次请求前未完成预热会首句卡顿数秒。
- 流式/实时链路注意取消与背压：客户端断开后生成循环是否及时退出，避免积压。
- 线程/进程不要阻塞事件循环（GIL 友好）；耗时推理放线程或进程池。

##### 1.5 性能
- 避免 N+1（循环内查库/查文件）；批量与缓存优先。
- 大文件 / 长音频处理避免整段读入内存；注意采样率转换与重采样开销。
- 不要重复加载大模型；复用单例（`offline_vc_infer.load_vc` / `RvcEngine`）。

##### 1.6 可维护性 / 测试
- 函数/模块是否单一职责？是否有「上帝函数」？命名是否表意？
- **重要行为必须有测试**：后端改完必须补/更新 `m2_server/tests/` 下用例（铁律 2）。
- 魔法数字（采样率、端口、超时常量）是否提取为具名常量？
- 导入副作用：本项目 `RVC/configs/config.py` import 时严格 parse `sys.argv`、`setup_env` 会 `chdir` 到 RVC 根——调用方路径必须绝对，且不要在生产模块顶层 import 触发副作用。

##### 1.7 破坏性文件操作（本项目特殊坑）
> 本环境 `shutil.rmtree` 被 safe-delete 包装成「移回收站」，且批量删触发 bulk guard。

- 🔴 删除/清理逻辑**不要假设永久删除**。要真正释放空间用 `tools/hard_delete.py`（先 truncate0 再删）。
- 测试里的临时目录清理必须设 `CODEBUDDY_SAFE_DELETE_ENABLED=0`，否则 `shutil.rmtree` 被拦导致用例随机失败。
- 不要写 `.ps1`/`.bat` 处理非 ASCII 路径（编码损坏）。

### 二、审查流程

> 与本文「一、审查标准」配套。本流程把「火眼眼」评审标准落到日常开发节奏，并与 `AGENTS.md` 铁律（改动即提交 / 改动即补测 / 踩坑必记）对齐。

---

#### 1. 原则

1. **小步快跑**：单个 PR ≤ 400 行（不含生成代码/迁移）；超了必须拆分。大改动先发设计/RFC，再分步合入。
2. **作者先自审**：提交前作者自己过一遍本文「三、作者自审清单」，不把明显问题丢给评审人。
3. **AI 先初审，人复核**：每个 PR 先用「火眼眼」专家做一轮自动审查，人工只盯 🔴 与有争议的 🟡。
4. **零阻断才可合入**：任意 🔴 未解决 = 不可 merge；🟡 需作者与评审协商一致（可记 TODO 跟进）。
5. **改动即对应 commit + 测试 + 记录**（铁律 1/2/3）。

| 角色 | 职责 |
|---|---|
| **作者（Author）** | 自审清单、跑本地门禁、写 PR 描述（含验证方式）、回应评审意见、补测。 |
| **评审人（Reviewer）** | 至少 1 人；按 GUIDE 给分级意见；对 🔴 有否决权。 |

## 11 端到端实测：音色保存与录课视频

> GUI 全链路一次跑通记录 + SECS（自标尺）0.806 vs 手工参考音 0.9888 的损耗归因 + 6 个已知问题。
> 原文：`端到端实测-音色保存与录课视频.md`（2026-10-27 并入）

### 端到端实测：上传音色 → 保存 → 用它录课出视频（2026-10-10）

> 测试方式：Windows 桌面自动化驱动真实 GUI（Chrome 加载 `localhost:5173`，与 Electron 同一套前端/后端），
> 全程模拟"老师"操作：上传一段录音 → 音色工坊切片/质检/采纳 → 存成音色 → 录课页上传 PPT → 逐页合成 → 导出成片。
> **目的**：回答两个问题——①音色存不存得住？②用保存的音色录视频，会不会出问题？

#### 结论先行

| 问题 | 答案 |
|---|---|
| 音色保存得住吗 | ✅ **存得住**。后端 `/api/voices` 出现 `teacher_voice`，`media/voicebank/teacher_voice/` 落盘，重启后端后仍在 |
| 保存的音色能录视频吗 | ✅ **能，全链路一次跑通**。3 页 PPT → 3 条旁白（58.8s）→ 1920×1080 mp4 成片 59.5s，零失败 |
| 像不像本人 | ⚠️ 首测 SECS 0.806 → **✅ 修复后 0.9905**（2026-10-10 晚：成片"电音"实为 float32→pydub 位级错读 bug，与参考音质量无关，见下文平反记录；同人上限 0.9928。**尺子口径=Qwen 自空间自标尺，非 CAM++**，2026-10-11 更正） |

#### 链路实录（每步实际发生的事）

1. **上传素材**：120s 本人录音（lesson_A.wav 截段）封装成 mp640×360 黑屏视频（音色工坊**只收视频格式**，见问题③）。
   放进 `media/raw_videos/` 后应用即刻识别（素材列表 2 → 3）。
2. **切片流水线**：点「运行流水线」→ 26 条切片（A/B 级），约 2 分钟（首次含去 BGM 模型下载）。
3. **质检采纳**：按「A」筛选 → 「批量采纳」两屏 → 26 段 / 117.7s。
   ⚠️ 目标 30s、超额采纳 117.7s **UI 不拦截**（问题⑤）。
4. **创建音色**：「进入音色库」带勾选素材过去 → 填 ID `teacher_voice` → 「创建参考音色」→ 后端确认创建成功。
   ⚠️ **「我的音色」页刷新后列表不显示它**（只有袋鼠骑士 v2），但数据真实存在（问题②）。
5. **录课合成**：录课页音色下拉 **直接出现「teacher_voice（自训）」并选中** → 上传 3 页测试 PPT
   （备注自动带出为讲稿）→ 「逐页合成」→ 3/3 成功（P1 23.7s / P2 19.4s / P3 15.7s），每页独立音轨 + 波形试听。
6. **导出成片**：「课件画面 + 旁白 → 视频」展开 → 30fps / 页间停顿 350ms → 「导出成片」→
   **59.5s，1920×1080 H.264 + AAC**，`outputs/course_1791599316778/course.mp4`（1.8MB）。UI 徽章同步显示「59.5s · 3 页画面」。

#### 音色相似度客观验证（SECS 余弦 —— 尺子是 Qwen 自空间，**不是 CAM++**）

> ⚠️ **口径更正（2026-10-11）**：本节原写"CAM++ 声纹"是错的。`tools/clone_eval.py` 的 SECS
> 打的是 worker 8001 的 `/emb`，实现是 `qwen3_tts_service._speaker_embedding`
> → `create_voice_clone_prompt(x_vector_only_mode=True).ref_spk_embedding`，
> **与克隆条件同一个编码器（自空间）**。真正的 CAM++ 在 `speaker_sep._sv_embed`（16k/192 维）。
> 为什么这条必须改：`pilotC` 双声纹实测（同批 48 样本）显示自空间**同人分 87.5% ≥0.98**、
> 30s 起 100%，而 CAM++ 同人只给 0.7486 —— 所以下面这些 0.99 量级的数是**在饱和尺子上读的**，
> 不能与 CAM++ 的阈值（现役 ≥0.95 那套）混用，也**不能**跨尺子对比。
> 门禁已改为双门槛（`tools/voice_dual_gate.py`，commit 24f9a11）；**这几条成片尚未补测 CAM++**，
> 补测前不得对外并列两个刻度。

| 对照组 | 自标尺 SECS（Qwen 自空间） |
|---|---|
| 本人两段不同录音（**同人上限**） | **0.9928** |
| pilot：手工挑 10s 干净参考音直接合成（前一轮实验） | 0.9888 |
| **本轮：音色库端到端（切片→采纳→自动参考音→成片）** | **0.8060** |

**0.806 的解读**（⚠️ 已被推翻，见下）：仍显著高于跨人区间（通常 <0.7），听感"像本人"；但相对手工参考音有明显损耗。
归因（待逐项验证）：音色库参考音由流水线从 26 段切片自动构建，切片含 16kHz 重采样与不同信噪比段；
pilot 那条是原始 24kHz 干净段直通 TTS。**改进方向**：采纳阶段用更严的质量阈值（只要 A 级、拉长最短时长），
或对构建出的 `reference.wav` 跑一次 `clone_eval` 再确认。

##### 平反记录（2026-10-10 晚）：0.806 的元凶是位级错读 bug，不是参考音质量

用户听成片反馈"全程电音、刺耳"。逐页 wav `astats` 检查实锤：三页 peak **一模一样**
（-4.997549 dB）、RMS -6.4 dB、Flat factor ≈9.8 —— float32 PCM 字节被
`AudioSegment(sample_width=4)` 按 int32 位级重解释，波形整体顶平成数字噪音
（工程档案 §8.70）。修复（`course_api._pcm_to_segment`，经 int16 落地）后同一音色、
同一课件重出：

| 对照组 | 自标尺 SECS（Qwen 自空间） |
|---|---|
| **修复后：同音色（teacher_voice）+ 同课件重新合成出片** | **0.9905** |
| 修复前（本轮首测，电音版） | 0.8069 |
| pilot 手工参考音 | 0.9888 |
| 同人上限 | 0.9928 |

修复后反超手工链路 —— **teacher_voice 自动参考音质量本来就够**，首测的"损耗"
几乎全部来自电音失真。新成片 `outputs/course_1791606782378/course.mp4`（59.8s，
1920×1080，音轨 Flat 0 / RMS -30 dB），三页 peak -8.4/-9.8/-11.7 自然分布、Peak count 3。
