## 1 产品是什么（一句话）

**把变好的声音直接送进微信和游戏的本地实时变声器。** 不上云、全程本机。

和「本地语音工作站」的区别：它们交付一个音频文件，这个项目**交付一句已经发出去的话**。

三条主路径：

1. **开麦说话**（实时变声）：麦克风 → RVC → 虚拟声卡 → 微信/游戏/Discord 的"麦克风"。
2. **打字让它说**（TTS）：文字 → 用你选的音色合成 → 一键发进微信（含歌声垫底）。
3. **训练变声**（自建音色）：一段素材 → 自动切片质检 → 挑干净片段 → 训练成你的音色。

三端共用同一个本地后端：**桌面端**（Electron，主力）· **手机浏览器遥控页**（零安装，推荐）· **移动端 Expo**（半弃用，见 §5.2）。

### 2.1 后端怎么长出来的（两条规矩，别绕开）

- **能力 = 插件 = 一个 `plugin.json`**。`server.py` 的 `_mount_all()` 只做一件事：读清单 → `mount_plan()` → `load_router()`。**没有 `plugin.json` 的能力等于不存在**（前端不会显示、路由不会挂）。
- **关掉的能力是真不 import** —— 不只是前端不显示。目的是"不拉 torch/CUDA 上下文、不吃显存"。所以**不要在模块顶层 import 重依赖**，否则关掉也照样吃资源。
- ⚠️ 新增一个 `APIRouter` 会同时踩**两条文档新鲜度断言**：README 的 router 计数 + 目录树清单（`test_docs_freshness.py`）。改完直接 grep README 这两处。

### 2.2 前端路由怎么来的（最容易搞错）

- `pages/` 下有 **23 个目录，但只有一部分是路由**。`App.tsx:153` 的 `routePlan` 是**读插件清单算出来的**，不是手写 `<Route>`。
- ⇒ **加页面 ≠ 改 `App.tsx`**。正确顺序：`plugin.json` 的 `routes` 字段 → `pages/<名字>/index.tsx` → 清单校验测试。
- 关掉插件，它的页面自动消失 —— 这是设计，不是 bug。

## 3 怎么跑 / 怎么验

```bash
# 后端（用项目根的 .venv，Python 3.11）
"D:/变声/.venv/Scripts/python.exe" m2_server/server.py

# 前端开发
cd web && npm run dev          # vite
cd web && npm run electron:dev # 桌面壳（vite + electron 并行）

# 只让前端在【安装版】里生效（一条命令，不碰主进程）
cd web && npm run ship         # 构建 → 同步进安装目录 → 逐字节自检

# 门禁（提交前，钩子会自动跑）
"D:/变声/.venv/Scripts/python.exe" tools/check.py --fast

# 复刻 CI 干净环境（推之前才需要，约 9.5 分钟）
"D:/变声/.venv/Scripts/python.exe" tools/check.py --ci-fidelity
```

**门禁 11 个步骤**（`tools/check.py` 的 `STEPS`）：`licenses` `gate` `ownership` `requires` `electron` `ps1lint` `petlayout` `nodetest` `ruff` `pytest` `web`。

`--fast` 只跑 8 项 —— **跳过 `ps1lint` / `nodetest` / `web`（前端）**，且 `pytest` 用的是 `FAST_TESTS` 子集。
⇒ **`--fast` 绿 ≠ 前端绿 ≠ 全量绿**，见 §6.3。`--fast` 实测约 5 分钟（pytest 占 ~294s）。

**跑测试的纪律**（血泪换来的）：

- **一次只跑一个全量**。并发跑两份会抢内存 → 进程被 OOM 打死 → 表现为「FAIL + 耗时远短于基线」，不是用例失败。
- 全量基线看**耗时**：显著短于基线 ⇒ 先怀疑进程被杀，别怀疑代码。
- 精确计数用 `--junitxml`（覆盖率表会吃掉汇总行，且它是**唯一留下失败 traceback 的地方**）。

### 5.1 技术路线（有实测数字）

### 5.3 判定方法本身的坑（**这个比技术坑更贵**）

- ⛔ **`grep` 零命中 ≠ 功能没做**。2026-10-14 用 `grep persona` 判定"人格包没做"（碰巧对了），但同一份表里 **AudioSeal 和"多语言"都判错了** —— 能力落在完全不同的模块名下。
  **正确核实顺序**：`plugin.json` 的 `routers` → 路由文件 → 权重/依赖是否落盘。三步都查完才敢说"没做"。
- ⛔ **`tail` 的沉默不算证据**。2026-10-04 我 `tail -60` 没看到某请求就断言"根本没发出去"，实际 12 条全 200（在前面 185~607 行）。**说"某请求从未发生"之前必须全量 grep**。
- ⛔ **「报告说做完了」≠「做完了」**。核对 `git show --name-only <sha>`；指标声称要能用一条命令复现。
- ⛔ **「单文件绿、多文件红」第一嫌疑是异步写入活过了 teardown**（daemon 线程 / `sleep(20)` 后重写 / 训练线程）。
- ⛔ **「本机绿 ≠ CI 绿」**。三根轴：依赖未声明（Pillow/comtypes 曾从未声明）、平台差异、编码。推前跑 `--ci-fidelity`。

### 8.1 音色与质检

#### 音色体检「三灯」 ✅ 现役

> 落点：`tools/voice_metrics.py`（测量）· `tools/voice_report.py`（分档合成）· `tools/voice_qc.py`（CLI 与落盘）
> · `clips_api.py`（`GET /voice/lamps`、`POST /voice/lamps/scan`）· `VoiceLamps.tsx`
> · 门禁 `test_voice_report.py`、`VoiceLamps.test.tsx`

把已经攒着的内部质检件（CAM++ 声纹 / 切片打分 / 变声验收）合成**三个灯**（相似度 / 自然度 / 夹嗓子风险），
让"这份音色的质量"第一次在界面上可见 —— **训练前就能给预期**。

- ★ **阈值锚在「20 条采样中位数」的 Bootstrap 分布（×2000 次重采样）**，不是文献数字。
  换素材集必须重标，否则灯是错的。
- ★★ **`tilt` 的方向与其余三个指标相反**：`"higher_better": True`（更接近 0 = 谱滚降更缓 = 更健康）。
  写成 `False` 会让 `-7.0`（健康）判红、`-8.0`（挤压）判绿 —— **灯整个反掉，而且看不出来**。
- ★ **H1-H2 的方向与外部调研相反**：通用表述是"越挤压 H1-H2 越低"，本机合成信号实测
  `-2dB→2.31 / -6→6.31 / -12→12.31 / -18→18.31` 完全线性且**越大越挤压**。**以实测为准**，
  别因为"文档那么写"改回去（docstring 里已标注这处冲突）。
- ★ **CPP 被刻意砍掉**：本机信号上不可靠，留着只会制造假阳性。
- **「没测到 ≠ 不合格」是最重要的不变量** —— 读不到就说读不到，别把缺数据渲染成红。
- `voice_qc.py` 与三灯**分工不同，别合并**：前者是切片级 CLI，后者是音色级汇总。

#### 嗓音保存 / 减负实测 ⏸ 协议在附录

研究层（大创）的两份协议，**必须逐字执行**，所以搬到 `附录-可执行规程.md` §4 / §5。
代码分别是 `tools/voicebank_eval.py` 与 `tools/voice_load.py` + `tools/vfi_score.py`。

- ★ **指标方向表**：`tilt` 越大越好、`h1_h2` 越大越挤压 —— 与 §8.1 三灯一致。
- ★ **能量法口径与低电平陷阱**：口播基线的能量阈值不能套到合成音上。
- 结论摘要：真人基线发声 **11:09 / 占空比 87.4%**，旁白合成 SECS 0.99（n=1 预实验）。

### 8.2 合成与变声引擎

#### 级联变声（录音 → ASR → TTS → RVC） ✅ 现役

> 落点：`cascade.py` · ASR 在 TTS worker `127.0.0.1:8001` 的 `POST /transcribe`

- **核心价值**：走文字中转，**源说话人的口音/发音习惯完全不进输出** —— 这是 RVC 直接转换做不到的（RVC 保留源发音特征）。
- **非目标**：不替代 RVC 实时链路；**固有 1.5~2s 滞后**，不做同声传译级体验；本期不做多路并发。
- ⛔ 想让它"边说边出声"= 白费，滞后来自 ASR+TTS 两段串行，不是调参问题（CUDA Graph 也只救 decode 步，见下）。

#### TTS 提速：CUDA Graph ⏸ 已停（未达止损线之外的收益）

> 原 `TTS_CUDA_GRAPH_PLAN.md`。基线 2026-08-30：ASR 11.3x（不是瓶颈）；**TTS 0.35~0.48x，唯一瓶颈**。

- 瓶颈定性靠 `py-spy`：**CPU 97% 单核跑满、GPU 20%**，栈在 `generate → _sample` ⇒
  **逐步自回归的 Python 开销压过了 GPU 计算**，不是算力/显存瓶颈。
- ★ **止损原则（别忘）**：单步 CUDA Graph 加速比 **< 1.5x 立即停**。要从 RTF 0.35 提到 ≥1.0
  需整体 2.5x，而 CUDA Graph 只覆盖 decode 步（prefill 不变）⇒ 单步得显著高于 2.5x 才有意义。
- ★ **同一负载反复跑波动 ±30%**，**小于 25% 的差异一律视为噪声**。

#### 真声直讲（真麦直通 CABLE） ✅ 可行性已真机验证

> 落点：`passthrough_worker.py`（常驻进程）· `passthrough.py`（后端）· 插件隐含在 `sound.rvc-live`

场景：老师用电脑讲课，**平时本人真声**，讲累了按热键让 AI 顶一句，学生那头听到**连续混音**。
现有三条链路都做不到 —— 实时变声会**整个替换**真声，级联要等 1.5~2s。

- ★ **必须用 `OutputStream`，不能用 `sd.play`**（后者阻塞且不给你混音窗口）。
- ★ **设备解析必须排除 `CABLE In 16 Ch`**（与 `rvc_live._device_matches` 同一个坑，见 `犯错档案-微信.md` §2.26）。
- ★ **与 `rvc_live` / `cascade` 互斥**：三者抢同一个输出设备与同一个麦克风。
- ★ **后台常驻进程不要依赖 stdin 判活**（父进程一死 stdin 就 EOF，进程会自己退）。

#### 特效声板（Soundboard） ✅ 现役

> 落点：`soundboard.py` · `board_worker.py` · 插件 `sound.fx-board` · `POST /api/soundboard/premix`

用户原话：「按住 Alt 说话的时候可以突然来一声爆炸声」。**不是剪辑软件，是给变声聊天加综艺感。**

| 决策 | 结论 | 为什么 |
|---|---|---|
| **实时声板是主轴** | 按 Alt 说话中途点格子即时出声，与 RVC 实时变声**同时**进微信 | 用户明确用法；共享模式 WASAPI 由系统混音器自动混合 |
| **离线混音是配菜但必须有** | 发送前勾选 → 烘进音频（`POST /api/soundboard/premix`） | 它是"点格子会抢焦点"那条路的兑底 |
| **预混端点放声板插件，不放 `effects.py`** | 两条路径共用 `sfx_lib.mix_into` 一份 DSP，但端点归 `sound.fx-board` | 端点若挂 `sound.effects`，关掉效果器后按钮就 **404**（速查表 68 / `犯错档案-工程.md` §8.40 同一类缺口） |
| **半自动播放窗口同样可用** | TTS → 播到声卡 → 按 Alt 录制期间点格子，人声与音效同进一条语音 | 声板**不进** `_send_lock`，播放窗口内点格子畅通 |
| 引擎进本体、素材走下载 | 插件带引擎+6 个出厂音效，更多素材包走 `core.market` | 「一切皆插件」：本体小、按需下载 |
| **素材只收 CC0** | 出厂包全部 CC0（可再分发、零署名义务） | 调研结论 |
| **不碰微信自动化** | 声板只管"把声音播进 CABLE" | 微信模块是全仓坑最密集区，能不碰就不碰 |

⚠️ 想"在语音播放中途插一声音效"**结构上做不到**：播放前就整段合成完并一次性灌进 CABLE，不存在"正在说话"的中间态。

#### 场景包（「你想干什么」） ✅ 现役

> 落点：`live_settings.py` 的 `SCENES`（**唯一真相源**）· `GET /rvc/live/scenes` / `POST /rvc/live/scene`
> · `LiveScenePacks.tsx` · `useLive.ts` 的 `applyScene`

四个一键组合：开黑 / 微信 / 直播 / 会议。用户想的是「我要开会」，不是「index_rate=0.5、关字幕、开降噪」。

- ★★ **`in_settings`（落盘）与 `on_start`（不落盘）必须分开**。混在一起会让"套用场景"顺带改用户的持久设置。
- ★★ **「现在高亮哪个场景」不能用设置反推**：开黑/微信/直播三场景的设置相同，反推会**恒等命中 order 最小的那个**。
  高亮必须记「上次点了哪个」，不能算。
- ★ **场景表只做加法映射**：场景 → 设置是单向的，不许出现"某个设置反向决定场景"。
- 加场景的顺序见原文档 §6；与「性能模式」的关系见 §7。

### 8.3 微信能力栈

#### 微信状态雷达（L0 像素 / L1 判断） ✅ 现役

> 落点：`chat_radar/`（`capture.py` / `sides.py` / `names.py`）· 插件 `hook.radar`

2026-10-23 三条路实测，差距不是一点点：

| 方案 | 左右位置 | 时间戳 | 耗时 | 可调试性 |
|---|---|---|---|---|
| Qwen3-VL-4B 一次读整段 | **0/4 对** | 0/2 | 5.76s | 错在哪不知道 |
| Qwen3-VL-4B 分段读 | 4/4 对 | 0/2 | 4.38s | 错在哪不知道 |
| **像素行投影（现方案）** | **11/11 对** | **2/2 对** | **171ms** | 每个数字都能打印 |

- ★ **抓图必须带 `PW_RENDERFULLCONTENT`**，否则后台窗口抓到黑图。
- ★ **坐标系必须分清**：`WindowInfo` 是**逻辑像素**，`image` 是**物理像素**（125% 缩放下 1.5 倍），
  UIA rect 是**屏幕物理坐标**。裁图前按 `img.shape[1] / window.width` 换算 —— 写死像素会切进头像。
- ★ 左右归属 = 行投影 + 最长连续段，**不许滚动、不许改微信状态**（只读边界）。
- **L1 分级触发**（钱花在刀刃上）：只有"对方最后发言 + 等够久"才叫模型，其余走规则。
- 群聊「谁说的」= 本节 + §4.5：**归属用像素 IoU、名字用 Ornith 读带序号的拼图**。

#### 长文分段发送（60s 硬上限） ✅ 现役

> 落点：`wechat_voice.py` 的分包 + `WECHAT_AUDIO_BUDGET_S`（54s）

把「一次发一条 wav」改成「**一次发一批 ≤54 秒的 wav**」，切分点落在句子/静音处，
**环境准备与声卡还原整批只做一次**。

- **D1 分包在后端做，不在前端** —— 前端只传整段文本，预算护栏在唯一出口。
- **D2 用「实测时长」贪心装箱，不用「字数 ÷ 语速」估算** —— 中文语速估算误差能吃掉 10 秒余量。
- **D3 逐句合成，不整段合成后再切** —— 整段切会把词切断，且丢句间自然停顿。
- **D4 复用 `split_sentences()`，不新写断句器** —— 已经有两处消费方。
- **D5 单句自己就超过预算时必须有兜底**（截断 + 告警，而不是发出去被微信砍）。

#### 全局托管（`/autopilot`） ✅ 现役 · ⚠️ 默认关、每次启动重开

> 落点：`chat_autopilot.py`（28KB）· 页面在 `hook.wechat` 托管页 · 桌宠建议区第 4 条固定入口

**四项拍板**（2026-10-24）：**文本消息** / **指定会话白名单** / **只回提问和 @我** / **每次启动重新开启授权**。

- ★ **这是对两条旧硬口径的"划例外"，不是推翻**：`assistant_api` 的「一切发送先出提案再等确认」
  与 `chat_radar`/`chat_read` 的「只看屏幕不发消息」仍然有效。
  例外只在**托管页**、只在用户**当次亲手勾选**后、只覆盖**文字**、只发给**白名单会话**。

> 落点：`m2_server/assistant/` + `assistant_api.py`

把「群里那句话」变成一张**待你点头的提案**。共同结构：读懂一句人话 → 变成一件具体的事 → 等我点头 → 才动手。

见 §4.5 与 §5.1 前五行。**一句话：UIA 没有发送方，但矩形有昵称像素；归属靠 IoU，名字靠 Ornith 读拼图。**

- ★ **拼图必须带红色序号并按号回填**：按数组顺序返回时，模型漏一条/多一条会整排错位 = 把 A 的名字安到 B 头上。
- ★ `read_names()` 是**独立入口**，占 6G 显存，**不许进任何自动刷新路径**（会和实时变声互斥）。
- ★ **入口是 `POST /api/radar/names`，不是 GET**：它会拉起模型、写缓存 —— GET 允许被浏览器/代理
  预取和重试，「预取一次 = 跑一次模型」。壳上另外两样：`Lock(blocking=False)`（双击不排队跑第二遍，
  实测一次 2.7s）＋ timeout 夹到 5~180s（传 10000 会一直攥着锁，后面的点击全排队）。
- ★ **认完按 `speaker` id 贴回屏上那几行，不重读 `/chat`**：重读要再遍历一遍 UIA，还会顺手把
  「怎么回」再问一遍模型。唯一要防的是**会话被换掉**（认人的 3 秒里用户点了别的群，id 是各自
  会话里重新编的）→ 先比 `chat` 标题，不一致就整份重读。
- ★ **认不出不是错误**：`learned:0` + `note` 走 200，提示行不涂红 —— 单聊没有昵称条、群友整段
  发表情、视觉权重没装都是常态，红字只留给「真的坏了」。
- ⚠️ 已知边界：引用卡片那条昵称在卡片内，识别不到 → 返回空串（**故意不猜**），会与同一人的普通消息分成两个人。

### 8.5 插件系统与能力开关

#### 「一切皆插件」 ✅ 已落地（30 个能力包）

> 落点：`plugin_manifest.py`（清单真相源）· `plugin_loader.py` · `server.py:_mount_all()` · `plugin.json`

灵感来自 DeepSeek Harness 的 "everything is a plugin"。**先说清楚哪些收益是真的：**

- ★★ **插件化救不了安装包体积**。实测拆 `VoiceMorph-Setup.exe`（101.5MB）：Electron 运行时 178MB（未压缩）
  + chromium dll ~68MB + `app.asar` 47.1MB→6.74MB + `backend/` 16MB。**exe 主体是 Electron，砍不掉。**
  真正的收益是**首次体验路径**与**按启用集装 pip extras**（省几个 GB）。
- ★★ **必须配「套餐预设」，否则重蹈 DSH 的覆辙**：DSH 讨论区第一条反馈就是
  *"everything is a plugin 对开发者是卖点，对终端用户是配置负担"*。所以默认给预设，插件清单收进「高级」。

| 预设 | 内容 | 面向 |
|---|---|---|
| 轻量 | `core.*` + `sound.offline-vc` | 只要一个能变声的，硬盘紧张 |
| **标准（默认）** | `core.*` + **变声本体**（`offline-vc` · `rvc-live` · `audition`） | 绝大多数人 ← 2026-09-23 拍板收窄 |
| 全能 | 全开（**除停用路线**） | 开发者 / 内容创作者 |
| 高级 | 逐项开关 | 排查、极客 |

- ★★ **「本体」定义只有一处**：`plugin_manifest.BODY_IDS`（+ `core.*` 与 `requires` 闭包，由 `expand()` 补）。
  就是「**选音色 → 变 → 听**」。其余 **9 项默认关闭**：训练、微调、发掘、输字变声、有声书、效果器、桌宠、皮肤市场、微信发送。
- ★ **「可关」的四个真实行为**：后端不 import（不拉 torch/CUDA）· 前端不注册路由不加载 chunk
  · `/api/diagnose` 不再对没启用的能力报红 · `setup_env.ps1` 不装它的 extras。
- ★ **首次运行播种**：`disabled_ids()` 在文件缺失时返回**空集**（= 全开），所以必须显式播种，
  否则"标准预设"在首次启动时形同不存在。
- ★ **真正值得走"按需下载"的只有边际依赖大的那几个**：`sound.tts`（`qwen-tts` + 4.9G）、
  `pet.companion`、`hook.wechat`、`sound.effects`。**不是** `sound.ft` —— 它的 extras 是
  `sound.workshop` 的真子集，边际依赖 = 0，做成下载省 0 字节却要付全套远程分发成本。
- ★ **按需下载的真障碍是"前端是构建期静态的"**，不是后端：`web/src` 在构建时就把插件清单算进了
  `routePlan`，运行时下载的插件**没有对应的 chunk**。所以"远程下载"要动的是构建链，不只是后端。
- ★ **挂载顺序没有语义**（2026-09-20 实测 139 条路由 0 重叠）—— 别为了"看起来有秩序"去排序
  `plugin.json` 的 `routers`，那不会改变任何行为，只会让 diff 变脏。


### 10.1 克隆路线裁决：RVC 赢，赢在音色不在自然度 `[本机实测]` 2026-10-14

同素材、同 3 句、同参考音，三种做法正面对照「克隆自己的声音」谁更像：

| 做法 | CAM++ 相似度 | 结论 |
|---|---|---|
| **RVC 训练式** | **0.8356 ~ 0.8447** | ✅ 现役 |
| 千问微调（QLoRA） | 0.8030 | ⛔ 该 pass 的是**这条克隆手段**，不是千问引擎 |
| 零样本克隆 | 0.8006 | ⛔ 5~10s 参考音的上限 |

- ★ **跨 seed 区间不重叠** —— 这不是"差不多"，是可复现的差距。
- ⚠️ **「自然度」这一轴本次判不了**：尺子失效（两只产物都用同一套 TTS 前端），
  **别引用这次实验去论证"RVC 更自然"**。

### 10.2 翻唱「闷 / 混杂」：主因在素材，旋钮救不了 `[本机实测]` 2026-10-14

| 候选解释 | 实测 | 结论 |
|---|---|---|
| 分离器漏伴奏 | `htdemucs_ft` 慢 1.5×、副歌**更脏** 3/3 次（中位 −3.08dB） | ⛔ 不换 |
| checkpoint 不对 | e10–e40 扫描，e30 在 **8/8 频段同号**把能量 800–4000Hz → 200–400Hz | ⛔ 不换（e30 = "更浑厚"，恰好加重"闷"） |
| `protect` 参数 | 本 fork 里是**死参数**（`pitchff` 恒 1，三档输出**逐字节相同**） | ⛔ 死路 |
| 变调没对齐 | 保持原调时对原唱 CAM++ **0.2557** = 真正的"像两个人" | ★ 真因之一 |
| 训练素材频谱倾斜 | 产物 4–8kHz 掉 **18.5dB**；同一模型过自己说话素材只掉 2.5dB | ★ 真因之二 |
| **训练切片 2kHz 以上 +3dB/oct 预加重后重训** | 4–8k 高 **4.2–6.2dB**、8–11k 高 6.0–7.6dB、质心 **+126~233Hz**，**总电平几乎不变**；两组独立复现 | ✅ **唯一可落地杠杆**（不用重录） |

- ⚠️ 剂量曲线（+6dB/oct）**未测**（Windows 提交内存耗尽没跑完）。听感定稿仍需人耳。
- ★ 方法论：**"两个东西差不多"必须先证尺子能分辨差异** —— 拿"整首歌 vs 分离人声"
  当对照（差 48.24dB），否则"没差异"无法证伪。

### 10.3 能唱多高 ≠ 模型上限，是训练集里有没有那个音高的音色 `[论文]+[本机实测]`

- ★★ **推翻「高音天花板 ~272Hz」**：那条结论来自 `pitch=-12`（降八度）产物。
  同一输入 `pitch=0` 实测中位 **351Hz**、周期度 0.942。
- **RVC 作者亲答**（issue #957）：训练集内需要带高音数据 —— 这是数据问题，不是架构上限。
- **音区 ≠ 音高**：DDSP-SVC 有独立的 `vocal_register_shift_key` / `formant_shift_key`；
  **RVC 只有一个移调旋钮**（这就是为什么"拔高就夹嗓子"）。
- **移调增强的论文证据是负面的**：WeSinger / SingAug / SPA-SVC 均报损伤音色。⛔ 别做。
- **SVS 路线门槛真实存在**：ACE 要 30–100 分钟歌声、Synth V 不支持自助训练。

**实时 VC / SVC 全景（2026-10-14）** —— 8GB + 中文 + <100ms + 离线，**没有单一最优解**：

| 方案 | 延迟 | 需训练 | 中文 | 判定 |
|---|---|---|---|---|
| **RVC v2** | **ASIO 90ms** | 是 | 好 | ✅ **四约束下最稳**，但"零样本"维度落后一代 |
| X-VC | 240ms | 否 | 零样本中文最佳（SIM 0.60） | ⛔ 延迟超标 |
| Conan-fast | 37ms | 否 | **仅英文，无中文验证** | ❓ 不可用 |
| Seed-VC | ~300ms（官方自述算法延迟） | 否 | 间接支持 | ⛔ 延迟 + 现役入口唱不了歌 |
| so-vits-svc | — | 是 | — | ⛔ **已被 RVC 取代，不要作为新选型** |

结论：**"免训练换声"在质量上已成熟、在延迟上尚未成熟。**

### 10.4 方言：从潮汕转向四川/重庆（2026-10-22）`[本机实测]`

潮汕路线 ⏸ **暂停**，原因**不是技术失败，是成本结构**：用户非潮汕母语者 ⇒
正字没人校、可懂度没人判、素材扒不到，三件事叠起来把 18.9h 语料门槛抬成硬墙。

四川/重庆把三个死结同时解开。三条路按成本排：

| 路 | 做法 | 成本 | 得到什么 |
|---|---|---|---|
| **A** 借现成方言音色 | `Qwen3-TTS-1.7B-CustomVoice`，`speaker=Eric` | 约 4GB 下载 | 立刻听到成都男声，**但不是你的声音** |
| **B** 零样本克隆你的四川话 | 你录 20–40 秒 + 写下原话 | 一次录音 | **你的音色 + 你的口音**，当天可听 |
| **C** LoRA 微调 | 录 10–30 分钟 | 半天 | 长句、多音字、语气词最稳 |

- ★★ **B 是这次转向真正的红利**：在潮汕方案里"我的音色"要靠 RVC 从别人的音频转，
  跨语言失真只能硬扛（§9.3 实测 **0.64–0.67**）。你自己能说四川话 ⇒
  **录音同时解决音色和口音，RVC 整条可以从链路里去掉。**
- C 不是 B 的对立面：B 若长句飘，直接拿**同一批录音**上 LoRA，数据不用重录。
- 定位：**研究用途，不做商用**（潮汕那份的 NC 语料结论仍成立）。

### 10.5 微信自动化：我们已在定义社区还没有的东西 `[社区]+源码逐条比对` 2026-10-14

需求"自动给个人微信发语音"只存在约 **6 个月**，社区来不及沉淀。四条路线格局：

| 路线 | 代表 | 状态 |
|---|---|---|
| **UIA + gate 热激活** | wechatauto-replica（440★） | ✅ 唯一可行主轴，但它**不发语音**（只有语音下载/通话/转发成文件）|
| | pywechat（2015★） | ✅ 社区**唯一实现发语音**的，但**零校验** |
| Hook | 全线不支持 4.x | ⛔ |
| 视觉 | 无成熟实现 | ⛔ |
| 官方 | 无个人号接口 | ⛔ |

**我们领先社区的 4 项**（逐条比对源码，不是自评）：

1. **单击话筒 → 持续录音 → 点浮层 ↑ 绿钮** —— pywechat 用 `mouse.move` 移出按钮来"松手"，
   再点**预先算好的原按钮中心**。我们更干净，它那个很脆弱。
2. **`≤54s` 分段 + 事前预算护栏** —— pywechat 超长**直接截断丢弃**后半段，用户无感知。**社区完全空白。**
3. **读 UIA `ChatVoiceItemView` 的 `语音15"秒` 校验** —— pywechat 零校验，另一个仓库走 DB 水位（要解密 SQLCipher）。**我们更轻。**
4. **绿钮 HSV 色域检测** —— 三个仓库**均无**。

外加一条：`犯错档案-微信.md` §2.2「发出去却是 60 秒」是全社区**唯一**的诊断。
pywechat 的「按住→播放→释放」范式在**结构上**就会触发它（原始 DOWN 永不解除 → 录满 60s），
**且因为它没有校验所以永远发现不了**。

> 社区缺的还有三件我们也没有：gate 扫描三件套、拟人节流、解除静音。要不要补见 §6.2。

### 10.7 用户需求与界面精简：病根不是"功能多" `[社区评价]+[本仓实测]` 2026-09-25

用户原话：「感觉我们这个应用还是有点问题……功能有点太冗余了，太复杂了」。
交叉了 Voicemod / MorphVOX / 叮咚 / 小火苗 / MagicMic 等同类产品的用户评价与本仓前端实测。

结论与后续三次改版一致：**抱怨的落点不是数量，是"入口和此刻该做什么无关"**。
所以对策不是砍功能，而是 ① 预设（§8.5）+ ② 按上下文推荐（§8.4 建议面板）+ ③ 一句话入口（§8.4 魔法时刻）。

### 10.8 主唱/和声分离：现有代际到顶，要换模型不是换参数 `[论文]+[本仓实测]` 2026-10-15

- blind2 五个候选**全员 UVR MDX 老系**（2022–2023），MVSEP 验证集上 Lead SDR ≈ **6.4–7.4 dB**。
- 当代天花板 **BS-Roformer karaoke = 10.10–10.77 dB**，差 **+3~4 dB**。
  ★ SDR 是 dB 尺度，**+3dB ≈ 失真能量减半** —— 这是"残留能否压到换声容限之下"的量级差。
- **Fullness ↔ Bleedless 训练互斥**，这解释了"忽弱忽小"。
- 物理边界：**unison 齐唱不可完美分**。
- ⚠️ **许可警告：chorus 模型 CC-BY-NC-SA，禁商用。**
- 结论：**三个新模型没有一个能直接当产品默认**；许可清账是定稿后的第一道手续。

### 10.9 电音归因 `[本机实测]` 2026-10-20

**两件事都不是 BWE 引入的，但 BWE 让第一件显形。** 即：电音来自模型本身的非周期成分缺失，
不是后处理链路引入的 —— 所以**换后处理救不了**，只能动训练域（见 §5.1 最后一行）。

### 10.10 微信语音「边有歌声边说话」 `[平台约束]+[本仓实测]` 2026-10-13

- **微信单条语音 60s 硬上限**、**16kHz 人声优化编码会把音乐高频削掉** → 平台侧无解。
- 结论：**合成侧混轨、发送链路零改动**。已实现为 `POST /api/soundboard/bgm/premix`（§4.4）。
- 与发送/声板/预混的冲突已对账：声板**不进** `_send_lock`，播放窗口内点格子畅通。

## 13 这份文档怎么维护

**什么时候改它**（只有这四种情况）：

1. **勾掉一项** —— §6 的某条做完了，移到 §4 并打勾（带 commit 或落点）。
2. **加一条"此路不通"** —— §5 新增一行，必须带**证据 + 日期**。没有证据的"我觉得不行"不要写进来。
3. **加一条设计决策** —— 写进 §8 对应子节，格式固定：**拍板了什么 / 为什么不选另一条 / 改它会打断什么**。
4. **数字过期** —— 改完先跑一遍命令再改，别凭记忆。过期值进 §11.3 黑名单。

**不要把它写成**：变更日志（`git log` 就是）、待办池（§6 只放"有明确下一步"的）、
外部资讯集合（§10 只放"能落到决策"的）。

**守卫在哪**（改完文档必跑 `pytest m2_server/tests/test_docs_references.py m2_server/tests/test_docs_freshness.py`）：
它查 `docs/<文件名>.md` 形式的死链、`§N.M` 引用能否解析、速查表行号 1..N 连续、§9 不许再长回去。
扫描范围 = `docs` `m2_server` `tools` `scripts` `tts_trial` `web/src` `web/electron` `.github` …，
`tts_trial` 是**2026-10-27 才补进来的**（此前整目录被跳过，于是
`docs/大创申报-2026-10/` 搬走后它的测试路径没人发现，一路绿到全量 pytest 才炸）；
它下面的 `venv312` / `MeanVC2` 仍在排除名单里，别整目录放开（11.6G / 6 万条目）。


**写法要求**：

- 每条**必须能落到一个文件、一个路由或一个命令**。写不出落点的，说明它还没做完，或者你还不够了解它。
- 数字**必须带实测日期**。跨天引用旧结论前先复算 —— 本项目已经因为"沿用三天前的结论"错过一次
  （`pitch=-12` 被当成模型能力上限）。
- 状态只用四种：✅ 完成 / ⚠️ 部分 / ❌ 未做 / ⏸ 停用。**不要用"基本完成""差不多"**。
- **不许再新开 `docs/*.md`**。新内容按上面四条塞进这四份之一；
  只有当它有"必须逐字执行"或"查事故要逐条翻"的属性时，才配进 `附录` / 两份档案。
