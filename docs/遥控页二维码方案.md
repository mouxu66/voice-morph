## 二、已建成的链路（逐层，均已核实）

```
桌面端 /capabilities 页
  └─ RemoteQrCard.tsx          四态渲染 + 复制地址 + token 提示
       └─ client.ts:191        getLan() → GET /api/system/lan
            └─ system_api.py:417  system_lan()
                 ├─ _lan_candidates()   UDP connect 10.255.255.255:1（只查路由表，不发包）
                 ├─ _is_rfc1918()       ★ 关键判据，见下
                 └─ 组装 http://<ip>:8000/remote.html[?api_key=…]
```

### 为什么 IP 判据是 RFC1918 而不是「第一个非回环地址」

本机跑着 **Mihomo TUN + ProtonVPN + Radmin VPN** 三层虚拟网卡。
`os.networkInterfaces()` / `getaddrinfo` 的返回顺序里，
`127.0.0.1` 之后紧接着的常常是 `198.18.0.1`（TUN 的假地址）或 VPN 的 `10.x` 隧道地址 ——
**不是**用户家里 Wi-Fi 路由器的那个 `192.168.x.x`。

`system_api._is_rfc1918()` 只收 `10/8`、`172.16/12`、`192.168/16`，
再叠加 `_lan_candidates()` 里「主路由优先」的排序，才是对的。
这条判据是**本机实测逼出来的**，不是理论推导 —— 换台机器（无虚拟网卡）时它同样成立，
但如果哪天出现别的虚拟网卡段位，得回去看 `_is_rfc1918`。

### 四个状态都处理了（`RemoteQrCard.test.tsx` 5 条钉住）

| 态 | 触发 | 界面 |
|---|---|---|
| `loading` | 请求在飞 | 「正在获取局域网地址…」 |
| `ready` | 拿到 url | 二维码 + 完整 URL + 复制按钮 |
| `no-lan` | `url` 为 null | 「没插网线 / 没连 Wi-Fi / 只有虚拟网卡」 |
| `error` | 请求抛了 | 「拿不到局域网信息 —— 后端没在跑？」 |

**二维码与展示文本同源**：都从同一个 `state.url` 生成
（`renderSVG(text)` + 直接渲染 `{state.url}`），不会出现「扫出来和看到的不一样」。
这是本仓的老坑类型（枚举表两侧不同步），这里靠单一数据源从根上避免。

### token 处理的诚实性

`token_set` 为真时提示「地址里已带上访问密钥，别发到群里」；
为假时显示后端给的 `note`（未设 `VM_API_TOKEN`，LAN 内任意设备可访问全部接口）。
**不静默隐藏这个事实** —— 与 `60秒魔法时刻.md` 那两条诚实性不变量同一个取向。

## 三、剩下的两个问题：一个事实、一个决策

卡片建好了，但有两件事挡着它真正被用上。**第一件是事实发现，第二件是产品决策**——
前者比后者更值得先看，因为它决定了「卡片该放哪」这个问题还成不成立。

### 问题 1（事实）：`standard` 预设下，遥控页三个 tab 有两个是灰的

`remote.html` 实际打的端点与它们归属的插件：

| 遥控页功能 | 依赖端点 | 归属插件 | 在 `standard` 里？ |
|---|---|---|---|
| 手机当麦 / 实时变声遥控 | `/api/rvc/live/*`、`/api/voices` | `sound.rvc-live`、`core.voices` | ✅ 都在 |
| **打字发语音** | `/api/wechat/send_text`、`/api/wechat/preview_text` | `hook.wechat` | ❌ **默认关** |
| **发进微信** | `/api/wechat/send_voice`、`/api/wechat/precheck` | `hook.wechat` | ❌ **默认关** |

（`standard` 全集 = 7 个 `core.*` + `sound.offline-vc` / `sound.rvc-live` / `sound.audition`，
`plugin_manifest.py:381`，实测 `expand()` 得出。）

**也就是说**：扫码进去的人看到的是**两个能用、一个半残**的页面 ——
而遥控页的主要卖点恰恰是「打字 → 发进微信」，那正好是灰掉的部分。
所幸 `block_reason` 已在 `51b0157` 接上，所以不会白等十几秒，会如实说明发不出去的原因。

> 注意别把依赖认错：遥控页**不依赖 `sound.tts`**（`grep` 过它的全部端点，
> 没有 `/api/tts/*`）。它的语音合成走 `/api/wechat/preview_text` 与 `/api/media/outputs/`，
> 也就是**复用微信发送那条链**，所以真正的卡点是 `hook.wechat` 一个。

### 问题 2（决策）：卡片放哪 —— 用户找不到它

`CapabilityIndexPage.tsx` 的头注把这个页面刻意排除在主导航之外：

> 本页就是那条路径：不改变任何现有入口，只做一份**可搜索、可浏览**的清单。
> 它刻意不放进主导航 —— 索引页是"我要找某个东西"时才来的地方，
> 常驻侧栏只会把刚做完的降噪又还回去。

这个判断对**索引清单**成立。但 `RemoteQrCard` 不是「索引项」，它是**一个要主动发起的动作**
（把地址递给手机）——「我想用手机遥控」这个念头出现时，用户不会去翻索引页，
他会去找「微信发送」那一页（因为遥控页的主要用途就是发微信语音）。

### 候选方案

| 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A · 移入微信发送页** | 放在「输字变声 → 微信发送」tab 顶部 | 意图最近：想发微信语音 → 顺手扫码 | 该 tab 属 `sound.tts`，默认关闭 → 大量用户看不到 |
| **B · 首页加一个入口** | 首页 hero 区加「手机遥控」小卡 | 曝光最高 | 首页是「60 秒魔法时刻」的所在地（`docs/60秒魔法时刻.md` 钉死过它的两按钮 hero），**不能再加第三个主动作** |
| **C · 保持现状，只加指引** | 在**核心必开**页面（首页 / 实时变声）加一句「要用手机遥控？去能力索引页扫码」 | 零结构改动、不动既有设计 | 多一次跳转，且依赖用户照做 |
| **D · 先修问题 1** | ~~先让 standard 下遥控页完整可用，卡片位置就随它走~~ **已否决**（2026-10-02） | 治本 | 要动 `BODY_IDS`（两处测试逐字钉住）；用户选了插件路线，见 §五 |

**我原先的建议是先 D 再 C**（问题 1 比位置更卡：把卡片搬到微信发送页只有在那个 tab
可见时才有意义）。**D 已被 §五 的插件方案取代** —— 它同样解决了"依赖默认关着"，
但不动 `BODY_IDS`、不拖累 `standard` 预设，且更符合"一切皆插件、按需安装"的既定架构。
卡片位置因此仍悬着（见下面第 2 条）。

### 需要你回答的问题（2026-10-02 更新：只剩一个）

1. ~~**遥控页算不算「变身本体」的一部分？**~~ **已由更好的方案回答**：
   用户 2026-10-02 拍板「手机控制做成一个插件，有需要就安装」——
   于是不动 `BODY_IDS`（`plugin_manifest.py:390`），
   改为新增可选插件 `hook.remote`，`requires` 三个能力实现同样的效果，
   且**不拖累 `standard` 预设**。落地细节见 §五。
2. **卡片放哪**：遥控插件装上后，二维码卡片是否要跟着「插件状态」出现/消失？
   现状是卡片无条件渲染在能力索引页（`CapabilityIndexPage.tsx:88`），
   插件关掉时它仍会显示一个扫不开的码 —— **这是一个真实的小缺陷，还没修**。
   修法有两种（按 `state` 隐藏 / 保留但显示"该能力未开启"），等你定。
3. **能力索引页本身要不要有导航入口**：它现在也没有侧栏项（独立于二维码，可不做）。

## 五、`hook.remote`：手机遥控做成可选插件（2026-10-02 落地）

### 定位

用户拍板：「手机控制那个桌面端应用，我希望它做的是一个插件，有需要就装。」
这个定位在插件系统里**原生成立** —— `requires` 是硬依赖闭包（`expand()` 自动补齐），
`extras` 声明要准备什么，关闭还有 409 守卫。

### 它不拥有任何功能 router

遥控页三个标签的端点分别属于三个已有插件：

| 标签 | 端点 | 归属插件 |
|---|---|---|
| 手机当麦 | `/api/capture/mic/upload` | `pet.companion` |
| 实时变声 | `/api/rvc/live/*` | `sound.rvc-live` |
| 打字发语音 | `/api/wechat/*` | `hook.wechat` |

所以插件定义里**不搬代码**，只声明依赖：

```json
{ "id": "hook.remote", "requires": ["sound.rvc-live", "hook.wechat", "pet.companion"],
  "routers": ["remote_api"] }
```

### 为什么 `routers` 不能是 `[]`

`plugin_manifest.py:198` 明确拒绝空 routers（「一个不挂 router 的插件不该存在」）。
本项目的取舍是**不放宽这条校验**，而是给它一个真正属于它的端点：

    GET /api/remote/capabilities   三个标签各自能不能用、缺什么、为什么

这不是为过校验而造端点 —— 它解决一个**真实存在的缺口**：
`remote.html` 原来自己在 JS 里手抄了三处 `capOff('hook.wechat')` 之类的字面量，
而依赖关系只写在清单里。两处靠人的记性保持一致，**清单改一次而页面忘了改，
手机端就会对着已关掉的能力显示可点按钮，且没有任何现有测试会红**
（`remotePage.test.ts` 钉的是"端点存在"，不是"依赖一致"）。
现在这份知识由后端从自己的 manifest 现算再吐给页面。

代价：`requires` 给 `sound.rvc-live` / `hook.wechat` / `pet.companion`
各加了一个依赖方，**直接改写了若干条以它们为样本的既有测试的前提**
（`enabled_ids` 的复活闭包会让"关掉它"变得不生效）。受影响的四条已改样本
而非放宽断言，各配一条"这个样本必须仍无人依赖"的守卫。

### A 方案的代价（已知并接受）

`sound.rvc-live` 的 `extras` 里有 **RVC 整合包 1.5 GB**。选A（三个依赖全拉）意味着
"装手机遥控"会连带拉这 1.5GB。判断依据：遥控页的价值就是
「手机当麦 → 立刻变声 → 发微信」这条链，断一截则都不成立，
1.5GB 在这里是必要成本而非浪费。

## 五、明确不做（避免下次重开讨论）

- ❌ **mDNS / zeroconf**：网页没有 Bonjour 浏览能力，`.local` 在安卓浏览器也不可靠。
  已于 2026-10-01 改判为「浏览器端走不通」，issue #1 的主语（已放弃的 Expo App）随之失效。
  CORS 对 `.local` 的放行保留即可。
- ❌ **在手机上装 App**：遥控页零安装是它的核心优势，引入安装成本就抵消了。
