### 3.8 `EnumProcesses` 在 psapi.dll，不在 kernel32 ✅（2026-09-12）

写 `wechat_proc.list_wechat_processes()` 的 ctypes 兜底时按直觉写了
`ctypes.windll.kernel32.EnumProcesses` → 运行即
`AttributeError: function 'EnumProcesses' not found`。
kernel32 只导出 `K32EnumProcesses`，裸名 `EnumProcesses` 属于 **psapi.dll**。

对策：`ctypes.WinDLL("psapi").EnumProcesses`，失败再退 `kernel32.K32EnumProcesses`；
且**整段兜底包 try/except 返回空列表**——"列不出进程"不该让上层（判断要不要重启微信）
直接炸掉，那只会把一次发送变成 500。

**泛化教训**：写"没有第三方库时的退路"时，别只测理想路径；
退路本身报错并把异常抛给调用方，比没有退路更糟。

### 3.9 本机全绿 ≠ 干净环境能跑：缺的是"传递依赖"，不是代码 ✅（2026-09-13）

**症状**：本机 `.venv` 跑 `tools/check.py --no-web` 全绿（576 passed）。按 CI 的方式
建一个**只装 `requirements-dev.txt`** 的干净 venv，同一条命令立刻红：

```
FAILED test_wechat_record.py::test_find_green_send_hit  - ModuleNotFoundError: No module named 'PIL'
FAILED test_wechat_record.py::test_find_green_send_miss - ModuleNotFoundError: No module named 'PIL'
ERROR  test_audio_diag_tools.py::test_name_of_tolerates_garbage_input
ERROR  test_audio_diag_tools.py::test_role_names_cover_all_core_audio_roles
       └─ fixture 要 exec_module(tools/cable_watch.py)，而它顶层 import comtypes
2 failed, 569 passed, 3 skipped, 2 errors
```

**根因**：`Pillow`(PIL) 和 `comtypes` **从未写进任何 requirements 文件**，本机有只是因为它们
是**别的包的传递依赖**——Pillow 来自 gradio/matplotlib/tensorboard，comtypes 来自
pycaw/uiautomation（都是 RVC/训练侧顺手装的，不在 `requirements.txt` 里）。
唯一能看穿这一点的是 `pip show pillow` 的 `Required-by` 一栏。

**后果比 CI 变红严重**：`m2_server/wechat_voice.py` 的 `_grab_gray` / `_find_green_send`
是**主进程内**的截图定位（`from PIL import ImageGrab` 写在函数体里），所以
`python -c "import server"` 干净环境也能成功、启动一切正常 —— **懒加载的 import 骗过了
"能不能启动"这个检查**。新用户按 README 装完依赖，跑到"发送语音"才炸。

**对策**：

1. 判断标准不是"哪里 import"，而是"**哪个进程会执行到这行**"：
   测试 / `tools/` 会碰的 → `requirements-dev.txt`；生产进程会碰的 → `requirements.txt`。
2. 本机验完**必须再用干净 venv 验一次**（CI 复刻，约 3 分钟）。已封装成一条命令：

```bash
python tools/check.py --ci-fidelity     # 改了依赖 / 加了测试之后跑它
python tools/check.py --ci-fidelity --recreate   # 手工装过东西、要零污染时
```

它做的事（手工也能复现，但没必要）：版本号从 `.github/workflows/ci.yml` **读**
（不写死，否则复刻自己会漂移）→ 建/更新 `.venv-ci/`（只装 `requirements-dev.txt`，
依赖指纹没变就跳过 pip install）→ 用它跑 CI 那条 `--no-web` 命令 + `tsc -b`。

输出末尾会诚实列出**没被复刻的差异**（runner 镜像、Linux 大小写、`npm ci` 全新安装、
偶发并发），别把它的绿当成 CI 一定绿 —— 但它的红一定是真红。

3. 别指望传递依赖：上游换实现或降级，你的功能就无声消失。测试路径上的可选依赖
   要么显式声明，要么 `pytest.importorskip` —— 但**不能两头都不做**。

**证据**：`git grep -ln PIL -- m2_server tools` = `wechat_voice.py` + 3 个 `tools/` 脚本 +
1 个测试；`pip show pillow` → `Required-by: gradio, matplotlib, tensorboard`。
另一条旁证：修复后瘦环境装到的是 **Pillow 12.3.0**，而本机 `.venv` 里是 **10.4.0**
（传递依赖钉的旧版）—— 两个环境连依赖版本都不一样，"本机验过"本来就不等于"能跑"。
修复（补声明）后：瘦环境 **573 passed + 3 skipped**、本机 **576 passed**，两边全绿。

**泛化教训**：`import` 写在函数体里（为了懒加载 / 可选降级）会让"启动成功"变成假的安全信号。
CI 的价值不在于它多跑一遍测试，而在于它跑在一个**和你机器不一样的环境**里。

### 3.10 本机全绿 ≠ CI 绿（第二根轴）：缺的是"本机资源"，不是代码 ✅（2026-09-13）

**症状**：按 §3.9 补完依赖声明、`--ci-fidelity` 报了绿之后推上 GitHub，
Actions **第一次跑就红**：

```
9 failed, 626 passed, 3 skipped, 4 errors in 80.30s

FAILED test_pet_market.py::test_install_remote_gif_skin       - FileNotFoundError: [WinError 2]
FAILED test_pet_market.py::test_install_queue_two_then_both_done
FAILED test_pet_market.py::test_uninstall_remote_removes_dir
FAILED test_pet_scan.py::test_scan_pixel_json_goes_live       - assert (0 == 1)
FAILED test_pet_scan.py::test_scan_gif_merges_states          - FileNotFoundError
FAILED test_rvc_worker.py::test_worker_call_falls_back_to_oneshot
       └─ rvc_convert.RvcError: 找不到 RVC 运行环境: D:\RVC\.venv\Scripts\python.exe
FAILED test_rvc_worker.py::test_worker_disabled_uses_oneshot_directly
FAILED test_seedvc.py::test_ft_ckpt_kangaroo_resolves         - kangaroo 微调产物缺失
FAILED test_wechat_record.py::test_find_green_send_hit        - assert (1378 + 480) <= 953
ERROR  test_pet_skin_build.py ×4                              - FileNotFoundError
```

**根因**：13 条红**没有一条是代码缺陷**，全部是"开发机有、runner 没有"的外部资源：

| 资源 | 中招用例 | 为什么报错看不出真因 |
|---|---|---|
| ffmpeg | 9 条（5 failed + 4 errors） | `common.find_ffmpeg()` 找不到时会**回落到字面量 `"ffmpeg"`**（生产代码需要这个兜底，好让 PATH 兜底），于是失败发生在 subprocess 里，只报 `[WinError 2]` |
| `D:\RVC\.venv` | 2 条 | `rvc_convert()` 的人话守卫 `raise RvcError("找不到 RVC 运行环境…")` 看着像生产代码坏了，其实是测试没桩掉 |
| kangaroo 微调产物 | 1 条 | 断言直接写"本机必须存在产物"，干净 runner 上必然红 |
| 开发机屏幕 1938×1609 | 1 条 | `_find_green_send` 会把取域 clamp 到屏幕内，而用例没桩屏幕尺寸 —— 断言里的 `1378 + 480` 其实编码的是**开发机分辨率**；runner 是 1024×768 → `box[0]` 从 1378 变 464 → 拿到 953 |

**为什么 `--ci-fidelity` 没拦住**：它只复刻了**依赖集**这一根轴（§3.9 的产物）。
"本机绿 ≠ CI 绿"其实有**两根轴**，轴②（本机资源）它完全看不见 —— 而且它当时是**绿的**，
这比不跑更危险：它给了一个"已经复刻过 CI 了"的错觉。

**对策**（三层，缺一层都拦不住）：

1. **资源探测集中到一处**：`m2_server/conftest.py` 顶部提供 `ffmpeg_bin` 夹具与
   `missing_local()`，缺资源时 **本机 skip（附安装提示）、CI 上 fail**。非对称是刻意的：
   本机缺 = 你没装，跳过即可；CI 缺 = workflow 的环境准备步骤没生效，
   **不许用 skip 把它掩盖成绿**。测试里别再写 `subprocess.run(["ffmpeg", ...])`。
2. **`--ci-fidelity` 加"裸 runner"模拟**（两层）：
   - `VM_BARE_RUNNER=1` → 探测一律判"不存在"，跳过集与 CI 对齐；
   - **从 PATH 摘掉含 ffmpeg 的目录** → 这层才是关键：第 1 层只约束"走了探测"的用例，
     而上面 9 条正是**绕过探测**直接调 ffmpeg 的写法，本机 PATH 上有它就照样绿。
3. **ffmpeg 在 CI 里真装**（`choco install ffmpeg`）。它是运行时依赖（提轨 / pet 皮肤转换 /
   预览生成），把 9 条用例 skip 掉换个绿色等于**整条 pet 链路在 CI 上没人管**。
   注意此时 `--ci-fidelity` 会跳过这些用例（模拟裸机器）、CI 会真跑它们 ——
   **两个绿灯合起来才是真绿**。

**写这个工具时又踩的两个坑**（都值得记住）：

- 验证"PATH 摘掉后 ffmpeg 就没了"时，我在**同一个进程**里 `subprocess.run(["ffmpeg"])`，
  结果**仍然成功**。因为 Windows `CreateProcess` 的搜索路径取的是**调用方进程**的 PATH，
  而不是你传给子进程的那份 `env`。必须在**剥净环境里再起一层进程**才是真实调用链。
- `shutil.which("ffmpeg")` 返回 `None` **不等于** `subprocess.run(["ffmpeg"])` 会失败：
  前者只看 PATH，后者的 Win32 搜索顺序还包含**应用目录**和**当前目录**。

**证据**：`gh run view 34768644638 --log-failed` 全量清单；
`VM_BARE_RUNNER=1 pytest` 本机 **108 passed + 9 skipped**（无一条崩）；
两层验证脚本实测"裸环境里 `subprocess.run(["ffmpeg"])` → `FileNotFoundError`"；
修复后本机全量 **656 passed**（原来 642 条 = 626 + 9 + 3 + 4）。

**泛化教训**：测试一旦依赖"开发机上的某样东西"，它测的就不再是代码。
凡是外部程序 / 绝对路径 / 屏幕尺寸 / 本机模型产物，要么走统一探测并显式跳过，
要么桩掉 —— **别让它以 `[WinError 2]` 的形式在 CI 上出现**，那种报错没人能一眼看出真因。
反过来，"本机绿 ≠ CI 绿"要按**轴**数：依赖集一根，资源一根，环境本身（镜像、大小写、
并发时序）一根。每发现一根，就得有一条机器对策，否则它会以同样的方式再犯一次。

### 3.11 「审计说历史干净」可能是工具自己判错了 ✅（2026-09-14）

**症状**：`python tools/audit_git_history.py` 报 13 处命中，**每一处**都标着 `[仅历史]`，
处置建议是"先清工作区，历史里的需 `git filter-repo` 重写"。可 `git grep` 一查，
工作区里明明还有 **7 个入库文件**带着第三方素材名 —— 结论与事实不符。

**根因**（四个独立的坑凑在一起，把结论带偏了）：

| # | 坑 | 表现 |
|---|---|---|
| 1 | `_tag()` 拿 `head[path] == blob_sha` 判「HEAD 仍含」 | blob sha 是**整份文件**的哈希：文件被重命名、或同一次提交里顺带改了别的行，sha 就变了 —— 而命中的那个片段可能一个字都没动、还挂在 HEAD 上。误报成 `[仅历史]` 的代价是：把"改工作区就能解决"错判成"只有重写历史能清"，要么白改一遍历史，要么让人以为"改了没用"就不改了 |
| 2 | 规则里**根本没有"第三方素材名"这一类** | 工作区里的片名压根不会被报出，于是"工作区已干净"这个判断缺机器守护；被报出来的那 13 处，命中的其实是 `/Users/<用户名>/` 这类**家目录**规则 |
| 3 | 规则源码**命中它自己** | 把来源标记（B 站站名之类）直接写成完整字符串，规则源码就命中了它自己 —— 历史清干净了这道门还是红的，然后大家学会无视它 |
| 4 | 工具扫的是**已提交**内容，工作区的改动它看不见 | 刚改完就复跑，报告还是旧结论（满屏 `[HEAD 仍含]`），差点据此以为"改了没用" |

**对策**：

1. **判定改成内容层面**：先扫一遍 HEAD 的内容建 `{命中片段: [含它的 HEAD 路径]}` 索引，
   片段在 HEAD 里出现过就是「仍含」（并指出在哪个文件），否则才是「仅历史」。
   片段是内容层面的东西，就用内容层面判 —— blob sha 只是个粗粒度的近似。
2. **第三方素材名单列一节**。具体标题**绝不写进仓库**（哪怕只写进那个防泄漏的工具 ——
   那是泄漏源换了个位置、还更隐蔽）：改从**不入库**的 `.audit-materials.txt` 读，
   一行一个子串，按字面匹配（`re.escape`，不是正则 —— 片名里的 `.` `）` 当正则会静默失配）。
3. **规则里的"机械痕迹"也拼出来**（`"哔哩" + "哔"`），同 `test_check_secrets.py` 里
   `_pv()` 那条纪律。
4. **摘要行拆成两类**：`HEAD 仍含 N 处 → 要动的文件：<文件名列表>` 与
   `仅历史 M 处 → 只有 filter-repo 能清`；工作区有未提交改动时额外打一行提示。
5. `--allow-history-only` 的**非对称**语义：只放行"仅历史 **且** 非凭据"，
   凭据类（任何位置）与「HEAD 仍含」（任何类别）都不接受降级 ——
   能降级的东西必须一眼看得出边界，把凭据也一起降级这道门就废了。

**证据**：`m2_server/tests/test_audit_git_history.py`（25 条）。其中
`test_old_sha_equality_judgement_would_have_misjudged` 把老判据写成反例钉住，
`test_tool_source_is_clean_under_its_own_rules` 钉住坑 3，
`test_allow_history_only_is_asymmetric` 钉住那四条边界。

**泛化教训**：**"扫描工具没报" ≠ "没有问题"**。工具给出 `[仅历史]` 这类结论时，
先手工 `grep` 一个反例再信它 —— 尤其是当它的输出会决定"要不要重写 git 历史"这种
**不可逆**动作时，它的判据本身得先被测试钉住。顺带一条：**工具不能命中它自己**，
否则它永远红、然后被人无视，跟没有一样。

### 3.12 `torch.jit.load` 打不开中文路径：C++ `fopen` 的窄字符坑 ✅（2026-09-14）

**症状**：MeanVC2 冒烟推理第 1 步就崩：

```
[1/5] Loading ASR model (JIT)...
RuntimeError: open file failed because of errno 2 on fopen: No such file or directory,
file path: D:\变声\tts_trial\MeanVC2\preprocess/ckpts/fastu2pp_80ms.pt
```

可 Python 侧 `os.path.exists()`、`os.path.getsize()` 都是 **True**，文件确实在
（Glob、`Get-Item` 都能找到；236MB 整）。

**根因**：同一个路径，Python 的文件 API（`torch.load`、`sf.read` 等）走 **宽字符** API，
`D:\变声` 毫无压力；而 `torch.jit.load` 底层是 C++ 的
`import_ir_module` → **窄字符 `fopen`**，非 ASCII 路径直接 `errno 2`。
所以这不是文件缺失，是"**PyTorch 的 JIT 序列化层在 Windows 上不吃中文路径**"。

**对策**：统一走一个 fallback 包装，失败时把权重复制到英文临时目录再 `jit.load`：

```python
def _jit_load_cn(ckpt_path, device):
    try:
        return torch.jit.load(ckpt_path, map_location=device)
    except (OSError, RuntimeError):
        if not os.path.exists(ckpt_path):
            raise                        # 真缺失就别吞错
        tmpdir = tempfile.mkdtemp(prefix="meanvc2_jit_")
        tmp_ckpt = os.path.join(tmpdir, os.path.basename(ckpt_path))
        try:
            shutil.copyfile(ckpt_path, tmp_ckpt)
            return torch.jit.load(tmp_ckpt, map_location=device)
        finally:
            shutil.rmtree(tmpdir, ignore_errors=True)
```

已落在 `tts_trial/MeanVC2/src/infer/infer_e2e.py`（ASR + Vocos 两处 JIT 加载都走它）。
该第三方仓库**不入库**（`.gitignore` 加 `tts_trial/MeanVC2/`，同 Qwen3-TTS / seed_vc 惯例），
补丁只在本机。

**证据**：对照实验 —— 同一 `fastu2pp_80ms.pt`，中文路径 `jit.load` 抛 `RuntimeError`；
复制到 `C:\Users\<你的用户名>\AppData\Local\Temp\` 后加载成功。补丁后完整推理冒烟通过
（BN (86,256)、SpkEmb (256,)，1 步 VC 出 3.4s 音频，`smoke_out.wav`）。

**可信度**：`✅本机实测`（torch 2.8.0+cu129 / Windows 11）。±：`torch.load` 走 Python
IO 层，不在本坑范围内 —— 只有 JIT 序列化（`torch.jit.load`）和原生库直读受影响。

### 3.13 本项目 x-vector 的 SECS 量程塌缩：单看相似度必误判 ✅（2026-09-14）

**症状**：做 MeanVC2 vs RVC 客观对比时，用项目自己的
`POST /emb`（`m2_server/qwen3_tts_service.py` 的 Qwen3-TTS x-vector）算 SECS，
结果"没转换的源音频"拿到 **0.964**，转换后的 MeanVC2 反而是 **0.954–0.960** ——
看起来"越转换越不像"，纯属荒谬。

**根因**：这个说话人向量的**余弦相似度量程被压缩**了。本轮实测动态范围只有约
**0.04**（底噪 0.964 → 参考音 1.000），而正常 ECAPA/x-vector 在同一说话人 vs
不同说话人之间通常拉开 0.2–0.5。量程一旦塌缩：
- 区分度低于数值噪声，排序基本随机；
- "未转换底噪"本身就很高，任何转换都难"跑赢"它。

**对策**：**判音色相似度必须配谱包络指标**，本项目用 **LTAS**（Long-Time Average
Spectrum，长时平均对数谱）互相关 —— 它对"是否朝目标音色的频谱包络靠拢"直接敏感，
且与具体模型无关。再加 **F0 统计**（YIN 中位 + 浊音比）看音高迁移是否到位。

本轮同一批音频的三方对照（同源同目标同条件）：

| 音频 | SECS | LTAS | F0中位 |
|---|---|---|---|
| 源音 未转换 | 0.964 | 0.866 | 125.0 |
| RVC kangaroo_v2 | 0.981 | **0.958** | 112.1 |
| MeanVC2 120ms | 0.954 | 0.936 | 119.2 |

→ LTAS 排序（RVC 0.958 > MeanVC2 0.936 > 未转换 0.866）**才是真相**；
SECS 排序（未转换 0.964 > MeanVC2 0.954）是假象。
F0 也在讲同一个故事：RVC 把 125→112 拉向目标，MeanVC2 只动 ~6Hz。

**推论（可复用）**：以后任何"音色像不像"的客观评测，**必须至少两轴**
（谱包络 + 音高），且**先跑一遍"未转换"做底噪基线** —— 底噪离 1.000 太近
（<0.05）就说明这个 embedding 在本任务上不可用作唯一判据。

**可信度**：`✅本机实测`（2026-09-14，`D:\meanvc2_exp\ab_metrics2.py`）。
±：量程塌缩是本项目 **Qwen3-TTS x-vector** 的特性，不代表 ECAPA 等标准 x-vector
也如此；换 embedding 前先重测底噪。

### 3.14 JIT 模型搬到别的设备会崩：trace 时冻结的常量不跟着 `map_location` 走 ✅（2026-09-14）

**症状**：把 MeanVC2 的 Fast-U2++ ASR 从 CPU 挪到 CUDA（`torch.jit.load(ckpt, map_location="cuda")`
+ 把输入/cache 一起 `.to("cuda")`，看起来该搬的都搬了），前向直接炸：

```
RuntimeError: The following operation failed in the TorchScript interpreter.
...
  p = torch.view((linear_pos).forward1(argument_3, ), ...)
RuntimeError: Expected all tensors to be on the same device,
but got mat2 is on cuda:0, different from other tensors on cpu
```

诡异点：报的是 **weight 在 cuda、input 在 cpu**，可我明明把 input 搬过去了。

**根因**：`map_location` 只负责搬 **注册的 `parameter` / `buffer`**。而 trace 时如果某个张量
被当成**常量冻结进图**（典型是位置编码、正弦表、`torch.zeros` 预建的 cache 之类的中间量），
它就**不随 `map_location` 搬家**，永远停在 trace 时的设备上。
于是权重到了 CUDA、那个常量还赖在 CPU → 设备不匹配。

**一眼识别**：看 torch 给的 "TorchScript, original code" 路径里的**环境名**：

```
D:\miniconda\envs\meanvc_cpu\Lib\site-packages\...   ← CPU-only 环境 trace 的，别想上卡
/home/xxx/miniconda3/envs/allin/...                  ← Linux 环境 trace 的
```

路径里出现 `cpu` / `allin` 这类痕迹，基本就可以判定**该 JIT 产物锁死在 trace 环境**，
不是改几行 `.to()` 能解决的。本项目 Vocos 也是 Linux 环境 trace 的，但它恰好**没有**被冻结的
常量张量，所以能上 CUDA —— **所以不能只看 trace 环境就一刀切，要实跑验证**。

**对策**：

1. **优先保持原设备**。MeanVC2 官方把 ASR 写死 `"cpu"` 就是这个原因，而它 CPU 上
   warm RTF 仅 0.062，本来就不是瓶颈。
2. 确实要跨设备，只有两条路：**重新 trace/导出**（需要原始训练代码），或
   **在 JIT 里定位并显式注册那些常量**（把常量改成 `register_buffer` 再重导出）。
3. **别浪费时间调 `.to()`** —— 症状会一直复现，而且报错位置（哪个算子）每次都不同，很误导。

**顺带**：同一轮里 `vocos.decode() on cuda` 也报过一次设备错误，但那次是**我自己的脚本 bug**
（CPU 轮次把 CPU 上的 mel 喂给了加载在 CUDA 的 vocos）。**跨设备基准脚本必须给每个 device
各加载一份模型**，别复用同实例。

**可信度**：`✅本机实测`（torch 2.8.0+cu129 / RTX 5060 / Windows 11）。
±：这是 TorchScript trace 的固有语义，不限 MeanVC2；ONNX / TensorRT 的导出有类似性质的
"常量烘进图"问题。

### 3.15 性能/资源测量的四个陷阱（本轮连踩，全是"数字看起来对但其实错"）✅（2026-09-14）

做 CPU/显存/RAM 三轴资源账时，**连续四次拿到假数字**。整理成通用清单：

**① 平均值被冷启动污染（与测 JIT 模型同源）**

RVC 稳态单次转换 0.27s，但首轮 **19.6–20.9s**（pipeline 构建 / CUDA 图捕获）。
10 次取平均得 2.42s，"看起来像是 9 倍退化"，实际是第 1 次把平均值拉飞了。
**对策**：先跑 2 次 discard 再统计；**任何"每次调用"的基准，先确认首轮是否含一次性初始化**。

**② 子进程 CPU 时间必须统计「进程树」，否则会得出物理上不可能的结论**

第一版只量 worker 进程，得出「等效 14.41 核」——而该进程只有 **1 个线程**，
单进程不可能用 14 核。真相：worker 是个 1 线程转发壳，真正推理在
**119 线程的子进程**里。**对策**：`psutil.Process.children(recursive=True)` 一并累加；
**结论违反物理上限（核数 > 线程数）时，一定是测量对象错了，不是机器神奇。**

**③ RAM 要区分「加载瞬时峰值」与「稳态驻留」**

MeanVC2 加载时 RSS 峰值 **3617MB**，稳态只有 **2285MB**（差 1.3GB）。
差额来自 WavLM-Large 的 1.2GB checkpoint 字典 + 模型实例的临时副本。
**报峰值会把成本夸大 58%**。**对策**：稳态要在"全部加载完 + 跑过一轮推理"之后取，
且至少稳定采样 3 轮。另外**进程内读 RSS 别手搓 ctypes 结构**（`PROCESS_MEMORY_COUNTERS`
对齐/字段易错，本轮得到 0MB 和 6MB 两个假值）——**用父进程 psutil 轮询子进程最可靠**。

**④ 别手写复刻上游的推理函数**

为了"逐块计时"自己复刻了一份 `vc_inference`，结果在
`apply_rotary_pos_emb` 报 `size of tensor a (28) must match b (16)` ——
kv_cache 的 `offset` / 切片语义抄错了。**对策**：计时就用 `time.perf_counter()`
包住上游原函数；真要逐块计时，改上游加钩子也不要重写。
**"为了测量而重写被测对象"是本末倒置，测出来的也不代表原件。**

**可信度**：`✅本机实测`（2026-09-14，`D:\meanvc2_exp` 下的 `rt_bench*.py` /
`rvc_cpu_cost*.py` / `mem_probe*.py`）。

### 3.15b Node 测试写了、看着也"能跑"，但从来没在自检里跑过 ✅（2026-09-14）
<!-- 编号修正 2026-09-17：本节原也写成 3.15，与上一节重号；改为 3.15b 以免后续编号整体位移。 -->

**症状**：`tools/` 下 4 个 `test-*.cjs`（`test-model-setup` / `test-setup-ipc` /
`test-updater` / `test-update-hook`）只靠人工敲 `node tools/test-xxx.cjs`，
`tools/check.py` 里没有任何一步会执行它们，CI 更不会。于是 `test-setup-ipc.cjs`
里 **3 条用例长期红着**，一直没人知道 —— 直到本轮改动了它依赖的
`runFirstRunGuide` 才暴露。

**根因**：这些脚本开头写的是
`require.resolve("electron", { paths: [webRoot] })`，**要求 `web/node_modules`
真实存在**。而 CI 的 backend job（windows-latest）**从不 `npm install`**，
所以就算把它们接进 `check.py`，在 CI 上也会 `MODULE_NOT_FOUND` 直接挂。
**"跑不了"和"没跑"互相掩护**：因为跑不了，所以没人接；因为没人接，所以没人发现跑不了。

**对策**：抽 `tools/electron-stub.cjs`，用 `Module._resolveFilename` 把
`require("electron")` 重定向到一个**不落盘的合成 id**，彻底不依赖 `web/node_modules`：

```js
const STUB_ID = "__vm_electron_stub__";
const orig = Module._resolveFilename;
Module._resolveFilename = function (request, ...rest) {
  if (request === "electron") return STUB_ID;   // 返回合成 id，不查磁盘
  return orig.call(this, request, ...rest);
};
require.cache[STUB_ID] = { id: STUB_ID, filename: STUB_ID, loaded: true, exports: stub };
```

（关键点：`_resolveFilename` 的返回值**不需要是个真实路径**，只要 `require.cache`
里有同 key 的条目即可命中缓存。写 `<stub>.cjs` 临时文件反而会污染仓库。）

然后在 `tools/check.py` 加 `nodetest` 步：glob `tools/test-*.cjs` 逐个 `node` 执行。
注意 `test-check-require.cjs` / `test-electron-load.cjs` **由别的步骤负责，
必须从 glob 里排除**，否则重复跑。

**证据**：接入后 `nodetest` = 7 个脚本全绿；`test-setup-ipc.cjs` 27 条通过
（改前 14 通过 / 3 失败，那 3 条从未被任何入口判定过）。
**可信度**：`✅本机实测`。
**推论（通用）**：**"测试文件存在" ≠ "测试在跑"**。新增测试文件时，
必须同时确认它被某个自动化入口 glob 到 —— 否则它只是一份文档。

#### 3.15 后续：接进门禁 ≠ 门禁就绿 —— "本机绿 ≠ CI 绿"的**第三根轴** ✅（2026-09-14 同日）

把 `nodetest` 接进 `check.py` 后本机七步全绿、`--ci-fidelity` 也绿，
**CI 却当场红**：`[FAIL] nodetest 2/7 个失败：test-model-scan.cjs, smoke-loadpath.cjs`

```bash
mv web/node_modules web/__nm_hidden_ci_sim__ ; \
```

（同一分区内的 `mv` 是 O(1) 改名，不动数据；用 `;` 而非 `&&` 保证一定还原。

**证据**：挪走 `web/node_modules` 后 6 个脚本全 OK；静态守卫对 7 个入口脚本零误报，
对 `require("electron")` / `require.resolve("electron")` 合成反例命中、对纯注释不命中。
**可信度**：`✅本机实测`（含 CI run `34855104217` 的真实红）。

### 3.17 "变声器不被反作弊封号" ≠ "本项目安全"：把舆论结论套到自己头上 ✅（2026-09-14）

**问法**：用户问"游戏里用变声器会不会被反作弊搞"。网上搜到的结论清一色是
"没事，变声器不封号"。

**坑**：这个结论**对"用户态变声器"成立，对本项目不成立**——而舆论几乎
不区分这两者（写博客的是卖软件的人，他们的产品恰好都是用户态的）。

**拆开看，这是两个完全独立的问题**：

| 问题 | 结局 | 判据 |
|---|---|---|
| **会不会被封号** | ❌ 不会 | 只有**注入游戏进程 / 改内存 / 给竞技优势**才封 |
| **会不会被拒绝启动** | ⚠️ 可能（VAN148） | 装了反作弊**不信任的内核驱动（.sys）** |

**根因**：反作弊（如 Vanguard）是**内核级**的，它扫的是内核驱动加载、
游戏内存完整性。**"变声器不被封号"的真正理由是"用户态软件碰不到内核"**——
可本项目末端用的 **VB-CABLE 恰好是内核驱动**（要当虚拟麦克风就必须是）。
所以本项目落在**第二个问题（启动）的风险面**上，而不是第一个（封号）的安全面。

**证据**：
- Riot 官方支持页（`support.riotgames.com/.../error-van-incompatible-software`）：
  "VAN: Incompatible Software" = 检测到不兼容的 `.sys`，**阻止启动**、弹窗直接列出文件名。
- 官方/社区公布的常见被点名文件（`ene.sys`/`rtcore64.sys`/`inpoutx64.sys`/`AsIO.sys`…）
  **全是 RGB / 超频 / 监控 / 主板工具，无一为音频驱动**。
- 厂商博客（`voxbooster`，**有立场**）承认 VB-CABLE 的内核驱动**曾被 Vanguard 1.x 标记**，
  导致无法启动，**后续 Vanguard 更新已修复**。
- 结论定级：✅ 一手（机制 = 启动拦截、非封号）；⚠️ 二手（VB-CABLE 曾被标记）；
  ❓ 未证实（当前版本共存性）。
**可信度**：机制 `✅一手（Riot 官方）`；VB-CABLE 具体指控 `📚二手/利益相关`；
当前版本共存 `❓未验证`。

**对策（写进 `docs/犯错档案-微信.md` §2.4 的四条）**：

1. **换 VC 模型不解决这个问题**——暴露点是 VB-CABLE，不是 RVC / MeanVC2。
2. **风险等级 = 可逆**（开不了游戏 → 卸 CABLE → 恢复），**与账号无关**。
3. 真要上 PC 游戏场景，**在一台装了目标游戏的机器上实测一次"装 CABLE 后能否启动"**
   即可（10 分钟），不必提前决策。
4. 备选：Voicemeeter（同为内核驱动，同一风险面）、外接 USB 声卡物理环路、
   或**只在不开反作弊游戏时启用 CABLE**。

**推论（通用）**：**引用"某类工具安全"的结论前，先确认自己的实现落在同一类里。**
"用户态安全"这个前提，一个内核态依赖就打破了——而项目往往把这依赖当基础设施，
不会主动想起来它也是"驱动"。

### 3.18 同一文件并行两处编辑，其中一处会静默丢失 ✅（2026-09-14）

**现象**：给 `scripts/release.ps1` 加 `-SkipSign` 开关，一条消息里发了两处编辑
（文件头用法注释 + `param()` 里加 `[switch]$SkipSign`）。**两处都返回"编辑成功"。**
提交后跑脚本，`-SkipSign` 完全没效果，仍旧走签名分支。

**根因**：两处编辑**各自读了一份原文件、各自整体写回** —— 后写的覆盖先写的。
注释那处生效了，`param()` 那处丢了。声明没了 → `$SkipSign` 成了未定义变量 →
`if ($SkipSign)` 恒为 `$null`（假）→ **静默走 else 分支**。

**为什么特别难发现**：

- 工具报"成功"（它确实写成功了，只是写的是旧快照）。
- 语法完全合法：PS 不要求变量先声明，`ps1lint` 全绿、token 数也对得上。
- 脚本**照常运行**，只是走了错分支 —— 无报错、无警告。

**发现方式**：改完用 `(Get-Command <脚本>).Parameters.Keys` 列出脚本**实际声明**的参数，
才看到 `SkipSign` 不在里面。（`grep '\[switch\]'` 等效。）

**对策**：

1. **同一文件的多处修改串行发**，不要放在一条消息里并行。
2. 改完要验证"**确实改了**"，而不是"工具说改了" —— 参数看声明列表，逻辑看 grep 命中。
3. **"声明 + 使用分离"的结构是静默失败高发区**：声明漏了，使用处只变成 `$null`
   （PS）/ `undefined`（JS），一路无痛跑到底。

**推论（通用）**：任何"匹配 old_string 再整文件写回"的编辑，都在一个读-写窗口里工作；
同文件并行编辑 = 竞态。这类竞态**不报错，只丢改动** —— 而且丢的往往是"声明"、
留下的往往是"使用"，组合起来正好是一个能跑但行为不对的程序。

### 3.19 读/建 Windows 快捷方式：COM 被拦 + `.lnk` 双编码假象 ✅（2026-09-15）

**现象**：要确认桌面「变声工坊」快捷方式指向哪份安装，用官方姿势读：

```powershell

```

被安全策略直接拦：*"COM object instantiation can run arbitrary code"*。

**备选路线也全废**（都是"看起来能绕、实际绕不过"）：

|---|---|
| 符号链接 | 需要管理员权限 |
| 硬链接 | 需要同盘（目标在 C:，构建产物在 D:） |
| `Start-Process` 拉起 | 只能启动，改不了已有 `.lnk` |

**第二个坑（更隐蔽）**：退而求其次去 grep `.lnk` 的字节找路径，得到的是**假象**：

```
C:\Users\<user>\AppData\Local\Programs\voice-morph-desktop\
.exe                      ← 看起来像"目标缺文件名"
```

真实目标是 `...\voice-morph-desktop\变声工坊.exe`。**根因**：`.lnk` 里
`LinkInfo.LocalBasePath` 用**系统 ANSI 代码页**存（简中 = GBK），
`变声工坊.exe` 的 GBK 字节是 `B1E4 C9F9 B9A4 B7BB 2E657865` ——
只有尾部 `.exe` 落在可打印 ASCII 区，中文名部分对 `[\x20-\x7e]` 完全不可见。
**grep 出来的"目录 + .exe"不是截断，是编码盲区。**

**第三个坑**：**不能把整个 `.lnk` 当单一编码解码**。同一个目标路径在文件里
**同时存在两份**：ANSI 的 `LocalBasePath`（`LinkInfo` 段）和 UTF-16 的
`LinkTargetIDList`。按 UTF-16 整体解会得到一堆乱码汉字，按 ASCII 整体解会漏掉中文名。

**对策**：

1. **读**：按 [MS-SHLLINK](https://learn.microsoft.com/openspecs/windows_protocols/ms-shllink/)
   结构解析字节，只读、无副作用、不需要权限。已落地为
   `tools/check-shortcuts.py`（`python tools/check-shortcuts.py`，退出码 0/1 可直接进自检）：
   读 Header 的 `LinkFlags` → 按 `HasLinkTargetIDList` 跳 IDList → 取
   `LinkInfo.LocalBasePath`（`bytes.decode("mbcs")`）+ `CommonPathSuffix`。
2. **建**：既然建不了 `.lnk`，就别建。**用新版安装器覆盖安装** ——
   安装器会自己重建正确的快捷方式，顺带修好注册表版本号与已安装代码，
   一次动作解决"快捷方式指错 + 已安装版本过期"两件事。
   覆盖安装前必须确认 `deleteAppDataOnUninstall: false`（本项目已是），
   否则 `%APPDATA%\<app>` 里的 `config.json` / `pet.json` 会被清掉。
   静默参数 `/S`，退出码 0 **不等于装完**（NSIS 会先返回、子进程继续），
   必须**回读产物指纹**验证，别信退出码。

**推论（通用）**：**"读不出来"时先怀疑编码，再怀疑权限。** 混合编码容器
（`.lnk` / Windows 注册表 `REG_EXPAND_SZ` / Office 二进制格式）里，
"按单一编码 grep"得到的干净结果，往往正是最误导人的那种结果 ——
它不会报错，只会让你看到一个**语法合法、语义错误**的值。

### 3.20 全量跑才偶发红的测试：后台线程 + 真 ffmpeg + 硬 deadline ✅现象 / ✅根因（2026-09-16 现象，09-18 定根因）

**现象**：给 `m2_server` 加了一个新测试文件（18 条，纯协议层、不载模型）后，
全量跑出现**随机的 2 条红**，且**每次红的用例不一样**：

| 轮次 | 结果 |
|---|---|
| 第 1 轮 | `test_pet_market.py::test_install_remote_gif_skin` |
| 第 2 轮 | `test_pet_market.py::test_install_remote_gif_skin` + `test_pet_scan.py::test_scan_pixel_json_goes_live` |
| 第 3–5 轮 | **824 passed 全绿**（连续三次） |

失败的永远是 **pet（桌宠）** 那两个，与本次改动（TTS API / 首页文案）零关系。

**定位过程（哪一步有效、哪一步是白费）**：

| 做法 | 结论 |
|---|---|
| 单跑那条用例 | ✅ 绿 |
| 两条一起跑 | ✅ 绿 |
| 「我的新文件 + pet 文件」按序跑（怀疑字母序邻接：`test_openai_compat` 正好排在 `test_pet_*` 前） | ✅ 绿 —— **邻接假设被否定** |
| 全量**排除**我的新文件（806 条） | ✅ 绿 |
| 全量**含**我的新文件，连跑 | 2 红 / 3 绿 —— **不是确定性失败，是负载相关的偶发** |

**根因（❓未验证 —— 没抓到失败断言原文）**：两条用例的共性结构可疑：

```python
# test_pet_scan.py:96
def _wait_status(pred, deadline=30.0, interval=0.05):   # ← 30 秒硬超时
    ...
    raise AssertionError(f"等待超时, 当前状态: {pet_scan.progress_scan()}")
```

两条都**在后台 worker 线程里调真 ffmpeg**（gif→webp strip / pixel JSON 试转），
然后按 deadline 轮询状态。全量跑到第 800 条时机器已有大量 ffmpeg 子进程与线程，
**30 秒可能不够**。旁证：同在 `test_pet_market.py` 里的兄弟用例用的是 **60 秒**
（`deadline = time.time() + 60`），两边不一致 —— 像是随手写的值。

> 当时之所以标 ❓：**没有抓到失败时的断言原文**（只看到 `- Ass...` 被截断）。
> 09-18 补齐了 —— 见本节的「已定根因」，**结论是两种形态并存**：当年的
> "deadline 不够"假设只对了一半（形态 B），还有一半是进程根本创建不出来（形态 A）。

**对策**：

1. **判定 flaky 的标准动作（本次有效）**：单跑绿 + 全量偶发 + 失败用例每次不同 →
   基本可判环境/时序，而非逻辑缺陷。**别急着改产品代码去"修"它。**
2. **别只跑一次全量就下结论**。本次 2 红 3 绿，只跑一轮会得出完全相反的结论
   （第 2 轮红 → 以为代码坏了；第 5 轮绿 → 以为修好了）。**连跑 2~3 轮**才算数。
3. **排他法定责**：全量 `--ignore=<新文件>` 跑一次。绿 → 差异只可能来自新文件或其负载；
   但仍需注意"负载相关"时它并不构成因果，只能说明**相关**。
4. **待办**：把 `_wait_status` 的 deadline 与兄弟用例对齐（30 → 60s），
   并在失败消息里带上已等待秒数 —— 否则下次红还是只能猜。

**✅ 已定根因（2026-09-18 补）**：这一族红有**两种形态**，都是环境，都不是代码。

| 形态 | 失败时的状态 | 触发条件 |
|---|---|---|
| A. 进程创建失败 | `status: 'failed'`（且 **message 为空**） | commit 峰值逼近上限，`CreateProcess` 报 `WinError 1450/1455` |
| B. 机器整体变慢 | `status: 'installing'` / `'queued'`（**根本没走到完成**） | 负载高 → 用例自带的硬 deadline 不够（即上面那版假设，**它是对的，只是不唯一**） |

**怎么区分**：看失败断言里的 `status`。`failed` = 形态 A；`installing/queued` = 形态 B。
两种都不能靠改业务代码修 —— A 要腾空间 / 调大页面文件，B 是"这台机器此刻跑不动"。

**形态 A 的原文证据**（`--tb=long` 落盘后 grep）：

```
assert done["status"] == "done", done
E  AssertionError: {'skin_id': 'pixel-cat', 'status': 'failed', 'phase': '失败', ...}
...
try:
>   hp, ht, pid, tid = _winapi.CreateProcess(...)
E   OSError: [WinError 1455] 页面文件太小，无法完成操作。
```

另一轮抓到的是兄弟错误码 `[WinError 1450] 系统资源不足，无法完成请求的服务`。

**形态 B 的原文证据**（同日稍后一轮，同样是这两条用例）：

```
E       AssertionError: {'skin_id': 'pixel-cat', 'status': 'installing', ...}
E       assert 'installing' == 'done'
E       AssertionError: {'pixel-cat': 'queued', 'pixel-capybara': 'queued'}
E       assert 'queued' in ('downloading', 'installing')
```

**一个便宜的机器状态探针：同一次全量的总耗时。** 正常 **~2m30s**；
出现形态 B 的那一轮是 **7m07s**（≈3×）。耗时异常拉长本身就是"这轮结果别当真"的信号，
比逐条读断言快得多。

**机制**：`test_pet_market` 的安装用例在后台 worker 里 `subprocess` 拉起 ffmpeg
做 gif→webp。全量跑到第 800+ 条时系统 commit 已接近上限（本机 C 盘长期 ~96% 满、
页面文件很小），于是要么 `CreateProcess` 直接失败（形态 A），要么每个子进程都慢一截
把 deadline 拖爆（形态 B）。

**推论**：
1. **排他法依然是最有效的定责手段**：全量 `--ignore=<本次新增/改动的测试文件>`
   跑一次，同一用例照样红 → 与本次改动无关（本次两轮都验过）。
2. 见到这两条：先 grep `WinError 145`；没命中且 `status` 是 `installing/queued` → 形态 B。
   **别去改业务代码"修"它。**
3. `test_pet_market` 把子进程异常吞成空 message 上报，**诊断性很弱** ——
   待办：worker 里把异常串写进 `message`，否则每次都要翻 subprocess 栈才知道是环境。

### 3.21 一句 TDZ 崩掉整个渲染器脚本：桌宠只剩一圈「透明玻璃球」 ✅本机实测（2026-09-17）

**现象**（用户原话）：「我的桌面人偶变成这样了 —— 为什么是透明的有这种颜色，
而且鼠标移在上面，像一个手掌一样，是你可以抓取的。这肯定是颜色不知道哪里有问题。」

截图实测：只有一个极淡的圆环 + 底部一点蓝灰渐变，**全图最暗像素 rgb(205,214,224)、
最大饱和度仅 20**（正常渲染的芙宁娜含大量深色描边，最暗接近纯黑）。

**根因**：不是颜色问题，是**脚本根本没跑**。

`web/electron/pet/pet.html` 里，2026-09-10 `b91707b`（动态皮肤）把

```js
applySkin();                                   // ← 调用在这里（第 377 行）
const BUBBLE = { ... };
...
const petBox  = document.getElementById("pet");
const sprite  = document.getElementById("sprite");   // ← 声明在这里（第 394 行）
```

`applySkin()` 内部要写 `sprite.style.setProperty(...)`，而 `sprite` 是**下方才声明的
顶层 `const`** → 暂时性死区（TDZ）→ 第一句就抛
`ReferenceError: Cannot access 'sprite' before initialization` → **整个内联脚本中断**。

脚本一断，后面所有事都没发生：

| 没发生的事 | 用户看到的现象 |
|---|---|
| `setSprite()` 从未执行 → 精灵图没有 `background-image` | 只剩 CSS `#pet::before` 那圈 `radial-gradient` 光晕 + `inset` 边框 =「透明玻璃球」 |
| 末尾 `window.pet.setIgnoreMouse(true)`（初始全窗穿透）从未执行 | 整个 220×480 透明窗一直吃鼠标、挡住底下窗口；光标停在 `#pet` 的 `cursor: grab` 上 =「像手掌，能抓取」 |
| 状态轮询 / 气泡 / 悬停快捷面板 / 拖拽 全部失效 | 桌宠完全没反应 |

**关键点：`cursor: grab` 是设计如此**（拖拽由 JS+IPC 手动实现），
它只是**最后一个还能生效的东西**——因为它是 CSS，不依赖 JS。用户把它当成症状，
其实是"病灶已经蔓延到只剩 CSS 还活着"的证据。

**为什么静态看代码看不出来**：`applySkin` 的定义在调用点之前（函数声明会提升），
看起来完全正常；坏的是**调用时机**相对 `const` 声明的先后。
这类顺序错误 ESLint 默认也不报（`no-use-before-define` 需显式开，且对函数内引用
不一定覆盖）。

**对策**：

1. **修**：把 `applySkin();` 挪到「DOM 引用」段（`petBox`/`sprite` 声明）之后，
   并在函数注释里写明"必须在 DOM 引用段之后调用"。
2. **补测（关键）**：`tools/test-pet-renderer-script.cjs` —— 喂一套最小 DOM 桩，
   `eval` **真实内联脚本**，捕获任何顶层异常；并断言 `sprite` 拿到了
   `background-image`/`--fw`/`--fh`、`#pet` 拿到了 `--dw`/`--dh`、
   初始穿透已下发。`tools/test-*.cjs` 被 `check.py` 的 nodetest 步 glob 自动收网。
3. **反向对照**：该测试支持传入 pet.html 路径。拿 `b91707b` 的旧版本跑 →
   **8/8 全红**；拿 `b91707b^`（用户一直看着正常的版本）跑 →
   渲染相关的 3 条断言全绿（`background-size: 5550px 150px` / `svg/idle.webp` 与修复版一致）。
   这证明"修好了"不是靠肉眼，而是与已知可用版本**参数等价**。
4. **顺带修的同类坑**：`--dw/--dh` 原写在 `sprite` 上，而 `var(--dw)` 的消费方是
   **父元素 `#pet`** —— 自定义属性不向上继承，`#pet` 永远退回硬编码 150px。
   内置皮肤恰好也是 150 所以看不出来，一旦换非 150 帧尺寸的皮肤，
   `::before` 光晕就会比角色小一圈。现在改写到 `petBox` 上。

**证据**（本机实测）：

| 命令 | 结果 |
|---|---|
| `node tools/test-pet-renderer-script.cjs` | **8 通过, 0 失败** |
| 同上，传 `b91707b:web/electron/pet/pet.html` | **0 通过, 8 失败**（含 `ReferenceError: Cannot access 'sprite' before initialization @ pet.html:349`） |
| 同上，传 `b91707b^:web/electron/pet/pet.html` | 渲染相关 3 条绿（与修复版参数一致） |
| `python tools/check.py --only nodetest` | 10 个脚本全绿 |

**推论（通用）**：**"样式/颜色看起来不对"要先问"脚本跑完了吗"。**
一个 `const` 顺序错误能让整个 `<script>` 静默死掉，而**残留的 CSS 会继续渲染**，
于是症状表现得像"样式 bug"。排查顺序应当是：
先看渲染进程 console 有没有异常 → 再查 DOM 上的内联样式有没有被写进去 →
最后才怀疑 CSS 本身。本次正是"CSS 是好的、JS 死了"，只看 CSS 会查反方向。

> **⚠️ 修完不等于用户看到修完**：`web/electron/**` 不在后端自动镜像
> （`backend_autosync.py` 只镜像 `m2_server`/`tools`/`web/dist`），
> 而安装版 `pet.cjs` 的 `PET_DIR` 只认 `resources/backend/web/electron/pet`
> 或 app.asar 内置副本 —— 改完必须重打包（`npm run electron:build`），
> 或临时把修好的 pet 目录放到 `resources/backend/web/electron/pet/` 热替。

### 3.22 无 GUI 时怎么"看见"UI：headless Chromium 出图 + 量测，别让用户当我的眼睛 ✅本机实测（2026-09-17）

**背景**：桌宠改版要验收 `web/electron/pet/pet.html` 的视觉效果，但 Electron GUI
在本机沙箱里起不来（Chromium GPU 进程必崩，`web/electron/smoke-pet-render.cjs`
文件头已记这条）。前一轮的做法是"改完热替、让用户重启截图给我看"——**把验收成本
转嫁给了用户，而且一轮只能验一个状态**。

**做法**：Playwright 缓存里的 `chromium-headless-shell` 就是标准 Chromium，
支持 `--screenshot`，可以离线渲染任意本地 HTML：

```bash
# 缓存位置（本机）：C:\Users\<用户>\AppData\Local\ms-playwright\chromium_headless_shell-*\chrome-headless-shell-win64\
chrome-headless-shell.exe --no-sandbox --disable-gpu --hide-scrollbars \
  --allow-file-access-from-files --force-device-scale-factor=2 \
  --window-size=220,480 --virtual-time-budget=6000 \
  --screenshot=out.png "file:///D:/.../pet.html"
```

落地产物：`tools/pet-panel-preview.cjs`（`--measure` 出数字，默认出图）。
它把 pet.html 复制到临时目录、在主脚本前后注入「假 preload 桥 + 假后端 + 展开面板」，
一次跑完 7 个场景（待机/亮色/离线/变声中/处理中/导览/忙态）。

**连踩的五个坑**（每一个都会让"看起来出图了"变成"图是假的"）：

| # | 坑 | 症状 | 对策 |
|---|---|---|---|
| a | `fs.cpSync` 拷 2.5MB 精灵图 | **node 进程直接消失**：无异常、无输出、exit 127（沙箱拦截，不是 ENOENT） | 一个字节都不拷：注入 `<base href="file:///…/pet/">`，让相对路径 `svg/*.webp` 直接解析回源目录 |
| b | headless 的 `prefers-color-scheme` **恒为 light** | `ok-dark` 与 `ok-light` 量出的数字**一模一样**（`--c-surface: 255 255 255`），暗色主题其实从没被渲染过 | `--force-dark-mode` / `--force-prefers-color-scheme=dark` 均无效 → 确定性地把 `@media (prefers-color-scheme: light)` 块从样式里**摘掉**，剩下的 `:root` 暗色令牌即唯一生效 |
| c | 截图/量测撞在入场动画中途 | `panel` 量到 **197.9** 而不是 204（204 × `scale(.97)` = 197.88），出图发虚 | 先注入 `*{animation:none!important;transition:none!important}` 冻结动画再量；想看动效再加 `--anim` |
| d | 普通浏览器里 `id="pet"` 让 `window.pet` 变成那个 `<div>`（具名元素访问） | `window.pet && window.pet.setIgnoreMouse(true)` **真值判断通过、调用抛 TypeError** → 脚本中断 → 精灵图不渲染、气泡不出现、药丸停在初始值，出图是一张"坏掉"的图 | 预览台**必须先模拟 preload 桥**（`window.pet = {…全 no-op…}`）。线上 Electron 里 `contextBridge` 先定义 `window.pet`，所以不受影响 |
| e | 只看图、不看数字 | "按钮文字好像被切了"只能靠肉眼猜 | 让页面把 `getBoundingClientRect` / `scrollWidth` / `clientWidth` / `rootScrollHeight` 打 console，`--enable-logging=stderr` 带出来。**⚠️ 但 `scrollWidth > clientWidth` 对带 `overflow:hidden` 的元素不可信，别照抄 —— 见 §3.26** |

**量测抓到的东西**（肉眼都看不出来）：主按钮「合成并发送」+图标实测需 69px 只分到 65px
（`flex: 1.35` 改成 `1.7` 修掉）；「变声中」时变声按钮需 50px 只分到 48px（去掉图标修掉）；
`panel` 宽度正好用满 204px 预算；`#root` 滚动高度恒 480（无纵向溢出）；
`petTop` 恒 320（面板向上生长，不推挤角色）。

**推论（通用）**：**"我改完了，你重启看看"不是验收，是转移成本。**
只要目标产物是「单端口/单文件、可离线渲染」的东西（HTML 面板、报表、图表），
就应该先想办法在本地把它渲染成像素、把布局量成数字，再交付。
这比让用户反复重启截图快一个数量级，而且**能一次覆盖多个状态**——
用户手动验一轮只能看到一个状态，脚本一轮能出七张。

### 3.23 「我写的测试」从来没跑过它声称要测的东西（假信心测试）✅本机实测（2026-09-17）

**现象**：为"后端离线提示一闪即逝"的修复写了断言"连续几轮轮询后提示仍在"，
断言**通过**。随后做变异反向对照——把修复退回旧写法（`if (backendOffline && !wasOffline) {…return}`），
断言**依然通过**。也就是说这条断言是空转的。

**根因**：驱动轮询时写了 `intervals[0]()`，想当然认为第一个 `setInterval` 是状态轮询。
实际 pet.html 里：

```
1272: setInterval(() => { …待机小剧场… }, 5000);   ← intervals[0]
1283: setInterval(tick, 1000);                    ← intervals[1] 才是轮询
```

驱动小剧场回调什么也没发生（它第一句就 `if (… || backendOffline) return`），
所以药丸当然一直是「后端离线」——**不是因为修复生效，而是因为根本没跑第二轮**。

**对策**：
1. 桩里记录周期：`setInterval = (fn, ms) => intervals.push({fn, ms})`，
   按 `ms === 1000` 唯一识别 tick，并断言"恰好一个"（周期变了会立刻报出来，
   而不是静默退化成空转）。
2. **每条新断言都做变异反向对照**：把被测的修复逐条退回旧写法，确认断言变红。
   本次 10 条新断言全部做了对照，其中就靠这一步揪出了上面这条空转。

**同类假通过（同一轮另一次）**：断言"亮色令牌块存在"时写成
`css.slice(mediaIdx).includes("--c-surface")` —— 把整个亮色令牌块删掉后**依然通过**，
因为文件后续规则里到处是 `var(--c-surface)` **引用**。
必须按大括号配对取出媒体块的**规则体**，并检查令牌是被**声明**（`--c-surface\s*:`）
而不是被引用。

**推论（通用）**：**"测试通过"和"测试有效"是两件事。**
断言写完必须问一句："如果我把这处代码改坏，这条断言会红吗？"
答不上来就去做变异对照——这比读一遍断言可靠得多。
`assert.ok(x.includes(...))` 这类"截尾/模糊匹配"断言尤其容易假通过，
要收紧到"结构性定位 + 精确判据"。

### 3.24 「反向对照」本身也会撒谎：变异没应用 / 测试没真跑 ✅本机实测（2026-09-17）

**现象**：按 3.23 的规矩给新断言做变异对照，脚本报"4 条变异全部被拦住"，
看起来很成功。但打开输出细看——**一条 FAIL 都没有**。
去查原因：测试进程报的是
`Error: ENOENT: no such file or directory, open 'D:\tmp\tmp.1ibjFUmcVX\m.html'`。
也就是说 4 个"被拦住"全是**读不到文件导致的崩溃退出**，跟断言一点关系没有。

**根因（两层）**：

1. **路径跨了两种世界观**。Git Bash 的 `mktemp -d` 给出 `/tmp/tmp.xxx`，
   MSYS 的 `cp` 把它写到 MSYS 自己的 `/tmp`（≈ `%TEMP%`）；
   而 Node 在 Windows 上把 `/tmp/tmp.xxx` 解析成**当前盘符下的 `\tmp\`**（`D:\tmp\...`）。
   一个写、一个读，两边根本不是同一个目录。
2. **判据太弱**。脚本只用"退出码非 0"判断"变异被拦住"——
   而**崩溃**的退出码也是非 0。于是崩溃被当成了"断言生效"。

**对策**：

1. 变异文件放在**两边都能解析的路径**（仓库内 `outputs/_mut/`，或传绝对 Windows 路径），
   别用 `mktemp` 的 MSYS 路径喂给 Node。
2. **先证明变异真的落盘了**：`grep -c` 改动前后的特征串计数，数不上变化就直接报"结论无效"。
   ```bash
   before=$(grep -c 'setBubbleVisible(false)' m.html)
   sed -i 's|{ setBubbleVisible(false); return; }|{ bubble.style.display="none"; return; }|' m.html
   after=$(grep -c 'setBubbleVisible(false)' m.html)   # 必须真的少 1，否则 sed 没匹配上
   ```
3. **再证明失败原因是断言而不是崩溃**：输出里必须出现 `FAIL <断言名>`；
   只要出现 `ENOENT` / `TypeError` / 栈回溯就判"结论无效"。
   判据写成"输出里同时有 `FAIL` 且没有异常栈"，而不是只看退出码。
4. 变异脚本本身也有 bug 时会静默放过（例：`if [ $? -eq 0 ]` 取的是上一条 `grep` 的退出码，
   不是测试的）——所以**判据只认输出内容，别认管道里飘忽的 `$?`**。

**证据**：修正路径 + 加落盘校验后重跑，6 条变异全部由**正确的断言名**拦住
（如"气泡显隐只有一个写入口"、"导览气泡走同一入口"），且还原后 md5 与改动前一致。

**推论（通用）**：**变异对照是"元测试"——它自己也需要被验证。**
顺序永远是：① 变异真的写进文件了吗 → ② 测试真的跑起来了吗 → ③ 失败原因是我预期的断言吗。
三步缺一步，"被拦住"就可能是巧合。

### 3.25 同一窗口里两个浮层抢高度：让位，而不是把整体做小 ✅本机实测（2026-09-17）

**现象**：桌宠快捷面板底部「最近发送」那行被切掉一截，并冒出内部滚动条。
只在**气泡同时出现**时发生（导览/处理中/后端离线），待机时一切正常。

**根因**：气泡与面板是同一个 220×480 透明窗里的**兄弟 flex 项**，
可用高是固定预算：

```
可用高 = 480(窗高) - 18(#root 上下留白) - 150(角色) - 6(面板下边距) - 气泡 - 6(气泡下边距)
```

量测三个场景（`tools/pet-panel-preview.cjs --measure`）：

| 场景 | 气泡高 | 面板拿到 | 面板自然高 | 被切 |
|---|---|---|---|---|
| guide | 82 | 217.8 | 224 | **6px** |
| think | 60 | 240 | 256 | **16px** |
| offline | 78 | 222 | 256 | **34px** |

面板 `flex` 默认可收缩，于是它被压扁、`overflow-y: auto` 生效，最下面那块被切。

**为什么不能"把面板整体做小"**：最坏情况（长导览文案 + 长状态文案）要砍 80px 才够，
那等于常态下永久牺牲呼吸感。而且窗口就这么大，两个浮层的内容量是**加法**，
靠"整体缩小"去追是追不上的。

**对策：让位（yield），只在冲突发生时才收**。
1. 冲突的判据是"气泡在屏"——加 `#root.compact`，在里面**收起最占地方、
   而此刻语义上最不重要的那一块**（这里是 `#recent`，50px + 9px 上边距 = 59px），
   顺带把行距各收 2~3px。让位后 guide 面板自然高 224 → 156，余量 60px。
2. **把触发点收敛成唯一入口**：气泡显隐散落在 4 处（`setState` 两分支、`playGuide`、
   离线分支），任何一处漏掉同步，那一处就会带着多余的内容去抢高度。
   统一成 `setBubbleVisible(show)`，它同时写 `display` 和 `.compact`，
   再用一条静态断言钉住"`bubble.style.display =` 全文件只出现一次"。
3. **让位块要选"本来就会显隐"的那个**：`#recent` 已经会随数据在有无之间切换
   （`:empty { display: none }`），所以它的出现/消失不是新行为，不会显得突兀。
   选一个"从来都在"的块去隐藏，用户会觉得功能坏了。

**验证**：新增 `tools/test-pet-panel-layout.cjs`，用真实 headless Chromium 量测并断言
"面板内容不溢出 / 没有元素被挤出窗口 / 按钮不被裁 / 让位规则与气泡显隐一致"。
7 个场景全部 `overflow=false`、`clipped=0`、`petTop` 一致。

**推论（通用）**：固定尺寸容器里两个浮层抢空间时，优先问三件事：
**① 谁可以按状态收起？（让位）② 收起哪个块最不伤功能？③ 触发点能不能收敛成一个入口？**
"整体等比缩小"几乎总是最差解——它同时牺牲了所有状态的观感，还未必够。

### 3.26 「测不出溢出」≠「没有溢出」：`scrollWidth` 的三种失明方式 ✅本机实测（2026-09-17）

**症状**：给桌宠加了一个分段开关，量测报 `scrollWidth(63) == clientWidth(63)`，
我据此判断"按钮宽度零余量、文字随时会被挤成省略号"，于是又缩字号又改内边距，
还砍掉了本想加的运行指示灯。

**根因**：我拿 `scrollWidth > clientWidth` 当"文字被截断"的判据，但它在这个场景下
**恒定不成立**，而且失败方式不止一种：

1. **居中溢出的方向问题（主要）**：`justify-content: center` 的内容放不下时，
   会向**两侧**溢出。而 `scrollWidth` 只统计"滚动可达的溢出"，
   起始侧（左边）那半截根本不计入 → `scrollWidth == clientWidth`。
2. **`overflow: hidden` 的容器**：滚动区域被裁剪，`scrollWidth` 会被钳到 `clientWidth`。
   偏偏 `overflow: hidden` 又是 `text-overflow: ellipsis` 生效的**前提条件** ——
   也就是说，**所有会显示省略号的按钮，这个判据都是瞎的**。
3. 反过来说，`scrollWidth == clientWidth` 也不等于"刚好卡满"：
   它只说明"没测到溢出"，真实余量可能还有 20px（我这次实测就是
   文字 41.36px / 可用 62px，富余得很）。

**对策**：别问滚动盒有多大，直接量**文字的自然宽度**（Range 给的是布局矩形，
裁剪发生在绘制阶段，不影响它）：

```js
var rng = document.createRange();
rng.selectNodeContents(el);           // 取内容的自然宽度
var textW = 0;                        // 多行的取最大一段
for (var r of rng.getClientRects()) textW = Math.max(textW, r.width);
var cs  = getComputedStyle(el);
var avail = el.clientWidth - (parseFloat(cs.paddingLeft) || 0) - (parseFloat(cs.paddingRight) || 0);
var clipped = textW > avail + 1;      // 这才叫证据
```

**证据**：把分段容器强制改窄（`VM_PET_HTML` 指到变异副本，不动仓库真文件），
新判据报 `textW 41.36 / availW 26 → clipped:true`；真文件 9 个场景全部 `clipped:false`。

**推论（比这条本身更重要）**：**换判据之前，先确认旧判据到底会不会失败。**
我这次的代价是做了三个没有必要的视觉妥协 —— 而只要先造一个"确定会截断"的变异
跑一遍，当场就能发现旧判据压根不报警。

### 3.27 「选定态」≠「运行态」：UI 必须对系统现状说真话 ✅本机实测（2026-09-17）

**症状（用户原话）**："千万变身，还有 RVC 变身。这两个用户不确定是用到底哪一种……
我觉得应该在桌宠上面应该会有一种体现提示，用户应该是哪一种变身？"

**根因（有两个，第二个更隐蔽）**：

1. 两个引擎（RVC 实时 / 千问变声）在后端是互斥的，但桌宠**根本开不了千问**：
   开关走的是主进程 `liveToggle` IPC，而它只认 `/api/rvc/live/*`。
2. 加了分段开关后，**最容易写错的一行**是把"高亮/药丸/按钮文案"挂在
   **`engine`（用户选了谁）**上，而不是 **`runningEngine`（实际在跑谁）**。
   于是在"我选了 RVC、但千问还在跑"（切换的那一瞬间，或从主界面另开的）
   就会告诉用户错的引擎 —— **这比没提示更糟**。

**对策**：

- 状态机里存**两个**变量，并让所有视觉输出**只**由 `runningEngine` 推导：
  选中 = 品牌紫，运行中 = 绿色 + 呼吸；两者可以同时出现（"选了 A、B 在跑"是合法状态）。
- 按钮文案也跟着 `runningEngine`：选中 RVC 但千问在跑 → 按钮写「开 RVC」，
  **不写**「停 千问」。
- 药丸/气泡标题点名引擎（「千问变声中」），别用无主的「变声中」。

**证据**：`qwen-dark` 场景实测 —— `sel=rvc, on=["rvc"], runningMark=["qwen"],
pill="千问变声中", liveLabel="开 RVC"`。8 条变异对照里，
「把药丸改由 `engine` 推导」这一条被专门断言拦住。

**推论（通用）**：凡是"用户的选择"与"系统的实际状态"可能不一致的地方
（引擎、播放/暂停、连接、开关），**展示必须在分歧时选择说真话**。
"用户刚才点了什么"是意图，"现在正在发生什么"才是事实。

### 3.28 关掉主窗 ≠ 关掉应用：一个 hide 掉的窗口就能把进程钉在后台 ✅本机实测（2026-09-17）

**症状（用户原话）**："我把这个应用给关了，它这个还在上面啊"、
"任务管理器看到它还在后台运行……右下角桌宠也没看到，只有任务管理器才能把它搞掉"。
同时那个置顶横幅还糊在屏幕上。

**根因**：Electron 的 `window-all-closed` 要"**一个窗口都不剩**"才触发。
而退出逻辑写在它里面：

```
主窗 closed → 只销毁了桌宠，漏了置顶横幅窗口
           → 横幅窗口仍存活（哪怕已 hide）
           → window-all-closed 永不触发
           → app.quit() 永不执行
           → 进程留在后台，且主窗/桌宠都已销毁 ⇒ 用户看不到任何 UI，只能开任务管理器
```

三个放大器凑在一起才让它这么难查：
① 那个窗口是 `transparent + frame:false + alwaysOnTop("screen-saver") + setIgnoreMouseEvents`，
   关不掉也点不到；② `hideAltHint()` 只调 `hide()`（窗口对象还活着，只是不可见）；
   ③ 应用没有托盘图标，进程活着却**完全没有入口**让用户关掉它。

**对策**（三层，缺一层都可能复发）：

1. 给每个"用完就藏"的窗口一个**真正的销毁函数**（`destroy()`，不是 `hide()`），
   并在主窗 `closed` 里逐个调；
2. `before-quit` 里再兜底销毁一遍（覆盖所有退出路径）；
3. **不要只依赖 `window-all-closed`** —— 它太脆弱，任何漏网窗口都会让它永不触发。
   在主窗 `closed` 里显式判断"已无窗口则 `app.quit()`"，把意图写死。

**证据**：改动后主进程加载自检 18 文件 0 失败；新增 `tools/test-electron-exit.cjs`
8 条静态断言；4 条变异（漏销毁 / 只 hide / 去兜底 / 退回半自动）全部被预期断言名拦住。

**推论（通用）**：**"关掉了"是用户的感知，不是程序的状态。**
凡是常驻/置顶/透明/无边框的辅助窗口，都要在退出链路上单独确认它被销毁；
而"进程还活着但没有任何可见入口"是最糟的失败形态 —— 用户既不知道它在跑，
也没有办法关掉它。

### 3.29 静态断言匹配到了注释：把真代码删掉，测试照样全绿 ✅本机实测（2026-09-17）

**症状**：为 §3.28 的修复写了 8 条静态断言，全绿。跑变异对照时却发现
"删掉 `app.quit()`"这条**没有触发任何失败** —— 退出码 0，测试仍然全绿。

**根因**：断言写的是"closed 处理器里包含 `app.quit()`"，而它匹配到的其实是
**我在上方注释里写的一句解释**：

```js
// window-all-closed 永不触发 → app.quit() 永不执行 → 应用无声无息留在后台
```

也就是说，这条断言从头到尾测的都是**我自己的注释**，跟代码在不在毫无关系。
这是 §3.23「假信心测试」的一个具体变体，而且更隐蔽 —— 因为注释是我刚写的、
内容还正好描述了这段代码，看起来"很合理"。

**两个连带错误**（同一批变异里一起暴露）：

1. **把代码注释掉不算有效变异**：`// altHint.destroyAltHint();` 之后，
   正则 `/altHint\.destroyAltHint\(\)/` **依然匹配**（字符串还在，只是不执行）。
   要验证断言有效，变异必须**整行删除**。
2. **按长度切代码块会越界**：我取"从 `win.on("closed"` 起 900 字符"，
   结果圈进了后面的无关代码与注释。必须**按结构切**（切到处理器自己的 `});`）。

**对策**：

```js
function stripComments(src) {
  return src.replace(/\/\*[\s\S]*?\*\//g, "")
            .replace(/(^|[^:'"`\\])\/\/[^\n]*/g, "$1");  // 避开 http:// 之类
}
```

**凡是断言"某段代码存在"，先剥注释再匹配。**（`[^:'"`\\]` 是为了不误伤 URL 里的 `//`。）

**推论**：写完静态断言后，至少做一次"**整行删除**"式变异确认它会红。
只做"注释掉"式变异是自欺 —— 注释掉的东西，正则照样认得。

### 3.30 打分器一加载，后面的 RVC 子进程就崩：跨进程 CUDA 上下文竞争 ✅本机实测（2026-09-18）

**症状**：试音间批量试音，**第一个音色成功，第二个起全部失败**。错误是
`RuntimeError: cuDNN error: CUDNN_STATUS_EXECUTION_FAILED`。

**看起来像**：显存不够。**实际不是**——当时 GPU 5498/8151，还剩 ~2.6GB，而单次 RVC 只要 ~1.0GB。

**根因**：客观打分器（CAM++ 声纹 `speaker_sep` + NatScore 的 whisper-small）是在**后端主进程**里
加载的，它占住了那个进程的 CUDA 上下文。而每件音色的 RVC 推理是**另起子进程**跑的，
两个 CUDA 上下文撞在一起 → cuDNN 执行失败。所以"第一件成功"是因为当时主进程还没加载打分模型；
一旦第一件跑完就去打分，第二件必崩。

**判据（怎么一眼认出这个坑）**：失败件数 = 总数 − 1，且错误里带 `cuDNN`/`CUDNN_STATUS`。
换权重、换音色、加显存都不管用 —— 因为问题不在显存，在**谁先碰了 GPU**。

**对策（顺序即一切）**：
1. **推理阶段绝不加载任何打分模型**，打分统一放**独立子进程**（`m2_server/audition_score.py`），
   跑完即退出、显存全还。顺带一个好处：整批只加载一次模型，比逐件起进程快 N 倍。
2. 阶段拆分：先跑完**所有**推理 → 释放独占位与任务锁 → 再异步打分。
   用户不该为了几个附加分数等着开不了实时变声。
3. 打分是附加信息：超时（`SCORE_TIMEOUT=300`）、子进程崩、权重缺失，一律只记
   `score_error`，**绝不把已经出来的试音结果标成失败**。

**同族推论**：任何"父进程加载模型 + 子进程也要用 GPU"的组合都要问一句"谁先占的"。
本项目里 `_live_proc_alive` / `_cascade_alive` 那套互斥只覆盖了"另一个子进程"，
没覆盖"本进程自己占着"。

### 3.31 子进程报错信息被 warning 淹没：报出来的"原因"是假的 ✅本机实测（2026-09-18）

**症状**：RVC 推理明明崩了，界面却显示
`RVC 推理失败: …/weight_norm.py:143: FutureWarning: torch.nn.utils.weight_norm is deprecated … |
WeightNorm.apply(module, name, dim)`。看着像"跑通了只是有个警告"，完全指不到真因
（真因是上一条的 cuDNN）。

**根因**：错误信息是取 `stderr` 的**最后 3 行**。torch 导入期会打一条两行的弃用警告
（警告本身 + 源码片段），它恰好压在末尾，把真正的 `RuntimeError` 挤出窗口。

**对策**：`ab_chain._fail_tail(stderr, stdout)` —— 先找含 `Error` / `error` / `Traceback` 的行；
没有才退而求其次，**去掉警告与源码片段/caret 行**再取末尾。已覆盖
`test_fail_tail_prefers_real_error_over_warning` 等 4 条回归。

**推论**：凡是"取末尾 N 行"的日志摘要，都要先问"末尾会不会是噪声"。
更稳的做法是**按特征挑**（关键错误行优先），而不是按位置取。

### 3.32 打分器去 ping 远端权重新鲜度：本地缓存齐全也要白等 2 分钟 ✅本机实测（2026-09-18）

**症状**：第一次算自然度分，卡了 ~2 分钟才出分。日志里是
`ReadTimeoutError(host='hf-mirror.com', port=443) … while requesting HEAD …/whisper-small/model.safetensors`
`Retrying in 1s [Retry 1/5]`。

**看起来像**：权重没下载。**实际相反** —— `~/.cache/huggingface/hub/models--openai--whisper-small`
有 923MB，权重早就齐了。

**根因**：transformers 每次加载都会去远端 ping 一次权重新鲜度；网络不通时它会重试 5 次、
每次 read timeout 10s。缓存命中并不代表不联网。

**对策**：在**导入 transformers 之前**设 `HF_HUB_OFFLINE=1` + `TRANSFORMERS_OFFLINE=1`
（这两个开关是导入期读的，设晚了不生效）。缓存真缺时会**立刻**报错而不是干等 —— 比等 2 分钟更好。
见 `m2_server/audition_score.py` 与 `test_audition_score_cli_offline_by_default`。

### 3.33 把"每次探测都很贵"的状态接口当廉价接口轮询 ✅本机实测（2026-09-18）

**症状**：试音间前端每 5 秒拉一次 `/api/audition/env`，而单次探测要起 **PowerShell 查进程**
（`_live_proc_alive` 1.31s + `_cascade_alive` 1.26s）→ 每次 2~3 秒，5 秒一次等于长期占着 CPU。

**根因**：数字看起来很小（"就一次 HTTP 请求"），但后端那侧的实现是**进程枚举**，不是读缓存。
同类测试也踩了：`test_env_shape` 里把 `audition_env()` 写在 12 个 key 的循环里 → 单条用例 31.8 秒。

**对策**：
- 前端：**空闲才轮**（跑任务时按钮已被任务状态禁掉，再探测没意义），间隔 8s，另留手动刷新。
- 测试：一次调用、多处断言，别在循环里调。用 `--durations` 定期体检，30 秒级的用例基本都有问题。

**推论**：写轮询之前先量一次单次调用耗时；超过 100ms 的都要考虑"什么时候真需要刷新"。

### 3.34 常驻 GPU worker 与「另一个要内存的子进程」不能共存 ✅本机实测（2026-09-19）

**背景**：试音间批量换声。一次性 CLI（`offline_vc_infer.py`）每个音色都要重新 `load_vc()`，
4.2s 音频实测**墙钟 32s**（推理只占 4.2s）→ 4 个音色 128s。项目里本来就有常驻 worker
（`--serve`，按 `(pth,index)` 缓存引擎），改用它后同一批 **19.6s**、第二轮 1.0s。

**但换上去之后，同一批的"客观分"全部失败**。症状分三种，且**随并发状态不同而不同**：

| 场景 | 打分结果 |
|---|---|
| 常驻 worker 不在 | ✅ 正常（secs 0.547 / nats 3.099） |
| 常驻 worker 活着并缓存了 4 个引擎 | ❌ `自然度打分失败：页面文件太小 (os error 1455)` |
| 只卸掉引擎缓存、**worker 进程仍在** | ❌❌ 打分子进程**直接崩**，退出码 `0xC0000005`（ACCESS_VIOLATION），无产物 |

**根因**：worker 进程本身（torch + hubert）就占着 1.5GB+ **提交内存**。打分子进程要再装
一份 torch + whisper-small + CAM++。这台机器提交上限本来就紧（C 盘 ~96% 满），
两者叠加就超了。

**★ 最值得记的一条：我最初的设计被自己的实验否掉了。**
第一版是"跑完 `unload` 一下：只丢引擎缓存、保留 hubert，这样既省显存又不用重付 10.5s 冷启"。
听起来很合理 —— **实测不够**：上表第三行说明卸引擎后 worker 进程仍占着那 1.5GB，
打分子进程反而崩得更彻底。**"意图正确"不等于"效果达成"**，删掉这个功能是对的，
留着一个"目的已被证伪"的接口比没有它更危险（下一个人会以为它在起作用）。

**对策（顺序即一切）**：批量推理结束 → **整个 `stop_worker()`**（进程退出，内存与显存全还）
→ 再起打分子进程。代价是下一批要重付 ~10.5s 冷启；相比"每个音色都重载"的子进程路径
仍然快一个数量级（实测 4 个全新音色：**128s → 73s，且打分从失败变成全部成功**）。

**判据**：凡是"A 常驻占资源 + B 也要资源"的组合，都要实测叠加后的余量；
别用"我卸一部分应该够了"来推。另外这类失败**必须能被看见** —— 打分失败只记
`score_error`，试音结果照常返回（见 §3.35 的反面：那个是"看不见"）。

### 3.35 多阶段任务留下"两个标志都是 False"的窗口：前端停止轮询、结果永远不显示 ✅本机实测（2026-09-19）

**症状**：批量试音跑完，界面显示"试音完成"，但四个结果的分数**永远停在"不可算"**，
而且没有任何错误提示（`score_error` 是空串）。手动再调接口，分数其实已经算好了。

**根因**：后端是两阶段任务，两个标志控进度 —— `running`（推理中）与 `scoring`（算分中）。
原来的写法是"决定要打分 → 先 `stop_worker()`（可达 10s）→ 再由打分线程把 `scoring` 立起来"。
于是中间有 ~10s 窗口，**两个标志都是 False**：

```python
finally:
    _mark(running=False)      # ← 第一个标志先落下
    stop_worker()             # ← 10s
    # 这里 scoring 还是 False（要等线程起来才置 True）
...
threading.Thread(target=_score_pass, ...).start()
```

前端轮询的判断是 `if (!running && !scoring) return`（不再拉）→ 在这 10s 窗口里正好
判定"任务彻底结束"→ 停止轮询 → 等分数真算出来也没人去取 → 界面卡在"不可算"。
**对用户说的是一句假话**：真实状态是"还没开始算"，界面说的是"算不了"（同一族的 §3.27）。

**对策**：**"进行中"的标志要在进入下一阶段之前立起来，而不是在阶段内部立。**
```python
finally:
    _mark(running=False)
    will_score = score and 有产物
    if will_score:
        _mark(scoring=True, score_total=len(pending))   # ← 先立标志
    stop_worker()                                       # ← 再去做耗时的事
```
并用 `will_score` 决定要不要起线程（而不是起完线程再让线程报"我没干活"）。

**守卫**：`test_batch_stops_worker_before_scoring` 断言顺序必须是
`["stop_worker", "score"]` —— 顺序写反就红。

**推论**：只要进度由**多个布尔标志**拼出来，就要问一句"有没有任意两个阶段之间存在
『所有标志都 False』的瞬间"。有 → 前端一定会在这个瞬间断掉轮询。
更稳的做法是给状态机一个显式的 `phase` 字段，而不是若干可以同时为假的 bool。

### 3.36 配置里引用了插件、requirements 里没声明它：只有 `--ci-fidelity` 看得见 ✅本机实测（2026-09-19）

**症状**：本机全量自检全绿（钩子、pre-push、`tools/check.py` 都过），
而 `python tools/check.py --ci-fidelity` 一跑就红：

```
=== [pytest] D:\变声\.venv-ci\Scripts\python.exe -m pytest m2_server -q --no-header …
ERROR: usage: python -m pytest [options] [file_or_dir] [...]
python -m pytest: error: unrecognized arguments: --cov=m2_server --cov-report=term-missing …
  inifile: D:\变声\pyproject.toml
```

**根因**：`pyproject.toml` 的 addopts 从建立那天就写着
`--cov=m2_server --cov-report=term-missing --cov-report=html --cov-report=json`，
而 **`pytest-cov` 既不在 `requirements.txt` 也不在 `requirements-dev.txt`** ——
它只存在于本机 `.venv`（某次手工装的残留，同批还有 `pytest-xdist` / `pytest-clarity`）。
于是：本机绿是因为那个残留，CI（只装 `requirements-dev.txt`）则**连参数解析都过不去**，
而且报错长得像"配置写错了"，不像"缺个包"。

**为什么三道门禁全是盲区**（这才是这个坑值得记的理由）：

- `ruff` 不看 pytest 配置；`requires` 只对账"测试 import 了什么"，而缺的不是 import；
- `--ci-fidelity` 的依赖指纹只管"requirements 变了就重装"，**不管"该写的没写"**；
- 其他所有检查都跑在本机 `.venv` —— 而那正是唯一装了这个包的地方。
  **一个包只在本机存在，就等于它不受任何门禁保护。**

**对策**：`requirements-dev.txt` 补上 `pytest-cov`（带注释说明为何不能改成给 CI 加
`-o addopts=` 去掉覆盖率：ci.yml 的立身之本就是"与本地、与 git 钩子跑同一条命令"）。

**守卫**（`m2_server/tests/test_check_ci_fidelity.py` §6）：静态对照
`pyproject.toml` 的 pytest 配置 ↔ `requirements-dev.txt` 的声明，两张表两个方向：

- `_ADDOPTS_OWNERS`（addopts 的长选项 → 发行包）**未知就失败** ——
  “未知”正是要强制人做一次显式决定的地方；
- `_INI_KEY_OWNERS`（插件提供的 ini 键 → 发行包）**已知就必须声明** ——
  ini 键大多是 pytest 自带的（`testpaths` / `filterwarnings`…），反向穷举会变成维护负担。

解析 requirements 时会剥掉注释 —— 那段解释为何要装它的注释自己就写着 `pytest-cov`，
注释被误当声明就又是一个假绿。
变异验证：① 把 `pytest-cov` 那行注释掉 → 正好 2 条变红；
② 把 `asyncio_mode = "auto"` 加回去 → `test_plugin_owned_ini_keys_have_their_plugin_declared` 变红。

**同一个“干净机盲区”里还埋着第二、第三件事**（同一个 `--ci-fidelity` 跑出来的）：

1. **anyio 4.15 把 `anyio.abc.BlockingPortal` 改成惰性别名**（`__getattr__` 时发废弃警告），
   而 **starlette 1.6.0 的 `testclient.py` 顶层还在引用它** ——
   叠上 `filterwarnings` 里的 `error::DeprecationWarning`，就变成 **import `fastapi.testclient` 即红**：
   6 条收集期 ERROR（`test_server` / `test_storage` / `test_ab_chain` / `test_cors_file_origin` …）。
   本机 `.venv`（anyio 4.14.2）全绿、干净 venv（anyio 4.15.1）全红 —— **同一个仓库，只因装没装最新版**。
   属于第三方自己的事，按已有先例（`pydub`/`audioop`）加一条**只匹配该消息**的 `ignore:`，
   并在注释里写明“starlette 更新后回来删掉这行”。
2. **`asyncio_mode = "auto"` / `asyncio_default_fixture_loop_scope` 是**惰性配置****：
   `pytest-asyncio` 不在任何 requirements 里（本项目也真的一条 async 用例都没有），
   在干净机上它只产出 `PytestConfigWarning: Unknown config option` ——
   一份“看着像已接好、实际是假的”配置。删掉这两项，要写 async 用例时再连同插件一起加。

**普适教训**：**配置里引用了一个能力，就必须有一道门禁去对账"那个能力是谁提供的、声明了没"。**
只装在开发机的包与只写在配置文件里的选项，是同一类隐形依赖。
且注意这里的第二个普遍形状：**“本机绿”可能只是因为本机恰好旧了一个版本** ——
依赖不钉死时，`--ci-fidelity` 复刻的不只是“干净机”，而是“**今天新装一台干净机**”。
加依赖后跑一次它（`docs/分发与打包说明.md` §2 也这么要求）。

## 八、桌面控制 / UIA 通用坑（2026-09-18，配套 `tools/desktop-control/`）

背景：为了给 agent 一对"眼睛 + 手"，写了 `tools/desktop-control/dc.ps1`
（PowerShell 5.1 + UI Automation，零第三方依赖，自带 `selftest` 与 WPF 沙箱靶子）。
下面这些坑**与微信链路无关**——任何 UIA / 桌面自动化都会撞上。

### §8.1 PowerShell 变量不区分大小写 → `$out` 撞参数 `-Out`

- **症状**：`probe` 报 `WriteAllText ... 找不到路径 'D:\变声\System.Collections.Specialized.OrderedDictionary\probe.json'`。
- **根因**：PowerShell 变量名大小写不敏感，`$out = [ordered]@{...}` 就是给参数 `$Out` 赋值；
  `switch` 块与脚本**同一作用域**，于是输出目录静默变成字典。
- **对策**：脚本里局部变量别与参数同形（`dc.ps1` 已把它改成 `$payload` 并留注释）。
- **证据**：✅本机实测，首次 `probe` 即撞。

### §8.2 `[ref]$null` 假成功 → UIA 模式探测全空

- **症状**：`tree` 里每个控件的 `pat`（支持的模式）都是空，包括右键能点的按钮。
- **根因**：`$el.TryGetCurrentPattern($pattern, [ref]$null)` 抛错的路径没有、结果永远拿不到 → 恒 false。
- **对策**：`$probe = $null; ... [ref]$probe`（真实变量）。
- **证据**：✅本机实测（修前 WinForms / WPF 的按钮都"没有模式"）。

### §8.4 给 agent 看的截图必须先降采样

- **症状**：`read_files` 对 2560×1600 的 PNG 返回 `[FILE_TOO_LARGE] ... images over 768 KB cannot be attached`。
- **根因**：附件上限 768KB，全屏 PNG 约 1.4MB。
- **对策**：`dc.ps1 shot -Preview` 顺带输出 1280 宽 JPEG（~100KB）。
- **证据**：✅本机实测。

### §8.5 被 `.gitignore` 覆盖的文件，`read_files` 一律 `[BLOCKED]`

- **症状**：产物落在 `tools/desktop-control/out/`（已 ignore），`read_files` 三个 JSON 全 `[BLOCKED]`，同文件 `cat` 正常。
- **根因**：读取工具遵守 ignore 规则。`.workbuddy/`（`.gitignore:120`）、`.workbuddy-ai/`（`.gitignore:122`）整目录如此。
- **对策**：**agent 要读的产物一律别放进 ignore 路径**；`dc.ps1` 只 ignore `out/*.png|json`，
  特意留下 `*.jpg` 预览可读。
- **⚠️ 更正（2026-09-20 复测）：「一律 BLOCKED」不成立，它是**那个** `read_files` 工具的行为，不是通则。**
  WorkBuddy 的 `Read`/`Write`/`Edit` 对 `.workbuddy-ai/memory/*.md`（同样被 ignore）**读写全部正常**，
  本次记忆目录合一就是靠它们完成的。**别再因此把记忆文件绕开标准文件工具去 `cat`。**
- **证据**：✅本机实测（两处：09-06 的 `read_files` BLOCKED；09-20 的 WorkBuddy 读写成功）。

### §8.6 DPI 缩放：UIA 矩形 vs 截图像素错位

- **症状**：本机 150% 缩放（物理 2560×1600 / 逻辑 1707×1067）下，不感知 DPI 的进程拿到的坐标
  与截图像素不在同一坐标系，点哪错哪。
- **对策**：脚本开头 `SetProcessDPIAware()`，与截图同源。
- **证据**：✅本机实测（感知后 Freebuff 窗口 UIA 矩形 `200,125,2160,1350` ↔ 1280 宽预览图上的 `100,62`，×2 精确对齐）。

### §8.10 WorkBuddy 环境里启动 Electron 应用会静默失败：`ELECTRON_RUN_AS_NODE=1` ✅本机实测（2026-09-19）

- **症状**：从 agent 的 shell 里 `Start-Process 变声工坊.exe --remote-debugging-port=9222`，
  报 `...\变声工坊.exe: bad option: --remote-debugging-port=9222` 且 `ExitCode=9`（主进程立刻退出）；
  **不带参数**启动则毫无报错、进程也不出现。带不带沙箱一个样。
- **根因**：WorkBuddy AI 给所有子进程注入了 `ELECTRON_RUN_AS_NODE=1`（外加 `NODE_OPTIONS` 指向它的
  node shim）。这个变量让 **Electron 应用退化成纯 Node 进程** —— 不加载 Chromium，于是 Chromium 专有的
  `--remote-debugging-port` 成了未知的 node 选项，node 报 `bad option` 并以 **9** 退出。
  识别线索：`bad option` 是 **node 的措辞**，不是 Windows / Electron 的。
- **对策**：启动前清掉这两个变量（只影响当前 PowerShell 进程，不动系统环境）：
  ```powershell
  Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
  Remove-Item Env:NODE_OPTIONS -ErrorAction SilentlyContinue
  Start-Process -FilePath $exe -ArgumentList "--remote-debugging-port=9222"
  ```
  诊断请用 `[System.Environment]::GetEnvironmentVariable('ELECTRON_RUN_AS_NODE')`，
  **别用 `Get-ChildItem Env:`** —— 本机有 `Path`/`PATH` 重复键，它会直接抛"已添加了具有相同键的项"。
- **证据**：✅本机实测，清变量后同一 exe 立即正常启动（CDP 9222 出现 `pet.html` 与主窗口两个 target）。

### §8.11 安装版的 `MEDIA_DIR` 是**包内空目录**，不是 `D:\变声\media` ✅本机实测（2026-09-19）

- **症状**：安装版（`变声工坊.exe`）里 `/api/voices` 只列 RVC 模型、`has_reference` 全 false；
  桌宠「合成并发送」必报 **`请先选择音色`**（HTTP 400）。
- **根因**：`m2_server/config.py` 的 `ROOT = Path(__file__).resolve().parent.parent`。安装版后端代码在
  `resources/backend/`，故 `MEDIA_DIR = resources/backend/media` —— 而那个 `media/voicebank/` 是**空的**，
  `D:\变声\media\voicebank\kangaroo\reference.wav` 不在它视野里。
  ⚠️ `RVC_ROOT` 默认是绝对路径 `D:/RVC`，所以 RVC 模型照样找得到 —— 这种"一半找得到一半找不到"
  最容易误判成"音色没训练好"。
- **对策**：启动时用 `VM_MEDIA_DIR` 覆盖（`config._path()` 中环境变量优先于默认值）：

### §8.21 「正则扒源码对账」的门禁在重构后会**两边都空**地白绿 ✅本机实测（2026-09-20）

- **症状**：`test_plugin_manifest.py` 原有两条门禁 —— 从 `App.tsx` 抓
  `<Route path="…">`、从 `StudioNav.tsx` 抓 `START_ITEMS`/`MORE_ITEMS` 数组，

  但 `_nav_items()` 是 `assert m, "找不到 START_ITEMS"` 先炸，
  若当时图省事改成"找不到就返回空列表"，就会变成
  **左 0 条 vs 右 0 条 → 白绿**，而且从此永远绿。
- **根因**：这类门禁的**校验力来自"两边各自独立地表达同一件事"**。
  一旦被校验的一侧改成"从另一侧派生"，两侧就不再独立 ——
  对账退化成 `X == X`，无论 X 是什么都成立。**重构恰好会制造这种退化**，
  而它发生的那一刻通常全绿，没人会注意。
- **对策**：把「A 与 B 对账」换成两条**方向不同**的断言：
  1. **A 不许再自己写**（`test_app_tsx_no_longer_hardcodes_page_routes` /
     `test_studio_nav_no_longer_hardcodes_nav_items`）：不许出现字面量页面路径、
     不许静态 import 页面、不许硬编码导航数组；**并且正面要求它确实调用了
     `buildRoutes(` / `navItems(`**（只看"没有写死"不够 —— 两条路都不走也是"没写死"）。
  2. **B 冻结快照**（`test_manifest_*_are_the_frozen_*`）：清单现在是 IA 的唯一来源，
     少一条没有任何别的东西会发现，所以要显式冻结。
     `A ∧ B ⇒ 前端呈现的集合 == 冻结的那一份`，与原命题等价。

### §8.22 「靠纪律别 add」不如「让它不在工作树里」：截图被无关提交顺带入库 ✅本机实测（2026-09-21）

  但代价是任何 `git add .` / `git add tools/desktop-control/` 都会连截图一起收。

     （会让人以为还能安心 add）。门禁测试专门断言这句话不许再出现。
- **顺带发现——回滚点会一起被重写**：`git branch backup/xxx master` 建的备份 ref

### §8.23 合规审计器读的是 HEAD，不是工作区：不提交就复跑，结论永远是旧的 ✅本机实测（2026-09-21）

- **症状**：改完 `AGENTS.md` / `docs/犯错指南.md` / `tools/verify_backend_sync.py`
  里写死的 `C:\Users\<用户>\...` 路径后立刻复跑 `tools/audit_git_history.py`，
  报告**纹丝不动，仍是一条「HEAD 仍含 11 处 → 要动的文件：AGENTS.md ...」**。
  第一反应是"我没改干净"，于是去 grep 工作区 —— 结果**工作区零命中**，
  两边对不上，很自然会怀疑是不是自己的编辑没保存。
- **根因**：审计器扫的是 **HEAD（已提交内容）**，不是工作区。它的用途是
  "推送前最后一道检查"，所以判据必须是"**将要推上去的东西**"，而不是"我本地当前的样子"
  —— 工作区里的未提交修改根本不会进远端，拿它当判据等于自欺。
  这个语义**已写在工具自己的 docstring 里**（`tools/audit_git_history.py:376`，
  是 2026-09-14 踩过同一个坑后补的），但只有在找这条注释时才看得到。
- **对策**：顺序**必须是**「改工作区 → **提交** → 再跑审计」。审计器的
  `RESULT: FAIL` 行也是按这个前提写的："HEAD 仍含 N 处 → 改工作区 **+ 提交** 即可"。
  推论：**别用审计器当"改对了没"的即时反馈**；要即时看工作区，直接 `grep` 跟踪文件，
  或 `git grep <pattern> --cached` 看暂存区。
- **附带发现——"仅历史"的计数会因 HEAD 侧归零而变大**：本次 HEAD 12 → 0 处后，
  仅历史从 103 → 113 处。**不是新泄漏**：同一片段若在 HEAD 与历史都存在，
  原先只算在 HEAD 那一栏；HEAD 侧清掉后，历史侧的那条才单独显形。
  所以看到"仅历史变多"要先确认 HEAD 侧是不是变少了，别当成回归。
- **证据**：✅本机实测。提交 `d95514e` 前复跑：`HEAD 仍含 12 处`；提交后复跑：
  `HEAD 仍含 0 处`，且 `--allow-history-only` 退出码 **0**
  （`凭据 0 处 / HEAD 仍含 0 处`）。工作区侧用
  `git ls-files | while read f; do grep -c "Users.mouxu\|Users/mouxu" "$f"; done` 复核为 0。

### §8.26 SPA 兜底把 `/api/*` 也吞了：关掉的能力端点返回 `200 text/html` ✅本机实测（2026-09-21）

- **症状**：在**已安装副本**上验收插件开关时发现 —— 关掉 `sound.rvc-live` 后
  `/api/rvc/live/status`、`/api/cascade/status` 返回 **`200 text/html`**（前端 `index.html`），
  而不是 404。同时 `/api/health` 正常 200 JSON。
- **根因**：`server.py` 最后的 SPA 兜底 `@app.get("/{full_path:path}")` 会吃掉
  **一切没匹配上的 GET 路径**，包括 `/api/*`（它只排除了「已存在的文件」）。
  路由不再挂载（插件被关）⇒ 路径落到兜底 ⇒ 首页被当成接口响应发回去。
  不是本轮插件化引入的：拼错任何 `/api/...` 都一直返回 200 HTML，只是插件化
  把「一个本该不存在的端点」变成常态，才把它从边角变成了主路。
- **为什么很危险**（比 404 难查得多，三个后果互相掩护）：
  1. 前端 `jsonFetch` 抛的是 `Unexpected token '<'`（像前端 bug，实际是后端语义）；
  2. Network 面板**没有任何红**（200 是成功），验收清单里「全程零 404」白过；
  3. 验收清单里「点一下应该 404」也是**永远不成立**的判据 —— 两条一起把真问题放过。
- **对策**：兜底里先把 `/api/`、`/v1/` 挡掉，给出 404 + JSON 且说清原因：
  ```python
  if full_path.startswith(("api/", "v1/")):
      return JSONResponse(status_code=404,
                          content={"detail": f"无此接口: /{full_path}（路径可能拼错，或其所属能力已被关闭）"})
  ```
  然后必须把断言落到**HTTP 响应**上，不是内部变量上：`mount_plan()` 里没有 ≠
  端点不可用。新增
  `test_plugin_switch.test_a_disabled_capability_endpoint_is_gone_at_the_http_level`
  （子进程 A/B：同一段脚本、只差一个状态文件；断言 `[404, "application/json"]`）+
  `test_server.test_api_paths_are_never_served_as_the_spa`（拼错路径也不许拿 HTML），
  另一条 `test_spa_fallback_still_serves_the_frontend` 守住反方向（真页面/静态资源照旧）。
- **变异验证**：把守卫改成 `if False:` → 两条新用例同时红，报
  `实际 [200, 'text/html'] == [404, 'application/json']` 与 `/api/nonexistent/whatever 没 404，而是 200`。
- **普适教训**：**「XX 不存在」也要有人负责「说它不存在」**。任何 SPA/静态兜底路由
  都会给不存在的 API 路径一个 200 —— 于是「404 语义」在项目里从来不是自然存在的，
  是得显式写出来的。推论：断言要落在**用户/客户端看到的那一层**（HTTP 状态码 +
  content-type），中间层（内部变量、挂载计划、内部标志）只能当辅助证据。

### §8.25 门禁工具的**输出编码**能把「通过」变成「失败」，而且两个方向都会炸 ✅本机实测（2026-09-21）

- **症状**：`tools/check.py`（**全量**）在 Windows 上恒红，两条用例失败：
  `test_audit_endpoint_ownership.py::test_check_mode_exit_code_matches_findings`、
  `test_plugin_deps.py::test_ownership_gate_exit_code`。而 `--fast` 一直绿 ——
  因为 `FAST_TESTS` 里没有这两个文件，所以**提交钩子永远看不到它们**（这就是它能挂住的原因）。
- **根因**（两个方向，同一个"没显式钉编码"）：
  1. **子进程写不出**：`tools/audit_endpoint_ownership.py --check` 的 stdout 被
     **重定向**（管道/文件 —— pytest 子进程、`> out.txt` 都算）时按 ANSI(cp936) 编码，
     而报告里的 `⚠️`（U+26A0）**不在 GBK 里** → `UnicodeEncodeError` → 退出码 **1**。
     实测它**判定其实是「通过」**：门禁假红，且报告只打了 460 字节就断在那行，
     后面整节（含"哪个模块有问题"）全丢。控制台直连不触发（Python 走 `WriteConsoleW`），
     所以它只在重定向时现形。
  2. **父进程读不进**：`tools/check.py` 的 `_env()` 会给子进程 `PYTHONIOENCODING=utf-8`
     （本意是防中文日志炸），于是子进程改吐 UTF-8；而用例里
     `subprocess.run(..., text=True)` **按 locale(cp936) 解码** →
     `UnicodeDecodeError: 'gbk' codec can't decode byte 0xaa`。
     同一份代码在 Linux CI 上永远是绿的（locale 是 UTF-8），所以 CI 也不报。
- **对策**（两侧都要，缺一不可）：
  1. **工具自己**在 `main()` 开头 reconfigure stdout（照 `tools/check.py` 的 `_console()`）：
     ```python
     try:
         sys.stdout.reconfigure(encoding="utf-8", errors="replace")
     except (AttributeError, OSError, ValueError):
         pass
     ```
     本批补了 8 个（`audit_endpoint_ownership` / `audit_plugin_deps` / `audit_git_history` /
     `auto_pipeline` / `check_app_exit` / `hard_delete` / `stress_live_test` / `uia_probe`）。
     ⚠️ **放在 `main()` 里而不是模块级**：这些工具会被测试 `import`，模块级 reconfigure
     会把 pytest 自己的捕获流也改掉。
  2. **测试自己**钉 `encoding="utf-8", errors="replace"`；子进程是**我们自己的脚本**时
     双向钉死（`env["PYTHONIOENCODING"]="utf-8"` + 解码侧同样）。
- **守卫**（`m2_server/tests/test_tool_stdout_encoding.py`，8 例）——
  写"文本级"守卫必须先解决"它会不会白绿"：
  · 静态规则用**判据本身**（`ch.encode("gbk")` 失败 = 真会崩），不是"看到符号就报"——
    纯中文/全角标点（`；`、`——`）在 GBK 里，**不报**；
  · 判"测试有没有钉 encoding"用 **AST**（`ast.Call` 的 `text=True` 关键字），
    因为文本扫法会被**字符串字面量**骗到 —— 实测这条守卫第一次跑就红在自己身上
    （牙齿测试里嵌着 `text=True` 的样例代码）；
  · 运行时守卫**真的把 stdout 交给管道**，并参数化两种环境（按机器默认 /
    `PYTHONIOENCODING=utf-8`），因为两个方向炸的不是同一侧；
  · 三条都做了**变异验证**：抽掉 reconfigure → 静态规则报 `audit_endpoint_ownership.py:626`、
    运行时守卫报「在『按机器默认』下崩了」；抽掉测试的 `encoding=` → 报
    `test_audit_endpoint_ownership.py:254`。
- **普适教训**：**门禁的输出编码不是装饰，是门禁的一部分**。一个"通过"被编码问题
  变成"失败"的工具，比一个不存在的工具更坏：它让人怀疑代码，而问题在环境里。
  推论：① 任何"会被重定向/被当子进程跑"的输出，写出侧就钉死编码；
  ② 子进程解码侧钉死同一编码，**不要依赖两边恰好都用 locale**；
  ③ 加了守卫要立刻问「它现在为什么是绿的」——本项目连续三次同类问题
  （`docs/犯错档案-微信.md` §2.28 的 `md5sum` 假红假绿、§8.21 的两边都空、本条）都是"守卫绿得没有理由"。

### §8.29 「模块级 cache + 组件各自 `useState`」= 一部分消费者会**永远**卡在错误态 ✅本机实测（2026-09-21）

- **症状**：用户截图里，主区域首页卡片都正常渲染，**左侧导航却一直空着**，
  只写一句「读不到能力清单，导航暂不可用」。用户的原话是「好像你们没给我接插件」
  —— 界面看起来像插件系统根本没接上。
- **根因**：`web/src/lib/pluginRoutes.tsx` 的 cache（`cached` / `inflight`）是**模块级单例**，
  但 `usePluginCatalog()` 把状态放在**每个组件自己的 `useState`** 里，`reload()` 只
  `setNonce(n => n+1)` bump **调用者自己那个实例**。于是：

  1. 后端由主进程 spawn，而窗口**不等它**就 `loadFile` 了
     （`web/electron/main.cjs` 里 `startBackend()` 只负责 spawn，不 `waitForBackend`；
     等健康检查的 `reportBackendTrouble` 是**失败提示**用的，不是加载前置），
     前端第一次 `GET /api/plugins` 必然赶在端口 bind 之前 → 失败；
  2. `App` 与 `StudioNav` 同时进 error（主区域弹 NoticePanel + 「重试」，侧栏写那句话）；
  3. 用户点主区域的**重试** → 只有 `App` 的 effect 重跑、cache 被填上、主区域恢复；
     `StudioNav` 的 effect 依赖是它自己的 `nonce`，永远不重跑 → **永久卡死**。
     它连"再去读一次已经填好的 cache"的机会都没有。

- **一眼判据（不用跑代码）**：**同一个状态在不同组件里可以不一致** —— 这就是病征。
  只要看到"这块好了、那块还坏着"，先查这个状态是不是"共享的 cache + 各存一份的 state"。
- **证据**（`%APPDATA%\voice-morph-desktop\backend.log`，一轮会话 9645 行）：
  整轮只有 2 次 `GET /api/plugins 200`。第一次紧跟 `market/installed` + `market/manifest`
  （= 点重试后首页才挂上），且**没有**伴随 `/api/health` → 说明那是**页内恢复**而非整页重载；
  第二次才是一次真正的整页重载。中间侧栏一直是坏的。
  单测也能原样复现：`pluginRoutes.catalog.test.tsx` 的 ★ 用例在改前输出
  `app: ready` / `nav: error`（改前 4 条红）。
- **对策**：状态收进模块级单例 + `useSyncExternalStore`，所有消费者订阅同一份，
  谁 `reload()` 都全体恢复；并给失败加**有预算的自动重试**（2s × 30 ≈ 60s，够冷启动；
  预算用完停下、按钮留给用户；成功或手动重试都重置预算）。
  改动 `b226a4f`，门禁 `web/src/lib/pluginRoutes.catalog.test.tsx`（7 条，
  已做变异测试：去掉自动重试 → 3 红；去掉上限 → 2 红；reload 不重置预算 → 1 红）。
- **普适教训**：
  1. **"缓存是单例"不等于"状态是单例"**。共享的读取结果 + 各自的状态 = 迟早分叉，
     而且分叉只在**首次失败**这类罕见路径上显形，平时全绿。
  2. **失败后的自愈能力要跟邻居对齐**。App 里的 health / voices 是 5s 轮询自愈的，
     清单却要用户手点 —— 同一屏里两种策略，用户只会认为"这块坏了"。
  3. 前端在"后端还没起来"时的第一次请求**失败是常态**，别把它当异常路径设计。

### §8.30 「就地改写素材」的工具**不收敛**：跑一遍就重写一次，体积逐次漂移 ✅本机实测（2026-09-22）

- **症状**：`tools/normalize_market_imgs.py` 第一遍写 24 张、第二遍**又全写一遍**，
  总体积从 280,047 漂到 278,531 字节。跑第三遍还会漂。视觉上看不出来，但
  "再跑一次应该什么都不改"这个最基本的性质不成立 —— 任何自动化/CI 里跑它都会抖。
- **根因**：两条叠加，缺一条都不会出问题：
  1. **存盘是不可逆的**：为压体积，`encode_png()` 会把 PNG 量化回调色板
     （`quantize(colors=256, FASTOCTREE)`）。量化后再读回来，像素值已经不等于写出去的那份。
  2. **"已居中"用了精确相等判定**：`bb[0] == (canvas[0]-cw)//2`。
     LANCZOS 缩放会在内容边缘留 alpha 渐变的抗锯齿像素，**量化又会把最外一列压到阈值以下**
     → bbox 比实际粘贴框偏 1px。于是"归一化过的图"永远判不出"已合规" → 每跑一遍重采样一次。

- **一眼判据**：**任何"就地改写素材/数据"的工具，都要自问"跑第二遍字节变不变"**。
  变，就说明它没有不动点 —— 而这类工具天然会被重复调用（CI、定时任务、别人手滑）。
- **证据**（本机实测）：
  - 25 张归一化后的图，只有 `diyin.png` 的 bbox 偏 1px：`(49, 68, 567, 549)`，
    `cw=518` 而目标 `want=519`；其余 24 张精确居中（`cw=ch=519`）。
  - 精确相等判定下 `md5sum -c` 报 `diyin.png: FAILED`（1 computed checksum did NOT match）。
- **对策**（`tools/normalize_market_imgs.py`）：
  1. 新增 `already-normalized` 分支：**已合规且已居中 → 一个字节都不写**。
     幂等靠"不做事"，而不是"算出一样的结果"。
  2. 居中判据留 `_CENTER_TOLERANCE_PX = 2` 的容差（2px/618px = 0.3%，肉眼不可见）。
  3. 测试钉住两条：`test_already_normalized_tolerates_one_pixel_bleed`（判据级，
     **变异测试守卫**）+ `test_second_run_writes_nothing`（文件级集成）。
- **★ 顺带一个"测试咬不住"的坑**：文件级那条测试**单独不足以**守住容差 ——
  它注入的是**硬边合成方块**，量化后边缘干净、正好落在目标尺寸上，**根本走不到
  "偏 1px"那条路**。变异 `_CENTER_TOLERANCE_PX = 0` 时它照样全绿。
  必须另写一条**判据级**用例（人为把内容右移 1px 再断言判为 skip），
  变异后才会红：`assert 'normalized' == 'skip'`。
  **教训：变异测试不是为了"证明测过"，而是为了暴露"这条测试其实没走到出问题的那条路"。**
- **普适教训**：
  1. **幂等 ≠ 确定性**。链路里只要有一处不可逆步骤（有损编码、量化、四舍五入落盘），
     "重算出相同结果"就不成立，只能靠"识别出无需改动 → 提前返回"。
  2. **几何量的判据必须带容差**。经过重采样 + 有损编码的 bbox / 尺寸，不可能精确等于理论值。
     容差不是"放宽标准"，是**正确性的一部分**。
  3. 真实素材里最刁的那个样本（这里是 `diyin.png`）往往只有 1/25 会触发，
     手写的合成样本大概率造不出它 —— 所以**跑真实数据 + 逐字节对账**不可省。

### §8.31 `github.com` 的 **DNS 解析结果**被阻断 ≠ 服务不可达 ✅本机实测（2026-09-22）

- **症状**：`git clone` / `git push` 报
  `Failed to connect to github.com:443 after 21085 ms: Could not connect to server`，
  而同一台机器上 `curl https://cdn.jsdelivr.net/...` 正常（HTTP 200）、
  `nslookup github.com` 也能正常解析出 IP。看着像"网络断了"或"GitHub 挂了"。
- **根因**：被阻断的是**那个 IP**，不是域名。本机 DNS（`dns3.hstc.edu.cn`）
  把 `github.com` 解析到 `20.205.243.166`，该 IP 的 443 超时；
  而 GitHub 的常规 IP 段全部可用：

  | 目标 | 结果 |
  |---|---|
  | `github.com:443`（DNS 给的那个 IP） | ✗ 超时 |
  | `github.com:443` @ `140.82.112.4 / 113.4 / 114.4 / 121.4` | ✅ HTTP 200 |
  | `github.com:22`、`ssh.github.com:443` | ✅ 通 |
  | `api.github.com:443`、`codeload.github.com:443` | ✅ 通 |

- **一眼判据**：**域名不通时，先换 IP 试一次再下结论**。
  同一个域名背后是一组 IP，"域名连不上"和"服务不可达"是两件事。
  （本机还撞过一次更迷惑的：`raw.githubusercontent.com` 0.01s 就失败 =
  DNS 层面就没了，而 `cdn.jsdelivr.net` 正常 —— 两个 CDN 走的完全不同的路。）
- **对策**：
  ```bash
  # 找能通的 IP
  for ip in 140.82.113.4 140.82.121.4 140.82.112.4; do
    timeout 25 git -c http.curloptResolve="github.com:443:$ip" \
      ls-remote --heads https://github.com/mouxu66/voice-market-assets.git && break
  done
  ```
  `http.curloptResolve` 需要 **Git ≥ 2.44**（本机 2.55 实测可用）。
  连接走指定 IP，**主机名仍是 `github.com`**，所以 TLS 证书照常校验，
  不需要 `http.sslVerify=false` 这类危险开关。已固化进
  `tools/market_imgs_push.py --git-resolve <IP>`（clone 与 push 都生效）。
- **★ 第二个坑：同一 IP 也是时通时不通**。实测 `140.82.113.4`
  前一次 `ls-remote` 成功、几分钟后 push 就超时；换 `140.82.121.4` 才推上去。
  所以**不能"找到一次通就固定用"**，要写成**多 IP × 多轮重试**。
- **普适教训**：
  1. 把"网络不通"当结论之前，先分清是 **DNS / TCP / TLS / 应用层**哪一层断的 ——
     本次 `nslookup` 正常（DNS 没问题）、换 IP 就通（TCP 层被针对），一秒就能定位。
  2. 这类环境的绕过手段要**写进工具并注释清原理**，别留在一次性命令行里：
     否则下次（或下一个人）会重新踩一遍，还可能误用 `sslVerify=false` 这种下策。

### §8.32 偶发假红的真因是**环境资源不足**，报出来的却是产品缺陷 ✅本机实测（2026-09-22）

- **症状**：全量跑偶发红，
  `test_offline_vc_infer_pth_guard.py::test_real_voice_weights_load_under_strict_mode`
  报的是：

  ```
  AssertionError: 连一个正常音色都没能加载 —— 严格模式可能真的挡了正常模型，
  那才该考虑放宽（这是必须正面回答的问题，别直接改测试）。
  被跳过的：['kangaroo_v2.pth', 'katoong_lanyangyang.pth', 'katoong_manbo.pth']
  ```

  它把 3 个真实音色**全部**算成「加载失败」→ `checked == 0` → 报红。
  单跑该文件**绿**；全量 3 次：**2 红 1 绿**。
  更坏的是这条报错本身在**指错方向** —— 它让人去怀疑 `weights_only=True`
  这个安全边界（那正是本文件存在的意义），而真因与它毫无关系。
- **根因**：**可用内存不足**。两条叠加：
  1. 本机物理内存 15.2GB，但常驻程序占掉大部分，**可用只有 ~4.3GB**；
  2. pytest 进程在 **collect 阶段**就因本模块顶层的 `pytest.importorskip("torch")`
     **常驻 ~600MB**（实测：不 import torch 时峰值 161MB，import 后 638MB），
     再连续 `torch.load` 三个 57MB 权重 —— 每个解包后的**瞬时占用远超文件体积**
     （`RSS 采样在 teardown 时刻，看不到这个瞬时峰值`）→ 顶到上限 →
     `torch.load` 抛 `MemoryError: DefaultCPUAllocator` →
     被 `load_checkpoint` 统一包成 `RuntimeError` → 三条全 skip → `checked == 0` → 红。

- **★ 排除过程（5 个假设被逐个证伪，这才是本次真正的成本）**：

  | 假设 | 结论 | 依据 |
  |---|---|---|
  | `market_install` 早绑定 `RVC_ROOT`，monkeypatch 失效 | ✗ 证伪 | 它写 `cfg.RVC_ROOT`（每次读），monkeypatch 有效 |
  | `test_market_search_install.py` 污染真实 `D:/RVC` | ✓ 历史属实，**现已修** | 坏文件时间戳 `2026-09-19 00:18:43`；`ast` 扫描证明现所有 `InstallManager` 用例都带 `fake_rvc` |
  | 线程泄漏（`Thread-512` 看着像 512 个线程） | ✗ 证伪 | 全量峰值**存活 20**、结束**存活 1**（MainThread）；`Thread-N` 是**创建序号**，不是存活数 |
  | `TestClient` 不用 `with` 泄漏 portal | ✗ 证伪 | 单跑该文件峰值线程 2、结束 1 |
  | 测试写真实目录 | ✗ 证伪 | `test_offline_vc_infer.py` 全部写 `tmp_path` |

  **实证手段**：写了个 pytest 取证插件（`pytest_runtest_teardown` 里采样
  `psutil.Process().memory_info().rss` + `threading.active_count()`，创新高才记），
  两次全量对照 —— 第 1 次崩在 56%，第 2 次 100% 跑完零失败、峰值 RSS 814MB / 峰值线程 20。
  复现尝试也全部失败：单跑绿、只跑到本文件的 40 个文件范围绿、人为占 1.5GB 内存后单跑绿
  → 确认为**偶发**（系统内存波动），不是确定性缺陷。
- **对策**（`test_offline_vc_infer_pth_guard.py`，三处对症）：
  1. `checked >= 3` → **只验 1 个就 `break`**：本用例的目的是"证明严格模式不挡正常模型"，
     1 个正常模型即可成立（"真实格式能被严格模式接受"另有机器无关的
     `test_strict_load_accepts_a_real_shaped_rvc_checkpoint` 覆盖）；
  2. 每加载一个就 `finally: del got`，**不把多个权重的峰值叠在一起**；
  3. **区分"内存不足"与"文件坏了"**：前者是环境问题 → `pytest.skip`；
     后者才是产品问题 → 照常报红。判据是 `"MemoryError" in msg or "out of memory" in msg
     or "DefaultCPUAllocator" in msg`。
- **★ 普适教训**：
  1. **"偶发红"必须区分「产品缺陷」与「环境噪声」，而且要在测试里显式区分** ——
     不区分，它会一直以"产品缺陷"的样子出现（这里还带一句会把人带偏的结论）。
  2. **测试的资源占用也是被测对象的一部分**：`importorskip("torch")` 在模块顶层
     = collect 阶段就常驻 600MB；一条用例连加载 3 个权重 = 3 个瞬时峰值叠加。
     **"这条测试在低内存机器上还跑得动吗"要当成设计约束**。
  3. **失败信息必须指向真因**。原实现把所有失败归成一句话，代价是它红的时候
     在**误导**人去做一件危险的事（放宽 `weights_only`）。改成分类后，
     报错本身就能告诉人"这是内存问题，去关几个程序"。
  4. 顺带一条工具经验：**`-q -q` 会写成 `-qq`，那会抑制 FAILURES 段**，
     于是"有 FAILED 行但没有 traceback"，查半天查不动 —— 要 `--tb=short` 显式要求。

- **★ 同源的第二条（同一批全量里一起红的）**：`test_pet_market.py::test_install_remote_gif_skin`
  报 `OSError: [WinError 1450] 系统资源不足，无法完成请求的服务。`
  —— 也是环境资源耗尽，不是产品缺陷。
  - **取证靠的是历史 junit**（`--junitxml` 的输出，1267 tests / 2 failures）里
    留着**两条失败的真实异常**：
    `DefaultCPUAllocator: not enough memory` + `MemoryError` 与 `WinError 1450`。
    而那两次全量的 stdout 日志用的是 `-qq`，**只有一个被截断的 `OSE...`**，什么也查不出来。
    → **"精确计数用 `--junitxml`"这条纪律还有第二个好处：它把 traceback 也留下来了。**
  - `WinError 1450 = ERROR_NO_SYSTEM_RESOURCES`；同族还有 `8 = ERROR_NOT_ENOUGH_MEMORY`、
    `1455 = ERROR_COMMITMENT_LIMIT（页面文件太小）`。三者的共同点是**"这次跑不动"**，
    而不是**"这环境没有"**（后者是 `WinError 2 / FileNotFoundError`）。
  - **对策**（`m2_server/conftest.py`）：加 session 级夹具 `ffmpeg_run`，
    统一"测试里跑 ffmpeg 造素材"的入口（`test_pet_market` / `test_pet_scan` /
    `test_pet_skin_build` 三处共用），只豁免上面那三个错误码，其余 `OSError` 照常抛。
    ```python
    _RESOURCE_EXHAUSTED_WINERRORS = {8: "...", 1450: "...", 1455: "..."}

    def _run(args, timeout=120):
        try:
            return subprocess.run([ffmpeg_bin, *args], capture_output=True, text=True, timeout=timeout)
        except OSError as exc:
            kind = _RESOURCE_EXHAUSTED_WINERRORS.get(getattr(exc, "winerror", None))
            if kind is None:
                raise                      # ← 尤其 FileNotFoundError：那是真问题
            pytest.skip(f"系统资源不足…{kind}…这是环境问题，不是产品问题")
    ```
  - ⚠️ **这里刻意不跟 `missing_local` 的"CI 上 fail"口径**：`missing_local` 处理的是
    **确定性缺失**（ffmpeg 没装 ⇒ 环境准备一定坏了），而这里是**瞬时资源竞争** ——
    同一份环境上一次绿、这一次红，**没有确定性判据**。在 CI 上 fail 只会把偶发噪声
    变成必现阻塞，反而更掩盖真问题。
  - **两条守卫**（`test_pet_market.py` 末尾）：三个错误码都要 skip（参数化）
    + **对照**：`WinError 2` 必须照常抛（防「资源不足就 skip」退化成「什么 OSError 都 skip」）。
    变异验证：关掉判定 → 前一条红 3 个；放宽成"全部当资源不足" → 对照那条红。

- **★ 一条实用小坑**：`--junitxml=/d/tmp/x.xml` 这种 **`key=value` 形式**的参数
  **不会被 Git Bash 转换成 Windows 路径**（它只转换看起来像独立路径的参数），
  于是 pytest 收到字面量 `/d/tmp/x.xml` → Windows 解析成 `D:\d\tmp\x.xml`。
  结果：**日志里一切正常，文件却"不见了"**。写 `key=value` 时一律用 `D:/...` 形式。

### §8.33 变异测试的"红"可能是**假红**：`pytest.raises(X)` 拿到别的异常会**静默变成跳过**，退出码仍是 0 ✅本机实测（2026-09-22）

- **症状**：写了一条对照守卫（`test_broken_file_still_reports_red`），断言
  "文件坏了要报 `AssertionError`"：

  ```python
  with pytest.raises(AssertionError, match="严格模式可能真的挡了正常模型"):
      test_real_voice_weights_load_under_strict_mode()
  ```

  做变异测试（把 OOM 判定放宽成"所有失败都算内存不足"，本应让这条守卫红）时，
  结果是 **`s`（跳过）**，不是 `F`（失败）—— **退出码 0，CI 全绿**。
- **根因**：`pytest.raises(X)` 只在异常**是 X** 时通过；拿到**别的**异常它会
  **原样放行**。而内层这次抛的是 `pytest.skip` 的 `Skipped`（继承 `BaseException`，
  不继承 `Exception`）→ 从 `pytest.raises(AssertionError)` 里逃逸出去 →
  **pytest 把整条用例标记为"跳过"** → 跳过在 CI 里通常**不算失败** →
  守卫**静默失效**，而且看起来还挺正常（有个 `s`，很容易被忽略）。
- **一眼判据**：**变异测试不能只看"有没有 FAILED 行"，要看退出码**。
  `s` / `x` / `X` 都不是失败；只有 `F`（和 `E`）会让 pytest 返回非 0。
- **对策**（已落地）：一律先抓成 `BaseException`，再**显式断言异常类型**：

  ```python
  def _run_inner() -> BaseException:
      with pytest.raises(BaseException) as ei:   # 故意抓全部
          test_real_voice_weights_load_under_strict_mode()
      return ei.value

  def _assert_exc_is(exc, want):
      assert isinstance(exc, want), (
          f"内层抛的是 {type(exc).__name__}：{exc}\n期望 {want.__name__} —— "
          f"异常类型不对说明走错了分支（尤其当它是 skip 时，会被 pytest 静默当作「跳过」）。"
      )
  ```

  实测：改法后两组变异都**真红**（`F`，退出码 1），且报错把两种异常类型都打了出来。
- **普适教训**：
  1. **`pytest.raises(具体类型)` 是"宽松"的**：它只保证"如果抛的是 X 就算过"，
     对"抛的是别的"没有任何约束。写"反向守卫"（断言某分支**不该**被走到）时，
     必须把"抛的不是 X"也变成失败 —— 用 `BaseException` + 显式 `isinstance`。
  2. **`skip` 在 pytest 里是"成功"**。任何用 skip 表达"环境不适用"的机制，
     都有被误用成"掩盖失败"的风险 —— 所以要配一条**对照守卫**
     （本文件里就是 `test_broken_file_still_reports_red`），
     钉住"该红的时候仍然红"。
  3. 做变异测试的**收尾动作**：看退出码 + `grep MUTATION` 确认无残留
     （本次也靠它发现过"变异忘还原"）。

### §8.34 门禁"假红"的第三层：**你自己并发跑了第二次全量** —— 判据是**耗时** ✅本机实测（2026-09-22）

- **症状**：`git push` 被 `.githooks/pre-push` 拦下，而输出**只有这几行**：

  ```
  [FAIL] pytest         98.2s
  [SKIP] 未执行（前一项失败）：web
  结果：未通过（pytest）
  ```

  但**手动**跑同一条 `tools/check.py --only pytest` → **PASS（251.7s）**。
  同一份代码、同一条命令，hook 里红、手动绿。

- **★ 判据（本次最有用的一条）：先看耗时，别先读用例。**
  全量 pytest 在本机稳定在 **231–252s**（`--junitxml` 三次基线 233.0 / 231.7 / 236.5）。
  hook 里只有 **98.2s** ⇒ 这**不是**"某些用例失败"，而是**跑到约 40% 就被打死了**。
  **凡「FAIL + 耗时显著短于基线」，先怀疑进程被外部干掉**（OOM / `SystemExit` /
  被 kill / 资源耗尽），而不是去逐个读用例 —— 后者的方向从头到尾都是错的。

- **根因：自己制造的资源竞争。** 当时后台还有一个 `git push` 任务在跑
  （它的 pre-push 正在跑全量 pytest），我**又并发**手动跑了一次全量 ——
  两个全量 pytest 同时顶层 `import torch`（各常驻 ~600MB）再各自 `torch.load` 权重，
  本机可用内存只有 ~4.3GB，直接见底，**后启动的那个中途死掉**。
  这与 §8.32 是**同一条资源轴**，只是压力来源不是"机器本来就不够"，
  而是"**我自己又开了一份**"。

- **对策**：
  1. **一次只跑一个全量。** 要复现门禁就**单独**跑；要推送就**别同时**手动跑。
     诊断前先自问一句"现在还有别的全量在跑吗"。这类假红**代码侧无缺陷**，
     改代码只会白改。
  2. 复现门禁要把**两步都跑全**：hook 是 `--ci-fidelity`（干净 venv，约 3 分钟）
     **加** 全量 `check.py`（约 4.5 分钟），共约 **9.5 分钟**。
     只跑第二步，资源画像与 hook 不一致，结论不可信。
  3. 日志**不要 `| tail -4`**。本次第一轮就是被 `tail` 截掉关键输出，
     只剩一行 `[FAIL] pytest`，白绕了一大圈才回头去拿完整日志。
     **落盘到文件再读**（`> log 2>&1`），要截也只截自己的汇总。

- **实测（2026-09-22）**：干净环境下完整复现 hook 两步 →
  `--ci-fidelity` **PASS**、全量 `[PASS] pytest 249.9s`、10 项全过；
  随后正式推送 → hook `[PASS] pytest 251.7s` 全过，
  `f28c457..06f7b74  master -> master`（**一次成功**）。
  网络侧按 §8.31 走 `-c http.curloptResolve=github.com:443:140.82.116.4`；
  本次包只有 **1.24MB**（327 文件 / +39603 −8122），体积不构成风险。

### §8.35 `branch.<name>.remote/merge` 丢了 → pre-push **每次都误判「首次 push」**，白跑 5 分钟 ✅本机实测（2026-09-22）

- **症状**：每次 `git push` 的 hook 第一行都是

  ```
  [pre-push] 首次 push（尚无可用上游分支） → 复刻 CI 环境再跑一遍（约 3 分钟）
  ```

  于是**每次推送固定约 9.5 分钟**（`--ci-fidelity` 约 5 分钟 + 全量约 4.5 分钟），
  哪怕这次只改了一个 markdown 文件。

- **根因**：`git rev-parse --abbrev-ref --symbolic-full-name '@{u}'` 返回 **rc=128**
  （`fatal: no upstream configured for branch 'master'`）。
  ★ **三个检查互相独立，只看一个会误判**：

  | 检查 | 本次结果 |
  |---|---|
  | `refs/remotes/origin/master` 是否存在 | ✅ 存在（`git for-each-ref refs/remotes/`） |
  | `remote.origin.fetch` 是否正常 | ✅ `+refs/heads/*:refs/remotes/origin/*` |
  | `branch.master.remote` / `branch.master.merge` | ❌ **两者都缺失**（只剩 VS Code 写的 `branch.master.vscode-merge-base=origin/master`） |

  于是 hook 的 `case "$upstream" in ""|*'{'*)` 把它判成「没解析出来」→ 走「首次 push」分支。
  疑似 `filter-repo` 重写留下的（hook 注释里 2026-09-13 那次同源）。

- **修**：`git branch --set-upstream-to=origin/master master`
  （**纯本地 `.git/config` 改动**，不进仓库，可 `--unset-upstream` 回退）。
  实测：修后同一条 `git push` → **5 分 7 秒**（正确跳过 `--ci-fidelity`），一次成功。

- **教训**：凡「**按上游 diff 决定跑多少**」的门禁，都要先确认上游**真的解析出来了** ——
  配置丢了**不报错**，只是每次都跑最贵的那条路径。
  看到「首次 push」这种话，先 `git branch -vv` 看一眼有没有 `[origin/master]`。

### §8.36 「只 patch `config.OUTPUTS_DIR`」挡不住预览写入：`MARKET_DIR` 是**导入时早绑定**的模块常量 ✅本机实测（2026-09-22）

### §8.37 早绑定泄漏的第二层：per-test 隔离挡不住「活过 teardown 的线程」，而守卫还会因此**假绿** ✅本机实测（2026-09-22）

- **症状（§8.36 修完之后仍在发生）**：§8.36 给 `test_market_search_install.py` 的 `fake_out`
  补了 `patch(mp, "MARKET_DIR", ...)` 并改 `autouse`，该文件 52 passed、全量也绿。
  但**下一次跑全量**时真实目录又被动了两处：
  - `outputs/market/` 多了 **8 个夹具名** sidecar（`guard_rb` / `kill_me` / `kill_bak` /
    `para` / `no_idx` / `test_voice` / `resume_voice` …），其中 `guard_rb_preview.json`
    **正是我那条新守卫自己的音色名**；
  - `outputs/market/imgs_cache/.revision` 被覆写成远端版本号 `20260922T080040Z`；
  - `media/ft/dstkoi/status.json` 被改写成测试数据
    （`{"stage": "error", "error": "训练退出码 0…"}`）—— 第三处，此前没人发现。
    ⚠️ **2026-09-22 同日更正**：本节初稿把这处写成「**用户真实微调任务**的状态」，
    **措辞过重** —— 该文件的 `voice_id` 就是 `dstkoi`，即
    `tests/test_finetune_resume.py:29` 的**夹具名**，内容是测试跑出来的，不是用户的微调任务。
    **但泄漏结论完全不变**：要害是**位置** —— 测试确实往**用户数据根 `media/`** 里写了东西，
    这跟写进去的文件叫什么名字无关。（该文件已于同日作为测试残留清出工作区。）

- **根因一：时序（这是本节的重点）。** 这些写入**不是**用例自己写的，而是来自
  **活过用例 teardown 的后台线程**：
  - `market_preview.generate()` 起 daemon 线程，`_worker` → `_maybe_backoff()`
    还会 `sleep(_BACKOFF_S = 20)` 之后**再写一次**；
  - `finetune._train_job()` 起的训练线程在用例结束后才落 `status.json`。

  monkeypatch 在**用例 teardown 就还原了**，于是线程后段的写入落回**真实**目录。
  ★ 所以「单跑一个文件」**根本看不出来** —— 进程退出会把 daemon 线程杀掉。
  必须"这个文件跑完还有别的文件在跑"才复现：

  ```
  pytest tests/test_market_search_install.py tests/test_audition_api.py   # → 立刻泄漏 3 个
  pytest tests/test_market_search_install.py                            # → 0 个（假绿！）
  ```

  ⇒ **判据：「单文件绿、多文件红」的污染类问题，第一嫌疑是「异步写入活过了 teardown」。**

- **根因二：修错了地方。** per-test patch 只覆盖"用例运行期间"，而早绑定常量是
  **导入时**求值的。要治本，就得让**导入那一刻**的 `cfg.OUTPUTS_DIR` / `cfg.MEDIA_DIR`
  就不是真实目录。`config.py` 本来就支持这两个环境变量：

  ```python
  # m2_server/conftest.py —— 必须放在任何 app 模块被导入之前
  _VM_TEST_OUTPUTS = tempfile.mkdtemp(prefix="vm-test-outputs-")
  os.environ["VM_OUTPUTS_DIR"] = _VM_TEST_OUTPUTS
  _VM_TEST_MEDIA = tempfile.mkdtemp(prefix="vm-test-media-")
  os.environ["VM_MEDIA_DIR"] = _VM_TEST_MEDIA
  ```

  放 `m2_server/conftest.py`（而不是 `tests/conftest.py`）是因为后者**导入期就会 `import config`**，
  晚一步就来不及。同文件的 `VM_WARMUP` / `VM_WECHAT_RESTART` 早就是同一手法。
  ⇒ **两行环境变量，替掉 40+ 处早绑定常量各自的补丁**，且以后新增模块**自动被覆盖**（不会漏）。

- **★ 根因三（最值钱）：我的第一版守卫是假绿。** 它扫出所有早绑定常量、在用例里
  `import` 它们、断言值不在真实 `outputs/` 下 —— 但**变异测试里它没红**
  （把 `VM_OUTPUTS_DIR` 整行注释掉，它仍然绿）。原因：`importlib.import_module(...)`
  是**在用例内**才导入的，而 `tests/conftest.py` 的 autouse 夹具此时已把 `cfg.OUTPUTS_DIR`
  换成本次用例的 `tmp_path` ⇒ 那些常量**绑定到 tmp_path**，永远"看起来正确"。
  这正是本项目的老朋友：**探针被运行时环境满足**（同族前科：`web_dist` 一致证明不了 dist 是新的、
  拿"安装目录下有没有 `outputs/`"当数据根探针、`--fast` 绿）。
  **修**：把取值挪到 **session 作用域**（`@pytest.fixture(scope="session", autouse=True)`）——
  它跑在任何 function 作用域 monkeypatch **之前**，拿到的才是"模块级早绑定会捕获到的那个值"。
  改完两组变异**双双真红**。
  ⇒ **判据：守卫读到的值，如果可能被「运行环境」摆正，那它就不是在验不变量。**

- **验证**：

  | 项 | 结果 |
  |---|---|
  | 两文件复现（修前泄漏 3 个） | **0 新增** |
  | 真实 `imgs_cache/.revision` | 不再被改（mtime 与内容都不动） |
  | `test_finetune_resume.py` + 任一文件 → 真实 `media/ft/dstkoi/status.json` | 前后 `(size, mtime)` **完全一致** |
  | **跑一遍完整全量**，前后对 `outputs/` + `media/` 做 1351 文件的 `(path,size,mtime)` 快照 | **diff 为空**（真实数据一个字都没动） |
  | 泄漏落点 | 改到 `%TEMP%\vm-test-outputs-*\` 与 `%TEMP%\vm-test-media-*\` |
  | 守卫变异（注释掉 `VM_OUTPUTS_DIR`） | `test_import_time_data_dirs_are_isolated` + `test_env_vars_are_the_mechanism` **双双红** |
  | 全量回归 | `[PASS] pytest 251.0s`、`EXIT=0`（**放宽到 media 后仍全绿**） |

- **一句话**：**per-test 的隔离只管"用例运行期间"；凡是「异步写入 + 导入时早绑定」，
  隔离必须放在「导入之前 / session 全程」。**
  新增守卫：`m2_server/tests/test_output_isolation.py`。

## 8.38 死参数：客户端发了、端点不读 —— 不报错、不生效、只误导

**症状**：`cascade_stream` 给 worker 的 `/tts` 与 `/tts_stream` 都发了 `"fast": True`，
注释还写着「短句用 beam_size=1 + 免时间戳，短块延迟约降一半」—— 读代码的人会以为它生效了。
**实际上这两个端点根本不读它**，那两行是**死参数**：不报错、不生效、只误导。

**为什么难发现**：死参数不会让任何东西变红 —— 没有类型检查、没有契约测试，
HTTP 端点收到多余字段默认静默忽略。它只会在「你以为做了优化、但延迟没降」时
以「性能不如预期」的形式冒出来，而那时你根本不会怀疑到这一行。

**定位方法：两边对账。** `fast` 到底属于谁，grep 一遍就能定：

| 发送点 | 目标端点 | 端点读吗 | 结论 |
|---|---|---|---|
| `cascade_stream.py` 的 `asr()` | `/transcribe` | ✅ `body.get("fast")` | 有效 |
| `qwen3_tts.py` 的 `transcribe()` | `/transcribe` | ✅ | 有效 |
| `tagging.py` | `/transcribe` | ✅ | 有效 |
| `cascade_stream.py` 的 `tts()` | `/tts` | ❌ | **死参数** |
| `cascade_stream.py` 的 `tts_stream()` | `/tts_stream` | ❌ | **死参数** |

四重证据（缺一不可 —— 「端点不读」很容易被某个中转层偷偷读掉）：
1. `/tts` 与 `/tts_stream` 的函数体里**没有** `body.get("fast")`；
2. 两者都走 `_gen_kwargs(body)`，其**白名单**是
   `do_sample/max_new_tokens/top_k/temperature/top_p/repetition_penalty` —— 不含 `fast`；
3. **后端自己**构造 `/tts` payload 时（`qwen3_tts.py` 的 `_tts_do`）**根本没发 `fast`**
   —— 这条最有力：同一个仓库里的另一个调用方就不发它，说明它不属于该端点的契约；
4. `tests/` 里没有任何断言钉住这两处。

**`fast` 的真实归属**：它是 **ASR（Whisper 解码）参数** ——
`_transcribe()` 里 `beam_size=1, best_of=1, condition_on_previous_text=False, without_timestamps=True`。
而 **TTS 侧没有 fast 档可言**：faster 后端自带 CUDA Graph，已是最快路径
（`_tts_blocking` 的 docstring 自己写着「等价旧 fast_tts 引擎」）。
⇒ 所以「让端点真读 `fast`」不是修 bug，而是**新造一套 TTS 侧语义**。**正解是删掉死参数。**

**修法与守卫**：删掉那两行，并加一条**通用契约守卫**
（`m2_server/tests/test_tts_payload_contract.py`）：

> AST 两边对账 —— worker 侧取每个 `@app.post("/x")` 读了哪些字段，
> client 侧取每个 HTTP 调用发了哪些字段，断言 **「client 发的 ⊆ worker 读的」**。

覆盖全仓「后端 → worker」的 **3 条链路**：`cascade_stream.py`（`requests.post`）、
`qwen3_tts.py`（`_post` 封装）、`finetune.py`（`_worker_post` 封装）。

★ **字段提取必须做两件「完整性」工作，少任何一件都会假红**：
1. **跟随委托** —— `/analyze` 端点只写 `body = await req.json()`，随后把 body 交给
   `_analyze_blocking(body)`，**字段是在辅助函数里读的**。只看端点函数体会得到**空字段集**，
   于是客户端发的任何字段都成了「端点不读」→ 假红。
2. **白名单展开** —— `/tts` 通过 `_gen_kwargs(body)` 读一组**动态 key**
   （`for k in ("do_sample", "max_new_tokens", …)`）。这种「读了但 key 是变量」的写法，
   要能把白名单提取出来并进接受集，否则客户端发 `temperature` 这类合法字段也会假红。

★ **client 侧必须限定 `requests.` 前缀**：`@router.post("/ft/upload")` 的 AST 同样是
`Attribute(attr="post")` —— 只看 `attr` 会把 `finetune.py` 里 **10 个 `/ft/*` 路由定义**
误判成 HTTP 调用（实测踩过：审计脚本报了 10 处假的「worker 里没有这个端点」）。

**变异测试（六组全真红）**：

| 变异 | 结果 |
|---|---|
| 客户端把 `fast` 加回 `/tts` payload | `test_client_fields_are_accepted_by_worker` + `test_fast_is_only_sent_to_transcribe` 红 |
| worker 的 `/tts` 端点开始读 `fast` | `test_tts_endpoints_do_not_read_fast` 红 |
| 客户端给 `/tts_stream` 加一个端点不认的字段（`turbo`） | `test_client_fields_are_accepted_by_worker` 红 |
| 破坏「跟随委托」（`_analyze_blocking(body)` → `dict(body)`） | `test_extractor_follows_delegation` 红 |
| 破坏「白名单展开」（`for k in (…)` → `for k in sorted(…)`） | `test_extractor_expands_dynamic_whitelist` 红 |
| 去掉 `requests.` 前缀限定 | `test_route_definitions_are_not_mistaken_for_calls` 红 |

⇒ **6/6 真红**。后三条钉的是「**提取器自己会不会退化**」，比前三条更值钱 ——
它们防的是「守卫悄悄变成永远绿的摆设」。

⚠️ 守卫还必须带**自检**（`test_guard_actually_parsed_something`）：AST 解析器若什么都没扫到，
「client ⊆ worker」会**空跑即绿** —— 这是守卫假绿的标准形态（同 §8.36/§8.37）。

**附带发现（同族）**：`/tts` 的 `X-Fast-TTS` 响应头在**成功路径上恒为 `"1"`**
（`_tts_blocking` 硬编码 `return wavs, sr, True`，`_tts_style_blocking` 成功分支同样 `True`），
而 `cascade_stream` 会读它 → 那个 `fast` 变量**恒真、不携带区分信息**。
头说的是实话，但恒成立就没信息量 —— 与「凡探测环境的判据都要问它会不会被运行时满足」同族。

## 8.39 清理数据目录：判据不能是「名字像不像调试」，必须是「有没有东西引用它」

**症状（我自己犯的）**：清理 `outputs/` 存量产物时，我把 `meanvc2_ab_archive/` 与
`seedvc_sweep/` 当调试产物移走了 —— 只因为名字里有 `ab` / `sweep`，看着像实验垃圾。
**实际上它们是有意留档**：`meanvc2_ab_archive/` 含 `README.md` + 10 个测量脚本 +
`input/`/`output/`；`seedvc_sweep/` 含 `report.md`（结论建议）+ `results.json` + A/B 试听。
而且**文档明确引用它们**（`docs/ROADMAP.md`、`docs/product/research/m1e_*.md` **3 处**，
措辞是「测量脚本与 A/B 音频**归档**在…」）。

**根因**：分级判据用的是「目录名 + mtime + 体积」这些**外观特征**，没有查**引用关系**。
`outputs/` 这类目录里，同名同形的两堆文件可能一堆是垃圾、一堆是留档，**外观上分不出来**。

**修法：清理前先 grep 引用，并把「引用」再分成两类**：

```bash
# ① 文档引用（docs/ 与根 *.md）—— 最强信号：有人指望它在那里
grep -rn "outputs/<目录名>" docs/ *.md
# ② 代码引用 —— 但要看是「产出」还是「消费」
grep -rn "outputs/<目录名>" --include=*.py .
```

- **文档引用** ⇒ 视为**留档**，默认**保留**（`meanvc2_ab_archive` / `seedvc_sweep` 属此类）。
- **代码引用**要再分：
  · 「产出目录」（脚本 `makedirs` / `--out-dir` 默认值）⇒ 移走**不影响运行**，脚本会重建
    （`experiments/tools/*.py` 的 `outputs/ab_test`、`seedvc_ft_eval.py` 的默认 out-dir 属此类）；
  · 「消费路径」（代码 `open()` / 读文件）⇒ **绝不能动**。
- **脚本名 ≠ 目录名**：`docs/犯错指南.md` 里出现的 `stress_live_test` 是**工具脚本名**，
  与 `outputs/stress_live/`（压力测试**产物**目录）毫无关系 —— grep 命中要**打开那一行看**。

**另一个反复踩的点：文档里对文件的引用会随清理失效。**
本文件附录原本写「截图都在 `outputs/`」，而那些 `wx_*.png` 正是被清走的东西。
⇒ **清理后必须把文档里的路径一并更新**（本次改成指向备份目录），
否则下次有人按文档去 `outputs/` 找图会一头雾水。

**执行纪律**（本次实际用的，可复用）：
1. 只读扫描 → 分级（A 明确调试 / B 运行产物 / C 产品数据与留档）；
2. **grep 引用**（本节新增，要放在「定级」之前 —— 本次就是漏了这步）；
3. dry-run + **反向校验**（把保留项当关键词 grep dry-run 清单，命中应为 0；非 0 要逐行核实是否无害子串）；
4. **移到库外备份**而不是直接删（同盘 rename 秒级、完全可逆；⚠️ 同盘移动**不释放磁盘空间**）；
5. 前后对账（`du -sh` + `find -type f | wc -l`，注意区分「顶层项数」与「累计文件数」两个数）；
6. 跑一次完整门禁，确认没破坏东西。

★ 一句话：**「像垃圾」不是判据，「没人引用」才是。** 清理前先 grep，清理后改文档。

## 8.40 「跨插件 tab」是一整类 bug，而门禁的两条判据**同时**漏了它 ✅本机实测（2026-09-23）

### 症状

一个页面属插件 A（路由随 A 一起消失），但页内某个 tab / 面板打的是**另一个可关插件 B** 的端点。
关掉 B 之后那块 UI 照旧渲染：轻则卡片一路显示「检测失败」，重则**整页空掉**。
而 `tools/audit_endpoint_ownership.py --check`、pytest、vitest **全是绿的**。

实测到的三处（都由「在页内打的是别的插件」造成）：

| 宿主页（宿主插件） | 打的可关插件 | 用户看到什么 |
|---|---|---|
| `pages/Live/index.tsx`（sound.rvc-live） | `sound.ft` 的 `getRvcGenStatus`/`listRvcDataset` | ★**实时变声页整个空掉**：它们与 `listRvcVoices` 同在一个 `Promise.all` 里，关掉 ft 让整个 tick reject、被 `catch` 吞掉 → `setVoicesInfo` 永不执行 → 连音色列表都没有 |
| `pages/Audition/index.tsx`（sound.audition） | `sound.rvc-live` 的 `rvcLive*` | 「一个个实时试」整档不可用（首屏 effect 里就 `refreshLive()`） |
| `pages/Tts/index.tsx`（sound.tts） | `sound.ft` 的 `getRvcModel`（经 `RvcDatasetCard`） | 卡片一路「检测失败」，诱导用户**去重训一个其实已经训好的模型** |

**最易忽略的一点**：这些**当天就是可达的用户 bug** —— 设置页点一下「标准」预设就会关掉 `sound.ft`
（`PRESETS["standard"]` 不含它），而全新安装（无 `plugins.json`）反而是 19 个全开。

### 根因（两条，都在审计工具里，且互相独立）

**A. 豁免条件不对称。** `find_ungated_core_entries()` 第一行就是

```python
if not is_core.get(pid):
    continue  # 非核心路由：整条路由会随插件消失，不需要页内门控
```

那句推断只覆盖了**宿主被关**这一个方向（=> 整页没了，确实不需要页内门控），
却漏了另一个同样可达的方向：**宿主开着、被它托管的插件关着**。
`sound.ft` 不被 `sound.workshop` 依赖（依赖方向是反的），所以「工坊在、微调关」完全正常，
但那个 tab 指向的 `finetune` 已经被卸载了。

⇒ **判断「注定同生共死」的正确依据不是「宿主是不是 core」，而是「该插件是不是宿主的 `requires` 闭包成员」**
（`enabled_ids()` 会把被依赖的插件复活，所以闭包内的 id 在页内永远不可能是缺口），
与宿主是核心还是可关**无关**。

**B. 归属链只有一条来源。** `load_client_funcs()` 只扫 `api/client.ts`。
凡绕开它自己 `fetch(BASE + "/x")` 的文件，在归属图里**根本不存在** ——
`pages/Effects/useEffects.ts` 打 `sound.effects` 的 `/effects/catalog`、`/effects/apply`，
而 **`client.ts` 里没有任何 effects 函数**（grep 为空）⇒ 整个 `sound.effects` 对审计不可见。

### 对策

1. 判据改成按 `requires` 闭包豁免（见上）；`find_ungated_core_entries` 收 `always_on` 参数。
2. 补 `load_raw_endpoints()`，用与 `load_client_funcs` 同一组正则扫全部 `web/src` 的裸 `fetch`/`xhr`。
   **解析不出来的路径静默跳过**：裸 `fetch` 里混着 `${base}/index.json`、`mediaUrl(...)`、blob 地址，
   报成「未定位」会淹没白名单机制。代价是「裸 fetch 的路径拼错」不报 —— 这是明确的取舍。
3. 页内修复照仓库既有范本 `pages/Tts/index.tsx`：
   `const ftOn = pluginVisible(catalog, "sound.ft")` + hook 收 `enabled`（`if (!enabled) return`）+ tab 条件展开。
   两处细节值得抄：**Audition 用「派生的 witMode」**而不是逐处加 `&& liveOn`（页面里那个判断有十来处，必漏）；
   **Live 把 ft 的调用从核心 `Promise.all` 里摘出去**（`ftOn ? getX() : Promise.resolve(null)`），
   而不是指望 `catch` 兜住 —— 兜住的结果就是整页空掉。
4. 门禁：`m2_server/tests/test_audit_endpoint_ownership.py` 新增宿主页托管用例；
   前端侧新增 `web/src/pages/crossPluginGate.test.ts`（20 条源码断言）。

### 证据

- 变异验证（把旧判据插回去）：`test_hosted_plugin_on_a_non_core_route_is_flagged` **红**（`assert 0 == 1`）；
  ★而 `test_repo_has_no_ungated_core_entries` **仍然绿** —— 正是旧判据的假绿形状：
  「真实仓库零缺口」这条断言在 bug 存在时也能通过。
- `python tools/audit_endpoint_ownership.py --check`：改判据后退出码 **1**（炸出 3 处），修完五处转 **0**。
- `vitest` 116 条（+20）· `pytest` 相关 13 文件 305 条 · `tsc` 0 · `eslint --max-warnings 0` 0。

### 附带教训：`skip` 的条件不能用**被测对象**的输出

`load_raw_endpoints` 的第一版用例写的是 `if src not in raw: pytest.skip(...)`。
把 `_RAW_REQUESTS` 清空后它只 **SKIPPED**（退出码 0，门禁毫无反应）—— 扫描器一坏就静默跳过，
正是这条用例要防的假绿。改成基于**源码文本**判断前提（"文件里还有没有 `/effects/` 与 `fetch(`"）
之后，同一个变异才真的变红。
⇒ **前提与结论不能来自同一个来源**；否则测试与被测对象一起坏，测试永远是绿的。

## 8.41 导入期副作用撞上 pytest 的**收集阶段**：夹具还没跑，`import server` 已经跑了 ✅本机实测（2026-09-23）

### 症状

给 `server.py` 加了一步「首次运行初始化」（把默认套餐落成一份 `outputs/plugins.json`）之后，
一批**与插件开关毫无关系**的用例集体变红：`test_manifest_covers_exactly_the_registered_routers`
（清单 26 个 router 对不上，实际只挂了 16 个）、`test_all_plugins_are_ok_on_a_healthy_start`
（期望 `counts = 19/19/0/0`）。

更阴的是第二个现象：初始化到底写去了**哪个路径**，取决于**哪个测试模块先被收集**。

**A. 「夹具已经隔离了」这个直觉在 `import` 期不成立。**

（不是报错，是"这次启动的行为和你刚写的文件不一致"）。

### 对策

1. **导入期副作用一律加环境变量总开关**，由 `m2_server/conftest.py` 在

2. **顺序不变量写进 docstring**（"必须在 `mount_plan()` 之前"），并用**子进程端到端**用例钉住：
   同 `test_plugin_manifest._HOOK_PROBE` 的手法 —— `import server` 只发生一次，
   同进程里拿不到"一次从零开始的挂载"，只有子进程能验证挂载集。
3. 需要验证这个初始化行为的用例：`monkeypatch.delenv(SEED_ENV)` + 自己的 `STATE_FILE`

### 证据

## 8.42 RVC venv 的 `python.exe` 是**启动器**：一个 `Popen` 换来两个进程 ✅本机实测（2026-09-23）

### 症状

给声板加常驻播放器（`Popen(cfg.RVC_VENV_PY, [board_worker.py, ...])`）之后查进程，
看到**两个** python 都在跑同一个脚本：

```
PID=3116  父=14964   D:\RVC\.venv\Scripts\python.exe        ...\board_worker.py "VB-Audio Virtual Cable|CABLE Input" ...
PID=6940  父=3116    C:\Users\<你>\AppData\Roaming\uv\python\cpython-3.12.12-...\python.exe  ...\board_worker.py ...
```

第一反应是「重复起了 worker → 每点一下会不会响两遍」，于是去查代码有没有漏洞。

### 根因

**`uv` 建的 venv 里，`Scripts\python.exe` 不是解释器本体，而是一个再执行基解释器的启动器**
（本机这个 venv 的基解释器是 uv 管理的 CPython 3.12.12）。
所以「一次 `Popen`」在进程表里**必然是父子两个**：启动器 + 真正跑脚本的那个。

⇒ 判据 `把 CommandLine 含 board_worker 的进程数当成"起了几个 worker"` 是**错的**，
本机会恒为 2。正确的计数是数**启动器的个数**（`父进程 = 后端 PID` 的那些），
或者直接看后端日志里"已就绪"打了几次。

### 对策

- 查"起了几个"时**按父子关系数根**，不要数同名命令行；
- 不必为此加"进程树杀"：**实测杀掉启动器，真身也跟着消失**
  （受控实验：起 `python.exe -c "...sleep(40)" zzzmarker` → 杀启动器 → 3 秒后真身已不存在）；
  所以 `proc.kill()` 的语义是够的；
- 反过来也要注意：`proc.poll()` 问的是**启动器**的存活，而启动器会一直等到真身结束 ——
  所以"poll 为 None ⇒ worker 可用"这个判断成立（本次靠它复用常驻进程）。

### 证据

- `Get-CimInstance Win32_Process` 的 `ParentProcessId` / `ExecutablePath` 两条输出（上面那段）；
- 受控实验：`Get-CimInstance ... -like "*zzzmarker*"` 在杀掉启动器后只剩我自己的 bash/powershell（自匹配）；
- 旁证：`/api/soundboard/warm` 返回 `{"ok":true,"ready":true,"samples":6}` —— 管道与设备都通，
  说明"两个进程"不是故障态。

### 附带教训（同一次）

用 `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like "*<关键词>*" }` 查进程时，
**你自己的查询命令也含那个关键词** → 必然自匹配。要么按 `Name -eq "python.exe"` 先收窄，
要么排除当前 PID，否则会看到"一堆幽灵进程"。

## 8.43 两个「守卫反咬一口」的形状：**假红**（注释里引用了被禁写法）与**假绿**（死代码 + 通配路由遮蔽）✅本机实测（2026-09-24）

写这两条是因为它们同一天出现，而且**症状完全相反**：一个盯着你说谎，一个骗你说没事。

### 症状 A：守卫被一条注释弄红

给声板加「素材」区（导入/装卸包）之后，`crossPluginGate.test.ts` 里一条**与本次改动无关**的
守卫红了：

```
expect(panelSrc).not.toMatch(/disabled=\{[^}]*busy/)
```

它守的是「格子**绝不能**因发送中的 busy 变灰」（发送时正是要出声的时候）。
我确实给素材按钮加了 busy 互斥，**但那个表达式没出现** —— 真凶是我写在旁边的一句解释性注释：

```tsx
// 合并回 `disabled={!sb.ready || Boolean(sb.busy)}` 会让那条守卫失效。
```

注释在源码里就是文本。而 `[^}]` 是**否定字符类，能匹配换行**，于是这个正则可以从
那句注释里的 `disabled={` 一路扫到 `busy`。**守卫被"引用禁令"这件事本身绊倒。**

### 根因 A

用文本正则守「形状」的守卫**看不见语法**，只看字节。它无法区分
「这个写法在 JSX 属性位上」与「这个写法出现在注释/字符串里」。

### 对策 A

1. 两条路：改守卫（上 AST，成本高）或改代码。**这里选后者** —— 把注释改成
   "两个锁必须分开命名 + 守卫用正则守格子"，不再逐字引用被禁的表达式；
2. 更普适的做法：守卫的**报错信息里指出匹配到的片段**（或至少给行号），
   否则下一个踩到的人会先去改自己的功能代码，而凶手是注释；
3. 顺带正面价值：这类守卫**确实是有效的** —— 它逼我把素材锁与格子锁拆成两个名字
   （`materialLocked`），意图因此更清楚。**别因为它假红过一次就删掉它。**

### 症状 B：自己写的守卫是死代码，而"补上它"会让另一个功能死掉

为了让「删掉一条包内素材」给出友好报错，`soundboard_delete` 里加了：

```python
if sfx_packs.split_id(sample_id) is not None:
    raise HTTPException(400, "这是音效包里的素材，请卸载整个音效包")
```

单测（只挂了声板 router 的小 app）**绿**：`DELETE /api/soundboard/arcade/coin` → 404，
断言写的是 `in (400, 404)`，看着"守住了"。

真后端一验，**状态码是 405**。原因：包内素材 id 形如 `arcade/coin`（两段），
而那条路由只有一段 `{sample_id}` → **压根匹配不上**，那句友好报错是**只能靠直接调函数碰到的死代码**；
真环境落到 SPA 的 GET 兜底 → "Method Not Allowed"。

更值得记的是**我差点"补上它"**：把路由改成 `{sample_id:path}` 看起来正交又便宜，
但 `DELETE /packs/{pack_id}`（卸载整包）声明在它**后面** → 通配先吃掉两段路径，
于是"卸载整包"会被判成"这是包内素材"，**卸载功能直接死**，而且症状是 400 而不是 404，
看起来像业务校验、不像路由错。

### 根因 B

1. 路由参数**不吃 `/`**（除非 `:path`），所以"带分隔符的 id"永远到不了那段 handler；
2. FastAPI **按注册顺序匹配**，`{p:path}` 这种通配必须放在所有具体路由**之后**
   —— `plugin_manifest.mount_plan()` 的注释里写过同一件事（"挂载顺序是行为"），
   这次是它在 router **内部**的翻版；
3. 只挂单个 router 的单测**看不见 SPA 兜底**，所以"没匹配上"在单测里表现为 404、
   在真环境表现为 405 —— 断言写成 `in (400, 404)` 时，两种都"过"，
   但**过的理由都不对**。

### 对策 B

1. 删掉死代码，并把"为什么这里没有守卫"写成注释（含真环境的 405 与 `:path` 的遮蔽风险）
   —— 留着会让人以为它挡了什么事，这比没有更糟；
2. 测试改成断言**真实行为**（`== 404`，并说明真环境是 405），**再顺手断言整包卸载仍通**
   （哪天真有人加了 `:path`，这条会立刻红）；
3. 判据：**任何"友好报错"都要有一条用例从 HTTP 打进去**。只从函数层调用的守卫，
   和没有守卫在"用户是否安全"这件事上等价。

### 证据

✅本机实测（2026-09-24）：
· A —— 改注释前 `crossPluginGate.test.ts` 35 条里红 1 条（就是那条正则），改完 35 全绿；
· B —— 隔离后端起在 `:8123`（`VM_MEDIA_DIR`/`VM_OUTPUTS_DIR` 指到 `D:/tmp`），
  `DELETE /api/soundboard/arcade/coin` 实测 **405 Method Not Allowed**；
  同一次会话里 `DELETE /api/soundboard/packs/arcade` 实测 **200 / count=6**（卸载仍通）。

### 同类第三例（假绿）：**归一化被当成了校验**

`sfx_packs.clean_stem()` 是**归一化**函数：`"../a"` → `"a"`、`"a/b"` → `"b"`、`"x.wav"` → `"x"`。
它返回的永远是"看着很干净"的字符串 —— 所以**拿它当校验就会静默放行**：

```python
if not clean_stem(item["id"]):        # ✗ "../a" 会通过（返回 "a"，非空）
    raise PackError("id 不合法")
if clean_stem(item["id"]) != item["id"]:   # ✓ 必须**原样**合法
    raise PackError("id 不合法")
```

同一个陷阱我在这次改动里踩了两次：清单条目的 id 校验（上面）、以及包 id
（`pack_dir()` 里就是靠 `clean_stem(pid) != pid` 才拦得住 `../evil`）。
判据：**归一化函数的名字里要有"收干净"的意思，校验点必须重新比一次**；
两者共用一份字符规则没问题（规则只该有一份），但"通过"的判据不同。
用例已钉：`test_clean_stem_is_normalizing_not_validating` +

## 8.44 变异验证脚本的**还原**步骤必须兜底：异常一次就把变异态留在工作树里 ✅本机实测（2026-09-24）

**症状**：给新门禁做变异验证（仓库惯例，见 §3.24）。脚本写得很直白：
`读原文 → 写变异 → 跑 vitest → 写回原文`。第一次运行就抛异常：

```
FileNotFoundError: [WinError 2] 系统找不到指定的文件。
  subprocess.run(["npx", "vitest", "run", ...])
```

异常从 `run()` 里冒出来，**跳过了写回原文那一步** —— 于是
`web/src/pages/Live/index.tsx` 停在被注入 bug 的状态里（少了一个 prop）。
更险的是：异常栈刷屏时，人只会说"脚本失败了"，**不会想到工作树是脏的**；
若此刻接着提交，注入的 bug 就成了正式改动。

**根因**（两件事叠在一起）：

1. **Windows 上 `npx` 不是可执行文件**，是 `npx.CMD`（`npm` / `yarn` 同理）。
   Python 的 `subprocess.run(["npx", ...])` 不做 `PATHEXT` 展开 → 直接 `WinError 2`；
   而同一行在 bash 里跑得好好的 —— 所以"我在终端里明明能跑"这个直觉在 Python 里不成立。
2. **脚本是直线式的**：写变异与还原之间隔着一次外部进程调用，任何异常都会让控制流
   跳过还原。这与 §3.24 记的"变异没应用 / 测试没真跑"是**同一族问题的另一面**：
   那次是"变异没落盘"，这次是"变异收不回来"。

**对策**：

1. 变异脚本一律 `try/finally` 兜底还原，并在 `finally` 里做**逐字节**核验：

   ```python
   orig = f.read_bytes()
   try:
       for label, old, new in muts:
           f.write_bytes(orig.replace(old, new))
           ...
           f.write_bytes(orig)          # 每条之间也要还原
   finally:
       f.write_bytes(orig)
       print("还原核验（字节一致）:", f.read_bytes() == orig)
   ```

2. **Windows 上取可执行路径用 `shutil.which`**（它认 `PATHEXT`）：
   `npx = shutil.which("npx")` → `D:
odejs
px.CMD`。
3. **判据不只是"测试红了"**：还要看还原核验那一行是 `True`；
   跑完第一件事是 `git status --short`，看有没有意外文件。
4. 每条变异的**期望断言**要事先写清（本次 M1 应由"两个 tab 共用同一个实例"拦下，
   M2 应由"按 sound.fx-board 门控"拦下）—— 只报"红了"而不报"被哪条拦的"，
   就分不清是断言生效还是脚本把文件写坏了。

**证据**：改成 `try/finally` + `shutil.which` 后重跑，两条变异分别被**正确的断言名**拦住
（各 `1 failed | 39 passed`），finally 打印的还原核验为 `True`（逐字节一致）。

**顺手核实的另一件事，以及一个更难看的坑（同一件事的两面）**：

1. `str_replace` 写入 **CRLF 文件**时会**沿用该文件的行尾** —— 把带 `

   的 `LivePage.tsx` 后，逐字节数出来仍是 `CRLF=809 / 孤立LF=0`。
2. **但"工作副本的行尾"不等于"blob 的行尾"**：本仓 `core.autocrlf=true`，检出来是 CRLF，
   而**已提交的 blob 是 LF**（本档历史几次追加都是 104/0、48/0 干净进账）。
   本次改用 Python 追加、并且"照着工作副本"写了 CRLF ⇒ 该文件在 blob 里**整篇从 LF 翻转成
   CRLF** ⇒ `git log --numstat` 变成 **2720 增 / 2661 删**，而真实改动只有 59 行
   （`git diff --ignore-all-space --numstat` 只剩 59/0，一验便知）。
   **对策**：追加重写文本文件时**以历史 blob 的行尾为准**（`git cat-file blob <rev>:<path>`
   之后再逐字节数），别以工作副本为准；docs 一律 LF。而且**提交后立刻核一行**
   `git log --numstat -1 -- <file>`：出现"整篇翻转"就 `git commit --amend` 修掉
   （未推送时最省事，也最干净）。判行尾只能用 Python 逐字节数，别用 grep 的 `\r` 模式
   —— 本次就是这么被误导的（速查表 80/81）。

## 8.45 毫秒级只读接口被串在**无超时的预热握手**之后 → 面板长期空着，用户以为"这功能不存在" ✅本机实测（2026-09-25）

**症状**：安装版桌面端「微信发送」页的音效声板长时间停在 `共 0 条（出厂 0）`，
空态还写着"插件自带的 6 条出厂音效应在此列出"。用户因此怀疑"前端是不是没重新构建"、
"特效库到底放哪" —— 把**加载失败**读成了**功能不存在**（而这正是最贵的误诊：
它会把人引去重新构建/重装，而问题一行都不在那边）。

**根因**：取数 effect 里先 `await soundboardWarm()`，再 `await refresh()` 取目录。
两件事的代价差了三个数量级：

- `/soundboard/catalog` 纯读目录+计数，真机 **25ms**；
- `/soundboard/warm` 要 `_spawn_worker()` 拉起常驻播放器，用
  `proc.stdout.readline()` 做就绪握手，而那次 `readline()` **没有超时**（`m2_server/soundboard.py`）。

串行 = 第二个请求继承第一个的**全部风险**：握手慢/卡住 → 目录请求永远发不出。
更隐蔽的是用户在握手期间离开页面（cleanup 置 `alive=false`）—— 请求**根本没发**，
所以后端日志上呈现为"有 warm、没有 catalog"，看起来像前端压根没实现取数。
判据其实就在日志里：**该发的请求缺失**比"请求超时"更能指向"被挡住了"。

**对策**：

1. 取目录/包列表与预热**解耦**：前者照常 `await`（毫秒级），后者 fire-and-forget
   （`void soundboardWarm().catch(() => {})`）—— 预热只影响"第一次点击"的延迟，
   失败也由后端在真点播放时给可读报错，不值得让整个面板陪它等。
2. 判据写成**源码不变式用例**（比渲染测试便宜、且正好防"有人改回串行"）：
   `expect(hookSrc).not.toContain("await soundboardWarm()")`。
3. 通用规则：**任何"拉起常驻进程/设备的预热"都不得挡住只读接口的取数**；
   反过来，**无超时的握手本身就是隐患** —— 它会让 `/warm` 与 `/play` 一起永久卡死
   （本次未改后端，仅记录）。

**证据**：CDP 实测（安装版 `web_dist`，`Page.reload` 后计时）——

## 8.46 CDP 驱动真界面时的两个**静默无操作**：坐标落在视口外、按当前文案定位 ✅本机实测（2026-09-25）

**背景**：用户要求"用鼠标模拟把这条流程走一遍，不要后端直接发"。做法是给**安装版**加
`--remote-debugging-port=9222`，用 `Input.dispatchMouseEvent` 派发**可信**事件（等价真人点）。
两个坑都不报错，而且症状与"点到了但被别的东西挡着"长得一模一样。

### 症状 A：脚本说"点了"，界面一点没变

`Session.click` 打印出了坐标、退出码 0，可模式没切、勾选没上。

**根因 A**：`Input.dispatchMouseEvent` 的 x/y 是**视口**坐标，而页面比视口长 ——
本机主窗 `innerHeight=783`，而「② 半自动」那张卡在 **y≈800 开外**（滚动位置为 0）。
事件落在**窗口之外**：不报错、不命中、无任何提示。
只有一条可靠判据：`document.elementFromPoint(x, y) === null` ⇒ 这个坐标上没有东西。

**对策 A**：点之前先 `scrollIntoView({block:'center'})`，再断言
`rect.y >= 0 && rect.y + rect.height <= innerHeight` **且** `el.contains(elementFromPoint(中心))`
（后者顺带挡住滚动后仍被固定头/遮罩压住那类）。
⚠️ `tools/desktop-control/cdp.py::Session.click` **不做这两步**：它是为桌宠那种固定小窗写的。
驱动长页面要自己在外面补 —— 本轮写在了临时脚本的 `click_text` 里（`D:/tmp/dc/drive.py`）。

### 症状 B：第一次轮换成功，第二次就"找不到元素"；重跑一遍还会把上次的勾选点掉

**根因 B**：两件都在"脚本假设自己从零开始":

1. 胶囊上的位置按钮**文案会随状态变**（`叠加` → `开头` → `结尾`），按当前文案定位的脚本
   在第一次点击后必然失效 —— 文案是给人看的，不是契约；
2. 界面状态是**累积**的：第二次运行里“点格子”把第一次已经勾上的**又取消**了。

**对策 B**：按 `title` / `aria-label` 里描述**交互**的那半句定位（本例
`（点一下切换位置）`，它不随状态漂）；每步先**读状态**再决定要不要点，
别写"从头点到尾"的直线脚本。

### 症状 C：脚本打印了两次"档位：实时"，中间那次点击像没发生

**根因 C**：判选中态读的是**文案的存在性** —— `if "预混" not in 所有 button 的文案拼接`。
可「实时」「预混」两个按钮的文案**永远都在**，条件恒为假，于是"切到预混"那一步被
**静默跳过**；紧接着那一下格子按在了**实时档**上（实时档只出声、不产生勾选胶囊），
脚本再去找胶囊就只能报"找不到元素" —— 症状和"点被挡住"一模一样，根因却在**判断式**里。

**对策 C**：选中态只能从**选中标记**读（本例是 `className` 里的 `bg-primary/15`，
更稳的是 `aria-selected`/`role`），不能从"文案在不在"推；并且读完先**断言**
（`"*预混" in 状态` → 不是就停手），别带着一个错的档位往下点。
同类：任何"两态按钮"（档位、开关、tab）都必须读**态**，别读**词**。

## 8.47 `subprocess.run` 用**相对路径 + 正斜杠**调 `.venv` 里的 python ⇒ FileNotFoundError ✅本机实测（2026-09-25）

**症状**：驱动脚本里 `subprocess.run([".venv/Scripts/python.exe", "tools/uia_probe.py", ...])`
抛 `FileNotFoundError [WinError 2]`（“系统找不到指定的文件”）——而**同一个脚本里**
`os.path.exists(".venv/Scripts/python.exe")` 回 `True`、`os.getcwd()` 就是项目根。

**根因**：Windows 的 `CreateProcess` 不把带**正斜杠**的相对可执行名当路径解析
（Git Bash 里 `.venv/Scripts/python.exe` 能用，是因为 bash 自己先把它转成了 `\`）。
与 cwd、权限、venv 都无关，**只和可执行名里的分隔形式有关**。

**证据**（同一个 cwd = `D:\变声`，同一个文件，只改写法）：

| 可执行名写法 | 结果 |
|---|---|
| `.venv/Scripts/python.exe` | **FAIL** FileNotFoundError |
| `.venv\Scripts\python.exe` | OK |
| `.\.venv\Scripts\python.exe` | OK |
| `D:/变声/.venv/Scripts/python.exe`（绝对 + 正斜杠） | OK |
| `D:\变声\.venv\Scripts\python.exe`（绝对 + 反斜杠） | OK |
| `sys.executable` | OK（但注意：本仓 venv 的 python 是**启动器**，见 §8.42） |

**对策**：`subprocess` 的**第一个参数（可执行文件）**一律用绝对路径 ——`os.path.join(root, ".venv", "Scripts", "python.exe")`
（`os.path.join` 在 Windows 上给的就是反斜杠）。带中文的根目录不受影响。
第二参数（脚本路径）用正斜杠没问题：那是**子进程自己**去开文件，不是 `CreateProcess` 找 exe。

## 8.48 用 CDP 的「可信鼠标事件」验「点窗口会不会抢前台」——全绿但**结论无效** ✅本机实测（2026-09-25）

**症状**：要验一个「非激活窗口」的性质（悬浮声板窗：点它不许把前台从微信抢走）。
第一版验收脚本用 `cdp.Session.click` 走 `Input.dispatchMouseEvent` 点格子，
结果全绿：格子亮了、后端计数 +1、`isFocused()` 也是 false。
**但这三条证据合起来仍不能证明「真人点不会抢前台」**。

**根因**：`Input.dispatchMouseEvent` 是往**渲染进程自己的输入管线**里塞事件，
不经过 Windows 的 hit-test 与窗口激活路径。而「点一个窗口是否把它带到前台」
恰恰**只由 OS 那条路径决定**（WS_EX_NOACTIVATE / `SetForegroundWindow` 的规则）。
换句话说：CDP 能证明「事件到达了页面」，证明不了「没激活窗口」。

**对策**：把「前台/激活」类断言从 CDP 路径里**整个换掉**，改用 OS 级注入：

```python
# SendInput（与物理鼠标同一条 hit-test / 激活路径），坐标用 GetWindowRect 拿物理像素
ctypes.windll.shcore.SetProcessDpiAwareness(2)      # 否则 GetWindowRect 被 DPI 虚拟化
_move_abs(x, y); _left(True); _left(False)
# 判据三条一起看：① 后端计数 +1（真播了）② GetForegroundWindow 前后同一个 hwnd
#                ③ win.isFocused() === false
```

在 Linux/macOS 或拿不到 SendInput 时，就把这条标成「**必须人手**」而不是用 CDP 顶替 ——
假绿的代价远大于一条空着的验收项。

**证据**（安装版 0.2.4，`tools/desktop-control/cdp.py` 只用来读状态）：

| 手段 | 计数 | 前台 hwnd | isFocused |
|---|---|---|---|
| CDP `Input.dispatchMouseEvent` | +1 | **未验**（这条路径不问 OS） | false |
| **SendInput**（最终采用） | +1（8→9，连跑三次） | **前后同一个**（微信→微信） | false |

两条容易顺手写错的陪跑判据：**收起后 CDP 调试目标仍在**（`hide()` 不销毁窗口对象）
→ 断言应写 `visible === false` 而不是「目标列表里没有它」；**播放高亮只保留素材时长**
（boom 1.4s）→ 想验「点击有反馈」必须在时长内读一次，读完再确认它会自己落。
