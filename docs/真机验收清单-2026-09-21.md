## 0. 通用前置与约定

### 0.1 两个必守的操作前提

| 事项 | 说明 |

响应里带 `restartRequired: true`。所以每条的流程都是：
**改开关 → 完全退出 → 重开 → 再看现象**。

可用预设（`POST /api/plugins/preset`）：`light` / `standard` / `full` / `core`。

## A. UIA 就绪判定顺序（§8.15）

**背景**：`uia_active = _uia_ready()` 原本排在会**杀+拉起微信**的 `pre_apply.result()`
**之前**，判定时微信还没起来 → 必然 False → 退化到像素链路。而像素链路按坐标盲点，
实测**点歪过一次，弹出了浏览器网页版文件传输助手**。
两处修复：① 判定挪到「录音环境准备」之后；② 新增 `_await_uia_active()` 重试 3 次，
重试前先 `reset_state()` 清掉那个 3 秒的否定结果缓存。

### 前置

- 微信 4.x 在跑且已登录，聊天窗口有一段可点「语音」的位置；
- `VM_WECHAT_RESTART` 保持**你拍板的 `0`**（见下条「已知边界」）；
- 应用与后端已起。

### 步骤

1. 完全退出应用 → 重开（确保走一次干净的启动链路）；
2. 从**桌宠**发一条文字到微信（或走主界面「微信发送」）：
   文本随便，例如 `测试UIA一`；
3. 发送过程中**别动键鼠**（`showAltHint` 会提示）；
4. 发送结束后看 `steps`，并对比后端日志。

### 预期现象

- `steps` 里出现 **`UIA 结构化访问就绪`**（而不是 `UIA 不可用（走像素链路）`）；
- 微信里收到语音，且**微信窗口焦点/鼠标位置没有被乱点**（不应出现浏览器被打开）。

### 观测点

- 发送结果的 `steps` 数组（源码位置 `m2_server/wechat_voice.py:1872`）；
- 后端日志里 `_await_uia_active` 的调用上下文（同一段链路）。

### 失败判据（命中任一条即不合格）

| # | 判据 |
|---|---|
| A1 | `steps` 里出现 `UIA 不可用（走像素链路）` —— 说明修复没生效或微信树确实没物化 |
| A2 | **桌面出现无关窗口被打开**（浏览器网页版文件传输助手等）—— 像素链路盲点的典型后果，**必须立即停止**并记录当时的坐标 |
| A3 | 微信收到的是**静音**语音（配合 §0.3 的 statistic 文件确认微信用了哪个设备） |
| A4 | 连续 3 次发送里 ≥2 次退化到像素链路（修复前的实测是 5 条里 4 条；修复后应接近 0） |

### 已知边界（别误判）

- `VM_WECHAT_RESTART=0` 下**不会**杀微信 → 微信可能仍绑着它启动时的物理麦。
  这条链路本身**允许**静音风险存在（用户拍板优先避开强制重登），
  `_binding_warning()` 会单独提醒，**不要**把它算成本次验收的失败。
- `_await_uia_active` 的重试延时是 0.5s × 3（因为重置了缓存，不必等满 3s）。
  微信冷启很慢时仍可能失败 —— 那是**微信太慢**，不是判定写错，记录实测耗时即可。

### 回执

`steps` 原文 + `backend.log` 里对应那段 + 微信收到的语音是否可听（用 `ffprobe` 看时长/电平，
或直接听）+ 桌面是否出现无关窗口。

## B. 桌宠能力门控（关 `sound.rvc-live` 后不许误报离线）

## C. 音色库页门控（本次 09-21 改动，`b5be352`）

**背景**：`/voices` 是 `core.voices`（路由恒注册），但页内嵌了三个**可关能力**的面板：
试音间三件套（`AbCompareCard` / `AbChainCard` / `AuditionEntry`，属 `sound.audition`）、
作品库（`WorksLibrary`，属 `core.history`）、音色挖掘面板与导入链路
（属 `sound.mine` / `sound.workshop`）。关掉对应插件后端点不再挂载，面板却照旧渲染
→ 用户点一下 404 且看不出原因。
**关键**：`useVoices` 挂载时会轮询 `getMineState`，所以门控必须收进 hook，
只在 JSX 藏按钮不够（会每 3 秒空转刷一次 404）。

### 前置

- 至少 1 个已保存音色（否则 `p.voices.length >= 1` 不成立，试音间卡片本来就不渲染）。

### 步骤（逐个能力验，每次都要「改开关 → 完全退出 → 重开」）

对 `sound.audition` / `sound.mine` / `sound.workshop` 各做一轮：

1. 关掉目标插件（`POST /api/plugins/<id>/disable`）；
2. 完全退出 → 重开；
3. 进「我的音色」页，**打开浏览器 DevTools 的 Network 面板**（或看后端日志）；
4. 静置 ≥ 10 秒；
5. 看页面上的面板是否还在，以及有没有 404 请求。

### 预期现象

| 关掉 | 页面上应消失 | 不应出现的请求 |
|---|---|---|
| `sound.audition` | 盲听对比卡、多链路卡、「去试音间」入口 | `/api/ab/run`、`/api/ab/chain` |
| `sound.mine` | 「自动挖掘」整卡、侧栏「不满意？继续挖」 | `/api/mine/state`（**包括挂载时的轮询**） |

**核心**：音色库页**始终可用**（它是核心页），只是少了几块；

| 现象 | 含义 |

## D. 桌宠发微信语音**真的换声**（`rvc_voice` 委托）

**背景**：`pet-actions.cjs` 的 send_text 载荷里 `rvc_voice: ""` 一度被记成
「桌宠面板单音色写死」。复核结论是**刻意的委托** —— 后端在 `rvc_voice` 为空时
按 `voice_id` 推（`resolve_rvc_voice`，实测 `kangaroo → kangaroo_v2`），
且面板本来就有音色下拉。本条的验收目标是**证明这条委托链真的通到换声**，
因为「留空」看起来太像漏填，光看代码说服不了人。

### 前置

- 微信在跑；`media/voicebank/` 里有目标音色（当前机器只有 `kangaroo`）；
- `D:\RVC\logs\` 下有对应实验目录（`kangaroo_v2`）；
- 桌宠面板的音色下拉**不是空的**（空的话先去 `/api/voices` 确认有 `has_reference` 的音色）。

### 步骤

1. 桌宠面板选一个音色（例如「袋鼠」）；
2. 发一条文字到微信；
3. 看 `steps` 里的换声那一条，并**听**收到的语音。

### 预期现象

- `steps` 里出现 **`RVC 换声 → kangaroo_v2`**（不是 `kangaroo`）；
- 收到的语音是**目标音色**，而不是通用 TTS 播音腔；


- 音效长度都 ≤1.6s：故意做短的（微信语音是叠加进人声，长音效会把整条消息搞糊）。
- 实时变声页的声板**没有「预混」档**（连模式切换按钮都不会出现）—— 实时链路里没有
  "要混的那条合成产物"，这是故意的，不是漏了。

### 回执

三段证据：① 语音消息的录屏/截图（证明里面有音效）；② `curl /api/soundboard/catalog`
里对应条目的 `count` 已 +1；③ 后端日志里 `board_worker` 的启动行数（应为 1）。
**G2 若命中**，额外回执「微信版本 + 录音方式（Alt / 话筒图标）」，那就是这条路径的真实边界。

## H. 预混模式：发送前把音效烘进音频（2026-09-24 新增）

**背景**：§G 那条路有一个没验证过的前提 —— **点格子会把鼠标焦点从微信挪走**，
按住的 Alt 录音可能被取消（G2）。预混模式是那条路走不通时的**确定性兑底**：
音效在发送**之前**就被混进音频文件（`sfxmix_<原名>.wav`），发送目标换成它，
全程不需要在微信里点任何东西，也就不存在"抢焦点"这件事。

两条链共用同一份 DSP（`sfx_lib.mix_into`），三个位置的说法完全一致：

| 位置 | 听感 | 等价于实时声板的什么 |
|---|---|---|
| **叠加** | 音效与人声同时响 | 录制中点格子（主场景） |
| **开头** | 先炸一声，再说话 | 按 Alt 前点一下 |
| **结尾** | 说完来一声 | 松开前点一下 |

### 前置

- 后端与桌面端均为最新（同 §G：`sound.fx-board` 已启用）；
- **已有一条合成产物**（`outputs/tts_*.wav`）—— 预混的源就是它（未合成时按钮不可用）。

### 只读探针（不用微信、不发任何消息）

```bash
# ① 混一条出来（append 到末尾，便于对照听"尾音多了一声"）
curl --noproxy '*' -s -X POST -H 'Content-Type: application/json' \
  -d '{"inserts":[{"sample":"boom","mode":"append","gain":1.0}]}' \
  http://127.0.0.1:8000/api/soundboard/premix
# 预期：{"ok":true,"wav":"sfxmix_tts_*.wav","seconds":<原时长+1.4>,"inserts":1,"skipped":[]}
```

**自动化可自证的部分（不用耳朵）**：混出的文件时长 = 原时长 + 音效时长（拼接档），
或与原时长相同（叠加档）；且 `glob("tts_*.wav")` 的结果**不变**（混出的文件不叫 `tts_*`，
所以不会顶替"最近一条合成产物"这个默认发送目标）。两条都有单测钉子。

### 步骤（当默认发送目标用）

1. 先在「单段合成」生成一条语音；
2. 到「微信发送 → ② 半自动」的声板面板，**切到「预混」**；
3. 点「爆炸」格子（只勾上，不发声）→ 胶囊上点一下切到「开头」；
4. 点「混进这条语音」→ 上方「发送内容」卡会变成 `sfxmix_*.wav` 并显示「已混入 1 条音效」；
5. **先点试听**：应先听到爆炸、再听到人声；
6. 点「自动发送到微信」（或 ②「开始播放」+ 手动按 Alt）；
7. 在微信里点开这条语音确认。

### 失败判据

- H1 试听里没有人声或没有爆炸（→ 看 `skipped` 是否非空、音效 id 是否真存在）；
- H2 发送出去的是**没混过**的那条（→ 检查「发送内容」卡显示的是不是 `sfxmix_*`）；
- H3 混完再合成一条新语音，发送却仍发旧的混音（→ **设计上源一变就自动失效**，
  此时卡片上的「已混入」徽标应当消失；没消失就是回归）；
- H4 点「混进」报「没有这个音效」（→ 素材被删了，面板目录还没刷新）；
- H5 微信收到的是**两条**语音或空消息（→ 发送链路的问题，不是预混）。

### 回执

- 「发送内容」卡截图（应显示 `sfxmix_*.wav` + 已混入 N 条）+ 微信里那条语音的截图；
- 一句话：试听与微信里的听感是否一致（爆炸在开头/末尾/同时）。

### H-bis. 「混好并直接发送」（2026-09-25 加，一键）

上面 §H 的步骤是**两步**（② 混 → ① 发）。而两步之间那个「发送目标已换成 `sfxmix_*`」
在界面上**看不见**：用户在两步之间重新合成了一条，`useWechatSend` 会（正确地）让预混失效，
于是发出去的是**没混**的那条，且一句提示都没有。新按钮把两步合成一步 ——
`wav` 显式交给发送方，顺序只剩一种（前提不变：`send_voice` 那条链路本来就是
程序点话筒起录、点绿钮发送，**不需要人按 Alt**，所以这条路没有 §G 的抢焦点问题）。

**步骤**：勾「爆炸」→ 胶囊上点一下切到「开头」→ 点**「混好并直接发送」** →
等 ① 卡片显示「发送中」（约 wav 时长 + 3s），**全程不要动键鼠**（微信会被抢前台）。

**预期**：微信里到达**一条**语音，先一声爆炸、再是 TTS 人声（开头档）；网页上不再有第二次点击。

- **H6** 点完没有任何语音到达 → 网页会显示是 `premix` 还是 `send_voice` 失败：
  - `premix` 失败 = 音频/素材问题（同 H1/H4）；
  - `send_voice` 失败多半是微信没开或停在登录页 →
    `curl --noproxy '*' -s http://127.0.0.1:8000/api/wechat/precheck` 一眼看出；
- **H7** 收到的那条**没有音效** → 发出去的是没混的那条（同 H2）；查发送历史里那条的 `wav` 名
  是不是 `sfxmix_*`。

### H-ter. 精确时间点：第 N 秒（2026-09-25 加）

「叠加」档的胶囊上多了一个输入框：`💥 叠加 第 [ 1.2 ] 秒`（只对叠加有意义 ——
开头/结尾是拼接，位置由档位本身决定；其它档位上不会出现这个框）。

**步骤**：勾「爆炸」→ 胶囊上**点一下切到「叠加」** → 在输入框里填 `2`（或面板上给的源时长的
中间值）→「混进这条语音」→ 试听：爆炸应出现在第 2 秒，而**不是**开头；源时长不变。

- **H8** 试听里爆炸仍在开头 → 框里填的值没发出去（看请求体里 `at_s` 是否为 2）；
- **H9** 填一个**超出源时长**的数（人声 4s 时填 30）→ 预期：面板先给一行琥珀色提醒
  （"它会被贴到末尾，而不是在你填的那一秒响"），混完后下方**再列一条后端回报**
  （"指定第 30.0s 超出人声长度（4.4s），已贴到末尾"），并且**混音依旧成功**（不是 4xx
  —— 它确实没地方响，但也不该让整条语音发不出去）。
  - 若只看到前半句、看不到后端回报 → 后端那份还是旧的（本轮只定向换了一个文件）。

**波形拖动**（2026-09-25 同日跟进）：勾「爆炸」并切到「叠加」后，面板上会出现一条
**源人声的波形**，「💥 0s」就是它的记号。

**步骤**：把那个记号拖到波形中间 → 胶囊上的秒数框应同步变成约「2.0」（源 4s 时）；
聚焦记号后按 ← → 应每次 ±0.1s；勾两条叠加音效时应看到**两枚**记号，各自拖得动。

- **H10** 波形区一直停在「波形加载中…」或干脆空白 → 先看是不是取不到音频
  （`last_tts` 的 `url` 404 / 输出目录里那条已被清掉）。**这不是致命失败**（秒数框仍能定位），
  但要看界面写没写原因 —— 空白与“加载中”在界面上分不出来，那是要报的。
- **H11** 拖完记号，秒数框没跟着变（或反之）→ 两处不是同一份状态（回归）；
- **H12** 点波形空白处把记号挪走了 → 回归：本设计**刻意**不响应轨道点击
  （多枚音效时"点一下该动谁"没有正确答案，误移比不移更糟）。

```bash
# ---- 看当前能力状态 ----
curl --noproxy '*' -s http://127.0.0.1:8000/api/plugins | python -m json.tool | head -40

# ---- 单个开关 ----
curl --noproxy '*' -s -X POST http://127.0.0.1:8000/api/plugins/<id>/disable
curl --noproxy '*' -s -X POST http://127.0.0.1:8000/api/plugins/<id>/enable

# ---- 一把恢复到默认（standard）----
curl --noproxy '*' -s -X POST http://127.0.0.1:8000/api/plugins/preset \
  -H 'Content-Type: application/json' -d '{"preset":"standard"}'

# ---- 每次改完都要：完全退出应用再重开 ----
```
