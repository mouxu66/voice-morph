# 真机验收清单 · 2026-09-21

> 为什么需要这份清单：**下面这些改动只有单测/变异测试，没做真机端到端**。
> 原因不是懒 —— 本项目的 AI 沙箱**起不来 Electron GUI**（Chromium GPU 进程被 kill，
> 见 `.workbuddy-ai/memory/MEMORY.md` 的环境观察），也没有可交互的微信窗口。
> 单测能证明「代码按写的跑」，证明不了「用户按下去真的对」。
>
> 所以这份清单把「只能真人验」的部分列成**可执行步骤 + 预期现象 + 观测点 + 失败判据**，
> 而不是留一句「待验证」。每条的**回执**要求写清楚留什么证据 —— 没有证据的"我试过了"
> 在下一次排查时等于零。

## 0. 通用前置与约定

### 0.1 两个必守的操作前提

| 事项 | 说明 |
|---|---|
| **「重启」= 完全退出应用** | 关窗口不算：桌宠常驻，主进程还在。必须从托盘/任务管理器确认进程退出，再打开。见根 `AGENTS.md`。 |
| **调本机端口一律加 `--noproxy '*'`** | 本机叠了 Mihomo/Clash 的系统代理 + TUN，不加这个 `curl` 会被代理劫持成 502/超时，症状像"后端没起来"。 |

### 0.2 插件开关是**重启生效**的

`POST /api/plugins/{id}/disable` 只改状态文件，**router 是启动时挂好的**，
响应里带 `restartRequired: true`。所以每条的流程都是：
**改开关 → 完全退出 → 重开 → 再看现象**。

可用预设（`POST /api/plugins/preset`）：`light` / `standard` / `full` / `core`。

### 0.3 观测点速查

| 观测点 | 路径 / 方式 |
|---|---|
| 后端日志 | `%APPDATA%\voice-morph-desktop\backend.log` |
| 能力清单（当前状态） | `curl --noproxy '*' -s http://127.0.0.1:8000/api/plugins` |
| 微信实际绑的采集设备 | `%APPDATA%\Tencent\xwechat\net\kvcomm\*_input.statistic` |
| 发送步骤日志 | 微信发送结果的 `steps` 数组（界面会显示最后 3 条） |

- 命中的**具体观测点**（哪个文件哪一行 / 哪个接口的哪个字段）；
- 与**失败判据**的对照结论。

## A. UIA 就绪判定顺序（§8.15）

**背景**：`uia_active = _uia_ready()` 原本排在会**杀+拉起微信**的 `pre_apply.result()`
**之前**，判定时微信还没起来 → 必然 False → 退化到像素链路。而像素链路按坐标盲点，
实测**点歪过一次，弹出了浏览器网页版文件传输助手**。
两处修复：① 判定挪到「录音环境准备」之后；② 新增 `_await_uia_active()` 重试 3 次，
重试前先 `reset_state()` 清掉那个 3 秒的否定结果缓存。

### 前置

- 微信 4.x 在跑且已登录，聊天窗口有一段可点「语音」的位置；
- `VM_WECHAT_RESTART` 保持**你拍板的 `0`**（见下条「已知边界」）；
- 应用与后端已起。

### 步骤

1. 完全退出应用 → 重开（确保走一次干净的启动链路）；
2. 从**桌宠**发一条文字到微信（或走主界面「微信发送」）：
   文本随便，例如 `测试UIA一`；
3. 发送过程中**别动键鼠**（`showAltHint` 会提示）；
4. 发送结束后看 `steps`，并对比后端日志。

### 预期现象

- `steps` 里出现 **`UIA 结构化访问就绪`**（而不是 `UIA 不可用（走像素链路）`）；
- 微信里收到语音，且**微信窗口焦点/鼠标位置没有被乱点**（不应出现浏览器被打开）。

### 观测点

- 发送结果的 `steps` 数组（源码位置 `m2_server/wechat_voice.py:1872`）；
- 后端日志里 `_await_uia_active` 的调用上下文（同一段链路）。

### 失败判据（命中任一条即不合格）

| # | 判据 |
|---|---|
| A1 | `steps` 里出现 `UIA 不可用（走像素链路）` —— 说明修复没生效或微信树确实没物化 |
| A2 | **桌面出现无关窗口被打开**（浏览器网页版文件传输助手等）—— 像素链路盲点的典型后果，**必须立即停止**并记录当时的坐标 |
| A3 | 微信收到的是**静音**语音（配合 §0.3 的 statistic 文件确认微信用了哪个设备） |
| A4 | 连续 3 次发送里 ≥2 次退化到像素链路（修复前的实测是 5 条里 4 条；修复后应接近 0） |

### 已知边界（别误判）

- `VM_WECHAT_RESTART=0` 下**不会**杀微信 → 微信可能仍绑着它启动时的物理麦。
  这条链路本身**允许**静音风险存在（用户拍板优先避开强制重登），
  `_binding_warning()` 会单独提醒，**不要**把它算成本次验收的失败。
- `_await_uia_active` 的重试延时是 0.5s × 3（因为重置了缓存，不必等满 3s）。
  微信冷启很慢时仍可能失败 —— 那是**微信太慢**，不是判定写错，记录实测耗时即可。

### 回执

`steps` 原文 + `backend.log` 里对应那段 + 微信收到的语音是否可听（用 `ffprobe` 看时长/电平，
或直接听）+ 桌面是否出现无关窗口。

## B. 桌宠能力门控（关 `sound.rvc-live` 后不许误报离线）

**背景**：桌宠 `tick()` 原本拿「cascade + live 两个接口都拉不到」当**后端离线**判据。
一旦关掉 `sound.rvc-live`，这两个接口同时消失 → 桌宠**永久显示「后端离线」**，
而后端其实好好的。修复改用 `core.system` 的 `HEALTH_API` 当判据，并给
市场/实时/微信三块加了 `CAP.*` 门控与 `refreshCapVisibility()`。

### 前置

- 应用与后端正常，桌宠可见。

### 步骤

1. 记下当前状态：`curl --noproxy '*' -s http://127.0.0.1:8000/api/plugins`；
2. 关掉实时变声：
   `curl --noproxy '*' -s -X POST http://127.0.0.1:8000/api/plugins/sound.rvc-live/disable`
   （响应里应有 `restartRequired: true`）；
3. **完全退出**应用 → 重开；
4. 让桌宠静置 ≥ 10 秒（`tick()` 每 1s 一跳）；
5. 观察桌宠气泡/药丸，再看后端日志。

### 预期现象

- 桌宠**不**显示「后端离线」，药丸是正常态；
- 实时变声相关的入口（`live` 行 / `engRow`）**隐藏**（`refreshCapVisibility()` 生效）；
- 后端日志里 `rvc_live` / `cascade` 相关 router **没有挂载**（不是挂载后 500）。

### 观测点

- 桌宠药丸文案与气泡（源码 `web/electron/pet/pet.html:1158-1172`，
  离线时是 `后端离线` / `后端没起来，先开主程序（点此看日志）`）；
- `/api/plugins` 里 `sound.rvc-live` 的 `enabled: false`；
- 后端启动日志里 26 个 router 模块的挂载账（`/api/capabilities`）。

### 失败判据（命中任一条即不合格）

| # | 判据 |
|---|---|
| B1 | 桌宠显示 **`后端离线`** —— 这就是本次要修的那个 bug，**修复未生效** |
| B2 | 桌宠点「实时变声」相关入口仍能点，点下去 404 |
| B3 | 后端日志出现 `sound.rvc-live` 相关 router 的 import/挂载**异常**（而不是干净地不挂载） |

### 顺带验（同一批改动里的另外两个可关能力）

同一手法各验一遍，判据同上（不许误报离线、入口要消失）：

- 关 `pet.market` → 皮肤/市场入口消失，桌宠不报离线；
- 关 `hook.wechat` → 「最近发送」行消失（`hide("recent", !CAP.wechat)`），桌宠不报离线。

### 回执

桌宠截图（气泡+药丸）、`/api/plugins` 的 JSON 片段、后端日志里 router 挂载那段。

## C. 音色库页门控（本次 09-21 改动，`b5be352`）

**背景**：`/voices` 是 `core.voices`（路由恒注册），但页内嵌了三个**可关能力**的面板：
试音间三件套（`AbCompareCard` / `AbChainCard` / `AuditionEntry`，属 `sound.audition`）、
作品库（`WorksLibrary`，属 `core.history`）、音色挖掘面板与导入链路
（属 `sound.mine` / `sound.workshop`）。关掉对应插件后端点不再挂载，面板却照旧渲染
→ 用户点一下 404 且看不出原因。
**关键**：`useVoices` 挂载时会轮询 `getMineState`，所以门控必须收进 hook，
只在 JSX 藏按钮不够（会每 3 秒空转刷一次 404）。

### 前置

- 至少 1 个已保存音色（否则 `p.voices.length >= 1` 不成立，试音间卡片本来就不渲染）。

### 步骤（逐个能力验，每次都要「改开关 → 完全退出 → 重开」）

对 `sound.audition` / `sound.mine` / `sound.workshop` 各做一轮：

1. 关掉目标插件（`POST /api/plugins/<id>/disable`）；
2. 完全退出 → 重开；
3. 进「我的音色」页，**打开浏览器 DevTools 的 Network 面板**（或看后端日志）；
4. 静置 ≥ 10 秒；
5. 看页面上的面板是否还在，以及有没有 404 请求。

### 预期现象

| 关掉 | 页面上应消失 | 不应出现的请求 |
|---|---|---|
| `sound.audition` | 盲听对比卡、多链路卡、「去试音间」入口 | `/api/ab/run`、`/api/ab/chain` |
| `sound.mine` | 「自动挖掘」整卡、侧栏「不满意？继续挖」 | `/api/mine/state`（**包括挂载时的轮询**） |
| `sound.workshop` | 「批量导入文件夹 / 选择文件 / 麦克风录音」三个控件与下方提示 | `/api/pipeline/status`、`/api/pipeline/run` |
| `core.history` | 作品库整块 | `/api/history*` |

**核心**：音色库页**始终可用**（它是核心页），只是少了几块；
**全程零 404**（Network 里不该有红的）。

🔴 **两个方向都要看，缺一不可**（2026-09-21 修正本条的判据）：

| 现象 | 含义 |
|---|---|
| Network 里**根本没发**对关掉端点的请求 | ✅ 门控生效（这才是预期） |
| 发了请求，回复 `404 application/json` | ❌ 门控漏了 —— 但至少是**可诊断**的 |
| 发了请求，回复 `200` 且 `content-type: text/html` | 💥 那就不是门控问题，是后端 SPA 兜底把 `/api/*` 吞了（2026-09-21 修掉）；前端只会抛 `Unexpected token '<'`，Network 面板里**连红都没有** |

修前实测：关掉 `sound.rvc-live` 后 `/api/rvc/live/status` 返回的就是 `200 text/html` ——
意味着本清单原先那句「点一下应该 404」**永远不成立**、而「零红」也照样成立，
两条判据一起把真问题放过去了。现在 `m2_server/tests/test_plugin_switch.py`
的 `test_a_disabled_capability_endpoint_is_gone_at_the_http_level` 钉住了这个语义。

### 观测点

- DevTools Network（或无 DevTools 时看 `backend.log` 的访问日志）；
- 页面截图（面板在/不在）；
- 门控的实现位置：`web/src/pages/Voices/index.tsx`（读清单）+ `useVoices.ts`（轮询门控）。

### 失败判据（命中任一条即不合格）

| # | 判据 |
|---|---|
| C1 | 关掉后**面板还在**，点一下拿到 `404 application/json` —— 门控没挂上或挂错了 id |
| C1b | 关掉后点一下拿到 **`200` + `text/html`** —— 这不是门控问题，是 SPA 兜底吞了 `/api/*`；先跑 `.venv/Scripts/python.exe -m pytest m2_server/tests/test_plugin_switch.py -q` 确认那条守卫还绿 |
| C2 | 关掉 `sound.mine` 后 `/api/mine/state` 仍被**周期性**请求（每 3 秒一次）—— 轮询没被门控收进去，这是"只藏按钮"的典型漏法 |
| C3 | **整页白屏 / 音色列表也没了** —— 门控写过头，把核心内容一起藏了 |
| C4 | 控制台报 `PluginCatalog` 相关异常 —— 清单获取失败时应当 fail-open（按可见处理），不是崩 |

### 回执

四组（每组：关的是谁 + 面板截图 + Network 截图或日志片段 + 是否零 404）。

## D. 桌宠发微信语音**真的换声**（`rvc_voice` 委托）

**背景**：`pet-actions.cjs` 的 send_text 载荷里 `rvc_voice: ""` 一度被记成
「桌宠面板单音色写死」。复核结论是**刻意的委托** —— 后端在 `rvc_voice` 为空时
按 `voice_id` 推（`resolve_rvc_voice`，实测 `kangaroo → kangaroo_v2`），
且面板本来就有音色下拉。本条的验收目标是**证明这条委托链真的通到换声**，
因为「留空」看起来太像漏填，光看代码说服不了人。

### 前置

- 微信在跑；`media/voicebank/` 里有目标音色（当前机器只有 `kangaroo`）；
- `D:\RVC\logs\` 下有对应实验目录（`kangaroo_v2`）；
- 桌宠面板的音色下拉**不是空的**（空的话先去 `/api/voices` 确认有 `has_reference` 的音色）。

### 步骤

1. 桌宠面板选一个音色（例如「袋鼠」）；
2. 发一条文字到微信；
3. 看 `steps` 里的换声那一条，并**听**收到的语音。

### 预期现象

- `steps` 里出现 **`RVC 换声 → kangaroo_v2`**（不是 `kangaroo`）；
- 收到的语音是**目标音色**，而不是通用 TTS 播音腔；
- 若推不到，`steps` 里会说明音色会不像 —— 那是**降级**，不是崩溃。

### 观测点

- 发送结果的 `steps`（源码 `m2_server/wechat_voice.py:1504` 附近，
  文案形如 `RVC 换声 → {名字}（用时 N.Ns）`）；
- 声音本身（人耳，或与直接调 `/api/tts` 的输出对比）。

### 失败判据

| # | 判据 |
|---|---|
| D1 | `steps` 里**没有**换声那一条，且没有"推不到"的说明 —— 链路静默跳过 |
| D2 | 换声名字与面板选的音色对不上（选 A 换 B） |
| D3 | 换声那一步报错 / 抛出（HTTP 500 或 steps 里带 traceback 字样） |

### 回执

`steps` 原文 + 一段收到的语音（或改用人耳结论 + 与 `/api/tts` 直出对比的差异描述）。

## E. 权重文件可用性（`auto_rb` 重装后 / 新装音色）

**背景**（本次 `be1d3fd` 查实的）：`auto_rb` 报「PyTorch 2.6 weights_only」是**误诊**。
真因是那两个 `.pth` 逐字节等于 `test_market_search_install.py` 的夹具
（`b"\x80\x02" + os.urandom(512*1024-2)`）—— 某次测试没隔离掉 `RVC_ROOT`，
把夹具写进了真实 `D:\RVC`。`weights_only=False` 同样加载不了；
而**所有真实音色**在 `weights_only=True` 下都正常。
已修的是**报错可读性**（`diagnose_pth` + `load_checkpoint`），
**文件本身仍是坏的，需要删掉后重装**。

### 步骤

1. 删掉坏文件（**先确认备份/知道要重装**，这是不可逆的）：
   - `D:\RVC\log` 下 `logs\auto_rb\`（含 `auto_rb.pth` / `added_auto_rb.index` / `source.json`）
   - `D:\RVC\assets\weights\auto_rb.pth`（与上面是**硬链接**，同一 inode）
2. 从音色市场重装该音色（或换一个）；
3. 装完后**立即**验证文件形状，别等报错：
   ```bash
   # 期望：zip 容器可读且含 data.pkl（或 pickle 前缀合法），大小是 MB 级不是 512KiB
   ls -l "D:/RVC/assets/weights/<id>.pth"
   ```
4. 用该音色跑一次离线变声 / 发一条微信语音。

### 预期现象

- 文件大小是**真实的 MB 级**（本机真实音色 `kangaroo_v2.pth` 约 57MB），
  不是恰好 `524288` 字节；
- 加载成功，`steps` 里出现换声；
- 若仍加载失败，报错应包含 **`结构判读：`** 一行，并明说
  **「这不是 PyTorch 版本问题」** —— 而不是 torch 那句误导性的
  "Re-running with weights_only=False will likely succeed"。

### 观测点

- 文件大小与魔数（`PK` = zip 容器 / `\x80` = pickle）；
- 加载失败时的报错原文（`diagnose_pth` 的判读结论）。

### 失败判据

| # | 判据 |
|---|---|
| E1 | 装完大小又恰好是 `524288` 字节 —— 装到的还是夹具/坏文件 |
| E2 | 报错里出现 `weights_only` 字样但**没有** `结构判读：` —— 说明走的是旧路径，修复没生效 |
| E3 | 有人把 `weights_only=True` 改成了 `False` 来"绕过" —— **这是错误的修法**（拿掉安全边界），有测试会红：`test_offline_vc_infer_pth_guard.py` |

### 回执

`ls -l` 输出 + 一次成功变声的 `steps`（或失败时的完整报错含结构判读）。
