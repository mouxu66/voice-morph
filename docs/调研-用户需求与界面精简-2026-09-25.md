# 调研：变声器类产品的用户需求与界面精简方向

> 2026-09-25 调研。触发：用户提出「感觉我们这个应用还是有点问题……我感觉我们功能有点太冗余了，太复杂了」。
> 方法：网上检索同类产品（Voicemod / MorphVOX / 叮咚 / 小火苗 / MagicMic / Clash 等）的用户评价与测评，
> 结合本仓前端实测（插件清单、首页、侧栏、极简模式现状）交叉判断。
> 证据分级：✅ 多家来源一致 / 📚 单一评测或厂商自述 / ❓ 待真机验证。

---

## 一、结论先说

1. **用户感受到的「冗余」往往不是功能多，而是「选项多到不知道从哪下手」**。
   行业里被骂得最狠的正是功能最全的 Voicemod —— 骂点不是缺失，而是「选项太多让人一开始不知所措」。
2. **真正的流失发生在第一天**。Andrew Chen 对 1.25 亿台设备的分析：App 平均 **3 天内流失 77% 日活**；
   另有 UX 研究称 **最高 80% 的用户因 onboarding 差而离开**。首次会话流失率可超 **70%**，
   而「界面杂乱」是最稳定的早期流失预测因子之一。✅
3. **行业解法是「渐进式披露」（progressive disclosure）**：新用户只看 3 个选项，不是 40 个。
   成熟产品把功能分三层——① 首屏唯一核心动作；② 按行为信号解锁；③ 永不自动露出，靠用户自己发掘。✅
4. **我们的问题不是「功能太多」，而是「功能暴露得太平、太早」**。
   本仓已有极简模式（且默认开启），侧栏其实只留 7 项 —— 所以「复杂感」主要来自
   **页面内部的并列信息密度**，不是导航。

## 二、用户真正要什么（按证据强度排序）

### 2.1 高频刚需（几乎每家测评都提到）

| 需求 | 证据 | 对我们的含义 |
|---|---|---|
| **自然、不像机械音** | 「音色生硬有 AI 感」「一听就是变声」是各测评列的第一大坑 ✅ | RVC 音色是我们的相对优势，应把「自然度」放到首屏可见 |
| **低延迟、不卡顿** | 「连麦存在延迟」「手游多人连麦卡顿断音」✅ | 我们有实测延迟数据，可以直接作为卖点 |
| **操作简单、零门槛** | 「界面很乱，找个功能要找半天，对小白不友好」✅ | ★ 本报告主题 |
| **免费/无广告套路** | 「免费版暗藏充值套路」「广告频发」被反复点名 ✅ | 开源本地跑，无广告是我们天然优势 |
| **不动系统设置就能用** | 「虚拟声卡那里我折腾了好久」✅ | 我们需不需要装虚拟声卡，是决策级问题 |

### 2.2 场景分布（用户实际在哪用）

按测评出现频率：**游戏开黑连麦 > 微信/QQ 语音 > 短视频配音 > 整蛊娱乐 > 直播** ✅

值得注意的是：**贴了「游戏内实时变声」标签的产品，几乎都被指出这条其实不成立**。
安卓侧的客观限制被行业文章讲得很清楚 —— Android 不允许第三方应用截取别的应用的麦克风流，
所以市面上的"实时变声"大多实际是「录完导出」（record-and-export），游戏里根本进不去。✅

> 原文：「Android's sandbox architecture blocks apps from intercepting another app's microphone stream,
> which is why most voice changer apps work in record-and-export mode, not live injection.」
> 「For games and Discord on Android, true real-time voice changing without root is largely unsupported.」

**这对我们是重要背书**：行业文章直接给出的建议是
「run the voice changer on a nearby PC, route audio through it」——
并明确说「The PC route is not a workaround — it's the configuration most serious content
creators and streamers already use.」✅

也就是说，**我们的「手机 → PC 串流推理」路线，与行业对"做不到的那部分"给出的唯一正解一致**。
这不是我们被迫的妥协，而是这个场景的标准答案。这一条应该写进我们的对外说明。

### 2.3 一个值得抄的结构（Voicemod 的用法文档）

Voicemod 官方的上手路径被压成三句话，非常干净：

1. 装上虚拟麦克风
2. 在你说话的 App/游戏里，把输入设备选成 Voicemod Virtual Microphone
3. 选一个声音，开始

**第 3 步才是"选声音"，前两步是"让它接上"。** 对照我们：
用户现在最该先做的事，可能不是「挑音色」，而是「确认链路通了」。我们的链路更长
（手机 mic → PC 推理 → 手机播放），更需要这种"先接通、再挑声音"的次序。

## 三、渐进式披露：行业标准解法

### 3.1 三层结构

| 层 | 内容 | 谁来触发 |
|---|---|---|
| 第一层 | 唯一核心动作 | 默认可见 |
| 第二层 | 进阶能力 | **行为信号**触发（如"建了 3 个歌单后出现协作歌单"） |
| 第三层 | 专家功能 | **永不自动露出**，靠文档/社区自己发掘 |

第三层的逻辑很关键：「发现的那一刻制造了奖励感和胜任感，这是教程给不了的」。
「当你用了几个月后偶然发现 Figma 的组件变体，你会觉得自己解锁了什么。这种感觉是被设计出来的。」✅

### 3.2 反面教材：早期 Microsoft Word

到 2000 年代中期，Word 的工具栏和菜单项累积过多，**微软自己的研究都发现用户找不到他们
知道存在的功能** —— 这直接导致了 Office 2007 的 Ribbon 重设计（把功能重组并部分藏进
任务导向的标签页）。✅

> 这段历史和我们现在的处境是同一个病：**功能都做出来了，但平铺在一起，于是等于没有。**

### 3.3 可量化的收益

Nielsen Norman Group 研究：渐进式披露能提升 **可学习性、效率、降低错误率**。
另有数据称 **超过 30% 的必填 onboarding 步骤其实可以完全删掉而不影响体验** ✅。

### 3.4 一条边界（别做过头）

「渐进式披露」≠「藏信息」。**定价、权限、重要后果、数据用途、关键流程信息不能藏。** ✅
对我们而言：环境体检、需要重装/下载多少 MB 这类"影响用户决策"的信息，必须留在能看见的地方。

## 四、我们现状实测（不是感觉，是数字）

### 4.1 界面暴露总量

- 前端页面目录：**16 个**，页面代码合计 **8596 行**。
- 后端插件清单：**20 个插件**（7 个 core + 13 个可关能力）。
- 侧栏主项：**7 个**（首页 / 我的音色 / 输字变声 / 实时变声 / 工具箱 / 试音间 / 训练变声 + 更多 2 项）。
- **但是**：有 **10 个能力没有导航入口**，它们散落在各页的 tab 里
  （音效器、特效声板、有声书、音色微调、音色挖掘、桌宠、微信发送、素材、历史、设备）。

> 侧栏整洁 ≠ 界面简单。**真正的复杂度藏进了页面内部的 tab 与并列面板里。**

### 4.2 已经做过的事（别重复劳动）

- **极简模式已存在，且默认开启**（`theme.ts`：`localStorage.getItem(SIMPLE_KEY) !== "0"`），
  默认把「更多功能」折叠起来。
- 首页已经做过一轮降噪：`HomePage.tsx` 里有明确注释 ——
  「此前顶栏写着「首页」、页内 hero 又贴一个 `HOME / 先玩，再定制`、往下还有七个等重的节标题，
  同一个词被砸了三次。这里收敛成一处」。
- 首页已经把首屏动作收敛成两个：「先听一个」/「我想做自己的」。

**所以问题不是「没人想过」，而是这套收敛只做到了导航层和首页，没往下贯穿到页面内部。**

### 4.3 页面体积排行（复杂度的物理证据）

| 页面 | 行数 |
|---|---|
| PetMarket 人偶市场 | 946 |
| Audition 试音间 | 876 |
| VoiceMarket 音色市场 | 828 |
| Live 实时变声 | 809 |
| Home 首页 | 646 |
| SoundboardPanel 声板 | 499 |
| Cascade 级联 | 487 |

**前四个都超过 800 行**。800 行的单文件页面，通常意味着它同时承担了「列表 + 详情 + 安装 +
对比 + 收藏 + 引导」多种职责 —— 这正是「感觉复杂」的来源。

## 五、具体建议（按性价比排序）

### P0 · 成本低、直接消解"复杂感"

1. **首屏只留一个动作**。行业共识是「新用户看 3 个选项，不是 40 个」。
   首页现在 hero 有两个按钮（先听一个 / 我想做自己的）—— 保留即可，
   但**往下每一屏都应只服务一个决定**，别再出现并列的多个入口。
2. **给「首次打开」单独一条路径**。Canva 的做法是注册时只问一句
   「你打算用 Canva 做什么？」，然后按答案裁剪整个体验。我们可以更轻：
   首次启动问一句「**游戏开黑 / 微信语音 / 做视频配音**」，只显示那条链路必需的步骤。
3. **给每页加「收起进阶」**。把 800 行页面里的对比、收藏、批量、参数这类内容
   收进一个默认折叠的「进阶」区。不改逻辑，只改默认可见性。

### P1 · 把行业验证过的次序搬过来

4. **把次序改成「先接通、再挑声音」**（抄 Voicemod 三步法）。
   我们的链路比它长，更需要先给一个「链路状态条」：手机连上没 / 后端活了没 /
   推理延迟多少 —— 通了再谈音色。
5. **把「自然度」和「延迟」提到首屏**。这是全行业一致的第一诉求，
   而恰好是我们有真实数据可秀的地方（我们有实测的 <200ms 目标与 VRAM 占用）。
6. **把 Android 限制讲成优势**。行业说「不 root 就做不到真·游戏内实时变声，
   正解是把处理放到 PC 上」—— 我们做的就是这件事。这应该是一个**显式的产品定位**，
   而不是用户在踩坑后自己悟出来的。

### P2 · 结构性

7. **10 个无导航能力的归口**。要么给它们一个统一的「工具箱」二级索引页
   （已经在工具箱里，但需要一条清晰的列表），要么明确标注它们属于哪个主流程的延伸。
   现状是它们只能靠"碰巧滑到那个 tab"被发现 —— 属于第三层功能
   （永不自动露出），这本身不算错，但**得有一条文档化的路径能找到**。
8. **给"能力管理"一个显式入口**。后端有 20 个插件、13 个可关，
   用户关掉后应该能在一个地方看到"我关了哪些、怎么开回来"。这属于
   §3.4 说的**不能藏的信息**。

### 明确不建议做的

- ❌ **不要删功能**。测评分野里"功能少"同样是差评（幻音盒子因「声线总量不足 50 种」被评 5.1/10）。
  要做的是**改默认可见性**，不是砍能力。
- ❌ **不要把 onboarding 做成强制教程**。「强制走完不可跳过的教程」被明确点名为
   bounce rate 上升的原因；每一步都要有 Skip，并保留随时重播的入口。
- ❌ **不要动首页已经收敛好的 hero 结构**（那是有注释保护的既有决定）。

## 六、给下一步的输入

如果要做，最小可验证的一步是 **P0-2：首次启动问一句用途，然后裁剪首屏**。
理由是：

- 它是行业里被反复验证、ROI 最高的一招（Canva / Slack 都在用）；
- 它不动任何现有功能逻辑，只加一层"默认显示什么"的判断；
- 它可以直接用行为数据证伪 —— 看首次会话是否走完关键动作。

需要先定的是：**我们认哪几种用途？** 目前看「游戏开黑 / 微信语音 / 配音」三类覆盖了
测评里的绝大多数场景，但要以我们自己的用户为准。

## 七、落地情况（2026-09-25 同日实施）

用户说「把这些都做了吧」，于是逐条实施。**但落地时发现报告里有两条是我想当然了** ——
记在这里，避免以后照着旧结论重复劳动或做错方向。

### 已做

| 条目 | 落点 | 说明 |
|---|---|---|
| P0-② 首次启动问用途 | `lib/useProfile.ts` + `components/UseCasePicker.tsx` | 三个用途（游戏开黑/微信语音/配音）+「我还没想好」。用途存 `vm-use-profile`、是否问过存 `vm-use-asked`（**必须分开**，否则跳过的人下次又被弹）。首页 hero 副标题与主次按钮按用途换 |
| P0-③ 进阶默认折叠 | `components/AdvancedSection.tsx` | 首页的「效果阶梯」+「术语表」两个区块收进去。**收起不是删除**，摘要行永远可见 |
| P1-④ 链路状态条 | `components/ChainStatusBar.tsx` | 后端/虚拟声卡/发送链路/输字链路四格，放在"挑声音"之前。落实「先接通、再挑音色」 |
| P1-⑤ 真实卖点条 | 首页 | 自然度 / 不吃配置 / 全程本地 —— 见下方"没做的那条" |
| P2-⑦ 能力索引页 | `pages/CapabilityIndex/` + `core.system` 的 `/tools` 路由 | 给散落的无导航能力一个统一落点。侧栏底部加「能做的事」入口 |

### 没做，以及**为什么**（比"做了"更重要）

1. **P0-①「每屏只服务一个决定」没有单独实施** —— 它与 P0-③ 是同一件事的两种说法，
   折叠区已经达到效果。单独再改一遍是重复劳动。

2. **P1-⑤ 原计划写"延迟 <200ms"——没写，因为那是目标不是实测。**
   `docs/ROADMAP.md:269` 明确把「实时链路延迟实测」列为**待验收项**，
   `功能档位与落地说明.md` 里的 "<200ms" 是**目标值**。
   把目标当实测摆到首屏，正是本报告第二节批评的那种"美化参数"。
   改成了三个**可验证事实**：音色自然（有本地评分模型）、8GB 显存可跑（实测）、
   全程本地（架构事实）。**等真机延迟测出来再加数字。**

3. **P0-③ 原写的"四个长页面加折叠"只做了首页。**
   实读 `Live` / `Audition` / `VoiceMarket` / `PetMarket` 后发现：它们是**操作面板**
   而非并列内容区，内部已有各自的折叠（如 `LivePage` 的 `logOpen`）。
   硬塞「进阶」区会**打断操作流**，是负收益。**行数多 ≠ 结构乱** ——
   这条建议当时是按行数推的，实读后不成立。

4. **P2-⑧「能力管理显式入口」发现早就做了**（`AppChrome` 里常驻且带计数，
   2026-09-23 补的）。差点重复劳动。**教训：动手前先查现状。**

### 新增的一条建议（实施中发现的）

5. **P2-⑨ 索引页需要跨语言门禁**（已做）。手工维护的索引表必然漂移，
   而漂移是**静默的**——现象是"某个东西找不到"，用户不会来报 bug。
   所以配了 `capabilityIndex.test.ts`：读后端所有路由 path，逐个断言索引页里出现过。
   **它当场就抓到了漏项**（`/pet-market` 被我手写成 `/pet`）。

### 门禁与测试

- 前端 `npx vitest run`：**198 条全过**（原 169 + 新增 29）
- `tsc --noEmit`、`eslint src`：干净
- `tools/check.py --fast`：**七项全过**
- 变异测试 5 个（撤第二个 key / 取链路条门控 / 改 badCount 口径 / 去 ready 门 /
  去索引页门控）**全部被捕获**，还原后逐字节核验、零残留
- 细节记在 `docs/犯错档案-工程.md` §8.52、速查表 93–95
