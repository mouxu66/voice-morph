# 特效声板（Soundboard）设计

> 2026-09-23 拍板。目标用户场景（用户原话）：**"我在录入一段文字让它变成语音，按住 Alt
> 说话的时候可以突然来一声爆炸声，这样有趣一点。"**
> 即：实时聊天中一键插入音效 —— 不是做剪辑软件，是给变声聊天加"综艺感"。

## 一、核心决策

| 决策 | 结论 | 依据 |
|---|---|---|
| **实时声板是主轴** | 按 Alt 说话中途点格子即时出声，与 RVC 实时变声**同时**进微信 | 用户明确用法；下文 §二 证明技术可行 |
| 离线混音是配菜，但**必须有** | 发送前勾选音效 → 烘进音频（已实现为 `POST /api/soundboard/premix`） | 它是"点格子会抢焦点"那条路的兑底（见 §五），不是锦上添花 |
| 预混端点放**声板**插件，不放 `effects.py` | 两条路径共用一份 DSP（`sfx_lib.mix_into`），但端点归 `sound.fx-board` | 面板属 `sound.fx-board`；端点若挂 `sound.effects`，关掉效果器后按钮就 404（速查表 74/§8.40 同一类缺口）。`effects.py` 里的 `mix` 效果类型是顺手多给的一个入口（"给任意音频插一声"） |
| **半自动播放窗口同样可用** | 文字转语音 → 播到声卡 → 按 Alt 录制期间点格子，TTS 人声与音效同进一条语音 | §四锁分析：声板**不进** `_send_lock`，播放窗口内点格子畅通 |
| 引擎进本体、素材走下载 | `sound.fx-board` 插件带引擎+6 个出厂音效；更多素材包走 `core.market` | 用户"一切皆插件"思想：本体小、按需下载 |
| 素材**只收 CC0** | 出厂包全部 CC0（可随开源项目再分发，零署名义务） | 调研结论，见 §六 |
| 不碰微信自动化 | 声板只管"把声音播进 CABLE"，微信怎么录走是现有链路的事 | 微信模块是全仓坑最密集区（犯错档案-微信.md 通篇），能不碰就不碰 |

## 二、为什么"实时"成立（调研 + 本仓实测）

**外部调研**：这正是 Discord/游戏主播圈成熟多年的 **soundboard + 虚拟声卡**玩法；
剪映等剪辑平台则是另一条路（云端素材库 + 时间线离线混音），不做实时注入 —— 我们两边各取所需。

**技术关键**：Windows 音频默认 **WASAPI 共享模式，多个应用同时往同一设备发声由系统混音器
自动混合**（独占模式才互斥，普通播放不会触发）。而本仓的实时变声链路恰好是共享模式的常驻形态：

```
RVC 实时变声（常驻）────写──→ CABLE Input ─┐
                                            ├ 系统自动混音 → CABLE Output → 微信当麦克风录
声板点「爆炸」────────写──→ CABLE Input ─┘
```

**本仓实测锚点**：
- `wechat_voice.py` 的实时变声（`rvc_live`）与 `manual_send` 流程已在同一虚拟声卡上并存运行；
- `play_worker.py`（91 行，常驻子进程，行协议 `ready/playing/done/error`）就是现成的
  "随叫随到"播放底座 —— 声板**复用它的协议与设备解析**，冷导入成本为零；
- `_send_lock` 只串行化"发送流程"，声板走**自己的轻量互斥**，两者互不阻塞。

## 三、总体架构

**新插件 `sound.fx-board`（特效声板）**，与 `hook.wechat` 平级、独立可关：

```
m2_server/
  soundboard.py            # 路由：catalog / play / stop / warm / import / delete
  board_worker.py          # 声板常驻播放器（预载素材 + 非阻塞抢占式 one-shot）
  plugins/sound.fx-board/plugin.json
  plugins/sound.fx-board/samples/   # 出厂 6 条（+ manifest.json 存名字/标签）
media/soundboard/          # 用户**导入**的音效（<media> 随用户数据根走）
web/src/pages/
  Tts/SoundboardPanel.tsx  # 声板格子面板（自门控；挂 WechatSendPage ② 与 ③）
  Tts/useSoundboard.ts     # enabled 契约 + 预热 + 乐观高亮
tools/gen_sfx.py           # 出厂素材合成器（可复现，改音色 = 改参数）
```

插件清单（沿用 `sound.effects` 的形态）：

```json
{
  "id": "sound.fx-board", "name": "特效声板", "kind": "builtin",
  "category": "sound", "order": 145,
  "summary": "聊天/语音消息中一键插入爆炸、掌声等短音效（实时播进虚拟声卡）",
  "requires": [],
  "routers": ["soundboard"], "hooks": [], "routes": [],
  "extras": { "python": [],
              "external": [{ "kind": "audio-device", "label": "VB-Audio CABLE（虚拟声卡）" }] }
}
```

**实现时改过一处决策：`requires` 从 `["sound.rvc-live"]` 改成 `[]`**（2026-09-23）。
理由：

1. 声板真正依赖的是**虚拟声卡**（外部设备，已用 `extras.external` 声明），不是实时变声引擎；
2. §五 的第二个场景（② TTS 播到声卡 + 回格子）**根本不跑实时变声** —— 挂上那依赖等于白白加了一道门槛；
3. `enabled_ids()` 会把"被启用插件依赖的已关插件"**复活** —— 用户只想拿声板配 TTS，
   却会连带被拖起 `sound.rvc-live`（torch + 模型）。那是很重的隐形代价。

门控照旧：面板挂在 `hook.wechat` 的页面里，所以**必须** `pluginVisible(catalog, "sound.fx-board")`
（速查表 74 / `docs/犯错档案-工程.md` §8.40 —— 宿主开着、被托管插件关着是可达状态）。

## 四、后端设计（board_player + 路由）

### 播放器要点

1. **预载常驻**：启动时把 `media/soundboard/*.wav` 全部读成 float32 PCM 常驻内存
   （one-shot ≤3s / 48kHz / 单声道 ≈ 0.6MB/条，6 条合计可忽略）。点格子 → 零 IO 直播。
2. **自带独立常驻播放器**（`board_worker.py`，实现在 P1 就定型了）：
   设计稿原打算"复用 `play_worker.py` 的协议"（方案 A/B），落地时改成了**独立进程**。
   原因是一个**静默故障**：`play_worker` 的行协议是**单命令串行**消费的
   （`_PlayWorkerHandle` 会把 stdout 上**所有**行都当自己那条命令的响应）。
   于是：TTS 人声正在播（占着 handle）→ 用户点"爆炸" → 爆炸的 `playing/done`
   被 TTS 的 handle 吃掉 → **TTS 那条命令提前认为播完 → 微信提前松开发送 → 消息被截断**，
   而界面显示成功。它只在"发送期间点声板"这条组合路径上现形 —— 正是用户主场景。

   所以两条链路各自持有自己的管道，互不消费对方的行；代价是多一个常驻子进程
   （顺便也换来了 P1 就有的好处：**非阻塞** `sd.play(blocking=False)` + **抢占**）。
   另一个红利：`wechat_voice.py` / `play_worker.py` **一行都不用改**。
3. **互斥**：声板自己的两把锁 —— `_CMD_LOCK`（
   worker 的行协议是「一条命令一行响应」，两条命令同时飞会让响应错位）与
   `_STATS_LOCK`（计数的读-改-写）。**不进 `_send_lock`** —— 那是发送语义的锁，
   进去就等于"录制中点格子要等 TTS 播完"，用户场景直接失效。
4. **音量**：`gain` 参数（0~1.5），播放前乘系数，默认 0.9；预载时统一归一化到峰值 0.9，
   避免某条素材震耳。
5. **播放计数**：`outputs/soundboard_stats.json` 记 `{id: count}`，`/catalog` 一起返回 ——
   就是用户最初想要的"使用热度"，本地零依赖；素材包市场版（P2）再叠加 GitHub Releases
   asset 的 `download_count`。

### 路由（prefix="/api/soundboard"）

| 端点 | 语义 |
|---|---|
| `GET /catalog` | `{ok, items:[{id,name,tags,duration_s,count,builtin}]}`（不含任何文件系统路径） |
| `POST /play` | `{id, gain?}` → 立即返回 `{"ok":true,"playing":true}`（非阻塞，不等播完） |
| `POST /stop` | 停掉当前 one-shot |
| `POST /warm` | 预热常驻播放器（面板挂载时调；否则第一次点击要付 ~2-3s 冷导入） |
| `POST /import` | 上传音频 → 校验（≤5s、≤2MB）→ 存 `<media>/soundboard/` |
| `POST /premix` | `{wav?, inserts:[{sample,mode,at_s,gain}]}` → 离线混出一条新 wav，返回 `{wav,seconds,inserts,skipped}`（`at_s` 只在 `layer` 生效；越界会贴到末尾并在 `skipped` 里说明，见 §五之「第 N 秒」） |
| `DELETE /{id}` | 仅可删导入的（出厂音效不许删） |

三条与"顺手写法"不同的决定（预混是**发送前置**动作，错了会发出一条内容不对的语音）：

1. **输出名带 `sfxmix_` 前缀**，不用 `tts_`：发送链路的默认口径是「取最近一条
   `tts_*.wav`」（`_resolve_wav` / `last_tts` 都这么找），混过的文件若叫 `tts_*`
   就会成为默认目标 —— 于是"再合成一条、点发送"会发出**上一次混过的旧内容**，
   且全程无报错。单测里有一条专门钉这个。
2. **同名覆盖 + 原子替换**（写 `.tmp` 再 `os.replace`）：反复试混不堆垃圾文件，
   也不会让正在播的那条读到半截文件。
3. **坏输入当场 4xx**（未知音效 / 未知位置 / 一条都没混进去），而不是像效果链那样
   "跳过并记录"：预混是一次明确的用户动作，静默跳过 = 发出的语音里少了那一声，
   而界面看不出任何异常。反之，效果链是批处理，单环失败不该让整条任务死。

实现与设计的两点差异（均为**简化**，不是妥协）：

- **不重采样**：导入素材保持原生采样率。播放端 `sd.play(data, sr, device=...)` 与
  `play_worker` 同路径（TTS 产物本来就是各种采样率，PortAudio 在共享模式下会处理）。
  多一道重采样只会多一个失真环节。
- **导入重名直接拒**（而不是自动改名/覆盖）："到底哪个在响"这种事，
  拒绝比隐式规则好查。

安全沿用既有惯例：上传走 `MAX_UPLOAD_BYTES`、路径只认 `OUTPUTS_DIR`/素材目录内的文件名
（拒绝 `..`），目录枚举不给绝对路径。

## 五、前端设计

音效格子面板目前挂在**四处**（同一个组件、同一份素材目录；宿主页不同，所以模式与门控写法也不同）：

| 挂点 | 宿主插件 | 模式 |
|---|---|---|
| 微信发送页 · ③ 手动 · 实时变声说话 | `hook.wechat` | 只有实时 |
| 微信发送页 · ② 半自动 · 播放到虚拟声卡 | `hook.wechat` | 实时 + 预混 |
| 实时变声页 · RVC 实时控制台 | `sound.rvc-live` | 只有实时（**主场景**，2026-09-24 加）|
| 实时变声页 · 千问变声控制台 | `sound.rvc-live` | 只有实时（**主场景**，2026-09-24 加）|

格子本身长这样：

```
[💥 爆炸] [👏 掌声] [⚠️ 警报] [🎵 升调] [🔔 叮] [👻 鬼畜]
```

- 点击 → `POST /play`，格子播放时高亮 ~播放时长（乐观 UI，不等响应）；
- 门控：整块 `pluginVisible(catalog, "sound.fx-board")` —— **必须**，速查表 74/§8.40
  的教训就是"宿主页挂着别的插件的 UI 没门控"；
- hook 契约：`useSoundboard(enabled)`，`enabled=false` 时不打后端（`useEffects` 同款）；
- P1 不做全局热键（全局键盘钩子是坑区，`hook.wechat` 有先例但别在 P1 背）；
  鼠标点格子已覆盖主场景 —— 手在微信按 Alt，鼠标点一下格子是自然动作。

### 一步到位：混好即自动发送（2026-09-25 加）

用户原话："我的系统里面不是有自动点击 alt 吗，不用手动点击……我想让你来自动化来搞。"

所以 ② 半自动的预混区多了一个按钮 **「混好并直接发送」**：
`POST /soundboard/premix` → 紧接着 `POST /wechat/send_voice`。
后者本来就是全自动的（程序点话筒进入持续录音态 → 播 → 点浮层绿钮 → UIA 复核），
**不需要人按 Alt** —— 所以这条路从头到尾没有 "按住 Alt 时点格子会不会被抢焦点取消" 的问题
（那正是 §G 的 G2，只在 ② 的"手动按 Alt"与 ③ 手动档上存在）。
用户动作只剩两个：勾哪一声、点一下。

为什么值得把两步并成一步（而不是"再点一下 ① 而已"）：两步之间那个
"发送目标已换成 `sfxmix_*.wav`"是界面上**看不见**的中间态 —— 用户在第 ② 步之后回 ① 之前
若重新合成了一条，`useWechatSend` 会（正确地）让预混失效，于是发出**没混的那条**，
而界面一句提示都没有。新按钮把 `wav` **显式**交给发送方，顺序只剩一种
（与 `useWechatSend` 里 `premix.source === sourceWav` 那条失效判据同一判据）。

⚠️ 同一条路上"**真人实时说话**"（③ 手动档 / 实时变声页）**还没有**全自动档：
那两处的人声来自用户的嘴，录音窗口必须由人开始与结束。要自动化它得给 `wechat_voice.py`
加两个薄端点（点话筒起录 → 说完点绿钮发送），而那正是 2026-09-25 另一条线在改的文件。

### 精确时间点：第 N 秒（2026-09-25 加）

`at_s` 早在 `sfx_lib.mix_into` 里就支持（`layer` 档：在第 N 秒处叠加），可界面上只能表达
"开头/叠加/结尾"三个词 —— 于是"说到第 3 秒来一炮"这种最自然的用法反而做不到。
现在「叠加」档的胶囊上直接多一个秒数输入框：

    [💥 叠加 第 [1.2] 秒 ✕]

三条设计判断（都是"别自作聪明"那一类）：

1. **只给叠加档**：开头/结尾是拼接，位置由档位本身决定；在它们身上放一个秒数框，
   用户填了也不会生效（后端也只在 `layer` 分支里读 `at_s`）—— 那是界面在骗人。
   `useSoundboard` 发请求时同理：非叠加档一律发 `at_s: 0`，不带着一个看着像生效的值。
2. **输入框不设上限**：面板只有在拿到 `sourceSeconds`（② 从 `lastTts.duration_s` 传下来）时
   才真知道人声多长，缺省时按最大值封顶等于**默默改掉他填的数**。改成两层：
   面板上先给一行看得见的琥珀色提醒，越界的**结果**由后端如实回报。
3. **越界就贴尾，但必须说**：`mix_into` 的夹紧本身是对的（贴到末尾，而不是留一截静音 ——
   静音在微信里就是一段空白），但静默夹紧会把"第 30 秒"变成"贴到末尾"，
   而调用方拿到的是一条完全成功的响应。所以现在它会在返回的 `notes` 里带一句
   `指定第 30.0s 超出人声长度（4.4s），已贴到末尾`，面板把它列在按钮下方。

> `notes`（响应字段名仍是 `skipped`）里既有"真跳过"（音效读不出来）也有"位置变了"
> 这类提示；面板**统一列出来**而不分类 —— 两者都是"界面看不出异常"的失败，
> 而分类只会让其中一类在某个版本里被漏掉。

**波形（2026-09-25 同日跟进）**：秒数框是精确手段，不是主要入口 —— 用户知道的是
"说到那句的时候来一炮"，那是**看在眼里**的，不是数出来的。所以预混区多了一条源人声波形，
音效位置就是波形上的**可拖记号**（`pages/Tts/PremixTimeline.tsx`）：

- **纯前端解码**（`fetch → decodeAudioData → 每桶取峰值`），**不加后端端点**。后端要多一条
  `/peaks` 就得在"素材目录枚举"之外再开一条读任意 outputs 文件的口子；而浏览器本来就要把
  整段音频拿来才能画。这条路径坏了也不影响实时声板与预混本身。
- **一枚记号都没勾时不解码**：面板挂在页面上就一直在，没勾任何音效却去拉整段 wav 是白烧 CPU。
- **解码失败不清空能力**：环境没有 Web Audio / fetch 失败 / 文件已过期时**写明原因**，
  秒数框照旧可用（拖不动 ≠ 定不了位）。"降级成一句可读的说明"与"静默不显示"在界面上
  看起来一样，但后者会让用户以为这功能坏了 —— 与上面那条"不静默跳过"是同一判据。
- **点轨道不移动任何记号**：多枚音效时"点一下该动谁"没有正确答案，误移比不移更糟
  （用户不会发现位置变了）。移动只有两个入口：拖记号本身、聚焦后按 ← →（±0.1s）。
- 取样取**峰值**不取 RMS：人说话的位置靠"看得见的口型"判断，峰值画出来的形状更接近
  "哪里在说话"；RMS 会把停顿与轻声糊成一片。

### 主场景：实时变声页（2026-09-24 新增）

用户原话："让边实时变声边打音效成为主场景，而不是只能在微信发送页用。"

它比微信发送页那条路**体验完整得多**，原因是一条实现细节：自我监听回环进程
（`rvc_monitor.py`）**tap 的正是 CABLE Output**，而 CABLE Output 就是微信/游戏当麦克风采的
那一支 —— 所以写进 CABLE Input 的音效，开自我监听时**用户自己耳机里也听得到**。
微信发送页那条路没有这个回环，点完只能回微信里逐条回放验证（§「已知边界」那一大段讲的就是它）。
实时变声一开，点击 → 当场听到 → 对方也听到，反馈闭环是完整的。

技术前提已核实（不是推断）：实时链路是 WASAPI **共享**模式
（`D:/RVC/rvc_headless.py` 的 `sg_wasapi_exclusive: False`），两种声音可以并发写同一设备。
仍需真机确认的是"变声真跑起来时混得起来"，见验收清单 §G 场景 C。

挂点与门控（**这一页的规矩与 Tts 页不一样，别照抄**）：

- hook 在**路由层**（`pages/Live/index.tsx`）调一次，两个 tab 共用 —— 各调一次就是两回预热
  + 两回目录请求，而且两块的"正在播"高亮会各说各话（与 Tts 页同一条判据）；
- **不按 `sound.rvc-live` 门控**：本页的路由由它认领，关掉它整页都不存在，
  所以"宿主开着"在这一页恒真 —— 再按它门控就是**过度门控**（把还能用的功能藏掉），
  与 `pages/OfflineVc/index.tsx` 前两个 tab 是同一条判据；
- **按 `sound.fx-board` 门控**，且门控写在**面板自己身上**（组件里 `if (!on) return null`）——
  这样它无论被谁塞进哪个页面都安全；门禁 `crossPluginGate.test.ts` 同时钉住上面两条；
- **不提供预混**：预混的输入是一条 `tts_*.wav` 合成产物，实时链路里没有这一步，
  硬挂上去只会渲染出一个按下去必然 4xx 的按钮；
- 两个 tab 都挂（RVC 实时与千问变声都是"说到一半插一声"的实时链路），
  且都是实时档 —— 这里不需要预混那条兑底。

### 半自动窗口内注入（「文字转语音 + 录制中点一下」，用户主场景之二）

用户场景：② 半自动把 TTS 产物播到声卡、按住 Alt 录制期间点格子 —— 爆炸与 TTS 人声
同时进 CABLE，微信**一条语音同时录到两者**。技术上与 §二 完全同机制（共享模式自动混音），
而锁的设计恰好为此留了门：TTS 播放流程持有 `_send_lock`（发送语义），声板**不进这把锁**
（§四第 3 条），播放窗口内点格子畅通无阻。

**已知风险（必须真机验收）**：点格子的瞬间鼠标焦点会离开微信 —— 按住的 Alt 录音
会不会因失焦被微信取消，**未验证**。若会取消，退路两条：
1. **预混模式（已实现）**：面板上切到「预混」→ 点格子只勾选、不发声 →
   点「混进这条语音」→ `POST /api/soundboard/premix` 把音效烘进一份新音频
   （`sfxmix_*.wav`），发送目标自动换成它。确定性 100%，代价是没有"即时感"。
   **实现时改了设计稿这条的走法**：原计划"走 effects 的 `mix` 链"，实际端点在
   **声板插件**里（理由见 §一 表格第二行），两份实现共享同一份 `sfx_lib.mix_into`——
   所以"叠加/开头/结尾"三个词在两条路径上行为完全一致。
   位置三档：**叠加**（与人声同时，等价于实时声板）/ **开头**（先炸再说话）/ **结尾**。
2. 全局热键触发（P3，不抢焦点）。

真机验收对应条目：Alt 录制中点格子后，语音消息是否同时含 TTS 与音效；失焦是否中断录音。

### 桌面特效窗口（悬浮声板窗，2026-09-25 **已实现**）

用户原话：「你能在我桌面上加一个窗口吗？新加一个特效窗口……但是（它）录进去的时候，
反正就很麻烦。」两个「麻烦」其实是两件互不相干的事，设计先把它们分开：

1. **说话时点它，会不会把微信的按住录音打断** —— 就是 §半自动 那段里的 G2（焦点问题）；
2. **它会不会被屏幕录制/截屏录进去** —— 内容保护问题，**与微信语音一点关系都没有**
   （音频进微信靠的是共享声卡混音，见 §二，跟窗口在不在屏幕上无关）。

#### 为什么必须是「不激活」的窗口

现有四个挂点**没有一个**能承担「按住 Alt 说话时点一下」：

- **主窗**是普通可聚焦窗 → 点它必然抢前台；
- **桌宠窗口也不是非激活窗**：`pet.cjs` 只挂了
  `setIgnoreMouseEvents(v, {forward:true})`（点击穿透），窗口本身
  **没有** `focusable:false` —— 因为面板里要能打字，必须可聚焦。
  于是「点桌宠面板」= 把前台从微信抢走，与点主窗等价；
- `alt-hint.cjs` 的置顶横幅**是** `focusable:false` + `showInactive()`，但它全程
  `setIgnoreMouseEvents(true)`（纯装饰）→ 从没验证过「非激活窗能不能被点到」。

所以新窗必须自己立住这条范式：**`focusable:false`（= Win32 `WS_EX_NOACTIVATE`）
+ `showInactive()` + `setAlwaysOnTop(true, "screen-saver")`，且**不开**点击穿透
（穿透就点不到了）。这正是 Windows 上「看得见、点得到、不改前台窗口」的唯一形态。

> ⚠️ **这条设计的第一个验收就是它本身**，而且必须用 **SendInput 级真实鼠标**：
> CDP 的 `Input.dispatchMouseEvent` 走的是渲染进程自己的输入管线，
> **测不到 OS 的激活路径** —— 用它点成功了不能证明真人点不会抢焦点（自欺）。

#### 窗口规格

| 项 | 决定 |
|---|---|
| 尺寸 | 2 行 × 最多 6 列（12 条素材时不换行溢出，内部横向滚动）；约 360×150 |
| 默认位置 | 屏幕右下角、**桌宠正上方**（贴同一个角落，用户已习惯往那儿看） |
| 外观 | 复刻 `pet.html` 的设计令牌（暗色玻璃 + 品牌紫 + 格子高亮），不另设一套 |
| 建窗 | `focusable:false` / `frame:false` / `transparent:true` / `alwaysOnTop("screen-saver")` / `skipTaskbar:true` / `show:false` |
| 显隐 | 一律 `showInactive()`；**不用** `show()`（那会尝试激活） |
| 拖动 | 抄 pet 的「渲染器报按下/移动 + 主进程 `setCursorScreenPoint` 挪窗」——`app-region` 在置顶透明窗上不可靠（pet.cjs 已记过） |
| 位置/开关 | 落盘 `userData/sfx-window.json`（抄 `pet.json` 的 `loadPref/savePref` 形状） |
| 收起 | 窗内一个「—」按钮 → `hide()`（不 destroy）；应用退出时**必须 destroy** |

#### IPC 面（渲染器不直连后端，抄桌宠那条路）

preload 只暴露：`sfx:list`（→ `GET /api/soundboard/catalog`，不带任何文件系统路径）、
`sfx:play(id)`（→ `POST /play`）、`sfx:stop`、`sfx:hide`、`sfx:drag-start|move|end`。
主进程侧复用 `backend.cjs` 的 `httpJson/backendPost`。

#### 行为规则（都是「别自作聪明」那一类）

1. **连点不禁用**：`board_worker` 是抢占式 one-shot，第二下就该「停前一声、播这一声」。
   防抖会让人以为「点太快没反应」—— 而主播式音效板恰恰是连点。
2. **播放高亮 + 失败必须可见**：格子按下时高亮 ~素材时长；后端 503（设备缺失）/404
   （素材被删）时格子上出红边 + 窗内一行可读原因。**静默失败是最不能接受的**
   （与预混那两条判据同源）。
3. **只做「实时」档**：预混（离线混音）不进来 —— 它的输入是一条要发送的 `tts_*.wav`，
   与「边说话边点」是两条路；塞进来会让「这一声到底进没进那条语音」变成猜。
4. **热键是兜底，不是替代**：若真机证明点击仍会激活（A1 失败），立刻退到
   **F1–F6 逐格热键**（绝不能含单 Alt —— 那会和微信按住说话打架）。窗口与热键
   都保留：窗口管「看得见」，热键管「碰不到鼠标时」。
5. **录音期自动浮现**（默认开）：收到 alt-hint 的 `press` 阶段 `showInactive()` 一次，
   `done` 后 ~3s 收起。这样「说到一半想点」时它**一定在眼前**，不用先去找热键。
6. **不做屏幕录制保护**（2026-09-25 用户拍板）：他关心的只有「点它会不会打断录音」；
   要做时可用 `setContentProtection(true)` 让窗口不进截屏/录屏（Windows 上生效），
   代价是连用户自己的截图里也看不到它 —— 所以**不要默认开**。
7. **销毁路径要接全**：主窗 `closed` 时与 `alt-hint` 一并 destroy（`window-all-closed`
   要求「一个窗口都不剩」，隐藏窗会让应用退不掉 —— alt-hint 那次实测踩过）。

#### 一个必须顺手修的既有缺陷（否则新窗只能显示 🎧）

emoji 现在**只活在** `SoundboardPanel.tsx` 的 `ICONS` 映射里（`boom→💥` …），
后端 `catalog` 只给 `id/name/tags/duration_s/count`。新窗若自己再抄一份
「id→emoji」，就是**第二处会漂的产品规则**（导入素材还一律落到 🎧）。
正确做法：把 `icon` 收进 manifest（出厂 6 条 + 音效包格式 + `/import` 可选参数），
由后端随 catalog 返回，前端两处都从它渲染。

#### 验收（机器能自证的部分）

- **A1（最关键）**：微信/记事本在前台 → 记录 `GetForegroundWindow()` → **用 SendInput
  真鼠标**点一格 → 断言：`/catalog` 的 `count` +1 **且** 前台 hwnd **未变** **且**
  主进程读到 `win.isFocused() === false`；
- **A2**：CDP 只用来读状态与截图，**不用来点**（点了不算数，见上）；
- **A3**：收起 → 热键唤出 → 位置与上次一致（`userData/sfx-window.json`）；
- **A4**：退出应用后进程不残留（隐藏窗必须 destroy）；
- **A5（仍须人耳）**：微信里按住 Alt 说着话点它，录音**不断**、那一声进得去。

#### 实现纪要（2026-09-25，已进安装版）

用户拍板的三件事：**默认收起 + 录音期自动浮现 + 热键随时唤出**；**不做**录屏保护；
同意重打 asar。

新增/改动的文件：

| 文件 | 作用 |
|---|---|
| `web/electron/sfx-window.cjs` | 建窗/显隐/销毁 + IPC + 热键 + `userData/sfx-window.json` |
| `web/electron/pet/sfx-window.html` | 格子渲染层（hide/show 复用，不重载页面） |
| `web/electron/pet/sfx-preload.cjs` | IPC 白名单（渲染层拿不到任何路径） |
| `web/electron/main.cjs` | 装配：注册 IPC/热键；主窗 `closed` 与 `before-quit` 里 destroy |
| `web/electron/alt-hint.cjs` | `press` → 唤出声板窗；`done` → 3s 后收起 |
| `web/electron/pet.cjs` | 右键菜单加「特效声板窗口（说到一半点一声）」 |
| `m2_server/sfx_lib.py` + 两份 manifest | 素材元数据新增 `icon`（格子图标随 catalog 下发） |
| `web/src/…/SoundboardPanel.tsx` | 改用 `it.icon`；旧后端仍回落到内置图标表 |

**A1 真机实测（2026-09-25 下午，安装版 0.2.4 + 重打 asar）**：

- 热键用**真键盘 SendInput**（Ctrl+Alt+S）→ 窗口出现，`sfx:info().focused === false`；
- 把前台换成微信（`GetForegroundWindow` = 微信）→ **SendInput 真鼠标**点「💥爆炸」格子 →
  catalog 里 boom 的 `count` **8 → 9**（连跑三次：9→10、10→11）而 **前台 hwnd 始终没变**，
  `isFocused()` 与渲染层 `document.hasFocus()` 均为 false；
- 定位用的是 **OS 的 `GetWindowRect`**（进程声明 DPI 感知）而非 Electron 的 DIP 推算 ——
  两条路算出来一致（DIP 1296 + CSS 70×1.5 ≈ 物理 2092），所以哪一条都不必猜。

三条容易踩的自欺，写在这里免得下个人重踩：

1. **CDP 的可信鼠标事件验不了这件事**：它走渲染进程自己的输入管线，绕过 OS 的激活路径。
   要验「点它不改前台」只能用 SendInput（或人手）。本轮先写错了、后来重写；
2. **收起后调试目标仍在**（hide 不销毁）→ 验收脚本别断言「目标列表里没有它」，
   要断言 `visible === false`；
3. **高亮只保留素材时长那么久**（boom 1.4s）→ 想验「点下去有反馈」必须在时长内读，
   读完再确认它会自己落。

拖拽另加了一道「粘住」防护（与上面三条无关，排查窗口位置时发现的）：指针在窗口外松手、
或窗口被收起时 `mouseup` 可能根本收不到，不兜的话 `dragging` 永远是 true ——
**之后鼠标一动窗口就跟着跑**，用户看不出原因也难以自恢复。现在 `blur` / `mouseleave` /
`visibilitychange` 都会结束拖动（渲染层单测已钉）。

**窗口位置**：默认落在「右下角、桌宠常用位置的正上方」，只在**真拖动过**之后才落盘
`userData/sfx-window.json`（清掉 pref 后干净启动实测：DIP 1297×419，点击与收起/唤出都不挪窗）。
位置是被记忆的用户数据，所以换了显示器后一定要过 `clampToWorkArea` ——
非激活窗如果被丢到屏外，用户既看不到也没常规手段拖回来。

## 六、素材：来源与版权（调研结论）

| 来源 | 许可 | 结论 |
|---|---|---|
| **Kenney**（kenney.nl）Impact Sounds 130 条 / Interface Sounds 50 条 / Digital Audio | **CC0**，官方明确标注 | 仍是**你将来上架货架时**的首选（再分发无需署名、完美契合开源）；但代码里**不内置**任何第三方素材 |
| Freesound | 混合（CC0/CC-BY/CC-BY-NC），且**原始文件下载要 OAuth2 登录** | 不做自动下载源；CC-BY 的署名义务对"发给微信的语音"没法履行 |
| 剪映素材库 | 平台分级商用许可，**不可再分发** | 只参考其分类组织（综艺/游戏/搞笑/转场），不碰素材 |
| 自家 DSP 合成 | 无版权问题 | 呼啦/叮/升调等短效果可用 numpy 现合成（effects.py 的现成函数族） |

**出厂 6 条（P1）实际全部是程序化合成**（`tools/gen_sfx.py`，2026-09-23）：
`爆炸` / `掌声` / `警报` / `升调` / `叮` / `鬼畜`，48kHz 单声道 16bit，共 **694KB**。

与设计稿写的"爆炸/掌声用 Kenney 的 CC0 素材"不同，理由三条（都在实现时定的）：

1. **版权链最短**：合成产物是本仓自己的作品 —— 不存在"这个包到底是 CC0 还是 CC-BY"的
   核对成本，也不用往 `THIRD_PARTY_NOTICES.md` 加署名条目；
2. **可复现**：`python tools/gen_sfx.py` 一条命令重出全部素材（固定种子，逐字节一致），
   二进制素材进了 git 就说不清当初按什么参数裁的；
3. **体积**：6 条 694KB，比任何整包都小。

风格上它们偏"游戏提示音"，不是好莱坞拟音。**这恰好是目标**：微信语音里叠一声爆炸
要的是综艺感。真要更真的素材，那是 P2 市场包的事（那时才需要 CC0 的 Kenney）。

每条 **≤1.6s** —— **微信语音按住说话是"叠加进人声"，太长的音效会把整条消息变 noisy，
短才有综艺感**。响度已拉平（软压缩把掌声那种瞬态密集素材的 RMS 抬上来，
否则峰值归一化下它会比警报听感轻约 20dB）。

### 6.1 素材的三种来源（2026-09-24 已实现）

| 来源 | 落盘位置 | 谁装的 | 能不能单条删 |
|---|---|---|---|
| **出厂 6 条** | `plugins/sound.fx-board/samples/` | 随插件 | 否（删了得重装） |
| **单条导入** | `<media>/soundboard/*.wav` | `POST /import`（面板「导入素材」） | **是** |
| **音效包** | `<media>/soundboard/packs/<pack_id>/*.wav` | `POST /packs/install`（zip）或 `/packs/download`（市场） | 否，**整包卸** |

三者共用同一份 DSP 与同一个格子面板 —— 用户看到的是"一条能点的音效"，
区别只在 `builtin`/`pack`/`removable` 三个字段上（后者决定界面给不给删除入口）。

**id 命名空间化**：包内素材是 `"<pack_id>/<stem>"`，裸 stem 只属于出厂/导入。
不这么做的代价是"后装的包把已有 id 顶掉，而界面看不出任何变化"。

导入与包的上限不同且是故意的：**导入 ≤5s**（手指点一下的场景），
**包内 ≤60s**（转场/环境音包确实需要更长）。

### 6.2 音效包的格式

    <pack_id>.zip
      pack.json      # {name, license, author?, description?, samples?: {stem: {name, tags}}}（可套一层同名目录）
      *.wav          # 素材
      LICENSE/README # 随便放，原样保留（署名要跟着分发走）

`license` **必填**：包会被装到**别人**的机器上，这行声明是那边唯一的许可依据
（`tools/audit_licenses.py` 只管仓库内的资产，管不到运行时下载的东西）。
安装时逐项校验，六道门全在 `sfx_packs._read_zip` / `install_zip`：
成员名不许绝对路径或 `..`、不许符号链接、**后缀白名单**（`.wav/.json/.txt/.md` 与无后缀，
夹带 `.exe/.py` 直接拒）、要有 `pack.json`、要有 ≥1 条 wav、**每条 wav 必须真能读且不超长**。
安装是**原子**的（先解到 `.tmp-*` 再整目录换进去），失败不留半截目录；
已存在同名包要 `overwrite=true` 显式覆盖。

`tools/pack_sfx.py` 是**生产端**：`--from <目录>` 打真实素材，`--demo <id>` 程序化合成
一套演示包（零第三方版权），两条路都会打印**可直接粘进清单的条目**（含 sha256/bytes）。

### 6.3 为什么是「资源包」而不是「插件」（2026-09-24 用户拍板）

用户原话是"把更多音效包做成可从市场下载的插件"，核实后改成了资产形态，两个原因：

1. **硬阻碍**：前端是构建期静态的（`lib/pluginRoutes.tsx` 的 `import.meta.glob` 在
   `vite build` 时就把页面打进 bundle）—— **下载下来的插件带不进一个已构建好的前端**，
   所以今天"插件"只能等于"随包发、可关"（§十 早已记录）；
2. **清单 schema 也不允许**：`plugin_manifest._validate()` 明写「一个不挂 router 的
   插件不该存在」，音效包要当插件得先把这条规则拆掉，连带改归属审计与关闭语义 ——
   而它只需**素材**、沿用已有的格子渲染，为省 0 字节动 schema 不划算。

于是归入**资产包**一类，与音色市场（装到 RVC logs）、桌宠皮肤市场（zip 解到 pet-skins）
同一形状，可复用同一条下载/白名单/安全解压的思路。

### 6.4 市场（货架）与发布

清单是个 JSON：`{"packs": [{id, name, license, url, sha256?, bytes?, downloads?, author?}]}`，
由 `VM_SFX_PACK_INDEX` 指向（URL 或本地路径）。三种情形都**不是异常**：
没配 → `note` 说"货架没开"；取不到/格式坏 → `error` 带原因；正常 → 条目（带 `installed` 标记）。
下载走 `sfx_packs._validate_url` 的**域名白名单**（HF 官方/镜像、魔搭、raw.githubusercontent），
清单里给了 `sha256` 就**必须**校验，没给则如实回报 `sha256_verified: false`（不假装验过）。

**发布步骤**（内容由你上传，代码里不带任何第三方素材）：

```bash
# ① 造包（自己录的用 --from；想先验链路用 --demo）
python tools/pack_sfx.py --from 我的音效/ --id mypack --name 我的音效 --license "自录，仅自用"
# ② 把 zip 传到托管位置（HF/魔搭/仓库 raw，或任何在白名单里的域）
# ③ 把脚本打印的条目粘进清单 JSON，然后让后端指过去：
#    VM_SFX_PACK_INDEX=<清单的 URL 或本地路径>
```

⚠️ **清单今天默认是空的**（`VM_SFX_PACK_INDEX` 未设），因为**没有可发布的托管位置**：
本仓还没开源、线上 Releases 为空（§十 已记）。所以界面显示的是"货架没开"+
「从 zip 安装」仍可用 —— 这不是缺功能，而是缺货架；内容一传上去，同一个界面就开始
列条目、显许可、带下载量。

## 七、边界（明确不做）

- **不做时间线/多轨剪辑** —— 那是剪映的活，我们是变声工具不是 DAW；
- **不改 wechat_voice 的任何发送自动化** —— 声板与发送流程唯一的交点是共享声卡；
- **P1 不做全局热键、不做 MIDI 键盘**（主播级 soundboard 的方向，往后放）；
- **不做自动音效**（说到关键词自动配爆炸）—— 需要 ASR 实时字幕联动，成本/收益不成立。

> ⚠️ **「不改 wechat_voice」这条在 2026-09-25 被用户需求突破了一次**，见 §八。
> 突破的方式是**最小侵入**：只在 `_split_for_budget` 里加了"解析标记 + 把音效时长并进
> 预算 + 拼接时接上去"，发送自动化本身（切卡/录音/UIA 校验/发送）一行没动。

## 八、「说话中间插一声」= 文字标记（2026-09-25，替代悬浮窗方案）

**用户原话**：

    不对呀，现在的方案不是手动按alt，不是程序自动按的吗？我就是想用这个自动按的
    时候如何在我说话的步骤能插一个爆炸声，然后我继续说话呢

这一句推翻了 §一 里"按 Alt 说话中途点格子"的前提：**程序自动按 Alt 时，用户全程
不碰键鼠** —— 他要的是"程序正在发声的时候插一声"。而这件事**悬浮窗做不到**，
原因是结构性的：

```
文字 → 逐句合成 → 拼成 wav → 一次性灌进 CABLE → 微信录音 → 发送
```

音频在**播放前**就全部合成完了，不存在"正在说话"这个中间态。所以改用
**合成阶段拌入**：在文字里写 `[爆炸]`。

### 用法（用户视角）

在文字转语音的输入框里，直接写方括号名字：

```
我今天去那个 [爆炸] 那个地方。然后我说完了。
```

- 名字按**声板上的显示名**写（`爆炸`/`掌声`/`警报`/`升调`/`叮`/`鬼畜`），
  也认 id（`boom`/`applause`…）；emoji 图标名（`[💥]`）同样可以；
- 音效插在**它前面那段文字之后** —— 上例里"那个"说完就炸，然后继续"那个地方"；
- `[掌声]` 单独成句也行（"在两句之间来一段掌声"）；
- 一句话里写多个标记时，**只接最后一个**（"说到这句末尾"的直觉），`steps` 里会说明；
- **写错名字会报错**（"没有这个音效：爆炸声。可用：爆炸、掌声…"），不会静默不生效。

### 实现（三个落点，都在既有函数里）

```
m2_server/sfx_mark.py        # 新建：解析 `[名字]` → (文字片段, 音效 id) 序列
m2_server/wechat_voice.py    # _split_for_budget：断句后解析 → 合成前剔除 → 拼接时接上
m2_server/tests/             # test_sfx_mark.py（33 条）+ test_wechat_chunking.py（11 条）
```

**★ 音效时长必须并进 `durs[i]`**（`d += sd + SFX_GAP_S`）。漏了这条的后果不是报错，
而是带音效的那条超 54s 预算 → 微信在第 60s **静默截断** → 用户丢了后半句还不知道。
变异实测：删掉这一行，测试报 `assert 65.3 <= 60.0`。

**已知取舍**：`arr[0]`、`[i]` 这类短方括号会被当成标记名并报"没有这个音效：0"。
区分代码与音效要读懂上下文，正则做不到 —— 这里选**错得响亮**（漏报比误报代价大得多）。
硬边界：名字超 24 字符就不算标记，长索引不会误报。

完整复盘（含三条口径、5 个变异证据、踩过的坑）见 `docs/犯错档案-微信.md` §2.45。
