# 场景包（「你想干什么」）

> **现役**。代码：`m2_server/live_settings.py`（`SCENES` 表，**唯一真相源**）、
> `m2_server/rvc_live.py`（`GET /rvc/live/scenes`、`POST /rvc/live/scene`）、
> `web/src/components/voice-studio/LiveScenePacks.tsx`（UI）、
> `web/src/pages/Live/useLive.ts`（`applyScene`）。
> 门禁：`m2_server/tests/test_live_settings.py::TestScene*`、`LiveScenePacks.test.tsx`。

一句话：用户心里想的是「我现在要**开会**」，不是「我要 index_rate=0.5、关掉字幕、开降噪」。
场景包把后者翻译成前者。

---

## 1. 四个场景

| 场景 | 键 | 性能档 | 降噪 | 自我监听 | 字幕 |
|---|---|---|---|---|---|
| 开黑 | `gaming` | game | 开 | 关 | 关 |
| 微信语音 | `wechat` | game | 开 | 关 | 关 |
| 直播 | `stream` | balanced | 开 | 开 | 开 |
| 会议 | `meeting` | game | 开 | 开 | 关 |

排序由 `order` 字段决定（10/20/30/40），高频的在前。

## 2. ★ 两类字段必须分开（最容易做错的一处）

场景里的字段分成**两桶**，语义完全不同：

| 桶 | 落盘？ | 什么时候生效 | 目前有谁 |
|---|---|---|---|
| `in_settings` | ✅ 写 `outputs/live_settings.json` | **持久**，跨重启保持 | `perf_profile`、`denoise` |
| `on_start` | ❌ **不落盘** | 只在**点场景那一刻**随变声启动传下去 | `monitor`（自我监听）、`subtitle`（字幕） |

**为什么必须分开**：`monitor` / `subtitle` 本来就不是设置项 ——
它们是 `rvc_live_start()` 的入参（见该函数签名）。硬把它们塞进设置文件，
要么是造出一套平行配置（与真正的启动参数打架），要么是承诺一个存不下来的状态。

所以 API 响应里也**分开回传**：

```jsonc
{
  "applied":         { "perf_profile": "game", "denoise": true },  // 已落盘
  "applied_on_start":{ "monitor": false, "subtitle": false },      // 本次已随重启生效
  "on_start_pending":{ ... },                                      // 运行中但没重启 → 还没生效
  "needs_restart": false
}
```

⚠️ **没重启时 `applied_on_start` 必须是空对象**，不能把 `on_start` 混进 `applied`。
否则界面会显示「已开自我监听」而实际没开 —— 最典型的一种假成功。
（`test_on_start_not_reported_as_applied_when_not_restarted` 钉住这条。）

## 3. ★ 「现在高亮哪个场景」不能用设置反推

**事实**：`gaming` / `wechat` / `meeting` 三者的 `in_settings` **完全相同**
（都是 `perf_profile=game` + `denoise=True`）。

所以「拿当前设置去反推最像哪个场景」会**恒等命中 order 最小的 `gaming`** ——
用户点了「微信语音」，界面却高亮「开黑」。这是假信息。

**正确做法**（`GET /rvc/live/scenes` 的实现）：

```
active = stored if (stored and scene_matches(stored, cur)) else None
```

- `stored` 来自设置里的 `scene` 键 —— 「上次点了哪个」，这才答得准；
- `scene_matches` 只当**布尔校验**（「还符不符合」），**不拿它选场景键**；
- 用户点完场景后手动改了降噪 → `scene_matches` 为假 → `active = null`，
  界面**一个都不高亮**，并提示「当前设置已被手动调整」。

`logout` 一句话记法：**`stored` 答「是哪个」，`scene_matches` 答「还算不算」。**

## 4. ★ 场景表只做加法映射

`SCENES` 里每个键都必须落到一个**已经存在**的状态上，**不引入新设置项**。
理由：否则场景会变成第二套平行配置，与单开关互相打架（读哪个？谁赢？）——
这正是要避免的复杂度。

`test_in_settings_only_uses_real_setting_keys` 用
`set(live_settings.DEFAULTS) - {"scene"}` 当白名单钉住这条：
往 `in_settings` 里写一个不存在的键会直接判红。

同理 `test_perf_profile_values_are_legal` 保证档位值一定在
`rvc_live.PROFILE_TUNING` 里 —— 写错会在重启时 400。

## 5. 行为细节

**应用场景时变声正在跑**：默认 `restart=True`，自动 stop → start，
把 `on_start` 的伴随项真的带上（「一键开黑」不该让用户再手动重启一次）。

**`restart=False`**：只落盘，`needs_restart=true`，前端提示用户自己重启。

**切到 game 档**：与 `/rvc/live/profile` 走同一套 `_sync_worker_for_profile()` ——
卸载 Qwen3-TTS worker 释放约 4.8GB 显存，响应里给 `tts_freed_mb`。

**未知场景名**：400 + 列出可选项。`live_settings.update(scene=...)` 也会拒绝
并把值归零 —— 否则界面会高亮一个不存在的场景。
文件里被手改坏的 `scene` 值同样在 `get()` 时归零。

**拉不到场景清单**：前端整块不渲染（`p.scenes.length > 0` 才渲染），
不让这个锦上添花的能力把整个实时页的反馈区变成报错。

## 6. 加一个新场景

1. 在 `live_settings.py` 的 `SCENES` 里加一项（`label` / `desc` / `icon` /
   `order` / `in_settings` / `on_start`）；
2. `icon` 必须是 lucide 的**大驼峰组件名**（如 `Gamepad2`），且要往
   `LiveScenePacks.tsx` 的 `ICONS` 表里登记 —— 没登记会回退成 `Radio`
   （有兜底，不会崩，但会显示错图标）；
3. `in_settings` 只能写 `live_settings.DEFAULTS` 里已有的键；
4. `perf_profile` 只能是 `rvc_live.PROFILE_TUNING` 的键（`balanced` / `game`）。

**不需要**改前端逻辑 —— 卡片是按后端返回的清单渲染的。
但如果新场景的 `in_settings` 与现有场景**完全相同**，请回头读第 3 节：
高亮会依赖 `stored` 键，这是预期的，不要"修"成反推。

## 7. 与「性能模式」的关系

`LivePage` 上两块都在：

- **场景包**（本节）= 上层概念，一键写多组开关；
- **性能模式**（`balanced` / `game` 两档）= 下层单开关，仍可单独调。

两者**不冲突**：手动改性能档不会清掉 `scene` 标记，但会让 `scene_matches`
变为假（因为 `in_settings` 对不上了）→ `active` 变 null → 场景卡片取消高亮。
这是对的：用户已经偏离了那个组合，就不该继续声称「你还在开黑模式」。
