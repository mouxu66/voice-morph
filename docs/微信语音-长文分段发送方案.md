# 微信语音：长文本分段发送方案

> 日期：2026-09-22
> 起因：用户实测 —— 长文本走「文字转语音 → 发微信」时，单条语音被微信在 60 秒处截断，
> 后半段没读出来就发出去了。
> 结论先行：**把「一次发一条 wav」改成「一次发一批 ≤54 秒的 wav」**，
> 切分点落在句子/静音处，环境准备与声卡还原整批只做一次。核心代码可以几乎全部复用现有件。

---

## 一、问题与现状事实（都是代码里查得到的，不是推测）

### 1.1 平台约束

微信语音消息**单条上限 60 秒**，到点自动结束并发送。这不是我们的 bug，是平台限制，
**无解**：不可能让一条语音超过 60 秒。

本仓已经在多处按 60s 处理（说明这条约束早就被知道，只是没有被正面解决）：

| 位置 | 原文 |
|---|---|
| `wechat_voice.py` 模块 docstring | 「（单条最长 60s）」 |
| `wechat_voice.py` 第 6 步注释 | 「找不到 ↑ 钮一律点 × 取消，绝不留下挂起的录音（单条最长 60s）」 |
| `_uia_verify_sent()` | 「⚠ 时长异常（{secs:.0f}s 远大于预期 {expect_s:.1f}s），**疑似 60s 截断复发**」 |
| `docs/犯错指南.md` 速查表第 2 条 | 「消息发出去了，但显示 **60"** ｜按下状态从未解除，录满 60s 自动截断」 |

⚠️ 注意最后两条的判据形状：**现状是「发出去之后才发现可能被截断了」，只在事后报警，不阻止它发生。**

### 1.2 当前链路（两条入口，都只发一条）

```
入口 A（桌宠面板，文字）
  pet.html #voiceSel/#say  →  pet-actions.cjs doSendTextToWechat
    → POST /api/wechat/send_text
       ├─ synth_wav(text)            ← 整段文本一次性 TTS，产出**一个** wav
       ├─ _rvc(wav, rvc_voice)       ← 整段换声
       └─ _do_send(wav)              ← **一次录音周期**：切卡 → 播放 → 录音 → 结束发送
                                       末尾 _restore_async 交后台线程还原声卡

入口 B（应用内 /tts?tab=wechat，已有音频）
  useWechatSend.ts → wechatSendVoice(wav)  → POST /api/wechat/send_voice
    → _do_send(wav)                 ← 同一个内核，同样只发一条
```

关键事实：

- **`_do_send()` 一次只处理一个 wav。** 它内部第 5 步「等 wav 真正播完」用的是
  `_wait_play_done(proc, duration)`，`duration` 是这条 wav 的完整时长 —— 也就是说
  **音频多长，微信就录多长**，超 60s 必被平台截断。
- **`_send_lock`（互斥整次发送）与 `_restore_lock`（互斥声卡切换）都已经存在**，
  批次内多条串行天然安全，不需要新造锁。
- 记录时长 = `PLAY_LEAD_S(0.8) + 音频 + TAIL_S(0.3) + 收尾延迟(~0.3)`
  （见 `wechat_voice.py:97-101` 与第 6 步的 `time.sleep(0.15)`）。
- 现有两个容易踩的上限：`pet.html` 的 `#say` 是 **`maxlength="200"`**；
  `pet-actions.cjs` 的 HTTP 超时是 **180000ms**。
- `HISTORY_MAX = 20`（`outputs/wechat_send_history.json`），一条批次会占多条。

### 1.3 所以问题在哪

不是"能不能发 60 秒以上"（不能），而是：

1. **文字入口根本不知道自己要发多长** —— TTS 出来才发现 90 秒，然后照发，被截断；
2. **成品音频入口（入口 B）没有任何长度检查** —— 有声书/长文合成的 wav 直接发，必被截断；
3. **没有任何机制保证"整段话都发出去"** —— 截断后剩下的部分丢了，用户要自己发现。

## 二、约束与预算算式

设：

- `MAX_MSG_S = 60`（微信硬上限，不可调）
- `PLAY_LEAD_S = 0.8`（自动发送专用静音头，盖住「点按钮 → 微信真正开始录」的延迟）
- `TAIL_S = 0.3`（播完后尾巴静音）
- `FINISH_LAG_S ≈ 0.3`（`time.sleep(0.15)` + 点发送钮的延迟）

则**单条可承载的音频预算**：

```
MAX_CHUNK_S = MAX_MSG_S − PLAY_LEAD_S − TAIL_S − FINISH_LAG_S − SAFETY_S
            = 60 − 0.8 − 0.3 − 0.3 − 4.6
            = 54.0 s
```

`SAFETY_S = 4.6s` 的构成（别省，这段余量买的是"绝不静默截断"）：

| 项 | 预留 |
|---|---|
| UIA 报的秒数是**整数向上取整**（`语音15"秒`），±1s | 1.0 |
| TTS 语速随句子/音色波动，拼接后的实测时长与预估会差 | 1.5 |
| 声卡驱动缓冲、`_finish_record` 前的抖动 | 1.1 |
| 微信侧到点前的自身计数余量 | 1.0 |

**唯一硬判据：`PLAY_LEAD_S + audio_s + TAIL_S + FINISH_LAG_S ≤ 60`，带 `SAFETY_S` 余量。**

下限同样有约束：**微信语音最短 1 秒**（速查表第 3 条「说话时间太短」）。
`MIN_CHUNK_S = 2.5s`，短于此的尾段并入上一段（能并则并，不能并就补静音而不是发一条 1.2 秒的）。

## 三、方案总览

```
                         ┌──────────────────────────────────────────┐
  文字入口 send_text ───→│ ① 切分：split_sentences()（已有）         │
                         │    逐句 TTS + 实测时长（复用 audiobook 形状）│
                         │ ② 分包：贪心装箱到 ≤ MAX_CHUNK_S          │
                         │ ③ 每包：拼接 → RVC 换声 → 落盘一个 wav     │
                         └──────────────────┬───────────────────────┘
                                            │  [wav_1, wav_2, wav_3]
  音频入口 send_voice ──→ ①' 按静音切分已有 wav ─┘
                                            │
                                            ▼
                         ┌──────────────────────────────────────────┐
                         │ ④ 批次内核 _send_batch(wavs)              │
                         │   _prepare_recording_env()  ← **只做一次** │
                         │   for wav in wavs:                        │
                         │       _record_and_send(wav)   ← 现有 3~6 步 │
                         │       每段重新取 before_count/before_msg   │
                         │       段间 BATCH_GAP_S 等待录音浮层消失     │
                         │   finally: 一次性还原声卡                  │
                         └──────────────────────────────────────────┘
                                            │
                          { outcome, total_chunks, sent_chunks,
                            failed_index, remaining_text, steps }
```

一句话：**把 `_do_send` 里"发一条 wav"的那半段抽出来变成可循环的 `_record_and_send`，
再在它外面套一层"环境只准备一次 + 循环发送 + 统一还原"。**

## 四、关键设计决策（含"为什么不是另一种做法"）

### D1 分包在**后端**做，不在前端

桌宠面板和应用内页都要受益，而且只有后端知道 TTS 的真实产出时长。
前端的职责退化为**展示与提示**（"这句话会分成 3 条发出去"）。

### D2 用「实测时长」贪心装箱，不用「字数 ÷ 语速」估算

- 字数→秒数只是代理量，中英混排、数字（"2026 年 9 月 22 日"读出来比看起来长）、
  标点停顿都会让它偏；偏小的方向就是**静默截断**，代价最大。
- 实测时长是**免费**的：为了分包我们本来就要逐句合成（见 D3），`sf.read` 一下就有秒数。
- 复用 `audiobook._audiobook_worker` 已经跑通的形状：逐句合成 → 记 `duration_s` →
  `AudioSegment` 拼接。

### D3 逐句合成，不整段合成后再切

三个理由，都不是偏好问题：

1. **切分点必须落在句子边界。** 整段合成后在 54 秒处硬切会把一个词切成两半（"我爱你"→"我爱"|"你"）。
2. **稳定性**：`audiobook.py` 的 docstring 已实测记录 —— 逐句走 x-vector 声纹克隆
   （`ref_text` 置空）批任务更稳，且 8GB 显存下 ICL 长参考会跌进 WDDM 共享内存慢路径。
   整段长文正是最长的那个参考。
3. **失败面小**：单句合成失败只毁一句，可以重试或跳过；整段失败就全废。

### D4 复用 `split_sentences()`，不新写断句器

`audiobook.split_sentences()` 已经处理了：中文全角句末标点、英文 `.!?` 后必须跟空白
（避免 `U.S.A`/`3.14` 误切）、碎片并入下一句、超长句在逗号处二次切分、无标点硬切。
**这些坑都已经踩过了**，重写只会重新踩一遍。

⚠️ 但要分清两件事：`_MAX_SENT = 80` 是**合成稳定性**阈值（80 字以内单次合成最稳），
**不是 60 秒预算**。所以流程是：先按 80 字切（为了合成质量），**再**按实测时长为 54 秒装箱。
两个阈值职责不同，不要合并。

### D5 单句自己就超过预算时怎么办（必须有兜底）

罕见但会发生（长排比句、无标点长串）。三级降级：

1. 在逗号处再切（`_SUB_SENT`，已有）；
2. 仍超 → 按字数硬切成两半，逐片合成测时长，递归直到 ≤ 预算；
3. 硬切的边界若落在句子中间，接受"语气略断"——**这比被平台静默截断好得多**。
   在 `steps` 里写明"第 N 句过长，已在逗号处切开"。

### D6 成品音频入口（`send_voice`）按**静音**切分

入口 B 拿到的是已有 wav（有声书导出、长文合成），没有句子信息。做法：

1. `pydub.silence.detect_nonsilent(wav, min_silence_len=250, silence_thresh=-40)` 拿非静音区间；
2. 贪心累积到接近 `MAX_CHUNK_S`，**切点选最近的一个静音间隙**（而不是正好 54.0 秒处）；
3. 目标点 ±`SEARCH_S(=6s)` 内找不到静音 → 硬切并在切点加 `5ms` 淡入淡出（防爆音）；
4. 外层仍用 `_trim_edges()` 裁首尾静音（已有）。

pydub 已是既有依赖（`audiobook.py` / `voices_api.py` 都在用），不引入新依赖。

### D7 环境准备与声卡还原**整批只做一次**

现状每发一条都要 `apply`（切卡，~3s，必要时还要重启微信 10~30s）+ `_restore_async`（~3s）。
批次内重复做就是白等 N×6s，而且**反复切卡本身就是故障源**（速查表第 22 条：切完必须重启微信才生效；
`_restore_lock` 的存在说明抢设备会出状态不确定）。

所以：`_prepare_recording_env()` 提到批次外，`_safe_restore()` 放到 `finally`。
这条也直接决定了 D8 的 refactor 边界。

### D8 refactor 边界：`_do_send` 的**对外语义一个字都不能改**

`_do_send` 被这些地方依赖，动了就是连环崩：

- `tools/tts_and_send.py` / `tools/wechat_e2e_check.py` / `tools/wechat_regression.py`（真机回归夹具）
- `m2_server/tests/test_play_worker.py`、`test_wechat_retry.py`、`test_wechat_restart.py`、
  `test_wechat_send_text.py`（20+ 条用例）
- `/api/wechat/send_voice`（入口 B）

所以拆成三层，**只加不改**：

```
_prepare_env(pre_apply)                    ← 新增，从 _do_send 第 2 步抽出（行为相同）
_record_and_send(wav, duration, env, ...)  ← 新增，= 现有第 2.5~6 步 + 校验 + 落历史
_do_send(req, pre_apply=None)              ← **签名与返回结构不变**，
                                             内部改为 _prepare_env → _record_and_send
_send_batch(wavs, pre_apply=None)          ← 新增，循环调 _record_and_send
```

`_do_send` 因此变成"只有一条的批次"，两条路径走同一段代码 —— 避免"批次修好了、单条还漏着"。

### D9 段间必须留 `BATCH_GAP_S`

`_trigger_record()` 的前置条件是**上一次的录音浮层已经消失**（速查表第 11 条：
「前一次失败后，后续全部失败」就是浮层残留）。所以段间：

1. 等浮层消失（复用 `_wait_record_overlay` 的思路，超时 `BATCH_GAP_S + 2s`）；
2. 再 `time.sleep(BATCH_GAP_S = 0.8s)`。

**不要**用固定 `sleep(0.5)` 当同步手段（犯过一次，见速查表第 55 条：固定 sleep 换轮询）。

### D10 每段都要**重新取** UIA 基线

`_uia_verify_sent(before_msg, expect_s, before_count)` 的判据是"**条数变多** 或 文本不同"。
批次内如果沿用第一条的 `before_count`，第二条起就会一直判成"已新增"（基线没动）。
所以 `before_msg / before_count` 必须**每段重取**，且在 `_finish_record()` 之前取。

### D13 批次的入参是**有序 wav 列表**，不许后端串联两次批次

**这是「两个入口要不要分开」这个问题的正式答案：不分开，但也不是"后端把两次批次串起来"。**

正确形状：`_send_batch(wavs)` 的入参定义成**有序 wav 列表**，"分包"只是"如何造出这个列表"
的**策略之一**（文字入口造出逐句装箱的结果，音频入口造出静音切分的结果）。于是：

```
entry A（文字）      → pack_chunks(逐句时长)  → [wav_1, wav_2] ┐
entry B（成品音频）  → split_by_silence()    → [wav_3]        ├→ _send_batch(...)  ← 切卡只一次
需要 A+B 一起发      → 前端把两个来源拼成 [wav_1, wav_2, wav_3] ┘
```

**为什么不能在 `send_text` 里顺手再调一次 `send_voice`：**

1. `_prepare_env()` 的作用域是「一整批」，`finally` 里还原（D7）。两次批次 = 两次切卡
   + 两次**可能的重启微信**（10~30s，且 2026-09-17 用户明确拍板"绝不杀微信"）——
   把 D7 里最值钱的收益原样吃掉。
2. 同一段话会在聊天里变成**两个语音气泡组**，中间夹着一段设备切换时间，
   用户听到的是"话说到一半停了"。
3. `_send_lock` 是 `acquire(blocking=False)` → 第二次调用直接 409
   `已有一次微信语音发送在进行中`。用户视角是"刚发完三条，现在不让发了"。
4. 不算假想风险：`send_voice` 在 `req.wav` 为空时取 `outputs/` 下**最新的 `tts_*.wav`**，
   中间任何一次 TTS/试听落盘都会改变"最新"指的是谁。

**落地判据（写进测试）**：`_send_batch` 在一次调用里，`_prepare_env` 与 `_safe_restore`
的调用计数必须**恒为 1**，与列表长度无关。

### D11 明确拒绝"压缩变速塞进 60 秒"

把 90 秒的话加速 1.5 倍塞进一条，技术上可行，但**音色与语气都会变**，
这是产品决定不是技术修补，而且用户要的是"读完"。**不做**，写在这里是为了防止下次有人提。

## 五、分包算法（纯函数，可单测）

```python
MAX_CHUNK_S = 54.0   # 见 §2 算式
MIN_CHUNK_S = 2.5    # 微信最短 1s，留出余量

def pack_chunks(durs: list[float], max_s=MAX_CHUNK_S, min_s=MIN_CHUNK_S,
                gap_s=0.3) -> list[tuple[int, int]]:
    """按实测时长把句子贪心装箱成 ≤max_s 的若干段，返回 [(起, 止)] 左闭右开。

    这是整个方案的**唯一硬判据**所在：返回的每一段，加上 PLAY_LEAD_S/TAIL_S
    都必须 ≤ 60。所以它是纯函数、必须被单测 + 变异测试覆盖。
    """
    out, i, n = [], 0, len(durs)
    while i < n:
        j, acc = i, 0.0
        while j < n:
            # 段内句子之间要留 gap；最后一段没有 gap
            add = durs[j] + (gap_s if j > i else 0.0)
            if acc + add > max_s and j > i:
                break
            acc += add
            j += 1
        out.append((i, j))
        i = j
    # 尾段太短 → 并入上一段（不能并就补静音，避免发一条 1.2 秒的）
    if len(out) >= 2 and sum(durs[out[-1][0]:out[-1][1]]) < min_s:
        last = out.pop()
        if last[1] == n:
            prev = out[-1]
            out[-1] = (prev[0], last[1])
    return out
```

单句超预算的情形在**调用方**处理（D5 的三级降级），因为那需要"再切一次并重新合成"，
不是纯函数能决定的。

## 六、发送编排（伪码）

```python
def _send_batch(wavs, pre_apply=None, on_progress=None):
    steps, results = [], []
    env = _prepare_env(pre_apply)          # ★ 一次
    try:
        for k, wav in enumerate(wavs):
            dur = _wav_duration(wav)
            # ★ 每段重取基线（D10）
            before_msg, before_count = _uia_snapshot()
            res = _record_and_send(
                wav, dur, env,
                index=k, total=len(wavs),
                gap_s=BATCH_GAP_S,          # ★ 段间等浮层（D9）
            )
            results.append(res)
            steps += [f"[第 {k+1}/{len(wavs)} 条] {s}" for s in res["steps"]]
            if on_progress:
                on_progress(k + 1, len(wavs), dur)
            if res["outcome"] != "ok":       # ★ 失败即停（见 D12）
                return _batch_result(results, wavs, steps, failed_index=k)
        return _batch_result(results, wavs, steps)
    finally:
        _safe_restore()                      # ★ 一次，且失败也要还原
```

### D12 失败策略：**失败即停**，并回传"剩下的原文"

- 继续发剩下的看起来"多送几条"，但失败通常意味着**环境已经坏了**（声卡/浮层/微信被抢焦点），
  后面几条只会变成静音或噪声音频 —— **发出去一条错的不如不发**。
- 回传 `remaining_text`，让界面能提供「继续发剩下的」按钮（手动重试时环境已被还原，可重来）。
- 与现有 `outcome` 体系对齐，新增 `outcome="partial"`（已有 `ok`/`cancelled`/
  `manual_fallback`/`failed`）。

## 七、可观测性（这是"下次不用人肉查"的关键）

| 出口 | 内容 |
|---|---|
| `steps` | 每条前缀 `[第 k/N 条]`，保留现有 `[12.3s]` 时间戳；含"语气借自谁""在逗号处切开"等说明 |
| 发送历史 | **每段一条记录**（`_append_history` 加 `batch_id` / `index` / `total` 字段），这样桌宠「最近发送」点一条重发的就是那一条 |
| `_uia_verify_sent` | 每段独立跑；保留现有"疑似 60s 截断复发"判据 → 批次里它变成**逐条**体检 |
| 桌宠面板 | 状态行显示「第 2/3 条发送中…」（`pet:send-result` 之外加进度事件，或复用 alt-hint 浮层） |
| alt-hint 浮层 | `showAltHint({stage, sub, progress})` 已支持进度，直接喂 `k/N` |
| 响应体 | `{outcome, total_chunks, sent_chunks, failed_index, remaining_text, wavs[], duration_s, steps}` |

**新增护栏（P0 就要有）**：单条路径也检查预算 ——
`_do_send` 拿到 `duration + PLAY_LEAD_S + TAIL_S > MAX_MSG_S − SAFETY_S` 时**拒绝发送**并报
「这段音频 X 秒超过单条上限，请走分段发送（会分成 N 条）」，**而不是**发一条注定被截断的。
这是"任何绕过分包的调用方也不会静默出错"的兜底，也是这条 bug 唯一的防复发机制。

### ⚠️ 批次会打坏的两个既有前端机制（P0 必改，不是 P2 体验）

**(1) `pet.html` 的 `watchSendOutcome()` 兜底看门狗会在第 1 条落库时提前收尾。**
它轮询 `/api/wechat/history` 的**最后一条**，一出现新记录就 `settleSendResult()` 并 return
（`pet.html:1675`）。而 §7 定了"每段一条历史" → 第 1 条落库即触发收尾，
状态栏在**后两条还在录**的时候就打勾"已发到微信 ✓"。

**(2) `settleSendResult()` 会把单条的 warning 套到整批上。**
它做 `if (last && Date.now()/1000 - last.ts <= 300) warn = last.warning`（`pet.html:1655`）
—— 第 3 条录成静音时，用户看到的是第 1 条的正常绿勾。

改法：批次响应带 `total_chunks`，`sent_chunks < total_chunks` 时看门狗**不收尾**；
warning 只在"确实对应本条"时才展示（或整批只要有一条 warning 就整体转警示态）。

**(3) `_append_history` 的 `duration_s` 语义会漂，重发不能还原原文。**
桌宠「最近发送」点一条重发走 `sendWav` → `/send_voice`，拿到的是**切好的 54 秒片**，
**不会**再拼回原文。这是可接受的（用户发的是那一条），但要写进 docstring，
免得下次有人以为点重发能还原整段。

## 十、测试计划

**纯函数单测（`pack_chunks`）** —— 这些是方案的硬判据，必须有：

- 空输入 / 单句 / 恰好等于预算 / 刚超预算 1ms；
- 末段 < `MIN_CHUNK_S` → 并入上一段；
- 首句就超预算（交给调用方降级，函数本身不崩）；
- **不变量**：返回的每一段 `PLAY_LEAD_S + Σdur + gap + TAIL_S ≤ 60`（对所有随机输入都成立）。

**编排单测**（打桩 `_record_and_send` / `_prepare_env` / `_safe_restore`）：

- 环境准备与还原**各只调一次**（3 条批次断言调用计数）；
- 第 2 条失败 → `sent_chunks == 1`、`failed_index == 1`、`remaining_text` == 第 2、3 条原文，
  且第 3 条**没有被调用**；
- 每段都**重新取** `before_count`（断言取用次数 == 条数）；
- `_do_send` 单条路径与批次路径在同样输入下产出等价的 `steps` 形状（防"两条路各修一半"）。

**护栏的变异测试**（本仓已有变异测试传统，见`docs/犯错档案-工程.md` §8.19）：

- 把 `MAX_CHUNK_S` 从 54 改到 70 → 断言"不超预算"的用例**必须变红**；
- 把预算护栏整段删掉 → 断言"超长单条被拒发"的用例**必须变红**。
  ⚠️ 变异要**整行删除**，不能只注释（断言可能匹配到注释里的同名文本，见速查表第 46 条）。

**真机验收**（`tools/wechat_regression.py` / `tools/wechat_e2e_check.py`）：

- 3 段文本（其中 1 句故意超长）→ 核对微信里条数 == 计划条数、
  每条 UIA 报的秒数 ≤ 60、**总时长 ≈ 原文时长**、逐条无「截断复发」告警；
- 一条 90 秒成品 wav 走入口 B → 核对切在静音处（听不到断词）；
- 中途拔掉 CABLE（制造失败）→ 核对失败即停 + `remaining_text` 正确 + 声卡已还原。

## 十一、风险与明确不做

| 风险 | 处置 |
|---|---|
| 改动碰微信自动化内核 | D8 的边界：`_do_send` 对外语义不变，先零回归再叠加批次 |
| 逐句合成比整段慢 | 句子数 × ~0.3-0.6s 的 worker 往返；worker 常驻。可接受，且换来稳定性 |
| 连发多条被微信限流/排序错乱 | 段间轮询浮层 + `BATCH_GAP_S`；P2 可加长停顿 |
| 6 段文本吃掉 6 条历史（`HISTORY_MAX=20`） | 可接受；或把批次折成一条摘要（待定，见 §12） |

**明确不做**：

- ❌ 不做"加速/压缩塞进 60 秒"（D11：改音色，是产品决定不是修补）；
- ❌ 不做"合并成一条更长的语音"（平台无解，别在这个方向浪费时间）；
- ❌ 不新写断句器（D4，已有且踩过坑）；
- ❌ 不用字数估算时长（D2，偏小方向代价是静默截断）；
- ❌ 不动 `_do_send` 的签名与返回结构（D8）。

## 二、关键发现：微信电脑版 4.1.7+ 官方支持发语音消息

2026 年 2 月微信 4.1.7 上线了 PC 端语音消息功能：

- 聊天窗口点输入框左侧**麦克风图标**，或按 **Ctrl + Win** 触发录音；
- **无需按住**：点一下开始录音，再操作结束，比手机版更利于自动化；
- 录音从**系统默认麦克风设备**采集 → 微信自己编码成 silk 发送；
- 快捷键可在 设置→快捷键 自定义。

**这意味着：只要让系统"麦克风"变成 CABLE Output（项目已有脚本），在微信里播放我们的 wav，微信录到的就是变声后的声音，发出去就是真正的语音消息。** 全程不 Hook、不注入、不碰微信内部协议，封号风险与正常使用无异。

## 三、四条路线对比

| 路线 | 原理 | 微信版本 | 真语音消息? | 封号风险 | 结论 |
|---|---|---|---|---|---|
| **A. 官方录音入口 + 虚拟声卡（UI 自动化）** | 麦克风切到 CABLE Output → 用 `uiautomation` 操控微信点击麦克风/发快捷键 → 播放 TTS 音频 → 停止并发送 | 最新版 4.1.7+ ✅ | ✅ 真·语音消息 | 极低（模拟人手操作） | **⭐ 推荐** |
| B. wcferry（Hook 注入） | DLL 注入微信进程，`SendVoice` 直接发 silk | 仅 3.9.11.25 老版，**不支持你的 4.x** | ✅ | 高 | 与你环境不兼容，排除 |
| C. wxauto / wx4py（UI 自动化库） | UIAutomation 桌面自动化 | wxauto 偏 3.9.x；wx4py 支持 4.x | ❌ 只能发文本/文件 | 低 | 发不了语音消息，可借鉴其 UI 自动化写法 |
| D. 协议号/第三方付费 API | 逆向协议 + silk 上传 | 无关客户端 | ✅ | 极高（异地登录设备特征） | 排除 |

### 路线 A 详细流程（拟实现）

```
网页输入文字 → POST /api/wechat/send_voice
  ├─ 1. TTS 合成（袋鼠音色）→ outputs/tts_*.wav     [已有能力]
  ├─ 2. audio_config.ps1 apply 把默认麦克风切到 CABLE Output [已有能力]
  ├─ 3. uiautomation 找到微信聊天窗口（指定联系人），触发录音（麦克风按钮 / Ctrl+Win）
  ├─ 4. 用 sounddevice 向 CABLE Input 播放 wav（微信同时从 CABLE Output 录）
  ├─ 5. 播放完毕 → 结束录音（微信自动发送或再点一次发送）
  └─ 6. 还原系统默认麦克风
```

需要新增的代码：
1. `m2_server/wechat_voice.py`：新模块，封装 UI 自动化（找窗口、点麦克风、结束录音）+ 音频播放到 CABLE；
2. `server.py` 加一个端点 `POST /api/wechat/send_voice`（参数：text / voice_id / 接收人）；
3. 前端 TTS 页加"发送到微信"按钮（或独立微信页）。

### 路线 A 的风险与不确定性（实现时需实测）

- ⚠️ 微信录音**防回采**：部分版本会主动过滤"循环回来的声音"（检测到采集设备是虚拟声卡可能拒绝录音或录出静音）。需实测 4.1.x 行为；若被过滤，备选方案是**真麦播放→手机/另一设备录**（体验差）或 CABLE + 混音卡。
- ⚠️ 录音起始/结束与音频播放的**时序对齐**（早启动≈静音头，需留 200ms 缓冲）。
- ⚠️ UI 自动化要求微信窗口可被定位（可最小化，不必前台置顶也可尝试；失败则闪一下窗口）。
- ✅ 若实测通过，这就是零 Hook、真语音消息、全自动的方案。
