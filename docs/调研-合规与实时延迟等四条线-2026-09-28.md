## 二、★ 合规：AI 内容标识已强制施行一年

### 2.1 法规坐标（两个文件，同一天生效）

| 文件 | 性质 | 发布 | 施行 |
|---|---|---|---|
| 《人工智能生成合成内容标识办法》（国信办通字〔2025〕2 号） | 部门规章（网信办 + 工信部 + 公安部 + 广电总局） | 2025-03-14 | **2025-09-01** |
| **GB 45438—2025**《网络安全技术 人工智能生成合成内容标识方法》 | **强制性国家标准** | 2025-02-28 | **2025-09-01** |

配套还有 **6 项《网络安全标准实践指南》**（网安秘字〔2025〕118 号，2025-08-28）：
文本/图片/**音频**/视频等内容的**文件元数据隐式标识方法**、元数据安全防护指南、
生成合成内容**检测框架**。📚
（<https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm>，
<https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=F32EA2A561F1886CD8D606513512D547>）

> 也就是说：这套东西**已经生效一年了**，不是"未来之患"。

### 2.2 谁被约束 —— 本地工具大概率**不在**强制范围内

- 办法**第二条**把适用对象限定为「**符合**《算法推荐规定》《深度合成规定》
  《生成式 AI 暂行办法》**规定情形的网络信息服务提供者**」📚 原文。
  即：触发条件是"作为**网络信息服务提供者**对外提供服务"，不是"你用了 AI 技术"。
- 官方/律所解读说得更直白（JunHe 2024 解读稿原文）：
  *"Enterprises and institutions that are engaged in the research and development or
  application of AI generative synthesis technology but **do not provide related services
  to the public in China** are not subject to these requirements."* 📚
- 对本项目的含义：**纯本机、不上云的桌面端，属"研发/应用技术但不向公众提供服务"**，
  原则上不在强制标识范围内。✅ 与项目自身定位（README「不上云，全程本机」）一致。

### 2.3 但有三条闸口会打到本项目

**闸口 A — 深度合成规定第 17 条第一款：「显著改变人声」触发显式标识义务**
办法**第四条第（二）项**正是它的落地：音频类要在**
起始、末尾或中间适当位置添加语音提示或者音频节奏提示**，
**或者在交互场景界面中添加显著的提示标识**。
「变声」= 显著改变人声 —— 这条正是冲我们来的。📚

**闸口 B — 微信是「内容传播平台」，它会核验我们产物的元数据（办法第六条）**
平台方义务逐条是：
1. 元数据里**查到**隐式标识 → 打「AI 生成」显著提示；
2. 没查到、但**用户声明**是 → 打「可能为 AI 生成」；
3. 没查到、用户也没声明、但**平台检测到其他生成合成痕迹** → 打「**疑似** AI 生成」。

> ★ **反直觉但关键**：不写标识**逃不掉**，反而更容易落到第 3 档被标成「疑似」。
> **主动按 GB 45438 写元数据隐式标识，输出反而是"确定"而不是"疑似"** ——
> 标识在这件事上是**控制权**，不是负担。

**闸口 C — 应用商店（办法第七条）**
分发平台在**上架/上线审核时**必须要求 app 说明是否提供生成合成服务；
提供了的，**要核验其标识相关材料**。→ 移动端（Expo App）若要上国内商店，这是硬门槛。📚

### 2.4 ★ 产品友好的合规路径（最重要的结论）

**第四条第（二）项给了"交互场景界面"这个出口。**
所以合规**不等于**往用户的微信语音条开头插一句「本音频由 AI 生成」——
那等于把产品毁掉。可以走的是：

```
显式标识  → 放在「交互场景界面」上（发送前的确认区 / 结果页角标 / 设置页说明）
隐式标识  → 写进产物文件的元数据（GB 45438 规定的字段，见 §2.6）
```

第四条还有一句要注意：*"服务提供者提供生成合成内容**下载、复制、导出**等功能时，
应当确保文件中含有满足要求的显式标识。"* → **导出路径**要单独检查。📚

### 2.5 第 9 条与第 10 条 —— 直接对应「微信一键发送」

- **第九条**：用户申请**不含显式标识**的内容时，可以给，但**必须**
  ① 通过**用户协议明确用户的标识义务和使用责任**；
  ② **依法留存提供对象信息等相关日志不少于六个月**。
  → 项目的免责声明 + 微信发送链路，正好落在这里，需要补**用户协议**与**6 个月日志**。
- **第十条**：任何组织和个人不得恶意删除、篡改、伪造、隐匿标识，
  **不得为他人实施上述行为提供工具或者服务**。
  → ⚠️ **真实风险点**：产物发给微信要转码（wav → mp3/SILK）。
  **如果转码把元数据标识丢掉了，就有被认定为"提供隐匿工具"的空间。**
  这是需要设计的一处（转码后回写标识，或改用"内容隐式标识"水印，见 §2.6）。
- **第八条**：服务提供者应在**用户服务协议**里写明标识的方法/样式，并提示用户阅读。

### 2.6 ★ AudioSeal 的定位变了（ROADMAP 该改的一处）

- 办法**第五条**：隐式标识含「生成合成内容属性信息、**服务提供者名称或者编码**、
  内容编号」等制作要素；并且 *"**鼓励**服务提供者在生成合成内容中添加**数字水印**等形式的隐式标识"*。📚
- 国标征求意见稿把这层说成**两类实现**：**元数据隐式标识** + **内容隐式标识**
  （后者即水印，抗元数据擦除）。要素含：生成合成标签（**确定 / 可能 / 疑似**）、
  服务提供者名称或编码、内容编号、传播平台名称或编码、传播平台内容编号。📚
- 本机现状：`docs/待办盘点-2026-09-26.md` 第三节记着 **AudioSeal 全仓 grep 零命中、未开始**，
  ROADMAP 里是 **P2-3**。
- → **结论：AudioSeal 从"面向分发的合规增强"升级为"合规手段本身"**
  （它同时解决 §2.5 那个"转码丢元数据"的问题，因为水印在音频内容里、不在容器里）。
  **建议从 P2 提到 P1**，与"微信发送"这条主链路绑定评估。

## 三、实时延迟：下一档是「架构级因果流式」

- **StreamVC**（Google，arXiv 2401.03078）：*"a light-weight (~20M param.) **causal**
  voice conversion solution that can run in real-time with **low latency on a mobile
  device"*；架构建在 **SoundStream** 之上，用**因果可学习的 soft speech units**
  + **whitened F0** 供给。📚（<https://arxiv.org/abs/2401.03078>）
  有非官方 PyTorch 复现：`yuval-reshef/StreamVC`。📚
- **它对我们的启示是结构性的**：RVC 是「逐块 VITS + 声码器」，
  块大小/上下文决定了延迟下限；StreamVC 把**因果性写进架构**，
  才能在 ~20M 参数下做到端侧实时。
  → 想再砍延迟，方向是**因果流式架构**，不是继续调 buffer / 减 steps。
- 同生态的现状（用于定位，不是要抄）：`w-okada/voice-changer`（VC Client）
  仍是开源实时变声客户端的事实标准，支持 RVC / Beatrice / MMVC 多种后端，
  社区讨论普遍以「**< 50ms 才算能实时对话**」为门槛 —— 与我们 p50 50ms 的口径一致。📚
- ❓ 我**没有**找到 2025–2026 年出现"取代 RVC 的实时开源新架构"的可靠证据。
  这个方向的公开进展看起来停在 2024 年的 StreamVC 一线。

## 四、TTS 生态：Qwen3-TTS 就在 2026 第一梯队

2026 年的横向对比（均 2026 年 5–9 月发布/更新）把主流开源克隆方案列为：
**IndexTTS-2、CosyVoice3、GPT-SoVITS(v2Pro)、Fish Speech、VoxCPM2、Higgs Audio V2、
Kokoro、VibeVoice**。📚

- 有一手社区观察直说：**CosyVoice 2/3 是 2024–2025 的主力，
  但 2026 年 Qwen3-TTS、IndexTTS-2 出来之后，CosyVoice 在情绪控制等维度被超越。** 📚
  → **项目选的 Qwen3-TTS 1.7B 正在这张表的第一梯队**，不用换。
- 可以借的两点：
  1. **IndexTTS-2 的核心卖点是「精确时长控制」+「情感与音色解耦」**
     （明确定位视频配音/对齐场景）。📚 → 对应我们「按字幕/时长对齐」这类需求时值得参考其解耦思路。
  2. **CosyVoice3-0.5B 更轻，且原生流式接口**（`stream=True`）。📚
     → 对「打字让它说」的首包延迟有参考价值（1.7B 自回归 vs 0.5B 流式的取舍）。
- ⚠️ 延迟数字**不能照抄**：有实测记录 IndexTTS-2 在 **RTX 4090** 上单句 **2 分钟+**（自回归代价），
  CosyVoice3-0.5B 约 **24 秒**。📚 这是别人的机器、别人的句子长度，
  **与本机 Qwen3-TTS 不是同一口径**，只作量级参考。（AutoDL / 4090 / 见来源）

## 五、Blackwell sm_120：旧坑已过时，残余风险换了个地方

- **旧坑（2025 年上半年）**：RTX 50 系（sm_120）配当时的 PyTorch → 
  `sm_120 is not compatible with the current PyTorch installation`，或**静默掉回 CPU**；
  解法是装 **cu128** 的 wheel。📚 一堆 2025 年的帖子都在讲这个。
- **现状（2026）**：cu128/cu129 已是常规发布线，这个坑对 PyTorch 本身**基本结束**。
  本机主 `.venv` 实测是 **`torchaudio 2.9.1+cu128`** ✅，与 TTS worker 的 cu129 分属两个 venv。
- **残余风险换了地方 —— 第三方库里预编译的旧 CUDA 二进制**：
  - ⚠️ **onnxruntime-gpu**：2026-05 仍有在案 issue
    *"GPU silent fallback to CPU on RTX 50 series (Blackwell)"*（infiniflow/ragflow #14565），
    绕过办法是把 **cu12 版换成 cu13 构建**。📚
  - 同类风险面：TensorRT / fairseq / pyworld / 旧版 demucs 等自带 kernel 的包。
- **本机现状**：项目**没有**直接依赖 onnxruntime（`grep` 只在
  `tools/audit_plugin_deps.py` 的说明文字里出现过一次 ✅），
  所以这是**潜在坑不是现行 bug** —— 但一旦走 ONNX/TensorRT 加速实时链路，就会踩上。
- **可做的一处加固**：`tools/doctor.py` 现在只打印
  `torch.__version__ / cuda.is_available() / device_name`。
  **`is_available()` 为 True 不代表算子真能跑核**（掉 CPU 是静默的）。
  建议加一条"**实跑一个最小 kernel + 打印 compute capability**"的自检，
  把这类"看着有 GPU 实际在跑 CPU"的问题在 doctor 阶段就暴露出来。

## 八、★ 修订：按「直接上传 GitHub、完全开源、不做移动端、不上架商店」重算

> 前提由用户在 2026-09-28 明确：**形态 = 代码直接开源在 GitHub**，
> **不做移动端**、**不上架应用商店**。以下是据此对第二节的重算结果。

### 8.1 卸载掉的（原来算进去了，现在不适用）

| 原条目 | 新判定 | 理由 |
|---|---|---|
| 第十四条…第七条「应用商店审核须核验标识材料」 | **不适用** | 不上架任何应用分发平台 |
| 移动端（Expo App）标识义务 | **不适用** | 不做 |
| 算法备案 / 安全评估 | **不适用** | 这两个手续针对**提供互联网信息服务**的提供者（办法第十二条把它与标识材料绑在一起）。开源**软件**、不对外提供服务 → 义务不成立 📚❓（无判例，但依据条文主体资格） |
| 「6 个月日志」（第九条） | **降级为可选** | 第九条义务主体是服务提供者；本地工具不留日志 → 义务不成立。但**用户协议/使用须知仍要写**（见 8.3） |

### 8.2 保留、而且被**放大**的

1. **微信侧元数据核验（第六条）** 不受工具获取方式影响 —— 开源后人更多，命中概率更高。
   主动写标识仍是「确定 vs 疑似」的选择题，不是义务题。
2. **深度合成规定第十七条第一款的后半句：「提供显著标识功能并提示使用者」**。
   对**开源工具**，这一句比第十六条更要紧：
   - 工具**内置标识能力 + 提示** → 把决定权交给使用者，责任边界清楚；
   - 工具**完全没有标识能力** → **默认行为就是「不带任何标识的 AI 语音直接发进微信」**。
3. **第十条（不得为他人隐匿标识提供工具或服务）在开源形态下被放大**：
   代码人人可改，但被审视的是**默认行为**。→ **建议默认开标识 + 提供开关，而不是默认关**；
   转码丢标识那处（§2.5）必须补，因为它是默认路径上的。

### 8.3 ★ 开源不自动免责（这一条是新增的，且推翻了「开源=免罪」的直觉）

法律实务界 2026 年的表述很明确，不是「免费开源自动免责」：

- 📚「**这是有条件的司法责任认定，不是『免费开源自动免责』**，也不能直接推广为全部
  开放权重模型、完整商业服务和下游运营者的免责规则。」
  ——《不等于免费商用——开源模型的五个误区》（2026-09-18）
- 📚「若 AI 提供者**通过算法设计实质参与了侵权内容的生成**，或**未尽到与其技术能力
  相匹配的合理注意义务**，则需承担直接侵权、帮助侵权或连带赔偿责任。」
  ——律所对 AI Agent 类软件的分析（2026-03）
- 📚 最高人民法院信息中心转载的圆桌「人工智能时代开源治理的法律回应」（2026-05）
  讨论的正是：基础模型 / 开源平台 / 深度学习框架的**网络服务提供者责任边界**。

→ **判准可以归成两句人话**：**设计有没有实质参与** + **有没有尽到与技术能力匹配的合理注意义务**。
对本项目，「合理注意义务」的具体化恰好就是一件件能写下来的东西：
**免责声明 + 使用须知（AUP）+ 标识能力 + 不预置他人音色 / 不随仓库分发素材与权重**。
（最后一条**已经做到了** ✅：`media/`、`models/`、`tts_models/`、权重后缀全部在 `.gitignore` 内，
仓库里已跟踪权重 = **0 个**。）

### 8.4 ★★ 新增：微信 UI 自动化 —— 开源场景下最实际的一条风险

**这条与「AI 标识」无关，是另一个法源：微信自己的用户协议与安全公告。**

- 📚 微信安全团队公开公告（2024-03）：**「微信明确禁止使用各类外挂」**，
  并对违规使用、以及售卖外挂信息的行为进行**专项清理与处罚**。
- 📚 微信用户协议相关条款（多方转引一致）：**不得自行或者授权他人、
  第三方软件或系统等对微信其组件、模块、数据进行控制、访问、读取或干扰**。
- 📚 2025-12 有公开报道：某 AI 助手操作微信受限，腾讯**以用户协议为据**。
- 本项目的机制是 **UIA（本机 UI 自动化，模拟人类点击）**，
  与「协议逆向 / 进程注入 / 外挂」是**不同机制** —— 这个区分对项目有利，
  **但用户协议那句「控制、访问、读取或干扰」在文本上仍可覆盖 UI 自动化**。❓ 无判例。
- 行业惯例（同类开源项目的做法）：直接在 README 里写
  「使用自动化工具操作微信可能违反微信用户协议，请自行评估风险」。
- ⚠️ **开源把这一条放大的原因**：README 目前把「**把变好的声音一键发进微信**」
  作为头号卖点。在**闭源本机软件**里这是个功能；在**公开仓库**里它是一个
  「**公开展示的、针对第三方客户端本机自动化的实现**」。被审视面完全不同。
