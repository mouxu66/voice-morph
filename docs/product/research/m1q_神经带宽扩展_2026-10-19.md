## 0. 一句话结论

1. **生成这条路成立。** 同一后期链、同一 seed 的 6 臂里，UniverSR 是**唯一「补了高频且「像你」没掉」**的：
   8–12k **−55.3 → −35.7dB**（+19.5dB），而「像你」cos **0.272 → 0.274**（不变）。
   对照：源高频移植补到 −28.7（最准）但 cos 掉到 **0.131**；谱折叠 cos 0.265 但 >8k 包络 CV 从 1.64 抬到 **2.01**。
2. **但还不够亮。** 高频相对中频的斜率：源 `hf_over_mid = −3.4dB`、UniverSR `−10.8dB` —— 差 7.4dB。
   这是「补上了，但补得不够」而不是「补错了」，因为「像你」与包络抖动两项都比另两条路好。
3. **两个坑把一个 bug 做成了「假绿」**（§3）：张量入口的采样率口径错 → 整段被拉慢 3 倍，而时长被截回原长、
   峰值正常、无报错、HF 指标「像没补」。这类错必须靠**跑手自检**（f0 前后对比）拦，不能靠看数字。
4. **README 的 `guidance_scale=1.5` 在我们的干声上等于不出活**：4s 实测量 8–11k 只从 −60.3 到 −59.1；
   `3.0` 才到 −35.5。默认已改 3.5 + `peak>0.99` 整体缩波。

## 1. 为什么选 UniverSR（而不是 AudioSR / BigVGAN / 各种 vocoder）

| 候选 | 结论 | 理由 |
|---|---|---|
| **UniverSR**（`woongzip1/universr-audio`） | **选它** | 📚 同一张音乐对照表上 LSD-HF **0.93**，AudioSR 是 **1.48**；57M 参数、4 步 ODE、pip 装、8GB 够 |
| AudioSR | 不选 | 📚 音乐上弱于 UniverSR；依赖更重（torchlibrosa 等），且它的强项是语音/通用音效 |
| BigVGAN / Vocos / DAC | 不选 | 它们是**声码器**（mel → 波形），不是「给已有波形补高频」；要接就得先自建 mel 前端，等于换整条后端 |
| YingMusic-SVC / HQ-SVC | 下次 | 研究显示唱歌域更强，但**只给 Linux**（本机无 WSL，见 §2 的环境约束） |
| SoulX-Singer | 下次 | 有唱歌能力，但 VRAM 要求未知、无 Windows 实测记录，硬上等于同时动两个变量 |

> 口径提醒：上表的 📚 数字来自各自的项目页/论文，**不是在同一个素材上跑的**。
> 真要横向比较，得用 §5 的同一段 25s 干声各跑一遍 —— 本轮没做（时间花在「先证明方向成立」上）。

## 2. 装它踩到的第一个现实问题：cu128 轮子下不动

`universr_repo/requirements.txt` 钉 **torch 2.7.1** —— 装进主 `.venv` 会顶掉生产用的 **2.9.1+cu128**
（RTX 5060 = sm_120，只认 cu128）。所以第一反应是建独立 venv，实测：

- `download.pytorch.org` 在这条线路上 **≈217 KB/s**，1.3GB 的 cu128 轮子 ≈ **100 分钟**；
- 清华 TUNA 的 pytorch-wheels 镜像 403；HF 镜像同样 ~0.4MB/s。

**改走快路**：主 `.venv` 本来就有同版本 torch → 只补 3 个**纯 Python** 依赖，全部 `--no-deps`：

```bash
./.venv/Scripts/python.exe -m pip install --no-deps timm torchdiffeq
./.venv/Scripts/python.exe -m pip install --no-deps -e universr_repo
# 实测装完：timm 1.0.25 / torchdiffeq 0.2.5 / einops 0.8.2 / torch 2.9.1+cu128（未被改动）
```

模型代码仍走**子进程**（`tools/universr_enhance.py`）——生产后端不 import `timm`，这条边界由
`m2_server/tests/test_cover_bwe_universr.py` 钉住。

**权重**：`universr_repo/ckpts/universr-audio/`（HF `woongzip1/universr-audio`）。下过一次就不再联网，
`universr_repo/` 已进 `.gitignore`（权重 + 第三方 clone 不入库）。

**显存**：25s **整段**一次前向在 8GB 上 **OOM**；分块 5s × 6 块（交叠 0.3s，线性交叉淡入淡出）可跑，
`load 0.87s + run 37.23s`。`chunk_s` 与 `overlap_s` 都是跑手参数。

## 3. 两个坑（都造成了「看起来正常」的错误结果）

### 3.1 张量入口的口径：`input_sr` 是「这波形就是这么多」，不是「内容带宽」

`UniverSR.enhance()` 的语义（读 `universr/inference.py` 实测）：

```python
if file_sr == target_sr:      # 48k 文件但带宽有限 → 模拟降质
    wav = self._apply_bandwidth_limit(wav, effective_sr, target_sr)
elif file_sr != target_sr:    # 真·低采样率 → 升到 48k
    wav = torchaudio.functional.resample(wav, orig_freq=file_sr, new_freq=target_sr)
```

而张量入口的 `file_sr` **就是** `input_sr`。第一版我把**已升到 48k 的波形**配 `input_sr=16000` 喂进去 →
模型认为「这 48k 采样率只是 16k 的内容」→ **再升采 3 倍** → 整段被拉慢 3 倍。

症状极具欺骗性：

| 症状 | 看起来像 |
|---|---|
| 时长被 `n = min(got, total)` 截回原长 | 正常 |
| 峰值 0.5651 | 正常，不报错 |
| 8–11k 仍然 −60dB | 「模型在我们的干声上不产高频」 |
| 4–8k 反而 −62dB | 被我误读成「高频没补上」 |

真正的指纹是**质心 190Hz、rolloff95 586Hz、voiced_frames 1873 vs 1445** —— 全是「变慢」的特征。
**对策**：先把波形真正降到 `input_sr`（内容只到 8k，16k 采样无损），再交给模型自己升到 48k；
并在跑手里加自检：`f0_in` vs `f0_out`，偏移 >0.5 八度直接 `SystemExit`。现在 141.3 → 141.6 才放行。

### 3.2 README 的默认 guidance 属于「能跑但不出活」

同一 4s 干声（8–11k 相对 0–4k）：

| guidance | 8–11k | 峰值 |
|---|---|---|
| 1.5（README 默认） | −59.1 | 0.616 |
| 2.0 | −52.3 | 0.616 |
| 3.0 | **−35.5** | 0.670 |
| 4.0 | −26.3 | **2.004**（削波） |
| 6.0 | +0.5（爆） | 5.984 |

所以：**这不是「模型不行」，是默认超参在唱歌干声上太保守**。现用 3.5 + `peak>0.99` 整体缩波。

## 4. 六臂结果（同一干声、同一后期链、同一 seed）

`media/covers/song2/bwe/listen.html`，25s《好久不见》，全部 40kHz 单声道：

| 臂 | 8–12k | 11–16k | hf_over_mid | 质心 | >8k 包络 CV | 像你 cos |
|---|---|---|---|---|---|---|
| ① 原唱（**仅亮度参照，非真值**） | −24.41 | −30.70 | −3.44 | 756 | 0.78 | — |
| ② 现役链（只抬已有残留） | −55.26 | −69.70 | −30.44 | 617 | 1.64 | 0.272 |
| ③ 抄原唱高频 + 链 | −28.71 | −36.80 | −3.79 | 629 | 0.87 | **0.131** |
| ④ 谱折叠 + 链 | −29.01 | −30.80 | −4.20 | 630 | **2.01** | 0.265 |
| **⑤ UniverSR + 链** | **−35.74** | **−40.60** | **−10.76** | 620 | **1.42** | **0.274** |
| ⑥ ⑤去掉空气感 EQ | −36.96 | −43.20 | −11.85 | 618 | 1.47 | 0.274 |

**怎么读这张表**：

- ③ 补得最准（离源 4.3dB），但把「像你」打掉一半 —— 抄来的相位里带着**别人的发声习惯**；
- ④ 保住「像你」，但包络 CV 2.01 意味着 >8k 的**明暗起伏**比源大一倍（听感上是「沙沙尾音」）；
- ⑤ 是唯一三项都不劣化的：cos 持平、CV 比 ② 还低、频段补了 19dB。**方向成立**；
- **⑤ 与源的差距是 7.4dB（hf_over_mid）**，这是下一步唯一要动的量。

> ⚠️ 「像你」用的是 **CAM++（语音）** 尺子。歌声上它的绝对值不可读，只做**同输入同 seed** 的相对比较。
> ① 那条**不是真值**：这是你的音色唱别人的歌，「你唱这一句的 8–12k」本来就不存在，它只给亮度参照。

## 6. 没做的事（别把这份文档读成「已完成」）

1. **耳朵裁决**：⑤ 是不是「亮而不沙」、有没有凭空编出的嘶声/金属味 —— 只有人能判。
2. **斜率还没对齐**（差 7.4dB）：guidance 4.0 能到 −26.3 但峰值 2.0，需要「先归一化再抬」或分段自适应 guidance，未试。
3. **区间一致性**：6 块各自独立采样（`seed + i`），块边界处的高频纹理是否连贯**没有专门测**（只有听感）。
4. **横向对比没在同素材上做**：AudioSR / YingMusic-SVC / SoulX-Singer 都只是 📚 数字。
5. **产品化没做**：`m2_server/cover_bwe.py` 已能跑（子进程 + 开关 + 缺环境降级），但**没接进 `cover_api` 路由**，
   也没有前端开关。
6. **CAM++ 尺子对歌声的有效性**：本轮只当相对量用，没有在「已知同人/异人」的歌声对上标定过。
