# 调研：RVC 翻唱「声音混杂、不纯粹」—— 社区怎么做 + 本机拆解（2026-10-14）

> **类型**：快照（数字只代表 2026-10-14 这次实测）
> **触发**：用户听完第一版翻唱的原话 —— *「我这个效果不满意。因为我的声音感觉有点混杂，
> 就是没有最纯粹的声音。感觉不怎么好，你去网上搜一下调研一下他们是怎么做的」*
> **结论一句话**：社区给的三个方向（**清干净输入 → 调对旋钮 → 补素材**）里，
> 我们这次的**主因是第三条（素材）**，加上一条社区没怎么提但本机量出来的
> **「变调没对齐 ⇒ 原唱音色泄漏」**；而**最像元凶的那个旋钮（`protect`）在本 fork 里是死的**。
> **原始数据**：`media/covers/knobs/{knobs.json,metrics.json}`（gitignore，产物不入库）+
> 试听页 `media/covers/knobs/listen.html`（11 条，音频内嵌）

## 0. 先给可操作的三句话

| 现象 | 本机实测原因 | 现在能做什么 |
|---|---|---|
| **混杂**（像两个人的声音） | **保持原调**时输出对**原唱**的声纹相似度 **0.2557**（对你只有 0.3762）⇒ 有 1/4 是原唱 | **用降八度那版**（−12）：对原唱 0.0609、对你 0.6240 —— 这是第一版就已经做对的事 |
| **不纯 / 闷** | 你的**训练素材**（12 分钟 PPT 录音）4–8 kHz 比这首歌的歌声**低 ~12 dB**，模型把这份倾斜**原样搬进输出**（4-8k 掉 **18.5 dB**） | 旋钮救不了：要么**补更亮、更干的素材**，要么承认这一版的天花板（见 §4 的三个选项） |
| 我想调参数试试 | 真正能动的只有 **index_rate / rms_mix_rate / 低通 / 变调**；`protect` **三档输出逐字节相同**（死参数） | 别动 `protect`；`index_rate` 保持 0.5（关掉反而更像原唱） |

## 1. 社区怎么做（三个方向，含来源）

### 1.1 先把输入弄干净：分轨 ≠ 干声

- **Demucs 三种模型都没有 lead/backing 分轨**：`htdemucs`（4 轨）、`htdemucs_ft`（微调版、
  官方说可能更好、慢约 4×）、`htdemucs_6s`（多 guitar/piano，官方自认 piano 效果不好）
  —— 六轨**不等于**人声拆得更细。`--two-stems=vocals` 也只是先全分再合并。
  [Demucs 官方仓库](https://github.com/facebookresearch/demucs)
- **要更干净的 lead，需要专用模型**：`Kim_Vocal_2` / `UVR-MDX-NET-Voc_FT` 是第一轮人声候选；
  lead/backing 要另用 karaoke 类模型。MVSEP 的 MDX-B Karaoke Type 1 验证集 lead SDR
  **7.94**、backing SDR 只有 **1.88** ⇒ **能拆出伴唱轨 ≠ 伴唱轨干净**。
  [Applio UVR 指南](https://docs.applio.org/guides/uvr/) ·
  [MVSEP MDX-B Karaoke](https://mvsep.com/algorithms/19)
- **去混响放在分离之后**，而且要克制（混响是烘焙进歌里的，强去会连真尾音一起抹掉）。
  社区常见链路：**分离 → （需要时）lead/backing → 对最终那条轻度 de-reverb → 轻度降噪**，
  每加一步都与上一步 A/B。UVR 的 `UVR-DeEcho-DeReverb` 是 VR 架构的去回声/混响模型。
  [UVR 讨论 #689](https://github.com/Anjok07/ultimatevocalremovergui/discussions/689) ·
  [Applio 指南](https://docs.applio.org/guides/uvr/)

> **本机对照**：我们用的是 `htdemucs`（cover_api 里硬编码）+ `--two-stems vocals`，
> 也就是"粗分离"档；本机**没有**装 `audio_separator`/UVR 模型（实测 `import` 失败），
> 所以"换成 RoFormer/Kim_Vocal"这条**本次没测**，属于未验证的可选方向。

### 1.2 调对旋钮（社区共识 + 本机实测差异）

| 旋钮 | 社区常用 | 本机实测（这个 fork） |
|---|---|---|
| `f0 method` | **唱歌用 RMVPE** | ✅ 已经就是 `rmvpe`（无需改） |
| `index_rate` | 0.5 起步，训练集干净可试 0.75；**0 只作诊断** | `0.5` 对；**实测关到 0 反而更像原唱**（0.0609 → **0.0863**），别关 |
| `protect` | 0.33 起步，0.5 = 关保护 | ⚠️ **本 fork 里是空操作**：0.33 / 0.5 / 0.0 三档 md5 相同（见 §3.1） |
| `transpose` | 只在音域不合时才动，**不要默认整八度** | 我们的 −12 是**算出来的**（歌 219.5 Hz vs 你 108.0 Hz），实测**必须降**（§3.2） |
| `filter_radius` | 很多 fork 有，默认 3（F0 中值滤波） | ⚠️ **本 fork 的 `pipeline()` 里压根没有这个参数**（一开始我还把 `resample_sr` 的参数位当成了它） |
| `checkpoint/epoch` | 不要只用最后一个，多试听几档 | 盘上有 e10/e20/e30/e40 四档，**本次未扫**（见 §5 未测） |
| 一句话处方 | 干净输入 + RMVPE + index 0.5 + protect 0.33 + 合理 transpose | 除 `protect` 外全部已满足 ⇒ **旋钮这一侧没有便宜的提升** |

### 1.3 补素材（社区的第一建议，也是本次的真因）

- **说话数据训的模型唱不了"目标本人的唱法"**，但**能唱**（SVCC 2023 就有"训练只有说话、
  输入是唱歌"的跨域任务，只是更难）。
  [SVCC 2023](https://vc-challenge.org/svcc2023/index.html)
- **最有效的补救不是加 epoch，是补目标本人的干净歌唱素材**（覆盖实际会用到的高低音区、
  长元音、颤音），或者干脆说话+唱歌混训。混训有研究支持但**没有通用比例**
  （Everyone-Can-Sing 用 1:1，且指出说话/歌唱音色差异会影响相似度）。
  [Everyone-Can-Sing](https://arxiv.org/html/2501.13870v1)
- **训练集里的混响/噪声会被学进模型**：社区把混响与噪声列为 RVC 伪影的常见相关因素，
  建议先清理再训练；但**"某个模型因为房间混响而发闷"没有找到确证的案例**（只有
  "训练集要干净"这类一般性建议）。[AI Hub 数据指南](https://docs.aihub.gg/rvc/resources/dataset-isolation/) ·
  [RVC issue #2689](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion-WebUI/issues/2689)
- **别指望换 40k/48k 提清晰度**：没有证据支持"40k 比 48k 干净"，要按预训练权重匹配。
  [RVC issue #514](https://github.com/RVC-Project/Retrieval-based-Voice-Conversion-WebUI/issues/514)
- 其他路线（**未在本机验证**）：Seed-VC 零样本 SVC（不训练、给参考音就能转）、
  so-vits-svc / DiffSVC（专门做歌声转换）。注意 Seed-VC 官方自己的评测里
  相似度更高（SECS 0.7405 vs RVCv2 0.7264）**但听感分 RVC 略高**（OVRL 3.12 vs 3.06）
  ⇒ "更新 ≠ 更纯净"。[Seed-VC 评测](https://github.com/Plachtaa/seed-vc/blob/main/EVAL.md)

## 2. 本机拆解怎么做的（可复现）

```bash
# ① 旋钮扫描 + 模型天花板（必须用 RVC venv；主 venv 没有 torch/infer）
D:/RVC/.venv/Scripts/python.exe experiments/cover_knobs.py \
    --source media/covers/lorezo_feed_the_one/01_original_vocal.wav \
    --voice myvoice_ppt12_full --pitch -12 --start 78 --seconds 20 \
    --out media/covers/knobs --ceiling-clips media/ft_work/ppt12/clips24k --ceiling-n 8

# ② 客观体检 + 试听页（主 venv）
.venv/Scripts/python.exe experiments/cover_metrics.py \
    --knobs media/covers/knobs/knobs.json --ref media/ft_work/ppt12/ref_24k.wav \
    --orig media/covers/lorezo_feed_the_one/01_original_vocal.wav \
    --start 78 --seconds 20 --page

# ③ 行为保持的端到端证明（重跑产品那次的输入，与产品产物比 md5）
D:/RVC/.venv/Scripts/python.exe experiments/cover_knobs.py --verify-product \
    --source media/covers/lorezo_feed_the_one/01_original_vocal.wav \
    --verify-against media/covers/lorezo_feed_the_one/02_my_voice_vocal.wav \
    --voice myvoice_ppt12_full --pitch -12 --out media/covers/knobs
```

口径：同一段 20 秒（78–98s，歌声最密处）、同一 seed（1234）、同一模型；
每条只换一个旋钮 ⇒ 差异归因于那个旋钮。**对照必须是 44.1 kHz 的原唱**
（拿 16 kHz 那份当对照会让 8 kHz 以上天然为空，把"高频掉得多"这件事**说小**）。

## 3. 实测结果

### 3.1 `protect` 是死参数（★ 本次最反直觉的一条）

源码上看，`infer/vc/pipeline.py` 的 `protect < 0.5` 分支把非浊音帧写成
`feats = protect × 转换后 + (1 − protect) × 原唱特征` —— 0.33 就是"掺 67% 原唱"，
**字面上就是"混杂"**。但本 fork 的 `get_f0()` 先把无音高帧 `np.interp` 插值掉、
再返回 `f0bak`，于是 `pitchf` 几乎处处 > 0 ⇒ `pitchff` 恒为 1 ⇒ 该分支等于没执行。

| 配置 | md5（前 12） |
|---|---|
| `protect = 0.33`（现役） | `dc785303d713` |
| `protect = 0.5` | `dc785303d713` |
| `protect = 0.0` | `dc785303d713` |

`get_f0` 探针：**非浊音帧 0 / 20808**（median f0 128.95 Hz）。
⇒ **别改这个参数**；也说明"从源码读出机制"之后**必须实测它是否真的会运行**。

### 3.2 真因一：原唱音色泄漏由"音高够不够得着"决定

CAM++ 余弦（同一段、同一 seed）。"对原唱"高 = 输出里混着原唱的音色：

| 配置 | 对你 | **对原唱** |
|---|---|---|
| A_base（**降八度 −12**） | **0.6240** | **0.0609** |
| G_p0（**保持原调 0**） | 0.3762 | **0.2557** |
| H（原调 + ir0 + 无低通） | 0.3779 | **0.3050** |

⇒ 保持原调时，输出"有 1/4 像原唱、只有 0.38 像你" —— **这才是"两个人的声音混在一起"**。
降八度把它压到 0.06。这条**独立支持了第一版的降八度建议**（原先只凭中位基频推断）。

### 3.3 真因二：训练素材的频谱倾斜被原样搬进输出（"闷"）

分频段能量，以 0–4 kHz 为 0 dB（逐频段绝对 dB 见 `metrics.json`）：

| 素材 | 谱质心 | 4–8 kHz | 8–11 kHz |
|---|---|---|---|
| **原唱**（44.1k） | 889 Hz | **−19.5 dB** | −18.7 dB |
| A_base（换成你的音色） | 538 Hz | **−38.0 dB** | −75.5 dB |
| **天花板·输入**（你自己的说话素材） | 369 Hz | −31.1 dB | −65.0 dB |
| **天花板·输出**（同一段过模型） | 353 Hz | **−33.6 dB** | −74.1 dB |

两个读数合起来是结论：

1. 翻唱输出比原唱在 **4–8 kHz 低 18.5 dB**（质心 889 → 538 Hz）—— 这就是"闷"；
2. **但模型在它自己的域内只丢 2.5 dB**（−31.1 → −33.6）⇒ 它不是"高频杀手"，
   它**忠实地复现了训练素材那份偏暗的倾斜**（你的素材 −31.1 dB vs 歌里 −19.5 dB，差 ~12 dB）。

⇒ 瓶颈在**素材**，不在模型结构，也不在旋钮。这与社区 §1.3 的建议同向，但**本机把它量化了**。

### 3.4 其余旋钮的收益（都很小，且不值得改默认）

| 配置 | 质心 | 4–8k | 对你 | 对原唱 | 判断 |
|---|---|---|---|---|---|
| A_base（现役） | 538 | −38.0 | 0.6240 | 0.0609 | 基准 |
| D_ir0（关检索） | 576 | −35.0 | 0.6061 | **0.0863 ↑** | 略亮但**更像原唱** ⇒ 别关 |
| E_nolp（去 11k 低通） | 538 | −38.0 | 0.6261 | 0.0635 | **只动 11k 以上那片本就空的区域**（质心不变）⇒ 无感 |
| F_rms1（用模型包络） | 519 | −37.4 | 0.6165 | 0.0596 | 无实质差异 |

## 4. 所以下一步该做什么（按性价比排）

1. **`protect` 别动**，`index_rate` 保持 0.5，`transpose` 坚持算出来的 −12 —— 这三条已经是最优组合。
2. **素材侧**（唯一能动"闷"的杠杆，三选一）：
   - ① **补一段干净、近距离、无混响的录音**（同一支麦、安静房间，1–2 分钟就够先试），
     混训后看 4–8 kHz 是否抬起来（尺子已就位：`cover_metrics.py`）；
   - ② **补唱歌素材**（本人哼唱实际音域内的长音/乐句）—— 直接补的正是"跨域"这一块；
   - ③ 什么都不补，接受这一版天花板（但那样"不纯"就会一直在）。
3. **输入侧**（未验证的次优选项）：换成 RoFormer/Kim_Vocal 级别的分离 + 轻度 de-reverb。
   本机没装这些模型，**要先装再量**，别先下结论。

## 5. 诚实边界（引用时必须一起带）

- **n = 1 首歌 / 1 段 20 秒 / 1 个说话人**；单个 seed（1234，本链路已固定种子 ⇒ 同参数可复现）。
- **CAM++ 是语音声纹尺子**，用在歌声上只作**同一输入下的相对比较**（A vs G 这种），
  不能当绝对像度读。
- **不测 NatScore**：项目自己的裁决书已实测它把真人排在所有合成之下，绝对值不可跨"真人/合成"比较
  （见 `m1f_千问微调vsRVC-声音克隆裁决_2026-10-14.md` §5）。
- **天花板测试的对照不是同体裁**：输入是你的**说话**素材、歌里是**演唱**，
  所以"素材比歌暗 12 dB"里混着**体裁与混音**的贡献（专业混音本来就亮），
  **不能**把 12 dB 全算到"你的麦克风差"头上。可确证的是：
  **模型会把训练素材的频谱倾斜搬到输出上**，而这份倾斜比这首歌暗。
- **未测**：换分离模型/去混响；checkpoint（e10–e40）扫描；多首歌；RoFormer/Seed-VC 等替代路线。
- **旋钮扫描只在"值变了"这一层**证明有效（md5 不同），"听起来更好"仍要人耳；
  试听页 `media/covers/knobs/listen.html` 就是为此准备的（11 条，可逐条播放）。
