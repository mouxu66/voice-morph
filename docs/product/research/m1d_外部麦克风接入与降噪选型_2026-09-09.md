# M1d · 外部麦克风接入与降噪选型调研

> 2026-09-09 · M1 系列（PC-first 范围内）· 研究问题：**用户没有专业麦克风时，手机/USB 麦克风能不能接入变声工坊？降噪能不能借鉴开源方案？**

## 0. 结论先行

1. **手机当麦克风：行，且有现成开源方案可借/可用。** GitHub 上已有一批"Android → PC 虚拟声卡"的成熟项目，共同架构 = 手机采 PCM → TCP（WiFi 或 USB adb forward）→ PC 播进 **VB-CABLE** → 任何应用把它当普通麦克风。我们已内置 VB-CABLE，接入成本极低。
2. **降噪不用"拿过来"——我们已经在用比它们更强的。** 离线链路已挂 DeepFilterNet3（`deepfilter_stream`，带三档强度 + 标定工具）。MicRouter 用的 RNNoise、MicYou 用的 PureVox 都是同类，我们不缺。**真正的缺口是实时链路（cascade / rvc_live）没挂降噪**，把自家 DFN3 复用过去即可。
3. **对自家系统而言，"手机麦克风"就是一个普通输入设备**——系统识别外部设备的能力已经有了（sounddevice 枚举，本机实测 19 个输入设备），缺的是**实时链路的输入设备选择 UI**（目前写死环境变量/关键词匹配）。
4. 推荐路径：**P-A 兼容层（快）+ P-B 自家 App 集成（顺）双轨**，P-C USB adb 直连作为 P-B 的增强选项。这把移动端 App 从"降级的遥控器"重新定位成 **PC 主线的免费麦克风外设**，与 m1c 的 PC-first 转向完全兼容。

## 1. 开源项目盘点（GitHub，2026-09 检索）

| 项目 | Stars/协议 | 连接方式 | 技术栈 | 降噪 | 对我们的价值 |
|---|---|---|---|---|---|
| **MicYou** (LanRhyme/MicYou) | 3.6k★ / GPL-3.0 | WiFi / **USB(ADB)** / Web 扫码 | Kotlin + Rust(Tauri2) | AI 降噪(PureVox) + 传统 + AEC7 + 去混响 + AGC + VAD | 最成熟活跃；**Web 扫码免装 App** 思路可借 |
| **MicRouter** (op30mmd/MicRouter) | 活跃(198 commits) | **USB(adb forward TCP)** | **Python 后端** + Flutter + 原生安卓 | RNNoise + 硬件 NS/AEC | **架构最像我们**（Python 后端收流→播到指定声卡），借鉴成本最低 |
| **PhoneMic** (NLarchive/PhoneMic) | 新项目 | USB(adb forward) | Kotlin + Python | 依赖手机端硬件 NS | 极简参考实现：AudioRecord→localhost TCP→VB-Cable |
| **AndroidMic** (PavlosPV/AndroidMic) | MIT | 蓝牙/WiFi/USB tether | Kotlin + C# | SpeexDSP + RNNoise | 滤镜链参考；蓝牙路径延迟偏高不采 |
| **audiosource** (gdzx/audiosource) | F-Droid 上架 | USB(adb) | Kotlin + Python | 无 | 仅 Linux PulseAudio，不适用 |

**共同终点**：PC 端把手机流写进虚拟声卡（Windows=VB-CABLE）→ 会议/游戏/直播软件直接选它当麦克风。**对我们同样成立：手机麦克风接入后 = 实时变声链路的一个输入源。**

**USB 关键事实**：无 root 安卓**不能**伪装成 USB UAC 麦克风（gadget 模式需内核支持）；可行路径是 **USB 数据线 + adb forward 跑 TCP 流**（免 WiFi、延迟低、不占局域网），代价是用户需开一次"USB 调试"。WiFi 路径则零设置，代价是延迟抖动看路由器。

| 输入设备选择 UI | ❌ 前端无下拉选择器 | — |

| 手机→PC 推流 | ✅ 移动 App 已有 mic→PC 流式链路（cascade 主链路本体） | mobile + cascade_stream |

**一个必须处理的设计冲突**：cascade 的防回环逻辑会拒绝"CABLE 作输入"。若手机流（经 MicYou 等）推进 CABLE，则"源=CABLE Output"恰好是要拦的场景。解法：防回环规则从"拒绝 CABLE"改为"**拒绝默认路由回环**"——当用户显式选择 CABLE 作输入时放行，但输出端禁止再写同一 CABLE（写第二虚拟声卡或直接进 RVC 引擎不落声卡）。

## 3. 三条接入路径对比

| 路径 | 做法 | 用户体验 | 工作量 | 建议 |
|---|---|---|---|---|
| **P-A 兼容层** | 引导用户装 MicYou/MicRouter 推流到 CABLE；我们加"输入设备选择"UI | 装两个软件，一次性设置 | **小**（设备选择器 + 防回环放宽 + 指引文档并入 A1 向导） | ✅ 先做，立刻兼容一切外置麦克风（USB 麦/手机/调音台） |
| **P-B 自家 App 麦克风模式** | 移动 App 加"当麦克风"模式：复用现有 mic→PC 推流，PC 端收流写 CABLE（或直进 RVC 跳过声卡，零回环风险） | **一个 App 搞定**，与产品配对/二维码体验一体 | 中（PC 收流端 + App 模式开关） | ✅ 立项，产品差异化：竞品都没有"自家手机=自家麦克风" |
| **P-C USB adb 直连** | 学 MicRouter：adb forward TCP，免 WiFi | 最稳最低延迟，但需开 USB 调试 | 中（在 P-B 上加传输通道） | ⏸ P-B 验证后作为"进阶连接"选项 |

**降噪落地（不依赖路径选择，独立可做）**：把 `deepfilter_stream`（DeepFilterNet3，已在依赖）挂到实时链路输入端：
- 位置：cascade 收帧后、ASR/RVC 前（与离线链路"降噪在前"次序一致，ASR 也受益）；
- 档位：复用 `audio_enhance.py` 三档强度设计 + "压弱人声"教训（默认中档）；
- 回退：DFN3 模型不可用/低配机 → 可选 afftdn 或关闭（RNNoise 留作低端备选，werman/noise-suppression-for-voice 6.3k★，LADSPA/C 实现极轻）；
- 验收：真机测 RTF 与端到端延迟增量（DFN3 帧级处理，预期 <30ms CPU 开销，不挤占 RVC 推理预算）。

## 4. 行动清单（接 M1b 的 A1-A6 序列）

- **A7 实时输入设备选择器**（小）：实时页加输入设备下拉（sounddevice 枚举 + 记忆选择），cascade 防回环逻辑放宽为"显式选择可越过，输出端防回写"。做完后 **USB 麦克风、调音台、P-A 手机方案全部即插即用**。
- **A8 实时降噪开关**（小-中）：DFN3 挂实时输入端 + 三档开关，默认开（中档）。
- **A9 手机当麦克风（自家 App 模式）**（中）：P-B 立项——App"麦克风模式" + PC 收流写 CABLE / 直进 RVC；二维码配对复用现有设计。
- **A10 兼容外设指引**（微小）：A1 发送链路向导里加"外置麦克风/手机麦克风"标签页，图文指向 MicYou/MicRouter 安装指引（P-A 兜底，也服务 USB 麦用户）。

**建议顺序：A7 → A8 → A10 →（真机实测后）A9。** A7+A8 是纯 PC 侧收益，覆盖所有用户；A9 是差异化功能，值得但需要 App 侧联动开发。

## 5. 局限声明

- MicYou/MicRouter 的**实际延迟未实测**（官方无数据），WiFi 模式抖动未知——P-A 上线前用自家耳听验收，P-B 立项前先拿 MicRouter 跑一次 USB 实测（adb 路径是我们 P-C 的直接参照）。
- DFN3 实时档的 CPU 占用需真机验证（沙箱 CPU 不代表用户低配机）；8GB 显存用户 GPU 已被 RVC/TTS 占用，DFN3 走 CPU 路径（deepfilter_stream 本就是 CPU/ONNX），无显存冲突。
- 手机端硬件 NS/AEC（安卓 AudioRecord 内建）质量参差，P-B 需保留"硬件增强开关"（MicRouter 同款做法）。
