## 2. 实时变声（VC）：为什么 RVC 换不掉

这是本次调研**证据最硬**的一节。

| 方案 | 算法延迟 | 端到端 | 参数 | 零样本 | 来源 |
|---|---|---|---|---|---|
| **RVC v2（现役）** | **~15ms** | 40ms 块下 **55–75ms**（不含网络） | — | ❌ 需训练 | clonemyvoice.io 2026 |
| **Seed-VC（流式）** | **343ms** | + ~100ms 设备侧 ≈ 440ms | 25M | ✅ | 同上 / seed-vc 官方 README（~300ms 算法 + ~100ms 设备） |
| **MeanVC（前代）** | — | **211ms** | 14M | ✅ | MeanVC2 官方 README |
| **MeanVC2** | — | **110ms**（流水线首包，40ms chunk） | **18M** | ✅ | **官方 README（已核）** |
| X-VC | 未查到具体 ms | — | 未查到 | ✅ | arXiv:2604.12456，SJTU |
| w-okada/voice-changer | 未查到 | — | 多模型壳 | 视后端 | GitHub |

**关键结论**：Seed-VC 的 343ms 是**方法本身的物理下界**——扩散/迭代去噪无法截断到低延迟而不崩音质。官方 README 自己写的是"算法延迟 ~300ms"，与第三方口径一致。项目里 `seed_vc/` 只能当**离线**备选，这一点原先的判断是对的。

> 2026 年的延迟瓶颈已从声学模型转移到**声码器**：HiFi-GAN 类 5–15ms/chunk，BigVGAN 全质量要 3–10 倍。所有 sub-100ms 系统都刻意选 GAN 声码器——这是设计取舍，不是实现细节。

### 2.1 曾被寄予厚望的唯一新选项：MeanVC2（已核官方一手数据）

> ⚠️ **读前提醒（v3）**：本节是**调研时的原始记录**，保留"为什么当初值得试"的推理链，便于复盘。**结论已被 §2.2-C 推翻——MeanVC2 最终判定为"否决，不接入"。** 请以 §2.2 / §2.3 的实测为准。

`github.com/ASLP-lab/MeanVC2` / HF `ASLP-lab/MeanVC2` / arXiv:2606.09050（西工大 ASLP@NPU + UNSW + WeNet）

**能力（官方 README 原文口径）**：

- **18M 参数**（前代 MeanVC 14M；对比 RVC 的量级、VoxCPM2 的 2B —— 差两个数量级）
- **端到端流水线首包延迟 110ms**（40ms chunk）；前代 MeanVC 是 **211ms** ——即官方口径的"将近减半"
- **零样本**：不需要为每个音色训练，直接喂参考音
- **单 CPU 核 RTF < 0.633**；FRC（未来感知分块）使峰值显存**降约 60%**
- 技术点：未来感知分块（FRC）+ 通用音色令牌编码器（UTTE，对参考音质量鲁棒）+ **Mean Flows 单步 1-NFE** ODE
- **Apache-2.0**（已核 LICENSE badge）；训练数据含 Emilia

**★ 架构（决定了它的上限，也决定了它为什么"能进本项目"）**：

识别-合成范式，五段式：**流式 ASR（Fast-U2++ / WeNet）提 BNF → ECAPA-TDNN + WavLM 出说话人嵌入 → UTTE 交叉注意力检索音色 → 4 层 DiT（CFM）出 mel → Vocos 声码器 → 16 kHz 输出**。

**★★ 官方已提供 Windows CPU-only 单 exe，且 README 直接写了 VB-CABLE 路由**：

| 可执行文件 | 延迟 | 说话人输入 | 体积 |
|---|---|---|---|
| `40ms_40ms.exe` | 40ms chunk + 40ms future = **80ms** | WAV 文件（WavLM + ECAPA-TDNN） | Full |
| `120ms_40ms.exe` | 120ms chunk + 40ms future = **160ms** | WAV 文件 | Full |
| `40ms_40ms_npy.exe` | 80ms | 预抽取 NPY | 小 ~1.2GB |
| `120ms_40ms_npy.exe` | 160ms | 预抽取 NPY | 小 ~1.2GB |

> 官方原话："**Audio Routing**: Input from microphone or **VB-CABLE Output** (capture PC playback); output to headphones/speakers or **VB-CABLE Input** (send to other apps, e.g., set as mic in Tencent Meeting)." 要求 Windows 10+ / 8GB RAM / ~4GB 磁盘。
> **这几乎就是把本项目的链路写进了它的文档**——麦克风或 CABLE Output 进，CABLE Input 出。且**纯 CPU，不动显卡**。

**为什么它值得单独拎出来**（⚠️ **v3：该推理已被实测推翻**，见 §2.2-C）：RVC 换音色的代价是"每个新音色都要训练一次"（项目为此建了整套 `finetune` 流水线）。MeanVC2 若真能零样本 + 110ms，等于**直接砍掉训练环节**，同时把整张显卡让给 TTS。且它保留了 **speaker-specific fine-tuning**（用 safetensors 预训练权重做初始化）——万一零样本相似度不够，还能退回"微调"路线，等于**两头都留着**。

**必须在实测中确认的三条风险**（**v3：三条已全部本机实测，结论见 §2.2**）：

1. **16 kHz 输出**（Vocos）。RVC 现役是 40k/48k。16 kHz 的带宽上限只有 8 kHz，**听感上大概率更闷**——这是 18M + 单步 ODE 的必然代价，不是配置问题。→ **实测确认：8 kHz 以上结构性为零，非配置可解**。
2. **相似度上限未知**。110ms 是**流水线延迟**，不是音质指标。"11 亿小时级"训练量换不来 18M 的表达力上限。**必须人耳 A/B，且用袋鼠参考音**。→ **实测确认：音色迁移全面弱于现役 RVC**（LTAS 0.914–0.936 vs RVC 0.958）。
3. **范式不同**：内容/节奏来自 BNF（ASR 瓶颈特征），音色来自 UTTE 检索。**它不像 RVC 那样完整保留源 F0/韵律**——语气会被 ASR 那一段重新"解读"一遍。对"游戏内实时变声"是加分还是减分，只有实测知道。→ **实测确认：音高迁移只做到 RVC 的一半**（F0 变化 −6Hz vs −13Hz），源音残留更明显。

### 2.2 MeanVC2 本机 CPU 实测（v3 新增，2026-09-14）

**环境**：Windows 本机 CPU（非 GPU）、torch 2.5.1+cpu、12 逻辑核；源音 `tts_models/ref/meituan_rat_002.wav`（异说话人 3.08s）→ 目标音色袋鼠；实验目录 `D:\meanvc2_exp`（不入库）。RVC 基线走项目现役 `m2_server.rvc_convert` + `logs/kangaroo_v2`。

**A. 音色/音高迁移（与 RVC 同源同目标对比）**

| 音频 | SECS¹ | **LTAS 谱形相关** | F0 中位 | 采样率 |
|---|---|---|---|---|
| 目标参考音（袋鼠） | 1.000 | 1.000 | 126.3 | 22050 |
| 源音 未转换 | 0.964 | 0.866 | 125.0 | 22050 |
| **RVC kangaroo_v2** | 0.981 | **0.958** | 112.1 | 48000 |
| MeanVC2 120ms preset | 0.954 | 0.936 | 119.2 | 16000 |
| MeanVC2 40ms preset | 0.960 | 0.919 | 119.3 | 16000 |
| MeanVC2 120ms / steps=10 | 0.958 | 0.914 | 119.6 | 16000 |

¹ **SECS 在本项目不可用作唯一判据**：项目 x-vector 的余弦量程塌缩（未转换底噪即 0.964，全量程仅 ~0.04），单看它会把"未转换"判得比"转换后"更相似。**必须配 LTAS**。已记 `docs/犯错指南.md` §3.13。

**结论**：**音色迁移 MeanVC2 弱于 RVC**（LTAS 差 0.022–0.044）；F0 只迁移一半；**加步数（3→10）无收益反降**；无削顶/无直流偏移。

**B. 实时余量（修正官方口径）**

| preset | 块时长 | 单块计算 | 块内 RTF | VC RTF(整段) | 算法延迟² |
|---|---|---|---|---|---|
| 120ms（1 线程） | 120ms | 40ms | 0.333 | **0.348** | 200ms |
| 120ms（12 线程） | 120ms | 40ms | 0.336 | 0.351 | 200ms |
| 40ms（1 线程） | 40ms | 38ms | **0.949** | 0.932 | **118ms** |
| 40ms（12 线程） | 40ms | 39ms | 0.967 | 0.973 | 118ms |

² 算法延迟 = chunk + block 前瞻(40ms) + 单块计算；未计网络/声卡缓冲。官方 exe 名里的 80ms/160ms 即是前两项之和，与本机实测吻合。

**三条修正官方口径的结论**：

1. **官方"单 CPU 核 RTF < 0.633"只对 120ms preset 成立**（实测 0.348）；**40ms preset 实测 0.932**，几乎贴着实时的边——**1 线程下只剩 5% 余量，任何后台负载都会掉帧**。
2. **多线程没有任何收益**（12 线程与 1 线程几乎完全一致）。per-chunk 张量太小，线程调度开销吃掉了并行度。含义有两层：**买不到余量**；但也意味着它**只吃一个核就能跑住**，可以和 TTS/其他负载共存。
3. **ASR 段不是瓶颈**：warm RTF 仅 0.062（120ms）/ 0.117（40ms）。（首测因含 JIT 首次 warmup 误得 RTF≈1，剔除热机后为 1/16。）

**C. 定位判定（v3 修订，2026-09-14）**：**否决，不纳入本项目**。

原判定是"互补而非替代"——留一个"零训练任意音色快试"的口子。但把三轴资源账（§2.3）算完后这个口子也站不住了：

| 维度 | MeanVC2 相对 RVC | 判定 |
|---|---|---|
| 音色迁移 | LTAS 0.914–0.936 vs **0.958** | ✗ 更差 |
| 音高迁移 | F0 只迁一半 | ✗ 更差 |
| 带宽 | 16kHz（8kHz 以上结构性为零） vs 48kHz | ✗ 更差 |
| 显存 | 0MB vs 377MB | ✓ 优（但 377MB 本就不是瓶颈） |
| **RAM** | **2285MB** vs 2509MB | ≈ 相当（"省内存"不成立） |
| CPU | 0.32 核 vs 限线程后 2.3 核 | ✓ 优（但 RVC 限线程后已足够） |

**唯一"省下的"是 377MB 显存**，而真正的 5GB 显存债是 TTS worker（仅级联模式需要，关掉即可）——**省这 377MB 要拿音色、音高、带宽三项全输去换，不划算**。加上它给出 16kHz（与项目 cascade 锁死的 24kHz 帧协议反方向），集成还要再改协议。

**最终结论**：**RVC 是固定音色的最优解，MeanVC2 在任何一个维度都不构成"用它替代 RVC"的理由**。实验室数据留档（§2.2 / §2.3 / §2.3-D），**不再接线、不再跟进**。若将来出现"只要不训练、音质可以差一点"的极端场景，实验沙箱 `D:\meanvc2_exp` 可随时复活，成本 17 分钟。

**D. 能不能上 GPU？——能跑，但不值得**（v3 补充实测，RTX 5060 Laptop 8GB）

分模块的可行性**不一致**，必须先拆开看：

| 模块 | 能否上 CUDA | 依据 |
|---|---|---|
| ASR（Fast-U2++ JIT） | ❌ **不行** | JIT 图在 **CPU-only conda 环境**下 trace；`map_location=cuda` 只搬注册参数，搬不动 trace 时冻结为常量的张量 → `Expected all tensors to be on the same device`。**官方把 ASR 写死 CPU 不是偷懒，是搬不动。** |
| 说话人编码器（WavLM-Large+ECAPA） | ✅ 可以 | `load_spk_model(device)` 已参数化，实测占用 **1236MB** |
| VC（DiT 18M + Vocos） | ✅ 可以 | `vc_inference(..., device)` 全程参数化；Vocos JIT 实测可上（80 参数全在 cuda:0） |

**但搬到 GPU 的收益极小**：

| preset | 单块计算 CPU→GPU | 加速 | 块内 RTF CPU→GPU | 算法延迟 CPU→GPU |
|---|---|---|---|---|
| 120ms | 38.2 → 29.7ms | **1.29×** | 0.319 → 0.248 | 198 → **189ms**（省 8ms） |
| 40ms | 43.1 → 39.4ms | **1.09×** | **1.080 → 0.989** | 123 → **119ms**（省 4ms） |

**关键判断**：

1. **GPU 救不活 40ms 档**。它在 CPU 上块内 RTF 1.08（跑不住），到 GPU 是 0.989——**刚好卡在 1.0，零余量**，任何负载就掉帧。
2. **延迟的大头与算力无关**。120ms 档的 160ms（chunk 120 + 前瞻 40）、40ms 档的 80ms 是**流式缓冲**决定的，换什么卡都省不掉。GPU 只能动剩下那 40ms 里的 8ms。
3. **根因是 latency-bound 而非 throughput-bound**：18M 模型 + per-chunk 小张量，每块 3 步 × 4 层 DiT 是一条**串行 kernel 依赖链**，GPU 的并行度用不上。这也解释了为什么多线程同样零收益（§2.2-B）。
4. **显存账算不过来**：MeanVC2 上 GPU 稳态占 **1615MB、peak 2153MB**；而 TTS worker 常驻时本机只剩 **2926MB**（8001 worker 占 4974MB，且它会在加载/卸载间摆动——曾观测到瞬时 7043MB 空闲，那是假象）。装得下，但只剩 ~0.8GB 余量，再叠任何东西就 OOM。
5. **工程代价**：首块有 **~5s 的 CUDA 预热**（cuDNN autotune/kernel 编译）。不预热的话"整段 RTF"会假性恶化到 2.05（vs CPU 0.326），这是冷启动假象、不是稳态。

**结论：MeanVC2 就该跑 CPU。** 120ms 档在有 TTS 竞争的单核上块内 RTF 0.319、整段 0.326，余量充足——**这正是它作为"CPU-only 单 exe"发布的设计意图**。把它搬上 GPU 换来 8ms、花掉 1.6GB 显存（8GB 笔记本上最稀缺的资源），不划算。

### 2.3 三轴资源账：RVC vs MeanVC2（v3 新增，2026-09-14）

**缘起**：显存只是账的一半。MeanVC2 省显存但吃 CPU，RVC 反之——哪边更重要取决于**游戏卡在哪**，所以要三个维度都量出来。

| 方案 | CPU 峰值占用 | 显存 | RAM 稳态 |
|---|---|---|---|
| **RVC 实时链路**（默认，OMP 未限制） | **14–17 核爆发**（单次转换 wall 0.30s 内烧 4.7 CPU 秒） | 377MB | **2509MB** |
| **RVC 实时链路**（`OMP_NUM_THREADS=2`） | **2.3 核** | 377MB | 2509MB |
| **MeanVC2**（CPU，`threads=1`） | **0.32 核**（平缓，单核 32% 占空） | **0MB** | **2285MB**（加载瞬时峰值 3617MB） |

**口径**：CPU 用「CPU 秒 / 音频秒」，两方案可比（RVC 1.355 → 0.209；MeanVC2 ≈ 0.32 核等效）。RAM 为进程树稳态 RSS，**必须区分加载瞬时峰值**（WavLM-Large 的 1.2GB checkpoint 有临时副本，峰值 3.6GB 不代表常驻）。

**三个结论**：

1. **★ RVC 默认配置在 CPU 侧是个隐患**。worker 只是个 1 线程转发壳，真正的推理跑在 **119 线程的子进程**里，每次转换瞬时拉满 **14–17 个核**。根源是 `OMP_NUM_THREADS` / `MKL_NUM_THREADS` / `OPENBLAS_NUM_THREADS` 全为 None（FAISS index 搜索 + MKL 吃满所有核）。
2. **★ 限制线程数是纯赚的优化**：`OMP_NUM_THREADS=2` 后 **CPU 秒/音频秒 1.355 → 0.209（降 6.5×）**、等效核数 **14.4 → 2.3**，而**稳态 RTF 0.094 → 0.091 完全不变**（转换是 GPU-bound，多余的 CPU 线程纯属互相踩踏）。**对 CPU 敏感的游戏（如无畏契约、CS2）这是从"会掉帧"到"基本无感"的差别。**
3. **RAM 不是区分因素**：两者稳态都在 **2.3–2.5GB**，相当。但这意味着**在 16GB 机器上，变声 + 游戏 + TTS worker 同时在线会让 RAM 先于显存告急**（实测开机状态只剩 5.5–6GB 可用，系统已在跑 `MemCompression`）。**换模型解决不了 RAM 问题，只能关进程。**

**动态比例判据（按游戏瓶颈资源选）**：

| 游戏瓶颈 | 该省什么 | 判断 |
|---|---|---|
| **CPU**（竞技 FPS / 高帧率，如无畏契约） | CPU 线程 | **RVC + 限 OMP 线程**。默认的 14–17 核爆发会直接造成帧时间抖动；MeanVC2 的 0.32 核虽更平缓，但它持续占据一个核的 32%，而这类游戏对**单核频率**敏感，未必更优——且音质更差 |
| **显存**（3A 高画质 / 大纹理） | 显存 | **RVC + 关掉 TTS worker**。RVC 只占 377MB 本来就不是问题；真正的 5GB 是 TTS worker（仅级联模式需要）。MeanVC2 省下的 377MB 换不回音质损失 |
| **RAM**（16GB 机器 + 现代 3A） | RAM | **两者相当（2.3–2.5GB），换模型无效**。要省只能关进程 |

**一句话**：要调的是**配置（限线程）**和**该关的进程（TTS worker）**，不是换模型。

### 2.4 反作弊 vs 虚拟声卡（v3 新增，2026-09-14）

**缘起**：用户问"游戏内变声会不会被反作弊盯上"。这是 **VC 模型选型之外**的独立问题——**换成 MeanVC2 还是一样**，因为它取决于链路末端那个"虚拟麦克风"是怎么来的，而不是怎么算出来的。所以单独开一节。

**先分清两件事**（舆论把这两件混为一谈，是本议题最大的坑）：

| 问题 | 结局 | 触发条件 |
|---|---|---|
| **会不会被封号** | ❌ 不会（无记录） | 只有**注入游戏进程 / 改游戏内存 / 给玩家不该有的信息**才会 |
| **会不会被拒绝启动** | ⚠️ 可能（VAN148） | 装了 Vanguard **不信任的内核驱动（.sys）** |

---

**A. 封号问题：✅ 安全（一手 + 社区共识）**

- **Vanguard 监控的是**：内核驱动加载、游戏进程内存完整性、运行时注入/钩子。**它不监控 Windows 用户态音频子系统**。
- **本链路不注入游戏进程**：游戏只看到"多了一个普通麦克风"，看不到变声器。**没有任何"竞技优势"** → 不在封号理由里。
- **Riot 无禁止变声器的规则**；公开渠道**未检索到任何"仅因用变声器被封"的记录**。变声器在这套判据里等价于"外接声卡"，不是作弊工具。

**B. 启动问题：⚠️ 真正的风险点（VAN148 "Incompatible Software"）**

Riot 官方支持页（`support.riotgames.com/.../error-van-incompatible-software`）的一手口径：

> "VAN: INCOMPATIBLE SOFTWARE" = **Vanguard 检测到一个它不兼容的驱动文件**（.sys）。错误弹窗会**直接列出那个文件路径**。处理方式 = 卸载对应软件 / 手动删掉那个 `.sys` / 重启。**这是"拒绝启动"，不是封号。**

**官方与社区公布的常见被点名文件**（`thespike.gg` 汇总 + 官方示例）：

| 文件 | 来源软件 | 类别 |
|---|---|---|
| `ene.sys` | RGB 灯控（ASUS/MSI/Gigabyte/ASRock） | 灯控 |
| `rtcore64.sys` | MSI Afterburner / RivaTuner | 超频/监控 |
| `EPMVolFlt.sys` | 老式磁盘/系统工具 | 低层硬件 |
| `inpoutx64.sys` | 低层硬件访问工具 | 低层硬件 |
| `AsIO.sys` | 华硕主板工具 | 主板工具 |

**⚠️ 关键观察：以上**全部是 RGB / 超频 / 监控 / 主板工具，**没有一个是音频驱动**。Riot 的官方"常见元凶"清单里**不含任何虚拟声卡**。

**C. ⚠️ 但有一条针对 VB-CABLE 的二手指控，必须如实记下**

厂商博客（`voxbooster`，**有立场、非中立**）承认：

> "VB-Audio Virtual Cable **has a kernel driver component**. On certain Windows versions, **Vanguard 1.x flagged this driver, preventing Valorant from launching** until the driver was uninstalled. **Fixed in later Vanguard updates.**"

**置信度定级**：
- ✅ **一手确认**：VAN 不兼容软件的机制 = 内核驱动 .sys → **阻止启动**（非封号）；官方常见元凶无音频驱动。
- ⚠️ **二手（利益相关方）**：VB-CABLE 的 .sys 曾被 Vanguard 1.x 标记，**后续版本已修复**。
- ❓ **仍未一手证实**：当前（2026-09）Vanguard 是否把 VB-CABLE 的驱动列入不信任名单。**没有找到 Riot 官方点名 VB-CABLE 的文件，也没有社区"VB-CABLE 现在装不上 Valorant"的批量报告。**

---

**★ 对本项目的真正含义（最重要）**

**"用户态变声器安全"这个结论，套不到本项目头上。** 本项目现役链路的末端就是 **VB-CABLE**：

- `m2_server/wechat_voice.py`：默认麦切 **CABLE Output**、wav 播进 **CABLE Input**；
- MeanVC2 官方 README 也把 VB-CABLE 路由写进了文档；
- 要在 PC 游戏里把变声结果"喂"给游戏，**PC 侧就必须有一个虚拟麦克风** —— 而无内核驱动的用户态虚拟麦克风在 Windows 上**不存在**（那正是手机端非 root 场景卡住的同一个根因）。

**所以：**
1. **反作弊的暴露点是 VB-CABLE 本身（内核驱动），不是 MeanVC2，也不是 RVC。** 换 VC 模型不改变这一点。
2. **风险等级 = "装不上游戏"（VAN148，可逆），不是"封号"（不可逆）。** 最坏情况 = 游戏开不了 → 卸载 CABLE → 游戏恢复。**没有账号风险。**
3. **VB-CABLE 是合法签名的商业驱动**，且本项目**不注入游戏进程** → 架构上落在封号判据的安全侧。
4. **可替代性**：若真被 VAN148 拦，可换 **Voicemeeter**（同厂，但同样内核驱动）或**低频的物理环路**（外接 USB 声卡），或**仅在不开反作弊游戏时启用 CABLE**（发送前开关声卡本来就是现役流程的一环）。
5. **行动**：**不作为阻塞项**。上 PC 游戏场景前，在一台装了 Valorant 的机器上**实测一次"装 CABLE 后能否启动"**即可——10 分钟能验完的事，不必现在决策。

> **仍待实测**：Vanguard 当前版本 + VB-CABLE 当前版本的共存性（`docs/犯错指南.md` 已记录该待验项）。

## 3. 实时 TTS：候选池与现役对照

### 3.1 dots.tts（小红书 dots 团队 + 上交 X-LANCE）

**这是本次调研最被低估的模型。** 2B 全连续自回归（无离散 token），AudioVAE 48kHz，Qwen2.5 骨干，Apache-2.0，七个 checkpoint。

**官方实测（单 H800，bf16，N=99）—— 注意这里有个大坑：**

| 版本 / 场景 | 首块延迟 p50 / p90 | RTF p50 | 峰值显存 |
|---|---|---|---|
| SOAR / **text_only** | **69 / 79 ms** | 0.18 | 7.85 GB |
| SOAR / **voice_cloning** | **225 / 404 ms** | 0.20 | **7.86 GB** |
| MF(4步) / **text_only** | **68 / 78 ms** | 0.13 | 5.73 GB |
| MF(4步) / **voice_cloning** | **204 / 381 ms** | 0.15 | **5.74 GB** |

> **🚨 最重要的单条发现**：论文/新闻里流传的「首包 85ms / 54ms」是 **text_only（无参考音）** 场景。**音色克隆场景要 204–225ms(p50)、381–404ms(p90)** —— 因为得先跑 speaker encoder 处理参考音。差 3 倍。
> 而我们项目的**每一个** TTS 调用都带参考音。看榜单时如果只看 85ms，会得出完全错误的结论。

- 显存随长度增长：<10s → 5.65GB；<20s → 6.53GB；<40s → **7.86GB**；<82s → 10.51GB
- 官方支持真流式：`DotsTtsRuntime.generate_stream()` 逐块 yield；双流 `DotsTtsRuntimeDoubleStreaming`（逐文本 token 喂）
- 权重体积（HF `dots-studio/dots.tts-mf`）：model 4.40GB + vocoder 0.72GB + speaker_encoder 0.03GB = **≈5.15GB**
- **第三方 GGUF 量化存在**（`cstr/dots-tts-soar-GGUF`）：Q4_K **2.32GB** / Q8_0 3.13GB / F16 4.64GB。**注意：官方只发 bf16，GGUF 是社区转的，且流式路径能否走通未验证。**
- 输出 **48kHz**，与项目 24000Hz 协议冲突 → 需加重采样或改协议

### 3.2 VoxCPM2（面壁智能 OpenBMB）

- 2B，tokenizer-free 扩散自回归，MiniCPM-4 骨干，AudioVAE V2，**48kHz 输出 / 16kHz 参考输入**
- **30 语言 + 9 种中文方言**（四川/粤语/吴语/东北/河南/陕西/山东/天津/闽南）
- **Voice Design**：纯文字描述造音色（"一个年轻女性，温柔，语速稍慢"），无需参考音
- 三级克隆：基础克隆 / 可控克隆（带风格指令）/ 终极克隆（参考音 + 转录文本，音频续写）
- 流式：`generate_streaming()`；RTF **0.30 @RTX 4090**（标准 PyTorch）/ 0.13（nano-vLLM）
- 显存 **~8GB**；bitsandbytes 量化可再降 40–50%
- 训练 236 万小时；Seed-TTS-eval：EN WER 1.84% / ZH CER 0.97%，SIM EN 75.3 / ZH 79.5
- Apache-2.0，GitHub **31.4k stars**，支持 LoRA 微调
- ⚠️ 官方 README 自承：**Voice Design 和可控克隆每次结果有差异**，建议生成 1–3 次挑最佳

### 3.3 对照：现役 faster-qwen3-tts

本机 RTX 5060 8GB 实测：显存 **4.41GB**、整句 RTF 0.61、TTFA **cs=8 → 0.48s**。

## 5. 六个反直觉的发现

1. **「宣称支持流式」≠「能用」**。Seed-VC 宣称实时（README 写得很清楚），实测算法延迟 343ms，是方法下界。判定标准必须是**有实测首包 ms 数**，而不是"支持流式"这四个字。

2. **榜单数字的测试卡决定一切**。dots.tts 测在 H800、VoxCPM2 测在 4090、AuK 测在 A800-80G、MOSS-TTS-Realtime 测在 **L20**。本机是 8GB 笔记本卡。**所有首包数字在下结论前必须折算。**

3. **★ 「同一场景内」还不够，要问到哪个 checkpoint**。v1 把 MOSS-TTS-Realtime 的 TTFB 180ms 安到了 MOSS-TTS-Local v1.5 头上——**同一篇 README、同一个家族，但是两个不同的架构和两个不同的大小（4B vs 未标）**。以后记 TTS 指标一律写成「模型@尺寸 / 场景 / 卡」三元组。

4. **小红书一家出了两个方向相反的模型**：
   - `dots.tts` —— 全连续自回归，**为交互/流式而生**，48kHz，Apache-2.0
   - `FireRedTTS3` —— LLM-DiT，统一"生成+编辑"，5.18B / 20.78GB，和 AuK 同类
   **同一个团队（FireRed vs dots，都属小红书）做出了路线相反的两个东西**，说明"统一编辑"和"低延迟流式"目前确实是两条互斥的路线——这正好解释了 AuK 为什么进不了实时链路。

5. **48kHz 正在成为新一波模型的默认输出**（dots.tts / VoxCPM2 / FireRedTTS3 / **MOSS-TTS-Local v1.5** 全是）。项目 cascade 帧协议锁死在 24000Hz，这意味着**任何一次 TTS 后端更换都要动协议或加重采样**——这是集成成本里最容易被低估的一项。同理，**MeanVC2 的 16kHz 输出**是反方向的协议不匹配（对虚拟声卡无碍，但有带宽上限）。

6. **许可不是二元的**。「Apache-2.0 ↔ 非商用」这个二分法会误判——IndexTTS2 是 **bilibili Model Use License**：**既不是 Apache，也不是 NC**，而是"免费授权 + 极高阈值（1 亿 MAU / ¥10 亿营收）才需另议"。判断许可要读**原文条款**，不能靠"是/否开源"或"能不能商用"两个标签。

#### CosyVoice 3 首包：为什么写"160–700ms"而不是"~150ms"

v1 写的"宣称 ~150ms"过于干净。实际公开数据是**三个数量级不同的口径**：

| 口径 | 数字 | 场景 |
|---|---|---|
| 厂商渠道文章 | 首包从 **400ms → 160ms** | 双向流式合成架构（厂商自述） |
| vLLM-Omni 优化记录 | 流式 TTFP **~810ms → ~195ms** | **中文声音克隆，warm**（深度优化后） |
| 第三方基准（datascale-ai） | 均值 **~700ms**；短句 575ms / 中句 485ms | 通用部署 |

**读法**：195ms 是**经过 vLLM-Omni 深度优化**的数字，通用场景约 700ms。**CosyVoice 3 的延迟高度依赖部署优化程度**，不能引用单一数字。这也解释了一个反直觉现象：**同一个模型，换个推理框架，首包能差 4 倍**——所以"本机实测"这条纪律在 TTS 上尤其不能省。

#### MOSS-TTS 三档为什么被拆开

| 档 | 架构 | 关键数字 | 能否作为本项目候选 |
|---|---|---|---|
| **Realtime** | 独立架构，为低延迟设计 | TTFB **180ms**（warm）、RTF 0.51，**测于 L20** | 数字好看但**未标 LLM 规模/显存**，且 L20 非消费卡 |
| **Local-Transformer-v1.5** | `MossTTSLocal`，骨干 **Qwen3-4B** | **voice_clone TTFP 2075ms**（并发1，英文）、RTF 0.474 | ❌ **4B + 48kHz + 2 秒级首包**，三条都不达标 |
| **Nano** | 0.1B | 4 CPU 核实时流式 | ⚠️ 纯文本可用，克隆能力未查 |

> ⚠️ **额外发现（vLLM-Omni PR #4664 实测记录）**：Local v1.5 在**并发不同文本**时 6/6 次产出错误音频（请求间状态串扰，被并行调度时的 row 分配 bug），官方 reviewer 明确要求"修好之前不要依赖并发服务"。本项目是单人单路，暂不影响；但**说明这个模型当前工程成熟度偏低**。

## 7. 建议（按性价比排序）

### P0 · 保持不动
- **实时变声继续用 RVC**。§2 的数据是结构性的，不是调参能追的。
- **TTS 继续用 faster-qwen3-tts**。在本机实测出更优项之前，没有理由换——现役是唯一有本机实测数字的（4.41GB / 0.48s），且是唯一 24kHz 的。

### P1 · MeanVC2 实验 —— ✅ **已完成（2026-09-14）→ ❌ 否决**

原计划要验证的三件事，**全部有答案**：

1. **相似度能否接近已训练的 RVC** → ❌ **不能**。LTAS 0.914–0.936 vs RVC 0.958。
2. **16 kHz 输出在游戏语音里能不能接受** → ❌ **结构性受限**（8kHz 以上为零），不如 RVC 的 48kHz 全带。
3. **单 CPU 核 RTF<0.633 是否属实** → ⚠️ **分档**：120ms 档 0.348 属实；40ms 档 0.932 不属实。

**产出**：`D:\meanvc2_exp`（不入库，throwaway 实验沙箱）——含可复现 venv、`run_infer.py`（funasr 桩）、`ab_rvc_baseline.py`、`ab_metrics2.py`（SECS+LTAS+F0 三轴）、`rt_bench.py` / `rt_bench_gpu.py`（时延/RTF + GPU 可行性）、`rvc_footprint.py` / `rvc_cpu_cost*.py` / `mem_probe*.py`（三轴资源账）。

**最终结论（v3 修订）**：**判死，不接入。** 三轴全无优势——音色/音高/带宽三项全输，省下的 377MB 显存换不回音质；RAM 两者相当（"省内存"不成立）。**不接线、不再跟进。** 详见 §2.2-C 判定表。

**保留价值**：若将来出现"只要不训练、音质可让步"的极端场景，沙箱可随时复活（17 分钟从 clone 到出声）。**这属于"留档"，不属于"路线"。**


### P2 · 有条件复测（不再有"最贴候选"）
- **MOSS-TTS 已作废**（v2）：其 Local 档是 **4B / 48kHz / TTFP 2075ms**，三条硬约束全不达标；180ms 属另一档且测于 L20。**除非官方给出 Local 档的中文克隆首包实测，否则不再作为候选。**
- 若要继续测 TTS，**首选 CosyVoice 3（0.5B）**——它是候选池里**唯一规模显著小于现役（1.7B）且输出 24kHz** 的模型，是"规模换延迟"这条路上唯一可能赢的赌注。但必须先固定推理框架，否则 160ms 与 700ms 的差距（§6.1）会让实测没有可比性。
- **先决条件**：任何 TTS 实测都必须带参考音测（参照 dots.tts 的教训），且必须记录本机首包与显存。

### P3 · dots.tts 本机实测（需先解决 48kHz）
- 先下 MF 权重（≈5.15GB），跑 `generate_stream` 的 **voice_cloning** 场景（不是 text_only！），量本机首包
- **前置条件**：48kHz → 24kHz 的重采样方案必须先定，否则改不了协议
- 若本机首包 ≥ 现役 0.48s，直接放弃，不纠缠

### P4 · IndexTTS2 作为离线能力补充（与主链路无关）
- 只为了 **精确时长控制**（有声书场景卡画面时长）
- 4GB 显存起步，可与主链路分时复用，不动实时链路
- ✅ **许可已核实为可用**（§6.2）：免版税授权，**仅"月活>1 亿 或 年营收>¥10 亿"才需另议**；但需带版权声明 + 免责声明，且**不得用于改进其他 AI 模型**（§3.4(c)）

### 不做
- ❌ FireRedTTS3 / AuK / Higgs v2 / Zonos2 / GLM-4-Voice —— 显存出局
- ❌ **MOSS-TTS-Local-Transformer-v1.5** —— 4B + 48kHz + 2 秒级首包（v2 新增）
- ❌ 所有云 API —— 违反"不上云"红线
- ❌ Seed-VC 做实时 —— 343ms，结构性不达标
- ❌ 任何 **CC-BY-NC / CPML** 权重（F5-TTS / MaskGCT / Llasa / OpenAudio / XTTS / Spark-TTS / Fish S2）—— 项目已开源，不能埋许可雷
