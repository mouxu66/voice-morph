# 手机遥控页（`web/public/remote.html`）

> 2026-09-28 新增。触发：用户问「不做移动端、不上架商店，手机这一侧还能怎么打磨」。
> 结论：**不做 App，做手机浏览器能打开的响应式遥控页** —— 零安装、零构建、不需要任何商店审核，
> 而复用的是现成的 Web 前端产物与后端局域网托管。
>
> 2026-09-29 增补：第三页「**手机当麦**」（手机录音 → PC 换声 → 发微信）。
> 触发：用户问「把按住说话搬到手机遥控页上，让手机当麦克风」。

---

## 一、怎么用

手机与电脑在同一个 Wi-Fi 下，浏览器打开：

```
http://<电脑局域网IP>:8000/remote.html?api_key=<VM_API_TOKEN>
```

- **没设 `VM_API_TOKEN`** 时可以省掉 `?api_key=`（后端默认 LAN-only 放行，见 `m2_server/server.py`）。
- URL 里带了 `api_key` 会存进 `localStorage`，所以**加书签之后不用每次带参数**。
- 页面是三个标签页，对应三件在手机上真正会做的事：

| 标签 | 能做什么 | 调的接口 |
|---|---|---|
| **打字发语音** | 选音色 → 打字 → 试听 / 一键发成微信语音；顶部卡片显示「微信开没开、这次会不会重启微信」 | `GET /api/voices`、`POST /api/wechat/preview_text`、`POST /api/wechat/send_text`、`GET /api/wechat/precheck` |
| **手机当麦** | 按住说话（或点一下调系统录音机）→ 传到 PC 换声 → 试听 → 发进微信 | `POST /api/capture/mic/upload`、`POST /api/wechat/send_voice`、`GET /api/wechat/precheck` |
| **实时变声遥控** | 看状态（就绪/音色/监听/输入输出设备/显存/档位）、启停变声、切音色、开关自我监听、强制还原声卡 | `GET /api/rvc/live/status`、`POST /api/rvc/live/{start,stop,reset,monitor}` |

> **「手机当麦」为什么不是实时音频回传**（那个我依然不建议做）：连续回传要走实时流，
> 延迟与抖动都不可控（行业里也没人做成的）。这里做的是**另一件事** ——
> 录一小段、松手才上传，语义与桌宠的「按住说话」完全一致，只是麦克风换成了手机。
> 一段 3 秒的音频延迟几百毫秒根本没人在意，所以它不需要流式链路，只需要一个上传端点。

### 改完怎么生效

| 场景 | 命令 |
|---|---|
| 源码模式（`npm run electron`） | 改完刷新即生效（页面在 `web/public/`，Vite 原样提供） |
| 已安装的桌面端 | `cd web && npm run ship`（构建 → 同步进安装目录 → 逐字节自检），然后完全退出应用再打开 |

没有独立的部署单元要记：这个页面就是前端产物的一部分，**走的是前端既有那条路**。

## 二、四个设计决策（都有代价，都不是随手选的）

### 1. 为什么是独立 HTML，而不是主应用里的一条 React 路由

手机上的诉求与桌面端**方向相反**：单手、竖屏、三个动作、不看参数。
塞进主应用只会继承那套侧栏与 800~900 行的页面密度 ——
而「感觉功能太冗余」正是 2026-09-25 那份用户调研的原始触发点。

顺带解决两件事：不需要动 React 路由表与插件清单的 `routes`（这不是一个"能力页"，
它只是**同一批接口的另一种排布**），也不需要为它做一次前端构建才能改一行文案。

### 2. 为什么所有请求都是同源相对路径（不写 `:8000`）

`web/src/backendSurfaceAudit.test.ts` 会清点「直接打后端端口的 UI 面」并要求逐个登记。
同源相对路径**既不需要登记，也不会因为换 IP / 换端口而失效** ——
手机浏览器本来就是从后端那个源打开的，没有理由把地址写死。
这条约束有测试兜着（见 §三）。

### 3. 为什么 token 走 `api_key` 查询参数

因为 `<audio src>`（试听回放）**带不了自定义 Header**。
这和 `mobile/` 当初的选择是同一条理由（`server.py` 的中间件注释里也写着这句）。
页面所有请求都过 `withKey()`，一处挂参数、全局生效。

### 4. 为什么页面要读能力清单

后端的能力可以**被用户关掉，关掉后连路由都不挂**（见 `docs/插件化设计.md`）。
关掉之后页面会拿到 404，而「404」对用户是零信息量的。所以：

```
启动时 GET /api/plugins → 记下每个插件的 state
  · hook.wechat 关掉    → 禁用「试听/发到微信」，并直接说去「设置 → 能力管理」开回来
  · sound.rvc-live 关掉 → 禁用「开始变声」，并给出同一指引
  · pet.companion 关掉  → 禁用整页「手机当麦」（上传端点归它管）
  · 状态轮询拿到 404    → 连接灯显示「部分能力未开启」而不是「断开」
```

最后一条尤其重要：**能力被关掉时状态端点恒 404**，若把它当成"连不上电脑"，
用户会去查 Wi-Fi 和后端进程 —— 方向完全错了。

> 这也让本页成为**第三个前端面**（主应用 / 桌宠 / 遥控页）里认清单的一员，
> 与 `petCapabilityGate.test.ts` 钉住的那条约定一致。

### 5. 「手机当麦」：为什么两条录音路径都得留

浏览器有一个硬限制：**`navigator.mediaDevices.getUserMedia` 只在安全上下文里存在** ——
https，或 `http://localhost`。手机用 `http://<电脑IP>:8000` 打开时它**压根不存在**
（不是“权限被拒”，是这个 API 没被暴露），所以本页不能只写一种：

| 打开方式 | 拿到什么 | 页面表现 |
|---|---|---|
| https / localhost | 安全上下文 | 真正的「按住说话」，页面里直接录 |
| 普通 http（手机默认走这条） | 没有 `mediaDevices` | 自动退成「点一下录音」→ `<input capture>` 调手机自带录音机 |

后一条是关键：`<input type="file" capture>` 是**表单控件**，不受安全上下文限制，
每台手机都能用。代价是多跳一次系统界面、不是真的“按住”，
好处是零配置 —— 而把处理放在 PC 上恰好就是当初选定的路线。
页面里这个回退**会写明原因**（`!canHold` 时直接告诉用户“普通 HTTP 下浏览器不给网页用麦克风”），
否则用户只会觉得“这按钮坏了”。

两条路径的产物是同一种东西（一段音频 → 同一个上传端点），所以后端只有一个端点，
不按「手机是怎么录的」分叉。

> 想在任何手机上都能按住说话，唯一的路是给局域网加 HTTPS（自签证书也行）。
> 本仓没做：它需要引入一个证书库依赖（`cryptography` 目前**不在** `requirements.txt` 里），
> 属于“加了一个依赖给一个次要体验”的取舍 —— 先记在这里，不动手。

## 三、机器可执行的契约（`web/src/remotePage.test.ts`）

这是一个自包含 HTML：写错一个接口路径**不会让 tsc 红、不会让打包失败**，
只会让用户在手机上点一下 404 且完全看不出原因。所以把四条会静默腐烂的契约钉住：

| 契约 | 为什么它值得一条测试 |
|---|---|
| 页面确实在 `public/` 下 | 放错目录（比如放 `src/`）Vite 不会拷进 `dist` → 「本机能看到、手机 404」 |
| 页面出现的每个 `/api/...` **真有对应路由** | 后端改名/删端点时直接红，而不是等用户在手机上撞见 |
| 一切请求同源（不写端口字面量） | 换 IP/端口就失效，且会在另一个测试里多出一条要维护的登记 |
| token 走 `api_key`、且认能力清单 | 前者是 LAN 鉴权的唯一可行方式；后者是「关掉的能力不该被裸渲染」的既有约定 |
| **上传的 FormData 字段名 ↔ 后端 `Form(...)` 参数名** | 2026-09-29 加：字段名拼错不会 500，只会静默用默认值（音色没传进去 = “怎么没换声”） |
| **发微信那一步的 `wav` 字段 ↔ `SendVoiceReq`** | 同上，跨了两个文件；从**后端源码**里读字段名来比，不手写第二份 |
| **时长上限 = `mic_capture.MAX_HOLD_SECONDS`** | 页面那个 `59` 是个真会漂的魔数（微信单条 60s - 1s 余量） |
| **上传不手写 `Content-Type`** | 手写会把 multipart 的 boundary 写坏 → 后端解不出表单（表现为 422“缺 file”） |
| **两种录音路径都在，且回退不静默** | 少了 https 那条 = http 下整页是死的；少了 capture 那条 = http 下无路可走 |

路由清单是**从 `m2_server/*.py` 扫出来的**（`APIRouter` 的 prefix + `@router.get/post(...)`），
不维护第二份手写清单。页面里允许「只写前缀」的路径（例如媒体 URL 拼 `.session/` 子路径）
必须登记在测试的 `DYNAMIC_PREFIXES` 里**并写明理由**，而且该前缀在后端要能兑现、
页面要还在用它（防死条目）—— 与 `backendSurfaceAudit.test.ts` 的 REGISTRY 同一套思路。

## 四、2026-09-29 实测踩到的两个坑（都不是写错代码，而是「本机测不出来」）

### 1. 页面能打开，但一按按钮就 403（局域网 Origin）

后端默认的跨站守卫只放行 `null` / `file://` / `localhost`。而**浏览器对同源 POST 也会带
`Origin` 头**（Fetch 规范：非 GET/HEAD 一律带），手机打开遥控页时那个 Origin 就是电脑的
局域网 IP → 被 403。症状极具误导性：页面能打开（GET 不带 Origin）、连接灯也是绿的，
**只有写操作全灭**。

对策：`LOCAL_ORIGIN_RE` 放行私有网段（10/8、192.168/16、172.16/12、`*.local`）。
它必须改在那个**共用正则**上，而不是只改守卫无关的小地方 —— 预检（JSON POST 会触发）
由 CORS 层直接短路返回，根本走不到守卫。

安全性没有降低：Origin 来自浏览器实际加载的页面地址，公网攻击者无法让自己的页面拿一个
`192.168.x.x` 的来源（DNS 重绑定时 Origin 仍是他的域名，照样被拦）。
回归测试：`m2_server/tests/test_cors_file_origin.py` 新增 10 例，含 `192.168.1.5.evil.com`
这种“看着像内网”的伪造来源必须仍然 403。

### 2. 试听播放器永远不显示（`audio:empty`）

CSS 里曾写着 `audio:empty { display: none }`，本意是“没音频时不留空壳”。但 `:empty` 看的是
**子节点**，而 `<audio src=…>` 并没有子节点 —— 于是设了 `src` 也不显示：点「试听」
毫无反应、控制台一声不吭、接口全正常。只有眼睛能发现。
（「打字发语音」那一页从写下那天起也中招，同次渲染实测一并修掉。）

空播放器由 JS 加 `.hidden` 收起，不再用 `:empty` —— **一切“隐现”只留一个开关**。

## 五、边界与已知不足（别把它当成万能）

- **不含训练**。手机上不能建音色、不能做素材切片 —— 那些留在桌面端的「训练变声 / 素材工坊」。
- **发送是阻塞式的一次请求**（合成 + 录进微信约 1~2 分钟）。期间页面只能给「已等 N 秒」，
  没有真实进度条：后端 `/api/wechat/send_text` 返回的是最终结果，中间步骤在响应里一次性给出。
  若以后要真进度，需要后端另开一个状态端点。
- **依赖 PC 上微信开着**，并且**可能会重启微信**（页面用 `GET /api/wechat/precheck` 提前告知）。
- **不做鉴权增强**：LAN 内谁拿到 `api_key` 谁就能用。这与后端既有的 LAN-only 模型一致，
  没有引入新的信任假设。
- **未做 mDNS/二维码**（发现性问题）—— 目前要在电脑上看一眼本机 IP 再手输一次，
  之后靠书签。二维码需要一个前端依赖（仓库里没有），所以刻意没做。
- **「按住说话」在普通 http 下拿不到**（浏览器安全上下文限制，见 §二.5）：会退成
  “点一下调系统录音机”，体验差一档但功能不缺。要真按住说话就得给局域网加 HTTPS。
- **手机录音不挑麦**：手机那段音频完全由手机决定用哪个麦克风（拿不到设备清单），
  而 PC 端那条链路会刻意避开虚拟声卡（`mic_capture.pick_mic_device`）—— 手机没有这个问题，
  因为它根本不经过 PC 的声卡。
