# 桌宠建议面板（2026-10-23 二次重构）

> 目标：把「功能菜单」换成「此刻能做什么」。
> 代码：`web/electron/pet/pet.html`（单文件）· 测试：`web/src/petActionPanel.test.ts`

## 1. 问题

上一版已经把面板从 13 个常驻入口压到 5 个（药丸 / 音色 / ♪ / ⋯ / 主按钮），
但用户的原话仍然是：

> 「功能太多显得很乱」「屏幕太小」「希望能根据上下文自动给我推荐哪些功能」
> 「有些功能我想用的话我也能找到」

真正的病根不是**数量**，是**入口和此刻该做什么无关**。打开面板的那一刻，上下文
通常已经把候选压到 2–3 个：

- 对方刚发消息（雷达判「该回了」）
- 有一条提案等你点头（`hook.assistant` 的 pending）
- 正在放歌（最可能想做的是停）
- 草稿里有字（那一件事就是把它发出去）

其余 9 个动作在这一刻是噪音。所以这一版按**信号排序**，而不是按功能分类铺开。

## 2. 形态

```
┌──────────────────────┐  204 × ≤300 px
│ [待机]     袋鼠骑士  ⋯ │  phead：变声开关（状态）+ 音色（状态）+ 唯一功能入口
│ [ 说点什么，或找功能 ] │  ask：一个框双用 —— 要发的内容 / 找功能的搜索词
│ ▸ 该不该回    对方在等 │  recs：最多 3 条，随上下文变（.warn 琥珀）
│ ▸ 点歌         搜 B 站 │                     （.hot 绿 = 有提案等你确认）
│ ▸ 音效           声板 │
│ [   按住说话   ]       │  fire：主按钮（文案仍是全面板唯一真相）
│ 微信已打开 · 按住说…   │  status / gesture
└──────────────────────┘
```

三种状态，同一个 DOM：

| 输入框 | recs 显示什么 | 数据来源 |
|---|---|---|
| 空 | `rankActions()` 前 3 条 | 雷达结论 + 提案 + 放歌态 + 使用频率 |
| 有字 | 搜索结果：后端解析的提案在前，本地动作在后 | `POST /api/assistant/observe`（dry_run）+ `matchActions()` |
| 一条都没有 | 整块 `hidden`，不占高度 | — |

## 3. 信号与打分（`rankActions`）

| 分 | 触发条件 | 条目 | 色 |
|---|---|---|---|
| 100 | 有 pending 提案 | 确认 发《晴天》 | 绿 `.hot` |
| 92 | 雷达 `action=now` | 该不该回（对方在等） | 琥珀 `.warn` |
| 88 | 正在放歌 | 停止放歌 | — |
| 62 | 雷达 `action=soon` | 该不该回（可以回了） | — |
| 30 / 26 / 22 | 兜底，永远在池子里 | 点歌 / 音效 / 该不该回 | — |
| 18 | 变声没开 | 开变声 | — |
| +0~15 | 使用频率（每次 +3，封顶 15） | 任意 | — |

三条规则：

1. **兜底池永远在，信号只负责排序**。空面板会让人以为坏了。
2. **主按钮能做的事不进推荐**（发语音 / 试听）。推荐只放主按钮干不了的，
   否则同一件事在面板上出现两次，用户又要在两个入口之间判断。
   例外：输入框有字时「发原样」会作为**对比项**出现（见 §5）。
3. **输入框有字时 `rankActions` 直接返回 `[]`**，把位置让给搜索结果。

## 4. 入口去哪了

| 原入口 | 现在 |
|---|---|
| phead 的 ♪ 按钮 | 抽屉的「声音」行 → 托盘（音效 + 放歌 + 放大镜搜歌） |
| 音色 chip | 仍是 chip，但透明底无边框（它是**状态**不是功能），点击开抽屉 |
| ⋯ 抽屉 | 保留，是唯一的功能入口：音色 / 声音 / 引擎 / 千问直出 / 该不该回 / 最近发送 |
| 11 项「全部功能」网格 | **删除**。理由见下 |

网格删除的三条理由（实测支撑）：

1. 抽屉里已经铺开 11 个动作里的 9 个，网格第一行就是重复；
2. 剩下没入口的（点歌）走「声音 → 托盘 → 放大镜」，本来就通；
3. 真要「找某个功能」，输入框打字更快 —— `ACT_META` 的 `kw` 覆盖全部 11 个动作
   （中英文），一打就出候选。

实测网格展开 164px，抽屉从 300px 涨到 **476px**，只能看到 2 行 —— 比没有更糟。

## 5. 输入框为什么能双用

同一个字符串既是「要发的内容」也是「搜索词」，区别由**下面给出的候选**决定，
不需要模式开关：

```
发首晴天                    ← 你打的
├ 发《晴天》        点歌      ← 后端解析结果（点了会搜歌、截 53 秒、发语音条）
└ [ 发原话 ]                ← 主按钮（把这几个字念出来发出去）
```

主按钮的文案因此会变：解析出提案时写「**发原话**」，否则写「合成并发送」。
不改的话两条路径看起来像同一件事 —— 这是本次唯一因为建议区而改的既有文案。

`matchActions` 之外的兜底：打了字但一条动作都没匹配上时，渲染层补一条
「发语音说这句 · 原样发」。这是**产品规则**（输入框里的话默认归宿就是发出去），
不写进 `matchActions` —— 那边保持「搜不到就是空」的诚实，测试钉着这一条。

## 6. 提案：面板成了 assistant 的正门

在此之前 `hook.assistant` 只能用 curl 驱动（提案落在磁盘上，桌宠不知道它存在）。
现在：

```
输入框打字 → /observe(dry_run) → 候选「发《晴天》」
   ↓ 点它（只创建，不执行）
POST /proposal → 推荐区顶部出现「确认 发《晴天》」(.hot)
   ↓ 再点一下
POST /proposals/{id}/confirm → 轮询到终态，步骤写进状态行
```

两步确认不是啰嗦，是后端的规矩：`/observe` 只产出提案，唯一执行入口是 `confirm`。
面板照着这条规矩做，API 和 UI 就不会有两套语义。

## 7. 实测

| 状态 | 面板高 | 备注 |
|---|---|---|
| 主面板 + 3 条推荐 | **227px** | 上限 300 |
| 输入框有字 + 1 条候选 | 167px | |
| 抽屉（收起） | **300px** | 刚好；为此把「最近发送」的 13px 分隔线换成 4px 外边距，抽屉底 padding 10→6 |
| 抽屉（旧版含网格） | 476px | 需要滚 176px，已废弃 |

`petActionPanel.test.ts` 21 条：
- 空态三条兜底 / 能力关掉不出现 / 搜索专用动作不进推荐池
- 提案盖过雷达 / now 与 soon 的理由与分数不同 / 放歌时第一条是停止
- 频率能顶进前三条 / 频率封顶 15（用 100 次也盖不过「该回了」）
- 搜「歌」「变声」「music」能命中 / 搜不到返回空 / 英文 kw 可用
- `ACT_META` 与 `ACT_RUN` 的 id 一一对应（漏一个就是死按钮）

**测试有效性已验证**：把兜底分从 26 改成 260 → 红 6 条；去掉频率封顶 → 红 1 条。

## 8. 踩的坑

1. **`#actGrid[hidden]` 没写 → 网格永远展开**。`display:grid` 会盖掉 UA 的
   `[hidden]{display:none}`。本文件第 N 次踩（`.field[hidden]`、`#fxPicks:empty`、
   `#songLayer[hidden]` 都是同一类）。
2. **`#panel button:not(.primary){flex:1}` 优先级高于 `#panel .rec`**（多了 `:not` 里的类），
   `.rec` 必须显式 `flex:0 0 auto`，否则在 column flex 里被拉成等高。
3. **`@electron/asar` 3.x 的 `createPackage` 是 async**：不 `await` 会在文件写完前
   就去 `listPackage`，报 ENOENT 且看起来像"路径不对"。
4. **`radarTick` 的慢轮询 5s 一次且不立即抓**：只靠它，用户悬停打开面板的头 5 秒
   永远看不到「该回了」。改成 `refreshPanel` 里 8s 节流主动抓一次。
5. **`refreshFire` 必须跟着 `/observe` 的返回重跑**：主按钮文案依赖 `obsState.hits`，
   不重算就一直是「合成并发送」，跟下面的候选自相矛盾。
6. **`.dl` 是 `flex:0 0 auto`**：行尾值（`#radarRowLabel` / `#trayRowLabel`）不写
   `margin-left:auto` 会紧贴标题，读起来像一句不通的话。

## 9. 待做

  文字还得靠 VLM（与「4B 视觉放 CPU 8.4s/图」那条结论直接相关）。
- **托盘本身还没改**：音效网格仍是 12 格平铺，`#tray` 内部还是"功能清单"式的。
  它现在从抽屉进，使用频率低了，优先级也低。
- **推荐的理由文案**：`hint` 只有 4–6 字（"对方在等"/"正在放"），
  够用但粗糙；真实理由（"等了 3 分 12 秒"）在 `lastRadar.verdict.reason` 里没被用上。
