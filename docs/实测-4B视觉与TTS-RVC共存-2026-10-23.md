# 实测：4B 视觉 + TTS + RVC 在单张 8GB 卡上的共存边界与 CPU 回退代价

> 日期：2026-10-23　机器：RTX 5060 Laptop 8GB（8151 MiB）/ Ryzen 7 8840HX 12C24T / 15.2 GB RAM
> 全部数据为本机实测，非估算。测试脚本在 `%TEMP%\vltest\`（`rvc_probe.py` / `tts_probe.py` / `vl_ask.py` / `vl_*_coex.sh`）。

## 0. 先纠正一个命名

本地实际模型是 **Qwen3-VL-4B-Instruct**（`D:\Qwen3VL-4B-Instruct-Q4_K_M.gguf` 2.33 GiB + `mmproj-Qwen3VL-4B-Instruct-Q8_0.gguf` 433 MiB），不是 Qwen3.5-4B。Q4 指 Q4_K_M，视觉投影包就是 mmproj。下文"4B"均指这个组合。

## 1. 结论速查

| 组合 | 峰值显存（总 8151） | 结论 |
|---|---|---|
| 4B + RVC | 6860（free 1040） | ✅ 宽裕，RVC 零掉速 |
| 4B + TTS | 7737（free 163） | ✅ 能跑，双方延迟无损，但没有余量 |
| 4B + TTS + RVC 三者 | 7707（free 193） | ❌ VL 首次请求 **54.7 秒**（正常 3.1s） |
| TTS+RVC 在 GPU、**4B 的 LLM 放 CPU** | 7780（free 120） | ✅ 8.4 秒/图，RVC 仍 16ms |

**最优形态不是"把语音放 CPU"，而是"把视觉的 LLM 放 CPU，mmproj 留在 GPU"。**

## 2. 单模型实测量

| 组件 | 配置 | 显存增量 | 延迟 |
|---|---|---|---|
| Qwen3-VL-4B | GPU 全量，ctx 8192 | 4134 MiB | 3.38 s / 3037 token |
| Qwen3-VL-4B | GPU 全量，ctx 4096 | ~3552 MiB | 3.05–3.14 s |
| Qwen3-VL-4B | `-ngl 0`，mmproj 留 GPU | **694 MiB** | 6.6–7.0 s |
| Qwen3-VL-4B | `-ngl 0 --no-mmproj-offload`（全 CPU） | **~30 MiB** | **38.5–40.0 s** |
| Qwen3-TTS 1.7B | GPU bf16（faster_qwen3_tts + CUDA graph） | 5017 MiB | RTF 0.66 |
| Qwen3-TTS 1.7B | CPU fp32（原版 qwen_tts） | 0 | **RTF 7.76–9.26** |
| RVC | GPU fp16（含 rmvpe + HuBERT + CUDA graph） | 449 加载 / **1372 峰值** | **16 ms** / 0.25s 块 |
| RVC | CPU fp32 | 0 | **200 ms** / 0.25s 块（RTF 0.80） |

RVC CPU 的块大小敏感度：0.25s→200ms（RTF 0.80）、1s→350ms（RTF 0.35）、3s→938ms（RTF 0.31）。块越小越吃亏，固定开销占大头。

## 3. 组合实测

### 3.1 4B(8192) + TTS　✅

```
[tts_resident] used=5693
[vl_up]        used=7737  free=163
VL 4 问：3.26 / 3.44 / 3.36 / 3.21 s   (中位 3.36)
TTS 3 次：RTF 1.03 / 0.66 / 0.66
结论：VL 共存 3.36s vs 独占 3.38s → 1.00x，双方都不掉速
```

### 3.2 4B(8192) + RVC　✅

```
基线 688 → RVC 常驻流式 2057 → VL 起来 6221 → 打点峰值 6860（free 1040）
VL 4 问：4.00 / 3.94 / 3.96 / 3.86 s   (中位 3.96，比独占慢 17%)
RVC 流式 p50：16–17 ms（独自跑是 18ms，不变）
```

VL 慢 17% 是因为 RVC 每 50ms 占 16ms 的 SM，属正常争抢；RVC 侧无感。

### 3.3 4B(4096) + TTS + RVC　❌

```
基线 712 → TTS 5693 → +RVC 7082 → +VL 7707（free 193）
VL 第 1 问：54.68 s   ← prompt processing 0.58 tokens/s
VL 第 2/3 问：3.14 / 3.05 s   ← 此刻 TTS 的 120s 驻留到期退出，显存回到 4922
```

**根因不是"总量超了"**：7707 只占 94%，而且 4B+TTS 在 free 163 时也只要 3.36s。
真正的差别是 **RVC 的 CUDA Graph**：它为固定的输入尺寸捕获了整张图，`torch reserved=1180 MiB` 里的地址被钉死在显存，WDDM 无法把它换页出去；于是 llama.cpp prefill 要一次性申请的大块 compute buffer 只能换掉自己的权重页 → 0.58 tok/s。TTS 虽然同样占 5 GB，但 PyTorch 的显存池可被驱动换出，所以不触发。
一句话：**CUDA Graph 锁死的显存，比普通显存"贵"得多。**

### 3.4 TTS + RVC 在 GPU、4B 的 LLM 在 CPU　✅（推荐）

```
基线 676 → TTS 5693 → +RVC 7086 → +VL(CPU,mmproj 在 GPU) 7719
VL 3 问：8.68 / 8.44 / 8.21 s   (中位 8.44)
RVC 流式 p50：15–16 ms（全程不变，即使 VL 在用 8 个 CPU 线程 prefill）
```

比全 GPU 的 3.4s 慢 2.5 倍，但换来 TTS 与 RVC 都能满速常驻，且 VL 的 prefill 走系统内存、不再和显存抢。

## 4. 回答"放 CPU 有多慢"

| | GPU | CPU | 倍数 | 可接受吗 |
|---|---|---|---|---|
| RVC（0.25s 块） | 16 ms | 200 ms | **12.5x** | 勉强。RTF 0.80 没有余量，块间抖动会累积成断续 |
| TTS（3.2s 语音） | 2.1 s（RTF 0.66） | **25–30 s**（RTF 7.8） | **11.8x** | 不可用。说一句话等半分钟 |

两者倍数接近（约 11–12x），但后果完全不同：RVC 是**实时链路**，200ms 一块等于给每个音频块加了 200ms 延迟且无抖动缓冲；TTS 是**请求-应答**，慢就是慢，不会破坏音质。

**反直觉的那一条**：4B 视觉模型放 CPU 只慢 1.9 倍（3.4s → 6.6s），因为它是一次性 prefill，3037 token 在 8840HX 上跑到 ~507 tok/s，比"自回归逐 token 生成"的 TTS 友好得多。所以三个模型里，**最该放 CPU 的恰恰是视觉模型**。

## 5. 落地建议（桌宠）

按"谁常驻、谁按需"分层：

| 层 | 放哪 | 显存 | 何时在 |
|---|---|---|---|
| RVC 实时变声 | GPU fp16 | 1372 | 只在游戏/语音时 |
| TTS 人偶说话 | GPU bf16 | 5017 | 常驻（或首句前懒加载 5–10s） |
| VL 分析画面 | **LLM 在 CPU，mmproj 在 GPU** | 694 | 点"怎么回"时拉起，空闲 60s 退出 |
| 像素雷达 | 无模型 | 0 | 常驻 |

两个组合都排得下：
- 平时：TTS(5017) + VL(694) + 基线(700) = 6411 ✅
- 变声时：RVC(1372) + TTS(5017) + 基线 = 7089 ✅（此时 VL 不拉）
- 若三者都要：7780，free 120，靠 WDDM 兜着，VL 稳定 8.4s —— 能跑但没余量

**省显存的更进一步**：现在喂给 VL 的是整窗截图（3037 token）。若只截聊天区 ROI（约 1/4 面积），token 降到 ~800，CPU 模式 prefill 约 2 秒，显存也可降到 2048 ctx —— 那时三者同卡的压力会小很多。这一点尚未实测。

## 6. 未测/已知缺口

- TTS 在 CPU 只能退回原版 `qwen_tts`（`faster_qwen3_tts` 的 torch 后端硬性要求 CUDA Graph，`from_pretrained(device="cpu")` 直接抛 `ValueError: CUDA graphs require CUDA device`）。所以 RTF 7.8 是"无图优化的 PyTorch CPU"上限，不是量化后的最优值。
- 没测 `backend="ggml"`（qwentts.cpp）的 CPU 路径，缺 GGUF 权重。
- RVC 的 CPU 测试用 fp32；`is_half` 在 CPU 上无意义。
- 三者同卡的 54.7s 只复现了一次，没有做"去掉 CUDA Graph 再试"的对照实验。若要确认根因，可用 `TORCH_CUDA_GRAPH_DISABLE` 或 RVC 侧关闭 `run_cuda_graph` 复测。
