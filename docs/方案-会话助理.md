# 会话助理（hook.assistant）：把"群里那句话"变成一张待你点头的提案

> 2026-10-23。代码：`m2_server/assistant/` + `m2_server/assistant_api.py` + 插件 `hook.assistant`。

## 1. 它解决什么

用户的原话（三个阶段，其实是同一条链路）：

1. **点歌** —「有人跟我说想让我发一首歌，识别到之后让我同意是否要发，它就能上网搜，之后再发」
2. **分析** —「我可以用千问这个模型来分析，分析完之后我再更好地回」
3. **发语音** —「用千问发语音、用 RVC 发语音、发方言这种有趣的东西，都希望 AI 帮我发」

共同结构是：**读懂一句人话 → 变成一件具体的事 → 等我点头 → 才动手**。

所以这里没有做三个功能，只做了一条流水线：

```
一段聊天文本
   ↓  extract.py（规则，几十微秒）
候选意图 [song.send / voice.say / reply.draft]
   ↓  api.observe  —— 只产出 Proposal，不执行
待确认队列（落盘，重启还在）
   ↓  用户点「确认」—— 唯一入口
executor.py
   ├─ song.send   : 搜歌 → yt-dlp 取流 → ffmpeg 截 53s → 发语音条
   ├─ voice.say   : TTS(+RVC) → 发语音条（复用 wechat_voice.send_text）
   └─ reply.draft : 只返回文本，**永不发送**
```

## 2. 三条硬规矩

**① observe 绝不执行。** 想让 AI"看到就发"，得先删掉 `assistant_api.py` 的一半。
置信度再高也只是排序靠前，不会跳过确认 —— 用户要的是"让我来同意"，不是"让我来得及撤销"。

**② 只有一个执行入口。** `/api/assistant/proposals/{id}/confirm`，且提案必须处于 `pending`。
重复点返回 409 而不是再发一条。状态机 + 线程表双保险（单看任一个都会漏）。

**③ 动作是白名单。** `schema.KINDS` 里没有的 kind 一律拒绝，与 `ai_actions.py` 同一口径。
新增能力必须在 `KINDS` 里声明 required 字段。

## 3. 能力边界（做不到的直说，不假装）

| 诉求 | 现状 | 说明 |
|---|---|---|
| 搜歌 | ✅ 只搜 B 站 | 下载白名单里没有 YouTube。搜 YouTube 会"确认了却下不了"，所以搜索源必须是下载白名单的子集（有测试钉住） |
| 发整首歌 | ⚠️ 截 53 秒 | 微信语音条 60 秒是硬上限（`wechat_voice.MAX_MSG_S`）。片段默认从 30% 处起（副歌常在这），可传 `start_s` 改 |
| 发方言 | ❌ | Qwen3-TTS 只有普通话/英文。执行时会**如实拒绝**并给两条替代路线，不会用普通话念一遍说这是粤语 |
| 换声发语音 | ✅ | 走 `rvc_convert.rvc_convert`（常驻 worker） |
| 分析后自动发 | ❌ | `reply.draft` 只回文本。替你按发送是越界 |
| 千问"上网搜" | ❌ | **模型本身不联网**。联网是 `yt-dlp` 干的活（它真的去 B 站搜），模型只负责理解那句话 |

## 4. 实测数据（2026-10-23 本机）

| 环节 | 耗时 | 备注 |
|---|---|---|
| 意图解析 | < 1 ms | 纯正则，不调模型 |
| 搜歌（B 站，3~5 条带标题） | 5~13 s | 非 flat 模式才拿得到标题；B 站连续搜索会 412，代码退避 3s 重试一次 |
| 下载一首 270s 的歌 | 12.6 s / 7.9 MB | `ytdlp_fetch.fetch` |
| 截段 + 转单声道 PCM | ~2 s | 269.5s → 53.0s，2.4 MB |
| 发送 | = 片段时长 + 3s | 微信录音链路 |

端到端（点歌 → 发出去）约 **1~2 分钟**，其中大头是发送时按实际时长录音。

## 5. API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/assistant/observe` | 喂聊天文本，返回候选提案。`dry_run=true` 只预览不落库 |
| POST | `/api/assistant/proposal` | 手动下一条指令（不经读屏） |
| GET | `/api/assistant/proposals` | 待办列表 |
| POST | `/api/assistant/proposals/{id}/confirm` | **执行**（唯一入口） |
| POST | `/api/assistant/proposals/{id}/cancel` | 取消（只对 pending 生效） |
| POST | `/api/assistant/search` | 手搜候选（"换一首"用），不下载 |
| GET | `/api/assistant/capabilities` | 能做什么、做不到什么 |

全部挂 `_require_loopback`（本机桌面能力，不给局域网调）。

### 解析示例

```
"小明：能给我发一首晴天吗"      → 发《晴天》
"用袋鼠的声音说今天真开心"       → 用袋鼠说一句
"用粤语说晚上好"                → 用粤语说一句（确认后会如实拒绝方言）
"你发的那首歌真好听"            → 不生成提案（评价不是请求）
```

## 6. 为什么先规则、不先上模型

点歌的句式收敛得很厉害（`发/来/放/唱/点` + `一(首|曲|个)` + 名字），规则跑完只要几十微秒，
而且每条命中都能**回指原文片段**（`Hit.matched`）—— 用户一眼能看出"AI 是看到哪句话才觉得要发歌的"。

反过来先上模型：一是不稳定（同一句两次解析出不同歌名），二是给不出"凭什么是这首"的凭据。

模型的位置留在 `looks_like_request` 之后：规则没命中、但句子像请求时，再交给模型深解析。
这一层**目前没实现**（见 §8）。

## 7. 踩过的坑（改代码前先看）

1. `(?:发来放唱点整甩求)` 在正则里匹配的是**连续字符串**，不是"任选一个字"。
   必须写字符类 `[发来放唱点整甩求]`。用错时所有点歌都抽不出来，且不报错。
2. f-string 里的 `{1,40}` 会被当 set 字面量求值 → 正则变成 `(1, 40)`。要写 `{{1,40}}`。
3. `to_dict()` 带 `label`/`sends` 派生字段，拿它落盘会让下次启动 `Proposal(**rec)` 抛
   TypeError → 整条被跳过 → 用户看到"待办全没了"。落盘必须用 `to_record()`。
4. `_gc()` 必须**原地删**。返回新 dict 而没赋回 `_CACHE`，内存里会留着已"清掉"的条目。
5. `faster_qwen3_tts` 的 `device="cpu"` 直接抛 `ValueError: CUDA graphs require CUDA device` ——
   想测 TTS 的 CPU 性能只能退回原版 `qwen_tts`（且参数名不同：`x_vector_only_mode`）。
6. 进度记录必须写**同一个 steps 列表**。早期版本 `_steps_append` 只写 store、局部另有一份，
   最后 `run()` 用局部列表覆盖 `prop.result` —— 中间步骤（搜索、取回音频）在 UI 上凭空消失。
   干跑时实测少了 2 步。现在 `_step(prop, steps, line)` 一次写两处。

## 8. 还没做

- **模型兜底解析**：`looks_like_request` 已经留好钩子，接本地 llama-server 输出结构化 JSON 即可。
- **读屏接入**：现在要调用方把文本喂给 `/observe`。接 `chat_radar`（像素）只能给几何量，
  拿文字还得靠 VLM 或 OCR —— 这一步和"4B 视觉模型放 CPU"的结论直接相关（8.4s/图）。
- **前端面板**：桌宠里还没有"AI 建议"卡片。目前只能 curl / 手动调。
- **发文件**：整首歌只能截段发语音条。要发完整文件得新做一条 UIA 拖拽上传链路。
- **多候选让用户挑**：现在 `pick_best` 直接选分数最高的一条。更好的做法是把前 3 条列在提案里让人选。
