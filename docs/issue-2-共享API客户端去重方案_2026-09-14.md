# issue #2 · 共享 API 客户端去重：实施方案

> 日期：2026-09-14 | 状态：**方案，未动任何代码**（issue 仍 OPEN）
> 摸底方式：只读调研（Explore agent 全仓扫），行号是当时的快照，动手前请复核。
> 前置条件：见 §5 —— **先让 `web/package.json` 那批在制改动落地并提交**。

## 1. 现状（事实）

两边是**完全独立的两套客户端**，连共享层都没有：根目录没有 `package.json`、没有
`pnpm-workspace.yaml`、没有 `shared/`；`web/package.json`（name=`voice-morph-desktop`）
与 `mobile/package.json`（name=`mobile`）互无 workspace 字段。

| | web | mobile |
|---|---|---|
| 客户端 | `web/src/api/client.ts`（**1609 行**，端点 + 类型全内联） | `mobile/src/api.ts`（334 行） |
| 类型 | `web/src/types.ts`（client.ts 反向 import） | 内联在 `api.ts` 里各写一份 |
| baseURL | `backendPrefix()`（`client.ts:32-38`）按页面协议自判 | 用户手填，存 `mobile/src/store.ts:21` |
| 鉴权 | **无任何鉴权头** | `X-API-Key` 头 + `api_key` 查询参数（`api.ts:134-178`） |
| 超时 | **无** | 10s `AbortController` |
| 调用方 | 32 个文件 `import from "@/api/client"` | 移动端页面 |

**已收敛的部分**（值得记一笔）：web 侧没有散落的 `*_api.ts`，`useWorkshop` /
`useEffects` / `useTts` 等全部走同一个 `client.ts`。所以这次去重的对象只有**两个文件**，
不是"满天飞"。

## 2. 重复面清点

### 2.1 端点（mobile 的 **19 个**全部与 web 重叠）

`mobile/src/api.ts` 里一共 19 个端点，**逐一核对过，全部都能在 `web/src/api/client.ts`
里找到**（即 mobile 是 web 的真子集）：

`/health`、`/voices`、`/rvc/voices`、`/pipeline/status`、`/offlinevc/run`、
`/offlinevc/status`、`/tts`、`/audio/apply`、`/audio/restore`、`/cascade/{start,status,stop}`、
`/rvc/live/{start,status,stop}`、`/rvc/train/status`、`/wechat/history`、`/wechat/send_voice`。

web **独有**（mobile 没有，且不该有）：market / pet-market / ft / ab / history /
storage / audiobook / mine / diagnose 等一大批。mobile 只有"遥控子集"。

> ⚠️ 核对时踩到一个**会误导人**的细节：`mobile/src/api.ts:76` 有一行注释写着
> `// 实时转写字幕（--asr-only 子进程）：running/stage/last_text/chunks`，
> 裸正则扫文本会把它当成端点 `/stage/last_text/chunks` 抓出来，于是得出
> "mobile 用了 web 没有的端点"这个**假结论**。将来写 §6.5 那条守卫测试时
> **必须先剥掉注释**（或者只认引号里的字符串字面量），否则守卫自己会误报。

### 2.2 类型（约 10 个重名）

`VoiceInfo`、`RvcVoice`、`RvcVoicesInfo`、`CascadeStatus`、`RvcLiveStatus`、
`TrainStatus`/`PipelineStatus`、`OfflineVcStatus`、`TtsResult`、`WechatHistoryItem`、
`WechatSendResult` —— 两边各写一份，且 **web 那份字段更多**（如 `source`、`perf_profile`）。

> 这是最危险的一类重复：后端加字段时，只有一边会跟上，另一边**静默漂移**且没有编译错误
> （两边是独立 tsconfig，不会互相检查）。

## 3. 两条路线

### 路线 A：抽 workspace 共享包

新增 `packages/api-contract/`（TS 源），`web` 与 `mobile` 都加 workspace 依赖；
web 走 Vite/tsconfig paths，mobile 走 Metro 的 `watchFolders` + `extraNodeModules`。

- 优点：单一事实源，类型/端点真共享，编译期就能发现漂移。
- 代价：**两边构建配置都要改**（根 `package.json`、`pnpm-workspace.yaml`、
  `web/tsconfig*.json`、`mobile/metro.config.js`），且 Metro 对 workspace 的处理
  在 Expo 里是出了名的容易踩坑（需 `watchFolders` + `resolver.nodeModulesPaths`）。
- 风险：中高。构建配置一坏，**两边都起不来**。

### 路线 B：轻量同步（单一事实源 + 机器校验）

把"契约"（端点路径常量 + 类型定义）落在一个**不参与构建**的目录，例如
`shared/api-contract/{endpoints.ts,types.ts}`，两边**照抄**（或由脚本生成），
再加一条 pytest 校验"两边与事实源一致"。

- 优点：**不动任何构建配置**，零启动风险；漂移照样会被机器拦住。
- 代价：不是真共享，仍需一次"同步"动作（但被测试兜住，不会忘）。
- 风险：低。

### 对比

| | A workspace | B 轻量同步 |
|---|---|---|
| 改构建配置 | 两边都要 | **不用** |
| 编译期发现漂移 | ✅ | ❌（靠 pytest） |
| 一次性工作量 | 大 | 小 |
| 坏了会不会两边都起不来 | **会** | 不会 |

## 4. 推荐：先 B，后视需要再 A

理由：这次的真实痛点是**类型静默漂移**，而不是"代码难看"。B 用最小代价把这个痛点
变成"测试会红"，且完全不动构建链路 —— 对一个**已公开发版**的项目，构建配置的
收益/风险比明显不如 A。

若将来 web/mobile 都要大规模扩接口，再上 A，那时 B 的契约文件正好是 A 的输入。

## 5. 前置条件与风险（动手前必须确认）

1. **`web/package.json` / `web/package-lock.json` 的在制改动必须先落地并提交。**
   路线 A 一定要碰它们；路线 B 虽然不用，但同一目录并行编辑会丢改动。
2. **本项目已踩过"并行编辑丢改动"**（`docs/犯错指南.md` §3.18，提交 `5bb72d1`）——
   动手前先 `git status` 确认没有在制的 web/mobile 改动，否则先停下。
3. **鉴权基线必须先拍板**：web 无鉴权、mobile 有 `X-API-Key`。
   建议**共享层只做"契约"**（类型 + 端点常量 + 路径拼接），
   **不共享传输层** —— 鉴权头、超时、错误处理各自保留，否则要么给 web 平白加鉴权，
   要么把 mobile 的安全要求降下来。
4. mobile 侧没有 CI（Expo 起不来），所以 B 的校验测试要放在 `m2_server/tests/`，
   用**文本解析**而不是 import。

## 6. 分步实施（路线 B）

1. **建契约文件** `shared/api-contract/endpoints.ts`：把 §2.1 那 14 个路径写成常量
   （如 `export const EP = { health: "/api/health", voices: "/api/voices", ... } as const`）。
2. **建契约类型** `shared/api-contract/types.ts`：以 **web 那份为准**（字段是超集），
   逐条与 mobile 那份比对，把 mobile 缺的字段补齐或显式标注 `// mobile 不需要`。
3. **web 侧**：`client.ts` 的路径字面量换成 `EP.*`；`types.ts` 改为 re-export 契约类型
   （**不改任何构建配置** —— `shared/` 用相对路径 `../../shared/api-contract/...` import
   即可，若 tsconfig 的 `include` 挡住，只调 `include` 一项）。
4. **mobile 侧**：`api.ts` 同样换 `EP.*`、类型改 re-export。
5. **加校验测试** `m2_server/tests/test_api_contract.py`：
   - 从 `web/src/api/client.ts` 与 `mobile/src/api.ts` 里抽出所有端点字面量，
     断言**它们都出现在**契约文件的端点集合里（拦住"随手写死一个新路径"）；
   - 断言契约里每个端点在**后端 FastAPI 路由表**里真实存在（拦住拼写错误 ——
     mobile 没有 CI，这类错现在只能等人工发现）；
   - 断言 §2.2 那批重名类型在两边都能在契约里找到同名导出。
   - **抽取实现的两个坑**（§2.1 那个假结论就是第一个坑踩出来的）：
     ① **必须先剥掉注释**，否则注释里提到的路径会被当成端点；
     ② 只认**引号内的字符串字面量**（含模板字符串），别裸扫整段文本。
6. 跑全量：`CODEBUDDY_SAFE_DELETE_ENABLED=0 .venv/Scripts/python.exe -m pytest m2_server -q`
   + `cd web && npx tsc -b`。

## 7. 测试点（验收）

- [ ] `web` 与 `mobile` 里**不再有**裸写的 `/api/...` 字面量（除契约文件本身）
- [ ] 契约里每个端点都能在后端路由表里找到
- [ ] 两边类型同名同字段（web ⊇ mobile，mobile 缺少的要有显式注释说明）
- [ ] `pytest m2_server` 全绿、`tsc -b` 通过、桌面端能正常打开
- [ ] 故意在 `mobile/src/api.ts` 里写错一个路径 → 测试**必须红**（验证守卫真的有效）

## 8. 回滚

路线 B 的回滚极简单：删掉 `shared/api-contract/` 与那条测试，把两处 import 换回内联。
**没有构建配置改动，所以不存在"回滚不干净"的情况** —— 这也是选 B 的理由之一。

## 附：issue #1（移动端 mDNS 自动发现）摸底结论 —— **已挂起，暂不做**

摸底结论留档，免得将来重查：

- 移动端 = **Expo SDK 54 + expo-router + RN 0.81.5**，`newArchEnabled: true`；
  `app.json` 只申请了 `RECORD_AUDIO`；依赖里**没有任何 mDNS 原生模块**。
- 唯一填地址处：`mobile/app/settings.tsx:86-111`（手输 `TextInput` + "测试连接" + 保存校验），
  默认值 `mobile/src/store.ts:21` = `http://192.168.1.10:8000`。**无扫码、无扫描**。
- 后端**完全没有服务发现代码**（全仓搜 `mdns|zeroconf|bonjour|avahi|SSDP|multicast` 零命中），
  `requirements*.txt` 里也没有相关库；只监听 TCP 8000（`m2_server/config.py:87-88`）。
- 后端已在 `0.0.0.0:8000` 服务前端静态资源（`m2_server/server.py:219-220` 的 `FileResponse`），
  手机浏览器可直接开 `http://<PC-IP>:8000`。

**关键岔路（将来要拍板）**：RN 里监听 mDNS **必须有原生模块 → 必须 dev build → 放弃 Expo Go**；
另一条路是**扫本网段**（并发探 `192.168.x.1-254:8000` 的 `/api/health`），
纯 `fetch`、Expo Go 里可用、**完全不用动后端**。
