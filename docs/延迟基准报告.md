# 实时变声链路延迟基准

- 档位：`balanced`（block_time = 250.0ms）
- 测量时间：2026-10-05 00:51:54

## ★ 口径声明（先读这一段）

端到端延迟是**三段之和**，不是单段：

```
端到端 = 分块缓冲 + 单块推理 + 驱动缓冲
```

| 段 | 值 | 来源 | 可靠性 |
|---|---|---|---|
| 分块缓冲 | 250.0ms | 档位配置 `block_time` 推算 | 高（配置值） |
| 单块推理 | 30.0ms | 实时日志实测（2017 个样本，取中位数） | 高（真实日志） |
| 驱动缓冲 | 20.0ms | **标称值**（未探测真实驱动） | 低（纸面参数） |

**合计 p50 = 300.0ms**，p95 = 360.0ms。

单块推理本身：p50 30.0ms / p95 90.0ms / p99 110.0ms。

## ★ 全部样本 vs 最近窗口（两个口径都要看）

上表用的是**全部 2,017 个样本**（含早期调参时的样本）。但日志尾部更贴近
「现在跑起来是什么样」，两者差得不少，所以一并列出：

| 窗口 | 推理 p50 | p95 | p99 | 端到端 p50 |
|---|---|---|---|---|
| 全量 2,017 样本 | 30ms | 90ms | 110ms | **300ms** |
| 尾部 200 样本 | 70ms | 120ms | **1210ms** | 340ms |
| 尾部 100 样本 | 80ms | 100ms | 1210ms | 350ms |

★ **p99 = 1210ms 是这里最该被注意的数字** —— 它意味着大约每 100 块里有
一次推理会卡到 1.2 秒。实时通话里这就是一次能被听出来的"卡壳"。
p50 只回答"通常多快"，**p99 才回答"会不会被打断"**，而后者更决定体验。

> 结论：拿 `300ms` 报端到端是**保守且可复现**的说法（全量口径）；
> 尾部窗口的 340–350ms 更悲观也更贴近现状，材料里写"约 300–350ms"更稳。

## 与材料里的声称对账

- 声称值：`50ms`（申报书 / README）
- 结论：**inflated** —— 实测端到端 300ms 是声称 50ms 的 6.0× —— 声称的口径几乎肯定是「单块推理耗时」而非端到端，建议在材料里改写口径

## 怎么复核

```bash
# ① 只看配置可推算的部分（零依赖）
python tools/bench_latency.py --profile balanced

# ② 带上你机器上的实时日志，得到推理段的实测值
python tools/bench_latency.py --profile balanced \
    --log <logs/<exp>/realtime_gui.log>
```

★ 换机器测出来的数**必然不同**（GPU、CPU、驱动、后台负载都会变）。
本报告的价值不在那个数字本身，而在**口径被拆开、每一段都能追溯**。
