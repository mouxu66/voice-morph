## 二、微信自动化：我们已在定义社区还没有的东西

### 2.1 时间线是理解格局的关键

**微信 PC 端直到 4.1.9（2026-04-21）才支持发送语音消息**
（[IT之家](https://www.ithome.com/0/942/316.htm)：官方交互 = 语音按钮 + 按住 Alt 说话 + **60 秒上限**）。
也就是说「自动给个人微信发语音」这个需求只存在约 **6 个月**，社区来不及沉淀。

### 2.2 四条路线的真实状态

| 路线 | 代表项目 | 对「发语音」这个具体需求 |
|---|---|---|
| **UIA + gate 热激活** | [wechatauto-replica](https://github.com/fanyuantaier/wechatauto-replica)（440★，活跃） | ✅ **唯一可行主轴**，但它**不发语音**（只有语音下载 / 语音通话 / 转发成文件） |
| | [pywechat](https://github.com/Hello-Mr-Crab/pywechat)（2015★，活跃） | ✅ **社区唯一实现发语音的**（`send_audios_to_friend`），但**无任何发送校验** |
| Hook / DLL 注入 | [WeChatFerry](https://github.com/lich0821/WeChatFerry)（6806★，**已归档**）、[ComWeChatRobot](https://github.com/ljc545w/ComWeChatRobot)（1812★，**已归档**） | ❌ **无一个支持发语音**，全部卡在 3.9.x |
| 纯视觉 / OCR | — | ⚠️ 只能兜底，不能做主轴 |
| 官方开放能力 | 企业微信 / 开放平台 / 公众号 | ❌ **不存在**给个人微信发语音的合法通道 |

**已死 / 被放弃的路线（明确写下来，别再走）**：
`cluic/wxauto`（7360★）对 4.x 已死（issues 关闭）；`wxauto4` 仅支持 **4.0.5** 且 2025-10 后无提交；
`wxautox4` 锁死 4.0.5 + 闭源 + 授权码；WeChatFerry 与 ComWeChatRobot 均已归档。

### 2.3 我们领先社区的 4 项（逐条比对源码的结论，不是自评）

| 我们的做法 | 社区做法 | 判定 |
|---|---|---|
| **单击话筒 → 持续录音 → 点浮层 ↑ 绿钮** | pywechat 用 `mouse.move` 移出按钮来"松手"（`WeChatAuto.py:3521`），再点**预先算好的原按钮中心**（`Uielements.py:1130`，不是浮层绿钮实际位置） | **我们更干净** —— 社区那个"移出按钮"其实很脆弱 |
| **`≤54s` 分段 + 事前预算护栏** | `utils.py:881-883` 超长**直接截断丢弃**后半段，用户无感知 | **我们独创**（社区完全空白） |
| **读 UIA `ChatVoiceItemView` 名称 `语音15"秒` 校验** | pywechat **零校验**；wechatauto-replica 走 DB 水位（要解密 SQLCipher） | **我们独创且更轻** |
| **绿钮 HSV 色域检测** | 三个仓库**均无** | **我们独创** |

**外加一条诊断**：`docs/犯错档案-微信.md` §2.2「发出去却是 60 秒」是全社区**唯一**的诊断。
pywechat 的「按住→播放→释放」范式在结构上就会触发它（原始 DOWN 永不解除 → 录满 60s），
**且因为它没有校验所以永远发现不了**。

### 2.4 ⚠️ 绿色区域判据：自有实测已证有偏差，但未修

**这是我们最该立刻修的一项**，且它与用户问的"区域色怪"直接对应。

`_find_green_send()` 目前的判据是「右下 560×140 内**全部**绿像素的质心」，
色域 `G>150 & R<120 & 80<B<180`，阈值只有 `>50` 像素。

**§2.19 已于 2026-09-18 离线量过 83 张真实截图**：

```
钮实际 x 范围 466–504，半径仅 19px
无虚线那族（1153 像素）：质心 = 钮心，偏差 0px        ✅
带虚线那族（1355 像素）：质心 x = 466 → 偏差 −19px  ❌
                                          ≈ 0.97 个半径
```

根因：浮层里的**波形虚线同样是绿色**，落进同一色域，把全局质心往左拉。
83 张汇总：20 张不触发 / **18 张 CENTER / 18 张 EDGE / 4 张 OUTSIDE**。

**修法当时已定**（`docs/犯错档案-微信.md:1345`）：

> 要修的方向是"取**最右侧那个够宽的连通块**的中心"，而不是全局质心。

**且测量工具已经实现了这套逻辑**：`tools/wx_green_judge_check.py` 的
`analyse()` 里有 `clusters()` + `MIN_BUTTON_W = 20` 的"最右侧够宽连通块"判据 ——
**只差接进主代码**。（2026-10-14 已落地，见 §七.①）

**限定**：这条只影响 `VM_WECHAT_UIA=0` 或热激活失效的窗口期（UIA 可用时直接给精确矩形）。
但那个窗口期真实存在 —— **微信每次重启 gate byte 就归零**，这正是降级链路存在的意义。

### 2.5 我们缺的（按优先级）

#### P0 — gate RVA 扫描三件套

`wechat_uia.py` 现状（2026-10-14 实读）：

```python
# L150 逐字节 Python 循环遍历可执行段
for i in range(0, max(0, len(raw) - 7)):
    if 0x40 <= raw[i] <= 0x4F and raw[i + 1] == 0x8D ...
```

```python
# L390-394 负结果不落盘
rva = _load_cached_rva(dll, fsize, mtime)
if rva is None:
    rva, cands = scan_gate_rva(dll)
    if rva is None:
        return False          # ← 不写缓存，3 秒节流后又重扫
```

本机 `Weixin.dll` = **196,834,352 B**（4.1.13.12）/ **201,552,944 B**（4.1.15.13）。
社区实测这个逐字节实现在 198MB DLL 上要 **6.6–9.8 秒**，numpy 向量化版 **0.56–0.77 秒（约 12×）**。

wechatauto-replica 比我们多的三件（`uia_driver.py:584-647, 656-675, 728-789`）：

1. **负结果也缓存** —— 原注释："含『扫过了，没有候选』这个负结果，不支持的版本每次都重扫最浪费"
2. **候选序列 + 写后校验 + 失败字节回滚** —— `for rva in candidates:` 写 1 → 校验 `mmui::` 真出现 → **失败恢复原值**再试下一个
3. **numpy 向量化 RIP 扫描**

（段落属性双重校验 `EXECUTE`+`WRITE` 与 xref ≤0x20000 距离过滤我们**已有**，不缺。）

#### P0 — 反风控拟人节奏层（最实的短板）

社区在 **2026-09-21 真机被要求重新登录**之后把节流层做进了库本体
（`rhythm.py`，`natural`/`calm`/`fast`/`off` 四档，默认开启）：

> 风控看到的是**动作的时间分布**而不是坐标：固定间隔、光标瞬时传送、永远命中控件正中、
> 逐字匀速键入、几秒内连发多条。

手段：`nap()` 等待加抖动（**倍率下限固定 1.0，只加长不缩短**）、`move_to()` 贝塞尔曲线、
`point()` 控件内缩随机落点、`gate()` 只管**对外可见的写动作**（读路径一律不节流）、
状态**落盘跨进程**（"一个演示脚本就是一个新进程，纯内存限速等于没有"）。

**对我们的紧迫性高于社区**：我们的方案向微信进程**写 1 字节内存**，敞口更大；
而 `_mouse_move_abs` 是**瞬时传送**、落点永远正中、批次内固定 `BATCH_GAP_S=0.8`。

#### P1 — 解除系统静音 + 设音量（静默失败盲区）

pywechat `WinSettings.py:63-75` 显式 `GetMute` / `SetMute(False)` / `SetMasterVolumeLevelScalar`，
并在 `get_default_output()` 里探测 `cable input` 是否存在。

**核实：我们的 `m2_server/audio_config.ps1` 里 `静音|mute|音量|volume` 零命中。**

后果隐蔽：**切到虚拟声卡后若系统静音 → 录出来是空语音 → 对方听不到 →
而 UIA 校验照样报成功**（语音条确实出现了）。这是 §2.15/§2.17 那类症状的**第三个成因**。

#### P1 — 物化自愈

wechatauto-replica：热写 gate → **校验 `mmui::` 真出现** → 失败**换候选 RVA 重试** →
生效过的按 DLL 身份缓存 → `_get_uia()` 30 秒节流自愈 → 唤醒后**重新锚定根控件**。
我们有 PID 缓存 + `reset_state()`，但没有"校验→换 RVA 重试"这一层。

#### P2 — 两项**不需要**做的

- **60s 整边界**（社区 `if duration != 60`）：我们的预算上限是 **54s**，结构上到不了 60s，**不适用**。
- **版本门 ≥4.1.9**：值得加，但只是文案与提前报错，不是缺陷。

### 2.6 合规姿态：维持「不 Hook、不注入、只模拟人手」

| 层 | 风险 |
|---|---|
| 协议外挂（Hook / 注入 / 私有协议） | ❌ **实锤大量封号**（itchat / 网页版 API 已封停，"一挂就封"是社区共识） |
| **UI 自动化（模拟鼠标键盘）** | ⚠️ **灰色地带** —— 影刀 RPA 社区有「批量发消息后微信自动退出」实测（行为检测）；**未找到「低频、拟人化、单条消息级」的封号判例** |
| 虚拟声卡录音频 | 普通音频设备信号，无公开判例 |

⚠️ **一处需要如实披露**：我们的方案会向微信进程**写 1 个字节内存**
（`wechat_uia.py:267` `WriteProcessMemory`）。虽然只写 1 byte 且可随时关
（`VM_WECHAT_UIA=0`），但"写内存"与"纯 UIA 只读"在法律性质上不同 ——
**建议在 README 免责声明里如实披露这一步并保留关闭开关**。

**未找到**（不编造）：微信官方封号率量化数据；《微信软件许可协议》关于自动化的明确条款原文。

## 四、实时变声：RVC 未过时，但确实落后一代

### 4.1 四约束下 RVC 仍是**唯一**成熟解

| 方案 | 延迟 | 中文 | 8GB | 需训练 | 零样本 | 许可 |
|---|---|---|---|---|---|---|
| **RVC v2（现状）** | 官方 170ms；**ASIO 90ms** | ✅ | ✅ | ✅ | ❌ | **MIT** |
| X-VC（SJTU，代码+ckpt 已开源） | 240ms | ✅ 流式 WER 中英双最佳 | 未找到 | 基座需 | ✅ | 待确认 |
| MeanVC 2 | 110ms | ✅ 内容编码器仅中文 | ✅ 47M | 需 | ✅ | 待确认 |
| Conan-fast | **37ms** | ❌ **仅英文**（LibriTTS/VCTK），WER 6.02→10.72 | ❌ 需 A100 | 需 | ✅ | MIT |
| Seed-VC | ~400ms（官方自述算法 ~300ms + 设备 ~100ms） | 间接 | 262M | 免 | ✅ | **GPL-3.0** |

**关键否定结论**：**8GB + 中文 + <50ms + 零样本 —— 四者同时满足的方案不存在。**

**RVC 确实落后的三点（正视）**：
1. **零样本维度完全空白** —— 每个音色都要训一个模型（vs X-VC/Seed-VC 的代差）
2. **抗泄漏靠检索式（top1 retrieval）而非解耦式** —— 这正是我们实测"跨音色 CAM++ 0.78、
   大移调泄漏 0.2557"的根因
3. 学术主线已迁到 **codec latent space + 一步转换**（X-VC RTF 0.014），
   RVC 的 VITS/HiFiGAN 架构属上一代

**RVC 不过时的理由**：唯一同时满足四约束（ASIO 90ms）；**MIT 许可**（对比 so-vits-svc 的
AGPL-3.0、Seed-VC 的 GPL-3.0）；38.7k star 生态最大。RVCv3 已在路线图上但
**未找到已发布的基座模型**。

### 4.2 三条已发表、可落地的修法（对症我们的实测痛点）

| 我们的痛点 | 文献对应 | 首选解法 | 落地度 |
|---|---|---|---|
| **±12 半音时音色泄漏 0.2557** | SPA-SVC 论文原文与现象**逐字对应**："in cross-domain SVC... where there is a **significant disparity in pitch**... models tend to generate audios with **hoarseness**"（[arXiv:2406.05692](https://arxiv.org/abs/2406.05692)，Interspeech 2024） | **cycle pitch shifting + SSIM loss** —— "without requiring additional data or increasing model parameters"，**纯训练策略，不加数据不加参数** | ⭐⭐ 最易落地 |
| **翻唱频谱闷（4–8kHz 掉 18.5dB）** | kNN-SVC 原文：WavLM 表征 "lacks harmonic emphasis, resulting in **dull sounds** and ringing artifacts"（[arXiv:2504.05686](https://arxiv.org/abs/2504.05686)） | **加法合成**补谐波；或 **NSF 神经源滤波**（SingNet [arXiv:2505.09325](https://arxiv.org/abs/2505.09325) 已开源 NSF-HiFiGAN 预训练） | ⭐⭐ |
| **跨音色相似度只有 0.78** | Seed-VC 三障碍：timbre leakage / insufficient timbre representation / **training-inference mismatch**（[arXiv:2411.09943](https://arxiv.org/abs/2411.09943)） | 若愿改架构：NeuCoSVC / DAFMSVC 最近邻 SSL 特征替换 | ⭐ 需改推理流程 |

**值得单独跟踪的一条**：**Zero-VC**（Interspeech 2026，[arXiv:2606.20218](https://arxiv.org/abs/2606.20218)）
是唯一**同时**解决"泄漏"与"延迟"的思路 —— 用**说话人匿名化（SA）**作扰动机制，
实现**严格因果、零前瞻**。它并指出 IB 类方法注入 F0 "**often requires buffering future frames,
creating algorithmic lookahead latency**" —— 这条与我们"要音色纯净 vs 要低延迟 vs 要韵律"
的三角冲突完全对应。

**与仓内既有调研的一致性**：`docs/调研-SVC跨音域与音色泄漏-2026-10-14.md` 的结论与本次外部调研
**完全一致**，包括"**先量训练集的 F0 分布再决定动不动 `f0_max`**"——RVC 的 1100Hz 上限约等于 C6，
对绝大多数流行翻唱**不是瓶颈**（附录 A 有音名对照表）。

### 5.1 一个"社区文档与代码不一致"的教训（对我们有用）

pywechat 作者博客说原理是「**按住发送语音的快捷键**」，但**源码里没有任何 Alt+S 发语音的路径** ——
`pyautogui.hotkey('alt','s')` 全部是**发送文本**。照着博客做会以为要用快捷键，照着源码做是点按钮。

⇒ **对我们**：`docs/犯错档案-微信.md` §2.10 已用五组对照实测证明**软件注入 Alt 完全无效**
（含决定性对照：同一时刻注入字符 `'a'` 能落进输入框 ⇒ 不是"没送到"，是微信对快捷键另走一条识别路径）。
**社区博客那条"快捷键路线"对我们已被实测否决，别再投入。**

## 六、我们做对的两件"方法论"（值得保留）

1. **延迟口径的自我更正**：`README.md` 从声称 `50ms` 改为
   **端到端 p50 ≈300ms**，并诚实标注 **p99 会到 1.2s**（`docs/延迟基准报告.md`）。
   社区大量项目只报"单块推理耗时"当端到端 —— 这个自我更正比数字本身值钱。
2. **判据标定方法论**（`docs/犯错档案-微信.md` §2.4）：
   > 判据要在"**真出问题的那一次**"上验证，不是在"顺利的那一次"上标定。

   wechatauto-replica 也犯过同类错误（把 `>102400` 当"原图未下完"判据，
   实测 **51.3% 的真原图被拒**）—— 说明这是行业通病，我们这边已避开。
