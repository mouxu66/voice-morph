## 一、项目全貌与总体评价

| 模块 | 技术栈 | 性能现状 | 评级 |
|------|--------|----------|------|
| TTS 推理 | 常驻 worker + CUDA Graph | RTF 0.35→2.3（约 5x），prompt 缓存 | 优秀 |
| 级联实时链路 | 分块状态机 + 预热 + 串行 | 端到端滞后 ≤2.5s 有指标监控 | 良好 |
| RVC 实时变声 | 子进程 + 基线参数固化 | 进程/声卡管理成熟 | 良好 |
| 离线变声 | 独立子进程 + 互斥 | 每任务冷加载权重（可优化） | 中 |
| 微调工坊 | venv312 子进程 + 硬链接 | 训练链路健壮 | 良好 |
| 效果器 | 纯 numpy/scipy | 混响/回声逐样本循环（可优化） | 中 |
| **桌宠** | Electron 多窗口 | **多客户端高频轮询叠加** | 需优化 |
| **移动端** | Expo RN | **后台轮询不感知 + 多定时器** | 需优化 |
| M1 流水线 | ffmpeg/demucs/pydub | 长音频整段入内存（可优化） | 中 |
| 工具链 | 脚本 | voice_qc 逐条串行转写（可优化） | 中 |

**总体结论**：核心 GPU 推理链路（TTS/RVC/级联）的工程优化已到生产级，是项目最强项。主要性能负债集中在**外围**：① 桌宠/前端/移动端三端对后端只读状态接口的高频、重复、无节流轮询；② `/voices` 等接口内部重复读全量 wav；③ 若干「逐样本/逐条串行」的 CPU 密集点。

## 二、已确认的性能问题（按优先级）

### 🔴 P1 — 三端对 `/api/cascade/status`、`/api/rvc/live/status` 的高频叠加轮询

这是全项目最值得关注的性能点。**同一个只读状态，被 4 个客户端同时无节流地轮询**：

| 来源 | 接口 | 频率 |
|------|------|------|
| 桌宠 `pet.html` | `cascade/status` + `rvc/live/status` | **每 1s**（`setInterval(tick,1000)`） |
| Electron 主进程 `main.cjs` | `cascadeRunning()` + `liveVoiceRunning()` | **每 2s**（`setInterval 2000`） |
| PC 前端各页 | `useCascade`/`useLive` 等 | 运行中 1s / 空闲 4~5s |
| 移动端 `index.tsx` | `cascadeStatus()` + `rvcLiveStatus()` | **每 1s**（`usePolling`） |

**后端叠加负载**：仅桌宠（1s + 2s）+ 移动端（1s）就使后端**每秒承受约 3 次 cascade/status + 3 次 rvc/live/status**，还不含前端。而这些接口内部**每次都会**：

- `cascade_status()` → `_worker_health()`（真实 HTTP GET 到 8001，2s 超时）+ `_cascade_alive()`（PowerShell 查进程）
- `rvc_live_status()` → `_model_status()`（glob 权重）+ `_asr_state()`（PowerShell 查 asr 进程）+ `_live_proc_alive()`（PowerShell 查 realtime_gui）

虽然 rvc_live/cascade 各自做了 1s/3s TTL 缓存，但**多个调用点各自独立缓存**，TTL 失效瞬间会并发起多个 PowerShell 冷启动（每个 300~800ms），且 `_worker_health` 会高频打 8001 worker。

**影响**：后端空闲 CPU 被轮询吃掉；PowerShell 进程频繁创建销毁；8001 worker 的事件循环被健康检查打断（虽推理已放线程池，仍有开销）；手机切后台/锁屏后仍在耗电打后端。

**建议**：
1. **后端加状态聚合缓存**：`/cascade/status`、`/rvc/live/status` 结果按 500ms~1s 内存缓存（`status` 类接口允许短暂陈旧），把「N 个客户端 × 每秒」收敛为「后端每秒 1~2 次真实计算」。
2. **进程探测统一 TTL 到 3s+**，并抽成单一 `process_alive_cache`，避免各模块各自起 PowerShell。
3. **桌宠改推模式**：Electron 主进程（main.cjs）已在轮询，可由主进程**只轮询一次**，再通过 IPC `pet:guide`/`pet:status` 推给桌宠窗口，去掉 pet.html 自己的 1s fetch。
4. 桌宠状态轮询降为 1.5~2s，空闲态降为 5s（动画本身 3s 一轮，1s 轮询对视觉收益不大）。

### 🔴 P2 — `/api/voices` 内部重复读全量 wav，且被所有端轮询

- `server.py::list_voices()` 对每个音色 `AudioSegment.from_wav(str(ref))` 读整个 `reference.wav` 只为算 `duration_s`（`server.py:270`）。
- 该接口被 **PC 前端 App 顶层 5s**、**级联页 1~4s**、**移动端 30s**、**桌宠面板 `loadVoices()`（每次悬停浮现都拉）** 同时调用。
- `list_voices` 还遍历 `RVC_ROOT/logs` 所有实验做 `exp_snapshot`（每目录 glob 计数），`list_clips()` 对每个切片 `AudioSegment.from_wav` 只为 `duration_s` + `max_dBFS`。

**建议**：`soundfile.info()` 只读文件头取时长；`/voices`、`/clips`、`/rvc/voices` 结果加目录 mtime 失效的内存缓存；`max_dBFS` 旁路缓存到 meta 文件或惰性计算。

### 🟠 P3 — 移动端 `usePolling` 不感知 AppState

`mobile/src/ui.tsx::usePolling` 用 `setTimeout` 串行（不会重叠，这点是对的），但**完全不监听前后台**——注释明写「页面失焦自动继续（简单实现）」。手机锁屏/切后台后，`index.tsx` 的 4 个轮询（1s/3s/5s/30s）仍在跑，持续耗电、占 WiFi、打后端。

**建议**：`usePolling` 内接入 `AppState.addEventListener('change')`，后台时暂停、回前台立即刷新一次；或至少把 1s 轮询在 `AppState !== 'active'` 时降为 10s。

### 🟠 P4 — 桌宠精灵图动画 1s 轮询收益低、成本高

`pet.html` 的精灵图 CSS steps 动画一轮是 3s（`SPRITE_ANIM.idle.dur=3.0`），但状态轮询是 1s；且 `render()` 每次 `setSprite` 都改 `backgroundImage`/`animation`，频繁重建 CSS 动画。状态 1s 轮询对「说话→字幕」的及时性有帮助，但对纯待机态属浪费。

**建议**：区分「运行中 1s / 空闲 5s」两档；状态无变化时（`lastKey` 相同）不重设 sprite（已有 `lastKey` 判断，可再补 `lastText` 不变时跳过 DOM 写）。

### 🟡 P5 — `history.py` 每次登记全量读+重写

`register()` 追加后 `_trim()` → `_read_all()`（读全文件）+ 全量重写；`delete()` 同样。2000 条时每次 TTS 完成触发 O(n) 写放大。

**建议**：惰性裁剪（超阈值才裁）或改 SQLite。

### 🟡 P6 — M1 流水线 `step3_slice` 整段音频入内存

`pipeline.py::step3_slice` 用 `AudioSegment.from_wav` 读**整段** 44.1k 音轨到内存再 normalize/切片。长视频（如 1 小时直播）整段 PCM 可达数百 MB。

**建议**：分块流式读取，或用 `soundfile` 按需切片；`normalize` 可先探峰值再处理。

### 🟡 P7 — `tools/voice_qc.py` 数据集预检逐条串行转写

`run_dataset` 对 N 条切片**串行**调 worker `/transcribe`，每条数秒，100 条就是几分钟，且无断点续跑。

**建议**：并发（线程池 + worker GPU 串行锁会排队，但转写可交错）；或加 `--limit` 抽样；转写结果缓存到旁路文件避免重复质检时重跑。

### 🟡 P8 — 效果器 `fx_reverb`/`fx_echo` 逐样本 Python 循环

`effects.py` 的 `fx_reverb`（4 comb + 2 allpass）和 `fx_echo` 是 `for i in range(len(x))` 逐样本循环，长音频（整段有声书）会慢。

**建议**：改用 `scipy.signal.lfilter`（comb = 延迟反馈可用 lfilter 系数表达）或 `np.convolve` 向量化。

## 三、各模块排查明细

### 1. TTS 主链路（qwen3_tts.py / qwen3_tts_service.py / fast_tts.py）— 优秀

已做对：常驻 worker 懒启动、僵尸 worker 清理、`_PROMPT_CACHE` 缓存、CUDA Graph 加速（约 5x）且优雅回退、GPU 串行锁、端点放线程池、超长参考自动截断（10s 上限防 WDDM 慢路径）。

可优化：
- `_PROMPT_CACHE` 无上限/LRU，频繁换音色会累积 prompt 对象。建议 `OrderedDict` LRU（上限 8~16）。
- `fast_tts` 图 LRU `max_graphs=4` 与 prompt 缓存应协调，减少换音色时的图重建（`graph_rebuilds` 有统计可监控）。

### 2. 级联链路（cascade.py / cascade_stream.py）— 良好

已做对：分块状态机、启动预热 ASR+TTS、fast 转写、交叉淡化、分阶段耗时统计、worker 忙/死区分。

可优化：
- `cascade_status()` 的 `_worker_health()` 是每轮询一次的真实 HTTP 探测（见 P1），应并入状态缓存。
- 临时文件 `cascade_tmp_chunk.wav` 每块覆写，当前串行无冲突，未来并行需注意。

### 3. RVC 实时（rvc_live.py）— 良好

已做对：基线参数固化、按命令行查杀进程、声卡三层还原、设备名精确枚举。

可优化：`_train_progress` 每次轮询全文读日志（`read_text().splitlines()`），日志越长越慢；`_maybe_run_qc` 每次轮询都做 mtime 比较，可移到训练完成事件一次性触发。

### 4. 离线变声（offline_vc.py / offline_vc_infer.py）— 中

已做对：独立子进程隔离、互斥防抢 GPU、ffmpeg 预处理、手动填充 VC 绕开 Gradio。

可优化：每任务冷启动 `torch.load` 整份权重 + `load_hubert`，频繁使用时可考虑进程常驻化（权衡显存）。

### 5. 微调工坊（finetune.py）— 良好

已做对：子进程训练、日志 tee 落盘、硬链接省磁盘。

可优化：`ft_upload` 整段 `read()` 进内存；`_find_train_pid` 每 status 轮询无缓存起 PowerShell（应加 TTL，rvc_live 已有范例）。

### 6. 桌宠（Electron）— 需优化（详见 P1/P4）

已做对：桌宠窗口透明/穿透、置顶提示横幅不抢焦点、显隐策略、拖动记忆、全局热键、微信发语音流程的引导编排都考虑周到；`pet.html` 渲染层逻辑清晰、状态机完整。

核心问题：**双层轮询**——Electron 主进程 `main.cjs` 每 2s 轮询一次（用于显隐判断），`pet.html` 渲染层又每 1s 轮询一次（用于动画/字幕），二者没有共享状态，属于明显的重复请求。

### 7. 移动端（Expo RN）— 需优化（详见 P3）

已做对：API 层带超时（AbortController）、鉴权头/查询参数兼容、`mediaUrl` 处理、音频播放/分享组件封装、Zustand 持久化。

核心问题：`usePolling` 不感知 AppState；`index.tsx` 挂了 4 个独立轮询定时器；移动端也命中 P2 的 `/voices` 全量读文件。

### 8. M1 流水线（pipeline.py）— 中

已做对：取消机制（`_run_or_cancel` 轮询 cancel_event）、demucs 分离、响度归一化、静音检测切分。

可优化：`step3_slice` 整段入内存（P6）；`main()` 里 `step3_slice(vocal, v.stem[:12])` 仍用旧 12 字符前缀，会复现 server.py 注释里修过的 `video_260828_*` 前缀碰撞（虽非性能问题，但属隐患，建议统一用 `_clip_prefix`）。

### 9. 工具链（tools/）— 中

- `voice_qc.py`：逐条串行转写（P7），变声验收四指标（时长比/f0/ASR重合/声纹）串行，单音色质检可达数分钟。
- `cascade_acceptance.py`：`check_latency` 每秒轮询属验收用途，可接受。
- `doctor.py`：体检脚本一次性，无性能顾虑。

## 五、结论

项目体量确实不小，性能画像呈现「**内核强、外围散**」的特点：

- **内核（GPU 推理链路）**：常驻 worker、CUDA Graph（RTF 提升约 5x）、GPU 串行锁、进程/声卡生命周期管理，均已做到生产级，无需大改。
- **外围（多端轮询层）**：桌宠（1s）+ Electron 主进程（2s）+ PC 前端 + 移动端（1s）四端对同一批只读状态接口的**高频、无节流、无共享**轮询，是全项目当前最大的性能负债，也是「一改就见效」的优化点。
- **中间地带**：`/voices` 全量读文件、逐样本 DSP、逐条串行质检等，属渐进打磨项。

**优先落地前三项**（状态接口缓存、进程探测 TTL 统一、桌宠单点轮询），可在不牺牲任何功能的前提下，把后端空闲 CPU 和 PowerShell 进程创建开销降一个量级，同时显著改善移动端续航。
